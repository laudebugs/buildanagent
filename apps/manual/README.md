# `@buildanagent/manual`: the textbook at manual.buildanagent.fyi

The book is a static Astro site with Pagefind search, built from the [book plan](../../docs/plans/build-book.md). This README first covers writing a chapter. The build computes every chapter, figure, listing and table number and checks every citation, glossary tag and analogy, so **a chapter is ready when `check:book` passes, because that check runs the same rules as the build**. The README then covers the book's look: where the design tokens come from, where each token may be used, how the fonts are made, and which components exist. Every colour, font and size on a page comes from one file, [`docs/design/book-tokens.json`](../../docs/design/book-tokens.json), so a design change starts there and never in the CSS.

## The outline places the chapter and gives it its number

Each chapter lives at `src/content/chapters/<slug>.md`, and its page is `/<slug>/`. Its slug must appear in [`src/outline.ts`](src/outline.ts), which lists the two parts and their chapters in reading order. The chapter's number is its position there, counted across both parts, so moving a chapter in the outline renumbers it, its figures, listings and tables, and every reference to them. The contents page lists every chapter in the outline, as plain text until its file exists. Each chapter also needs its fact-check log at `fact-checks/<slug>.md`, and `check:book` fails without it ([`fact-checks/README.md`](fact-checks/README.md)).

The outline also gives each chapter its opening type: `scenario`, `incident`, `question`, `fact`, `code` or `analogy`. `check:book` fails when two consecutive chapters share an opening type, or when one type opens more than a quarter of the chapters, rounded up.

## The front matter is strict, and the chapter ends with exercises

The front matter takes exactly these six keys, and any other key, a misspelt one included, fails the check:

```yaml
---
title: "Use the least autonomy that works: a call, a workflow, then a loop"
summary: One or two sentences for the page's description.
opening: scenario
sources: [anthropic-building-effective-agents]
glossary: [agent, agent-loop, workflow]
switchTo: [B11]
---
```

- `opening` must be the type the outline plans for this chapter. To change it, change the outline, which reruns the rotation check.
- `sources` lists the register ids the chapter relies on, in the order its source list shows them; it needs at least one.
- `glossary` lists the glossary ids the chapter links, once in each paragraph that uses them; it may be empty.
- `switchTo` lists the todos whose code will join the chapter's `verify/` listings as a first tab, while the `verify/` listings stay (BK8); it may be empty.

The chapter's last `##` section is `## Exercises`, and it holds a list and nothing else: `check:book` fails on a paragraph or a box after the list, since either would render inside the exercises. The layout adds the chapter's sources after it, so the chapter has no sources section of its own.

## The registers keep one entry per line, so branches that add entries merge cleanly

The three registers, `src/data/sources.json`, `src/data/glossary.json` and `src/content/analogies.json`, are JSON arrays with one entry per line, sorted by id. The sort compares UTF-16 code units, so the order never depends on a machine's locale. Git merges by line, so two branches that each add an entry merge cleanly. They conflict only when both add at the same place in the order. An entry that sorts last also edits the old last line's comma, so it conflicts with a neighbor too. Biome skips these three files, because it would put each entry back on many lines.

To add an entry, write it as one line anywhere in the array, then run `pnpm --filter @buildanagent/manual registers:format`, which sorts the array and leaves every other entry as it is. [`test/registers.test.ts`](test/registers.test.ts) fails on a repeated id and on a register that differs from the canonical layout, and its message names the command. If two branches add entries that sort next to each other, or at the end, git reports a conflict: keep both lines, then run `registers:format`.

## Citations point at the source register

Cite a source with `[@id]`, or several with `[@a; @b]`. The id must be in [`src/data/sources.json`](src/data/sources.json) and in the chapter's `sources`. The page shows each citation as the source's position in `sources`, such as `[1]`, linked to `/sources/#<id>`.

Each register entry names the fact-check log that verified it:

```json
{"id":"anthropic-building-effective-agents","title":"Building effective agents","publisher":"Anthropic","url":"https://www.anthropic.com/engineering/building-effective-agents","kind":"post","asOf":"November 2026","verifiedIn":"docs/research/agent/fact-check.md"}
```

`kind` is `docs`, `repo`, `paper`, `spec` or `post`, and an optional `version` holds a tag or commit. `verifiedIn` is a path from the repository root, and it must name a fact-check log. Four kinds count: a `fact-check*.md` file under `docs/research/` or in `docs/plans/reviews/`, a `docs/reference/<sdk>/fact-check.md`, and a chapter's own log in `apps/manual/fact-checks/`. That log must contain the URL, whether as an inline link, a bare URL or a reference-style definition. To cite a new source, first add its row to the chapter's fact-check log, `apps/manual/fact-checks/<slug>.md`, then add the entry with that log as `verifiedIn`. Set `"secondary": true` when the check rests on a search summary or a secondary write-up; the sources page then says so.

## How to cite a research paper

Name a research paper with `[[paper:id]]`, never as bare text. The rule covers papers and named research systems, such as ReAct or SkillCFI, but not specs, standards or vendor docs. Its register entry has `"kind":"paper"` and three more fields:

- `short`, the name the page shows, such as `"SkillCFI"`;
- `blurb`, one clause that says who wrote the paper, where and when it appeared, and what it does or found, such as `"a November 2026 arXiv paper by Ruan et al. on control-flow integrity for agent skills"`;
- `aliases`, optional, for other spellings, such as `["τ-bench"]`.

The blurb shows in parentheses after the name, so it has no parentheses of its own and no closing full stop, except the one in a closing "et al.". The `url` must be the paper's own page: its arXiv abstract, its DOI, or its page at a venue that `src/book/papers.ts` lists.

A chapter's first `[[paper:id]]` of a paper shows the name as a link to `/sources/#<id>`, then the blurb. Every later one shows the linked name alone. So does one in a heading, a box title or a tab's caption, and it never counts as the first mention: the blurb would end up inside the heading's link and the contents. Name the paper in the text as well.

When the sentence already says what the paper is and who wrote it, write the first mention as `[[paper:id described]]`, and no blurb is added. `check:book` lists every `described` mention, so a reviewer can read each sentence.

A `[@id]` citation of a paper still cites it and counts as a linked mention, but it cannot be the chapter's first mention, because a number says nothing about the paper. As for any citation, the id must be in the chapter's `sources`.

`check:book` fails when a chapter:

- writes a paper's `short` name or an alias as bare text outside code and links, raw HTML's text included (the match is case-sensitive and whole-word). If the word means something else, reword it;
- first mentions a paper with a `[@id]` citation, or marks a later mention `described`;
- writes `[[paper:id]]` for an id that is not a paper, for a paper still pending, or for a paper missing from its `sources`;
- writes `[[paper:id]]` inside a link's text, writes it with one bracket too few, such as `[paper:id]`, or names a paper only in a heading.

A footnote renders after the chapter's text, so a mention in one counts after every mention in the text. The front matter's `summary` is not checked, so keep paper names out of it.

It also fails on a paper entry without `short`, `blurb` or a paper-page `url`, unless the paper is pending, and on an entry of another kind that links an arXiv abstract or a DOI. [`src/data/papers-pending.json`](src/data/papers-pending.json) lists the papers whose `short` and `blurb` are not written yet. They are exempt until the content todos write and fact-check each blurb, add the paper's names and empty the list. An id on the list must be a paper with no `short` or `blurb`, so the list can only shrink. `check:book` prints how many remain.

The sources page shows each paper's name and blurb, and under "Cited in" links each chapter that mentions the paper to its first `[[paper:id]]` there, or to the top of the chapter when only a `[@id]` citation names it. `audit:papers` reports every paper's mentions in each chapter, which first mentions lack a description, and capitalised names near "paper", "arXiv" or "et al." that no register paper uses.

## References name an id, and the build writes the number

Mark a numbered block with a container directive, its caption in brackets and its id after `#`:

```markdown
:::figure[The loop runs until a stop condition holds]{#tool-call-round-trip}
::svg{alt="What the drawing shows"}
:::

:::table[How each SDK stops the loop]{#stop-defaults}
| SDK | Default cap |
| --- | --- |
:::

:::listing[One model call]{#one-call}
…a fenced code block…
:::
```

Ids are kebab-case and unique across the book for each kind. A table must hold a table and a `:::listing` a code block, and every block needs a caption. A table wider than its column, as on a narrow phone, scrolls sideways inside its own region. The region takes keyboard focus, shows the accent focus ring and takes its name from the table's caption, as a listing's code does. A 2px rule in the muted text colour sets the header apart, and it reaches 3:1 on the page in both themes. Each body row has a 1px rule in the divider colour, which is decorative only, so the cell padding and the lines together separate the rows. A column aligned in the Markdown keeps its alignment. Refer to a block with `[[fig:tool-call-round-trip]]`, `[[tbl:stop-defaults]]` or `[[lst:one-call]]`, and to a chapter with `[[ch:tools]]`. The build replaces each reference with a numbered link such as "Figure 3.2"; a reference to a planned chapter shows its number without a link. An unknown id or a malformed reference fails with the file and line. Inside code, both reference and citation syntax stay as written. A `:::listing` with its code in the chapter suits a snippet that runs nowhere, such as a JSON response. It shows in the same panel as a file listing, highlighted by its fence's language and numbered from 1, but with no path, line range or pin. A fence with no known language shows as plain text. Code a reader should trust comes from a real file through `::listing`, described next. A figure holds its generated drawing, as [the figures section](#a-figure-is-a-script-that-draws-an-svg-and-the-build-inlines-it) describes.

## A listing shows a region of a real file

A listing shows only code that CI type-checks and runs, because the build cuts it from a real file instead of taking it from the chapter. The chapter names the file and a region in it with a leaf directive, written with two colons:

```markdown
::listing[One model call]{#one-call file="verify/vercel-ai-sdk/examples/01-generate-text.ts" region="call"}
```

The file marks the region with comments on their own lines, which change nothing when the example runs:

```ts
// #region call
const { model, requests } = scripted(["Hello from the mock."]);
const result = await generateText({ model, instructions: "You are terse.", prompt: "Say hello." });
// #endregion
```

The build cuts the lines between the markers, drops any markers of regions nested inside, removes the indentation the lines share and highlights them with Shiki. The caption line shows the number, such as "Listing 1.1", then the caption you wrote, the file's path, the line range and the pinned version of the harness's main package, such as `ai@7.0.173` as of November 2026. Each code line also shows its own number in the file. Without `region`, the listing shows the whole file without its markers. References use the same id as any listing, `[[lst:one-call]]`.

Region names are kebab-case and unique in their file, and an `// #endregion` may repeat its name (`// #endregion call`). The build finds markers line by line without parsing the code, so a line inside a template literal or a block comment that starts with `// #region` also counts as a marker.

The pin comes from the harness's own `package.json`. [`src/data/harnesses.json`](src/data/harnesses.json) names each harness's main package, such as `ai` for `verify/vercel-ai-sdk`. The weekly SDK-update job rewrites those pins, so each caption follows the harness's current pin; prose that names a version still says "as of <month year>".

### A listing from our own packages shows the workspace version

A harness can also be one of our own packages. The table lists `packages/sdk`, `packages/gateway` and `packages/harness`, each with its own name (`@buildanagent/sdk`, `@buildanagent/gateway`, `@buildanagent/harness`) as its main package. `@buildanagent/harness` is private, so its caption shows the version it declares, `0.0.0`. Their listings come from `examples/`, where the numbered files, such as `packages/sdk/examples/01-one-call.ts` or `packages/gateway/examples/01-text-stream.ts`, are the book's examples on our packages:

```markdown
::listing[Our SDK]{#one-call-ours file="packages/sdk/examples/01-one-call.ts" region="call" replay}
```

Because the package is its own main package, the caption shows the version its `package.json` declares, such as `@buildanagent/sdk@0.1.0-alpha.19` as of November 2026, and that version must be exact too. Each package's `test` runs its numbered examples offline, each in its own Node process, and records each transcript in the package's `results/transcripts/`. One shared runner does this, [`scripts/transcripts/book-examples.ts`](../../scripts/transcripts/book-examples.ts), and each package's `test/book-examples.test.ts` ([the SDK's](../../packages/sdk/test/book-examples.test.ts), [the gateway's](../../packages/gateway/test/book-examples.test.ts), [the harness's](../../packages/harness/test/book-examples.test.ts)) calls it. A transcript records the package as `@buildanagent/<package>@workspace`, such as `@buildanagent/sdk@workspace`, rather than its version, because the run uses the package's source as it stands. The release job's version commit may change only the version, so a transcript that named the number would go stale at every release. A replay from our package therefore needs a transcript recorded at `workspace`. An example gets a line on each model event only when it builds its model with the `scripted()` helper in its package's `examples/lib/check.ts`, which lends each run the line that started it. The gateway's helper plays a scripted Anthropic Messages stream through the gateway's real adapter over `mockTransport()`, and records only the usage classes the script set. The SDK's `packages/sdk/examples/04-scripted-model.ts` builds its model by hand, because that is what it shows, so its transcript has no lines and its listing takes no `replay`. To add one of our examples, mark its region, run `pnpm --filter @buildanagent/<package> test` and commit the transcript it writes.

The book loads every listing before it renders a page, so `check:book` and the build fail on the same problems, each named with the chapter's file and the directive's line. A listing fails when:

- its file is missing, its path is not a plain path from the repository root (it is absolute, or holds `./`, `..` or `//`), or the file resolves through a symbolic link to a place outside the repository;
- the file is not TypeScript (`.ts`, `.tsx`, `.mts` or `.cts`), or no workspace package's `typecheck` covers it, as the next paragraph explains;
- the file sits in no harness that `harnesses.json` lists, or the harness's `package.json` lacks the main package or pins it as a range instead of an exact version;
- the region is missing, empty or malformed (an unnamed or repeated `#region`, an `#endregion` without its `#region` or naming another one, a `#region` never closed), and such a message also names the file's own line;
- the directive lacks a caption or `file`, or takes an attribute other than `id`, `file`, `region` and `replay`, the last of which takes no value.

A file counts as covered when `pnpm typecheck` would check it. Its nearest `package.json` must match a glob in `pnpm-workspace.yaml` that no `!` glob cancels, and one `tsc -p <config>` in that package's `typecheck` script must hold the file in its program. To decide, the check runs the manual's own `tsc`, from its exact `typescript` devDependency, as `tsc -p <config> --listFilesOnly`. TypeScript therefore applies `extends`, `files`, `include` and `exclude` itself, and a file that an included example imports also counts.

Five of these rules are our choices, not BK9's: an exact pin, TypeScript files only, paths from the repository root only, a file inside a harness that `harnesses.json` lists, and no attribute but `id`, `file`, `region` and `replay`, which catches a misspelt `region`. The harness rule covers our own packages too: a file in a package the table does not list, such as `packages/agent-safety/src/index.ts`, fails as "in no harness".

To add a listing, mark the region in the example, run that harness's `pnpm test` to confirm its results do not change, then write the directive and run `check:book`. Renaming or deleting a region breaks every chapter that lists it, and `check:book` names each one. When a chapter's `switchTo` todos are all done, `book:switch-report` says the chapter is ready for tabs on our own packages (BK8).

## Notes, SDK tabs and replays make a listing interactive

A file listing can carry three kinds of interaction, BK9's tiers, and each one reads in full with JavaScript turned off. All three build on the same `::listing`, so `check:book` and the build check them as they check the listing, and each problem names the chapter's file and line.

### Notes explain marked lines

An example marks a line by ending it with a `// book:note <id>` comment. The chapter then writes the listing as a container and gives one note for each marker:

```markdown
:::listing[The loop runs until the model answers]{#tool-loop file="verify/vercel-ai-sdk/examples/02-tool-loop.ts" region="loop"}
::note[The model's first answer asks for the tool.]{#first-call}
::note[The loop stops when the model answers with text.]{#stop}
:::
```

The build takes each marker off its line, highlights the line and puts a numbered marker at its end. The marker links to its note, and the notes form a numbered list under the code, in the order of their markers in the file. A note is Markdown, so citations, glossary terms and references in it work as in a paragraph. Because the marker sits on the line itself, a note follows its line when the file changes around it.

A listing fails when a note names an id that no marker in its lines carries, when a marker in its lines has no note, when a note repeats an id or lacks text, and when the container holds anything but notes. A marker fails, with the file's own line, when its id is not kebab-case, when its id appears twice in the file, or when it stands on a line of its own instead of ending a line of code. One rule is our choice: a listing that gives no notes shows its marked lines plainly, so one chapter can annotate a region that another lists bare. Like region markers, a marker is found by its text, so `// book:note` inside a string also counts.

### Tabs show one concept in several SDKs

A `:::tabs` block holds two or more file listings, usually from different harnesses:

```markdown
:::tabs
::listing[AI SDK]{#approval-ai file="verify/vercel-ai-sdk/examples/03-tool-approval.ts" region="approval-response"}
::listing[OpenAI Agents SDK]{#approval-openai file="verify/openai-agents-sdk/examples/05-approval-resume.ts" region="approve-resume"}
:::
```

Each listing keeps its own number, path and pin, and its caption names its tab. Without JavaScript the listings follow one another, each under a heading made from its caption, one level below the heading the block follows. Because the heading shows the caption, the caption line below it shows only the number, path, lines and pin. The chapter's "On this page" list leaves these headings out. With JavaScript, `scripts/tabs.ts` turns those headings into a tab list that the arrow keys, Home and End move through. The block fails when it holds anything but file listings, holds fewer than two, or has a caption of its own.

### A replay steps through a recorded run

Add `replay` to a file listing, and the page shows the recorded run of its example beside the code:

```markdown
::listing[One model call]{#one-call file="verify/vercel-ai-sdk/examples/01-generate-text.ts" region="call" replay}
```

The run comes from `<harness>/results/transcripts/<example>.json`, such as `verify/vercel-ai-sdk/results/transcripts/01-generate-text.json`, which the harness's `pnpm test` writes and CI's results-drift check keeps current, so a replay cannot drift from its code. Without JavaScript the replay lists every event of the run: the messages the example sent, the model's answers, each tool call and result, and each `check()` with its outcome. Under an answer's text, the replay also shows the model id and the token usage the mock reported, such as "Model id: claude-sonnet-5-5" and "Usage: 1,000 uncached input, 1,500 cache read, 500 cache write, 200 output tokens", but only where the example's script set them. A default that no script chose, such as the AI SDK helper's 10 input and 5 output tokens or ai/test's `mock-model-id`, stays out of the transcript, and so does any token class the mock did not report ([`events.ts`](../../scripts/transcripts/events.ts)). With JavaScript, `scripts/steps.ts` reveals one event at a time, with back, next, restart and play, and marks the listing line that each event came from. Each event also says where it came from, with or without JavaScript: "line 6" for a line the listing shows, "line 42, outside this listing" for one it leaves out, and "no source line" when the transcript names none. Neither script makes a network request, and `test/page-scripts.test.ts` checks that in happy-dom.

A listing and its replay share a row whenever the pair is at least 52rem wide, a container query on the pair itself. On a chapter page the pair, like every listing, figure, table and tab block, takes the whole article column, wider than the prose; so does a box. The code takes three fifths of the row and the run the rest, with their tops aligned. The run is as tall as the listing card, notes included, and its events scroll inside it under a fixed header and controls. Its CSS size containment keeps a long run from stretching the row, so no script measures anything. Beside a short listing the run keeps a minimum height of 18rem, a choice of ours, and the listing card stretches to match. In a narrower column, as on a phone or a portrait tablet, the run sits under its listing at a fixed height and scrolls the same way. That height is 24rem or 70% of the small viewport height, whichever is less, both choices of ours. Because the height is fixed, not a maximum, revealing an event never moves the page below the run. Stepping scrolls the current event into view inside the run, never the page, and does it instantly when the reader prefers reduced motion. The scrolling events take keyboard focus and are named "Events of" the run's title, so a keyboard reader can scroll them with the arrow keys and Tab out again. The transcript's path wraps only after a slash, never at a hyphen inside a name. Printed, the run shows every event under its listing, with no scrolling and no controls.

The replay shows a request's new messages only. When a request resends messages the replay already showed, as when a handoff gives the conversation to another agent, they fold into one "History" event that counts them. A part that the format has no shape for, such as Pi's system prompt sections or the text LangChain's fake model makes up, shows under a name a reader can follow. A body longer than 600 characters stops there and says how many more it holds, a limit that is our choice.

A replay fails when the transcript is missing or malformed, when it records another file, and when it was recorded at a pin other than the harness's current one. The pin check covers both the harness's main package and the package its recorder attaches to, which the transcript names as `mock`, and rerunning the harness's `pnpm test` fixes a stale pin. Eight `verify/` harnesses record transcripts: `vercel-ai-sdk`, `pi`, `openai-agents-sdk`, `langchain`, `google-adk`, `cloudflare-agents`, `claude-agent-sdk` and `copilot-sdk`. So do three of our packages. `packages/sdk`'s recorder attaches to its own `ScriptedModel`, and `packages/gateway`'s wraps the scripted model's adapter. `packages/harness` uses the SDK's recorder, attached to `ScriptedModel` because its turns run on it, and records its own package as the mock. The harness's `examples/lib/check.ts` also holds `memoryLock()`, a session lock in memory: the harness ships only a file-backed lock, and a book example writes no file. The models of `claude-agent-sdk` and `copilot-sdk` answer over HTTP, so their recorder sits in the mock server. It reports the conversation without what the Claude Code program and the Copilot runtime add around it: system reminders, the program's environment note and the runtime's clock reading. An example that calls no model, such as `cloudflare-agents/examples/01-state.ts`, has no transcript. The transcript format lives in [`scripts/transcripts/events.ts`](../../scripts/transcripts/events.ts), with its recorder and writer beside it.

## A box sets a passage apart from the chapter's argument

A box holds material that a reader can skip without losing the thread, such as Chapter 1's account of how the examples run without a key. Write it as a `:::box` container with a title and an id:

```markdown
:::box[How these examples run without a key]{#how-these-examples-run-without-a-key top}
Every listing in this book runs against a mock model, …

::listing[The scripted mock behind this chapter's AI SDK listings]{#scripted-mock file="verify/vercel-ai-sdk/examples/lib/check.ts" region="scripted"}
:::
```

The page renders the box as an `<aside>` whose `aria-labelledby` names its title, and the title is a heading that carries the box's id, so a link to `#how-these-examples-run-without-a-key` lands on the title. The `top` flag sets the title's level:

- A box marked `top`, written `:::box[Title]{#id top}`, is a top-level box: its title is a level-2 heading, so the box stands beside the chapter's sections and the chapter's "On this page" list shows it. `top` is a bare flag with no value, and the box must sit directly in the chapter, not inside another block. Chapter 1's box is marked `top`.
- A box without `top` sits inside its section, wherever it falls: its title is a heading one level below the heading the box follows, as a tab heading is. "On this page" shows only level-2 headings, so it leaves the box out. A box that ends a section, or follows another box, is still one level down.

Position never decides the level; only `top` does. Two examples:

```md
## A section

Text.

:::box[A side note]{#a-side-note}
Skippable material, an h3 under the section.
:::

:::box[How these examples run]{#how-these-examples-run top}
Skippable material at the chapter's top level, an h2 listed in "On this page".
:::
```

To move a box into its section, drop `top`; to lift it to the top level, add it.

Inside, a box takes any Markdown: paragraphs, citations, glossary terms, analogies, references and file listings, which are numbered and checked like any other. A `:::listing` container with notes fits inside too, once the box's fence has four colons, `::::box`. So does a `:::tabs` block inside a `::::box`, and its tab headings sit one level below the box's title. The box draws a thin card border in the rule colour, which is decorative. A 4px left rule in the muted text colour marks its boundary, at 7.22:1 on the light page and 6.94:1 on the dark one, above WCAG 1.4.11's 3:1. A listing inside keeps its own panel in both themes. In print the border takes the muted text colour, and the title stays on the same page as the text after it. The box needs no script and writes no inline style.

A box fails when its id is missing or not kebab-case, when it takes any attribute but its id and `top`, when `top` has a value (`top=x`), when a `top` box sits inside another block, when its title is missing or blank, when it holds nothing, and when it holds a heading or another box. It also fails when its id repeats another id on the page, such as `#exercises` (the slug of `## Exercises`) or `#lst-greet` (the id of Listing `greet`). The check covers every id on the page, from heading slugs to ids in a listing's raw HTML, so two boxes cannot share an id either. These rules are our choices. The heading rule keeps the title as the one heading a box adds to the page's outline.

## The live run compares the listed examples with real APIs, only when the owner starts it

Every listing runs against a mock model, and CI never holds a provider key. Once in a while the owner checks that the mocks still behave like the real APIs, with a workflow that only they can start and approve ([book plan BK18](../../docs/plans/build-book.md#bk18-an-occasional-live-run-compares-real-flows-with-the-mock-transcripts-accepted)). `.github/workflows/live-run.yml` runs the examples in [`src/data/live-examples.json`](src/data/live-examples.json) against the real APIs and compares each run's flow with the example's mock transcript. A pull request then records the date in [`src/data/live-comparison.json`](src/data/live-comparison.json), which pages show beside the listings the live run covers.

### What a page says

A chapter page with a file listing opens with one of three lines. A listed file counts as compared once the live list names it and a live run has committed its transcript on at least one provider, in `<harness>/results/live/<provider>/<example>.json`; a file the list names whose transcript no run has committed does not count yet. When one of the page's listings shows a compared file, the line is "Listings on this page are verified against mock models; last compared with live APIs on 1 December 2026", or ends "not yet compared with live APIs" before the first complete run. When none of the page's files is compared, the line is "Listings on this page are verified against mock models only", because no comparison covers them. A listing of a file that is not compared also carries "Verified against mock models only" in its caption. Every `google-adk` listing carries that caption, because the harness's pinned TypeScript release reaches only Gemini. Adding a provider package or a Gemini key is a separate change the owner approves. The build reads both files and looks for each entry's live transcript when it loads the book. It fails on a date that is not `YYYY-MM-DD` or an entry without its provider, and it clears its content cache when either file changes or a live transcript appears or goes.

### What the owner sets up once

The workflow relies on these exact names and settings:

1. **The `live-run` environment**, with the owner as its required reviewer, **Allow administrators to bypass** turned off, and **Protected branches only** as its deployment branches. That setting admits every protected branch, so the run is safe only while `main` is the one protected branch. Before it receives its key, each provider's job reads the environment and the protected branches through GitHub's API. It stops when the owner's review is no longer required, when administrators can bypass it, or when a branch other than `main` is protected. A custom deployment policy that names only `main` would admit `main` alone, whatever else is protected. Switching to one also means changing the pre-run check, which expects "Protected branches only".
2. **Two environment secrets in `live-run`**: `ANTHROPIC_API_KEY` and `OPENAI_API_KEY`. No other provider key appears in the workflow, no other workflow names either one, and each provider's job names only its own. GitHub releases them only after the owner approves the jobs. An Anthropic key that belongs to no workspace also needs an `anthropic-workspace-id` header, which the live run doesn't send, so use a key scoped to one workspace.
3. **A monthly spend limit at each provider**, the hard ceiling on what a run can cost: on the Anthropic workspace the key belongs to (Console → Spend limits → Workspace limits) and on the OpenAI project its key belongs to (the project's hard spend limit, which stops its traffic once reached). The run's own cost guard catches our mistakes, not malicious package code, as the next section explains.
4. **The pull request token**, `SDK_UPDATES_TOKEN` or else `RELEASE_PR_TOKEN`, the repository secrets `sdk-updates.yml` already uses ([CI plan §3c](../../docs/plans/ci.md#3c-weekly-sdk-updates-added-2026-11-19)), so `ci.yml` runs on the results pull request.

### How to start a run and read its results

Start it from **Actions → live-run → Run workflow** on `main`, or with `gh workflow run live-run.yml --ref main`, then approve the `live-run` deployments when GitHub asks. Two jobs hold keys, one per provider, each on its own runner. Each job writes its key to a file that only the runner's user can read. `scripts/live/run.mjs` then reads the file, deletes it, and runs that provider's listed examples one after another, each through its harness's `scripts/run-examples.mjs --live`. The report job, which holds no key and runs no package code, then does the rest:

- **The run's summary and the provider jobs' reports** show each example's outcome, its checks passed, its model calls and the amount spent, against the job's share of the $1.00 cap and the run's $0.50 target.
- **An issue**, opened only when a flow differs, lists each difference by example: a changed sequence of tool calls (by name and argument keys), a changed stop reason, or a `check()` that changed result or did not run. A listed entry with no live transcript counts as a difference too. When the run's report shows that the example ran, the difference says its transcript did not reach the results commit, rather than that it never ran. Text, argument values, ids and timing never count. A real model varies between runs, so a difference is a prompt to look at the live transcript beside the mock one, not proof that a mock is wrong. The run stays green either way. The live jobs' text reaches the issue only inside code blocks that it can't close, with every @ mention broken, and a transcript may name tools and argument keys only with letters, digits, `_`, `.` and `-`.
- **A pull request** from `live-run/results` holds the live transcripts, each in `<harness>/results/live/<provider>/<example>.json`, where the harness is a `verify/<sdk>` directory or `packages/sdk`. It also holds the date, which the report job takes from its own clock, when the results commit holds at least one listed entry's live transcript and the job of every provider those entries run on completed every example. An entry whose transcript the commit lacks neither moves the date nor holds it back. Merge the pull request to move the date on the listing pages.

### What a run may cost

The owner's rule is that a run may cost at most $1.00 and should aim for less than $0.50. Each provider's job may spend half of the cap, so the two together stay within $1.00. Before every model call, the harness's live mode projects the call's cost from the gateway's price catalog: every input token at the dearest input rate, plus the call's whole `maxTokens` at the output rate. When the job's spend so far plus that projection would pass its share, the call never goes out, the job stops, and its report names the call. A streamed call that fails, or is cancelled before its final event, counts at its projection. The list as committed projects $0.3247 a run at the catalog's prices as of November 2026. The projection counts twice each example's mock model calls, at 8,000 input tokens a call. The four Anthropic examples, on `claude-haiku-5-5` with 1,024 output tokens a call, project $0.0508; the three OpenAI examples, on `gpt-5.4-mini` with 2,048, project $0.2739.

That guard protects against our own mistakes, such as an example that loops or a model that answers at length. It can't contain malicious package code. The example's process must hold the key to call the provider, so code that runs there, a pinned dependency included, can read the key, call the provider without the guard, or misreport its spend in the ledger that `run.mjs` reads. The provider's spend limit is therefore the hard ceiling, and the owner sets it once (above).

### Changing the live list

An example may join the list when its harness has a live mode and a mock transcript, its tools are in-process functions with no host access, and its provider is one its harness's pinned packages reach. The list may name one file once for each provider, and each provider's run of it writes its own live transcript, in `results/live/<provider>/`. Eight harnesses have a live mode: `vercel-ai-sdk`, `langchain`, `pi`, `openai-agents-sdk`, `cloudflare-agents`, `claude-agent-sdk`, `copilot-sdk` and our own `packages/sdk`. `claude-agent-sdk` and `copilot-sdk` make their model calls from a child process, the `claude` CLI or the Copilot runtime, so their live mode runs the example in a network namespace. It sends those calls through [`scripts/live/proxy.mjs`](../../scripts/live/proxy.mjs), which alone holds the key, refuses host tools and applies the cost guard ([how it works](../../verify/claude-agent-sdk/README.md#a-live-run-sends-the-clis-calls-through-a-proxy-that-alone-holds-the-key)). The list names none of their examples yet, because adding one changes what a run costs. Both of `live-run.yml`'s provider jobs run the step that `ci.yml` runs to allow unprivileged user namespaces, since Ubuntu 24.04 restricts them and the live mode refuses to run without one. After an edit, run `node --test scripts/ci/live-run.test.mjs`: it fails until the recorded `projection` matches the list, and it names the figures to write. An example whose checks test the mock's exact wording will differ on every run, so prefer examples whose checks test the flow, as the listed triage capstones do.

Our SDK's live mode runs its book examples through our gateway's own adapters for Anthropic's Messages API and OpenAI's Chat Completions API, and the list runs our triage agent on both. `packages/sdk/scripts/run-examples.mjs` runs one example, and only under `run.mjs`. In a live run, the examples' `scripted()` helper ([`examples/lib/live.mjs`](../../packages/sdk/examples/lib/live.mjs)) builds the model on the real adapter, which receives the key explicitly and sends HTTP only through `ProviderConfig.transport`, the gateway's own seam, so no package code is patched. Before a request leaves, that transport checks the cost guard and refuses: any endpoint but the provider's; a host tool; another model; a body that sets no output allowance; any allowance field above `maxTokens` (OpenAI takes `max_completion_tokens` and `max_tokens`, and each one present must hold the limit); a body field outside the adapter's known set, such as Anthropic's `mcp_servers` or `container`; and an OpenAI `n` other than 1, so a `providerOptions` extra can't make a call cost more than its projection. Our adapters stop reading at the answer's final event, Anthropic's `message_stop` or OpenAI's `[DONE]`, and cancel the body, so the transport settles the guard there, from the usage the answer streamed, which it merges as our gateway's Anthropic adapter does: a count a `message_delta` sends as `null` keeps the `message_start` value; an answer that fails, ends or is cancelled before its final event settles at its projection. The transport passes on none of the provider's headers, except a failed answer's `retry-after` and `retry-after-ms` when they hold a plain number, so our gateway's retries wait as long as the provider asked. The examples' offline setup still loads: a provider key variable still stops an example, every other `fetch` still reaches only the loopback interface, and only real model requests turn on, in a live run alone. When an example times out, its runner deletes the earlier live transcript, so the report never shows an old run as this one. Our gateway retries a request that fails before any output, so the transport charges every attempt, a refused one at its projection. The examples' `calls` and the transcript count only the run's calls, so a retried 429 changes neither an example's checks nor its flow.

A run commits none of the SDK's live transcripts until the owner changes `live-run.yml` to stage `packages/` and diff `packages/*/results/live/**` ([fact-check log](../../docs/plans/reviews/fact-check-build-book.md), row T65-10). Chapter 7's listings of our triage agent then keep "Verified against mock models only", its entries neither move nor hold back the comparison date, and each run's issue lists both entries as missing their transcripts.

## Code in the prose resolves to a listing, a transcript, a `.d.ts` or the standard library, or cites a fact-check row

Inline code that names an API is checked like code in a listing, by the owner's rule ([BK17](../../docs/plans/build-book.md#bk17-code-in-the-prose-is-checked-like-code-in-a-listing-accepted)). The check reads two kinds of span. An identifier or a dotted member path, such as `generateText`, `result.steps` or `response.json()`, is checked by every name in it; a name after a dot is a property, whatever it spells, so `part.type` is checked by `part` and `type`. Any other span is checked when the TypeScript compiler parses it as code, such as `stopWhen: isStepCount(5)`, `maxTurns = 10` or `` `hi ${name}` ``: every identifier in it counts, labels, property names, type names and a template literal's expressions included, but no string or number. Each name must appear in one of four places:

1. **The chapter's file listings.** Every identifier, keyword and string the listed lines hold counts, property names included, read with the TypeScript compiler from the real file. A name that only a comment holds, or that the file holds outside the listed region, does not count.
2. **Their transcripts.** The transcript of each listed example, whether or not the listing replays it, gives its tool names, message roles, stop reasons and `check()` messages.
3. **The `.d.ts` exports of the packages they import.** The compiler resolves each package import from the listed file, so the harness's own `node_modules` and the package's `exports` map pick the `.d.ts`. The compiler then lists the module's exports after every `export *` and re-export. Only exports count, by their exported names. An option such as `maxTurns`, which a type declares as a member, is no export, and a default export counts as `default`, not as its local name.
4. **The standard library their harnesses compile against.** By the owner's decision of 2026-11-19, built-ins resolve: a global that TypeScript's library declares, as the nearest `tsconfig.json` above the listed file selects it with `lib` and `types`. A harness that extends the workspace's base config gets ECMAScript 2024 and Node.js's globals, so `Promise`, `fetch` and `process` resolve, but `document` does not. A member path whose root is such a global resolves through the global's type, so `JSON.parse` resolves by both names. An environment variable is no property, because `process.env` has only an index signature, so `OPENAI_API_KEY` and `process.env.OPENAI_API_KEY` need a listing or a marker, as any other name does.

A name found in none of them fails `check:book` and the build at the chapter's line, and the message names every listing, transcript, package and library searched. To keep such a name, check it by hand, log the check as a row of the chapter's fact-check log, and cite the row right after the span:

```markdown
The run stops once it has spent `maxBudgetUsd`{checked=row-12}.
```

The marker must touch the span, with no space between them. The cited row must appear once in `fact-checks/<slug>.md` with a ✅ or ✏️ verdict. A ⚠️ row, a missing row, a row numbered twice, a malformed marker and a marker that stands apart from its span all fail. The page shows the code without the marker, and a marker may follow any inline code.

The check also fails when a listed file imports a package whose types it cannot read: no `.d.ts` resolves, as when the harness is not installed, or the `.d.ts` declares its module only ambiently, with `declare module`, so it has no exports to list.

Three skip patterns leave a span alone, and `test/checked-code.test.ts` tests each one:

- **Shell commands:** a span that starts with `git`, `node`, `npm`, `npx`, `pnpm`, `tsc` or `tsx`, the workspace's own toolchain, such as `pnpm test`.
- **File paths:** a span with a slash and no space, or a dotted name without `()` that ends in one of 20 file extensions, such as `package.json` or `AGENTS.md`.
- **Literal values:** a number, a quoted string, a template literal without `${…}`, `true`, `false`, `null`, `undefined`, `NaN` or `Infinity`.

The test fixes each list in full, so any addition shows up in review; add a command when a chapter first needs it. Keep the lists short, or the rule loses its force. Two kinds of span are not code and go unchecked: a reserved word alone, such as `const` or `await`, and arithmetic notation, which joins plain names and numbers only with `^`, `+`, `-`, `*`, `/` or `**`, such as `pass^k` or `n - 1`. Assignments, updates, unary, logical and nullish operators, `typeof` and `as` are code, so `maxTurns = 10`, `a ?? b` and `foo as Bar` are checked. A span the compiler cannot parse is not checked either, and fenced code in a `:::listing` comes from no file, so its names do not count.

The workspace's typescript 7.0.2 exports no stable compiler API, only `./unstable/*` clients that run the native compiler in a child process. The check therefore reads code with typescript 6.0.3, installed as `typescript-api`, which is our choice. The compiler loads on first use: a process that renders no chapter, such as `book:switch-report`, never loads it, but a build loads it once the book has a file listing, because the render dependencies read each listed file's imports. A standard library loads only when a name resolves nowhere else. One book load parses each listed file once and lists each package's exports once, however many spans need them. `astro.config.mjs` hashes each written chapter's fact-check log, each listed example's transcript and each listed file's nearest `tsconfig.json` with its other render inputs. The render dependencies name each package a listing imports at the version its harness resolves. An edit to any of these inputs renders every chapter again.

## A figure is a script that draws an SVG, and the build inlines it

Each flat figure is a TypeScript script, and the SVG it writes is committed beside it. A test redraws every figure and fails when a committed SVG differs from what its script draws now, so a figure cannot drift from its script. The build inlines the SVG instead of linking it, so the figure takes the page's colours in both themes and needs no JavaScript. To add a figure to a chapter:

1. Write `figures/<chapter slug>/<figure id>.ts`. Its default export draws the figure with [`figures/lib/svgkit.ts`](figures/lib/svgkit.ts) and returns it; [`figures/call-workflow-loop/who-decides.ts`](figures/call-workflow-loop/who-decides.ts) is the sample.
2. Run `pnpm --filter @buildanagent/manual figures:build`, which writes `<figure id>.svg` beside every script. Commit both files.
3. Place the figure in the chapter with its caption, its id and its alt text:

   ```markdown
   :::figure[A call, a workflow and a loop differ in who decides the next step]{#who-decides}
   ::svg{alt="Three columns of boxes joined by arrows: a call, a workflow and a loop."}
   :::
   ```

The kit throws while drawing, naming the figure, when a mark breaks one of its rules:

- A label uses a character that the embedded code font lacks, such as `↺`; the message names the character and its code point. The font is the upright Manual Code subset in `public/fonts/`, so the check matches what readers see.
- The figure is wider than 520 units, the widest a chapter's figure panel shows whole on any screen about 640 px or wider. This limit is our choice.
- A mark leaves the canvas, a label is wider or taller than its box leaves room for, two labels overlap, or a line or curve crosses a label.
- `connect()` joins two boxes that overlap or share no band across the gap between them, or an arrow is shorter than twice its head.
- An id does not start with `<figure id>--`. Inlined figures share the page's id space, and kebab-case ids never hold `--`, so two figures cannot clash.

The figure colours its marks with the `fig-*` classes in `src/styles/figures.css`, never with colour attributes. The kit measures labels at those classes' font sizes. Each committed SVG also embeds the code font as a data URI and the panel tokens of both modes, so the file renders on its own, for example in a pull request. The build drops that `<style>` element when it inlines the figure, because the page serves the same font and tokens and its content security policy allows no inline style. A change to the kit, the `fig-*` rules, the tokens or the code font therefore makes the figures stale: rerun `figures:build`. The font makes each committed SVG about 61 KB, but no page carries it.

A page shows a figure at its natural size, so its labels stay at 12 px, the approved phone label size, on every screen (BK11). Where the panel is narrower than the figure, as on a phone, the drawing keeps its size and the panel's drawing area, the stage, scrolls sideways. A figure never splits into a second drawing, and none of this needs JavaScript. The note "Scroll sideways to see the whole figure →" shows under the drawing exactly when the stage overflows, because the note's animation runs on the stage's scroll timeline, which stays inactive while nothing scrolls. A browser without scroll-driven animations never shows the note, but the stage still scrolls. The stage takes keyboard focus on every screen, since CSS cannot make it focusable only while it overflows, and the figure's caption names it for screen readers.

The inlined drawing may hold only what the kit writes: `g`, `rect`, `path`, `circle` and `text` elements, the kit's attributes, and links to ids inside the figure. A script, an image, a `foreignObject`, a second `<style>`, an event handler or a link elsewhere fails the build, so a hand-edited SVG cannot put script or outside content on a page.

The build and `check:book` fail, with the chapter's file and line, when a figure lacks its alt text or its caption, or holds anything besides one `::svg` or `::viewer`. They also fail when its SVG is missing or was drawn for another figure. Figure numbers come from the outline, like every other block's.

::svg{alt="Three order tickets hang from a rail…"}

## An isometric figure is drawn with the anatomy skill and proved by its audits

A few chapters get an isometric centerpiece, an interactive drawing of a small machine (BK10). Each is a script like a flat figure, but it draws with the anatomy skill vendored in [`.agents/skills/anatomy/`](../../.agents/skills/anatomy/SKILL.md), pinned at upstream commit `1482e84` ([THIRD-PARTY-NOTICES.md](../../THIRD-PARTY-NOTICES.md)). Read the skill's `SKILL.md` and `references/craft.md` before designing one. One rule in them gives way to the book's: the skill allows at most one engraved label in a drawing, but a book figure may label each of its real parts, by the owner's decision of 2026-11-19 ([BK10](../../docs/plans/build-book.md#bk10-flat-diagrams-and-a-few-isometric-centerpieces-accepted)). To add an isometric figure to a chapter:

1. Write `figures/<chapter slug>/<figure id>.ts`. Its default export builds the camera with the kit's `fitProjection`, makes the audit's `recorder`, draws every part through `IsoParts` from [`figures/lib/isokit.ts`](figures/lib/isokit.ts), and returns an `IsoFigure` with the card's title, hint and readout. `IsoParts` draws each slab or cylinder with the kit and records the same shape for the audit, so the audit checks what the page shows. A part whose name starts with `stand.` is the ground, and every other part must rest on one that leads to it. Chapter 1's [`loop-bench.ts`](figures/call-workflow-loop/loop-bench.ts) is the book's centerpiece, and the fixture book's smaller [`loop-bench.ts`](test/fixtures/book/figures/first/loop-bench.ts) is the sample the tests use.
2. Run `figures:build`, which writes `<figure id>.html`, the kit's card around the drawing, beside the script. Commit both files; the staleness test covers fragments as it covers SVGs.
3. Run `figures:audit`. For every isometric figure it runs the skill's geometry audit, which must print `audit passed`, then the skill's `scripts/lines.mjs` on a light and a dark check page, which must each print `line ends: 0`. The line check needs Chrome; set `CHROME_PATH` if the skill's search does not find it. The book's CI job runs the same command.
4. Place the figure with `::viewer` where a flat figure has `::svg`:

   ```markdown
   :::figure[The agent loop's bench: context, model and tool, each with a lamp]{#loop-bench}
   ::viewer{alt="An isometric bench with three stations: …"}
   :::
   ```

The build inlines the fragment in the chapter, with no iframe, on the same scrolling stage as a flat figure, so the drawing keeps its natural size and its labels never shrink under 12 px. The alt text goes first, as a visually hidden paragraph, and the drawing itself is hidden from screen readers. The card's top-left corner shows the figure's number. The first paint is complete: the static page already shows the first step's part lit and its readout. Where parts carry `data-iso-step` and `data-iso-readout` attributes (pass them as `attributes` to `IsoParts`), [`src/scripts/iso-figures.ts`](src/scripts/iso-figures.ts) walks through the steps, moves the lit part and the readout, and adds Play and Next step buttons. It plays only while the card is on screen and starts paused when the reader prefers reduced motion. Without JavaScript the reader sees the first step and no buttons.

The fragment may hold only what the kit writes for a card and its drawing. Its elements are `figure`, `div`, `span`, `svg`, `g`, `path`, `circle` and `text`, each with the attributes and values the kit writes, and its ids start with `<figure id>--`. Its `data-*` attributes come from a closed list, each with the values it may take: the kit's tones, shades, flags and card corners, the part names `isokit.ts` writes, and the step number and readout text that `iso-figures.ts` reads. Anything else fails the build, for example:

- a script, an event handler, a link or a `url()`;
- a style element or attribute;
- an image, an iframe or a second drawing;
- an entity the kit never writes, in text or in a value;
- a self-closing tag outside the drawing, which HTML would ignore.

Flat SVGs and fragments go through one checker, `src/book/markup.ts`, and each kind adds its own allowlist. Two kit helpers write inline styles, `fadeLineSvg` and pulsing dots, so a book figure cannot use them, because the page's content security policy allows no inline style.

Ids need a prefix only when a page shows a figure twice. A chapter page shows each figure once, and figure ids are unique across the book, so a chapter's ids keep their names. The component gallery shows Chapter 1's centerpiece, [`figures/call-workflow-loop/loop-bench.ts`](figures/call-workflow-loop/loop-bench.ts), once per theme, so each copy's ids take the theme as a prefix. Under `BOOK_FIXTURE_DIR` it shows the site fixture's sample instead, and the build test checks its prefixed ids.

## Glossary terms link once per paragraph

[`src/data/glossary.json`](src/data/glossary.json) holds each term's definition in plain text, its spellings (`match`, the term itself when omitted) and at least one register source. A chapter tags a term by listing its id in `glossary`. The build links the term to `/glossary/#<id>` once in each paragraph, list item, table cell or caption where it appears, so a reader who starts mid-chapter still finds the link, and a paragraph that repeats the term underlines it once. Headings, box and tab titles, links, code and HTML stay plain. Terms match any case and a plural, while an abbreviation (`"kind": "abbr"`, with its `expansion`) matches its exact case. A tagged id that the glossary lacks fails the check, and so does a tagged term that the chapter's text never uses outside those plain places.

Each link opens its own card on hover and on keyboard focus. The card takes the classes and styles of the gallery's `GlossaryTerm`, but its markup differs in four ways: it has no id, no `role` and no `<dfn>`, and it carries `aria-hidden="true"`. A term can link many times on a page, so screen readers hear the definition through `aria-describedby` instead. That attribute points into one hidden list at the end of the chapter, with one entry per term, so ids stay unique however often a term links.

The card's text therefore repeats in the page's HTML after every link. In Chapter 3 the cards and their markup add 24.7 KB to the page, or 1.2 KB once compressed, as of November 2026. We keep the cost because the card opens through CSS alone; a card the script built from one copy would leave a reader without JavaScript no card. Four things keep the repeated text out of the way. `aria-hidden` hides it from screen readers and from Firefox's reader view, whose Readability library drops `aria-hidden` elements. `data-pagefind-ignore` keeps it out of the book's search, the card stays hidden until it opens, and the print stylesheet never shows it. [`src/scripts/glossary.ts`](src/scripts/glossary.ts) closes an open card on Escape and places it at fixed coordinates inside the viewport, so a card never makes a phone screen scroll sideways and a scrolling table never clips it. The pointer can move from the term onto its card and the card stays open, as WCAG 1.4.13 asks.

Use a common word sparingly as a tag. Even once per paragraph, "session" links 42 times in Chapter 5 and "tool" 43 times in Chapter 3, as of November 2026. A chapter that finds a term too dense can drop its tag.

## Each analogy explains one concept, across the whole book

Analogies are optional (BK22). A chapter that uses one first registers it in [`src/content/analogies.json`](src/content/analogies.json):

```json
{"id":"kitchen-ticket-rail","concept":"agent loop","analogy":"a kitchen ticket rail","chapter":"call-workflow-loop","illustration":"ticket-rail","breaks":"A cook remembers yesterday's orders; a model sees only what the transcript carries."}
```

The chapter then marks each use with `:analogy[the ticket rail]{#kitchen-ticket-rail}`. A later chapter refers back to the same analogy by the same id; it may not name an analogy from a later chapter. `illustration` is the id of a figure in that chapter, or `null`; that figure carries the analogy's mark, as the figures section describes. The check compares analogies and concepts without case, punctuation or a leading article. It fails on the same analogy listed twice, on an analogy that explains a second concept, on a concept given a second analogy, and on a chapter that names an id the register lacks. It cannot tell that two different phrasings describe nearly the same image, such as a kitchen ticket rail and a waiter's order spike, so reviewers catch near-duplicates when they vet a chapter's analogies.

## The tokens come from one JSON file

`scripts/generate-tokens.ts` reads `book-tokens.json` and writes `src/styles/tokens.css` and `src/styles/reading.css` ([A reader chooses a typeface pairing and a text size](#a-reader-chooses-a-typeface-pairing-and-a-text-size)). The generated file puts the light page and light panel values on `:root` and on any `[data-theme="light"]` element. The dark values apply under `prefers-color-scheme: dark`, unless the reader chose light, and on any `[data-theme="dark"]` element. Because the panel tokens follow the same rule, a code or figure panel always matches its page: a light panel framed by `#E4D6C2` in light mode, C1 Ember in dark mode.

Four checks in three test files guard the file. First, `test/tokens.test.ts` fails when either committed CSS file differs from what the script writes, and when a page or panel token has a value in one mode only. Second, `test/contrast.test.ts` reads every pair from the JSON file's `contrast` lists and recomputes its WCAG ratio from the colours the CSS ships. It fails below 4.5:1 for text and below 3:1 for focus rings, and it fails when a recorded ratio differs from the recomputed one at two decimals. Third, `test/styles.test.ts` fails when a stylesheet or component writes its own hex colour. Fourth, the same file fails when a decorative token colours anything but a border or a background.

To change a token, edit the JSON file, update its recorded ratio if a colour changed, then run `pnpm --filter @buildanagent/manual tokens`.

The package's `exports` map lets `apps/docs` reuse the generator without copying it: `./design/tokens`, `./design/contrast`, `./design/woff2`, `./figures/svgkit` and `./styles/figures.css`. The `fig-*` rules sit in `figures.css`, apart from `components.css`, so a site that takes the figures does not take the book's page styles. `tokensCss()` takes an optional header comment and font folder for such a site.

## The fonts are self-hosted subsets

The site serves Instrument Serif, Literata and Google Sans Code, and the reading pairings' Atkinson Hyperlegible, Space Grotesk, Inter and Bitter, from `public/fonts/`, so a reader's browser fetches nothing from another origin. The files come from [google/fonts](https://github.com/google/fonts) at the commit `fonts/sources.json` records. That file is the one list of the families. For each family it records the upstream folder and the SHA-256 of each upstream file, the served folder and file names, the licence files and, for Google Sans Code, the neutral name. Two scripts rebuild the served files, and both run only when a font changes:

```sh
cd apps/manual
node scripts/fetch-fonts.mjs
uv run --no-project --with fonttools==4.68.0 --with brotli==1.2.1 \
  python -I scripts/subset-fonts.py fonts/sources.json fonts/upstream public/fonts
```

`fetch-fonts.mjs` downloads the upstream files into the gitignored `fonts/upstream/` and refuses a file whose hash differs from the manifest; after a re-pin, `--record` writes the new hashes. `subset-fonts.py` writes WOFF2 subsets with Latin, punctuation, arrows, maths and box-drawing characters, and copies each family's `OFL.txt` beside them.

Google Sans Code's `TRADEMARKS.md` keeps the Google mark off modified versions, so its subsets are named Manual Code in their files, their CSS and their name tables. Instrument Serif and Literata keep their names, because neither licence reserves a font name and neither family has a trademark file; the owner chose to keep Literata's name on 2026-11-19. The four reading families keep theirs too. None has a trademark file, and only Bitter's licence reserves a name, "Bitter Pro", which the served family, Bitter, does not use; that name appears in the subsets only in the copyright notice's URL, which the OFL requires them to keep. Inter's and Bitter's name tables also carry trademark notices, which the subsets keep, as Literata's does. [THIRD-PARTY-NOTICES.md](../../THIRD-PARTY-NOTICES.md) records those notices and the licences. `test/fonts.test.ts` checks the licence files, and it reads each subset's WOFF2 name table to check the family names, that no Manual Code name record mentions Google and that no Bitter name record but the copyright names Bitter Pro. It reads its list of families from `fonts/sources.json` and `book-tokens.json`, so a new family is checked once both files list it.

## A reader chooses a typeface pairing and a text size

A reader can set the book in one of four typeface pairings and at one of five text sizes; the owner chose both lists on 2026-11-23 (design S1). The choice lives in the reader's own browser and applies before the first paint. This part ships the fonts, the early script and the CSS; the settings panel that writes the choice is [T70](../../docs/todos/ready/T70-manual-reading-settings-ui.md).

| Pairing | `data-reading-font` | Headings | Body |
| --- | --- | --- | --- |
| Book (the default) | none | Instrument Serif 400 | Literata |
| Readable | `readable` | Atkinson Hyperlegible 700 | Atkinson Hyperlegible |
| Sans | `sans` | Space Grotesk 600 | Inter |
| Slab | `slab` | Bitter 700 | Bitter |

The code face, Manual Code, the figures' labels and Pagefind's search page stay the same in every pairing. Space Grotesk has no italic, so the browser slants its roman for an italic word in a Sans heading.

**The data.** The `font.reading` block of `book-tokens.json` lists the pairings, the faces only they use, each pairing's heading weight and the sizes 90, 100, 115, 130 and 150 percent. `scripts/generate-tokens.ts` writes `src/styles/reading.css` from it: an `@font-face` rule for each reading face, `--weight-display` and `--reading-scale` on `:root`, and one rule per pairing and per size. A pairing's families appear only under `:root[data-reading-font="<id>"]`. A browser downloads a face only once an element uses its family, so declaring every face costs nothing, and a page fetches only the chosen pairing's files. A size step sets the root `font-size` to its percent, which every rem length follows, and sets `--reading-scale` to match.

**The early script.** `public/scripts/reading-settings.js` reads two localStorage keys, `manual-reading-font` and `manual-reading-size`, and sets `data-reading-font` and `data-reading-size` on `<html>`. It accepts only the exact values in its lists, `readable`, `sans` or `slab` and `90`, `115`, `130` or `150`, and removes the attribute for the defaults, `book` and `100`, and for anything else. `BaseLayout` loads it as a blocking script in `<head>`, right after `theme.js` and before the stylesheet, so the attributes are on `<html>` before the first paint. It then adds a preload link for the chosen pairing's upright files, which is why the layout itself preloads no font. Every storage call sits in try/catch, so blocked storage gives the default, and so does the rest of the start-up, which runs after the script has put its API on `window`. Without JavaScript the page shows Book at 100% and preloads nothing. The script uses optional chaining and `??`, so it runs from Safari 13.1, Chrome 80 and Firefox 74, and it avoids `Object.hasOwn` (Safari 15.4), `at()`, `structuredClone`, `replaceAll` and logical assignment. In an older browser it is a syntax error: the page shows Book at 100% and `window.manualReadingSettings` stays undefined, so the settings panel must check for it.

A blocking script cannot be a module, so it cannot export. It leaves its lists and functions, frozen, on `window.manualReadingSettings`: the two keys, `PAIRINGS` (each id with its preload files), `SIZES`, `readFont`, `readSize`, `read(storage)` and `apply(root, settings)`. The settings panel will use them, so the allow-lists live in one place. `test/reading-settings.test.ts` runs the script in a sandbox and checks that its lists match `book-tokens.json`.

**The header keeps its size.** The header is the book's controls, not its text. Every rem length in it is divided by `--reading-scale`, so it stays one 52 px row on a phone and one 56 px row on a desktop at every text size, and the wordmark never shortens to an ellipsis. The wordmark's size is a clamp of rem and viewport parts, so only its rem parts are divided; the viewport part is left alone, and the wordmark measures the same at 1024 px wide at every size. The search field's height and padding are divided like the buttons'; only its text follows the reader's size, which keeps the 16px minimum under a finger. `check:reading` measures the header on a 1280 px desktop at every size.

**Sizes in px.** Text sized in px would ignore the reader's size. The notes popover's quote (13px), note and field (15.5px) and action row (12px) now use rem: 0.8125rem, 0.96875rem and 0.75rem, the same sizes at 100%. Figures keep px: an SVG's text scales with its SVG, and `figures/lib/svgkit.ts` measures labels at those sizes. The search box now caps itself at its column's width and lets its field shrink, because at 150% on a phone the gallery's sample box was wider than the screen.

**Checks.** `test/reading-settings.test.ts` checks the script: the allow-lists, ignored values, the defaults, storage that throws, a browser without `Object.hasOwn`, a failing start-up, the preloads and its place in the layout. It also checks that the CSS names a pairing's families only under that pairing's attribute and that every pairing's files are in `fonts/sources.json` and `public/fonts/` with their `OFL.txt`. `test/build.test.ts` checks the built pages: the script comes before the stylesheet, and no page preloads a font itself.

`check:reading` measures a build in Chromium, with each pairing and size stored before the page loads. For each pairing it checks the computed font of the title, a section heading and the body, and that the page requests only that pairing's fonts and the code face's. It confirms the attributes are on `<html>` in the first animation frame and that each size sets the root font size. It checks that a sample of pages never scrolls sideways at 150% on an iPhone 14, checks the header at that size and runs axe in each pairing. WebKit is not checked.

## The components work without JavaScript

Each component in `src/components/` renders its full content with no script. A few then add behaviour as progressive enhancement, and their buttons render with `hidden` until the script shows them:

- **Layout:** `SiteHeader`, `ChapterHead` (the wide title), `Sidebar` with `Contents`, the article column in `layouts/ChapterLayout.astro`, and `PrevNext`. The columns switch with container queries on the `.layout` element, not with viewport media queries, so the layout follows the width it is given: the sidebar joins at 64rem, holding "On this page" above "All chapters". From 83rem "On this page" moves to a sticky 15rem rail right of the article while "All chapters" keeps the left column, so the prose sits between the two and the page's headings use the space right of it. The 83rem is the sidebar, the rail, their gaps and a 52rem article, so the rail never stacks a listing and its run. The article stops at `--article-max`, 59.5rem (the measure, a gap and a side note). A chapter page is therefore at most 90.5rem wide (the sidebar, the article, the rail and their gaps) and centred. On a wide screen the prose ends 20rem (320 px) before the rail instead of leaving a wide empty band, and the title and figure panel line up with the columns under them. Side notes float beside the prose whenever the article itself is at least 59.5rem wide, the measure, a gap and the note: from a 73rem layout beside the sidebar alone, and from 90.5rem once the rail is there. Printed, the page drops both navigation lists. A page with no chapter (the contents, glossary, sources, search and 404 pages) has neither sidebar nor wide blocks, so `.page--single` narrows it to one column the width of the measure, centred under the header. Prose and headings keep the measure, while listings, listing-and-run pairs, figures, tables and tab blocks take the whole article column and clear any side note. They stop at the rail's edge rather than pass under it, so the sticky rail never covers one.
- **Code:** `ListingBlock` with `AnnotationMarker` and `Annotations`; `Tabs` with `TabPanel`, which show every panel under its own heading until `scripts/tabs.ts` builds the tab list; `Replay` with `StepControls`, which `scripts/steps.ts` steps through. A chapter's notes, `:::tabs` and replays render the same markup from `listing-html.ts` and `replay-html.ts`, and `ChapterLayout` loads both scripts.
- **Figures:** `FigureFrame` on grid paper, which becomes the isometric stepper when it has steps; `scripts/steps.ts` then shows one step at a time and dims the figure parts of the others. `GeneratedFigure` puts a figure from `figures/` in a `FigureFrame`, inlined as a chapter's is; the gallery uses it.
- **Prose:** `SideNote`, `GlossaryCard`, `GlossaryTerm` (its card opens on hover and focus and stays open while the pointer is on it, and `scripts/glossary.ts` lets Escape close it), `Citation` and `SearchBox`. A chapter's box has no component: the Markdown pipeline writes its `<aside>` ([A box sets a passage apart](#a-box-sets-a-passage-apart-from-the-chapters-argument)).
- **Reading place:** the Contents page's "Resume reading" link, hidden until `public/scripts/reading.js` finds a stored place ([A reader's place stays in their own browser](#a-readers-place-stays-in-their-own-browser)).
- **Notes:** none in the built page. `public/scripts/notes.js` adds the selection toolbar, the Notes button and its panel on a chapter page, and only where the browser can draw highlights ([A reader's notes stay in their own browser](#a-readers-notes-stay-in-their-own-browser)).
- **Theme:** `ThemeToggle`, driven by `public/scripts/theme.js`, which applies a stored choice before the first paint. The button shows a sun in the dark theme and a moon in the light one, and its accessible name gives its action, "Switch to light theme" or "Switch to dark theme". Both follow the system setting while the reader has stored no choice.

The gallery at `/gallery/` renders every component in both themes, one above the other at full width, so each shows the layout at the width a reader sees it. It stays out of the search index and carries `noindex`. Its citation and glossary samples link to the `/sources/` and `/glossary/` pages. The owner compares the gallery with the reference board after any design change.

## A reader's place stays in their own browser

The book remembers how far a reader got in each chapter and offers a link back from the Contents page, with no server, account or cookie. One script, `public/scripts/reading.js`, does both jobs. Like `theme.js`, it is a same-origin file served as-is from `public/`, so the content security policy allows it by path. `BaseLayout` loads it on every page as a module, which runs once the page is parsed.

- **What it records.** On a chapter page, the script collects the chapter's section headings. These are every `h2` and `h3` with an id in the article, except a tab's heading (its id starts `lst-`) and any heading inside a listing, a replay, a figure or text marked `data-pagefind-ignore`. When the reader's scrolling pauses for 400 ms, it takes the last of those headings whose top has reached the top of the window. A reader who has scrolled to the bottom of the page reaches the last heading too, because a short last section never lets that heading rise to the top. The script stores the heading only if it lies further into the chapter than the stored one, so a reader who scrolls back up keeps the furthest place. If the page is hidden during the pause, the script stores the place then, though browsers don't fire that event every time. A chapter that the reader reopens with Back, from the browser's back/forward cache, counts as a new visit and becomes the chapter to resume again.
- **What it stores.** One localStorage key, `manual-reading`, holds each chapter's place under its slug: the heading's id and text, and the time of the last write, as in `{"v":1,"chapters":{"tools":{"id":"…","text":"…","at":1795331838668}}}`. Every chapter keeps its own place, and the most recent write picks the chapter to resume. The key holds at most 100 places; past that, the place written longest ago goes first.
- **What the Contents page shows.** The Contents page holds a hidden "Resume reading" link inside a paragraph that keeps the link's two-line height, so the contents never move when the link appears. When storage holds a place in a chapter the Contents list still links, the script names that chapter by number, puts the heading on the second line, points the link at `/<chapter>/#<heading id>` and shows it. If the chapter has since lost that heading, the link still opens the chapter, at its top, because a browser that finds no element for a fragment leaves the page where it opened. The next heading the reader scrolls past then replaces the lost one. A stored chapter that the Contents list no longer links has left the book, so the script drops its place. When Back restores the Contents page from the back/forward cache, the script reads storage again, so the link names the chapter just left.
- **What it never does.** The script makes no request and sets no cookie, and it writes stored text into the page only as text, never as markup. Each browser keeps its own places, and a reader removes them by clearing the site's data in the browser's settings. With storage blocked, every storage call fails inside a `try`, the chapter reads as usual and the link stays hidden. Without JavaScript the link stays hidden too.

`test/reading.test.ts` checks the script's pure functions against damaged and hostile stored values. It then runs the script in happy-dom over a small chapter and Contents page, with storage working, blocked and throwing, and with every network API set to fail the test. `test/build.test.ts` checks the built Contents page's hidden link and the script on every page. The site header has no resume link, because its row wraps on a narrow screen and a link that appeared after load would push the page down. Progress marks per chapter on the Contents list are a follow-up (BK23 in the [book plan](../../docs/plans/build-book.md#bk23-a-readers-place-stays-in-their-browser-proposed)).

## A reader's notes stay in their own browser

A reader can highlight a passage of a chapter and attach a short note to it, with no server, account or cookie (BK24 in the [book plan](../../docs/plans/build-book.md#bk24-a-readers-notes-stay-in-their-browser-proposed)). One script, `public/scripts/notes.js`, does the work. It offers four highlight colours, a panel, a popover on a click, a marker on highlights with a note and Share; the bullets below cover each, then storage, matching, rendering and tests. Like `reading.js`, it is a same-origin file served as-is from `public/`, and `ChapterLayout` loads it as a module on chapter pages only. The built page holds none of its interface: the script adds everything it shows, marks it `data-pagefind-ignore`, and adds nothing inside the article except, in a narrow window, a note's dot.

- **When it runs.** The script starts only on a chapter page, only where the browser has `CSS.highlights` and the `Highlight` constructor, and only when it can read localStorage. Anywhere else it adds nothing and throws nothing. As of November 2026 the CSS Custom Highlight API works in Chrome from version 105, Safari from 17.2 and Firefox from 140; Firefox before 146 draws a highlight's background but not its underline, so a highlight with a note also gets a marker.
- **How a reader makes a note.** Selecting text inside the article shows a small toolbar beside the selection, with four colour buttons (Amber, Green, Blue and Pink, each a swatch beside its name) that highlight in that colour, and Add note. The colour a reader picked last is the one Add note and the panel's Highlight use; a new reader starts with amber. Add note opens only the note popover at the passage (the A1 design in [`docs/design/notes/`](../../docs/design/notes/README.md)), never the notes panel; the popover is described below. The panel opens only from the Notes button and Alt+Shift+N, and its own form, which the panel offers for the selected text and for a highlight whose passage the chapter lost, still takes a note too. A browser without the Popover API gets that form from Add note instead. If another tab deletes the highlight a note edits before the reader saves, the form keeps the typed text and says so, and the next save adds the highlight back with the note; deleting that highlight from the panel itself closes the form. A note on a passage another tab highlighted meanwhile goes on that highlight, from the form and from the popover alike. An empty popover field keeps the other tab's note, and the highlight keeps its colour unless the reader picked one in the popover. From the keyboard, Alt+Shift+N moves focus into the toolbar when text is selected and opens the panel otherwise; the Notes button in the window's corner opens the panel too and offers the last selection. Escape closes the toolbar or the panel, and focus returns to where it was. Selecting text from the keyboard needs the browser's caret browsing, F7 in Chrome and Firefox.
- **What the panel offers.** The panel is the B1 design in [`docs/design/notes/`](../../docs/design/notes/README.md): a modal `<dialog>` on the window's right, 25rem wide, or the whole width on a window as narrow as a phone's. It runs from the sticky header's bottom edge to the window's foot. Like the popover, it takes `--header-height` as its top while the header shows and the window's top while a phone's header is slid away, and it moves when the header slides. Its header holds the title "Notes", the count, such as "3 in this chapter", and Export and Close as icon buttons, each named by its label and its tooltip. A hint line under it says "Click a note to go to its passage.", and the footer says "Saved in this browser only." The footer's tooltip and the panel's accessible description add that clearing the site's data deletes the notes. The body between them scrolls. The panel lists the chapter's highlights in reading order, one card each: a bar in the highlight's edge colour, the passage, the note and two buttons. The passage and the note together are one button that closes the panel and goes to the passage; "More actions" opens the card's menu. A passage the chapter lost is not a button and has no Share. The menu holds Edit (Add note on a plain highlight), Share, Colour (four `menuitemradio` dots, the highlight's own checked) and Delete. The arrow keys move through it and wrap, Left and Right move between the colours, Home and End go to the first and last item, Escape closes the menu and gives focus back to its button without closing the panel, and Tab closes it. Only one menu is open at a time, and a press elsewhere in the panel closes it. A colour recolours the highlight and the card at once and leaves the menu open on that colour. Delete deletes at once, with no confirmation and no undo, as the old panel's Delete did. It works from the stored list, never overwrites a stored value this page cannot read, says what it deleted in the live region, and moves focus to the next card's menu button, or to Export when no card is left. Edit closes the panel first, on a phone as on a desktop, so the popover is the only thing open. It then scrolls the passage to just below the header and opens the note popover there, the sheet on a phone, with the field ready; focus then follows the popover's own rules. A passage the chapter lost has nowhere to open the popover, so its Edit opens the panel's form. With no highlights, the panel says "No notes yet. Select text in the chapter, then choose Add note." Export copies the chapter's notes to the clipboard as Markdown, shows the same Markdown in a field to copy by hand, and offers it as a `.md` download through a `blob:` link, which the content security policy leaves alone because no directive governs downloads. Escape and a click on the backdrop close the panel, and focus returns to where it was.
- **What it stores.** One localStorage key, `manual-notes`, holds each chapter's highlights under its slug, as in `{"v":2,"chapters":{"tools":[{"id":"…","quote":"…","prefix":"…","suffix":"…","section":"<heading id>","offset":412,"note":"…","at":1795331838668,"color":"green"}]}}`. The script reads version 1, which had no colours, as amber, and writes nothing on load, so a visit that only reads leaves the stored bytes as they were; the first change writes version 2. The script draws an unknown colour in amber. If a later version wrote it as 1 to 32 letters, digits or hyphens, the script keeps it as stored until the reader picks a colour; it reads any other value as amber. The script reads versions 1 and 2 only. A copy of the script from before version 2 treats version 2 as unreadable and refuses it. A chapter keeps at most 200 highlights, a highlight marks at most 1,000 characters, and a note holds at most 500. At the cap, a passage already highlighted can still take a note; only a new highlight is refused. Past a limit, or when the browser refuses to store a change, the toolbar stays open and says why, as does the panel when it is open. A stored value this page cannot read, written by a newer version of the book or damaged, is never overwritten. The script reads it as no notes and refuses every change with a message, and the panel's export gives the value back exactly as stored, as `notes-as-stored.txt`. Clearing the site's data starts over.
- **How a highlight finds its passage again.** The script joins the article's prose text nodes into one string, with each run of white space collapsed to a space. It leaves out figures, listings, replays, controls, hidden glossary cards and anything marked `aria-hidden` or `data-pagefind-ignore`, so the text it searches stays the same before and after the page's other scripts run. A highlight stores its quote, 32 characters on each side and the heading it sits under. On load the script scores every repeat of the quote in the article by how much of the stored context matches. The best match wins wherever it sits, so a paragraph moved under another heading is found there even when a similar sentence stays behind; the stored section breaks a tie, then the stored offset. A quote found in its section with its context intact is drawn as before. One found in another section, with changed context, or by its context alone after its own words changed is drawn and marked "moved" in the panel. One the chapter no longer holds is marked "not found" and stays listed with its text and note. When another script changes the article's text, the script finds every highlight again and redraws it once the text has stayed unchanged for 100 ms.
- **How it looks.** The CSS Custom Highlight API draws each highlight from a `Range`, so no element wraps the chapter's text. Each colour has two highlight names, one for a plain highlight and one for a highlight with a note: eight `::highlight()` names in all (`manual-hl-amber` to `manual-note-pink`), because the specification advises one name per highlight. The rules in `components.css` give each name its colour token (`--color-highlight` for amber, `--color-highlight-green`, `--color-highlight-blue` and `--color-highlight-pink`), draw its text in `--color-text` and underline it in `--color-accent`; a noted name's underline is dashed. The script registers the names in one fixed order, plain ones with priority 0 and noted ones with priority 1, so where highlights overlap, a noted highlight paints over a plain one and a later colour paints over an earlier one. Text on every colour reaches 8.4:1 or better, and the accent on every colour reaches 3.5:1 or better; recorded in `docs/design/book-tokens.json` and checked in `test/contrast.test.ts`; each colour stays below 1.7:1 against its page, so the background is decoration and the underline and the marker mark a highlight. Because the light accent reaches only 3.56:1 on the pink, below the 4.5:1 text needs, highlighted text always takes `--color-text`: a highlighted link keeps its underline but takes the body colour. The toolbar and the button are fixed, so neither moves the chapter's text, and printing hides the highlights, the markers, the popover, the toolbar, the button and the panel.
- **A note has a marker.** Firefox before 146 draws no underline from a highlight, so a highlight with a note also gets a marker in the highlight's own colour. Which marker depends on the room beside the text column, measured from the right edge of the first paragraph or of the widest block that holds a noted passage, whichever is further right: with 44 pixels or more free, the marker is a speech bubble in the margin; with less, it is a numbered dot after the passage. A resize or a rotation across that width swaps one for the other, and a swap back leaves the article's markup as it was before any dot went in. The number is the note's place among the notes in the panel's order, and the panel names each note "Note N".
  - **In the margin (a wide window).** The marker is a 28 pixel button, outlined in the colour's edge shade on a page-coloured fill, with a 14 pixel bubble icon, set level with the passage's first line, 8 pixels right of the column, or of the passage's own block when that is wider, and never past the window's edge. Nothing is added to the article. The markers live in one container, the last child of `body`, marked `data-pagefind-ignore`; it sits at the page's origin, as wide as the page, clips its horizontal overflow and takes no pointer events, so a marker can never widen the page, and each marker takes pointer events back. The script sets `left` and `top` through the element's style object, which the content security policy allows where a `style` attribute would be blocked. Two markers that begin within 32 pixels of each other are stacked with a 4 pixel gap, so they never overlap. Hovering or focusing a marker brightens its passage with a stronger shade of the same colour (the `manual-hover-*` highlight names), and the marker fills with the highlight's colour. Clicking it, or Enter or Space on it, opens the popover. A redraw moves a marker that is already there and does not replace it, so a marker that has focus or the pointer keeps it. The markers move again when the article's size changes, when fonts finish loading and when the window resizes.
  - **After the passage (a narrow window).** The dot is the one element the script puts inside the article: an inline `span` with `role="button"`, `tabindex="0"` and an `aria-label` such as "Note 1", marked `data-pagefind-ignore`, so the chapter's text model skips it and Pagefind never indexes it. It holds no text: its number is generated content, so no one can select, copy or search it, and the stored anchors, the joined text and a copy of the passage are the same with or without it. The line reserves room for the dot, so it never covers a character, and a word joiner at the start of its content keeps it on the line of the word before it. It is about 16 pixels across, raised like a footnote mark, filled with the highlight's colour and bordered in its edge shade. An invisible `::after` reaches 14 pixels around it for a finger and 4 pixels for a pointer, so a drag that starts beside a dot still selects text. 
  - **How the dot stays out of the text.** The dot goes after every inline element the passage ends in, such as a link or code, and after a heading, never inside one. The script inserts a dot by splitting the text node at the passage's end, and takes every dot out and joins the text again before each redraw, so nothing piles up. Enter on a focused dot opens the popover on keydown and Space on keyup, like a button, and focus returns to the dot when the popover closes or the page redraws.
  - **Colour shades.** Both markers and the hover highlight use two shades per colour: an edge shade that reaches 3:1 on the page and a hover shade under which text keeps 4.5:1. Both are recorded in `docs/design/book-tokens.json` and checked in `test/contrast.test.ts`.
- **Add note and a click open one popover.** Add note on a selection, and a click on a highlight or a marker, open the same native `popover` on top of the page, so writing a new note and editing a saved one behave alike. It sits under the passage's last line, starting where that line of the passage starts, and flips above the passage's first line when the window has no room below. It is clamped to the reading column (the first paragraph's box) and to the window, 8 pixels in, and placed again on every scroll, resize and redraw, so it stays with its passage. The sticky header's height, `--header-height`, is the top limit for the popover and the selection toolbar while the header shows; while a phone's header is slid away (`data-header-hidden` on the root) the limit is the window's top. A passage under the header counts as out of the window. A passage outside the window when the popover opens is scrolled into view first: the page scrolls by the passage's own first line, not its block, which can be taller than the window, so the line lands 16 pixels below the sticky header. When that scroll goes up and a phone header has slid away, the scroll makes room for the header's full height, because any upward scroll brings it back. The toolbar and the popover are placed again whenever the header slides away or back. While the passage is scrolled out of the window the popover is hidden but stays open with what the reader wrote, and it shows again, with focus back in it, when the passage returns. Opening another highlight, such as with Enter on its marker, while a new note is open drops the new note, as Cancel does. Escape that ends an input method's composition stays with the field. Focus goes to the note field when the popover is for writing: a new note, Add note on a passage already highlighted, and a plain highlight. On a saved note it goes to the checked colour. The `focus()` call is made synchronously inside the click that opens the popover, since iOS Safari opens its keyboard only for a focus made in the tap's own handler (the fact-check row `fix/manual-note-editor-flow-1`, ⚠️: secondary sources only). The script does not rely on the `autofocus` attribute. To find the highlight, the script tests the click's point against `Range.getClientRects()` of each highlight's range; it does not call `highlightsFromPoint()`, which not every engine ships. A drag that selects text, a click on a link or a control and a browser without the Popover API open nothing, and a link inside a highlight still follows its link. The popover closes on Escape and on a click outside. Both go through `closeEditor`, described under "Writing a note here". A highlight cannot take focus, so the notes panel, which offers the same actions, is the keyboard and screen-reader path.
  - **What it shows, in order.** A head row with the four colours on the left and, while a note is being written on a wide window, "Esc to cancel" on the right; the passage as a small quotation; the note as the main text, or the field; and a row of actions below a hairline. The colours are one radio group named "Highlight colour": each is an 18 pixel circle in a 24 pixel target, a `role="radio"` named for its colour, and the checked one is ringed and is the group's only tab stop. The arrow keys move between them and wrap round, Home and End go to the first and last, and each move checks the colour it reaches. The quotation sets in 13 pixel upright type (never italic) in the muted text colour, with a 3 pixel bar on its left in the highlight's edge shade. Two lines show, cut with an ellipsis, and the full text is in the tooltip, which a touch screen does not show; the panel lists the full passage. The note sets at 15.5 pixels. The actions are in monospace capitals: Edit, Share and Remove on a saved note, and Save note and Cancel while writing, with Share and Remove after them on a stored highlight and the count, such as "45 / 500", at the row's end. Save note is filled in the accent with page-coloured text, the pair the page's text selection uses; Remove is in the `danger` colour. The count is the field's accessible description. Every piece of text, the note and the passage included, goes in as text, never as markup.
  - **A new note is a draft until Save.** Add note on a passage with no highlight draws a draft: the passage is painted under the plain highlight name of the checked colour, but nothing is stored, it gets no marker and no click opens it. Changing the colour repaints the draft at once and stores nothing. Save note stores it as a highlight with the note, in the checked colour, which becomes the colour the next highlight takes; with an empty field it stores a plain highlight and says "Highlight saved without a note.". Every other way of closing drops the draft, so Cancel, Escape and a click outside never store anything and leave no highlight behind. We chose this over storing the highlight on the first colour change because then Cancel would have to delete what it stored, and another tab would see a highlight the reader had not kept. At the 200-highlight cap Add note on a new passage is refused in the toolbar, as before.
  - **Writing a note here.** A plain highlight shows an "Add a note" field in place of the note, with Save note, Cancel, Share and Remove. Edit turns a note into the same field. Save note re-reads the stored notes first, so another tab's changes are kept; if another tab deleted the highlight, Save note adds it back with the note. Saving unchanged text writes nothing. A note holds up to 500 characters. Edit puts focus in the field with the caret after the note's last character. One routine, `closeEditor` in `notes.js`, closes the popover for Save note, Cancel, Remove, the Close button, a swipe down, Escape and a click outside. Escape anywhere on the page calls it before the browser's own light dismiss; a click outside closes the popover in the browser. The browser's `beforetoggle` event clears the popover's state at once, the draft included, and its `toggle` event then calls `closeEditor`, unless the popover has opened again by then. `closeEditor` blurs the field, so the on-screen keyboard goes, hides the popover and clears the sheet layout, so a closed sheet is `display: none` and covers nothing. It then moves focus to the note's marker when the popover was opened from the keyboard, is a sheet or was closed with Escape. With no marker left, after Remove or a dropped draft, a keyboard reader's focus goes to the passage's block, which takes `tabindex="-1"` until it loses focus again. After a mouse close focus stays on the page, because a focused margin marker would keep its passage brightened. After a click outside it stays where the reader clicked. If a keyboard reader opened the popover and focus fell to the page, it returns to the marker. It never scrolls. Save keeps the highlight and its marker and says "Note saved." in the page's polite live region (`role="status"`, visually hidden, outside the popover); Remove deletes the note and its highlight, with no confirmation, as before, and says "Note removed." ("Highlight removed." for a highlight with no note). A save that fails, because the stored value is unreadable or the browser refuses it, keeps the editor open with the reason. Anything typed and not saved is dropped by every way of closing but Save note. The reader reopens a saved note by pressing its marker.
  - **A bottom sheet in a narrow window.** In a window 40rem wide or narrower the popover is a full-width sheet at the bottom, rounded at the top, with a handle and a dimmed backdrop. The quotation shows two lines. The sheet is a flex column packed at the top, never a grid, so no extra height can stretch its rows apart. It sits on the bottom edge of the visual viewport, which is how it clears an on-screen keyboard, and is at most half that viewport's height, or 55% below a 520 pixel viewport. `layoutSheet` in `notes.js` sets `--notes-sheet-bottom` and `--notes-sheet-max` from `visualViewport`. Past its maximum the sheet scrolls inside itself, its handle and action row sticking. Below a 520 pixel viewport it drops the quotation, and whenever the keyboard opens or closes the page scrolls to keep the passage visible above the sheet. That scroll keeps the passage's first line 16 pixels below the sticky header while the header shows. A closed sheet is `display: none` on every layout. On a touch screen a colour is a fixed 44 pixel target with a 22 pixel dot, and every action is a 44 pixel target too; with a mouse a colour is a 24 pixel target with an 18 pixel dot. A colour shows a 2 pixel focus ring on `:focus-visible` only, rings the pressed colour on the dot itself and uses system colours for its rings in forced colours. A tap outside closes the sheet (the browser's light dismiss). A swipe down on the handle moves the sheet with the finger; letting go past 80 pixels closes it, and letting go earlier springs it back. A resize or rotation across that width while the popover is open lays it out again as the other kind, popover or sheet, and keeps a new note, the typed text and focus, even when the passage was scrolled out of the window meanwhile. The sheet's top strip is 44 pixels tall and holds the handle and, at its right end, a Close button: a 44 pixel target named "Close note", a cross drawn as inline SVG in `currentColor`, with the same hugging 2 pixel focus ring as a colour and the safe-area inset kept clear. It shows in the saved-note view and in the add and edit states, and it calls the same `closeEditor` as Save, Remove and a swipe. A wide window's popover has no such button, because it already closes on Escape and on a click outside. When the keyboard opens, the visual viewport's `resize` event lays the sheet out again and scrolls the field into view inside the sheet, never the page.
- **Share copies a quote and a link.** Share writes the passage in quotation marks, the chapter's title and a link to the clipboard, and never the note. The link is the page's origin, path and query, with any fragment dropped, then the passage's section heading and a text directive: `#<section>:~:text=…`. The directive carries the passage whole when it is 120 characters or fewer and inside one block, and otherwise its first and last 40 characters, each trimmed to whole words and taken from one block. The directive adds up to 32 characters of context from the passage's own block when the passage's first term also appears elsewhere in the page's text, not counting this script's interface. A browser without text-fragment support lands on the section heading. If the browser has no clipboard or refuses the write, the text appears in a field with its text selected to copy by hand. The script sends nothing anywhere; the text leaves the browser only when the reader pastes it.
- **What the export holds.** The Markdown quotes each passage, then its note as a second quotation under a "Note:" line. Every line of both is escaped with backslashes, so it reads as plain text in any CommonMark renderer. Everywhere in a line the script escapes `\`, `` ` ``, `*`, `_`, `[`, `]`, `!`, `&`, `<`, `~` and `|`, so no code, emphasis, link, image, reference, entity, HTML, strikethrough or table appears. At the start of a line it also escapes `#`, `>`, `+`, `=` and `-`, and the `.` or `)` after a number, so no heading, quote, list or rule begins. A line's leading spaces go, and a blank line in a note stays a blank line of the quotation.
- **What it never does.** The script makes no request and sets no cookie, and it writes stored text into the page only as text, never as markup. Each browser keeps its own notes, nothing syncs them, and clearing the site's data deletes them, so export is the way to keep a copy.

## The header stays in reach, and a line shows how far the reader is through the chapter

The header is sticky on every page, so Contents, Glossary, Sources, search and the theme toggle stay in reach. It is 56px tall on a desktop and one 52px row on a phone. A phone here means a window up to 760px wide or a touch screen, and `src/styles/header.css` holds every rule.

- **One viewport query.** `header.css` is the one place the book uses a viewport-width media query, because the header's height sets the page's scroll padding, which a container query cannot reach. `test/styles.test.ts` allows the query in that file alone, and `test/header-static.test.ts` fails if the stylesheet and `src/scripts/header.ts` name different queries.
- **One height variable.** `--header-height` carries the height (56px, or 52px on a phone) to everything that must clear the header. `html { scroll-padding-top }` is the height plus 12px, so a jumped-to heading, a footnote or a note's "go to passage" stops below it. The sticky offset of the chapter's left and right rails uses it too.

On a phone the row holds the wordmark, a search button, the settings slot, the theme toggle and a menu button. The menu lists Contents, Glossary, Sources and Notes. The Notes entry shows on chapters only and presses the existing Notes button, so `public/scripts/notes.js` is unchanged. The search button opens the existing search box in a panel under the row.

Both are buttons with `aria-expanded` and `aria-controls`. Escape closes them and returns focus to their button, and a tap outside, a link or tabbing out of the header closes them too.

Without JavaScript the phone buttons stay hidden and the links and the search box show in a wrapped header (`@media (scripting: none)`). That header is static and scrolls away with the page, because a sticky header of unknown height would hide the scroll padding's room.

**Hiding.** On a phone the header slides up while the reader scrolls down and returns on the first upward scroll. `src/scripts/header-state.ts` holds the decision as a pure function, `nextHeaderState(prev, scrollY, flags)`, tested over scroll traces in `test/header-state.test.ts`. A move under 8px changes nothing and keeps its starting point, so a slow scroll still adds up. The header stays shown on a desktop, within one header height of the top, while the menu or search is open and while keyboard focus is inside it.

Only focus that matches `:focus-visible` counts, so a button a finger tapped does not pin the header. Focus moving into a hidden header shows it. A hidden header stays in the page's flow (it only translates), so nothing below it moves. With `prefers-reduced-motion: reduce` the header still hides and returns, with no transition. `header.ts` runs one passive scroll listener. Each animation frame reads the scroll position and the cached measurements, then writes the `data-header-hidden` attribute on `<html>` and one transform.

**The progress line.** Chapter pages carry a fixed 3px `.reading-progress` element, which `ChapterLayout.astro` places outside the layout container because the container's layout containment would otherwise capture a fixed child. Its bar fills with `transform: scaleX()` in the accent colour, and `readingProgress(scrollY, start, end, viewportH)` gives the value: 0 at the top of the chapter, 1 when the end of the main text reaches the bottom of the window, clamped. The end is the top of the chapter's Sources section, so the sources, the previous and next links and the footer do not count.

The script measures `start` and `end` on load, on resize, when fonts load, when the article's size changes, when the body resizes and when a `details` element toggles, never during a scroll. The line rides the header's bottom edge and, while a phone's header is hidden, moves to the very top of the window. It is `aria-hidden`, hidden in print and drawn with `--color-accent`, so it works in both themes. The home, glossary, sources and search pages have none.

**The settings slot.** `SiteHeader.astro` holds `<div class="site-header__slot" data-slot="settings">` with a named Astro slot. While nothing fills it the wrapper is empty, `:empty` removes it from the layout and it takes no room. When S1 ships its "Aa" button, render it into the slot: `<SiteHeader><SettingsButton slot="settings" /></SiteHeader>` in `BaseLayout.astro`. The button then sits between the search and the theme toggle on a desktop and a phone. Give it a 44px target on a phone, as the other header buttons have (`.site-header .control`).

**Checks.** `check:header` builds nothing: build first, then run it. It measures:

- both heights and the sticky position;
- hiding and returning, the threshold and focus;
- the menu and search;
- the progress at 0, 50% and 100%, and the line's position with the header hidden;
- a hash jump down and up, with the heading 12px below the header;
- the rails' offset at 1280 and 1600px;
- the popover, toolbar and a glossary card against the header;
- the progress line's end after opening "All chapters" on a phone;
- reduced motion, on the header and the line;
- one-row headers at 761, 800 and 1024px;
- an axe-core run (`axe-core` is a pinned dev dependency, with no network use).

It is not part of `pnpm test`, and `.github/workflows` does not run it yet. What it cannot show: Safari's collapsing toolbar, rubber-band scrolling and a real iPhone.

## The book installs as an app and opens offline

A reader can install the manual from the browser's address bar and open the contents, the search and every page they have read with no connection ([ADR 0059](../../docs/decisions/0059-offline-manual-service-worker.md)). A service worker at `/sw.js` does the work, and it stores only the files of the build it came with. That rule keeps an old build from mixing with a new one, and a deploy needs nothing beyond the usual build.

- **What the build adds.** `scripts/offline-build.mjs` runs after Pagefind. It lists every file of `dist/` with its size and SHA-256 in `dist/offline-manifest.json`, a page as it is with the placeholder still in its mark, leaving out `_headers`, `sw.js`, the list itself and `404.html`. It then writes the build id into every page's `<meta name="manual-build">`, which the layout renders with the placeholder `__MANUAL_BUILD__`, and bundles `src/offline/sw.ts` and `src/offline/worker.ts` with esbuild into `dist/sw.js`, a classic script with the id and the list stamped at its top. The id hashes a format version, the worker's code, the files and the shell, so any change gives a new worker, and a browser installs a new worker only when its bytes differ.
- **What the worker saves.** On install it saves the application shell: the contents, the offline page (`src/pages/offline.astro`, at `/offline/`) and the search page, with every stylesheet, script, font, icon and manifest they link, and every Pagefind file a search needs. The build prints the shell's file count and size on its `Offline:` line. The shell leaves out the fonts of the reader's optional typeface pairings: 8 files, 359,320 bytes, which `OPTIONAL_FONTS` derives from `font.reading` in `book-tokens.json`. The list still holds them. It also copies every file an older build's cache holds with unchanged content. The worker compares a page with its mark set back to the placeholder, so a saved chapter carries over when only its mark changed, and is stored with the new build's mark.
- **What it saves after install.** The page a reader lands on loads before the worker controls it, so `offline.js` asks the worker to save it and the files it loaded. A page the reader opens later is saved when its bytes match the list. The whole book, about 5 MB as of 2026-11-23, is saved only when the reader asks, with the footer's control.
- **What a reader gets.** A page comes from the network, and from the saved copy when the network fails or takes more than 3 seconds. A page that is not saved shows the offline page, and a page asked for without its slash redirects to it, as Cloudflare does online. Hashed files, under `/_astro/` and Pagefind's `index/` and `fragment/`, come from the cache first. For a page that came from the cache or matched the list, every other asset comes from the cache first too, and from the network only when its bytes are this build's. The worker keeps that record in its cache, so it survives a restart of the worker.
- **What the worker refuses.** It answers only same-origin GET requests for listed paths, and leaves everything else, `/sw.js` and `/offline-manifest.json` included, to the browser. A path is decoded segment by segment before the lookup. An encoded dot segment, slash or control character matches nothing. A response is stored only when it is a plain 200 with the listed size and hash, no `Set-Cookie`, no `Vary: *` and no `no-store` or `private`. A 404 or an error page is shown, never saved.
- **A page a CDN rewrote.** A page whose bytes differ from the list, for example because Cloudflare obfuscated an email address in it, is stored only while it keeps this build's mark, and STATUS reports it under `rewritten`. Any other changed file is refused. Every file the worker fails to save while installing, or when a page asks it to, is reported under `failed` with the reason.
- **How a reader saves the whole book.** The footer of every page holds a "Save the manual for offline reading" control, `public/scripts/save-offline.js`. It sits in the footer because saving concerns the whole book, not the chapter on screen, and the footer is on every page, the offline page included. It shows the build's size from `/offline-manifest.json`, which it fetches past every cache, and the room `navigator.storage.estimate()` reports. A press on Save sends `SAVE_ALL`, and the worker downloads every listed file it lacks, six at a time, checked like any other store. A progress bar follows the download, and the control then shows "Saved on <date>, version <first 8 digits of the build id>" and a Remove button. The date lives in the worker's cache beside the files, so a copy the browser evicts shows as not saved when the page loads again.
- **A save that stops early is partial, never saved.** The worker counts a copy as saved only once every listed file is stored. A full quota, a dropped connection, a file from a newer deploy or a press on Cancel leaves a partial record, and the control shows "Partly saved" with the reason and Try again. A second save skips the files already stored. If the browser stops the worker mid-save, the control notices once 15 seconds pass with no progress and shows the copy as partial. Remove keeps the shell, so the book still opens, and deletes every other saved file. An older build's cache that an open tab still reads stays until that tab closes. Remove also marks every other build's cache, so a build that is waiting, or one installed later, never offers the removed copy back. A copy saved again after the Remove still carries over.
- **Where the control does nothing.** It says so, and offers no button, in a browser without service workers, on a host that does not register the worker, with storage turned off, after a failed install, on a page the worker does not control yet and when the worker does not answer. When a new build is waiting or deployed, it asks for a Reload first. After the update, an older saved copy offers "Update the saved copy", which downloads only the changed files. The control never downloads or reloads by itself, and it does not call `navigator.storage.persist()`, because Firefox answers that call with a permission prompt the reader did not ask for.
- **How an update reaches the reader.** The new build's worker installs in the background and waits. `public/scripts/offline.js` shows "A new version of the manual is ready" with Reload and Not now. Only Reload asks the waiting worker to take over and reloads the page. Another open tab offers the same Reload. Until it is pressed, that tab's page keeps getting its own build's files from the older cache, which the new worker keeps while such a page is open and deletes once none is.
- **Where the worker runs.** `offline.js` registers the worker only on a host that the page's `<meta name="manual-offline-hosts">` names, and the build writes only the `site` host from `astro.config.mjs` there. A preview at `pr-<n>.manual.buildanagent.fyi` registers nothing, and it unregisters any worker and deletes any `manual-` cache an earlier visit left. `MANUAL_OFFLINE_TEST_HOST` adds `127.0.0.1` or `localhost` for the browser check, and the build refuses any other value.
- **Its headers and icons.** `public/_headers` sends `/sw.js` and `/offline-manifest.json` with `Cache-Control: no-cache` and the manifest as `application/manifest+json`. The policy's `manifest-src 'self'` lets the browser read the manifest. `public/manifest.webmanifest` lists a 192 and a 512 pixel icon and a maskable 512 pixel one, and every page links a 180 pixel apple-touch icon. `pnpm --filter @buildanagent/manual icons` draws them from `public/favicon.svg` and records the favicon's hash, so an edit to the favicon fails `test/offline-assets.test.ts` until the icons are drawn again.

The page and the worker exchange six messages, which the ADR lists with their replies. `STATUS` reports the build, what the cache holds, the saved or partial copy, a running save, and the rewritten and failed files. `SKIP_WAITING` comes from the notice's Reload, and `SAVE_PAGE` from a page the worker did not control. `SAVE_ALL`, `CANCEL_SAVE` and `REMOVE_ALL` come from the save control. The worker answers only a tab or window of its own origin, never a frame or another worker.

### Check a deploy once it is live

After a deploy, run `pnpm --filter @buildanagent/manual offline:verify https://manual.buildanagent.fyi`. It fetches the deployed `/offline-manifest.json` and every file it lists, and compares each with its recorded size and SHA-256, a page with its mark set back to the placeholder. A page that a Cloudflare feature such as Email Address Obfuscation rewrote but that keeps the build's mark is listed as rewritten. The worker still saves that page, but the feature should be turned off for the host. Any other difference, a missing file or a `/sw.js` of another build makes the command fail, because the worker would refuse that file. To clear readers' saved copies after a bad deploy, ship a new build: its worker replaces the old one and deletes the old cache. To withdraw the feature, ship a `/sw.js` that deletes every `manual-` cache and unregisters itself, because deleting `/sw.js` leaves installed workers in place.

## The book deploys from main's workflow, and a pull request only ever gets a preview

GitHub Actions publishes the book, not Cloudflare's own Git integration. Two workflows split the work so that no pull request can change a job that holds a Cloudflare token ([book plan BK15](../../docs/plans/build-book.md#bk15-an-assets-only-worker-on-a-custom-domain-behind-a-guard-and-a-switch-proposed)). First, `book-build.yml` builds the site with no secrets on every pull request and every push to `main`, and uploads `dist/` as the `book-dist` artifact. Second, `book-deploy.yml` runs after each build finishes. GitHub always runs that second workflow from the file on `main`, so editing it on a branch changes nothing until the branch merges.

`book-deploy.yml` never checks out or runs a pull request's code. It takes the artifact and the build's commit SHA from the triggering run, and everything else from `main`: `wrangler.jsonc`, `public/_headers`, the scripts and Wrangler itself. It has six jobs. `resolve` runs first and decides which of the three deploy jobs runs. Two comment jobs then follow the preview and its deletion:

1. **`resolve`** names no environment and holds no Cloudflare secret, so it has no secrets check. It asks GitHub's API whether a push is still `main`'s newest commit, which open pull requests from a branch of this repository have the build's commit as their head, or which closed pull request a `book-pr-closed` run belongs to. If the API call fails, the job fails and nothing deploys.
2. **`production`** deploys to manual.buildanagent.fyi with `wrangler deploy`, from the `book-production` environment. It runs only for a push to `main` from this repository, only while the variable `BOOK_DEPLOY_ENABLED` is `true`, and only for `main`'s newest commit. A fork's branch named `main` never reaches it, and a running deploy is never cancelled.
3. **`preview`** runs `wrangler preview --name pr-<number>` from the `book-preview` environment, for each open pull request whose head is the build's commit and whose branch lives in this repository. The preview is served at `https://pr-<number>.manual.buildanagent.fyi`, and each commit's deployment also gets its own address, `https://<deployment id>.manual.buildanagent.fyi`, where the id is 8 lowercase hex digits, such as `https://40f313de.manual.buildanagent.fyi`. Cloudflare's docs give `<deployment id>-<preview name>` instead, but Wrangler 4.160.1 printed the shorter form for the first preview, so the workflow accepts only the shorter form. If the preview job warns that Wrangler reported the preview's URL but no commit URL of that form, Cloudflare has changed the id's form. Update the pattern to match in both places in `book-deploy.yml`, the record step and the comment script. A push to `main` gets no preview, because it already deploys production or is held back on purpose. Preview URLs are public, like the book.
4. **`delete-preview`** runs `wrangler preview delete` from the `book-preview` environment when a pull request closes.
5. **`comment`** and **`comment-deleted`** keep one comment on the pull request with the preview's addresses, as [the comment section](#each-previews-addresses-go-into-one-comment-on-its-pull-request) describes.

Each pull request has its own queue, shared by its previews and its deletion. A preview and its deletion therefore never overlap, and no other pull request's run can replace one that is waiting.

A fork's pull request gets no preview and no comment. A preview job holds a token that can also deploy the production Worker, and a fork's artifact holds whatever the fork wrote, so the book previews only branches of this repository, whose authors can already push to it (the owner's decision, 2026-11-19). To preview a fork's change, a maintainer pushes it to a branch here and opens a pull request from that branch.

Before Wrangler runs, `scripts/stage-dist.mjs` checks the artifact, because a pull request's build may have put anything in it. The script reads the zip itself and refuses the whole artifact if an entry escapes `dist/`, is a symbolic link or a dot file, is a file Cloudflare reads as configuration (such as `_redirects`), or breaks Cloudflare's limits of 25 MiB per file and 20,000 files. It skips the artifact's own `_headers`, refuses a `_headers` directory, and writes `main`'s copy in its place. For a preview, it runs with `--preview` and adds `X-Robots-Tag: noindex` to that copy's `/*` rule, because Cloudflare adds the header to `workers.dev` previews but not to previews on a custom domain. Production never gets it.

Next, `scripts/guard-deploy.mjs` refuses a deploy unless seven rules hold. Six are settings in `wrangler.jsonc`: exactly the one custom-domain route with `previews_enabled: true`, no `main`, `assets.directory: "./dist"`, `not_found_handling: "404-page"`, `workers_dev: false` and `preview_urls: false`. `preview_urls: false` keeps every preview off `workers.dev`. The seventh rule is that `dist/_headers` matches `public/_headers`, or, with `--preview`, matches it plus the one `X-Robots-Tag` line. Without `--config`, Wrangler looks for a `wrangler.json` in this directory and every one above it before it reads `wrangler.jsonc`, so every Wrangler call passes `--config wrangler.jsonc`. The guard also refuses when any other Wrangler config, or a `.wrangler/deploy/config.json` redirect, sits in `apps/manual/` or a directory above it. The guard is adapted from the owner's garment engineering textbook and is licensed Apache-2.0 only ([THIRD-PARTY-NOTICES.md](../../THIRD-PARTY-NOTICES.md)).

Deleting a preview needs a third workflow, `book-pr-closed.yml`, because GitHub runs a `pull_request` workflow from the pull request's merge commit, so an unmerged branch supplies the file. A job there that held the preview token would run whatever a branch wrote into it, and a fork's run gets no secrets, so a fork's preview would never be deleted. `book-pr-closed.yml` therefore holds no secret and does nothing but finish. Its run starts `book-deploy.yml` from `main`, which finds the closed pull request through the API and deletes its preview.

Every page gets the headers in [`public/_headers`](public/_headers). The content security policy allows only the book's own origin: scripts, styles, fonts, fetches and Pagefind's worker all come from it, and no inline script or style runs. Pagefind's search also needs `'wasm-unsafe-eval'` to compile its WebAssembly, and `data:` images for its search icon. `Strict-Transport-Security` keeps browsers on HTTPS for a year, for manual.buildanagent.fyi and any name under it, the previews included; it leaves out `preload`. Files under `/_astro/`, whose names carry a content hash, are cached for a year.

**A preview runs its branch's own code in the browser.** Each preview is served on its own hostname under manual.buildanagent.fyi, so its scripts run on an origin apart from the book's. The book sets no cookies and has no sign-in, so a preview's script finds nothing of the book's to read.

### Each preview's addresses go into one comment on its pull request

After a preview deploys, the pull request gets a comment from `github-actions[bot]` that holds three things: the short SHA of the commit it shows, the preview's address, `https://pr-<number>.manual.buildanagent.fyi`, and that commit's own address. The preview's address follows the pull request's newest commit; the commit's own address keeps showing that commit. Each later preview edits the same comment instead of adding one. When the pull request closes and its preview is deleted, the comment changes to say the preview is gone. The comment carries no `workers.dev` address and so no part of the Cloudflare account's subdomain.

The URLs pass from the preview job to the comment job with no new permission for the job that holds the token:

1. Wrangler writes what it deployed, as JSON lines, to the file that `WRANGLER_OUTPUT_FILE_PATH` names. A step with no secret then keeps only the two URLs of the exact forms above and uploads them as the artifact `book-preview-urls-<number>`, one per pull request, because a matrix job's outputs would overwrite each other. A failed preview uploads nothing, so the comment never shows an old address as new.
2. The `comment` job holds `pull-requests: write` and nothing else: no environment, no secret, no checkout. It downloads that artifact, checks both URLs again, and writes only while the pull request is open with this commit as its head. It edits only a comment that `github-actions[bot]` wrote and that starts with the hidden marker `<!-- book-preview -->`, so a person's comment that quotes the marker stays as it is.
3. `delete-preview` uploads `book-preview-deleted-<number>` only when its deletion worked, and `comment-deleted` then edits the comment. It never creates one.

The comment's text is fixed in the workflow, and nothing in it comes from the pull request: no branch name, no title. Every failure in the comment script warns and stops without failing the run, so a comment never holds up a deploy.

## What the owner sets up

The owner creates every piece below; the workflows only use them, by these exact names. Until a piece exists, the job that needs it stops at its first step, which names the missing secret and links here. This repository can therefore merge the workflows before the setup is done.

| Where | Name | What it holds or allows |
| --- | --- | --- |
| Cloudflare | the `buildanagent.fyi` zone | In the account both tokens belong to. `manual.buildanagent.fyi` must have no CNAME record, because Cloudflare refuses a custom domain on a hostname that has one. No DNS record or certificate is needed for the previews: Cloudflare creates the wildcard record and certificate for `*.manual.buildanagent.fyi` itself |
| Cloudflare | the Worker `buildanagent-manual` | Created once by hand, or by one first deploy with a short-lived token that has Workers Admin. Workers Editor cannot create a Worker, so neither stored token needs Admin |
| GitHub environment | `book-production` | Deployment branches: protected branches only, which here means `main`. Secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` |
| GitHub environment | `book-preview` | Deployment branches: protected branches only, which here means `main`. Secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`, its own token |
| Production token, in `book-production` | An account-owned API token | Account › Workers › Editor, plus Zone › Workers Routes › Write on the `buildanagent.fyi` zone. The zone permission is needed whenever a deploy changes the custom domain, which includes the first deploy with `previews_enabled`; between such changes it can be removed |
| Preview token, in `book-preview` | An account-owned API token | Account › Workers › Editor, scoped to the Worker `buildanagent-manual`, with no zone permission. Creating a preview on the custom domain changes no domain setting |
| GitHub repository variable | `BOOK_DEPLOY_ENABLED` | `true` turns production deploys on |

`CLOUDFLARE_ACCOUNT_ID` is the ID of the account that owns the zone and the Worker. Both tokens are account-owned, because Wrangler needs that kind for per-Worker permissions. Cloudflare's [Workers roles](https://developers.cloudflare.com/workers/authorization/workers/) page lists what each role allows.

**`book-preview` must allow protected branches only, like `book-production`.** Its token holds Editor on the book's Worker, which can also deploy to production. Without the rule, any workflow on a branch of this repository could name `book-preview` and read that token. `book-deploy.yml` runs from `main`, so the rule leaves its previews working. The owner set it on 2026-11-19.

One risk remains, accepted: the preview job handles a branch's artifact while it holds that token. Cloudflare's Workers roles have no permission for previews alone, so the token could also deploy the production Worker. Only branches of this repository get a preview, so only people who can already push here can supply that artifact. The artifact check, the guard and `main`'s own Wrangler also stand between the artifact and the token, and no code from the artifact ever runs in the job.

Before the first deploy, check by name that each environment holds both secrets and that both allow only protected branches. Then watch the first production deploy and one pull request's preview: the site should serve the book with the `_headers` values, and the preview should carry `X-Robots-Tag: noindex`.

**Custom-domain previews start with the next production deploy.** `previews_enabled` and `preview_urls: false` change the Worker's settings, and only `wrangler deploy` sends them; `wrangler preview` does not. Until the production job runs once with this config, previews deploy with no address on manual.buildanagent.fyi, the preview job warns, and no comment appears. To turn them on:

1. Give the production token Zone › Workers Routes › Write on `buildanagent.fyi`, if it was removed.
2. Set `BOOK_DEPLOY_ENABLED` to `true`, if it is not, and push to `main` or rerun the latest `book-deploy` run for `main`. The deploy prints a note that the previews' DNS and certificate may take a few minutes.
3. Open a pull request from a branch of this repository and check that the comment's two addresses serve the book with `X-Robots-Tag: noindex`.

The first preview on the custom domain, pull request #89's on 2026-11-19, served both of its addresses with `noindex`.

The same deploy turns off the old `workers.dev` previews. Any still listed stop serving there. A branch's old preview is deleted when its pull request closes, and a fork's, which the workflow no longer deletes, goes when Cloudflare's limit of previews per Worker removes the least recently deployed one.

**To pause production,** set `BOOK_DEPLOY_ENABLED` to anything other than `true`, or delete it. Pushes to `main` still build the book and pull requests still get previews; the `production` job is skipped until the variable is `true` again.
