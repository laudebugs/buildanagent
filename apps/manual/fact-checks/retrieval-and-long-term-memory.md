## The research question, answered before drafting

**Question** (set by U18). When should an agent retrieve instead of carrying context, and how should memory that outlives a task be written, recalled and forgotten?

**Answer, from the todo's sources only.** An agent should carry a small, stable core in every request (its instructions, an index of what it remembers and its most-used tools) and fetch everything else through a tool when a step needs it. Long inputs degrade well before the window fills, and a prompt cache makes carried text cheap only while it stays unchanged ([U18's report](../../../docs/research/memory/retrieval-and-memory.md#carry-the-small-stable-core-and-retrieve-the-rest-when-a-step-needs-it); [main report](../../../docs/research/agent-sdks-and-harness-design.md), layer 5, "just-in-time retrieval by reference"). The first retriever should be keyword search, BM25 or grep, because BM25 stays a strong baseline outside a dense model's training domain; vectors join after a measured miss and are fused with the keyword list, for example by reciprocal rank fusion at k = 60, because the two fail on different queries (U18, "Start with keyword search"). Retrieved text is untrusted input, so the tenant filter runs inside the retriever, before ranking, as OWASP LLM08 asks of a "permission-aware" store. A retriever is measured on its own, with recall@k on 20 to 50 labelled queries, some of which should return nothing (U18, same section). Memory that outlives a task is best kept as small, typed records, each with its source, written through an explicit tool and recalled through a short index plus search. A recalled record is a claim about the past, so the agent checks it against its source before acting on it, as Copilot checks a memory's citations. A record is forgotten by an expiry that only a successful check renews, and deleting it reaches every copy only if the harness makes it, since a session log keeps the write (U18, "Long-term memory works best as sourced records"; [main report](../../../docs/research/agent-sdks-and-harness-design.md), layer 6). What to store has two primary answers in the papers: Reflexion keeps a verbal lesson from a failed attempt, and Voyager keeps a verified skill as code ([agent research papers](../../../docs/research/papers/agent-research-papers.md#our-loop-already-is-a-react-loop-later-papers-add-layers-around-it-not-a-rival-architecture)). A directory of files is enough for one agent and one user, and a service earns its price on one of three signals: many end users each needing an isolated profile, recall across thousands of records, or temporal questions (main report, layer 6).

**The one-line rule the chapter teaches.** Carry pointers and search for the rest with keywords first, filtering by tenant before ranking; keep lasting facts as sourced records that the agent checks before trusting and that expire unless a check renews them.

**Gaps.** No source measures how a real model behaves on the T41 fixture, so the chapter claims only what the scripted runs show: which documents reach the model. No example fuses keyword and vector lists, so the fusion paragraph cites its paper and says so. No source measures recall on a labelled set of our own agents' queries, so the chapter teaches how to build that set and reports no figure for it.

## Register entries, analogies and outline, before drafting

**Sources.** The chapter cites register entries in this order: `anthropic-effective-context-engineering`, `modarressi-nolima`, `anthropic-pricing`, `anthropic-prompt-caching` and `buildanagent-harness-plan` in the first section, and the entries each later section adds, which its rows list. **Analogies vetted.** The todo's three analogies are all used, and none is in `analogies.json` yet:

- *Retrieval: a reference librarian who fetches the few books you need.* It explains fetching a few relevant items from a large stock on request, and the choice among them. It is close in image to Chapter 13's hardware-store back room (deferred tools), but that clerk fetches a named item, while the librarian judges which items fit a question, which is the ranking this chapter is about, so the two explain different concepts. Its break note, that "the librarian's choice is a search ranking, and a wrong ranking looks just as confident", names the failure the second section measures. It gets the flat illustration the todo requires.
- *Long-term memory: a card file of contacts updated after every meeting.* It explains records written after an event and read in a later one, distinct from Chapter 5's patient's chart, which is one patient's record across shifts, the session. Its break note, that "a model may write a wrong card and later trust it, so writes need rules", is MINJA's attack (row group § Long-term memory).
- *Forgetting: an office shredding schedule.* It explains forgetting by a rule set in advance. Its break note, that "deleting a fact from memory does not delete it from logs or caches unless the harness does", is what T43's example runs.

**Outline**, with the opening type `scenario`, which differs from Chapter 11's `analogy`:

1. *Opening:* a support agent meets three questions in one week, one that needs a document, one that matches nothing and one that needs a memory that may be stale.
2. *Carry a small, stable core, and fetch everything else through a tool when a step needs it:* the librarian, NoLiMa's degradation, the cache's price, our four-part carry rule, our harness's pointers and T41's search tool with its replay.
3. *Rank with keywords first, filter by tenant before ranking, and measure the retriever on labelled queries:* BM25 and its failures, vector search and LIMIT, fusion without a listing, OWASP LLM08, the filter-before-rank check, the planted document with PoisonedRAG and BadRAG, and recall@k.
4. *Store a lasting fact as a sourced record, check it before acting on it, and let it expire unless a check renews it:* the card file, what to store (Reflexion, Voyager, Copilot), writes need rules (MINJA), recall through an index and search (Cloudflare's context blocks), the check before use, and the shredding schedule with T43's expiry and the session log.
5. *A directory of files is enough for one agent and one user; buy a service on one of three signals:* the main report's three signals, our harness's file-based memory, and the stores our SDKs already give.
6. *Exercises:* the todo's store, recall and expire exercise; a labelled query set; and fusion on paper.
