# Fact-check: Use the least autonomy that works: a call, a workflow, then a loop

The claims log for [`call-workflow-loop.md`](../src/content/chapters/call-workflow-loop.md), checked section by section as each was drafted (BK21). Each row names the claim, the section it sits in, the verdict and the primary source. Pages were read on 2026-11-19; package claims are checked against the harness pins of that date: `ai@7.0.162`, `@google/adk@2.5.0` and `@earendil-works/pi-coding-agent@1.5.2`.

## The research question, answered before drafting

**Question.** When does a single model call do the job, when does a fixed workflow, and what makes a task need an agent loop?

**Answer, from the todo's sources only.** One call does the job when the model can finish the task from what one request carries. Anthropic's advice is to start there: "finding the simplest solution possible, and only increasing complexity when needed", because "optimizing single LLM calls with retrieval and in-context examples is usually enough" for many applications ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). A fixed workflow fits when the steps are known before the run starts. Anthropic defines workflows as "systems where LLMs and tools are orchestrated through predefined code paths" and recommends them for "predictability and consistency for well-defined tasks"; prompt chaining, the simplest of its five patterns, suits a task that "can be easily and cleanly decomposed into fixed subtasks" (same post). A task needs an agent loop when nobody can write the path down in advance: when the next step depends on what the last tool returned. Anthropic's agents "dynamically direct their own processes and tool usage" and suit "open-ended problems where it's difficult or impossible to predict the required number of steps, and where you can't hardcode a fixed path" (same post). Our agent guide turns this into four questions asked in order, the first "yes" setting the shape ([agent guide §2](../../../docs/guides/agent.md#2-choose-the-least-autonomy-the-task-allows-a-workflow-in-code-with-one-bounded-loop-for-the-ambiguous-middle)). The loop itself is the same in every SDK we verify: "a model calls tools in a loop until a stop condition holds" ([feature table](../../../docs/comparison/feature-table.md)), and the SDK guide adds that a loop should be capped in model calls and end with a stop reason ([SDK guide §3](../../../docs/guides/agent-sdk.md#3-the-loop-should-be-one-in-process-pure-function-capped-in-model-calls-that-ends-with-a-stop-reason)).

**The one-line rule the chapter teaches.** Ask who decides the next step. If your code can decide it before the run, write a call or a workflow; if only the model can decide it, after reading a tool's result, write a loop and cap it.

**Gap.** The sources give no measured comparison of a workflow and a loop on one task with the model held fixed; the agent guide names that gap too ([agent guide §2](../../../docs/guides/agent.md#2-choose-the-least-autonomy-the-task-allows-a-workflow-in-code-with-one-bounded-loop-for-the-ambiguous-middle)). The chapter therefore states the choice as our recommendation and claims no measured gain for either shape.
