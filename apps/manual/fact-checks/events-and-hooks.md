## The research question, answered before drafting

**Question.** How should an SDK expose what happens inside a run, and where may outside code change it?

**Answer, from the todo's sources and the pinned docs only.** An SDK should give a run two separate surfaces. The first is a stream that only describes the run. The four SDKs read here converge on its shape: partial events for a live display and one authoritative end event per message that a log keeps, with Pi's `message_end` ("the authoritative final message") and Copilot's persisted `assistant.message` beside ephemeral deltas ([Pi JSON event stream](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/json.md), [Copilot streaming events](https://github.com/github/copilot-sdk/blob/v1.0.31/docs/features/streaming-events.md)). Copilot's own union also shows why the stream must be closed: its runtime emitted ten event types that the typed `SessionEvent` union omitted ([Copilot fact-check F6](https://github.com/laudebugs/buildanagent/blob/2174e4c/docs/reference/copilot-sdk/fact-check.md)). The second surface is a small set of moments where code may change the run: before and after a tool call (Copilot's `onPreToolUse` and `onPostToolUse`, LangChain's `wrapToolCall`, ADK's before and after tool callbacks, Pi's `tool_call` and `tool_result`) and before and after a model call. Across all four, a hook that returns nothing changes nothing and a hook that returns a value replaces the step or its result, so the same function can watch or change the run depending on its return value. Only our SDK gives watching its own type, with a frozen copy of each event and a failure that becomes an event instead of a failure of the run.

**Gap.** None of the four SDKs' docs says what happens to a run when a listener of the event stream throws, so the chapter makes no claim about it for Pi, Copilot, LangChain or ADK.
