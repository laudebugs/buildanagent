You are ten, holding a choose-your-own-adventure book, and on page 14 you open the cave door. Page 31 says the troll eats you. You keep a finger in page 14, flip back and take the tunnel instead. When you close the book, every path is still printed in it, the troll's page included, and a friend who opens it tomorrow can follow any of them.

A harness's session log works like :analogy[that book]{#adventure-book}. [[ch:memory-and-sessions]] treated a session as a chart that one run writes and the next run reads. This chapter opens the chart and looks at its pages. Each page is an entry that names the entry it follows. In Pi, going back to an earlier entry writes nothing, and the next entry written there starts a second path beside the first. The book differs in who turns the pages: here the harness or the user forks, every path stays readable to them, and the model sees only the path being followed.

By the end of the chapter you can say why one append-only tree of typed entries is the right shape for a session log, how a layered context policy shortens what the model sees without deleting an entry, and how a long task outlives any one window by keeping its state in files. Exercise 1 has you fork a session, compact one branch and show that the other is unchanged; Exercise 2 then undoes the compaction. Our harness builds the log and the first two context layers; the other three layers and the progress-file hook are design, not shipped.

## One append-only tree of typed entries keeps every path, so going back erases nothing

Pi, a coding-agent harness, stores a session as a JSONL file with one JSON object per line, and it links the lines into a tree: every entry carries an `id` and a `parentId`, so a new branch needs no new file [@pi-session-format]. [[lst:session-tree-pi]] builds a two-branch tree from three scripted answers.

:::listing[Branching from the first answer leaves both paths in the session]{#session-tree-pi file="verify/pi/examples/05-session-tree.ts" region="tree" replay}
::note[`getLeafId()` returns the id of the entry that the next prompt will follow. Pi calls it the leaf, the current position in the tree. After the first answer, it names that answer.]{#first-answer}
::note[`branch()` moves the leaf back to an earlier entry and writes nothing. Pi's own comment says "Existing entries are not modified or deleted."]{#branch}
::note[Two entries now name the first answer as their parent: the abandoned "Refine it." and the new "Try something else.". That is a fork.]{#children}
:::

The replay shows what the model receives. The second request resends the system prompt, the first question and the first answer, then adds "Refine it." The third request, sent after `branch()`, resends the same three messages and adds "Try something else." It carries neither "Refine it." nor "Refined plan A.". Both are still in the session's entries (checks on lines 28 to 31), and the model's own path leaves them out (line 32). Pi's guide says it in two sentences: "Pi stores entries as a tree, so returning to an earlier point does not erase the branch you leave", and "The model receives the active branch, not every branch in the session file" [@pi-sessions].

A tree of messages alone would not be enough, because messages are only one of Pi's entry types. The file also holds `model_change`{checked=row-3}, `thinking_level_change`{checked=row-3} and `usage`{checked=row-3} entries, and three that later sections use: `compaction`{checked=row-3}, `context_edit`{checked=row-3} and `branch_summary`{checked=row-3} [@pi-session-format]. Each of those three adds history instead of rewriting it. A `context_edit`{checked=row-3} hides an earlier entry from the model's context while "the target entry and its metadata remain unchanged in raw history", and its edits are "branch-relative: navigating to a point before the edit reveals the target's original contribution again" [@pi-session-format]. Typing the entries pays off in reversal: to undo a change, you choose a path that does not include it.

Our harness takes the same shape and makes it stricter. Every entry in its log carries an `id`, a `parentId`{checked=row-10}, a position number `seq`{checked=row-10}, a timestamp, a `type`{checked=row-10} and an `origin`{checked=row-10} that says whether the user, the operator, the model, a tool or the harness produced it [@buildanagent-harness-readme]. One model call writes one `message_block`{checked=row-11} entry for each content block, then a `message_end`{checked=row-11} and a `usage`{checked=row-11} entry. A finished tool call writes a `tool_result`{checked=row-11} entry, and streamed deltas reach live clients but are never stored. The per-block grain lets a tool result sit between two calls of one message, which a per-message line cannot do [@buildanagent-harness-plan]. As of November 2026 the plan keeps that grain provisional until a test compares per-delta, per-block and per-message logs.

Why keep every entry instead of the winning path? Two recent papers bear on the question, and neither settles it. Hou and colleagues argue that datasets of agent output keep patches and commits but structurally cannot hold failed retries, fallbacks or abandoned sessions [@hou-messy-middle]. Theirs is a six-page position paper whose only evidence is one 93-day deployment, which the authors call "a design probe, not a validation study". Wong computes governance metrics from an append-only ledger in which a control plane writes every trial, over six tasks and 1,445 trials [@wong-governed-ml]. Neither paper tests a session tree. In our reading, a log that keeps abandoned paths and retried calls holds the record they say is missing, and our harness writes a `usage`{checked=row-18} entry for each retried model call, so a retry shows in a session's cost even when its text does not [@buildanagent-harness-readme].

A tree that never deletes makes the next two sections possible. A fork is one more child of an old entry, and a compaction is one more entry on a path.

## HEAD, a fork and a writer lock make the tree something any process can resume

A tree needs a bookmark for where the next entry goes. Call it HEAD, after git's word: HEAD is the entry that the next append follows. Pi keeps its version, the leaf, in memory only. When Pi loads a file, it sets the leaf to the last entry in file order, and `branch()` writes nothing, so a branch you start and abandon before any new entry is gone when the file loads again [@pi-session-manager]. Our harness writes HEAD into the log instead. Its `checkout`{checked=row-20} call appends an entry that names the entry to go back to, and a reload replays the entries, so HEAD comes back where it was left [@buildanagent-harness-readme]. An entry appended after a checkout follows the checked-out entry, and the branch you left stays in the file.

Moving HEAD stays inside one file. A fork or a revert leaves it. Pi gives the reader both choices: `/tree` "moves within the current session file", and `/fork` "creates a new session from an earlier user message" [@pi-sessions]. Our harness writes a new file for a fork and for a revert, so no write ever edits an old file. [[tbl:head-moves]] lists what each move writes.

:::table[What a checkout, a fork and a revert write in our harness]{#head-moves}
| Move | Writes | Leaves unchanged | Afterwards |
| --- | --- | --- | --- |
| `checkout`{checked=row-20} | One `checkout`{checked=row-20} entry in this file | Every earlier entry | The next entry follows the checked-out entry |
| `fork()`{checked=row-22} | A new file: a header that names this file and the entry as its parent, and a `checkout`{checked=row-20} of that entry | This session, entirely | The fork is a session of its own, whose path crosses into the parent's file |
| `revert()`{checked=row-23} | A new file of the same kind, then a move of the session's pointer to it | The old file, which keeps every entry | This session goes on from the entry, and the entries after it leave its tree |
:::

A fork shares its prefix with its parent and never copies it. The new file holds only a header and a `checkout`{checked=row-20}, and the fork's `path()`{checked=row-22} reads from the root through the parent's file up to the fork point, while an entry the parent writes later is not part of it [@buildanagent-harness-readme]. A revert goes the other way. It keeps the old file as it was and points the session at the new one. That pointer is the only mutable state in the design, and a crash before it moves leaves the old file in use.

Two writers can fork a tree by accident. Suppose a scheduled job and you both resume the same session in the same minute, and each appends to the tail it last read: the file would hold two answers to one question, a fork nobody chose. Pi's session manager takes no lock, so that race is yours to prevent. In our harness one writer at a time holds a session. `acquire()`{checked=row-26} creates `<session>.lock` with the exclusive-create flag and records the holder's process id, host, a token and a lease. If a second writer tries, it gets `"would_block"`{checked=row-26} at once and never waits. The holder renews its lease, 30 seconds by default, every 10 seconds; a lock counts as stale only when the lease has lapsed and, on the same host, the process is gone [@buildanagent-harness-readme]. Readers never lock, and network file systems are unsupported because an exclusive create is not reliable on them. The store adds a second guard: an append names the entry the log must end with, so a writer holding a stale view throws a `ConflictError`{checked=row-28} and writes nothing.

The lock keeps writers apart, and resume lets a different process pick up where one stopped. [[ch:memory-and-sessions]] showed that a resume brings back only what was saved. Cloudflare Agents shows the same rule from the other side. Its guide says an idle agent leaves memory after about ten seconds without a message while its WebSocket clients stay connected, and that the agent's state and SQLite rows persist while its in-memory variables do not [@cloudflare-agents-websockets]. [[lst:hibernation]] evicts an agent and wakes it with a message.

:::listing[An evicted agent wakes with its state and its connection, and without its memory]{#hibernation file="verify/cloudflare-agents/examples/08-hibernation.ts" region="evict"}
::note[`h.evict()` evicts the Durable Object through Miniflare, the local Workers runtime, so the agent leaves memory as an idle one does. The WebSocket stays open.]{#evict}
::note[The `onStart`{checked=row-30} hook ran a second time: a new instance replaced the old one.]{#restarted}
::note[The class field `memory`, set to 42 before the eviction, is back at 0.]{#memory-reset}
::note[`this.state`{checked=row-30} came back from storage, because `setState`{checked=row-30} had saved it there.]{#state-reloaded}
::note[A message sent over the same WebSocket reaches `onMessage`{checked=row-30} on the new instance.]{#still-open}
:::

The listing's lesson is the rule our harness follows: keep nothing in memory that the log lacks. Everything the agent needed after the wake, its topic and its connection, sat in storage, and what sat only in a class field was gone. Our harness applies that to a run. `session.toContext()`{checked=row-31} rebuilds the SDK's context from the entries between the root and HEAD, the messages in order and the system prompt of the latest turn, byte for byte, and its result deep-equals the context of the run that wrote the log. A turn that passes no history takes it from the log, so a new process goes on from the file alone [@buildanagent-harness-readme]. `runTurn()`{checked=row-33} writes the user's input before the first model call, so a turn that dies at once still leaves the question in the file. A crash can also leave a tool call without a result. The next turn settles it before anything else: a call to a tool that writes gets an `unknown` outcome and the instruction to check before retrying, because the write may have happened, and a call to any other tool gets an error that says it was interrupted.

## Context policy runs five layers, cheapest first, and none of them deletes an entry

Your desk holds a laptop, two folders and a coffee, and everything else you own sits in the drawer. A delivery of boxes arrives; whatever does not fit goes back in the drawer, and nothing reaches the desk unless someone carries it. :analogy[That desk with limited space]{#limited-desk} is a model's context window. Anthropic calls context "a finite resource with diminishing marginal returns" [@anthropic-effective-context-engineering], so more on the desk does not mean better work. Each turn the harness rebuilds the context from the session log, and the context policy is the code that decides which entries make it onto the desk. The model can read only what lands there.

:::figure[A desk with limited space: the harness decides what sits on it, and the model reads only the desk]{#limited-desk analogy="limited-desk"}
::svg{alt="On the left, a box labelled session log, the drawer, every entry, with a note under it that the model cannot open the drawer. An arrow labelled harness decides runs from it to a large box on the right, the desk, which is the context window and holds three cards: system prompt, summary of earlier work and recent messages. An arrow runs from the desk down to a box labelled model reads the desk."}
:::

Our plan sets the policy as five layers ordered by cost, shown in [[fig:context-layers]]. The harness package builds the log, forks and writer lock of the last section, and its context component builds the first two layers, the write cap and masking, and none of the other three [@buildanagent-harness-context]. The numbers below are the plan's defaults, which it marks provisional until an ablation run tests each layer on and off [@buildanagent-harness-plan].

:::figure[Five context layers, cheapest first: the first two write no summary entry, the last three add one]{#context-layers}
::svg{alt="A table of five rows with three columns. Layer 1, write cap: cap a tool result at 64 KiB and spill the rest to a file; the log gets the capped result and a file path. Layer 2, mask: show older tool results as 500 characters, in steps; the log gets nothing, because it is a view built at read time. Layer 3, summarize: between turns, replace old messages with a summary; one compaction entry. Layer 4, mid-turn: the same, when one step reaches 90 percent of a window under 128K tokens; one compaction entry. Layer 5, overflow retry: on a provider overflow error, compact once, then retry; one compaction entry. A note says the layers run cheapest first, from the top down."}
:::

The two cheap layers write no summary entry, and our harness builds both. Layer 1 caps a tool result when the harness writes it and spills the full text to a file. The model reads the first part and a line that names the file, and the stored entry holds the same cut text and the file's path; if the spill store cannot write, the text is still cut, and the notice says the rest was not kept [@buildanagent-harness-context]. The cap counts the bytes the entry takes in the log, with JSON escaping, plus 1 KiB for the entry's own fields, so a capped result is a little under 64 KiB of plain text. With the default cap and the store's default bound, the store, which refuses an entry over 64 KiB, never has to refuse it [@buildanagent-harness-context][@buildanagent-harness-readme]. Layer 2 shows older tool results as their first 500 characters and a pointer line, moving the cutoff only every eight messages so that the cached prefix stays stable, and it never edits the log. There is one exception for a model that thinks inside a tool loop: while the loop holds signed thinking, the cutoff is computed as though the transcript ended where the loop began, so it stops moving and nothing in the loop is masked, and the loop's own thinking blocks stay valid; the view leaves out the signed thinking of earlier turns that follows the first masked result [@buildanagent-harness-context]. Anthropic's guide names its closest relative: "One of the safest lightest touch forms of compaction is tool result clearing" [@anthropic-effective-context-engineering]. The three expensive layers all write a summary. Layer 3 fires between turns when the context passes a budget, which defaults to the smaller of the window minus 16,384 tokens and 200,000, and keeps a verbatim tail of about 20,000 tokens. Layer 4 fires when one step reaches 90% of the window, and by default only for windows under 128,000 tokens. Layer 5 answers a provider's overflow error with one compaction and one retry [@buildanagent-harness-plan]. Pi runs the same triggers: it compacts when the context passes the window minus a reserve of 16,384 tokens, keeps the latest 20,000 tokens, and on an overflow error compacts once and retries [@pi-compaction].

Why cheapest first? One study gives the order a measured basis, with limits. In SWE-agent on SWE-bench Verified, masking old observations matched LLM summarization's solve rate at about half the raw agent's cost [@swe-agent-observation-masking]. For Qwen3-Coder 480B, masking solved 54.8% of tasks at $0.61 each, summarization 53.8% at $0.64, and the raw agent 53.4% at $1.29. The result did not hold for every model. With thinking on, masking cut Qwen3-32B's cost by only 9.8%, and it lowered Gemini 2.5 Flash's solve rate by 9.9% against the raw agent. Each cell is one run of 500 tasks, and the authors warn that the finding "may not generalize to domains where agent-environment interactions are more succinct". We read it as a reason to try masking first, and the plan tests each of its five layers against a baseline.

### A compaction is an entry, so the recap stands in for the episodes and the episodes stay

You join a series at episode 11, and the first ninety seconds tell you what you missed. :analogy[That recap]{#previously-on-recap} stands in for ten episodes, and it has a cost: a person wrote it, and it can leave out the detail that matters tonight. Compaction does the same to a session. A model writes a summary of the older messages, the harness puts the summary where those messages were, and the next call reads the summary instead. The difference is where the episodes go. The recap on television replaces what you watched, while in a tree the summary is one more entry and the older ones stay in the file. [[lst:compaction-pi]] compacts a two-question session.

:::listing[A compaction appends one summary entry and the next request carries the summary, not the old messages]{#compaction-pi file="verify/pi/examples/06-compaction.ts" region="compact" replay}
::note[`compact()` asks the model to summarize. With the example's tiny `keepRecentTokens`{checked=row-45}, the cut falls inside the last user message's span, so Pi sends two summary requests and merges their answers.]{#compact}
::note[The result is one `compaction` entry on the path, which holds the summary and the first entry it keeps.]{#entry}
::note[The entry count rises by exactly one: no original entry is removed.]{#originals}
:::

The replay shows both halves. The two summary requests carry the conversation to summarize, each inside its own template. The history summary ends "Keep each section concise. Preserve exact file paths, function names, and error messages." The summary of the split turn's prefix ends "Only summarize information explicitly present above. Do not infer or recreate later messages." After the compaction, the next request opens with a message that begins "The conversation history before this point was compacted into the following summary:", then the summary, the latest answer and "Thanks." The checks on lines 42 and 43 confirm that the request holds the summary and omits "The capital of France is Paris.", though that answer still sits in the session. Pi's guide states the rule in one sentence: compaction "does not delete the original session entries" [@pi-sessions].

The recap can drop facts, so the original entries stay, and the harness can put any of them back on the desk. Our harness shapes its compaction entry for that. Besides the summary, it records which layer wrote it, the first entry kept, the token counts before and after, the model and the prompt version that wrote the summary, the `usage`{checked=row-50} entry that holds its cost, and an optional focus hint [@buildanagent-protocol-entries]. Anyone can read what replaced what, at what price. To reverse a compaction, you pick a path that skips it. Pi builds a model's context by walking from the current leaf to the root and using the latest compaction on that path [@pi-session-format], so a branch that leaves the path before the compaction sees the original messages again. Exercise 2 does exactly that.

## A progress file and a feature list carry long work across windows

Compaction shortens one window, and a task too big for one window cannot fit into one summary. Anthropic hit the limit on a job of over 200 features, a clone of claude.ai, run by Opus 4.5 in a loop across context windows. Its engineers wrote that "compaction isn't sufficient", because each new session "begins with no memory of what came before", like engineers working in shifts [@anthropic-effective-harnesses] (published 26 November 2025). Left alone, the agent failed in four ways, and the post pairs each with a fix in a file. [[tbl:long-running-failures]] lists them.

:::table[Four failures of a long run, and the file or routine that answers each, from Anthropic's long-running harness]{#long-running-failures}
| What goes wrong | The first session sets up | Each later session does |
| --- | --- | --- |
| It declares victory on the whole project too early | A structured JSON feature list, written from the spec | Reads the feature list first and chooses a single feature |
| It leaves bugs, or progress nobody wrote down | An initial git repository and a progress notes file | Reads the progress notes and the git log first |
| It marks features done too early | The same feature list, with every feature "failing" | Tests the feature itself, and marks it "passing" only after careful testing |
| It spends time working out how to run the app | An `init.sh`{checked=row-56} script that starts the development server | Reads `init.sh`{checked=row-56} first |
:::

The first session is a different job from the rest. An initializer agent writes the `init.sh`{checked=row-56} script, a progress log named `claude-progress.txt`{checked=row-56}, an initial commit and the feature list, in which every feature starts as failing. Each later session, the post says, handles "only one feature at a time", then commits its progress to git with a descriptive message, so a bad change can be reverted and the next session starts from a clean state [@anthropic-effective-harnesses]. The feature list is JSON on purpose, because "the model is less likely to inappropriately change or overwrite JSON files". The coding agents may edit it only by changing a `passes`{checked=row-57} field, and the prompt calls it "unacceptable to remove or edit tests".

Files beat summaries for this job because a file is exact. A summary is a model's memory of the work, and it can lose the one feature that still fails. A feature list says "failing" or "passing" for each entry, the git log says what changed, and the next session reads both at the start instead of trusting a recap. The harness writes the session log; the model keeps these files itself, in the working directory, where its own tools can open them. The two complement each other. Compaction keeps one window usable, the log keeps every entry, and the progress file tells the next window what is left to do.

Our plan carries the idea into the harness: a plan and progress file convention for long tasks, with a hook that reads the files again when a session resumes [@buildanagent-harness-plan]. The evidence is thin. Anthropic's post reports no success rates or measured comparisons, calls its result "one possible set of solutions", and says it is "still unclear whether a single, general-purpose coding agent performs best across contexts" [@anthropic-effective-harnesses]. Use the pattern for the failures it names, and measure it on your own tasks.

## Exercises

1. **Fork a session, compact one branch, and show the other is unchanged.** Make a scratch file, `verify/pi/examples/zz-fork-compact.ts`, and copy the setup of `06-compaction.ts` into it, down to the `try`. Script five answers: one capital each for France, Japan and Italy, then two summaries, because the example's tiny `keepRecentTokens`{checked=row-45} makes Pi send two summary requests. Ask about France and save `sm.getLeafId()` as `firstAnswerId`, as [[lst:session-tree-pi]] does. Ask about Japan and save that leaf too. Call `sm.branch(firstAnswerId)`, ask about Italy and save its leaf. Now go back to the Japan leaf, record `JSON.stringify(sm.getBranch())` and the entry count, return to the Italy leaf and call `session.compact()`. Check that the count rose by one, that the recorded Japan branch is identical, and that after you branch back to the Japan leaf, the messages of `sm.buildSessionContext()`{checked=row-62} contain "Tokyo" and no summary, while the Italy branch's contain the summary. Predict each check, then run `pnpm --filter ./verify/pi exec tsx examples/zz-fork-compact.ts`, which needs no network, and delete the file. Which of the checks would fail if compaction rewrote entries instead of appending one?
2. **Undo the compaction by moving HEAD.** Extend the scratch file: after the compaction, call `sm.branch()` with the id of the Italy answer you saved before it, and read the messages of `sm.buildSessionContext()`{checked=row-62} again. Predict whether they hold the summary or the original answers, and what happened to the compaction entry. Then answer from the second section: Pi's `branch()` writes nothing, so which entry type would our harness append to make that move survive a restart, and what would Pi find in the file when it loads it again?
3. **Write the files for a long task.** Pick a task of your own that needs more than one session, such as migrating a service's tests, and write the feature list as JSON with three to five features, every one failing, and a progress file of four lines. Match each of Anthropic's four failures in [[tbl:long-running-failures]] to the line of your files that prevents it, and mark the failure that none of your lines prevents. Then say which of your lines a compaction summary would have to carry if you had no files, and how likely a model is to carry each one exactly.
