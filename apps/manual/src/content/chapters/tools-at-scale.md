Five MCP servers, 58 tools and about 55,000 tokens: that is what Anthropic estimated in November 2025 for a setup with GitHub, Slack, Sentry, Grafana and Splunk, before the conversation had started [@anthropic-advanced-tool-use]. The post gives no method for the figure, but the arithmetic holds for any agent. Every tool you register puts its name, description and schema into every request, and the Claude Agent SDK's documentation says selection accuracy "degrades with more than 30-50 tools loaded at once" [@claude-agent-sdk-tool-search].

This chapter answers one question: how does an agent with dozens of tools stay usable, and how do MCP servers and skills fit after MCP's 2026-07-28 revision? Four mechanisms carry the answer. One registry names and gates every tool. Deferral keeps most definitions out of the request until the model asks for them. MCP brings in tools you did not write, and skills bring in procedures instead of tools. Each section shows its mechanism in a listing that CI runs, and says where our own harness is built and where it is still a design.

## One registry should name, defer and gate every tool, whatever its source

Suppose your agent ships with six built-in tools and you connect a GitHub server and a Slack server. By evening it holds dozens of tools from three origins, and three questions each need one answer. What is each tool called, so that a rule or a log line can point at it? Does the model receive the tool's whole definition, or only a hint that it exists? And may this call run?

The SDKs answer these separately, each in its own corner. Naming is the first corner. Pi calls an MCP tool `mcp__github__create_issue`{checked=row-4}, replaces every character other than letters, digits and underscores, and adds a hash suffix to the tools of a server whose cleaned names collide [@pi-mcp-servers]. [[ch:tools]] showed the Claude Agent SDK's version of the same prefix. Selection is the second corner. Pi lets you choose the tools the model may use, and [[lst:pi-active-tools]] shows the three ways to do it [@pi-sdk-docs].

:::listing[Pi chooses the tools a session offers: an allowlist, an exclusion, or none]{#pi-active-tools file="verify/pi/examples/03-tool-selection.ts" region="active-tools"}
::note[An allowlist replaces the default set, so this session can only read.]{#allowlist}
::note[An exclusion starts from the defaults and removes two tools, which leaves `read` and `edit`.]{#exclude}
::note[`noTools: "builtin"` leaves the model with none of the built-in tools.]{#none}
:::

An unlisted tool is not on the menu, so the model never sees its definition. A model can still ask for a tool by name, though, and what happens next is part of the gate. [[lst:pi-inactive-call]] scripts that request, and the answer is an error result the model can read, not a crash.

:::listing[A call to a tool outside the active set comes back as an error, and the loop continues]{#pi-inactive-call file="verify/pi/examples/03-tool-selection.ts" region="inactive-call"}
::note[Only `read` is active, but the scripted model asks for `ls`.]{#only-read}
::note[The call yields an error tool result, which the model reads on its next request.]{#error-result}
::note[The loop sends a second request instead of ending the run.]{#continues}
:::

The third corner, whether a call may run, lives in other code again, as [[ch:approvals-guardrails-and-injection]] showed. Three answers in three places drift apart, and a rule that names a tool one way while a log records it another way protects nothing. A harness that owns the loop can ask for one place, which our harness calls the tool registry. The registry, `createToolRegistry`{checked=row-8}, exists today in the private `@buildanagent/harness` package, as of November 2026 [@buildanagent-harness-readme]. It takes tools from four origins (built-in, extension, client and MCP server) and settles the three questions at registration, once.

:::figure[One registry names every tool once, sets what each request carries and feeds the permission pipeline]{#one-registry}
::svg{alt="Four boxes on the left, built-in tools, MCP server tools, extension tools and client tools, each with an arrow into one tall box labelled one registry. Inside it are three boxes: names it once, with the example mcp__github__x; sets exposure to direct, deferred or hidden; and marks trust, with MCP output untrusted. Two arrows leave the registry. One goes to a box saying each request carries direct tools plus tool_search. The other goes to a box saying the permission pipeline decides every call."}
:::

The registry answers the questions in this order. It gives each tool a canonical name of 1 to 64 characters, namespaces an MCP tool as `mcp__<server>__<tool>`{checked=row-10}, and throws a `DuplicateToolError`{checked=row-10} when a second tool takes a name. An extension may replace a built-in only by registering with `override: true`{checked=row-11}, and an MCP tool may never replace anything [@buildanagent-harness-readme]. It sets an exposure for each source, `direct`{checked=row-13}, `deferred`{checked=row-13} or `hidden`{checked=row-13}, and defaults MCP tools to `deferred`{checked=row-13} and every other source to `direct`{checked=row-13}. It marks an MCP tool's output untrusted, because the server wrote it and you did not. Finally it hands each run its definitions in registration order, so the cached prefix of a request does not move when a tool activates.

The permission pipeline reads the same description. It decides every call in one order, hooks first, then deny rules, ask rules, the mode, allow rules, the host callback and a default for what no rule settled. A deny at any step ends the decision, and a hook or callback that throws counts as a deny. Each verdict, allows included, becomes a `permission_decision`{checked=row-17} entry in the session log [@buildanagent-harness-readme]. Because the registry named the tool and marked its trust before the call reached the pipeline, a rule written for `mcp__github__create_issue`{checked=row-10} matches the tool that actually runs and a log reader finds it under the same name.

Two limits keep this honest. First, the built-in tools, the extension loader and both MCP transports are not built yet (todos N21 to N25 are open as of November 2026), so today you register such tools by hand and the chapter's MCP and skill sections describe a design. Second, a registry records where a tool came from and how far to trust its output, but it never reads the tool's code. ACaM, a November 2026 paper, calls the resulting gap Description-Code Inconsistency: "nothing enforces that the description and its implementation agree" [@santra-acam]. The authors injected hidden exfiltration paths into 14 variants of 10 real agents and left each tool's description unchanged, so each injected path is a laundered capability by construction. On 43 unmodified real-world agents the tool surfaced 123 code-execution and credential-exposure paths that the authors checked by hand, structural flaws and not understated descriptions. The registry makes every tool visible in one place, and nothing in it yet checks that a tool does what its description says.

## Deferring a tool keeps its definition out of the request until the model asks for it

Picture :analogy[a hardware store that shelves the common tools and fetches the rest from the back room]{#hardware-store-back-room}. Hammers and tape measures hang in plain sight, the hole saw and the pipe die set wait in back, and a clerk brings one out when a customer asks. A deferred tool follows the same plan. The request carries a name for it, with no description and no schema, and the model receives the definition only after it searches for the tool and the SDK loads the match [@claude-agent-sdk-tool-search].

:::figure[A hardware store that shelves the common tools and fetches the rest from the back room: the shelf is the tools every request carries]{#back-room analogy="hardware-store-back-room"}
::svg{alt="Two panels side by side. The left panel, the shelf in plain sight, holds a hammer, a tape measure and screws, and a note says it is like the tools every request carries. The right panel, the back room where tools are asked for, holds a hole saw, a pipe die set and a tile cutter, and a note says it is like the tools a search loads on the next step. An arrow labelled asks runs from the shelf to the back room, and an arrow labelled brings runs back."}
:::

The saving is large once the shelf holds dozens of tools. Anthropic estimates 50 or more MCP tools at about 72,000 tokens of definitions, about 77,000 tokens in all before any work, against about 8,700 tokens with its tool search tool, which loads about 500 tokens up front and three to five discovered tools at about 3,000 [@anthropic-advanced-tool-use]. In the same post, Anthropic reports that Opus 4 improved from 49% to 74% on its MCP evaluations with tool search, and Opus 4.5 from 79.5% to 88.1%. Both are Anthropic's own internal tests, published in November 2025, and the post gives no eval size, so treat them as a direction and not a rate.

[[lst:deferred-server]] shows how little code the choice takes in the Claude Agent SDK. Three tools sit in one server, the server is deferred by default, and a second copy of it opts out.

::note[A deferred server: the model sees these tools' names, not their schemas, until it searches.]{#deferred-default}
::note[`alwaysLoad: true` puts every definition into the first request, so no search is needed.]{#always-load}
:::

[[lst:deferred-checks]] holds what the example asserts about the first request and the one after it, and its replay steps through the run with the mock model standing in for the choice. The first request offers a search tool, `ToolSearch`, and no weather definition. The model still knows each tool's name, because the CLI behind the SDK lists the names in a message, but it has no description or schema to read. It calls `ToolSearch` for one tool by name, and the next request carries that single definition. The other two never reach the model in any request, and the eager server from [[lst:deferred-server]] sends all three at once and never offers `ToolSearch` at all.

The store's customers pay for the back room in minutes, and a model pays in two ways. Each search adds one round trip, and the Claude Agent SDK's documentation says that with fewer than about ten tools whose definitions fit comfortably, loading everything upfront is typically faster [@claude-agent-sdk-tool-search]. A loaded definition also stays in the context for later turns, until the SDK compacts the messages where the model found it. So the shelf should hold the tools your agent uses on most runs, and `alwaysLoad` is the setting that puts them there. Finding the rest depends on words: the search matches a query against tool names and descriptions, and the SDK's documentation notes that `search_slack_messages`{checked=row-28} surfaces for a wider range of requests than `query_slack`{checked=row-28} [@claude-agent-sdk-tool-search]. Pi sends the same signal at the server level, because it lists a server's `description`{checked=row-34} in the system prompt and ranks the server's tools by it when `tool_search`{checked=row-33} runs [@pi-mcp-servers].

Our harness builds the same mechanism into its registry, as of November 2026 and in code that no listing shows. MCP tools default to `deferred`{checked=row-13}, and `tool_search`{checked=row-35} is a registered tool that matches the words of a query against the names, aliases and descriptions of deferred tools, ignores common words and words under three letters, and records up to five matches in an `activated`{checked=row-35} set [@buildanagent-harness-readme]. An interceptor then sets each request's `activeTools`{checked=row-37} to the run's tools, the activated names and `tool_search`{checked=row-35}, so a deferred tool is absent from one request and present in the next. A `hidden`{checked=row-13} tool never appears in a search, because hiding a tool means the model should not learn it exists. The registry also estimates the tokens that `direct`{checked=row-13} tools add before any message, which makes the saving visible at session start. Pi's four exposure levels, `codemode`{checked=row-33}, `deferred`{checked=row-33}, `direct`{checked=row-33} and `hidden`{checked=row-33}, rest on the same split: sending a tool, finding a tool and denying a tool are different decisions, and a registry that keeps them apart lets you change one without touching the others.

## MCP's 2026-07-28 revision makes every request stand alone and turns a server's questions into results

MCP is :analogy[a USB port: one plug shape for many devices]{#usb-port}. Anthropic announced it in November 2024 as an open standard that replaces fragmented integrations with a single protocol [@anthropic-model-context-protocol], so any client that speaks it can use any server's tools. A mouse only moves a cursor, though, and an MCP server is closer to installed software. It chooses its tools' names, descriptions and results, and the specification tells clients to treat a tool's annotations as untrusted unless the server is trusted, and to keep a human able to deny tool calls [@mcp-tools-spec]. That is why the registry from the first section marks MCP output untrusted.

Connecting takes little code, and each of the three SDKs below puts it in a different place. The AI SDK converts a server's tools into its own and hands them to `generateText`. Cloudflare's `Agent` class connects and holds the connection for you. The Copilot SDK starts the server inside its runtime and renames each tool `<server-key>-<tool-name>`{checked=row-66}, here `orders-order_status` [@ai-sdk-mcp-tools; @cloudflare-agents-mcp-client; @copilot-sdk-nodejs-readme].

These listings show connecting, not the revision. The AI SDK example speaks the legacy handshake, and the Cloudflare example does not show which era its client chose. What the 2026-07-28 revision changes is the conversation behind these calls, and [[tbl:mcp-changes]] sets the old and new designs side by side [@mcp-changelog-2026-07-28; @mcp-deprecated-features].

:::table[What the 2026-07-28 revision changes for an MCP client]{#mcp-changes}
| Concern | Before 2026-07-28 | In 2026-07-28 |
| --- | --- | --- |
| Opening a connection | An `initialize`{checked=row-41} handshake, then a session id header | No handshake and no session: every request carries its version and capabilities in `_meta`{checked=row-41} |
| Learning what a server offers | The handshake's reply | An optional `server/discover` call, which every server must answer |
| A server needing the user | The server sends its own request mid-call | The call returns an `input_required`{checked=row-49} result, and the client retries with the answers |
| Roots, Sampling, Logging | Active features | Deprecated, still working, removable from the first revision on or after 2027-07-28 |
| Registering a client with an authorization server | Dynamic client registration | Deprecated in favour of Client ID Metadata Documents |
:::

The first change makes a request self-contained. There is no handshake and no session id, and every request names the protocol version and the client's capabilities in `_meta`{checked=row-41}. A server that supports a different version answers with `UnsupportedProtocolVersionError`{checked=row-41}, which lists the versions it does support, and the client retries with one of them [@mcp-changelog-2026-07-28; @mcp-versioning]. A server that needs state across calls hands out an explicit handle, and the handle travels as an ordinary tool argument. No instance needs the memory of an earlier request, and the specification says the retry flow described below needs no shared storage layer across server instances and no stateful load balancing [@mcp-multi-round-trip-requests].

The second change gives clients a way to ask first. Every server must implement `server/discover`, which reports its supported versions, capabilities and identity, and a client may call it before anything else, though it need not [@mcp-server-discover]. It matters most on stdio, where there is no HTTP status to react to. A client that wants to work with old and new servers probes with `server/discover` and falls back to `initialize`{checked=row-41} on any error that is not a recognised modern one. On HTTP it sends a modern request and inspects the body of a 400 reply before falling back, and in both cases it remembers the answer for the server process or origin [@mcp-versioning]. A client built only for the new revision fails against an old server, so the dual-era client is the safe default for as long as you connect to servers you do not control. The AI SDK documents exactly this behaviour for its stdio transport, and Cloudflare Agents negotiates for every connection [@ai-sdk-mcp-tools; @cloudflare-agents-mcp-client].

The third change moves the server's questions into its answers. Suppose a tool needs your GitHub username before it can run. In the old design the server sent a request of its own in the middle of the call. In the new one the call returns an `input_required`{checked=row-49} result, with `inputRequests`{checked=row-49} that name what it needs, and the client gathers the answers and retries the same request with `inputResponses`{checked=row-49} [@mcp-multi-round-trip-requests]. The server keeps nothing between the two requests. It folds what it needs into an opaque `requestState`{checked=row-50} string, and the client echoes it back unchanged. Every result now carries a `resultType`{checked=row-53} of `complete`{checked=row-53} or `input_required`{checked=row-49}, and a client treats a missing one as `complete`{checked=row-53}.

For an agent, this means a tool call can come back asking for a person. Your loop must be able to pause there and resume, which is the job of [[ch:approvals-guardrails-and-injection]]. Cloudflare Agents handles it for you: the SDK invokes your elicitation handler, sends the answer and continues the original call, which stays pending in memory while the person answers. A hibernation or isolate restart loses that call, and the caller retries [@cloudflare-agents-mcp-client]. Where a call must survive such a restart, [[ch:durable-and-portable-agents]] returns to the problem. The specification also repeats a warning from the approvals chapter. A server must treat `requestState`{checked=row-50} as attacker-controlled input, because the client holds it between the two requests, and when it influences authorization or business logic the server must protect its integrity with an HMAC or authenticated encryption and reject state that fails verification [@mcp-multi-round-trip-requests]. A saved pause that nobody signed is as editable here as it was there.

The fourth change is a set of deprecations. The revision deprecates Roots, Sampling and Logging, and the dynamic client registration protocol. They keep working through a deprecation window of at least twelve months, and the earliest revision that may remove them is the first one released on or after 2027-07-28, so the dates are a floor and not a schedule [@mcp-deprecated-features; @mcp-changelog-2026-07-28]. The migrations point away from the protocol. Pass directories and files as tool parameters instead of Roots, call model providers directly instead of using Sampling, and log to stderr or send OpenTelemetry instead of using Logging. The revision also removes `ping`{checked=row-56}, `logging/setLevel` and the roots change notification, and a client sets the log level on each request in `_meta`{checked=row-41}. In short, build nothing new on the deprecated features.

Our own MCP client is a design as of November 2026. Todo N24 plans to negotiate the era per server and to register each server's tools as deferred tools, so every call goes through the permission pipeline, but the client is not built and the plan does not yet handle `input_required`{checked=row-49}. A proposal in our source-update report would turn each input request into a pause that a person answers through a signed approval. Neither is adopted, so read both as intent and not as behaviour.

## Skills cost a name and a description until the model opens one

Think of :analogy[a mechanic's service manuals, opened only when that model of car comes in]{#service-manuals}. The shelf lists every manual by make and year, and the mechanic pulls the one for the car on the lift. A skill is a folder with a `SKILL.md` file, and it works the same way: the file's name and description go into the prompt at startup, at about 100 tokens per skill, and its body, under 5,000 tokens by Anthropic's guidance, enters the context only when the model decides the task matches [@anthropic-agent-skills-overview; @claude-agent-sdk-skills]. Bundled reference files load when the model reads them, and a bundled script runs through a shell, so only its output enters the context.

A skill adds instructions, not an interface. Pi's documentation draws the line: use a skill when a workflow needs more context than a prompt template but no new executable integration point [@pi-skills]. A tool lets the model do something new. A skill tells it how your team does something it can already do, such as report the weather in one city's format. [[lst:skills-run]] sets up that case in the Claude Agent SDK, with two skills on disk and one of them enabled.

::listing[Two skills on disk, one enabled for the run]{#skills-run file="verify/claude-agent-sdk/examples/09-skills.ts" region="skills-run"}

[[lst:skills-checks]] shows what the model receives. Its first request lists the enabled skill's name and description and carries no body. The skill left out of the `skills` option never reaches the model, though it stays on disk, because the option is "a context filter, not a sandbox" [@claude-agent-sdk-skills]. The mock model then calls the `Skill` tool, and from that request on, the body sits in every request of the run.

:::listing[The listing is cheap, the body arrives on demand and then stays]{#skills-checks file="verify/claude-agent-sdk/examples/09-skills.ts" region="skills-checks" replay}
::note[The first request holds the name and the description.]{#listed}
::note[It does not hold the body.]{#body-withheld}

The manual leaves the bay when the car does, and a skill's body does not. It stays in the context and costs its tokens in every later request of the run. The listing has a cost of its own: Anthropic's figure of about 100 tokens per skill comes to about 1,000 tokens for ten skills and about 20,000 for two hundred. Finding the right skill depends on the description, which Anthropic says must name what the skill does and when to use it [@anthropic-agent-skills-overview]. Even a good description can miss. Pi's documentation says "A model might fail to load a relevant skill", and gives a command, `/skill:name`, that forces one [@pi-skills]. No source measures how often a model misses, so treat loading as likely and not as guaranteed.

Our harness plans the same layout, and none of it is built yet (todo N23 is open as of November 2026). It would advertise each skill's name, description and path, load the body through the ordinary `read`{checked=row-81} tool, record a `skill_loaded`{checked=row-81} entry in the session log, and discover skills in `.agents/skills` from the working directory up to the repository root, as Pi does [@pi-skills]. The layout is a file-based cousin of Voyager, an agent that played Minecraft with GPT-4 and kept each skill as executable code in a vector database, keyed by an embedding of the skill's description and retrieved five at a time [@wang-voyager]. Voyager added a skill only after the program had run and passed the environment's feedback. A skill folder you download has run nowhere.

That gap matters, because the permission pipeline checks one call at a time and a skill steers a sequence of calls. SkillCFI, a November 2026 paper, tested 53 public skill packages and accepted none as written: 28 stopped at inventory before any model call, the compiler rejected the other 25 as unsupported, and the authors adapted seven of those 25 into enforceable contracts [@ruan-skillcfi]. Its runtime check blocked all 80 violating requests on the authors' abnormal tasks under each of three refusal messages, where a permission-style allowlist let every one of them through, because each request used only the skill's own vocabulary. The check assumes a trusted skill, though; screening a malicious one is a separate problem [@ruan-skillcfi]. ACaM's finding from the first section applies as well, because a description can omit what the code does [@santra-acam]. No current todo of ours checks a skill's steps or a tool's code at run time, so the pipeline and the sandbox remain the only limits on what a loaded skill can make the agent do. A skill you did not write deserves the review you would give a script you did not write.

## Signing in to a remote MCP server is a credential problem, so it belongs after the credential boundary

Everything above assumed the connection already worked. A remote server such as GitHub's must first learn who you are, and the specification answers with OAuth. Authorization is optional. An HTTP server that implements it acts as an OAuth resource server, and a stdio server is told not to follow the flow and to take its credentials from the environment [@mcp-authorization].

The questions that follow are credential questions. Where does the token live, and which process may read it? How does a client register itself with the authorization server now that dynamic client registration is deprecated? What may a hostile server's metadata make your client fetch? Each depends on the boundary between the model and its credentials, which [[ch:permissions-sandboxes-and-credentials]] builds, so this chapter stops at the door. One rule carries over from the first section: an MCP server's tools and output stay untrusted, whatever token signed you in.
