Your support agent now serves two customers, Acme and Globex, from one knowledge base of fourteen short articles. Three questions reach it in one week. On Monday an Acme admin pastes an error code, E4021, and asks what it means. On Tuesday another Acme user writes "I forgot my login credentials", in words that appear in no article. A month later someone asks whether deploys freeze on Fridays, a fact the agent stored thirty days earlier from a runbook that may have changed since. The first question needs the one article that holds the code. The second needs an agent that notices nothing matches, and the third needs a memory that knows when it has gone stale.

This chapter answers two questions with those three in mind. When should an agent fetch text instead of carrying it in every request, and how should memory that outlives a task be written, recalled and forgotten? Every listing runs offline against a scripted model, so each shows what reaches the model and never what a real model would do with it. The chapter's answer comes in four parts: carry a small, stable core and fetch the rest through a tool; rank with keywords first, filter by tenant before ranking and measure the retriever on labelled queries; store each lasting fact as a record with its source and an expiry, and check it before acting on it; and keep that memory in files until one of three signals says a service will pay for itself.

## Carry a small, stable core, and fetch everything else through a tool when a step needs it

You ask a reference librarian how to fix a failed export. Ten minutes later two books sit on your desk, chosen from a hundred thousand, and you never see the rest. :analogy[A reference librarian who fetches the few books you need]{#reference-librarian} is what retrieval does for an agent. Retrieval means fetching text into a model request only when a step needs it, through a tool call or a search the harness runs. Carrying means the opposite: putting text into every request, whether the step needs it or not. Anthropic calls the first approach "just in time": agents "maintain lightweight identifiers (file paths, stored queries, web links, etc.) and use these references to dynamically load data into context at runtime using tools" [@anthropic-effective-context-engineering].

:::figure[A reference librarian who fetches the few books you need: the stacks stay out of sight, and the librarian's choice decides what reaches your desk]{#reference-librarian analogy="reference-librarian"}
::svg{alt="On the left, a box labelled the stacks holds rows of small book shapes, with notes under it: 100,000 books, like the corpus. In the middle, a box labelled the librarian, ranks the stock, receives an arrow from above marked question: failed export, and a note under it reads like the search tool and its ranking. An arrow runs from the stacks into the librarian, and another from the librarian to a box on the right labelled your desk, which holds two books numbered 1 and 2, with the notes two books and like the request."}

Why not carry the whole stock? [[ch:the-session-log-and-context]] treated the context window as a desk with limited space, and a crowded desk costs more than room. Long inputs lose quality well before the window fills. NoLiMa tested 13 models that each claim at least 128K tokens of context, and at 32K tokens 11 of them scored half or less of their short-input score [@modarressi-nolima]. GPT-4o, the strongest of the thirteen, fell from 99.3% at short lengths to 69.7% at 32K. The test is a hard case on purpose. Each question shares almost no words with the sentence that answers it, so the model has to make an association rather than match a word, and the authors say models "often rely on surface-level cues in longer contexts". A long input that hands the model the exact words it needs is easier, which is no comfort for the questions users actually write.

Carrying is cheap only while the carried text stays the same. A prompt cache stores the front of earlier requests, and as of November 2026 Anthropic bills a cache hit at 0.1 times the base input price on most models, and at 0.05 times on Claude Opus 5.5 and Claude Sonnet 5.5 [@anthropic-pricing]. Any edit spoils the saving, because "Modifications to cached content can invalidate some or all of the cache", and a change to the tools or the system prompt invalidates every level after it [@anthropic-prompt-caching]. A cache also lowers the price of carried tokens, not their cost to the model's attention, which the NoLiMa result measures.

Our rule follows from those two facts. It is our synthesis, and no source states it whole. Carry a body of text in every request only when all four conditions hold:

1. it stays unchanged for the cache's lifetime;
2. it is small, well under the 32K tokens where NoLiMa's losses are large;
3. most requests need much of it, as when every answer compares several documents;
4. requests reuse it often enough to repay the cache write.

Fetch everything else, and keep a pointer to it in the request instead of the text. Claude Code is Anthropic's own example of the split: "CLAUDE.md files are naively dropped into context up front, while primitives like glob and grep allow it to navigate its environment and retrieve files just-in-time, effectively bypassing the issues of stale indexing and complex syntax trees" [@anthropic-effective-context-engineering]. The same page names the price, since "runtime exploration is slower than retrieving pre-computed data". A fetch costs a model call and a tool call, and you pay that only for the steps that need the text.

Our harness plan already keeps pointers in three places, each from an earlier chapter. Its first context layer caps a tool result at 64 KiB and spills the rest to a file that the agent can reread by path. Its tool registry can mark a tool `"deferred"`, so the request carries the tool's name and the definition arrives only after a search, and MCP tools start that way. Skills appear in the prompt as a name, a description and a path, and their bodies load through the ordinary read tool [@buildanagent-harness-plan]. [[ch:tools-at-scale]] covered the last two. A search tool over documents is the fourth pointer: the request carries the tool, and the documents stay in the stacks until a query asks for them.

[[lst:search-tool]] is that tool in the AI SDK. It searches the fourteen articles from this chapter's opening with BM25, a keyword ranking that the next section explains, written by hand in the same file so that no search package or embedding service is involved.

:::listing[A search tool for one tenant: the model writes the query, and the session decides whose documents it searches]{#search-tool file="verify/vercel-ai-sdk/examples/17-keyword-retrieval.ts" region="search-tool" replay}
::note[The tenant filter runs on the documents before they are ranked, and the next section shows why the order matters. The tenant comes from `searchTool(tenant)`, which your code calls with the signed-in session's tenant; the schema gives the model only `query`.]{#filter-first}
:::

The replay's first run is Monday's question. The scripted model calls `search_docs` with "What does E4021 mean?", and the tool returns one article, kb-01, "Export failed with E4021", with a score of 2.54. kb-01 is the only Acme article that holds the code, and a rare word such as an error code is exactly what keyword ranking rewards. The model's next request carries that one result, and its answer repeats the article's text, because the script tells it to repeat the first result. The model never sees the other thirteen articles, Globex's copy of the same error page included. The librarian's choice decides what reaches the desk, and the next section is about how that choice can go wrong.

## Rank with keywords first, filter by tenant before ranking, and measure the retriever on labelled queries

Monday's question worked because an error code is a rare word. BM25, the ranking behind the search tool, rewards exactly that. It scores a document for a query by adding up, over the query's words, how rare each word is across the documents times how often the document uses it, and it damps both a word repeated many times and a long document. [[lst:bm25]] is the whole function.

:::listing[BM25 in twenty lines: rarity times a count that saturates, damped for long documents]{#bm25 file="verify/vercel-ai-sdk/examples/17-keyword-retrieval.ts" region="bm25"}
:::

The two constants are the usual ones. `K1` sets how fast repeating a word stops adding to the score, `B` sets how strongly a long document is marked down, and SQLite's built-in full-text search fixes both "at 1.2 and 0.75 respectively" [@sqlite-fts5]. The rarity term is the logarithm of one plus a ratio, so it never goes negative, even for a word in every document. One of the example's checks shows the rarity at work. For "password webhook", kb-02 says "password" three times, while "webhook" appears only in kb-09, and kb-09 ranks first. A count of shared words without rarity would put kb-02 first.

Keyword search sounds old-fashioned beside embeddings, and it still makes the right first retriever. BEIR compared ten retrieval systems on 18 datasets, most of them outside the systems' training data, and concluded that "BM25 is a robust baseline" [@thakur-beir]. Measured by nDCG@10, a score of how high the relevant documents rank, the dense retriever DPR averaged 47.7% below BM25 and TAS-B 2.8% below, while BM25 followed by a cross-encoder reranker averaged 11% above it. Dense models win where they were trained, and BM25 trailed them by 7 to 18 points on MS MARCO, their training set. The authors also warn that their datasets carry a lexical bias, because keyword systems helped build their relevance labels, which favours BM25. The lesson for an agent is narrow: start with keywords, and let a measured miss, not fashion, justify anything more.

Keyword search has a failure of its own, and Tuesday's question shows it. "I forgot my login credentials" shares no word with kb-02, "Reset a password", so in the replay of [[lst:search-tool]] the tool returns an empty list and the scripted model says the documents have nothing on that. That run is one hand-picked query, chosen to fail, and it measures no recall. Vector search is the usual answer: it embeds the query and each document as vectors and ranks by the distance between them, so a paraphrase can land near its document. LIMIT shows that the two kinds fail on different queries [@weller-limit]. On a simple synthetic task of 50,000 documents and 1,000 queries, state-of-the-art embedding models "struggle to reach even 20% recall@100" while "BM25 comes close to perfect scores". The authors prove that one vector of a fixed size can return only a limited number of distinct top-k sets. When they swapped the task's words for synonyms, the order turned: "BM25 drops more than 89% whereas Qwen3 embedding drops 38.9%".

Opposite failures suggest running both retrievers and merging their lists, and reciprocal rank fusion is the usual merge. It gives each document the sum of 1/(k + rank) over the lists that rank it, so it needs only ranks, never the two retrievers' incomparable scores. Its authors fixed k = 60 in a pilot and found that value "near-optimal, but that the choice was not critical" [@cormack-rrf]. Their experiments fused runs submitted to TREC, not a keyword list with a vector list, and LIMIT leaves "hybrid sparse/dense solutions" to future work. No example in this book fuses two lists: T41's example has no vector search and no hybrid variant, so this paragraph rests on the paper alone.

Ranking is not the only thing a retriever decides. It also decides whose documents compete, and that decision belongs before the ranking. OWASP's entry on vector and embedding weaknesses lists "Cross-Context Information Leaks" in "multi-tenant environments where multiple classes of users or applications share the same vector database", and its first mitigation is "permission-aware vector and embedding stores" with "strict logical and access partitioning" [@owasp-llm08-vector-embedding-weaknesses]. The same rule holds for keyword search, and the order matters even when nothing leaks. [[fig:filter-before-rank]] runs Acme's query "settings export" both ways.

:::figure[Filter by tenant before ranking: the same query ranks differently when the other tenant's articles count toward a word's rarity]{#filter-before-rank}
::svg{alt="At the top, the query settings export, for Acme, splits into two columns. The left column, rank first, ranks all 14 articles and then keeps Acme's, and returns kb-04 single sign-on, kb-02 reset a password and kb-08 delete a workspace, with a note that export is in 6 of 14 articles, so it counts as common. The right column, filter first, keeps Acme's 9 articles and then ranks them, and returns kb-10, a planted export article, kb-01 export failed with E4021, and kb-04 single sign-on, with a note that export is in 2 of 9 articles, so it counts as rare."}
:::

The word "export" appears in six of the fourteen articles, so ranked across both tenants it counts as common, and a Globex article takes a place in the top three. Filtering that ranking afterwards leaves kb-04, kb-02 and kb-08, none of them about exports. Filtered first, Acme's nine articles hold "export" only twice, it counts as rare, and the tool returns kb-10, kb-01 and kb-04, which the replay's sixth run records with scores of 2.15, 2.14 and 1.11. T41's checks require that ranking, and both post-filter variants fail them: ranking everything and then filtering, and cutting the top three and then filtering. In SQL the rule is a `WHERE tenant_id = ?` clause inside the query that ranks, never a filter on its results.

The first article of that Acme list should worry you more than the order. kb-10 is a planted document, a prompt injection that arrives through retrieval instead of through the user. Its text repeats "failed export fix" and then tells the reader to run a script at an outside address and turn off the audit log first. [[lst:planted]] asks the question it was written for.

:::listing[A planted article that repeats the question's words ranks first, and what ranks first is what the model reads]{#planted file="verify/vercel-ai-sdk/examples/17-keyword-retrieval.ts" region="planted"}
::note[kb-10 scores 9.23 for "How do I fix a failed export?", against 3.54 for kb-01, the real answer, because it repeats every word of the question. With kb-10 removed, the same question gets kb-01's advice.]{#planted}
:::

Read the result for what it shows and no further. The scripted model's second turn is defined to repeat the first search result, so the run shows that the ranking decides what the model reads. It does not show that a real model would follow the planted instruction. Two papers measure that second step, against dense retrievers rather than BM25. PoisonedRAG wrote five texts for each of 100 target questions into Natural Questions' knowledge base of 2,681,468 texts [@zou-poisonedrag]. Its black-box texts begin with the target question itself, the same trick as kb-10, and with PaLM 2 answering, 97% of target questions got the attacker's answer. Inside a ReAct agent, the success rates fell to 72%, 58% and 52% on the paper's three datasets, and none of the four defences the authors tried stopped the attack. BadRAG planted 10 passages, 0.04% of its corpus, that are retrieved only for queries holding a trigger word [@xue-badrag]. With the Contriever retriever on Natural Questions, 98.2% of triggered queries ranked a planted passage first, but only 13.9% did with DPR, so the retriever changed the result. For one trigger topic, GPT-4's share of negative answers rose from 0.22% to 72%. Neither paper tested a keyword retriever, so our fixture shows the mechanism by construction, not a measured rate. OWASP's defences sit upstream: "Accept data only from trusted and verified sources", and "Maintain detailed immutable logs of retrieval activities" [@owasp-llm08-vector-embedding-weaknesses].

None of these checks says how well the tool retrieves, and that number needs a labelled set. Recall@k is the fraction of a query's relevant documents that appear in its top k results, averaged over the queries, and it says whether the right text reached the request at all, before any answer is graded. Anthropic's advice on evals sizes the set: "20-50 simple tasks drawn from real failures is a great start", and "Test both the cases where a behavior should occur and where it shouldn't" [@anthropic-demystifying-evals]. For a retriever, label 20 to 50 real queries with the ids of the documents that answer them. Include exact identifiers, paraphrases, queries from a second tenant and queries that should return nothing, such as a question about a product you do not sell. Report recall@k on the answerable queries, and count how often the empty ones return anything at all. T41's checks are five cases chosen to pass or fail, so they test the code, not the retriever's recall, which only such a set can measure.
