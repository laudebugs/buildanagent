Your support agent now serves two customers, Acme and Globex, from one knowledge base of fourteen short articles. Three questions reach it, two in one week and a third a month later. On Monday an Acme admin pastes an error code, E4021, and asks what it means. On Tuesday another Acme user writes "I forgot my login credentials", in words that appear in no article. A month later someone asks whether deploys freeze on Fridays, a fact the agent stored thirty days earlier from a runbook that may have changed since. The first question needs the one article that holds the code. The second needs an agent that notices nothing matches, and the third needs a memory that knows when it has gone stale.

This chapter answers two questions with those three in mind. When should an agent fetch text instead of carrying it in every request, and how should memory that outlives a task be written, recalled and forgotten? Every listing runs offline against a scripted model, so each shows what reaches the model and never what a real model would do with it. The chapter's answer comes in four parts: carry a small, stable core and fetch the rest through a tool; rank with keywords first, filter by tenant before ranking and measure the retriever on labelled queries; store each lasting fact as a record with its source and an expiry, and check it before acting on it; and keep that memory in files until one of three signals says a service will pay for itself.

## Carry a small, stable core, and fetch everything else through a tool when a step needs it

You ask a reference librarian how to fix a failed export. Ten minutes later two books sit on your desk, chosen from a hundred thousand, and you never see the rest. :analogy[A reference librarian who fetches the few books you need]{#reference-librarian} is what retrieval does for an agent. Retrieval means fetching text into a model request only when a step needs it, through a tool call or a search the harness runs. Carrying means the opposite: putting text into every request, whether the step needs it or not. Anthropic calls the first approach "just in time": agents "maintain lightweight identifiers (file paths, stored queries, web links, etc.) and use these references to dynamically load data into context at runtime using tools" [@anthropic-effective-context-engineering].

:::figure[A reference librarian who fetches the few books you need: the stacks stay out of sight, and the librarian's choice decides what reaches your desk]{#reference-librarian analogy="reference-librarian"}
::svg{alt="On the left, a box labelled the stacks holds rows of small book shapes, with notes under it: 100,000 books, like the corpus. In the middle, a box labelled the librarian, ranks the stock, receives an arrow from above marked question: failed export, and a note under it reads like the search tool and its ranking. An arrow runs from the stacks into the librarian, and another from the librarian to a box on the right labelled your desk, which holds two books numbered 1 and 2, with the notes two books and like the request."}
:::

Why not carry the whole stock? [[ch:the-session-log-and-context]] treated the context window as a desk with limited space, and a crowded desk costs more than room. Long inputs lose quality well before the window fills. NoLiMa tested 13 models that each claim at least 128K tokens of context, and at 32K tokens 11 of them scored half or less of their short-input score [@modarressi-nolima]. GPT-4o, the strongest of the thirteen, fell from 99.3% at short lengths to 69.7% at 32K. The test is a hard case on purpose. Each question shares almost no words with the sentence that answers it, so the model has to make an association rather than match a word, and the authors say models "often rely on surface-level cues in longer contexts". A long input that hands the model the exact words it needs is easier, which is no comfort for the questions users actually write.

Carrying is cheap only while the carried text stays the same. A prompt cache stores the front of earlier requests, and as of November 2026 Anthropic bills a cache hit at 0.1 times the base input price on most models, and at 0.05 times on Claude Opus 5.5 and Claude Sonnet 5.5 [@anthropic-pricing]. Any edit spoils the saving, because "Modifications to cached content can invalidate some or all of the cache", and a change to the tools or the system prompt invalidates every level after it [@anthropic-prompt-caching]. In our judgement, a cache also lowers the price of carried tokens, not their cost to the model's attention, which the NoLiMa result measures.

Our rule follows from those two facts. It is our synthesis, and no source states it whole. Carry a body of text in every request only when all four conditions hold:

1. it stays unchanged for the cache's lifetime;
2. it is small, well under the 32K tokens where NoLiMa's losses are large;
3. most requests need much of it, as when every answer compares several documents;
4. requests reuse it often enough to repay the cache write.

Fetch everything else, and keep a pointer to it in the request instead of the text. Claude Code is Anthropic's own example of the split: "CLAUDE.md files are naively dropped into context up front, while primitives like glob and grep allow it to navigate its environment and retrieve files just-in-time, effectively bypassing the issues of stale indexing and complex syntax trees" [@anthropic-effective-context-engineering]. The same page names the price, since "runtime exploration is slower than retrieving pre-computed data". A fetch costs a model call and a tool call, and you pay that only for the steps that need the text.

Our harness plan already keeps pointers in three places. Its first context layer caps a tool result at 64 KiB and spills the rest to a file that the agent can reread by path. Its tool registry can mark a tool `"deferred"`, so the request carries the tool's name and the definition arrives only after a search, and MCP tools start that way. Skills appear in the prompt as a name, a description and a path, and their bodies load through the ordinary read tool [@buildanagent-harness-plan]. [[ch:tools-at-scale]] covers the last two in the next chapter, where its hardware-store clerk fetches tools the way our librarian fetches books. A search tool over documents is a fourth pointer: the request carries the tool, and the documents stay in the stacks until a query asks for them.

[[lst:search-tool]] is that tool in the AI SDK. It searches the fourteen articles from this chapter's opening with BM25, a keyword ranking that the next section explains, written by hand in the same file so that no search package or embedding service is involved.

:::listing[A search tool for one tenant: the model writes the query, and the session decides whose documents it searches]{#search-tool file="verify/vercel-ai-sdk/examples/17-keyword-retrieval.ts" region="search-tool" replay}
::note[The tenant filter runs on the documents before they are ranked, and the next section shows why the order matters. The tenant comes from `searchTool(tenant)`, which your code calls with the signed-in session's tenant; the schema gives the model only `query`.]{#filter-first}
:::

The replay's first run is Monday's question. The scripted model calls `search_docs` with "What does E4021 mean?", and the tool returns one article, kb-01, "Export failed with E4021", with a score of 2.54. kb-01 is the only Acme article that holds the code, and a rare word such as an error code is exactly what keyword ranking rewards. The model's next request carries that one result, and its answer repeats the article's text, because the script tells it to repeat the first result. The model never sees the other thirteen articles, Globex's copy of the same error page included. The librarian's choice decides what reaches the desk, and the next section is about how that choice can go wrong.

## Rank with keywords first, filter by tenant before ranking, and measure the retriever on labelled queries

Monday's question worked because an error code is a rare word. BM25, the ranking behind the search tool, rewards exactly that. It scores a document for a query by adding up, over the query's words, how rare each word is across the documents times how often the document uses it, and it damps both a word repeated many times and a long document. [[lst:bm25]] is the whole function.

:::listing[BM25 in twenty lines: rarity times a count that saturates, damped for long documents]{#bm25 file="verify/vercel-ai-sdk/examples/17-keyword-retrieval.ts" region="bm25"}
:::

The two constants are the usual ones. `K1` sets how fast repeating a word stops adding to the score, `B` sets how strongly a long document is marked down, and SQLite's built-in full-text search fixes both "at 1.2 and 0.75 respectively" [@sqlite-fts5]. The rarity term is the logarithm of one plus a ratio, so it never goes negative, even for a word in every document. One of the example's checks shows the rarity at work. For "password webhook", kb-02 says "password" three times, while "webhook" appears only in kb-09, and kb-09 ranks first. A count of shared words without rarity would put kb-02 first.

Keyword search sounds old-fashioned beside embeddings, and it still makes the right first retriever. BEIR compared ten retrieval systems on 18 datasets, most of them outside the systems' training data, and concluded that "BM25 is a robust baseline" [@thakur-beir]. Measured by nDCG@10, a score of how high the relevant documents rank, the dense retriever DPR averaged 47.7% below BM25 and TAS-B 2.8% below, while BM25 followed by a cross-encoder reranker averaged 11% above it. BEIR also shows an in-domain effect: neural systems trained on MS MARCO beat BM25 there by 7 to 18 points, but DPR, the one dense model not trained on it, scored below BM25 even on MS MARCO. The authors also warn that their datasets carry a lexical bias, because keyword systems helped build their relevance labels, which favours BM25. The lesson for an agent is narrow: start with keywords, and let a measured miss, not fashion, justify anything more.

Keyword search has a failure of its own, and Tuesday's question shows it. "I forgot my login credentials" shares no word with kb-02, "Reset a password", so in the replay of [[lst:search-tool]] the tool returns an empty list and the scripted model says the documents have nothing on that. That run is one hand-picked query, chosen to fail, and it measures no recall. Vector search is the usual answer: it embeds the query and each document as vectors and ranks by the distance between them, so a paraphrase can land near its document. LIMIT shows that the two kinds fail on different queries [@weller-limit]. On a simple synthetic task of 50,000 documents and 1,000 queries, state-of-the-art embedding models "struggle to reach even 20% recall@100" while "BM25 comes close to perfect scores". The authors prove that one vector of a fixed size can return only a limited number of distinct top-k sets. When they swapped the task's words for synonyms, the order turned: "BM25 drops more than 89% whereas Qwen3 embedding drops 38.9%".

Opposite failures suggest running both retrievers and merging their lists, and reciprocal rank fusion is the usual merge. It gives each document the sum of 1/(k + rank) over the lists that rank it, so it needs only ranks, never the two retrievers' incomparable scores. Its authors fixed k = 60 in pilot experiments and found that value "near-optimal, but that the choice was not critical" [@cormack-rrf]. The pilots fused 30 configurations of one search engine, Wumpus, on four TREC collections, and a second set of experiments fused rankings that TREC participants submitted. Neither fused a keyword list with a vector list, and LIMIT leaves "hybrid sparse/dense solutions" to future work. No example in this book fuses two lists: this chapter's keyword-retrieval example has no vector search and no hybrid variant, so this paragraph rests on the papers alone.

Ranking is not the only thing a retriever decides. It also decides whose documents compete, and that decision belongs before the ranking. OWASP's entry on vector and embedding weaknesses lists "Cross-Context Information Leaks" in "multi-tenant environments where multiple classes of users or applications share the same vector database", and its first mitigation is "permission-aware vector and embedding stores" with "strict logical and access partitioning" [@owasp-llm08-vector-embedding-weaknesses]. The same rule holds for keyword search, and the order matters even when nothing leaks. [[fig:filter-before-rank]] runs Acme's query "settings export" both ways.

:::figure[Filter by tenant before ranking: the same query ranks differently when the other tenant's articles count toward a word's rarity]{#filter-before-rank}
::svg{alt="At the top, the query settings export, for Acme, splits into two columns. The left column, rank first, ranks all 14 articles and then keeps Acme's, and returns kb-04 single sign-on, kb-02 reset a password and kb-08 delete a workspace, with a note that export is in 6 of 14 articles, so it counts as common. The right column, filter first, keeps Acme's 9 articles and then ranks them, and returns kb-10, a planted export article, kb-01 export failed with E4021, and kb-04 single sign-on, with a note that export is in 2 of 9 articles, so it counts as rare."}
:::

The word "export" appears in six of the fourteen articles, so ranked across both tenants it counts as common, and a Globex article takes a place in the top three. Filtering that ranking afterwards leaves kb-04, kb-02 and kb-08, none of them about exports. Filtered first, Acme's nine articles hold "export" only twice, it counts as rare, and the tool returns kb-10, kb-01 and kb-04, which the replay's sixth run records with scores of 2.15, 2.14 and 1.11. The example's checks require that ranking, and both post-filter variants fail them: ranking everything and then filtering, and cutting the top three and then filtering. In SQL our rule is a `WHERE tenant_id = ?` clause inside the query that ranks, never a filter on its results.

The first article of that Acme list should worry you more than the order. kb-10 is a planted document, a prompt injection that arrives through retrieval instead of through the user. Its text repeats "failed export fix" and then tells the reader to run a script at an outside address and turn off the audit log first. [[lst:planted]] asks the question it was written for.

:::listing[A planted article that repeats the question's words ranks first, and what ranks first is what the model reads]{#planted file="verify/vercel-ai-sdk/examples/17-keyword-retrieval.ts" region="planted"}
::note[kb-10 scores 9.23 for "How do I fix a failed export?", against 3.54 for kb-01, the real answer, because it repeats the question's content words, "fix", "failed" and "export", five times each. With kb-10 removed, the same question gets kb-01's advice.]{#planted}
:::

Read the result for what it shows and no further. The scripted model's second turn is defined to repeat the first search result, so the run shows that the ranking decides what the model reads. It does not show that a real model would follow the planted instruction. Two papers measure that second step, against dense retrievers rather than BM25. PoisonedRAG wrote five texts for each of 100 target questions into Natural Questions' knowledge base of 2,681,468 texts [@zou-poisonedrag]. Its black-box texts begin with the target question itself, the same trick as kb-10, and with PaLM 2 answering, 97% of target questions got the attacker's answer. Inside a ReAct agent, the success rates fell to 72%, 58% and 52% on the paper's three datasets, and none of the four defences the authors tried stopped the attack. BadRAG planted 10 passages, 0.04% of its corpus, that are retrieved only for queries holding a trigger word [@xue-badrag]. With the Contriever retriever on Natural Questions, 98.2% of triggered queries ranked a planted passage first, but only 13.9% did with DPR, so the retriever changed the result. For one trigger topic, GPT-4's share of negative answers rose from 0.22% to 72%. Neither paper tested a keyword retriever, so our fixture shows the mechanism by construction, not a measured rate. OWASP's defences sit upstream: "Accept data only from trusted and verified sources", and "Maintain detailed immutable logs of retrieval activities" [@owasp-llm08-vector-embedding-weaknesses].

None of these checks says how well the tool retrieves, and that number needs a labelled set. Recall@k is the fraction of a query's relevant documents that appear in its top k results, averaged over the queries, and it says whether the right text reached the request at all, before any answer is graded. Anthropic's advice on evals sizes the set: "20-50 simple tasks drawn from real failures is a great start", and "Test both the cases where a behavior should occur and where it shouldn't" [@anthropic-demystifying-evals]. For a retriever, label 20 to 50 real queries with the ids of the documents that answer them. Include exact identifiers, paraphrases, queries from a second tenant and queries that should return nothing, such as a question about a product you do not sell. Report recall@k on the answerable queries, and count how often the empty ones return anything at all. The example's checks are five cases chosen to pass or fail, so they test the code, not the retriever's recall, which only such a set can measure.

## Store a lasting fact as a sourced record, check it before acting on it, and let it expire unless a check renews it

A good account manager keeps :analogy[a card file of contacts, updated after every meeting]{#contact-card-file}. After each call she writes a card: who, what they asked for, where she heard it and the date. Before the next call she pulls the card, and she never rereads the old call notes. Long-term memory is that card file for an agent: anything it writes during one task and reads in a later one. A session, which [[ch:memory-and-sessions]] covered, keeps one conversation however many runs it spans; long-term memory crosses from one session to the next, and each card in it is a memory record. The card file breaks in one place. A model may write a wrong card and later trust it, so the writes need rules, and the rest of this section builds them.

### What to store: a small, typed record that carries its source

The papers give two answers to what a card should hold, and neither is a transcript. Reflexion keeps a verbal lesson. After a failed attempt, a second model reads the trajectory and its pass-or-fail signal and writes what went wrong, so that "the agent can then verbally state that it should have taken a different action", and only that lesson goes to long-term memory [@shinn-reflexion]. The memory stays small on purpose, bounded at "a maximum number of stored experiences, Ω (usually set to 1-3)", and it spans retries of one task, not separate tasks. Voyager keeps a skill as code. Each time GPT-4 "generates and verifies a new skill", the program joins a library keyed by an embedding of its description, and a GPT-4 critic does the verifying [@wang-voyager]. Removing that check cut the items Voyager discovered by 73%, the largest drop among its feedback types. GitHub's Copilot stores facts about a repository, each with a subject, the fact, citations such as `src/client/sdk/constants.ts:12` and a reason [@github-copilot-agentic-memory]. All three keep something small that a later step can act on, and each either verified it or attached where it came from.

The rules matter because a memory store is an attack surface that outlives the attack. MINJA's attacker behaves "like a regular user": it sends ordinary queries, never touches the store, and leaves records that the agent itself writes [@dong-minja]. Two of the paper's three agents stored every execution record, "due to the lack of user judgment of the agent outcomes". Across all three agents, 98.2% of the attack's queries planted a malicious record on average, and later queries from victims carried the attacker's reasoning in 76.8% of cases. Expiry alone does not save you, because the attacker can strike just before the victim. Detection did little better: a screening prompt written for one agent caught its planted records but none on the other two, and a general prompt flagged many honest queries. MINJA's victims shared one memory bank, and the paper notes that separate banks for each user can be defeated by an attacker who poses as the victim. Our harness plan turns these findings into write rules [@buildanagent-harness-plan]. The agent writes through one explicit memory tool, one record per fact, and each record carries a subject, the fact, a source (a file and line, a URL or the user's own words), a type, a created date, a last-validated date and an expiry. Once a session reads output from an untrusted tool, every record it writes is low-trust and expires first. The memory tool cannot write skills or instructions, the procedural memory that a planted record would most like to change.

[[lst:remember]] is the write half of that design on LangChain, with fewer fields: a record with its subject, fact, source and an expiry 30 days after it was created.

::note[The record carries its own `source` and `expires`, because the installed store has no expiry setting. `created` comes from an injected clock, so a test can move time forward.]{#record}
:::

Two traps sit in this short listing, and the example's checks cover both. The `InMemoryStore` that the tool writes to comes from `@langchain/langgraph`. The `"langchain"` package exports a class of the same name that is a plain key-value store without `search()`, and core's tool runtime declares that key-value type, which is why the listing casts `runtime.store`. The example also builds its store without a semantic index, so its recall is a filter on the subject, not a vector search.

### When to recall: a short index every session, search for the rest, and a check before acting

Recall has two halves. A short index loads with every session, so the agent knows what it knows, and search finds the rest when a step needs it. Claude Code loads "the first 200 lines or 25KB of `MEMORY.md`, whichever comes first" at session start and reads its topic files "on demand using its standard file tools" [@claude-code-memory]. Cloudflare's Agents SDK puts both halves in the agent's own SQLite, as [[lst:context-blocks]] shows.

:::listing[Two context blocks: a writable memory the prompt shows in full, and a search block the prompt only counts]{#context-blocks file="verify/cloudflare-agents/examples/11-context-memory.ts" region="context-blocks"}
::note[The system prompt is rendered once per instance and then frozen, so a write during a run reaches the prompt only on the next instance. That keeps the provider's prefix cache warm.]{#frozen}
::note[The blocks supply their own tools: `set_context` because a block is writable, and `search_context` because one has a search provider.]{#tools}
:::

The example writes "Ada prefers metric units" to the memory block and a note about staging deploys to the search block, then evicts the Durable Object and starts a new instance. [[lst:evict-and-recall]] is that step.

:::listing[Evict the agent, wake it, and recall]{#evict-and-recall file="verify/cloudflare-agents/examples/11-context-memory.ts" region="evict-and-recall" replay}
:::

In the replay, the new instance's system prompt holds the fact under the MEMORY header and, under NOTES, only "1 entries indexed.". The scripted model then calls `search_context` with "deploying thursday", and the note comes back, "The staging deploy runs on Thursdays after the freeze review", although the query uses other word forms. The search block is an FTS5 table with the Porter stemmer, so the match is still keyword search, only with stemmed words. A second agent name has its own database: its prompt shows both block headers with no content under them, and the same query finds nothing. Three limits apply as of November 2026. Everything in `agents/context` is experimental and "may change between releases" [@cloudflare-agents-context]. Vectorize and Workers AI, Cloudflare's vector search and embeddings, have no local simulation [@cloudflare-bindings-per-env], so no example here runs semantic search on Cloudflare. And the run's FTS5 table executed in local workerd, which the example checks, but that proves the local runtime, not a deployed one.

A recalled record is a claim about the past, so check it before it changes what the agent does. Copilot's agent is "prompted to verify its accuracy and relevance by checking the cited code locations", and "If the code contradicts the memory, or if the citations are invalid", it stores a corrected version [@github-copilot-agentic-memory]. GitHub reports a pull-request merge rate of 90% with memory against 83% without, a vendor's measurement on its own tasks, and its seeded test of false memories ended with agents that "consistently verified citations". GitHub's documentation still warns that the check "is a judgment Copilot makes, rather than a guarantee enforced by the system", so "a stored fact should not be relied on as a rule that will always be followed" [@github-copilot-memory-docs]. For our agents the rule is ours: before a recalled record changes an action, reread its source, and rewrite or delete a record whose source has changed or vanished. The Friday deploy freeze from the opening is exactly that case. Its record names `runbook.md#freeze`, and the runbook may have moved the freeze since.

### When to forget: an expiry that only a successful check renews, and every copy the harness keeps

An office runs :analogy[a shredding schedule]{#shredding-schedule}: each box of files carries a destroy-after date, and on that date the box goes to the shredder whether anyone opened it or not. Forgetting is the same kind of rule for memory: a rule set in advance that stops a record from reaching the model. Copilot's version expires a memory 90 days after it was created by default, and "Simply retrieving a memory does not reset this period"; only an upvote, which Copilot gives a memory it has validated, starts the period again [@github-copilot-memory-docs]. Owners can set repository facts to anything from 7 to 180 days.

None of the stores in our listings expires a record by itself, so the expiry example builds the schedule into the recall tool. [[lst:recall]] reads the record's `expires` against the injected clock, and [[lst:recall-run]] runs a recall before the date and one after it.

:::listing[A recall tool that drops and deletes any record past its expiry]{#recall file="verify/langchain/examples/11-store-recall-expire.ts" region="recall"}
::note[The clock passes the expiry, so the tool deletes the record from the store instead of returning it.]{#expire}
:::

:::listing[Recall on a new thread, then again after the clock passes the expiry]{#recall-run file="verify/langchain/examples/11-store-recall-expire.ts" region="recall-run" replay}
::note[The second recall runs 30 days and one millisecond after the record was written. The model is told "No unexpired memory." and never sees the fact.]{#after-expiry}
:::

The replay shows each step. The write run, on thread "write", stores "Deploys freeze on Fridays." with the source `runbook.md#freeze`. A reader agent on another thread, "read-1", recalls the record with its source and both dates, and the record stays in the store. The clock then moves 30 days and one millisecond. On thread "read-2", the recall tool returns "No unexpired memory.", the scripted model answers "I have nothing on that.", and the example's checks confirm the store no longer holds the record. The expiry here is plain: it starts at the write and nothing renews it. Renewing it on a successful source check, as Copilot does, is Exercise 1.

Shredding a card does not shred its photocopies, and that is where the schedule stops matching the software. Deleting a fact from memory leaves it in logs and caches unless the harness deletes those too. [[lst:session-log]] reads the first thread's checkpoint after the record is gone.

:::listing[The record is gone, and the write is still in the session log]{#session-log file="verify/langchain/examples/11-store-recall-expire.ts" region="session-log"}
::note[The fact is still there, in the arguments of the remember call that the write thread's checkpoint keeps.]{#log}
:::

The store and the checkpointer are separate objects, so the delete never touches the log. Vendors document the same gap. Zep warns that deleting an episode "does not regenerate the names or summaries of nodes shared with other episodes", so "This episode information may still exist within these nodes" [@zep-deleting-data]. Claude Code shows the reverse case: it deletes old transcripts after `cleanupPeriodDays`{checked=row-99}, but excludes the memory files from that sweep, so they "stay until you or Claude edits or deletes them" [@claude-code-memory]. Our harness keeps session logs with no automatic deletion by default, and its plan therefore amends that rule: deleting a memory marks the log entries that carry the fact, so that a targeted purge or the retention purge can remove them [@buildanagent-harness-plan]. Until a harness does that, forgetting means the model stops seeing a fact, not that the fact is gone.

## A directory of files is enough for one agent and one user; buy a memory service on one of three signals

Picture the owner's coding agent a year in, with three hundred memory records about one repository and one person. Every rule in the last section fits in a folder. Each record is a small file with its fields at the top, a short index lists one line per record, and the agent finds the rest with grep. The repository's git history then gives you rollback and a diff for every write, and in our judgement a few hundred records need no search index at all. Our harness plan takes exactly that design as an extension that a host loads: one memory tool over `.agents/memory/`, an index capped at 200 lines or 25 KB that loads at session start, and the agent's own grep and glob tools for everything else [@buildanagent-harness-plan]. The plan considered a memory service, such as AWS's AgentCore Memory or Zep, and chose files.

Your SDK may already give you a store, and for one user it is enough. [[lst:store-langchain]] passes LangGraph's store to an agent, whose tool writes through `runtime.store`, and [[lst:sql-cloudflare]] keeps notes in the Cloudflare agent's own SQLite.

::listing[LangChain: a store passed to the agent]{#store-langchain file="verify/langchain/examples/09-long-term-store.ts"}

Both stores sit inside your deployment and hold whatever fields you give a record. The LangChain example checks that the store the tool writes to is LangGraph's, with `get()` and `put()`, as the previous section's traps warned. The Cloudflare example binds every value as a parameter, so a note that holds SQL comes back as text, and the table lives beside the SDK's own tables in the agent's database. Its `find` matches a substring with `LIKE`{checked=row-107} and ranks nothing. For ranked search in the same database, use an FTS5 table, as the context blocks do, whose `bm25()` function ranks with the constants of the second section [@sqlite-fts5].

The main report names when a service earns its price, and the rule is one of three signals [@buildanagent-main-report]:

1. many end users each need an isolated profile;
2. recall must span thousands of records, where keyword search over files starts to miss;
3. users ask temporal questions, such as what they preferred before March.

The first signal arrives with the first other user, which is why our agent platform plan gives each tenant its own memory namespace, filtered inside the query before ranking, once it builds memory [@buildanagent-agent-platform-plan]. In our reading, the second is the measured miss from the second section, so you see it on your labelled queries before you pay for it. The third, by the same reading, needs a store that keeps old values with their dates rather than overwriting them, which a folder of current facts does not.

Published benchmarks will not choose the service for you. The main report records that "Long-term memory products have contested benchmarks": Zep has publicly disputed the comparison on the LoCoMo benchmark in Mem0's paper [@buildanagent-main-report]. Run your own labelled queries through the candidate instead, including the ones that should return nothing. Before buying, check four things that the shredding schedule makes urgent: a full export, hard deletion across every revision the service keeps, a maintained TypeScript client, and a way to reach the service from every place your agent runs. These four checks are our recommendation. Each one decides whether a delete in your harness can reach the service's copy.

Retrieval and memory turn out to be one discipline. Carry a small, stable core in every request and keep pointers to the rest. Search with keywords first, filter by tenant before you rank, and measure the retriever on labelled queries before you trust a change to it. Treat what comes back, a planted article or a remembered fact, as a claim with a source: check the source before acting, and let the record expire unless a check renews it. Then make the delete reach every copy, the session log included, because forgetting is complete only when the harness says so.
