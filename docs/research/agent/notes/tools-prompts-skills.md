# Tool contracts, system prompts and skills: how to write and test them

Research note for our agent product, which will run on our own TypeScript harness. Question: how should the agent's tool contracts, system prompt and skills be written and tested? Evidence is as of November 2026. Primary sources are Anthropic's engineering posts and platform docs, the Claude Code docs, OpenAI's cookbook, the mirrored SDK docs under `docs/reference/*/source/`, and this repo's own research and skill tests. platform.openai.com, developers.openai.com and arxiv.org were unreachable from this environment, so OpenAI's function-calling guide and the RAG-MCP paper were first cited from search summaries and marked (secondary). Re-verification R1 (2026-11-18) read both from developers.openai.com and arxiv.org; see [fact-check.md](../fact-check.md#re-verification-against-primary-sources-r1).

The short answer: spend the effort on tools before the prompt. Write each tool as a contract with a namespaced name, a description of three or more sentences, an unambiguous schema with examples where needed, typed and actionable error results, declared side-effect class, and an output budget. Keep the always-loaded prompt short and stable. Move procedures into skills that load on demand, and move anything that must always hold into code (hooks, gates, tool design), because prompts guide and do not enforce. Test the contract with unit tests against a scripted model, and test behavior with an eval suite of real-failure tasks that is rerun on every prompt, tool or model change.

## 1. Tools deserve more design effort than the prompt

**Anthropic's measured gains came from tool changes, not prompt changes.** On SWE-bench, Anthropic spent more time optimizing tools than the overall prompt; requiring absolute paths removed a class of errors, and a rewritten tool description cut task time by 40% (`docs/research/agent-sdks-and-harness-design.md:103`, citing [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) and [multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)). Refining tool descriptions helped Claude Sonnet 3.5 reach state of the art on SWE-bench Verified, and removing "2025" from a web-search tool's query parameter description improved results ([Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)).

**Anthropic's tool docs call the description "by far the most important factor in tool performance."** A description should say what the tool does, when to use it and when not, what each parameter means, and what the tool does not return, with "at least 3–4 sentences" per tool ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)). LangChain's context-engineering guide says names, descriptions and argument descriptions "aren't just metadata—they guide the model's reasoning" (`docs/reference/langchain/source/src/oss/langchain/context-engineering.mdx:671`). The Vercel AI SDK asks for semantically meaningful names, `.describe()` on every schema property, and a description of the tool's output when tools depend on each other (`docs/reference/vercel-ai-sdk/source/content/docs/03-ai-sdk-core/20-prompt-engineering.mdx:16-22`).

**Pass tools through the API's `tools` field, not as prompt text.** OpenAI measured a 2% SWE-bench Verified gain from API-parsed tool descriptions over descriptions injected into the prompt ([GPT-4.1 prompting guide](https://raw.githubusercontent.com/openai/openai-cookbook/main/examples/gpt4-1_prompting_guide.ipynb)). Anthropic's API builds its own tool-use system prompt from the definitions and places the user's system prompt after them ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools), "Tool use system prompt").

## 2. A tool contract has eight parts, and each one has primary guidance

### 2.1 Granularity: a few consolidated, workflow-shaped tools beat many thin API wrappers

- Anthropic: "More tools don't always lead to better outcomes"; overlapping tools "distract agents"; build "a few thoughtful tools targeting specific high-impact workflows", for example `schedule_event` instead of separate availability and booking calls ([Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)).
- Anthropic's API docs go further: group `create_pr`, `review_pr` and `merge_pr` into one tool with an `action` parameter, because fewer tools "reduce selection ambiguity" ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)).
- Context engineering names "bloated tool sets that cover too much functionality" and "ambiguous decision points about which tool to use" as failure modes ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).
- OpenAI's guide says to "Combine functions that are always called in sequence" and "Don't make the model fill arguments you already know": define `submit_refund()` with no parameters and pass the `order_id` in code ([OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling)).

The `action`-parameter advice is in tension with read-only versus state-changing classes (§2.6): one tool that both reads and merges cannot be marked read-only or parallel-safe. Split along the side-effect boundary first, then consolidate within each side.

### 2.2 Names: namespace by service and resource, and test prefix versus suffix

- Prefix names by service, such as `github_list_prs` and `slack_send_message`; this matters most with tool search, which matches on names ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)).
- Prefix versus suffix namespacing had "non-trivial effects" on Anthropic's evals, so choose by measurement ([Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)).
- Name rules differ by provider: Anthropic requires `^[a-zA-Z0-9_-]{1,128}$` ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)); MCP recommends `^[A-Za-z0-9._-]{1,128}$`; OpenAI's SDK rewrites non-alphanumerics to `_`; Claude and Pi expose MCP tools as `mcp__<server>__<tool>` (`docs/research/agent-sdk/notes/tools.md:180-187`).
- Skills that reference MCP tools should use fully qualified names to avoid "tool not found" errors ([Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), "MCP tool references").

### 2.3 Input schemas: unambiguous names, enums, flat shapes, nullable over optional

- Name parameters unambiguously: `user_id`, not `user` ([Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)).
- "Use enums and object structure to prevent invalid states"; OpenAI's counter-example is `toggle_light(on: bool, off: bool)` ([OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling)). LangChain's example uses `z.enum(["pending","shipped","delivered"])` for status (`context-engineering.mdx:713-715`).
- Keep parameter complexity low; nested, optional and union-heavy Zod schemas are hard for models (`20-prompt-engineering.mdx:18`). Use `.nullable()` instead of `.optional()` for strict providers (`20-prompt-engineering.mdx:56-65`).
- Ask for "a short explanation or the supporting evidence", not "reasoning", in a parameter; a reasoning parameter can trigger a `reasoning_extraction` refusal on Claude ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)).
- Validate every call in the harness, because provider strict mode is not enough: Vercel's raw JSON Schema and dynamic MCP tools reach `execute` unvalidated (`docs/research/agent-sdk/agent-sdk-research.md:65`).

**Input examples fix what schemas cannot express.** `input_examples` raised accuracy on complex parameter handling from 72% to 90% in Anthropic's internal testing; use realistic data, show minimal, partial and full calls, and keep to 1–5 examples per tool, only where the schema leaves usage unclear ([Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)). Each example must validate against the schema or the API returns 400, and examples cost about 20–50 tokens each for simple cases and 100–200 for nested ones ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)). Vercel exposes `inputExamples` and a middleware that inlines them for providers without native support (`docs/reference/vercel-ai-sdk/source/content/docs/03-ai-sdk-core/40-middleware.mdx:62, 192-193`).

### 2.4 Errors: return every failure as a result the model can act on

- Anthropic: "prompt-engineer your error responses to clearly communicate specific and actionable improvements" ([Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)).
- The SDKs that do this best name the failing path and echo the received arguments (Pi); OpenAI's default hides the cause behind "An error occurred while running the tool. Please try again." (`agent-sdk-research.md:61, 65`).
- Mark failures as failures. The Claude Agent SDK's `isError: true` lets the handler "add context the raw exception lacks, such as which request failed or what to try instead" (`docs/reference/claude-agent-sdk/source/custom-tools.md:24, 429`). Vercel's and OpenAI's MCP adapters drop `isError` (`agent-sdk-research.md:71`).
- Unknown-tool errors should list the available or loadable names and point at tool search when the tool is deferred (`docs/research/agent-sdk/notes/tools.md:242-243`).
- Skill scripts should follow the same rule: "Solve, don't defer," with messages such as "Field 'signature_date' not found. Available fields: …" ([Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)).

### 2.5 Outputs: return high-signal fields, readable identifiers and a format switch

- Resolve opaque UUIDs into meaningful names, which improved retrieval precision; offer a `response_format` of concise or detailed (Slack example: 206 versus 72 tokens) ([Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)).
- Return "semantic, stable identifiers" and "only the fields Claude needs to reason about its next step" ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)).
- Keep three result channels apart: model-visible `content`, UI and log `details`, and `structuredContent` for code (`agent-sdk-research.md:71`).

### 2.6 Side effects: declare read-only, destructive, idempotent and open-world, then enforce in code

- MCP's four annotations, as the Claude Agent SDK documents them: `readOnlyHint` (default false; controls parallel batching with other read-only tools), `destructiveHint` (default true), `idempotentHint` (default false) and `openWorldHint` (default true) (`custom-tools.md:335-338`).
- "Annotations are metadata, not enforcement" (`custom-tools.md:340`), and MCP says clients "should never make tool use decisions" on annotations from untrusted servers (`agent-sdk-research.md:69`).
- A missing hint can change gating: in Claude's `auto` or `plan` modes, an unset `destructiveHint` counts as false for `always_ask` calls, so the classifier may approve them (`custom-tools.md:420`).
- Programmatic tool calling "works best for tools that can run in parallel or are safe to retry", so idempotency is also a precondition for code-mode execution ([Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)).
- High-risk actions belong in tool design, not prompt text: Anthropic's payment guidance says to give the agent a tool that queues a payment for a person to release and "no tool that can move money", because the prompt block "guides Claude and doesn't enforce anything" ([Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices), "Payments, account numbers, and financial records").

### 2.7 Output size: budget every tool and spill the excess to a file

- Use pagination, range selection, filtering and truncation with sensible defaults; Claude Code caps tool responses at 25,000 tokens by default, and truncation messages can steer the agent toward narrower queries ([Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)).
- Claude saves a result over 25,000 tokens, or text over 50,000 characters, to a file and returns an error naming the path (`docs/reference/claude-agent-sdk/source/mcp.md:898-900`). Pi truncates built-in tools at 2,000 lines or 50 KB, head for reads and tail for bash (`docs/research/agent-sdk/notes/tools.md:171-174`). Vercel and OpenAI apply no cap (`tools.md:174`).

### 2.8 Parallelism: parallel by default, serialised by resource

All in-process SDKs run a step's calls in parallel and return results in model order; only Pi lets a tool force sequential execution, and its file tools serialise per path (`agent-sdk-research.md:69`). Claude's newer models call independent tools in parallel by default, and a prompt block can raise that to about 100% or reduce it ([Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices), "Optimize parallel tool calling").

## 3. Selection degrades somewhere between 10 and 50 tools, so defer the rest

**The thresholds vary by source, but all fall in the tens.** Vercel's docs suggest five or fewer tools (`20-prompt-engineering.mdx:17`). OpenAI's guide says to "Aim for fewer than 20 functions available at the start of a turn", calling it "just a soft suggestion" ([OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling)). Anthropic recommends tool search at "10+ tools" or more than 10K tokens of definitions ([Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)). The Claude Agent SDK docs say accuracy "degrades with more than 30-50 tools", and 50 tools can use 10–20K tokens (`docs/reference/claude-agent-sdk/source/tool-search.md:15-16`). LangChain's LLM tool selector targets agents "with many tools (10+)" (`docs/reference/langchain/source/src/oss/langchain/middleware/built-in.mdx:2204-2206`). The RAG-MCP paper reports selection accuracy of 13.62% with every MCP tool in context against 43.13% with retrieval ([arXiv 2505.03275v1](https://arxiv.org/abs/2505.03275v1) abstract: "43.13% vs 13.62% baseline").

**Deferred loading has measured gains, and Anthropic keeps three to five tools always loaded.** Tool search cut definitions from about 77K to 8.7K tokens and raised MCP-eval accuracy from 49% to 74% on Opus 4 and from 79.5% to 88.1% on Opus 4.5; Anthropic advises "Keep your three to five most-used tools always loaded, defer the rest" ([Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)). Claude Code's `auto` mode turns search on once deferrable definitions reach 10% of the context window, and never defers core tools such as Bash, Read and Edit (`tool-search.md:51, 57`).

**Three implementation forms exist, and only one is provider-neutral.** Provider-native search (Anthropic `defer_loading`, OpenAI's Responses-only `toolSearchTool()`), SDK-emulated search (Vercel's `toolSearch()`, an ordinary function tool that adds matches "on the next model step"), and host-level exposure (Pi's `direct | model-only | codemode | deferred | hidden`) (`docs/research/agent-sdk/notes/tools.md:196-205`). Per-step tool filtering is the fourth option: LangChain's `LLMToolSelectorMiddleware` asks a model to pick the relevant tools first (`built-in.mdx:2202-2210`), and its guide recommends selection by "authentication state, user permissions, feature flags, or conversation stage" (`context-engineering.mdx:723-725`).

**Code mode is the other lever for heavy tool traffic.** Programmatic tool calling cut average tokens from 43,588 to 27,297 (37%) on complex research tasks and can remove 19+ inference passes for 20+ calls; it suits three or more dependent calls or large intermediate results ([Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)). Exposing MCP servers as code cut one workflow from about 150,000 to 2,000 tokens (`docs/research/agent-sdks-and-harness-design.md:103`).

**Tool-set changes break the prompt cache.** The cache prefix runs `tools`, then `system`, then `messages`, and "Modifying tool definitions (names, descriptions, parameters) invalidates the entire cache" ([Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). Vercel's `toolOrder` keeps definitions stable for caching (`tools.md:189`). Deferred tools that load mid-conversation, and per-step tool filtering, trade cache hits for smaller context; measure both.

## 4. The system prompt should be short, sectioned, stable and pitched at the right altitude

**Aim for "the minimal set of information that fully outlines your expected behavior."** Anthropic's context-engineering post describes a "right altitude" between brittle hard-coded logic and vague guidance, recommends XML tags or Markdown headers to separate sections, and advises starting minimal and adding guidance from observed failures ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). OpenAI's suggested sections are Role and Objective, Instructions, Reasoning Steps, Output Format, Examples and Context; Markdown headers are the default delimiter, XML works for documents, and JSON "performed particularly poorly" ([GPT-4.1 prompting guide](https://raw.githubusercontent.com/openai/openai-cookbook/main/examples/gpt4-1_prompting_guide.ipynb)).

**Explain why, use canonical examples, and avoid shouting.** Anthropic recommends giving the motivation behind an instruction and testing a prompt on "a colleague with minimal context" ([Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)). Use "diverse, canonical examples" rather than "a laundry list of edge cases" ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Newer Claude models are "more responsive to the system prompt", so "CRITICAL: You MUST use this tool" now overtriggers and should become "Use this tool when..." ([Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)).

**Agentic reminders measurably help on some models.** OpenAI's three reminders (persistence, use tools instead of guessing, plan before each call) raised its internal SWE-bench Verified score by close to 20%, and planning alone by 4% ([GPT-4.1 prompting guide](https://raw.githubusercontent.com/openai/openai-cookbook/main/examples/gpt4-1_prompting_guide.ipynb)). Anthropic warns that such anti-laziness prompting can overtrigger on Claude 4.6 and later ([Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)). These reminders are therefore model-specific and must be evaluated per model.

**Order the prompt for caching: static first, volatile last.** Cache writes happen at a breakpoint, so the breakpoint belongs "on the last block that is identical across requests", and a timestamp belongs in the user turn, not the system prompt ([Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). LangChain's dynamic prompts are per-call ("transient") changes (`context-engineering.mdx:46-50, 106-108`); each one is a cache miss unless it sits after the cached prefix.

**The Claude Code preset is not a default for a non-coding product.** Anthropic says to write your own prompt "for agents with a different surface, identity, or permission model", and notes that the SDK's minimal default omits the preset's safety instructions (`docs/reference/claude-agent-sdk/source/modifying-system-prompts.md:11, 17, 34`).

## 5. Each instruction belongs in exactly one of five places

| Place | Loads | Put here | Evidence |
|---|---|---|---|
| System prompt | every request | role, surface, output format, stable policy | [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) |
| Project file (CLAUDE.md / AGENTS.md) | every session, as a user message | facts needed every session: commands, conventions, layout, "always do X"; under 200 lines | [Claude Code memory](https://code.claude.com/docs/en/memory) |
| Tool description and schema | every request with the tool (or on search) | when and how to call the tool, parameter meaning, what it does not return | [Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools) |
| Skill | description every request; body on demand | multi-step procedures, reference material, scripts | [Extend Claude Code](https://code.claude.com/docs/en/features-overview) |
| Hook, gate or tool design | never in context | anything that must hold every time | [Extend Claude Code](https://code.claude.com/docs/en/features-overview) |

**The Claude Code docs give concrete triggers for each place.** Add to CLAUDE.md when Claude "makes the same mistake a second time"; move "a multi-step procedure or [something that] only matters for one part of the codebase" to a skill or path-scoped rule ([Claude Code memory](https://code.claude.com/docs/en/memory), "When to add to CLAUDE.md"). Files over 200 lines "consume more context and reduce adherence", and contradictory instructions make Claude "pick one arbitrarily" (same page, "Size", "Consistency"). CLAUDE.md "is delivered as a user message after the system prompt", with "no guarantee of strict compliance" (same page). "An instruction like 'never edit `.env`' in CLAUDE.md or a skill is a request, not a guarantee. A `PreToolUse` hook that blocks the edit is enforcement" ([Extend Claude Code](https://code.claude.com/docs/en/features-overview), "Hook vs Skill").

**Context engineering favors identifiers and just-in-time retrieval over pre-loading.** Agents should keep "lightweight identifiers (file paths, stored queries, web links, etc.)" and load data through tools; Claude Code drops CLAUDE.md in up front and uses glob and grep for the rest ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). This repo's harness research reaches the same layering: skills are "files the model reads on demand", and project trust gates loading, not execution (`docs/research/agent-harness/agent-harness-research.md:134`).

## 6. Skills are procedural memory with three-level progressive disclosure

**The format is a folder with a `SKILL.md` whose frontmatter routes the model.** At startup the agent pre-loads each skill's `name` and `description`; the body is level two and bundled files are level three ([Equipping agents with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)). Pi implements the Agent Skills specification and adds only "name, description, and path" to the system prompt (`docs/reference/pi/source/coding-agent/skills.md:7, 41-45`). Names are lowercase with hyphens, at most 64 characters; descriptions at most 1,024 (`skills.md:81`; [Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)). Claude Code truncates `description` plus `when_to_use` at 1,536 characters in its listing, and every listed skill "adds to your context on every turn" ([Claude Code skills](https://code.claude.com/docs/en/skills)).

**The description is the routing key, so write it as "what plus when", in third person.** Pi: state "both what the skill does and when it applies"; "Helps with PDFs" is not enough (`skills.md:37`). Anthropic: the description is "injected into the system prompt", must be third person, and is how Claude chooses among "potentially 100+ available Skills" ([Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)). A model "might fail to load a relevant skill", so offer an explicit `/skill:name` override (`skills.md:45`). This repo's format rule matches: "`description` says *when* to load the skill, because agents decide from the description alone" (`.agents/skills/README.md:17`).

**Keep the body short and the references one level deep.** Keep `SKILL.md` under 500 lines, split by domain, link every reference directly from `SKILL.md` (nested links get partial `head -100` reads), add a table of contents to references over 100 lines, avoid time-sensitive text, and use one term per concept ([Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)). Match "degrees of freedom" to fragility: exact scripts for fragile sequences, heuristics for open tasks (same page). Prefer bundled scripts for deterministic steps, since only their output costs tokens (same page, "Runtime environment").

**Loaded skills persist and compete for context.** In Claude Code, an invoked skill enters the conversation as one message and stays; after compaction, Claude Code re-attaches the first 5,000 tokens of each recent skill within a combined 25,000-token budget, so older skills can drop out ([Claude Code skills](https://code.claude.com/docs/en/skills)). Our harness will need an equivalent policy for skills that survive compaction.

**Skills are a context filter, not a sandbox.** Install skills only from trusted sources and audit their scripts and network instructions ([Equipping agents with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)). Claude's `skills` allowlist is "a context filter, not a sandbox", and Pi's project trust "does not limit what tool calls can access" (`agent-harness-research.md:134`). Claude Code's `allowed-tools` pre-approves tools but "does not restrict which tools are available" ([Claude Code skills](https://code.claude.com/docs/en/skills)).

### 6.1 Our five SDK skills worked for fresh agents because they were concrete and pinned

- **Structure.** Each skill has the same five sections: when to use it, a minimal setup copied from a verified example, patterns that hold, gotchas from the fact-check, and how to verify (`docs/plans/agent-skills.md:28-36`; for example `.agents/skills/claude-agent-sdk/SKILL.md:10, 14, 55, 71, 83`). Each is 83–89 lines and links to the reference instead of copying it (`.agents/skills/README.md:18`).
- **Test.** A skill counted as done only when a fresh agent given only that skill built the triage agent and passed the SDK's offline capstone test (`docs/plans/agent-skills.md:36`). All five passed on the first attempt (`docs/todos/done/K2-sdk-skills.md:67`; `docs/todos/done/K3-langchain-skill.md:130`).
- **What the fresh agents still needed.** Their reports asked for exact test recipes for each mock model, call-split and resume details, a guardrail code snippet, corrected tool-search advice and the authoritative denial record (`K2-sdk-skills.md:67`). The LangChain tester asked for four clarifications about mock behavior and the runner's lack of type-checking (`K3-langchain-skill.md:130`). The fixes replaced prose with runnable snippets: a `state.getInterruptions()` call, a typed `InputGuardrail`, and a precise `ScriptedModel` call shape (commit `7ebb21f`, `.agents/skills/openai-agents-sdk/SKILL.md`). The lesson is that gaps showed up in testing recipes and exact API shapes, not in the conceptual guidance.
- **Side benefit.** The Pi fresh-agent test found a real SDK defect, `ModelRuntime.create()` writing `~/.pi/agent/auth.json` (`K2-sdk-skills.md:67`). A fresh-agent test is therefore an integration test of the documented path as well as a test of the skill.
- **Gap.** The plan asked to "record how each test was run" (`K2-sdk-skills.md:56`), but the todos record only outcomes, not the transcripts or prompts, so a failed run cannot be replayed.

## 7. Prompts, tools and skills are tested in two layers: contract tests and evals

### 7.1 Contract tests run offline against a scripted model

- Four of five SDKs ship a scripted test model (Pi `fauxProvider`, OpenAI `ScriptedModel`, Vercel `MockLanguageModelV4`, LangChain `fakeModel()`), and our harness had to mock the Messages API over HTTP for Claude (`agent-sdk-research.md:95`). Each repo example asserts one documented behavior offline (`verify/*/examples/`, such as `verify/pi/examples/02-custom-tool.ts` and `verify/vercel-ai-sdk/examples/03-tool-approval.ts`).
- What a tool-contract test should assert, from the evidence above: the schema rejects bad input with a path-level message; every failure returns `isError` with actionable text; unknown tools list alternatives; output over budget spills to a file and returns a pointer; read-only tools run in parallel and stateful ones serialise; approval gates fire (assert on the denial record, as with Claude's `permission_denials`, `.agents/skills/claude-agent-sdk/SKILL.md:62`); every `input_examples` entry validates against the schema.
- Lint the static surface too: description length and "when not to use" text, name pattern, and namespace collisions at registration (`docs/research/agent-sdk/notes/tools.md:253-254`). Claude Code's `/doctor prompt-audit` checks instruction files for "instructions written for older models", references to missing files or commands, and contradictions ([Claude Code memory](https://code.claude.com/docs/en/memory), "Audit your instruction files"), which is a model for a CI check on our prompt files.

### 7.2 Behavior is tested with evals built from real failures, graded on outcomes

- Start with "20-50 simple tasks drawn from real failures", grade "what the agent produced, not the path it took", combine code, model and human graders, keep capability suites (low pass rate) separate from regression suites (near 100%), and report pass^k for customer-facing agents ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).
- Isolate each trial in a clean environment, calibrate LLM judges against humans, give judges an "Unknown" option, and read transcripts, because "You won't know if your graders are working well unless you read the transcripts" (same source).
- For tools specifically: generate realistic multi-call tasks with verifiable outcomes, track total tool calls, tokens and tool errors, ask the agent for feedback, have a model analyze transcripts and refactor tools, and hold out a test set to avoid overfitting ([Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)).
- For skills: build evaluations before the skill, establish a no-skill baseline, write minimal instructions to close the gap, and iterate with one Claude instance writing the skill and a fresh one using it ([Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), "Build evaluations first"). That page also says "there is not currently a built-in way to run these evaluations" (same section). Observe navigation: unexpected read order, missed links and never-read files are signals (same page).
- Test each skill and prompt on every model it will run on; what works for Opus "might need more detail for Haiku" (same page).

### 7.3 A/B tests must hold the model, settings and harness fixed

Harness changes alone can swing scores widely (`docs/research/agent-sdks-and-harness-design.md`, "Harness choice can swing scores widely"), so a prompt or tool A/B must pin model ID, temperature, reasoning effort, tool set and harness version. Inspect's agent bridge does not forward generation settings such as temperature by default (`agent-sdks-and-harness-design.md:119`). Vercel recommends `temperature: 0` for tool calls and structured output (`20-prompt-engineering.mdx:89-113`), but non-determinism remains, so compare pass^k over several trials rather than single runs ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Inspect the exact request sent: Vercel exposes `request.messages`, raw HTTP bodies and provider warnings for unsupported features (`20-prompt-engineering.mdx:117-152`).

## 8. Prompts and tools are versioned artifacts coupled to model versions

**Prompts go stale when models change.** Anthropic's migration guidance says prompts written to fix undertriggering on older models now overtrigger, and that "If in doubt, use [tool]" should be removed ([Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)). Teams with evals can tune prompts for a new model "in days" rather than "weeks of testing" ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). This repo already pins each skill to an SDK version and adds "update the skill" to each reference's upgrade steps (`.agents/skills/README.md:19`; `docs/plans/agent-skills.md:49`).

**Treat a tool definition change as a breaking change to the cache and to recorded sessions.** Editing names, descriptions or parameters invalidates the whole prompt cache ([Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)), and a replayed session log that references a renamed tool hits the unknown-tool path. Skill guidance asks for an "old patterns" section rather than date-conditional text ([Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)). No primary source we reached defines a versioning scheme for prompts or tools; OpenAI's hosted prompt objects with versions were not checked because its docs were unreachable.

## Design implications for our agent

1. **Tool registry with a full contract.** Each tool declares `name` (namespaced `<service>_<verb>_<resource>`, checked against `^[a-zA-Z0-9_-]{1,64}$` and for collisions), a description of three or more sentences including when not to use it, a Standard Schema with enums and nullable fields, optional `inputExamples` (1–5, validated at registration), `effects: { readOnly, destructive, idempotent, openWorld }`, an output budget and an `exposure` (`direct | deferred | hidden`) (§2; `notes/tools.md:233-256`).
2. **Consolidate within a side-effect class, never across it.** Use an `action` parameter for related reads or related writes, but keep read-only tools separate from mutating ones so the scheduler and gate can trust the class (§2.1, §2.6).
3. **Enforce effects in code.** First-party `effects` drive parallelism and the approval gate; third-party MCP annotations may only relax a gate for trusted servers. Irreversible actions (sending, paying, deleting) are designed as "prepare" tools plus a human release, not as prompt rules (§2.6).
4. **Errors as typed results.** Every failure returns `isError: true` with the failing path, received value, and a next step; unknown tools list loadable names; skill scripts follow the same rule (§2.4).
5. **Output budget per tool, default 25K tokens, with spill-to-file.** Over budget, write the full output to the session's artifact store and return a pointer plus a narrower-query hint; offer `response_format: concise | detailed` on search-like tools (§2.5, §2.7).
6. **Defer beyond about ten tools.** Keep three to five core tools always loaded, defer the rest behind a provider-native search where available and our own `tool_search` function tool elsewhere, and A/B the cache cost of mid-session loading (§3).
7. **Prompt in sections, static first.** Role and surface, instructions with reasons, output format, a few canonical examples; no shouting; volatile data in the user turn after the cache breakpoint. Model-specific reminders (persistence, planning) live in a per-model overlay chosen by eval (§4).
8. **One home per instruction.** Always-true facts in a short project file (under 200 lines); procedures and reference in skills; enforcement in hooks and gates. Adopt the Agent Skills format unchanged with Pi-style metadata in the prompt, an explicit `/skill:name` override, and a compaction policy that re-attaches recent skills within a token budget (§5, §6).
9. **Two test layers in CI.** Offline contract tests per tool on our scripted model (schema, error text, budget, parallelism, gating, example validity) plus a static lint of descriptions and prompt files; then an eval suite of 20–50 real-failure tasks with outcome graders, separate capability and regression sets, pass^k over several trials, and a held-out split (§7).
10. **Fresh-agent tests for every skill, with recorded transcripts.** Keep the K2/K3 bar (a fresh agent passes the capstone from the skill alone), and store the prompt, model ID and transcript so failures can be replayed (§6.1).
11. **Version prompts, tool sets and skills together with the model.** Give each a content hash recorded in every session's first event and in OTel span attributes, rerun the regression suite on any change to any of them or to the model, and keep superseded behavior in "old patterns" sections rather than date conditions (§8).

## Unresolved gaps

- OpenAI's function-calling guide was unreachable in the original round; R1 (2026-11-18) read it on developers.openai.com and confirmed the "fewer than 20 functions" target. Its wording is "prevent invalid states", not "unrepresentable".
- The RAG-MCP numbers come from the abstract, read directly in R1; the paper body was not read.
- No source gives a controlled tool-count degradation curve for current models; the 5, 10, 20 and 30–50 thresholds are guidance, not shared measurements.
- No primary source defines a versioning scheme for prompts or tool definitions.
- The K2/K3 fresh-agent tests recorded outcomes but not transcripts, so the evidence for what made skills work is the testers' reports and the resulting diffs.
