# Redesign a workflow before you automate it, and give a model the loop only when a measured gap remains

The owner asked whether an AI chat, a workflow or an agent should solve a problem that redesigning the app would solve, and wants to measure some of the workflows they run (todo [U24](../../todos/done/U24-research-redesign-vs-ai.md)). Their hypothesis is that an agent can simplify a workflow, but that for a plain workflow the gain from a model in the loop is often marginal, and that defaults, fewer steps and better search may fix the real problem. This report reads the evidence on that hypothesis as of November 2026. We fetched and read the studies and posts on 2026-11-23. We read Scheibehenne et al. and Parasuraman and Manzey only at their abstracts because both are paywalled, and we did not refetch OpenAI's guide, which we know only through Chapter 1's quotation of it. The [fact-check log](fact-check-redesign-vs-ai.md) records each claim and what was read.

The hypothesis survives, with one qualification: no study we found tests it directly. The controlled studies of generative AI at work measure a model against the old way of working, and none that we found measures it against a redesign of that way. Three controlled studies compare a model with a search interface, which is a design choice but not a redesign of a workflow. The studies show that a model can help, but not that a model beats a better interface. The evidence that does compare designs comes from a different field and points the other way: a changed default raised 401(k) participation from 37% to 86% in one firm, and Hammer's 1990 case against automating a broken process is still the clearest statement of the principle. Meanwhile the production evidence on agents shows teams choosing simple, bounded designs, and the cost evidence shows agents spending several times the tokens of a chat. Added automation also carries its own costs, because people watch an automated system badly and lose the skill to take over.

Five findings follow, and each has a section below. First, the controlled studies find real gains from a model on short, self-contained tasks: a 56% time cut for a coding task and a 37% cut for a writing task. They also find a 19% slowdown for experienced developers on their own large repositories, so the gain depends on the task and not on the technology. Second, deployed agents are mostly bounded and supervised, and only about four in ten of their teams compare them with a non-agent baseline, so the production evidence cannot say how often a redesign would have done as well. Third, the evidence on defaults, steps and search is large in effect, but it comes from other settings and some of it, such as the choice-overload effect, fails to replicate on average. Fourth, a model in the loop brings a cost per run and its own errors, and an agent adds run-to-run variance on top; a redesign has errors and upkeep too, so the owner should measure both. Fifth, the owner can settle the question for one workflow with a small paired measurement of four arms, which the [measurement section](#one-workflow-can-be-measured-with-four-arms-a-paired-design-and-a-plan-written-before-the-first-run) specifies and the [worked example](#a-worked-example-on-made-up-numbers-picks-the-redesign-because-the-models-extra-gain-is-smaller-than-its-upkeep) works through on made-up numbers.

The decision rule that follows uses the owner's four outcomes. Ask first whether the work should exist in this form, and redesign it if not. Write plain code if fixed rules suffice. Add one model call inside a fixed workflow if only a judgement or a piece of language is missing. Use an agent only when the number of steps depends on what each step returns and a measurement shows the agent clears the cost and reliability bars. Chapter 1 of the book teaches a call, a workflow and a loop; this report proposes that it add the earlier question, whether the work should exist, and a plain-code outcome.

## Four outcomes, and six other terms, are used one way throughout

**Redesign** means changing the interface or the process so the problem stops arising: a better default, a removed step, a search that finds the item. **Plain code** means a program with no model in it, such as a rule, a script or a database query. **One model call in a fixed workflow** means code that fixes the steps and calls a model once, or a fixed number of times, for a judgement or a piece of language. An **agent** means a loop in which the model chooses its next step after reading the last result. These four are the outcomes of the owner's graphic, and they match the shapes in [Chapter 1](../../../apps/manual/src/content/chapters/call-workflow-loop.md), whose title is "Use the least autonomy that works: a call, a workflow, then a loop".

A **task** is one unit of work with a start and an end, such as filing one ticket. An **arm** is one way of doing the task that the measurement compares. A **run** is one attempt at a task in one arm. A **trial** is a repeat run of the same task in the same arm, used to measure whether an agent gives the same result twice. **Task time** is the seconds from the first event of a run to its last, and **steps** are the user-visible actions it takes.

## The controlled studies compare a model with the old way of working, so none shows a model beating a redesign

Five studies give the best controlled numbers on generative AI at work, and each one measures a model against the status quo. [Table 1](#table-1) lists them. In every one, the comparison group worked as before, with no model and no changed interface: customer-support agents without the assistant, professionals without ChatGPT, programmers with web search and Stack Overflow, consultants without GPT-4, developers with AI tools disallowed. A reader who wants to know whether a model beats a better interface cannot read that off these results.

<a id="table-1"></a>

| Study | Setup and size | Metric and result | Limits the authors state or show |
| --- | --- | --- | --- |
| Brynjolfsson, Li and Raymond, "Generative AI at Work" (NBER; arXiv v2, November 2024) | A chat assistant introduced in stages at one Fortune 500 software firm; 5,172 support agents in the data (3,517 never treated, 1,636 observed after treatment); 3 million chats | Resolutions per hour up 15% on average; about 30% for less-experienced or lower-skilled agents, and minimal for experienced ones | One tool, one firm, one occupation; short to medium run |
| Noy and Zhang, "Experimental Evidence on the Productivity Effects of Generative AI" (working paper, 2 March 2023) | Preregistered online experiment, 444 college-educated professionals, half given ChatGPT, on short incentivised writing tasks | Time down 37% (10 minutes from 27); grades up 0.45 standard deviations | Short, self-contained tasks "may inflate our estimates"; only direct, immediate effects |
| Peng et al., GitHub Copilot trial (arXiv, February 2023) | 95 freelance programmers recruited on Upwork, 45 given Copilot and 50 not; one task, an HTTP server in JavaScript | 35 finished; those given Copilot took 71.17 minutes against 160.89, 55.8% less (95% interval 21% to 89%) | Standardized task; no code-quality measure; authors at Microsoft Research and GitHub |

| Becker et al., METR (arXiv, July 2025) | 16 experienced open-source developers, 246 tasks of 2.0 hours on average, each task randomly assigned AI allowed or disallowed | Tasks took 19% more time with AI allowed, though developers had forecast 24% less | The authors caution against generalising; small greenfield projects or unfamiliar code may differ |

**The gains are real on short, self-contained tasks and reverse on a hard, familiar one.** Peng et al.'s programmers wrote one standard server and finished 56% faster with Copilot. Noy and Zhang's writers cut 37% from tasks the authors call "relatively short, self-contained". In METR's trial, the same kind of tool made experienced developers slower on their own repositories, which had 23,000 stars on average, and both the developers and outside experts had predicted a speed-up. The developers still believed afterwards that AI had cut their time by 20%, so their own impression of the gain had the wrong sign. METR lists the reasons it could not rule out and warns that the result "does not imply that current AI tools do not often improve developer's productivity".

**The gains also depend on whether the task lies inside what the model can do, which a redesign does not.** Dell'Acqua et al. call this the "jagged technological frontier". Inside it, consultants finished 12.2% more tasks. On the one task chosen to lie outside it, consultants with a model were 19 percentage points less likely to reach the correct answer (84.5% correct without AI against 60% and 70% with it). Brynjolfsson et al. add that the gain concentrated in novices and in rare problems, "where human agents have less baseline training and experience". In our reading, that pattern is the one a better knowledge base or search could also serve, but no arm in the study tests it.

**Two of the five studies have authors at a firm with a stake in the tool, and we read all five as working papers or preprints.** Peng et al. include authors from Microsoft Research and GitHub. Dell'Acqua et al. include three Boston Consulting Group authors and disclose that Lakhani advises the firm on AI strategy. Science published Noy and Zhang's paper in 2023 and Organization Science Dell'Acqua et al.'s in 2026, and we did not read those versions. None of this makes the numbers wrong, but it is a reason to weigh them as tests of "a model against nothing" and not as a verdict on "a model against the best design".

## Three controlled studies compare a model with a search interface, and find faster work and overreliance on wrong answers

Three studies come closer to a model-against-design comparison, because they set a chatbot against a search interface. Two were randomized and one was a counterbalanced crossover. Each one is model against search, not model against a redesign of a workflow: the search arm was a lookalike built for the study, a Bing-based tool, or a search function the authors added to the platform, and none was redesigned and then tested against the old one. [Table 2](#table-2) lists them.

<a id="table-2"></a>

| Study | Setup and size | Metric and result | Limits |
| --- | --- | --- | --- |
| Xu, Feng and Chen, "ChatGPT vs. Google" (arXiv 2307.01135, July 2023) | 112 Prolific participants randomly assigned to a ChatGPT-like or a Google-Search-like tool the authors built; 95 kept (48 and 47); three search tasks | Self-reported time for the three tasks 11.35 minutes with the chatbot against 18.75 with search; overall task performance not significantly different; the chatbot did worse on fact-checking | Both tools were replicas built for the study; time is self-reported, though server logs show the same direction (5.79 against 14.95 minutes on the tool); tasks were information lookups; the authors warn of overreliance |

**The pattern matches the controlled studies of work: the model saves time and fails on the cases it gets wrong.** Xu et al. find no significant difference in overall performance and a gap on fact-checking. Spatharioti et al. find that accuracy on the one hard task collapses without a warning. The model arm did best on routine lookups and worst on the case where it erred, which is Dell'Acqua et al.'s jagged frontier again.

**One result is a design change, and it helps.** In Spatharioti et al.'s second experiment, colour-coded highlighting of low-confidence information in the model's answer raised accuracy on the hard task from 26% to 53% or 58%, with most other measures unchanged. On that task the highlighted groups also issued more queries (3.0 and 3.6 against 2.2) and took longer to decide, so the gain cost some extra time. The authors made no change to the workflow, but the result shows that the interface around a model is itself something to measure.

**What we searched.** The three studies came from a review of this report's first draft, which named the gap. Our own queries were few: the studies named in the brief, plus one web search on search success. We did not run an exhaustive search for randomized comparisons of a model with a redesigned interface, a default or a search box, so "none that we found" is the most the report can say.

## Deployed agents are bounded and supervised, and few teams compare them with a non-agent baseline

The study that measures production agents most widely finds teams choosing the simplest design that works. Pan et al., "Measuring Agents in Production" (MAP, arXiv 2512.04123v4, 4 June 2026, ICML 2026), interviewed 20 deployment teams and surveyed 306 practitioners, of whom 86 ran systems in production or pilot, across 26 domains between April and November 2025. It finds that 68% of deployed agents execute at most 10 steps before a human intervenes (the body also says "fewer than 10"), that 70% prompt an off-the-shelf model, and that 74% depend mainly on human evaluation. Sixteen of the 20 interviewed teams used structured workflows instead of open-ended autonomous planning. The authors read this as organisations trading capability for control.

**Teams adopt agents for productivity and mostly do not test that against the alternative.** Of the practitioners with deployed agents, 80% cite increased productivity and 72% cite fewer human task-hours. Among those who had evaluated an alternative for the same goal, 83% preferred the agent. Only 38.7% of respondents compare their agent with a non-agent baseline such as existing software or human execution, and 26% report that no meaningful baseline exists. The authors say that baselines are hard to compare because the old process often mixes people, legacy software and documents. The 83% probably rests on that minority, although MAP does not say the two groups are the same, and the MAP authors list participation bias among their limits: teams joined on company policy, and survey respondents "likely skew toward our professional networks".

**Anthropic's own guidance reaches the same default.** Its December 2024 post "Building effective agents" advises: "When building applications with LLMs, we recommend finding the simplest solution possible, and only increasing complexity when needed. This might mean not building agentic systems at all." It adds that "agentic systems often trade latency and cost for better task performance", that "optimizing single LLM calls with retrieval and in-context examples is usually enough" for many applications, and that "the autonomous nature of agents means higher costs, and the potential for compounding errors" (fetched 2026-11-23 from [anthropic.com/engineering/building-effective-agents](https://www.anthropic.com/engineering/building-effective-agents)). The post is a vendor's advice to its customers, not a measurement, and it does not mention redesigning the application. We did not find a public postmortem from Cognition or another agent vendor that we could verify at its primary source, so the report cites none.

## An agent costs several times the tokens of a chat and gives different results on repeat runs

**Anthropic's own data puts an agent at about 4 times a chat's tokens and a multi-agent system at about 15 times.** The June 2025 post on its multi-agent research system says "agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats", and that "multi-agent systems require tasks where the value of the task is high enough to pay for the increased performance" (fetched 2026-11-23 from [anthropic.com/engineering/multi-agent-research-system](https://www.anthropic.com/engineering/multi-agent-research-system)). The same post reports that its multi-agent system beat a single-agent Claude Opus 4 by 90.2% on its internal research eval, and that token use alone explained 80% of the variance in performance on the BrowseComp evaluation. Those figures come from the vendor's own system and its own eval, and they describe research tasks that are broad and parallel. They are the upper end of what an agent costs, not the cost of an agent on a plain workflow.

**Repeat runs of one agent on one task disagree, and the τ-bench paper has a metric for it.** Yao et al., "τ-bench" (Sierra, arXiv 2406.12045v1, June 2024), simulate customer conversations in which an agent follows a policy and uses tools, and score the final database state. They define pass^k as the chance that all k independent trials of a task succeed, averaged over tasks, and estimate it from n trials with c successes as the average over tasks of C(c, k) / C(n, k). The best model they tested, gpt-4o with function calling, solved 48.2% of the tasks on average (61.2% in retail and 35.2% in airline), and its retail pass^8 fell below 25%. A single success rate hides that: an agent that gets a task right 8 times in 10 gets 8 trials in a row right only 17% of the time if its trials are independent (0.8^8). The models in that paper are from 2024, so the numbers show the shape of the problem and not today's rates. The paper also prices a run: $0.38 for the agent and $0.23 for the simulated user per retail task, so one trial of every task cost about $200.

**A fixed workflow can cap its cost and its variance, which an agent cannot.** In our reading, a workflow that calls a model once has a token count per run that the prompt and the input fix, so its cost varies little. An agent's token count depends on how many steps it takes, and each step sends the history so far again. The [measurement section](#one-workflow-can-be-measured-with-four-arms-a-paired-design-and-a-plan-written-before-the-first-run) shows how to measure both, and the worked example gives the arithmetic with prices dated to this month.

## The studies cannot tell the owner whether a redesign would have done as well

Four limits apply to all of the evidence above. First, no study found here compares a model with a redesign of a workflow; the three search studies compare it with an existing search interface. Second, the effects are specific to a task mix: short and standard tasks favour the model, and large, familiar and context-heavy tasks do not. Third, several studies are vendor-run or vendor-adjacent, and the production surveys select teams that kept their agents. Fourth, the studies measure speed and rated quality for people already doing the work, and most do not measure what the model's output costs to maintain: the prompt, the evals and the retraining when a model changes. MAP's interviewed teams called weight tuning "brittle to model upgrades", which suggests that the maintenance cost is real, but MAP does not measure it in hours. The owner's own measurement is therefore the only evidence that can answer the owner's question, and the measurement section says how to make it.

## A changed default moved behaviour by tens of percentage points where it was tested

The best-known defaults studies show what a redesign can do with no model at all. They come from other settings than ours, and the report uses them as evidence about the size of the effect a design change can have, not as predictions for the owner's workflows.

**In one firm, automatic enrollment lifted 401(k) participation from 37% to 86%.** Madrian and Shea studied a large US company in health care and insurance that changed its plan so that new hires were enrolled unless they opted out. Employees hired in the year before the change became eligible but had to enroll themselves, and 37% of them participated after 3 to 15 months of tenure. Of those hired in the year after, who were enrolled unless they opted out, 86% participated, and "none of the economic features of the plan changed" (NBER working paper 7682, May 2000; published in the Quarterly Journal of Economics, volume 116, 2001). The default also set the contribution rate at 3% and the fund as a money-market fund, and a substantial fraction of the new hires kept both, "even though very few employees hired before automatic enrollment picked this particular outcome". The comparison is between two yearly cohorts at one firm, not a randomised trial, and we read the working paper, not the journal version.

**A second study found the same direction for organ donation, with a controlled experiment and a cross-country comparison.** Johnson and Goldstein's Policy Forum piece in Science (302, pp. 1338–1339, 21 November 2003) reports three studies. We describe two: an online experiment with 161 respondents, each of whom answered under one of three defaults, and a comparison across countries. "Revealed donation rates were about twice as high when opting-out as when opting-in", and the opt-out rate did not differ significantly from the rate with no default. Across countries, the four opt-in countries had lower effective consent rates than the six opt-out countries, with no overlap and nearly 60 percentage points between the groups. The authors say that the cross-country gap is larger than the lab gap partly because changing the default there costs forms, calls and mail. The country comparison is observational, and the authors add a regression on donation rates that controls for other factors.

These two studies do not show that every default helps. They show that where a choice has a costly or effortful alternative, the starting option decides a large share of outcomes, and that the cost of a redesign here is a decision, not a model.

## Practitioner research says fewer form fields and a visible search box help, but states its samples only in part

Two practitioner sources measure steps and search. Both are commercial research and are labelled so.

**Baymard Institute, which sells checkout research, finds that most checkouts show far more fields than needed.** Its checkout page reports 25 rounds of usability testing with 4,400 or more participant-and-site sessions and a benchmark of 344 leading e-commerce sites. It also reports 12 quantitative studies with 20,240 participants, and it describes the usability testing as qualitative (fetched 2026-11-23 from [baymard.com/research/checkout-usability](https://baymard.com/research/checkout-usability)). Its cart-abandonment page reports that the average US checkout shows 23.48 form elements by default and that an ideal one needs 12 to 14, so most checkouts could cut 20% to 60% of the fields they show. In its survey of US online shoppers, the reasons listed for abandoning a cart, once the 42% who were "just browsing" are set aside, include "The site wanted me to create an account" (18%) and "Too long / complicated checkout process" (17%), against "Extra costs too high" (40%) ([baymard.com/lists/cart-abandonment-rate](https://baymard.com/lists/cart-abandonment-rate), 2026-11-23). It also estimates that fixing the checkout problems it documents would raise the average large site's conversion rate by 35.26%. Baymard's figure is an estimate for sites it benchmarked, not a measured before-and-after, and the page does not state the sample of the abandonment survey.

**Nielsen Norman Group, a usability consultancy, reports that a visible search box changes how people find things.** Its 2001 Alertbox "Search: Visible and Simple" says that changing the useit.com homepage from a link to a search box raised search use by 91%, and that in a study of "a large group of people" shopping on e-commerce sites the first query succeeded 51% of the time, the second 32% and the third 18% (fetched 2026-11-23 from [nngroup.com/articles/search-visible-and-simple](https://www.nngroup.com/articles/search-visible-and-simple/)). The page states no sample size or measurement method for either figure, and the data are 25 years old. We use them only as practitioner evidence that findability is a design variable.

## Hammer's case for obliterating a process before automating it is a consultant's argument with company cases

Michael Hammer, a consultant, argued in the July–August 1990 Harvard Business Review that companies spent on technology to speed up processes that should not exist. His text says: "heavy investments in information technology have delivered disappointing results—largely because companies tend to use technology to mechanize old ways of doing business". It concludes: "It is time to stop paving the cow paths. Instead of embedding outdated processes in silicon and software, we should obliterate them and start over." (read from a reprint of "Reengineering Work: Don't Automate, Obliterate", hosted at folk.idi.ntnu.no. The reprint's byline calls him president of "an information technology consulting firm", and HBR's page calls him founder of "a management research and education firm".) His cases are Ford, where reengineering accounts payable cut head count by 75% where a conventional programme would have cut 20%, and Mutual Benefit Life, where an application passed through as many as 30 steps, 5 departments and 19 people before redesign.

Two cautions apply. The cases are the author's own account of company programmes, with no control group, and we found no independent check in this round. And Hammer's remedy used technology: the redesigned MBL process gave case managers workstations that "run an expert system". His claim is therefore not "do not use software". His claim is that the process should be redesigned first, and software should serve the new process. A model in the loop of a redesigned process fits that claim, and a model laid over an unchanged process is the pattern he warns against.

## Choice overload is a warning against leaning on a famous result: the jam study does not hold on average

Iyengar and Lepper's 2000 jam study is the standard example for "fewer options". In a store, 60% (145 of 242) of passing customers stopped at a display of 24 jams and 40% (104 of 260) at a display of 6. Of those who stopped, about 30% (31 of 104) bought a jar after the 6-jam display, against 3% (4 of 145) after the 24-jam display. Counted over everyone who passed, that is about 12% (31 of 260) against 2% (4 of 242) (Journal of Personality and Social Psychology 79(6), 2000, Study 1; the paper has two more studies, which we skimmed but did not check closely). Scheibehenne, Greifeneder and Todd's meta-analysis in the Journal of Consumer Research (37(3), 2010) pooled 50 published and unpublished experiments, 63 conditions and 5,036 participants, and found "a mean effect size of virtually zero" with large variation between studies, and conditions that might produce the effect but none sufficient. We could read only that abstract, so its details are unverified here. The lesson for this report is narrow: do not cite "fewer choices always help" as a design law. A redesign still has to be measured, which is the owner's plan.

We did not use Hick's law or Fitts's law. Neither is needed for the argument, and we did not verify either at its primary source in this round.

## Added automation has its own costs, because people watch an automated system badly and lose the skill to take over

Bainbridge's "Ironies of Automation" (Automatica 19(6), 1983, pp. 775–779) names the cost. Its second irony: "the designer who tries to eliminate the operator still leaves the operator to do the tasks which the designer cannot think how to automate". Skills fade without use: "a formerly experienced operator who has been monitoring an automated process may now be an inexperienced one". And monitoring itself fails: "it is impossible for even a highly motivated human being to maintain effective visual attention towards a source of information on which very little happens, for more than about half an hour". The paper is about industrial process control, not language models, and it predates them by nearly four decades. Its argument transfers to a reviewer who approves a model's output hundreds of times a day, but the paper does not test that case.

Parasuraman and Manzey's review of complacency and bias in human use of automation (Human Factors 52(3), 2010, pp. 381–410) reports, per its abstract, that "automation complacency occurs under conditions of multiple-task load" and "cannot be overcome with simple practice", and that automation bias "cannot be prevented by training or instructions". We could read only the abstract. The METR and Dell'Acqua results in the earlier section are the same warning in experimental form: developers misjudged the sign of the effect on their own speed, and consultants did worse on the task the model got wrong.

In our reading, these sources tell the owner to count the human's supervision cost as part of a model's cost. A workflow where a person approves a model's answer is not automated; it moves the person's work from doing to checking, and checking has its own error rate.

## One workflow can be measured with four arms, a paired design and a plan written before the first run

The owner's question has a local answer that no paper can give, so the method below measures one workflow in four arms: the current interface, a redesigned interface, a fixed workflow with one model call, and an agent. The method is ours. The statistics are standard, and we checked each number in this section by arithmetic, not against a source.

**Write the plan before the first run, and commit it.** The plan names the workflow, the task set, the four arms, the five metrics, the margins that count as a win, and the rule that picks the arm. A plan written after the numbers are in tends to find the winner the author hoped for. Noy and Zhang and Dell'Acqua et al. both preregistered their studies. [The worked example](#a-worked-example-on-made-up-numbers-picks-the-redesign-because-the-models-extra-gain-is-smaller-than-its-upkeep) shows a rule written this way.

**Define each metric before collecting it.** [Table 3](#table-3) gives the five, with how to collect each and the usual trap.

<a id="table-3"></a>

| Metric | Definition | How to collect it | Trap |
| --- | --- | --- | --- |
| Task time | Seconds from the first event of a run to its last | Timestamps from the event log; a stopwatch only where no log exists | Counting only the model's latency and not the person's wait or checking time |
| Steps | User-visible actions on the shortest successful path: clicks, fields filled, confirmations | Count them from the UI path or the log. For the model arms, also count model calls and tool calls | Counting a step the person skips as often as one they take |
| Error rate | Share of runs with at least one error from a fixed list | Set the list first: wrong outcome, broken policy, harmful side effect, incomplete. A reviewer who does not know the arm checks each run against an answer set | Letting a reviewer see which arm produced the run |
| Cost per run | Model cost plus the person's time | Model cost is tokens times price, with the price's source and date; time comes from task time and a stated hourly rate | Using an old or list price, or leaving out cached and retried tokens |
| Maintenance burden | Hours per month and changes per quarter to keep the arm working | Count edits to prompts, code and settings, model-version changes and incidents from the commit and ticket history | Treating a redesign or plain code as free to keep and a prompt as free to write |

**Use a paired design: every task runs in every arm.** Take 20 to 50 real tasks from the last month's records, include the hard ones, and run each task in all four arms in a random order. A paired design cancels the difference between easy and hard tasks, which is usually larger than the difference between arms. One caution applies to the arms a person operates: a person who has done a task once remembers its answer, so give the human arms matched tasks or leave days between repeats, and say which you did.

**Report medians, spreads and the paired differences for a typical run, and use means for totals.** Task times are skewed, because a few tasks take far longer than the rest, so the median and the interquartile range describe the typical run better than the mean does. A monthly total is a sum over runs, so it needs the mean paired difference. Report the median of each arm, the median of the per-task differences, and the count of tasks where one arm was faster. Test the count with an exact sign test, which assumes nothing about the shape of the times.

**What 20 to 50 runs can and cannot show.** With 20 tasks and no ties, a two-sided exact sign test needs 15 or more tasks to go the same way for p < 0.05 (15 of 20 gives p = 0.041; 14 of 20 gives 0.115). With 50 tasks it needs 33 (p = 0.033; 32 gives 0.065). A sample of that size can confirm a gain that is large and consistent, such as "faster on almost every task". It cannot confirm a gain of a few percent. Error rates are weaker still. A Wilson 95% interval for 2 errors in 20 runs runs from 2.8% to 30.1%, and for 3 in 20 from 5.2% to 36.0%, so 20 runs cannot rank those two arms. Five errors in 50 runs gives 4.3% to 21.4%. The honest use of a small sample is to set a margin first ("no more errors than the current interface") and to report "no evidence of a difference" for anything inside the interval.

**Measure an agent's reliability with repeat trials and pass^k.** Run each task k times in the agent arm, with k of at least 3, and compute pass^k as Yao et al. define it: for a task with n trials and c successes, C(c, k) / C(n, k), averaged over tasks. For k = n it is the share of tasks that succeeded every time. A single success rate hides repeat failure, so give both model arms, the one-call workflow and the agent, the same repeat trials and hold them to the same pass^k bar. The one-call workflow's variance is usually smaller, but the measurement should show that and not assume it. Arms with no model need one trial.

**Price the runs from a dated source.** As of 2026-11-23, Anthropic's pricing page lists Claude Sonnet 5.5 at $2 per million input tokens and $10 per million output tokens, and Claude Haiku 5.5 at $0.10 and $0.50 for prompts up to 100,000 tokens ([platform.claude.com/docs/en/about-claude/pricing](https://platform.claude.com/docs/en/about-claude/pricing)). Prices change, so record the date beside every cost figure and refetch before a decision.

## A worked example on made-up numbers picks the redesign, because the model's extra gain is smaller than its upkeep

**Every number in this section is invented to show the arithmetic. None is a measurement, and no real workflow was run.** The example workflow is triaging an inbound support ticket: choose its category and owner. It uses 20 tasks and the four arms.

**The plan, written first.** An arm passes if it meets all three conditions. First, its median task time is at least 30% below the current interface's. Second, its accuracy holds: its pass^1 is at least 0.70, no more than 10 points below the current interface's single-run success rate of 0.80, and every arm with a model, the one-call workflow and the agent alike, has a pass^3 of at least 0.75. Third, its net hours per month, after maintenance, are positive at 400 runs a month. Among passing arms, take the least autonomous one, in the order redesign, plain code, one model call, agent, unless a more autonomous passing arm cuts the median time by a further 25% of the less autonomous arm's.

**The task times, in seconds, for the 20 tasks in the same order in each row.** The model arms' times come from each arm's first trial.

```text
A current UI   188  59  52 156  76 117 119 117  84  98  39 145 122  63  77  92 275 127  66  67
B redesign      90  25  26  67  34  60  48  45  39  43  20  58  52  23  34  38 121  64  24  37
C one call      87  28  22  68  31  47  43  45  32  38  20  70  55  20  29  39 126  51  29  34
D agent        127  51  29  92  47  60  89  91  43  48  18 119  67  46  58  46 206  90  61  66
```

**The medians and spreads.** Sorted, each row has 20 values, so its median is the mean of the 10th and 11th. The medians are A 95 s, B 41 s, C 38.5 s and D 60.5 s, with means of 106.95, 47.4, 45.7 and 72.7 s and interquartile ranges (by the inclusive quartile method) of 66.75 to 123.25 s for A, 32 to 58.5 for B, 29 to 52 for C and 46.75 to 90.25 for D. Against A, the redesign (B) cuts the median by 54 s, or 56.8% (41 / 95 = 0.432); the one-call workflow (C) cuts it by 56.5 s, or 59.5%; and the agent (D) cuts it by 34.5 s, or 36.3%. All three clear the 30% bar.

**The paired tests.** B is faster than A on all 20 tasks, so the exact two-sided sign test gives p = 2 / 2^20 = 1.9 × 10^-6, and the median of the 20 per-task differences is 54.5 s. B against C is a different picture. They tie on 2 tasks, leaving 18, and C is faster on 11 of those and B on 7. The exact two-sided p is 0.48, and the median per-task difference is 3.0 s. The data cannot tell B from C, and the 3-second gap (1.7 s between the means) is far inside the margin the plan set.

**The accuracy.** With errors counted as a wrong category or owner, A made 4 in 20 runs, so its success rate is 0.80, and B made 2, so its rate is 0.90. Each model arm ran three trials per task. For the agent, 14 tasks succeeded in all three trials, 3 in two, 1 in one and 2 in none. Its successful runs total 14 × 3 + 3 × 2 + 1 × 1 = 49 of 60, so pass^1 = 49 / 60 = 0.817. For pass^3, only the 14 tasks that never failed count, so pass^3 = 14 / 20 = 0.70. For k = 2 the formula gives (14 × 1 + 3 × (1/3) + 0) / 20 = 0.75, because a task with c = 2 of n = 3 contributes C(2, 2) / C(3, 2) = 1/3. For the one-call workflow, 16 tasks succeeded in all three trials, 2 in two, 1 in one and 1 in none. That is 16 × 3 + 2 × 2 + 1 = 53 of 60 runs, so pass^1 = 0.883, and pass^3 = 16 / 20 = 0.80. Both model arms clear the pass^1 bar of 0.70. The agent's pass^3 of 0.70 fails the 0.75 bar, and the workflow's 0.80 clears it. The data do not show that the agent is worse, however: the Wilson 95% intervals for pass^3 are 0.48 to 0.85 for the agent and 0.58 to 0.92 for the workflow, and they overlap. The bar, fixed before the run, is what excludes the agent, and a looser bar would admit it.

**The costs.** The one-call workflow sends 1,800 input and 150 output tokens per run. At Sonnet 5.5's $2 and $10 per million tokens on 2026-11-23, a run costs 1,800 × 2 / 1,000,000 + 150 × 10 / 1,000,000 = $0.0036 + $0.0015 = $0.0051, or $2.04 a month at 400 runs. The agent makes 6 model calls and sends 21,000 input and 1,100 output tokens in all, so a run costs $0.042 + $0.011 = $0.053, or $21.20 a month. The agent costs 10.4 times as much as the workflow, a ratio of the same order as Anthropic's 4× to 15× figures, though those compare agents with a chat.

**The time saved and the upkeep.** At 400 runs a month, an arm's hours saved against A are the mean paired difference times the runs, (106.95 − arm mean) × 400 / 3,600: B saves 6.62 hours, C 6.81 and D 3.81. Suppose maintenance, from the plan's estimates, is 0.5 hours a month for B, 2 for C and 4 for D, after one-off builds of 12, 6 and 20 hours. Net hours a month are then B 6.12, C 4.81 and D −0.19. B repays its build in 12 / 6.12 = 2.0 months, C in 6 / 4.81 = 1.2 months, and D never does.

**The decision.** B passes all three conditions. C passes all three. D fails the second, because its pass^3 is below the bar, and the third, because its net hours are negative. Between B and C, C's median of 38.5 s is 6.1% below B's 41 s, short of the 25% needed to prefer the more autonomous arm, so the rule picks B, the redesign. The choice would flip if C's median fell to 30.75 s or below, which is 25% under B's. The example also shows the owner's hypothesis at small scale: the model arm saved a little more time than the redesign and cost more to keep, so the extra gain was marginal. It does not show that this happens in general, and a real workflow may rank the arms differently.

## Four questions asked in order give the four outcomes of the owner's graphic

We did not see the owner's graphic, so the questions below are our proposal, and its wording may differ. They produce its four outcomes: redesign, plain code, one model call in a fixed workflow, and an agent.

1. **In an app you control, could a better default, fewer steps or a search that finds the item remove the problem?** If yes, the outcome is **redesign**. Ask whether the step exists only because of how the screen is built, whether a user could finish with half the fields, and whether most users pick the same value anyway.
2. **If not, can fixed rules do the whole job?** If the inputs are structured and the rule can be written down, the outcome is **plain code**: a query, a script, a validation.
3. **If not, can your code set every step from the input alone, with a model supplying only a judgement or a piece of language at set points?** A route chosen by a rule, or by one classification call, counts as set by the input. If yes, the outcome is **one model call, or a fixed number of calls, in a fixed workflow**.
4. **If not, the next step depends on what an earlier step returned, so no fixed sequence covers the cases that matter. Has a measurement shown that those cases are worth an agent's cost and that the agent clears the reliability bar?** If yes, the outcome is an **agent**, with a step cap. If the answer is no, or nobody has measured yet, the outcome is **one model call in a fixed workflow that handles the common cases and sends the rest to a person**. This workflow covers less than question 3's did, so it is not circular: the owner starts with the lower-autonomy outcome and measures the agent as a fourth arm before building it.

| Path | Q1 | Q2 | Q3 | Q4 | Outcome |
| --- | --- | --- | --- | --- | --- |
| 1 | yes | not asked | not asked | not asked | Redesign |
| 2 | no | yes | not asked | not asked | Plain code |
| 3 | no | no | yes | not asked | One model call in a fixed workflow |
| 4 | no | no | no | yes | Agent, with a step cap |
| 5 | no | no | no | no, or not measured | One model call in a fixed workflow, common cases only, the rest to a person; measure the agent |

Five paths and four outcomes: every combination of answers ends at exactly one outcome, because a "yes" stops the walk and the last question has an answer for both of its branches. The ticket-triage task in the worked example walks path 1 if the app allows a redesign, and path 3 if fixed rules cannot read the ticket text. An order-status question whose number of lookups depends on what each lookup returns walks path 4 or 5.

Chapter 1 asks different questions. It asks whether one call does the job, whether the steps are known in advance, whether the number of steps depends on what each tool returns, and, last, whether the work needs several agents. Our list adds two outcomes the chapter lacks, redesign and plain code, and its question 3 merges the chapter's first two questions, because both end in a model call that your code orders. The chapter's multi-agent question has no place in our list, because the owner's graphic has no multi-agent outcome. The questions do not replace the measurement. They tell the owner which arms to put in it.

## Each branch has evidence for it and a case where it fails

**Redesign (question 1)** rests on the defaults studies, on Hammer and on the checkout and search findings. Madrian and Shea's 37% to 86% and Johnson and Goldstein's near-doubling in the experiment show the effect size a changed start can have, and Baymard's 20% to 60% of fields removable shows how often the cost is in the screen. It fails when the owner does not control the application (a third-party tool whose interface cannot change), when the burden is the content and not the friction (reading and summarising 200 emails), and when a default locks people into a worse outcome. Madrian and Shea's 3% money-market default stuck for many employees "even though very few employees hired before automatic enrollment picked this particular outcome". A default is a choice for the user and needs the same care as any other.

**Plain code (question 2)** rests on the simplest-solution advice in Anthropic's post, on MAP's finding that 16 of 20 interviewed teams used structured workflows, and on Chapter 1's own quotation of OpenAI's guide that "a deterministic solution may suffice". It fails when the input is unstructured text or the rules are too numerous and exceptional to maintain, which is where OpenAI points agents in the same chapter.

**One model call in a fixed workflow (question 3)** rests on the studies where a model helped with a short, bounded task (Peng et al., Noy and Zhang, Dell'Acqua's inside-the-frontier tasks) and on Anthropic's statement that optimising single calls with retrieval and examples is "usually enough". It fails in three ways. The number of steps may depend on results, as in Chapter 1's order-status question. The model's errors may be costly while a tired reviewer approves them, which the automation literature predicts. And the task may lie outside the model's frontier, where Dell'Acqua's consultants did worse with it.

**Agent (question 4)** rests on Anthropic's own statement that agents suit open-ended problems where the number of steps cannot be predicted, and on MAP's evidence that teams run them in latency-tolerant, supervised, bounded settings (66% accept response times of minutes or longer). It fails on cost and variance, as the 4× and 15× multiples and the pass^8 result show, and on speed for experienced people in familiar territory, as METR's 19% slowdown shows.

**One case sits across the rule.** A model can be the redesign: a model that fills a form from free text removes the fields, which a person might call a redesign and a programmer a model call. The rule files it under question 3, since it adds a model, and the measurement will show whether it beats a plain redesign. In our reading, the useful test is always the same: what is the cheapest arm that passes?

## Chapter 1 should add one section that asks whether the work should exist

Chapter 1 sorts a task into a call, a workflow or a loop, and it already says "the simplest solution possible". It begins at the point where the owner has decided that a model will do the work. The proposed section would stand before its first shape and teach the earlier question, in the chapter's voice. We have not edited the chapter, and the text below is a proposal for the owner and for the chapter's author.

> **Ask whether the step should exist before you ask which shape runs it.** A model call is cheap to add and costly to keep, so check whether a change to the screen would remove the work. A company that changed its 401(k) plan so that new hires were enrolled unless they opted out saw participation of 86% in the new group against 37% in the group before, with no model involved [@madrian-shea]. Michael Hammer's 1990 advice to redesign a process before you automate it still stands [@hammer-obliterate]. The studies of generative AI at work compare a model with the old way of working, with none we found comparing it with a redesign of the workflow, so they cannot say which is better for your workflow [@dell-acqua; @peng-copilot]. Measure it: run twenty real tasks through the current screen, a redesigned screen, a fixed workflow with one model call and an agent, and keep the least autonomous arm that passes the margins you wrote down first.

## Measure the first workflow in four arms, then ship the cheapest arm that passes

The owner's hypothesis is a sound default and an untested claim. The default is sound because every strand of evidence we verified, from Anthropic's advice to MAP's 68% and 16 of 20, favours the simplest design that works, and because the defaults and Hammer evidence shows that the simplest design is often a change to the screen. The claim is untested because we found no study that compares a model with a redesign of a workflow, and because teams that deploy agents rarely compare them with any baseline. The remedy is cheap. Pick the workflow that bothers the owner most, write the plan and its margins, run 20 real tasks through the four arms, and ship the least autonomous arm that passes. If the redesign wins, a model has no place in that workflow. If a model arm wins by a margin that survives its upkeep, the owner has the first measured case for one.
