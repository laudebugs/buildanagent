# Approval placement and outcome contracts for multi-step agent actions (as of November 2026)

*Working material for the [sagas report](../sagas.md); the report and its [fact-check log](../fact-check-sagas.md) supersede this note where they disagree.*

Running example throughout: one agent-proposed action that (1) updates an order (e.g. marks it `refunded`), (2) issues a payment refund, and (3) emails the customer. All sources fetched 2026-11-18 with `curl -sSL --max-time 30`; page dates are given where the page states one.

## Saga theory relevant to agents: pivot, compensatable and retriable steps, countermeasures, and where an irreversible refund or email must sit

### Takeaway
A saga guarantees "all steps complete, or compensations amend the partial execution", and compensation is semantic, not a state restore. Every step before the pivot (point of no return) must be compensatable and every step after it must be retriable. In the example the refund is the pivot (Stripe can cancel only some refunds, briefly, and only via the Dashboard), the order update goes before it as a compensatable step guarded by a semantic lock, and the email goes after it as an idempotent, retriable step. An email can never be compensated, only followed by a correction email.

### Cited Findings
**Garcia-Molina and Salem, "Sagas" (SIGMOD 1987, ACM 0-89791-236-5/87/0005/0249)**
- Definition: "A LLT is a saga if it can be written as a sequence of transactions that can be interleaved with other transactions. The database management system guarantees that either all the transactions in a saga are successfully completed or compensating transactions are run to amend a partial execution." The guaranteed sequences are T1…Tn, or T1…Tj, Cj…C1. — [Sagas paper PDF (Cornell course mirror)](https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf)
- Compensation is semantic: Ci "undoes, from a semantic point of view, any of the actions performed by Ti, but does not necessarily return the database to the state that existed when the execution of Ti began". In the airline example, Ci cannot just write back the old seat count, because other transactions may have changed it in between. — [Sagas paper](https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf)
- The paper's motivating LLTs include ones that pause "for inputs from the users" (the airline transaction "pauses for customer input after each reservation"), which is the agent-with-approval case. — [Sagas paper](https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf)
- Recovery has two modes: "compensate for the executed transactions, backward recovery, or execute the missing transactions, forward recovery (Of course, forward recovery may not be an option in all situations)". Forward recovery needs save-points. — [Sagas paper](https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf)
- If a compensating transaction itself fails (for example, because of a bug), "the system is stuck it cannot abort the transaction nor can it complete it". The fallback is "manual intervention": a programmer is given "a description of the error", corrects it, and the saga continues. "Relying on manual intervention is definitely not an elegant solution, but It IS a practical one." — [Sagas paper §6](https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf)
- The paper's vocabulary has no "pivot" term. It has compensating transactions, save-points, and backward and forward recovery. (Our reading of the 11-page PDF; "pivot" does not appear in the text.) — [Sagas paper](https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf)

**Chris Richardson, microservices.io**
- The saga is "a reliably coordinated sequence of local transactions… either all steps complete successfully or, if a local transaction fails because it violates a business rule, the changes made by the completed steps are undone by compensating transactions". Coordination is by choreography or orchestration. The listed drawbacks are "lack of automatic rollback" and "lack of isolation", so "a saga developer must typical[ly] use countermeasures, which are design techniques that implement isolation". For the countermeasures the page refers to "Chapter 4/section 4.3 of my book Microservices Patterns". — [microservices.io saga pattern](https://microservices.io/patterns/data/saga.html)
- The microservices.io pattern page itself does not define pivot, retriable or compensatable transactions, or the individual countermeasures. Those come from the book and from Richardson's talks. **Secondary (search summary of Richardson's slide decks):** a pivot transaction is the "go/no-go" point, "neither compensatable nor retriable", and because it is not retriable all preceding transactions must be compensatable. Retriable transactions follow the pivot and are "guaranteed to succeed". A semantic lock is an application-level flag that a compensatable transaction sets and a retriable transaction releases. — [QCon SF slides](https://pt2.slideshare.net/chris.e.richardson/qconsf-acid-is-so-yesterday-maintaining-data-consistency-with-sagas), [Saturn 2018 slides](https://www.slideshare.net/chris.e.richardson/saturn-2018-managing-data-consistency-in-a-microservice-architecture-using-sagas) (via web-search summary, not read in full)

**Microsoft Azure Architecture Center, Saga pattern (ms.date 2025-02-25)**
- "Compensable transactions can be undone or compensated for by other transactions with the opposite effect." "Pivot transactions serve as the point of no return in the saga. After a pivot transaction succeeds, compensable transactions are no longer relevant. All subsequent actions must be completed for the system to achieve a consistent final state." The pivot "can be the last undoable, or compensable, transaction. Or it can be the first retryable operation in the saga." "Retryable transactions follow the pivot transaction. Retryable transactions are idempotent." "Irreversible or noncompensable transactions can't be undone or retried." — [Azure saga pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/saga)
- Anomalies: lost updates, dirty reads, and fuzzy (nonrepeatable) reads. Countermeasures: **semantic lock** ("application-level locks when a saga's compensable transaction uses a semaphore to indicate that an update is in progress"), **commutative updates**, **pessimistic view** ("Reorder the sequence of the saga so that data updates occur in retryable transactions to eliminate dirty reads"), **reread values** ("Confirm that data remains unchanged before you make updates. If data changes, stop the current step and restart the saga"), **version files**, and **risk-based concurrency based on value** ("use sagas for low-risk updates and distributed transactions for high-risk updates"). — [Azure saga pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/saga)

**Microsoft, Compensating Transaction pattern (ms.date 2026-04-16)**
- Compensation "can overwrite changes from other concurrent application instances… the compensating transaction must intelligently account for concurrent work". Undo steps run in reverse order by default, "might not need to undo the work in the exact reverse order", and may follow business rules ("canceling a flight reservation might not entitle the customer to a complete refund"). — [Azure compensating transaction](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)
- "Compensating transactions are eventually consistent operations and can fail. The system should record progress so that it can resume the compensating transaction from the point of failure… design each step as an idempotent command. Sometimes manual intervention is the only way to recover from a failed step. In these situations, the system should raise an alert that includes detai[ls]…" — [Azure compensating transaction](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)
- On human decision points: "When decisions are high impact or hard to automate reliably, include a human in the decision-making process." The page also says to "pause the workflow for human review before you decide whether to continue on an alternative path or trigger compensation", and that "the workflow can start compensation automatically for clear, low-risk conditions or pause for human review when the situation is ambiguous, high impact, or requires a manual decision". It "treats compensation as a last resort": retries come first, then alternatives, then compensation. — [Azure compensating transaction](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)

**Irreversibility of the example's steps**
- Stripe refunds: "you might be able to cancel a refund before it reaches the customer. Some card refunds support cancellation for a short period of time. The refund must not have been processed as a charge reversal. Only Dashboard cancellations are currently supported for card refunds." Refunds awaiting customer bank details can be cancelled until those details arrive. — [Stripe refunds docs](https://docs.stripe.com/refunds)
- Stripe idempotency: with an idempotency key, "if a connection error occurs, you can safely repeat the request without risk of creating a second object". In API v1, retries return the saved first response, "including 500 errors". Keys can be pruned after 24 hours, after which a reused key creates a new request. — [Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests)

### Inferences
- **Order the example as compensatable → pivot → retriable.** (Inference from the Azure definitions plus Stripe.)
  1. The order update goes first and is compensatable. It writes a semantic-lock status such as `refund_pending` rather than `refunded`, and its compensation restores the prior status if nothing else changed it (reread values).
  2. The refund is the pivot. It is not reliably compensatable through the API, so treat it as the point of no return, and call it with an idempotency key so that a timeout can be retried within the key's lifetime.
  3. The email goes after the pivot and must be retriable: idempotent through a message id or outbox, with a fixed recipient and pre-approved content. It cannot be compensated. Its only "countermeasure" is a follow-up correction email, which is a new external action.
  4. A final retriable step flips `refund_pending` → `refunded` and releases the lock.
- **Never put the email before the refund.** Sending "your refund is on its way" and then failing the refund leaves an uncompensatable false statement. This is the "pessimistic view" countermeasure applied to communication.
- **Partial pivot outcomes.** The Sagas paper's "manual intervention" case maps directly onto the agent case where the refund succeeded but the order compensation or the email fails irrecoverably. Code should surface that outcome to a person, not to the model's discretion.
- A refund whose result is unknown (timeout, no response) is neither success nor failure. The orchestrator should resolve it by retrying with the same idempotency key or by reading the refund state, before it decides between forward and backward recovery.

- Richardson's own definitions (book §4.3) were not read; the pivot/retriable/semantic-lock wording attributed to him comes from a search summary of his slides. Cite Azure for the definitions, or obtain the book.
- The ACM DL page (doi 10.1145/38713.38742) was not fetched; the text comes from a Cornell course mirror of the paper.
- No source was found on email "unsend" semantics. Treating email as uncompensatable is our inference, though uncontroversial.

## Where human approval goes: before the pivot, before the whole saga, or per step, and how approvals expire

### Takeaway
Vendors agree that sensitive, irreversible or financial actions need a person (OpenAI cites "authorizing large refunds"; Anthropic's computer-use docs cite "completing financial transactions"). Their APIs approve **one tool call at a time**, though, and none of them models a saga. Saga theory implies one approval of the **whole plan, taken before the first compensatable step**, covering the pivot's exact arguments and the post-pivot email text. After the pivot nothing may need a fresh human "yes", because everything after it must be retriable. This repo already binds each approval to a canonical-input hash and policy version and expires it on age or policy change (AD3). The open design point is binding to the state the plan was computed from as well, so that an approved but unexecuted plan re-validates or fails closed when that state changes.

### Cited Findings
**Vendor guidance**
- OpenAI, *A practical guide to building agents* (PDF): rate each tool "low, medium, or high—based on factors like read-only vs. write access, reversibility, required account permissions, and financial impact", and use the ratings for "pausing for guardrail checks before executing high-risk functions or escalating to a human". "High-risk actions: Actions that are sensitive, irreversible, or have high stakes should trigger human oversight until confidence in the agent's reliability grows. Examples include canceling user orders, authorizing large refunds, or making payments." — [OpenAI practical guide PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) (fetched from cdn.openai.com; openai.com itself returns 403)
- Anthropic, computer-use tool docs: recommends "Asking a human to confirm decisions that might result in meaningful real-world consequences and any tasks requiring affirmative consent, such as accepting cookies, completing financial transactions, or agreeing to terms of service". Also: "If your application asks a human to confirm consequential actions, make that check before each block runs, because a batch can complete a multistep action within one turn." — [Claude computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)
- Anthropic, *Building effective agents*: agents "can then pause for human feedback at checkpoints or when encountering blockers", and stopping conditions such as a maximum number of iterations "maintain control". It recommends "extensive testing in sandboxed environments, along with the appropriate guardrails". — [Anthropic engineering](https://www.anthropic.com/engineering/building-effective-agents)
- OpenAI Agents SDK (JS) HITL: `needsApproval` is `true` or an async predicate per tool. When a call needs approval, "the SDK pauses the run, returns `interruptions`, and lets you resume later from the same `RunState`". State can be serialized (`result.state.toString()`) and restored with `RunState.fromString(agent, serialized)`. — [OpenAI Agents SDK HITL](https://openai.github.io/openai-agents-js/guides/human-in-the-loop/)
- Same page, "Keep approval state on the server": `RunState.fromString()` "does not authenticate the snapshot or the person submitting it". The server must authenticate the reviewer ("Never obtain the authenticated identity from the approval request body"), "Do not accept replacement tool calls, arguments, approval records, or serialized state from the client", and "Atomically check ownership and consume the pending request… Concurrent or replayed submissions must not resume the same snapshot twice." Crucially: "Consumption prevents resubmitting this snapshot; it does not guarantee exactly-once tool side effects. Reconcile completed or uncertain tool side effects before initiating recovery". — [OpenAI Agents SDK HITL](https://openai.github.io/openai-agents-js/guides/human-in-the-loop/)
- Same page, "Versioning pending tasks": for long-lived approvals across agent or SDK upgrades, store your own version number with the serialized state, and run two SDK versions in parallel through package aliases. — [OpenAI Agents SDK HITL](https://openai.github.io/openai-agents-js/guides/human-in-the-loop/)
- LangGraph interrupts: on resume "the runtime restarts the entire node from the beginning—it does not resume from the exact line where interrupt was called", so "Side effects called before interrupt must be idempotent". Resume requires the same thread ID and `new Command({ resume })`. — [LangGraph interrupts](https://docs.langchain.com/oss/javascript/langgraph/interrupts)
- Microsoft Agent Framework (page ms.date 2026-10-22): wrap a function in `ApprovalRequiredAIFunction`. The agent returns `ToolApprovalRequestContent` carrying the `FunctionCallContent` (name and arguments) for the user to approve or reject, and the reply is created with `CreateResponse` on that content. — [MAF tool approval](https://learn.microsoft.com/en-us/agent-framework/agents/tools/tool-approval)
- Temporal AI Cookbook, "Human-in-the-loop AI agent" (last updated Oct 21, 2026): the Workflow uses an LLM to propose an action. If the action is risky it "pauses and waits for human approval via Temporal Signal", then "Executes the action if auto-approved (if not risky) or human approved, or cancels if rejected/timed out". It can wait "for hours, days or indefinitely" while consuming no compute, with "Durable timers". With no signal, "After 5 minutes (default), the Workflow will automatically complete with a timeout result." Signals carry a request id, so a decision binds to a specific pending request. — [Temporal HITL cookbook](https://docs.temporal.io/ai-cookbook/human-in-the-loop-python)

**This repo's positions**
- Tiers by worst-case effect under full injection: T3 external communication ("one person approves the exact text"), T4 irreversible or money ("one person below a cap; two above it", with a per-day value budget, e.g. `billing_issue_refund`), and T5 never offered. "An edited call is a new input and re-enters the pipeline." The approval card shows "the canonical arguments, the context segments that shaped them, the affected customer and amount, and the rule that required approval". Prompts are a budget, so T0 and T1 never prompt. — [docs/guides/agent.md §5](../../../guides/agent.md)
- AD2: the tier table is code, and T4 is denied while `caps` is `null`. "The v1 planner holds no refund tool (AD2)". T2–T4 register with `approvalReuse: "none"`, "so no sticky or grouped resolution can skip the person". — [docs/plans/build-agent.md AD2](../../../plans/build-agent.md)
- AD3: approval binds to "the host-signed pause" over "request id, kind, call id, tool, canonical input hash and policy version". The quorum table gives T3 one approver valid 24 h, T4 up to the cap one approver valid 24 h, and T4 above the cap "2, distinct" with at least one `billing`, valid 24 h; "The validity windows are our proposal." "A partial quorum fails closed in three cases: its window lapses, the policy version in the pause differs from the current one, or an approver is the requester or lacks a counting role." — [docs/plans/build-agent.md AD3](../../../plans/build-agent.md)
- Architecture rule: code executes every side effect, and the model proposes ("every side effect run in code behind the gate its tier sets"). — [docs/plans/build-agent.md AD1 evidence, citing agent guide §9](../../../plans/build-agent.md)

### Inferences
- **Per-step approval is wrong for a saga with a post-pivot external step.** (Inference.) If the order update and refund are approved step by step and the T3 email is approved only after the refund, an approver who rejects or edits the email leaves the saga past its pivot with a mandatory retriable step blocked on a person. That violates the "retriable after pivot" rule. All approvals a saga needs (the T4 refund amount and recipient, and the T3 email's exact text) should therefore be gathered **before the first compensatable step**, as one plan approval whose canonical hash covers every step's arguments. That is still compatible with AD3 if each step's signed pause is pre-collected, or if a "plan" kind of signed request is added.
- **The minimum is approval before the pivot, not just before the saga.** Pre-pivot steps are compensatable, so running them speculatively and compensating on rejection is safe in theory. That is why Azure lets clear, low-risk cases compensate automatically. In practice, approving up front avoids holding semantic locks while a person decides: the Sagas paper notes that a paused saga holds no database locks, but semantic locks are application-visible.
- **Approved but unexecuted plans need a precondition, not only a timer.** AD3 expires on age and policy version. Saga "reread values" suggests a third binding: a hash or version of the state the plan was computed from (order status and version, refundable balance, amount already refunded). If the state changed between approval and execution, fail closed and return `stale_approval` to the agent with a reason, and do not execute. OpenAI's server-side consumption rule (consume once, atomically) prevents double execution of one approval but, by its own words, not double side effects. Idempotency keys on the refund and email close that gap.
- **Timeouts should resolve to "not executed".** Temporal's recipe completes with a timeout result when no signal arrives. For a saga gated before the pivot, an expired approval means nothing irreversible happened, and the agent should be told exactly that.
- **No surveyed SDK has a "plan" or "saga" approval primitive.** OpenAI, LangGraph, MAF and Temporal's recipe approve single calls or single pending requests. Batch approval in the OpenAI SDK covers concurrent pending calls, not an ordered compensatable plan. (Inference from the pages read; not exhaustively verified across all SDKs.)

- No vendor source found that discusses approval placement relative to a saga pivot explicitly; the placement argument is our synthesis.
- OpenAI's developers.openai.com agent safety guide was not fetched (openai.com family returns 403). The practical-guide PDF on cdn.openai.com stands in for it.
- Anthropic's claude.com/docs guidance on "agent safety" beyond the computer-use page and *Building effective agents* was not searched further.
- No vendor documents approval expiry beyond Temporal's timer recipe. The repo's 24 h and 4 h windows are self-declared proposals.

## Result contracts: how the agent learns "completed", "failed and compensated", "compensation failed, needs a human" and "unknown/pending"

### Takeaway
Workflow engines report coarse terminal states (Step Functions: `RUNNING | SUCCEEDED | FAILED | TIMED_OUT | ABORTED | PENDING_REDRIVE` with `error` and `cause` strings; Temporal: a result or an `ApplicationFailure` with `type`, `details` and `nonRetryable`). None of them distinguishes "failed and fully compensated" from "failed, compensation incomplete", so the saga orchestrator must add that distinction to the tool result itself. The model needs a typed outcome plus four facts: what changed, what was undone, what still needs attention, and whether a retry is safe.

### Cited Findings
- AWS Step Functions `DescribeExecution`: `status` takes the values `RUNNING | SUCCEEDED | FAILED | TIMED_OUT | ABORTED | PENDING_REDRIVE`, with `error` and `cause` strings "if the state machine execution failed". `redriveStatus` is `REDRIVABLE | NOT_REDRIVABLE | REDRIVABLE_BY_MAP_RUN`, and `redriveStatusReason` gives reasons such as "Execution is SUCCEEDED and cannot be redriven" or "redrivable period exceeded". — [Step Functions DescribeExecution](https://docs.aws.amazon.com/step-functions/latest/apireference/API_DescribeExecution.html)
- Temporal (TypeScript): "The one Temporal error class that you will typically raise deliberately is `ApplicationFailure`." Activity exceptions are converted to it, so "an error's type, severity, and any additional details can be sent to the Temporal Service". `nonRetryable: true` stops automatic retries ("deliberately failing a Workflow due to bad input data"). Activities retry by default until a timeout or a non-retryable condition, after which "you could implement a Saga Pattern that uses try and catch blocks to 'unwind'". "You will only fail a Workflow by manually raising an `ApplicationFailure` from the Workflow code"; other workflow exceptions only fail the Workflow Task and are retried as bugs. — [Temporal TS failure detection](https://docs.temporal.io/develop/typescript/failure-detection)
- Temporal saga caveats: Workflow timeouts or retries can stop compensations from running, and "terminate and reset will not allow Workflow code to execute any finally or defer statements". — [Temporal blog, saga compensating actions (May 2023)](https://temporal.io/blog/compensating-actions-part-of-a-complete-breakfast-with-sagas)
- MCP 2025-11-25 tasks (core, "currently considered experimental"): `failed` includes the case where "the tool call result has `isError` set to true", with a `statusMessage` such as "Tool execution failed: API rate limit exceeded". `tasks/result` "returns exactly what the underlying request would have returned". — [MCP 2025-11-25 tasks](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks)
- Repo position: tool errors are typed `isError` results that "name the cause and the next step", plus "what not to do next". The sketched shape is `{ ok: false; isError: true; cause: string; next: string; avoid?: string }`, and the example error reads "do not guess an order". — [docs/guides/agent.md §3 and §9](../../../guides/agent.md)
- Azure: on a failed compensation, "raise an alert that includes detai[ls]" and emit "structured telemetry, including failure reason and correlation IDs". — [Azure compensating transaction](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)
- OpenAI Agents SDK: "Reconcile completed or uncertain tool side effects before initiating recovery". The SDK acknowledges an "uncertain" side-effect state. — [OpenAI Agents SDK HITL](https://openai.github.io/openai-agents-js/guides/human-in-the-loop/)

### Inferences
- **A proposed result contract for the saga tool (our design, not from any source):**
  ```ts
  type SagaOutcome =
    | { status: "completed"; operationId; effects: Effect[] }                       // all steps done
    | { status: "failed_compensated"; operationId; failedStep; cause; effects: []; undone: Effect[]; retrySafe: boolean; next }
    | { status: "failed_needs_human"; operationId; failedStep; cause; effects: Effect[]; undone: Effect[]; outstanding: Effect[]; handedOffTo; retrySafe: false; avoid }
    | { status: "pending"; operationId; phase: "awaiting_approval" | "running" | "pivot_unknown"; pollAfterMs; retrySafe: false }
    | { status: "rejected" | "stale_approval" | "expired"; operationId; reason; effects: [] }  // nothing executed
  ```
  Here `Effect = { step, kind: "order_update" | "refund" | "email", id, summary }`.
  - `effects` lists what changed and is still in force. `undone` lists what was compensated. `outstanding` lists what is half-done and owned by a person. `retrySafe` says whether calling the same tool again with the same `operationId` is idempotent.
  - `failed_compensated` and `failed_needs_human` are separate statuses because Step Functions and Temporal both fold them into `FAILED` or `ApplicationFailure`.
  - `pending` with `phase: "pivot_unknown"` covers the refund timeout. It tells the model not to re-issue the refund and not to tell the customer it failed.
- **Mapping engines onto the contract:** Temporal workflow success → `completed`. An `ApplicationFailure` thrown after a successful unwind → `failed_compensated`, with `details` carrying the `undone` list. Compensation-activity failure → `failed_needs_human`, with `nonRetryable: true`. A Step Functions `FAILED` result needs `cause` parsed into the same fields. `TIMED_OUT` and `ABORTED` map to `failed_needs_human` unless the saga records that no step started.
- **The status words are aimed at the model's next action.** In `failed_needs_human` the result should say what the model must not do (re-issue the refund, promise the customer anything), matching the repo's `avoid` field. The handoff itself is code's job.
- **MCP `isError: true` is too coarse on its own.** It marks failure but not whether side effects persist. The structured outcome belongs in `structuredContent` or the text, with `isError` true for the two failed statuses only. (Inference.)

### Gaps
- No agent SDK or framework found that standardizes a saga or compensation-aware tool result. Searching agent tooling for "compensated" outcomes found nothing primary.
- Temporal's client-side `WorkflowFailedError` wrapping was not re-read for this note; only the activity- and workflow-side `ApplicationFailure` docs were.

## Long-running actions and async results: operation ids, polling, resumption

### Takeaway
Both agent protocols now have durable task handles with a fixed state machine. In the MCP 2026-07-28 revision, Tasks moved out of the core spec into an **extension** (`io.modelcontextprotocol/tasks`, maintained in `modelcontextprotocol/ext-tasks`) with states `working | input_required | completed | failed | cancelled`. A2A 1.0.0 has `SUBMITTED, WORKING, INPUT_REQUIRED, AUTH_REQUIRED, COMPLETED, FAILED, CANCELED, REJECTED`. Temporal uses Signals to resume a waiting workflow. A saga tool should return an operation id at once, surface approval as `input_required`, and deliver the typed outcome on the terminal poll.

### Cited Findings
- **MCP 2026-07-28 Tasks:** "MCP Tasks is an extension to the core MCP specification. Host support varies by client." The full spec lives in the `modelcontextprotocol/ext-tasks` repository. Negotiation works through `io.modelcontextprotocol/tasks` in the per-request `_meta` `io.modelcontextprotocol/clientCapabilities.extensions`, and the server advertises it in `server/discover`. — [MCP 2026-07-28 Tasks](https://modelcontextprotocol.io/specification/2026-07-28/basic/utilities/tasks)
- Flow: the server returns `CreateTaskResult` (`resultType: "task"`) with `taskId`, status, `ttlMs` and `pollIntervalMs`, and "The task is durably created before the response is sent". The client polls with `tasks/get`. At `input_required` the response carries an `inputRequests` map (e.g. "an elicitation for user confirmation"), which the client answers via `tasks/update`. `tasks/cancel` is cooperative: "the task may still reach a non-`cancelled` terminal status". "`completed`, `failed`, and `cancelled` are terminal." Push updates arrive via `notifications/tasks` through `subscriptions/listen`, and "Polling is the default". Clients should "Persist task IDs" so polling resumes after a crash. Listed use cases include "Human-in-the-loop workflows. Approval gates, review steps". — [MCP 2026-07-28 Tasks](https://modelcontextprotocol.io/specification/2026-07-28/basic/utilities/tasks)
- **MCP 2025-11-25 (previous revision):** Tasks lived in the core utilities and were "currently considered experimental", with `tasks/result` and `notifications/tasks/status`. The method names differ from the 2026-07-28 extension (`tasks/update` and `notifications/tasks`), so cite the revision explicitly. — [MCP 2025-11-25 tasks](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks)
- **A2A** (latest released version 1.0.0; earlier 0.3.0, 0.2.6, 0.1.0): task states `TASK_STATE_SUBMITTED, WORKING, INPUT_REQUIRED, AUTH_REQUIRED, COMPLETED, FAILED, CANCELED, REJECTED` (plus `UNSPECIFIED`). The terminal states are `COMPLETED, FAILED, CANCELED, REJECTED`, which "cannot accept further messages". The interrupted states are `INPUT_REQUIRED` and `AUTH_REQUIRED`. Streams "MUST close when the task reaches a terminal state", and resubscription "MUST return a Task object as the first event". — [A2A specification](https://a2a-protocol.org/latest/specification/)
- **Temporal:** Signals inject the human decision into a waiting Workflow. The workflow holds `pending_request_id` and `current_decision` state, waits on a condition with a durable timer, and on timeout "will automatically complete with a timeout result". — [Temporal HITL cookbook](https://docs.temporal.io/ai-cookbook/human-in-the-loop-python)
- **Step Functions:** `DescribeExecution` on an execution ARN is the poll, and `PENDING_REDRIVE` together with `redriveStatus` tells a caller whether a failed run can resume. — [Step Functions DescribeExecution](https://docs.aws.amazon.com/step-functions/latest/apireference/API_DescribeExecution.html)

### Inferences
- **Map saga phases onto protocol states.** Awaiting the pre-pivot approval maps to MCP `input_required` or A2A `INPUT_REQUIRED`. Running maps to `working`. An approver's rejection maps to A2A `REJECTED`; MCP has no `rejected` state, so it becomes `completed` carrying `status: "rejected"` in the result (or `failed`, by design choice). Both compensation outcomes are terminal (`failed`), and the typed `SagaOutcome` in the result or error distinguishes them.
- **The pivot-unknown phase must stay non-terminal.** A refund in flight with an unknown result should stay `working` until reconciled, because terminal states cannot change in either protocol.
- **Cancellation semantics match sagas.** MCP's cooperative `tasks/cancel` ("may still reach a non-cancelled terminal status") is the right model. Cancel before the pivot leads to compensation and `cancelled`; cancel after the pivot is refused or ignored, and the saga runs forward to `completed`.
- **The agent loop should not block on approval.** Return the operation id, let the run end or continue other work, and resume on the terminal notification. This matches OpenAI's serialized `RunState` and Temporal's zero-compute wait. Our repo's harness log should record the operation id so a resumed run can poll it. (Inference; the repo's resume mechanics were not checked for this note.)
