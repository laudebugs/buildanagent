*Working material for the [server rollback report](../server-rollback.md); the report and its [fact-check log](../fact-check-server-rollback.md) supersede this note where they disagree.*

All pages below were fetched on 2026-11-18 with `curl`. Versions come from the NuGet flat-container and registration APIs on that date. Claims marked **(inference)** are mine, not the source's; claims marked **(not verified this pass)** come from prior knowledge and need a check before they go in the report.

## Temporal tables: SQL Server/Azure SQL, EF Core, PostgreSQL, MariaDB; restoring state before a tool call, and limits

### Takeaway
SQL Server/Azure SQL system-versioned temporal tables plus EF Core's `IsTemporal`/`TemporalAsOf`/`TemporalAll` give a .NET backend a built-in, per-row "state as of time T" with a documented restore recipe (query `TemporalAsOf`, re-`Add`, `SaveChanges`). MariaDB has equivalent native system versioning (and can query `AS OF TRANSACTION`). PostgreSQL still has **no native system-time versioning** even in PostgreSQL 19 (RC 2 as of 12 Nov 2026); PG 18 added only application-time constraints (`WITHOUT OVERLAPS`, `PERIOD` foreign keys), so PostgreSQL needs triggers or an extension. Restore is per table and per row, keyed on transaction begin time, and does not undo side effects outside the database.

### Cited Findings

**SQL Server / Azure SQL system-versioned temporal tables**
- A system-versioned temporal table keeps "a full history of data changes, allowing point-in-time analysis"; it has two `datetime2` period columns and a reference to a history table with a mirrored schema, into which the system stores the previous version of a row on every update or delete. Listed uses include "auditing all data changes and performing data forensics" and "reconstructing the state of the data as of any time in the past". — [Microsoft Learn: Temporal tables](https://learn.microsoft.com/en-us/sql/relational-databases/tables/temporal-tables?view=sql-server-ver17)
- Period timestamps are the **begin time of the current transaction (UTC)**: "all rows inserted within a single transaction have the same UTC time"; on update/delete the old row's `ValidTo` is set to the transaction begin time. If one transaction updates the same key several times, temporal queries return only the version before the transaction and the current row after it. — [Microsoft Learn: Temporal tables](https://learn.microsoft.com/en-us/sql/relational-databases/tables/temporal-tables?view=sql-server-ver17)
- `FOR SYSTEM_TIME` has five subclauses: `AS OF`, `FROM … TO`, `BETWEEN … AND`, `CONTAINED IN (…)`, and `ALL`; it works on a single table, through joins and through views. — [Microsoft Learn: Temporal tables](https://learn.microsoft.com/en-us/sql/relational-databases/tables/temporal-tables?view=sql-server-ver17)
- Limits: a temporal table must have a primary key; the history table can't have constraints (PK, FK, etc.); the history table must be in the same database; `TRUNCATE TABLE` isn't supported while `SYSTEM_VERSIONING` is ON; direct modification of history-table data isn't permitted; `INSTEAD OF` triggers are not allowed on either table and `AFTER` triggers only on the current table; FileTable/FILESTREAM can't be used; node/edge (graph) tables can't be temporal; regular queries see only the current table. Page last updated 2026-08-18. — [Microsoft Learn: Temporal table considerations and limitations](https://learn.microsoft.com/en-us/sql/relational-databases/tables/temporal-table-considerations-and-limitations?view=sql-server-ver17)
- Schema changes: `ALTER TABLE` add/alter/drop column propagates to the history table and takes a schema lock on both tables; `ALTER COLUMN` never runs online. Adding a computed, IDENTITY, SPARSE (with compressed history), COLUMN_SET or ROWGUIDCOL column, or making a column with existing NULLs `NOT NULL`, requires `SYSTEM_VERSIONING = OFF` first. — [Microsoft Learn: Change the schema of a system-versioned temporal table](https://learn.microsoft.com/en-us/sql/relational-databases/tables/changing-the-schema-of-a-system-versioned-temporal-table?view=sql-server-ver17)
- Retention: per-table `HISTORY_RETENTION_PERIOD` in DAYS/WEEKS/MONTHS/YEARS, default `INFINITE`; requires the database flag `is_temporal_history_retention_enabled` (default ON, but set OFF automatically after a point-in-time restore); finite retention only on history tables with a clustered rowstore or clustered columnstore index; a background task deletes aged rows (rowstore: chunks of up to 10,000; columnstore: whole row groups, typically ~1M rows). Turning `SYSTEM_VERSIONING` OFF does not preserve the retention value. Alternatives: partition sliding window, custom cleanup script. — [Microsoft Learn: Manage retention of historical data](https://learn.microsoft.com/en-us/sql/relational-databases/tables/manage-retention-of-historical-data-in-system-versioned-temporal-tables?view=sql-server-ver17)
- The history table is PAGE-compressed by default; the recommended indexing is a clustered columnstore on the history table for storage size. — [Microsoft Learn: Temporal table considerations and limitations](https://learn.microsoft.com/en-us/sql/relational-databases/tables/temporal-table-considerations-and-limitations?view=sql-server-ver17)

**EF Core temporal table support**
- EF Core supports creating temporal tables through Migrations, converting existing tables, querying history, and "restoring data from some point in the past". Configuration: `modelBuilder.Entity<Employee>().ToTable("Employees", b => b.IsTemporal());`, with optional `HasPeriodStart("ValidFrom")`, `HasPeriodEnd("ValidTo")`, `UseHistoryTable("…")`. Period columns are UTC and are shadow properties by default. — [Microsoft Learn: EF Core SQL Server temporal tables](https://learn.microsoft.com/en-us/ef/core/providers/sql-server/temporal-tables) (last updated 2026-05-12)
- Query operators: `TemporalAsOf`, `TemporalAll`, `TemporalFromTo`, `TemporalBetween`, `TemporalContainedIn`. All temporal queries are **no-tracking by default**. — [same page](https://learn.microsoft.com/en-us/ef/core/providers/sql-server/temporal-tables)
- Documented restore of a deleted row: `var employee = await context.Employees.TemporalAsOf(timeStamp2).SingleAsync(e => e.Name == "Rainbow Dash"); context.Add(employee); await context.SaveChangesAsync();` — the re-insert creates a new current row, and `TemporalAll` afterwards shows the earlier versions plus the restored one (history is preserved, not rewritten). — [same page](https://learn.microsoft.com/en-us/ef/core/providers/sql-server/temporal-tables)
- New in EF Core 11: period columns can be mapped to CLR properties (`b.HasPeriodStart(e => e.PeriodStart)`), configured `ValueGenerated.OnAddOrUpdate` so SQL Server always generates them. — [Microsoft Learn: What's new in EF Core 11](https://learn.microsoft.com/en-us/ef/core/what-is-new/ef-core-11.0/whatsnew); note the temporal-tables page (dated 2026-05-12) still says EF Core 11 is "currently in preview", which is stale now that 11.0.0 shipped on 2026-11-10 (see versions below).

**PostgreSQL**
- PostgreSQL 18 added "temporal constraints, or constraints over ranges, for PRIMARY KEY, UNIQUE, and FOREIGN KEY constraints", specified by `WITHOUT OVERLAPS` for PK/UNIQUE and `PERIOD` for foreign keys. These are application-time (valid-time) features, not system versioning. — [PostgreSQL 18 release notes](https://www.postgresql.org/docs/18/release-18.html)
- PostgreSQL 19 is not yet released: the release notes say "Release date: 2026-??-??, AS OF 2026-10-09", and the site banner announces "19 RC 2 Released" on 12 Nov 2026. PG 19 adds `range_minus_multi()`/`multirange_minus_multi()` (Paul A. Jungwirth) and a new documentation section about temporal tables. A search of the PG 19 release notes for "PORTION" (as in `UPDATE/DELETE … FOR PORTION OF`) found no match. — [PostgreSQL 19 release notes (devel)](https://www.postgresql.org/docs/devel/release-19.html)
- The new PG docs section 5.7 "Temporal Tables" covers application time (range columns, `WITHOUT OVERLAPS` keys backed by GiST and needing `btree_gist`, temporal foreign keys) and states under 5.7.2 System Time: "PostgreSQL does not currently support system time, but it could be emulated using triggers, and there are external extensions that provide such functionality." — [PostgreSQL devel docs 5.7 Temporal Tables](https://www.postgresql.org/docs/devel/ddl-temporal-tables.html)
- `temporal_tables` (arkhipov) is a C extension implementing system-period temporal tables (system period = transaction time) via a versioning trigger; latest tag v1.2.3 — [github.com/arkhipov/temporal_tables README](https://raw.githubusercontent.com/arkhipov/temporal_tables/master/README.md); tags via `git ls-remote`.
- `periods` (xocolatl) "recreates the behavior defined in SQL:2016 (originally in SQL:2011) around periods and tables with SYSTEM VERSIONING"; README badge says "compatible 9.5–15" (i.e. not advertised for 16–18). — [github.com/xocolatl/periods README](https://raw.githubusercontent.com/xocolatl/periods/master/README.md)
- nearform `temporal_tables` is a PL/pgSQL rewrite "targeting AWS RDS, Google Cloud SQL, and Azure Database for PostgreSQL where custom C extensions aren't permitted". — [github.com/nearform/temporal_tables README](https://raw.githubusercontent.com/nearform/temporal_tables/master/README.md)

**MariaDB**
- MariaDB supports `WITH SYSTEM VERSIONING` (with implicit, hidden `ROW_START`/`ROW_END` pseudo-columns or explicit ones), `ALTER TABLE … ADD/DROP SYSTEM VERSIONING`, and `FOR SYSTEM_TIME AS OF`, `BETWEEN`, `FROM … TO`, `ALL`; it can also query `FOR SYSTEM_TIME AS OF TRANSACTION 12345`. History can live in `PARTITION BY SYSTEM_TIME` partitions (by `LIMIT` or `INTERVAL`). — [MariaDB docs: System-Versioned Tables](https://mariadb.com/docs/server/reference/sql-structure/temporal-tables/system-versioned-tables)
- History removal needs the `DELETE HISTORY` privilege (`DELETE HISTORY FROM t BEFORE SYSTEM_TIME …`, including `BEFORE SYSTEM_TIME TRANSACTION`); `TRUNCATE` of a versioned table is protected per the standard; `ALTER` on a versioned table requires `system_versioning_alter_history = KEEP` (SQL:2011 does not allow `ALTER TABLE` on system-versioned tables); `system_versioning_insert_history` allows direct inserts into row start/end columns. — [same page](https://mariadb.com/docs/server/reference/sql-structure/temporal-tables/system-versioned-tables)

### Inferences
- **Restoring "the state before tool call X"** (inference): record, per tool call, the transaction begin time or (safer) `SYSUTCDATETIME()` captured just before the call's transaction starts, plus the primary keys it touched. Restore = for each touched key, read `FOR SYSTEM_TIME AS OF @before` (EF: `TemporalAsOf(before)`) and either re-`Add` (row was deleted), overwrite current values (row was updated), or `Remove` (row did not exist at `@before`). Because timestamps are the transaction *begin* time, one tool call per transaction gives clean boundaries; several tool calls in one transaction cannot be separated.
- The restore is itself a new write, so it appears in history; that is good for audit but means "undo" is a compensating write, not a rewind — the same model as compensating events in event sourcing.
- Timestamp-only restore is unsafe under concurrency: restoring a row to `AS OF T` silently overwrites any human or other-agent change made after T. A per-tool-call restore should compare the current row to the version the tool wrote (e.g. a rowversion column, or the agent's `PeriodStart`) and refuse or flag on mismatch.
- **Cascades** (inference): history captures cascaded deletes on child temporal tables too, but only if every affected table is temporal; non-temporal tables in the cascade are lost. The restore must re-insert parents before children to satisfy FKs (current tables keep their FKs; history tables have none).
- **Schema changes**: a migration between the tool call and the restore changes the history table too; restoring rows from before a dropped column loses that column. EF temporal queries map history rows through the *current* model.
- Retention cost scales with write volume; an agent that rewrites rows often produces many history rows. A finite `HISTORY_RETENTION_PERIOD` also bounds the undo window, and a point-in-time database restore silently turns retention cleanup off.
- Temporal tables do not cover side effects outside the database (emails, external APIs) — those need compensation (sagas, covered by another researcher).

## Event sourcing: Marten and KurrentDB (formerly EventStoreDB) as audit and undo mechanisms

### Takeaway
Marten (PostgreSQL) and KurrentDB both store append-only streams with optimistic concurrency and first-class correlation/causation metadata, so an agent's tool-call id can be recorded as causation and every event it produced can be found later. Neither store supports removing individual events from the middle of a stream; "undo" is normally a compensating event, with archiving/soft delete or hard delete (Marten `TombstoneStream`, KurrentDB tombstone + scavenge) reserved for whole streams or GDPR-type purges, followed by projection rebuilds.

### Cited Findings

**Marten (current 9.62.0)**
- Event metadata: `opts.Events.MetadataConfig.HeadersEnabled`, `CausationIdEnabled`, `CorrelationIdEnabled`, `UserNameEnabled` must each be enabled ("By default, Marten runs 'lean'… The database table columns for this data will not be created unless you opt-in"). "The CorrelationId and CausationId is taken automatically from any active OpenTelemetry span, so these values should just flow from ASP.NET Core requests"; `LastModifiedBy` and `Headers` must be set manually on the session and then flow to events on `SaveChangesAsync()`. Sessions also expose settable `CorrelationId` (example: `theSession.CorrelationId = "The Correlation";`). — [Marten: Event Metadata](https://martendb.io/events/metadata.html)
- `FetchForWriting<Order>(id)` loads current aggregate state for a command handler; `FetchForWriting<Order>(id, expectedVersion)` makes Marten "throw a ConcurrencyException if the expected starting version… has been incremented by some other process", with the same check re-evaluated at `SaveChangesAsync()`. A multi-stream variant returns one handle per id, with a null aggregate at version 0 for a new stream. — [Marten: Command handler workflow](https://martendb.io/scenarios/command_handler_workflow.html)
- Under Quick append, expected-version appends (`FetchForWriting()`, `AppendOptimistic()`, `StartStream()` with a version) are checked inside `mt_quick_append_events`; `StartStream` throws `ExistingStreamIdCollisionException` for an existing id. — [Marten: Appending events](https://martendb.io/events/appending.html)
- Marten "tombstone events" (in Marten's own vocabulary) are placeholder rows for sequence numbers of *failed* transactions so async projections don't stall on gaps — not a delete marker. — [Marten: Appending events](https://martendb.io/events/appending.html)
- Archiving: `session.Events.ArchiveStream(streamId)` is a soft delete (`is_archived = TRUE`; optional `UseArchivedStreamPartitioning` hot/cold partitions); archived events are excluded from LINQ queries and from the async daemon by default; appending to an archived stream throws `JasperFx.Events.ArchivedStreamException`; `UnArchiveStream()` reverses it; projected aggregates must be deleted manually if desired. Permanent deletion uses `TombstoneStream()`: "a hard delete of the stream and every event in it", e.g. "to clean up after a plan or workflow that should leave nothing behind". — [Marten: Archiving streams](https://martendb.io/events/archiving.html)
- Projection rebuilds: `daemon.RebuildProjectionAsync("Shop", ct)`; `opts.Projections.MaxConcurrentRebuildsPerDatabase` (since 9.13); `RebuildWithBulkCopy`; `UseOptimizedProjectionRebuilds` rebuilds single-stream projections stream by stream. — [Marten: Rebuilding projections](https://martendb.io/events/projections/rebuilding.html)

**KurrentDB (formerly EventStoreDB)**
- Rename: "Event Store – the company and the product – are rebranding as Kurrent… EventStoreDB will be referred to as KurrentDB; Event Store Cloud will now be called Kurrent Cloud." — [KurrentDB README](https://raw.githubusercontent.com/kurrent-io/KurrentDB/master/README.md)
- Licence: the repository's `LICENSE.md` is the **Kurrent License v1** (copyright 2011–2026 Kurrent, Inc.), a source-available licence that forbids providing the software "as a hosted or managed service" and forbids circumventing "the license mechanisms in the software". — [KurrentDB LICENSE.md](https://raw.githubusercontent.com/kurrent-io/KurrentDB/master/LICENSE.md). Some features require an enterprise licence key ("For most features that require a license, KurrentDB will not start if the feature is enabled but the license key is not provided"), with licence keys introduced for "24.10+". — [Kurrent docs: Installation](https://docs.kurrent.io/server/latest/quick-start/installation.html)
- Server versions: git tags reach `v26.2.3` (latest as of 2026-11-18 via `git ls-remote`); docs site's latest is v26.0 at docs.kurrent.io/server/latest; Kurrent blog posted "Quick preview of KurrentDB v26.2" on 20 Aug 2026. — [KurrentDB repo tags](https://github.com/kurrent-io/KurrentDB); [Kurrent blog index](https://www.kurrent.io/blog)
- Reserved event metadata: `$correlationId` ("the application-level correlation ID for the message") and `$causationId` ("the application-level causation ID"); built-in projections follow them. Stream metadata lives in `$$<stream>`; `$maxAge`, `$maxCount`, `$tb` (TruncateBefore) etc. — [Kurrent docs v26.0: Event streams](https://docs.kurrent.io/server/v26.0/features/streams.html)
- "In KurrentDB, you cannot selectively delete events from the middle of a stream. It only allows truncating the stream." Soft delete sets `$tb` to Int64 max and allows the stream to be reopened by appending; hard delete appends a `$streamDeleted` tombstone, prevents recreation, and reads return `StreamDeleted`/410; deleted events stay visible in `$all` and to `fromAll` projections until scavenged, and system-projection link events become unresolved. — [Kurrent docs v26.0: Event streams](https://docs.kurrent.io/server/v26.0/features/streams.html)
- Scavenging: deleted/expired events remain in the database and in `$all` until a scavenge, which rewrites chunks without them and removes them from the index; "Scavenging is destructive. Once a scavenge has run, you cannot recover any deleted events except from a [backup]". — [Kurrent docs v25.1: Scavenging](https://docs.kurrent.io/server/v25.1/operations/scavenge.html)
- .NET client optimistic concurrency: `AppendToStreamAsync("order-123", StreamState.NoStream, [evt])`; stream states `Any`, `NoStream`, `StreamExists`, or an expected revision noted when reading. — [Kurrent docs: .NET client, Appending events](https://docs.kurrent.io/clients/dotnet/v1.0/appending-events.html)

### Inferences
- **Recording the agent tool call** (inference): in Marten, enable `CausationIdEnabled`/`CorrelationIdEnabled`/`HeadersEnabled`, set `session.CausationId = toolCallId`, `session.CorrelationId = agentRunId` (or let them flow from an OpenTelemetry span that carries those ids) and put model/agent name in `Headers`; in KurrentDB, write `{"$causationId": toolCallId, "$correlationId": runId, ...}` into each `EventData`'s metadata JSON. Either way you can later query "all events caused by tool call X".
- **Undo by compensating event** (inference, standard event-sourcing practice): for each event caused by the tool call, append an inverse event (`PriceChangeReverted`, carrying `causationId = undoRequestId` and a reference to the reverted event) using `FetchForWriting` with the version the agent left, so a concurrent change aborts the undo with `ConcurrencyException` instead of clobbering it. Projections update normally; no rebuild needed. History stays complete for audit.
- Deleting events (Marten `TombstoneStream`, KurrentDB hard delete + scavenge) is all-or-nothing per stream and irreversible after scavenge, so it fits "the agent created a scratch stream that should not exist" or GDPR erasure, not routine undo. After any deletion, projections that consumed those events must be rebuilt (Marten `RebuildProjectionAsync`) or patched.
- A useful agent-specific pattern (inference): have the agent write to its own "proposal" stream and only promote to the real stream on approval — undo of an unapproved proposal is then `ArchiveStream`.
- Terminology trap for the report: "tombstone" means a failed-sequence placeholder in Marten's appending docs, a hard-delete via `TombstoneStream()` in Marten's archiving docs, and a `$streamDeleted` marker in KurrentDB.

## Simpler audit approaches for comparison: audit tables, EF Core interceptors, CDC

### Takeaway
An EF Core `SaveChangesInterceptor` that writes before/after values (with the tool-call id) into an audit table is the lightest way to make each agent write reversible, and it works on any provider including PostgreSQL. SQL Server CDC and Debezium read the transaction log, so they see all writers but run asynchronously, keep only a retention window (CDC default 3 days), and know nothing about tool-call ids unless the application writes them into the row.

### Cited Findings
- `ISaveChangesInterceptor` exposes `SavingChanges`/`SavedChanges`, `SaveChangesFailed`/`SaveChangesCanceled` and optimistic-concurrency hooks; `SaveChangesInterceptor` is a no-op base class. Microsoft's sample "SaveChanges can be intercepted to create an independent audit record of the changes made", registered with `.AddInterceptors(_auditingInterceptor)` writing to a separate `audit.db`, and warns: "This is not intended to be a robust auditing solution." — [Microsoft Learn: EF Core interceptors](https://learn.microsoft.com/en-us/ef/core/logging-events-diagnostics/interceptors)
- SQL Server CDC: the source is the transaction log; enabled with `sys.sp_cdc_enable_db` then per table; at most two capture instances per source table; there is "a built-in latency" between commit and appearance in change tables; `cdc.lsn_time_mapping` maps commit LSNs to transaction commit times; the cleanup job runs daily at 2 A.M. and "retains change table entries for 4320 minutes or 3 days" by default. — [Microsoft Learn: About change data capture](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/about-change-data-capture-sql-server?view=sql-server-ver17)
- Debezium release series as of Nov 2026: 3.7 "latest stable" (3.7.1.Final, 6 Nov 2026), 3.6 stable (3.6.4.Final, 10 Nov 2026), 3.8.0.Alpha1 in development (2 Nov 2026); the PostgreSQL connector supports PostgreSQL 14–18 with `decoderbufs` and `pgoutput` plug-ins; SQL Server, MariaDB and MySQL connectors are listed. — [Debezium releases](https://debezium.io/releases/)

### Inferences
- In an interceptor, `ChangeTracker.Entries()` with `OriginalValues`/`CurrentValues` per `EntityState` gives the before/after images needed to generate an inverse operation; the tool-call id can be passed via a scoped service or `DbContext` property (inference; the interceptor page does not show `OriginalValues`, so cite [EF Core change tracking](https://learn.microsoft.com/en-us/ef/core/change-tracking/) when writing — not fetched this pass).
- Interceptors only see writes made through that `DbContext`; raw SQL (`ExecuteUpdate`/`ExecuteDelete` bulk operations, other services) bypasses the change tracker, so the audit is incomplete for them (inference; check the interceptors page's notes on `ExecuteUpdate` before stating).
- CDC/Debezium are good for downstream audit streams and catching non-EF writers, but poor for synchronous "undo this tool call now" because of latency and retention; temporal tables give the same before-images synchronously and queryably.

### Gaps
- Did not verify whether `ExecuteUpdate`/`ExecuteDelete` trigger `SaveChangesInterceptor` (they do not go through SaveChanges per my prior knowledge **(not verified this pass)**).
- No primary source compared the storage cost of temporal history vs audit tables vs CDC.

### Inferences
Sketch for the report (inference, assembled from the cited APIs above; not run):
1. **Per tool call boundary.** The agent harness assigns each tool call an id. The ASP.NET Core endpoint that executes the tool opens one `DbContext` transaction per tool call and starts an OpenTelemetry `Activity` tagged with the tool-call id (so Marten's automatic correlation/causation pick it up).
2. **Record.** A `SaveChangesInterceptor` writes an `AgentChange` row per entity: tool-call id, table, key, state, original and current values, and the captured UTC time before the transaction. On SQL Server, mark the touched tables `IsTemporal()` so before-images are also kept by the engine; the audit row then only needs keys + time.
3. **Reverse (SQL Server).** For each recorded key, `TemporalAsOf(before)` → re-`Add`, overwrite, or `Remove`; first check the current row is still the version the agent wrote; save in one transaction tagged with a new "undo" causation id.
4. **Reverse (PostgreSQL without temporal).** Use the interceptor's stored before-images, or event-source the agent-writable aggregates in Marten: append compensating events with `FetchForWriting(id, versionAfterAgent)`; `ArchiveStream` for agent-created scratch streams.
5. Side effects outside the database go through compensations/sagas.
