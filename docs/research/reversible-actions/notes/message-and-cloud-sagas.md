# Sagas and compensation in MassTransit, NServiceBus and AWS Step Functions (as of November 2026)

*Working material for the [sagas report](../sagas.md); the report and its [fact-check log](../fact-check-sagas.md) supersede this note where they disagree.*

Running example used throughout: an agent action with three steps. T1 updates an order, T2 refunds a payment, T3 sends an email. When T3 fails or a human rejects the action, the compensations run: C2 reverses the refund, then C1 restores the order. Nothing can "unsend" the email, so it usually goes last, after the risky steps.

Sources were fetched on 2026-11-18 with `curl`. masstransit.io now redirects to `masstransit.massient.com`; the URLs below are the canonical `masstransit.io` paths, which redirect there. Versions come from the NuGet registration API (`https://api.nuget.org/v3/registration5-semver1/<id>/index.json`).

## MassTransit: state-machine sagas, routing slips (Courier), outbox, retries, schedules, licensing

### Takeaway
MassTransit is the only one of the three with **built-in step-by-step compensation**: routing slips. Each `IActivity<TArguments, TLog>` pairs `Execute` with `Compensate`. When an activity faults, MassTransit calls `Compensate` on the earlier activities that stored a compensation log, and publishes `RoutingSlipFaulted`, or `RoutingSlipCompensationFailed` if a compensation itself fails. Saga state machines (`MassTransitStateMachine<T>`) are the durable coordinator: they hold the human-approval wait through scheduled events and track routing slips through their events. v9 is a commercial product from Massient, Inc.; the current release is 9.3.0 (2026-11-18), while v8 (8.5.12, 2026-10-21) remains Apache-2.0.

**Saga state machines**
- A saga state machine derives from `MassTransitStateMachine<T>`, and the instance implements `SagaStateMachineInstance` with `Guid CorrelationId` and a `CurrentState` property, which can be a `State`, a string or an int set through `InstanceState(...)`. "Before being merged into the MassTransit codebase, saga state machines were a separate project known as Automatonymous. From MassTransit v8 onwards, saga state machines are part of the main assembly." — [Create a saga state machine](https://masstransit.io/documentation/patterns/saga/state-machine)
- The building blocks include `Finalize()`, which marks the workflow complete, and `SetCompletedWhenFinalized()`, which removes finalized instances from the repository — [Saga State Machines concepts](https://masstransit.io/concepts/saga-state-machines/)
- Persistence: the docs list saga repositories for Azure Cosmos, Azure Service Bus (message session), Azure Table, Dapper, DynamoDB, Entity Framework, Marten, MongoDB, NHibernate and Redis — [Saga configuration (site navigation)](https://masstransit.io/configuration/saga/)
- Repositories are either identity-only, which correlate only on `CorrelationId` (for example Redis or Azure Service Bus sessions), or query repositories (Entity Framework, NHibernate, Marten). Optimistic concurrency "is recommended" for almost every scenario, with a retry policy for concurrency exceptions — [Saga State Machines concepts](https://masstransit.io/concepts/saga-state-machines/)
- The docs explain why sagas need an outbox: if the repository throws a concurrency exception after the saga has published, "they were already published, but the saga state has not been updated … This issue … can be solved by postponing the message publish and send operations until all persistence work is done … called an outbox." — [Saga State Machines concepts](https://masstransit.io/concepts/saga-state-machines/)

**Routing slips (Courier): the built-in compensation**
- "MassTransit Routing Slips address this challenge by enabling distributed transactions with fault compensation." Compensation can be "through traditional rollbacks or by performing offsetting operations." — [Routing Slips concept](https://masstransit.io/documentation/concepts/routing-slips)
- A routing slip carries "an itinerary that contains an ordered list of activities," "an activity log that contains an ordered list of completed activities," "a compensation log that contains data related to completed activities that can be compensated if the routing slip faults," variables, subscriptions and exceptions — [Routing Slips concept](https://masstransit.io/documentation/concepts/routing-slips)
- Interfaces: `IActivity<TArguments, TLog>` (with `Execute` and `Compensate`) and `IExecuteActivity<TArguments>` (execute only). "When an activity fails, the Compensate method is called for previously executed activities in the routing slip that stored compensation data. If an activity does not store any compensation data, the Compensate method is never called." Compensate returns `compensation.Compensated()`, or `Failed(...)` if it cannot undo the step — [Create a routing slip activity](https://masstransit.io/guides/routing-slips/)
- Execution results are `Completed` (optionally with a log), `Faulted`, `Terminate` (stop without fault) and `ReviseItinerary` (add activities at runtime). A thrown exception becomes a fault, and "a RoutingSlipFaulted event will be published" — [Create a routing slip activity](https://masstransit.io/guides/routing-slips/)
- Each compensating activity gets **two receive endpoints**, one for execute and one for compensate, each with its own retry policy (`ConfigureExecuteEndpoint` and `ConfigureCompensateEndpoint`) — [Routing slip activity configuration](https://masstransit.io/configuration/routing-slip-activity/)
- Execution: `IRoutingSlipExecutor.Execute(routingSlip)` or `bus.Execute(routingSlip)`, with a `TrackingNumber`. Slip-level events are `RoutingSlipCompleted`, `RoutingSlipFaulted` and `RoutingSlipCompensationFailed`. Activity-level events are `RoutingSlipActivityCompleted`, `…Faulted`, `…Compensated` and `…CompensationFailed` — [Execute a routing slip](https://masstransit.io/guides/routing-slips/execute/)
- "Because Routing Slips carry their state on the wire, it's not possible to query the state of a currently executing routing slip." The documented pattern is a saga state machine that correlates on `TrackingNumber` and subscribes with `builder.AddSubscription(address, RoutingSlipEvents.Completed | …)` — [Track using a saga](https://masstransit.io/guides/routing-slips/monitor-using-a-saga/)
- `AddSubscription` can also send a custom message such as `OrderProcessingCompleted` to an address the caller chooses on completion — [Build a routing slip](https://masstransit.io/guides/routing-slips/build/)

**Outbox, retries and redelivery**
- In-memory outbox: `UseInMemoryOutbox(context)` buffers messages sent or published from `ConsumeContext` until the consumer succeeds. Transactional outbox: a **Consumer Outbox** ("combines an inbox, which detects duplicate received messages, with an outbox") and a **Bus Outbox** (messages sent from a container scope such as an ASP.NET request). These are available for Entity Framework Core and MongoDB. `DisableDuplicateDetection` was added in v9.1, and the bus outbox delivery back-off in v9.2.1 — [Outbox configuration](https://masstransit.io/documentation/configuration/middleware/outbox)
- The 9.2 changelog adds `ITransactionalOutbox`, which lets code explicitly commit or abort the active transactional outbox scope, and support for multiple DbContexts in the EF bus outbox — [Change Log](https://masstransit.io/reference/change-log/)
- Retry: `UseMessageRetry(r => r.Immediate(5))`. Redelivery ("second-level retry"): `UseDelayedRedelivery(r => r.Intervals(5m, 15m, 30m))`, which on RabbitMQ needs the delayed-exchange plug-in. A plug-in-free alternative is `UseQueueBasedDelayedRedelivery`. "Redelivery controls when consumer work is attempted again; it does not control messages produced by a failed attempt … configure an outbox" — [Redelivery](https://masstransit.io/configuration/middleware/redelivery/); [Retry](https://masstransit.io/configuration/middleware/retry/)

**Timeouts and schedules (human approval)**
- `Schedule(() => OrderCompletionTimeout, instance => instance.OrderCompletionTimeoutTokenId, s => { s.Delay = TimeSpan.FromDays(30); … })`. The token id stored on the saga instance "can later be used to unschedule the event." The bus "must be configured to include a message scheduler" (transport-native scheduling, Quartz.NET or Hangfire) — [State Machine Scheduled Events](https://masstransit.io/guides/saga-state-machines/schedule-event/); scheduler options are listed in the navigation at [Schedulers](https://masstransit.io/configuration/schedulers/)

### Inferences
- For the running example, the natural MassTransit design is a routing slip with `UpdateOrder` (compensating), `RefundPayment` (compensating) and `SendEmail` (an `IExecuteActivity` with no compensation), launched and monitored by a saga state machine. The saga holds the human-approval wait: a `Schedule` timeout plus an `Approved`/`Rejected` event, persisted in the saga repository. The routing slip is executed only after approval.
- Compensation ordering: the docs describe an "ordered list" compensation log and say compensation runs on "previously executed activities." **They do not state "reverse order" explicitly** in the pages fetched. Reverse (LIFO) order is the conventional reading of the routing-slip pattern; confirm it against the source or a test before stating it as fact.
- The caller learns the outcome from events, not from a return value. `RoutingSlipCompleted` means success. `RoutingSlipFaulted` means a step failed and compensation ran successfully, so "failed but compensated." `RoutingSlipCompensationFailed` means compensation itself failed and the slip needs manual repair. The three-way distinction exists natively.
- State-machine sagas on their own have no compensation primitive. You hand-write compensation as `When(PaymentFailed).Send(new RestoreOrder…)` behaviours. This is inferred from the absence of a compensation API on the state-machine pages fetched.

## NServiceBus (Particular Software): sagas, timeouts, outbox, recoverability, licensing

### Takeaway
NServiceBus sagas (`Saga<TData>`, `IAmStartedByMessages<T>`, `ConfigureHowToFindSaga`, `RequestTimeout<T>`, `MarkAsComplete`, `ReplyToOriginator`) are durable message-driven state machines with **no built-in compensation**. You write compensation as explicit command messages that the saga sends to handlers, and Particular's guidance forbids I/O inside the saga itself. The outbox provides exactly-once *processing* semantics via deduplication on `MessageId`. Recoverability performs immediate and then delayed retries before moving the message to the error queue. The current release is 10.2.9 (2026-09-03). The licence is RPL 1.5 or a commercial agreement, and runtime does not enforce it.

### Cited Findings
**Versions and licensing**
- NuGet `NServiceBus`: **10.2.9 (2026-09-03)** is the latest stable; 10.0.0 shipped 2026-01-29, 10.1.0 on 2026-02-06 and 10.2.0 on 2026-05-21. On 9.x, 9.2.12 shipped 2026-06-17. No 11.x packages are listed — [NuGet registration, NServiceBus](https://api.nuget.org/v3/registration5-semver1/nservicebus/page/9.0.5/10.2.9.json); [NuGet flat container](https://api.nuget.org/v3-flatcontainer/nservicebus/index.json)
- `NServiceBus.Persistence.Sql` latest is 9.0.7 — [NuGet flat container](https://api.nuget.org/v3-flatcontainer/nservicebus.persistence.sql/index.json)
- Support table: 10.2.x is Current (released 2026-05-21); 10.1.x is in mainstream support until 2026-11-21; 9.2.x is in mainstream support until 2028-01-29 and extended support until 2030-01-29; 8.2.x is in extended support until 2028-04-16. Policy: "Major versions are supported for two years after the release of the next major version"; minors for six months after the next minor — [Support policy](https://docs.particular.net/nservicebus/upgrades/support-policy)
- Licence: the source and binaries are under the "Reciprocal Public License 1.5 (RPL1.5)". If you do not want to release your source under those terms, you use them under the commercial License Agreement — [NServiceBus LICENSE.md](https://raw.githubusercontent.com/Particular/NServiceBus/master/LICENSE.md)
- Runtime behaviour: "No technical limitations are enforced at runtime when either no license is found, invalid or corrupt license data is provided, or a license has expired." The licence is read once at startup. It is configured with `endpointConfiguration.License(...)`, `LicensePath(...)`, a `license.xml` file or the `PARTICULARSOFTWARE_LICENSE` environment variable. RSA-4096/SHA-256 signed licences need 9.2.12+, 10.0.5+, 10.1.7+ or 10.2.6+ — [Licensing](https://docs.particular.net/nservicebus/licensing/)

**Sagas**
- "With NServiceBus, behavior is specified by writing a class that inherits from Saga<T> where T is the saga data class." The canonical example is `OrderSaga : Saga<OrderSagaData>, IAmStartedByMessages<StartOrder>, IHandleMessages<CompleteOrder>`, with `ConfigureHowToFindSaga(SagaPropertyMapper<OrderSagaData> mapper)` and `mapper.MapSaga(saga => saga.OrderId).ToMessage<StartOrder>(m => m.OrderId)…`, and `MarkAsComplete()`. Saga data derives from `ContainSagaData`, and all public get/set properties are persisted. The docs page is versioned for NServiceBus 10.x — [Sagas](https://docs.particular.net/nservicebus/sagas/)
- "Sagas are, in essence, a message-driven state machine." Several `IAmStartedByMessages<T>` interfaces handle out-of-order delivery — [Sagas](https://docs.particular.net/nservicebus/sagas/)
- "A saga should only interact with its own internal state and send or publish messages. It must not perform any I/O operations." For external systems, sagas should "Send (command) messages to dedicated message handlers" that "execute the … long-running external operations and reply the result back to the saga" — [Sagas: Avoid External Resource Access](https://docs.particular.net/nservicebus/sagas/)
- Reporting to the caller: "Using Reply() or Return() will send a message to the current messages' caller. The saga data also contains the original client's return address and the message ID of the original request." `ReplyToOriginator(context, msg)` replies to whoever started the saga — [Sagas: Notifying callers of status](https://docs.particular.net/nservicebus/sagas/)
- Consistency: if the persistence can share the receive transaction (DTC, or SQL Server transport with SQL persistence), the message receive, sends and saga update are atomic. Otherwise (Azure Storage, CosmosDB) the docs say to enable the outbox, complete from a timeout, or use soft delete — [Sagas: Consistency considerations](https://docs.particular.net/nservicebus/sagas/)

**Timeouts**
- `IHandleTimeouts<MyCustomTimeout>` together with `RequestTimeout<MyCustomTimeout>(context, TimeSpan.FromHours(1))` "sends a timeout message, which is delivered after the specified delay or at the specified time" — [Saga timeouts](https://docs.particular.net/nservicebus/sagas/timeouts)
- "After a timeout has been requested, it cannot be changed (i.e. rescheduled) or revoked." The saga ignores stale timeouts using flags in its data. Timeouts queued after `MarkAsComplete` are ignored — [Saga timeouts](https://docs.particular.net/nservicebus/sagas/timeouts)

**Outbox**
- The outbox runs in two phases. Phase 1 deduplicates by `MessageId`, then stores the outgoing messages and the business data changes "in a single transaction." Phase 2 dispatches the messages and marks them sent. Duplicates "will be deduplicated by the outbox feature … in the endpoint that receives them." The transport transaction mode must be `ReceiveOnly`. Messages sent from outside a handler (for example a Web API) cannot be deduplicated unless they reuse the same `MessageId` — [Outbox](https://docs.particular.net/nservicebus/outbox/)

**Recoverability**
- "By default, up to five immediate retries are performed." Delayed retries default to 10 s, 20 s and 30 s, with a full round of immediate retries in each cycle. The delay between two delayed retries is capped at 24 hours. After both levels fail, the message moves to the error queue. Unrecoverable exceptions skip retries; by default only `MessageDeserializationException` counts, and more can be added with `recoverability.AddUnrecoverableException<T>()`. Automatic rate-limiting acts as a circuit breaker during outages — [Recoverability](https://docs.particular.net/nservicebus/recoverability/)

### Inferences
- For the running example, one saga (`AgentActionSaga`) sends `UpdateOrder`, waits for `OrderUpdated`, sends `RefundPayment` and so on. On a failure reply, or a `Rejected` approval message, it sends `RevertRefund` and then `RestoreOrder`. The ordering is whatever the saga author codes, typically reverse order tracked by flags in saga data. **Compensation is entirely hand-written.** No `Compensate` API or routing slip exists in the NServiceBus docs fetched.
- Approval wait: a saga parked between messages is just a persisted row, and the docs note that indefinitely-running sagas are "functionally equivalent to maintaining any other business entity record." An approval can wait indefinitely, with `RequestTimeout` as the deadline. Because timeouts cannot be revoked, the timeout handler must check state.
- Outcome reporting is by messages (`ReplyToOriginator`, or published events such as `AgentActionCompensated`). The "succeeded / failed / compensated" distinction exists only if the author defines message types for each.
- A failed *compensation* command follows normal recoverability: it is retried and then lands in the error queue, where an operator can retry it (via ServicePulse, a Particular product; not verified in this session).

### Gaps
- No NServiceBus page fetched mentions "compensation" explicitly. The "explicit messages" conclusion rests on the saga I/O guidance quoted above.
- Commercial pricing (particular.net/pricing) was not fetched.

## AWS Step Functions: Standard vs Express, Retry/Catch, saga pattern, callbacks, variables/JSONata, execution status

### Takeaway
Step Functions has no "saga" or "compensate" keyword. Compensation is **declarative but hand-wired**: each forward Task's `Catch` routes to a chain of compensating Task states, which ends in a `Fail` state. AWS Prescriptive Guidance documents exactly this as the saga orchestration pattern, using Standard workflows. Standard workflows run up to one year with exactly-once state execution and 90-day execution history. They are the only type that supports `.waitForTaskToken` callbacks for human approval. The caller sees `SUCCEEDED`, `FAILED`, `TIMED_OUT`, `ABORTED` or `PENDING_REDRIVE`. There is no native "compensated" status, so "failed after compensation" must be encoded in the `Fail` state's error and cause or in the output.

### Cited Findings
**Workflow types**
- Standard workflows are "exactly-once … tasks and states are never run more than once, unless you have specified Retry behavior in ASL," which suits "non-idempotent actions, such as … processing payments." They run up to one year, and their execution history is retrievable "for up to 90 days after your execution completes." Express workflows run up to five minutes. Asynchronous Express is at-least-once and Synchronous Express at-most-once. Express history is inspected through CloudWatch Logs — [Choosing workflow type](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-standard-vs-express.html)
- "Express Workflows only support Request Response integrations." `.waitForTaskToken` is marked "Standard" only in the integration table — [Integrating services / integration patterns](https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html)
- Quotas: maximum execution history is 25,000 events, and "If the execution history reaches this quota, the execution will fail." History is retained 90 days after close, reducible to 30 days by request — [Service quotas](https://docs.aws.amazon.com/step-functions/latest/dg/service-quotas.html)

**Retry and Catch**
- Task, Parallel and Map states can have `Retry` (fields `ErrorEquals`, `IntervalSeconds` default 1, `MaxAttempts`, `BackoffRate` default 2.0, `MaxDelaySeconds`, `JitterStrategy`) and `Catch` (fields `ErrorEquals`, `Next`, and `ResultPath` in JSONPath). Retriers and catchers are "scanned … in the order listed in the array." Catch applies "when … there is no Retry field, or if retries fail to resolve the error." `States.ALL` must be alone and last. `States.TaskFailed` matches everything except `States.Timeout` — [Handling errors](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html)
- On redrive, the retry counts for re-run states reset to 0 — [Handling errors](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html)

**The saga pattern**
- AWS Prescriptive Guidance, "Saga orchestration": "The Revert Payment, Revert Inventory, and Remove Order Lambda functions indicate the compensatory transactions that the orchestrator runs when any step in the workflow fails. If the workflow fails at the Update Inventory step, the orchestrator calls the Revert Inventory and Remove Order steps before returning a Fail state to the caller." "The sample solution uses the standard workflow in Step Functions." — [Saga orchestration pattern](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/saga-orchestration.html)
- The CDK (C#) sample wires the compensations as explicit `.Next` chains: `revertInventoryTask … .Next(removeOrderTask)`, and `removeOrderTask … .Next(failState)`. Choice states route on `$.Status` (for example `"ORDER_PLACED"`). The code is in [aws-samples/saga-orchestration-netcore-blog](https://github.com/aws-samples/saga-orchestration-netcore-blog) — [Saga orchestration pattern](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/saga-orchestration.html)
- The same page lists the drawbacks: participants must be idempotent, compensations add latency, and the orchestrator can be a single point of failure. It says Step Functions mitigates that last one with multi-AZ fault tolerance — [Saga orchestration pattern](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/saga-orchestration.html)

**Callbacks for human approval**
- "Callback tasks provide a way to pause a workflow until a task token is returned. A task might need to wait for a human approval … you can pause Step Functions until the workflow execution reaches the one year service quota." The task resumes on `SendTaskSuccess` or `SendTaskFailure`. The token comes from `$$.Task.Token` (for example `"Resource": "arn:aws:states:::sqs:sendMessage.waitForTaskToken"`). Tokens only work from principals in the same AWS account. A heartbeat timeout is recommended so the task does not wait indefinitely — [Wait for a Callback with Task Token](https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html)

**Variables and JSONata**
- "Step Functions recently added variables and JSONata to manage state and transform data." `Assign` is supported on Pass, Task, Map, Parallel, Choice and Wait, and up to 256 KiB can be stored per state. The reserved variable `$states` has `.input`, `.result`, `.errorOutput` and `.context`. "$states.errorOutput can be used in the Catch field's Assign or Output." Variables have workflow-local scope, and Parallel and Map branches cannot see each other's variables — [Workflow variables](https://docs.aws.amazon.com/step-functions/latest/dg/workflow-variables.html)

**Execution status and redrive**
- `DescribeExecution.status` takes the values `RUNNING | SUCCEEDED | FAILED | TIMED_OUT | ABORTED | PENDING_REDRIVE`. It also returns `error`, `cause` ("if the state machine execution failed"), `output` and `redriveStatus` — [DescribeExecution API](https://docs.aws.amazon.com/step-functions/latest/apireference/API_DescribeExecution.html)
- "You can use redrive to restart executions of Standard Workflows that didn't complete successfully in the last 14 days," continuing "from the unsuccessful step" with the same input — [Redrive](https://docs.aws.amazon.com/step-functions/latest/dg/redrive-executions.html)

### Inferences
- For the running example: `UpdateOrder` → `RefundPayment` → `WaitForApproval` (`.waitForTaskToken`, `HeartbeatSeconds`/`TimeoutSeconds`) → `SendEmail` → `Succeed`. Each forward Task carries `Catch: [{ErrorEquals:["States.ALL"], Next:<the compensation for the previous completed step>}]`. Compensations chain in reverse: `RevertRefund` → `RestoreOrder` → `Fail` (with `Error: "ActionCompensated"`). A `SendTaskFailure` on rejection raises the error that the approval state's `Catch` routes into the chain.
- **Ordering is whatever the author wires** in `Next`. There is no compensation log, so a step that never ran must not be routed into its own compensation. Each Catch has to point at the correct entry in the chain. This is more error-prone than MassTransit's automatic log.
- Compensation failures are not distinguished natively. If a compensating Task fails without its own `Catch`, the execution ends `FAILED` with that task's error. To tell "compensated" from "compensation failed," use distinct `Fail` `Error` names or a `Succeed` state with a status field.
- The approval wait is durable: it is server-side state in a Standard execution for up to one year, with no compute held. Each wait, heartbeat and compensation adds history events toward the 25,000 cap.
- Exactly-once state transitions (Standard) still do not make the external side effects idempotent. A `Retry` on `RefundPayment` can double-refund unless the payment API takes an idempotency key. This follows from the "unless you have specified Retry" wording.

## Cross-cutting comparison for the agent action (order update, refund, email)

### Takeaway
Of the three, only MassTransit routing slips give you automatic compensation driven by a log. NServiceBus leaves compensation to hand-written messages. Step Functions makes it declarative, but you wire it by hand with `Catch` → compensating states. All three keep an approval wait durably. They report outcomes differently: MassTransit through routing-slip events (completed, faulted, compensation-failed), NServiceBus through messages the author defines, and Step Functions through execution status plus `error`/`cause`.

### Inferences
- Design lessons for our own harness: (1) Pair each tool with an optional `compensate(log)` and persist a compensation log, as MassTransit does, rather than wiring per-step catch edges by hand. (2) Model three terminal outcomes: completed, compensated (failed but rolled back) and compensation-failed (needs a human). Only MassTransit's events express all three natively. (3) Put irreversible steps (the email) last, after the approval. (4) Every compensating and forward step needs an idempotency key, because all three systems retry.
- "Failed vs compensated" is a reporting convention in NServiceBus and Step Functions. A caller polling `DescribeExecution` sees only `FAILED` unless the `Fail` state's `Error` encodes it.
