## Q1. What do the eight SDKs expose for rewind, checkpoint, fork, resume, retry, idempotency, error/denial results and compensation?

### Takeaway
Every SDK can rewind or fork the *conversation*, and two (Claude, Copilot) can restore *local files*. None restores external data. None offers compensation: no SDK has a saga, an inverse action or a "compensated" result kind. Idempotency appears in four places, and none of them covers tool side effects: OpenAI's session-history `operationId`, Cloudflare's `operationId` on turn submission and append-by-id, LangGraph's documented rule that side effects must be idempotent because a node re-runs on resume, and the harness-level "idempotent append" pattern. Tool results can carry only an error flag or a denial kind. Copilot's five-value `ToolResultType` is the richest.

### Inferences
- Rewind in all eight SDKs is *agent rewind*: it changes what the model sees, or for Claude and Copilot, local files. None of it reaches the helpdesk, so for triage every SDK leaves *data rollback* to the application.
- LangGraph is the only SDK whose docs say plainly that resume re-runs side effects. Its "make side effects idempotent or put them after the interrupt" rule is the strongest primary-source argument for idempotency keys on our write tools.
- OpenAI's `operationId` contract (same id + same transaction = no-op; same id + different transaction = fail) is a ready-made shape for a tool-call idempotency key, but OpenAI applies it only to history.
- Copilot's `rejected` / `denied` / `timeout` split is the closest SDK analogue to the `not_applied` / `unknown` outcomes. No SDK has a `compensated` or `partial` kind.

### Gaps
- Whether Vercel re-executes a tool when a client re-sends an approval response that was already consumed (a replay) is not covered by our reference or examples.
- Whether OpenAI's `RunState` resume or ADK's confirmation resume can run a call twice after a crash between execution and persistence is not tested in our harnesses.
- Copilot's file-change tracking and rewind, and Cloudflare's `agents` harness module, are unverified (d.ts only).

## Q2. What do our build plans and ADRs already specify for idempotency, undoing a write, compensation, logging a rollback and returning it to the model?

### Takeaway
The plans specify *agent rewind* in detail: an immutable log, HEAD, fork, revert, playback versus re-run, crash recovery that writes aborted results, and resumes that run an approved call "once". They specify no *data rollback*. No plan has an undo or compensation tool, a rollback entry type, a rollback result kind, or an idempotency key on tool calls. The only idempotency is `SessionStore.append`, which is idempotent by entry id.

### Inferences
- "Exactly once" in N13, N40, B15b, N35 and A15 is tested only as "the approved call runs once on a clean resume". No test covers a crash *after* the helpdesk accepted a write and *before* the `tool_result` entry is appended. N7's crash rule ("aborted error result") would then report an effect that may have happened as an error, which is the `unknown` case. A re-proposal could then duplicate it, a risk A5's "no duplicate refund" rule mitigates only for refunds.
- `Session.revert()` and `rerunFrom()` rewind the log only. After a revert past a sent reply or an escalation, the log and the helpdesk disagree, and no entry records that.
- The natural homes for rollback data already exist: `product_record` (namespaced, e.g. `triage.rollback`) for rollback records, `tool_result.details` for the structured outcome, and `WriteReceipt.id` as a handle for later compensation. All three are inferences; no plan says so.

### Gaps
- No ADR covers idempotency keys, compensation, an undo window or rollback outcomes.
- The plans do not say whether the canonical `inputHash` or `callId` should be passed to the helpdesk as an idempotency key.

## Q4. What do the three guides recommend on reversibility and approvals?

### Takeaway
The agent guide is the only document that classifies actions by reversibility: T1 "undoable", T2 "reversible but costs people's attention", T4 "cannot be undone, or moves value". It handles irreversibility with approvals, caps, limits and a kill switch, never with compensation. The SDK and harness guides recommend signed, durable pauses and an immutable log with non-executing playback.

### Cited Findings
- The tier table: T0 scoped read; **T1** "writes visible only inside the org, undoable", which runs freely and is logged; **T2** "reversible but costs people's attention", gated by a policy rule and a person above a threshold; **T3** content reaches an outsider, and one person approves the exact text; **T4** "cannot be undone, or moves value", with one person below a cap and two above; **T5** never offered. — [agent.md:111-120](../../../../docs/guides/agent.md)
- OpenAI rates tools by "read or write access, reversibility, permissions and financial impact". — [agent.md:122](../../../../docs/guides/agent.md)
- An approval is a gate only if the approver sees the exact action, its provenance and its blast radius. "An edited call is a new input and re-enters the pipeline". Prompts are a budget, so T0/T1 never prompt. — [agent.md:143](../../../../docs/guides/agent.md)
- Abuse limits, decision logs and a graded kill switch "bound the damage between detection and response". — [agent.md:147](../../../../docs/guides/agent.md)
- Rollout: shadow, then a canary that auto-applies only `category` and `priority`, with every T2+ action still approved. The dashboard tracks the reopen rate. — [agent.md:190-200](../../../../docs/guides/agent.md)
- SDK guide §7: "An approval should end the run in a signed, resumable log state, not block a callback". — [agent-sdk.md:147-160](../../../../docs/guides/agent-sdk.md). Retries: HTTP retries before output are safe, mid-stream retry is unsafe, and OpenAI refuses replay once output has started. — [agent-sdk.md:43](../../../../docs/guides/agent-sdk.md)
- Harness guide §2: immutable files, so "revert, fork and migration write new files and move a pointer". Codex is the model ("Revert writes 'a new immutable rollout file'"), and Cloudflare's mutable rows are rejected because they "cannot serve as an audit trail". — [agent-harness.md:23, 43](../../../../docs/guides/agent-harness.md). §5: a deny-first pipeline, with re-evaluation on resume so that a deny wins. — [agent-harness.md:108-125](../../../../docs/guides/agent-harness.md)

### Inferences
- The guides treat "reversible" as a label that lowers a tier's gate. None of them says *who* reverses a T1/T2 write, *how*, or *within what window*. That is the gap an undo-window recommendation would fill.

### Gaps
- No guide defines an undo window, a compensation step or a rollback result for the model.

## Q6. What do the plans not yet say about rollback?

### Takeaway
The plans cover agent rewind (log, HEAD, fork, revert, playback, safe resume) and prevention (tiers, approvals, quorum, caps, kill switch, shadow). They omit data rollback entirely: idempotency keys, an unknown-outcome state, inverse operations, undo windows, compensation order, rollback entries and rollback results for the model.

### Cited Findings (each gap is an absence, confirmed by the files cited)
- **No idempotency key on tool calls or helpdesk writes.** `ToolDefinition` and `Helpdesk` carry none. — [build-sdk.md:310-326](../../../../docs/plans/build-sdk.md); [build-agent.md:302-316](../../../../docs/plans/build-agent.md). Contrast OpenAI's `operationId` contract — `verify/openai-agents-sdk/node_modules/@openai/agents-core/dist/memory/session.d.ts:108-128` — and LangGraph's idempotency rule. — [interrupts.mdx:1365-1375](../../../../docs/reference/langchain/source/src/oss/langgraph/interrupts.mdx)
- **No `unknown` outcome.** A crash mid-call yields an "aborted error result". — [N7-rebuild-resume-replay.md:29](../../../../docs/todos/ready/N7-rebuild-resume-replay.md); [B11-loop-core.md:34](../../../../docs/todos/ready/B11-loop-core.md). No reconciliation step is planned.
- **No outcome kind beyond `isError`.** — [build-sdk.md:332-336](../../../../docs/plans/build-sdk.md); `CodeCallResult` is only `done | denied | awaiting_approval`. — [build-harness.md:433-436](../../../../docs/plans/build-harness.md)
- **No rollback or compensation entry.** — entry union, [build-harness.md:257-291](../../../../docs/plans/build-harness.md)
- **Revert is log-only.** — [N5-head-fork-revert.md:14](../../../../docs/todos/ready/N5-head-fork-revert.md). Nothing reconciles a revert or re-run past an executed side effect. `rerunFrom()` "calls the model again", and its re-proposed calls would pass the gate again. — [build-harness.md:315](../../../../docs/plans/build-harness.md)
- **No inverse helpdesk methods and no undo window** for T1/T2, despite the "undoable" and "reversible" labels. — [agent.md:116-117](../../../../docs/guides/agent.md); [build-agent.md:302-316](../../../../docs/plans/build-agent.md)
- **No compensation order across a multi-action ticket.** The workflow maps stops to handoff "without retry". — [A13-triage-workflow.md:30](../../../../docs/todos/ready/A13-triage-workflow.md). It does not say what to do with writes already made before the stop.
- **No approval covering a whole plan.** Each call is approved separately per its tier. — [build-agent.md:112-117](../../../../docs/plans/build-agent.md)
- **No test of a crash between the helpdesk accepting a write and the log append.** The capstone tests only a clean second-process resume. — [build-agent.md:676](../../../../docs/plans/build-agent.md)
- **No operator undo path.** The kill-switch runbook (A23) stops actions and does not reverse them. — [build-agent.md:362-371](../../../../docs/plans/build-agent.md)

### Inferences
- The cheapest additions consistent with the existing design (our inference): pass `callId` or `inputHash` as the helpdesk idempotency key; extend `ToolResult` or `details` with an outcome (`not_applied | applied | compensated | partial | unknown`); record compensations as `product_record` or a new entry; add inverse methods for T1/T2 with an undo window; and require the refund (the pivot) before the reply when both are proposed.
- None of the SDK features would carry over: none reaches external data, so our own harness must own data rollback whichever SDK the comparison favoured.

### Gaps
- Whether real helpdesks (Zendesk, Intercom, Freshdesk) accept idempotency keys on writes depends on A24's choice, which the owner has not made. — [build-agent.md:250](../../../../docs/plans/build-agent.md)
