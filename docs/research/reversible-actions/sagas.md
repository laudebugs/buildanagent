An agent that updates an order, refunds the payment and emails the customer touches three systems that share no transaction. If the refund fails after the email has gone out, the customer holds a promise that nobody can take back. Garcia-Molina and Salem named this shape a **saga** in 1987: a sequence of local transactions in which either every step completes or compensating steps semantically undo the steps that ran ([Sagas paper](https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf)). For an agent, the saga's step order and its approval point matter more than the engine that runs it.

I compared six engines, Temporal (.NET and TypeScript), Azure Durable Functions, Dapr Workflow, MassTransit, NServiceBus and AWS Step Functions, against this example. Of the six, **only MassTransit's routing slips run compensation for you**, from a log the slip carries. The other five leave the undo to code you write, and every engine except MassTransit reports "failed and compensated" and "failed with compensation incomplete" as the same status. Agent SDKs add a second gap, because they approve one tool call at a time. In this report, I show that a saga tool for agents must own three things no engine supplies: **the step order around the irreversible refund, one approval over the whole plan, and a typed outcome that says what is still true.**

## The refund is the pivot, so the email must come after it

A saga guarantees one of two sequences: T1…Tn, or T1…Tj followed by Cj…C1 ([Sagas paper](https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf)). Two properties of that guarantee shape the agent case. First, **compensation is semantic, not a state restore**. Ci "undoes, from a semantic point of view, any of the actions performed by Ti, but does not necessarily return the database to the state that existed" before, because other transactions may have changed the data in between. Second, when a compensating transaction fails, "the system is stuck". The paper's fallback is manual repair, which it calls "definitely not an elegant solution, but It IS a practical one" ([Sagas paper §6](https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf)). The paper also motivates sagas with long transactions that pause "for inputs from the users", which is the agent-with-approval case.

The paper has no word for the point of no return, so this report uses Microsoft's. **Compensable** transactions can be undone. The **pivot** is "the point of no return", after which "all subsequent actions must be completed". **Retryable** transactions follow the pivot and "are idempotent" ([Azure saga pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/saga)). Chris Richardson uses the same three terms in his talks, but the definitions attributed to him come from a search summary of his slides, not from his book **[secondary]** ([QCon SF slides](https://pt2.slideshare.net/chris.e.richardson/qconsf-acid-is-so-yesterday-maintaining-data-consistency-with-sagas)). Because sagas lack isolation, Microsoft also lists countermeasures. Three of them matter here. A **semantic lock** is an application-level "update in progress" flag, and the **pessimistic view** reorders the saga so that risky updates happen in retryable steps. **Reread values** confirms that data is unchanged before an update and restarts the saga if it changed ([Azure saga pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/saga)).

In the example, the refund is the pivot. Stripe can cancel only some card refunds, only "for a short period of time", and "only Dashboard cancellations are currently supported for card refunds", so an agent calling the API cannot rely on reversing one ([Stripe refunds](https://docs.stripe.com/refunds)). The email cannot be unsent at all. Its only remedy is a correction email, which is a new external action rather than a compensation (our inference; no source discusses email "unsend" semantics). Those two facts yield a four-step order:

1. The order update runs first and writes a semantic lock such as `refund_pending`. Its compensation rereads the order and restores the prior status.
2. The refund runs second, with an idempotency key so that a timeout can be retried. Stripe replays the saved first response for a reused key, but it may prune keys after 24 hours ([Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests)).
3. The email runs third, idempotent by message id, with content approved in advance.
4. A final retryable step flips `refund_pending` to `refunded`.

**Sending the email before the refund is the one order to forbid.** A "your refund is on its way" message followed by a failed refund leaves a false statement that no step can compensate.

A refund call that times out is neither a success nor a failure. Before the orchestrator chooses backward recovery (compensate) or forward recovery (finish), it must resolve the call, either by retrying with the same idempotency key or by reading the refund's state. Microsoft's Compensating Transaction pattern explains why the compensations need the same care: they "are eventually consistent operations and can fail". The system therefore "should record progress so that it can resume the compensating transaction from the point of failure", design each step as an idempotent command, and raise an alert when only a person can recover ([Azure compensating transaction](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)).

## Five of six engines leave compensation as code you write

Every engine gives you durable state and retries, but only one treats compensation as a primitive. The table summarizes the comparison, and the sections after it explain what each difference costs an agent.

|---|---|---|---|---|
| Temporal .NET `Temporalio` 1.22.0 / TS `@temporalio/workflow` 1.26.0 (too new; pin 1.25.0) | Hand-written list of closures, run in a `catch` | Author's loop | Signal or Update plus `condition` / `WaitConditionAsync` | Failed (samples rethrow) |

### Temporal: a reverse loop, and the two official samples register compensations at different times

Temporal ships a `Saga` class only in Java. For TypeScript, Python and Go, "you'll need to keep track of the compensations yourself" ([Temporal blog](https://temporal.io/blog/compensating-actions-part-of-a-complete-breakfast-with-sagas)), and the .NET sample takes the same hand-written approach. The .NET sample keeps a `List<Func<Task>>` and adds each compensation **before** its forward activity. On any exception, it reverses the list, awaits each entry while logging and swallowing compensation errors, and then rethrows ([SagaWorkflow.cs](https://raw.githubusercontent.com/temporalio/samples-dotnet/main/src/Saga/SagaWorkflow.cs)). The TypeScript sample instead `unshift`s each compensation **after** its step succeeds ([saga/src/workflows.ts](https://raw.githubusercontent.com/temporalio/samples-typescript/main/saga/src/workflows.ts)).

Temporal's own blog labels the TypeScript order `// DON'T DO THIS`. A step can partly apply and then time out, and if its compensation was never registered, nothing undoes it. The blog's fix is to register each compensation first and write it to tolerate a step that never happened ([Temporal blog](https://temporal.io/blog/compensating-actions-part-of-a-complete-breakfast-with-sagas)). For a refund, the .NET order plus an idempotency key is therefore the safe choice.

Temporal's retry defaults decide when a step really fails. Activities retry **without limit** by default, starting at 1 s with a backoff of 2.0 and a 100 s cap ([Retry policies](https://docs.temporal.io/encyclopedia/retry-policies)). As a result, "an Activity Failure will never directly cause a Workflow Failure" until retries or timeouts run out or a non-retryable `ApplicationFailure` is thrown. Only then does the `catch` that unwinds the saga run ([TS failure detection](https://docs.temporal.io/develop/typescript/failure-detection)).

Three traps matter for agents. First, cleanup after cancellation must run inside `CancellationScope.nonCancellable`, or it is cancelled before it starts ([TS cancellation scopes](https://docs.temporal.io/develop/typescript/workflows/cancellation-scopes.md)). Second, "terminate and reset will not allow Workflow code to execute any finally or defer statements", so a terminated workflow never compensates ([Temporal blog](https://temporal.io/blog/compensating-actions-part-of-a-complete-breakfast-with-sagas)). Third, the agent integrations turn model calls into activities automatically, but tools "execute in the Workflow" and must call activities for any I/O ([Temporal AI SDK docs](https://docs.temporal.io/develop/typescript/ai-sdk)). The OpenAI Agents integration offers `activityAsTool` for this ([`@temporalio/openai-agents`](https://registry.npmjs.org/@temporalio/openai-agents)). A side-effecting tool that is not an activity leaves nothing durable to compensate.

For approval, a Temporal **Update** makes a better gate than a Signal. A Signal handler "cannot return a value", and the server acknowledges a Signal before the workflow processes it. An Update, by contrast, is "a trackable synchronous request", and its validator can reject it "before it is written to History" ([TS message passing](https://docs.temporal.io/develop/typescript/message-passing); [.NET message passing](https://docs.temporal.io/develop/dotnet/message-passing)). A validator can therefore refuse an approval whose request id or plan hash differs from the pending one.

### Durable Functions and Dapr: the same Durable Task model, with Completed as the documented outcome

Microsoft treats orchestrations as ordinary code, so "error handling and compensation don't require new concepts" ([Durable Functions error handling](https://learn.microsoft.com/en-us/azure/azure-functions/durable/durable-functions-error-handling?tabs=csharp-isolated)). Its Durable Task .NET sample debits one account and tries to credit another. In `catch (TaskFailedException)`, it refunds the source account and then **returns** `"Transfer failed: … Compensation completed."`. The instance therefore ends with `RuntimeStatus` Completed, not Failed, and a caller must parse the output to learn that the saga rolled back ([error handling](https://learn.microsoft.com/en-us/azure/azure-functions/durable/durable-functions-error-handling?tabs=csharp-isolated); [instance management](https://learn.microsoft.com/en-us/azure/azure-functions/durable/durable-functions-instance-management)). The docs show only one compensating call, never a reversed list.

Retries and approvals follow the same code-first model. Retries are opt-in per call through `TaskOptions`, bounded by a maximum number of attempts; the separate retry timeout is unbounded by default ("By default, retries continue indefinitely"). Approval is `WaitForExternalEvent` raced against a durable timer with `Task.WhenAny`, and while the orchestrator waits, the app can unload and Consumption-plan billing stops ([external events](https://learn.microsoft.com/en-us/azure/azure-functions/durable/durable-functions-external-events)). External events arrive **at least once**, so Microsoft recommends a unique id in each event, which an approval payload needs anyway.

Two status notes apply to Microsoft's stack. The JavaScript/TypeScript Durable Task SDK (`@microsoft/durabletask-js`) is still in preview and is incompatible with the `durable-functions` package ([Durable Task SDKs overview](https://learn.microsoft.com/en-us/azure/azure-functions/durable/durable-task-scheduler/durable-task-overview)). Support for the .NET in-process model ended on 10 November 2026 ([.NET isolated overview](https://learn.microsoft.com/en-us/azure/azure-functions/durable/durable-functions-dotnet-isolated-overview)).

Dapr Workflow, stable since Dapr 1.15 ([Dapr blog](https://blog.dapr.io/posts/2025/02/27/dapr-v1.15-is-now-available/)), is the only code-first engine whose docs describe the multi-step pattern directly: "register compensation activities for each step and execute them in reverse order" ([Dapr workflow patterns](https://docs.dapr.io/developing-applications/building-blocks/workflow/workflow-patterns/)). Its sample is in Java only. The sample records a compensation name after each successful step and reverses the list in `catch (TaskFailedException)`. It then logs any failing compensation, continues, and ends with `ctx.complete("Order processing failed, compensation applied")`, again a Completed instance. The same page's .NET retry snippet compensates and then `throw;`s, which ends the instance as Failed.

The Java sample also has no `return` after `ctx.complete` in the `catch`, so control falls through to the "send confirmation" step. `complete` does not stop the code: in Microsoft's Durable Task Java SDK, the next `callActivity` throws `IllegalStateException("The orchestrator has already completed")` ([durabletask-java](https://raw.githubusercontent.com/microsoft/durabletask-java/main/client/src/main/java/com/microsoft/durabletask/TaskOrchestrationExecutor.java)), so the sample is a docs bug. For approval, Dapr's `WaitForExternalEventAsync` throws `TaskCanceledException` on timeout, and an event that arrives before the workflow waits is saved to history and consumed later ([features and concepts](https://docs.dapr.io/developing-applications/building-blocks/workflow/workflow-features-concepts/)).

### MassTransit: the only built-in compensation, now behind a commercial licence

MassTransit's routing slips carry an itinerary, an activity log and a **compensation log** inside the message. Each `IActivity<TArguments, TLog>` has `Execute` and `Compensate`. "When an activity fails, the Compensate method is called for previously executed activities in the routing slip that stored compensation data", and an execute-only `IExecuteActivity<TArguments>` is never compensated ([routing slip activities](https://masstransit.io/guides/routing-slips/)). The example maps cleanly onto this model: `UpdateOrder` and `RefundPayment` become compensating activities, and `SendEmail` becomes execute-only.

The docs call the itinerary and the activity log "ordered" but never state the compensation order. The source does: the compensate host takes `CompensateLogs.Last()` and forwards the slip with that entry removed. Compensation therefore runs last-in, first-out, and MassTransit publishes `RoutingSlipFaulted` only after the last compensation succeeds ([HostCompensateContext.cs](https://raw.githubusercontent.com/MassTransit/MassTransit/develop/src/MassTransit/Courier/HostCompensateContext.cs); [CompensatedCompensationResult.cs](https://raw.githubusercontent.com/MassTransit/MassTransit/develop/src/MassTransit/Courier/Results/CompensatedCompensationResult.cs)). MassTransit is therefore the **only engine with all three terminal outcomes built in**: `RoutingSlipCompleted`, `RoutingSlipFaulted` (a step failed and every compensation succeeded) and `RoutingSlipCompensationFailed` ([execute a routing slip](https://masstransit.io/guides/routing-slips/execute/)).

A routing slip cannot hold the approval wait itself. Because a slip's state travels with the message, nobody can query it, so the documented pattern is a saga state machine that correlates on the slip's tracking number ([track using a saga](https://masstransit.io/guides/routing-slips/monitor-using-a-saga/)). That state machine is also where the approval wait lives, with a `Schedule` timeout that needs a configured message scheduler ([scheduled events](https://masstransit.io/guides/saga-state-machines/schedule-event/)).

Licensing is the catch. "MassTransit v9 (and beyond) requires a license to use", although an expired key only logs a warning ([license configuration](https://masstransit.io/configuration/license/)). v8 remains Apache-2.0 and was still patched in October 2026, with 8.5.12 on 21 October ([NuGet](https://api.nuget.org/v3/registration5-semver1/masstransit/page/8.0.11/9.3.0.json)). The GitHub README still says "Apache 2.0", which contradicts the v9 package metadata ([README](https://raw.githubusercontent.com/MassTransit/MassTransit/develop/README.md)).

### NServiceBus and Step Functions: durable coordinators, hand-wired undo

NServiceBus sagas are "a message-driven state machine" that "must not perform any I/O operations". Instead, they send commands to handlers that call external systems and reply ([NServiceBus sagas](https://docs.particular.net/nservicebus/sagas/)). Compensation is therefore a set of command messages that the author sends in whatever order the saga data's flags dictate, and no page read mentions a compensation API. Timeouts "cannot be changed … or revoked", so the approval-deadline handler must check whether approval already arrived ([saga timeouts](https://docs.particular.net/nservicebus/sagas/timeouts)). The outbox deduplicates incoming messages by `MessageId` and stores outgoing messages with the business data in one database transaction ([outbox](https://docs.particular.net/nservicebus/outbox/)). A failed compensation command follows normal recoverability: five immediate retries, then delayed retries, then the error queue ([recoverability](https://docs.particular.net/nservicebus/recoverability/)).

Step Functions makes the saga declarative but still hand-wired. AWS's Prescriptive Guidance routes each forward Task's `Catch` to a chain of compensating Lambdas that ends in a `Fail` state, using Standard workflows ([saga orchestration](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/saga-orchestration.html)). Step Functions keeps no compensation log, so the author must point each `Catch` at the correct entry in the chain, which is more error-prone than a routing slip. Standard workflows suit payments, because states run exactly once "unless you have specified Retry behavior". Only Standard workflows support `.waitForTaskToken`, which can pause for a human up to the one-year execution limit ([workflow types](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-standard-vs-express.html); [callbacks](https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html)).

Exactly-once state transitions do not make the refund API idempotent. A `Retry` on the refund state can still refund twice without an idempotency key. Executions also fail outright at **25,000 history events** ([quotas](https://docs.aws.amazon.com/step-functions/latest/dg/service-quotas.html)), a ceiling that a long agent loop with many heartbeats could approach.

## Approval belongs before the first compensable step and covers the whole plan

Vendors agree that money and irreversible actions need a person. OpenAI's agent guide names "authorizing large refunds" and "canceling user orders" as high-risk actions that "should trigger human oversight" ([OpenAI practical guide](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)). Anthropic recommends confirmation before "completing financial transactions" and adds that the check must happen "before each block runs, because a batch can complete a multistep action within one turn" ([Claude computer use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)). Yet every agent SDK surveyed approves **one tool call at a time**:

- the OpenAI Agents SDK, through `needsApproval` and a resumable `RunState` ([OpenAI HITL](https://openai.github.io/openai-agents-js/guides/human-in-the-loop/));
- LangGraph, through `interrupt` ([LangGraph interrupts](https://docs.langchain.com/oss/javascript/langgraph/interrupts));
- Microsoft Agent Framework, through `ApprovalRequiredAIFunction` ([MAF tool approval](https://learn.microsoft.com/en-us/agent-framework/agents/tools/tool-approval));
- Temporal's human-in-the-loop recipe, which approves one proposed action through a Signal ([Temporal HITL cookbook](https://docs.temporal.io/ai-cookbook/human-in-the-loop-python)).

None of them models a saga or a plan.

Per-step approval breaks the saga's rule that nothing after the pivot may block. Suppose the refund is approved and executed, and the email is approved afterwards. A reviewer who then rejects or edits the email strands the saga past its pivot, with a mandatory step waiting on a person. The approval therefore has to come **before the first compensable step, as one decision whose canonical hash covers every step's arguments**: the order change, the refund amount and recipient, and the exact email text. This placement is our synthesis, because no vendor source discusses approval relative to a pivot.

The theoretical minimum is approval before the pivot. Steps before the pivot are compensable, so they could run speculatively and be compensated if the reviewer rejects the plan. Microsoft endorses automatic compensation "for clear, low-risk conditions" and a pause for review when a case is "ambiguous, high impact" ([Azure compensating transaction](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)). Approving up front is still better in practice, because speculative execution holds a semantic lock that the rest of the application can see (the `refund_pending` order) while a person decides. Only an eval with realistic approval delays can measure that trade-off, so this preference stays open until one runs.

This repo's existing gate fits the design with one extension. The agent guide already tiers external email as T3 ("one person approves the exact text") and refunds as T4 ("one person below a cap; two above it") ([agent guide §5](../../guides/agent.md#5-safety-is-a-policy-table-and-a-context-split-tier-every-tool-by-worst-case-effect-bind-identity-and-cut-the-outbound-leg)). AD3 binds each approval to a host-signed pause over the request id, kind, call id, tool, canonical input hash and policy version, and the approval expires on age or on a policy change ([build-agent plan, AD3](../../plans/build-agent.md#ad3-a-role-based-quorum-per-tier-and-amount-band-bound-to-the-host-signed-pause-and-expiring-on-age-or-policy-change-accepted-with-sdk-d5-and-hd5)). A saga needs either pre-collected signed pauses for every step or a new "plan" kind of signed request.

A saga also needs a **third expiry condition: the state the plan was computed from**. Microsoft's "reread values" countermeasure says to stop if the data changed ([Azure saga pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/saga)). For the agent, that means hashing the order version, the refundable balance and the amount already refunded at approval time, and failing closed with `stale_approval` if any of them differs at execution. OpenAI's server-side rules complete the gate: authenticate the reviewer on the server, never accept replacement arguments or state from the client, and atomically consume the pending request. Consumption, OpenAI warns, "does not guarantee exactly-once tool side effects" ([OpenAI HITL](https://openai.github.io/openai-agents-js/guides/human-in-the-loop/)), so idempotency keys on the refund and the email close that gap. An approval that times out should resolve to "nothing executed", as Temporal's recipe does when it completes "with a timeout result" ([Temporal HITL cookbook](https://docs.temporal.io/ai-cookbook/human-in-the-loop-python)).

## The agent needs five outcomes, and only MassTransit tells "compensated" from "compensation failed"

Engines report coarse terminal states. Step Functions returns `RUNNING | SUCCEEDED | FAILED | TIMED_OUT | ABORTED | PENDING_REDRIVE` with free-text `error` and `cause` ([DescribeExecution](https://docs.aws.amazon.com/step-functions/latest/apireference/API_DescribeExecution.html)). Temporal returns a result or an `ApplicationFailure` with a type and details ([TS failure detection](https://docs.temporal.io/develop/typescript/failure-detection)). The Durable Functions and Dapr samples return a Completed string. Only MassTransit separates "compensated" from "compensation failed". MCP's `isError: true` marks a failure but not whether its side effects persist ([MCP 2025-11-25 tasks](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks)). A model that sees only "failed" cannot tell whether the customer's money moved, and that one fact decides its next sentence to the customer.

The saga tool should therefore return a typed outcome that the orchestrator computes, not the model. The shape below is our design. It extends the repo's existing error shape, which already names the cause, the next step and "what not to do next" ([agent guide §3](../../guides/agent.md#3-tools-deserve-more-design-effort-than-the-prompt-few-workflow-shaped-tools-identity-from-trusted-context-and-errors-that-say-what-to-do-next) and [§9](../../guides/agent.md#9-reference-architecture)):

```ts
type Effect = { step: string; kind: "order_update" | "refund" | "email"; id: string; summary: string };

type SagaOutcome =
  | { status: "completed"; operationId: string; effects: Effect[] }
  | { status: "failed_compensated"; operationId: string; failedStep: string; cause: string;
      effects: []; undone: Effect[]; retrySafe: boolean; next: string }
  | { status: "failed_needs_human"; operationId: string; failedStep: string; cause: string;
      effects: Effect[]; undone: Effect[]; outstanding: Effect[]; handedOffTo: string;
      retrySafe: false; avoid: string }
  | { status: "pending"; operationId: string;
      phase: "awaiting_approval" | "running" | "pivot_unknown"; pollAfterMs: number; retrySafe: false }
  | { status: "rejected" | "stale_approval" | "expired"; operationId: string; reason: string; effects: [] };
```

Each field answers a question the model would otherwise guess at. `effects` lists what changed and still holds, `undone` lists what was compensated, and `outstanding` lists what a person now owns. `retrySafe` says whether calling again with the same `operationId` is idempotent. In `failed_needs_human`, the `avoid` string tells the model what not to do, such as "do not re-issue the refund or promise the customer a date", while code performs the handoff itself. In `pending`, the `pivot_unknown` phase covers the refund timeout and tells the model neither to retry nor to tell the customer the refund failed. The fifth outcome, not executed, covers rejection, a stale approval and expiry.

Mapping the engines onto this union takes little code. Temporal success becomes `completed`. An `ApplicationFailure` of a distinct type, thrown after a clean unwind, becomes `failed_compensated`. Both Temporal samples swallow compensation failures today, so a saga tool must instead raise them as a non-retryable failure that maps to `failed_needs_human`. Step Functions needs distinct `Fail` error names, for example `ActionCompensated` and `CompensationFailed`, because its status alone says only `FAILED`.

Delivery should be asynchronous, because an approval can take hours. The MCP 2026-07-28 revision moved Tasks into an extension, `io.modelcontextprotocol/tasks`, with the states `working | input_required | completed | failed | cancelled`. A task is created durably before the response is sent, polling is the default, and "approval gates" are a listed use case ([MCP 2026-07-28 Tasks](https://modelcontextprotocol.io/specification/2026-07-28/basic/utilities/tasks)). A2A 1.0.0 adds `REJECTED` and `AUTH_REQUIRED` and rejects further messages to a task in a terminal state ([A2A specification](https://a2a-protocol.org/latest/specification/)).

The saga tool should return an operation id at once and surface the plan approval as `input_required`. It should keep `pivot_unknown` in `working` until the refund is reconciled, because MCP terminal states cannot change, and it should put the typed `SagaOutcome` in the terminal result, with both failure statuses mapped to `failed`. MCP's cooperative cancel, which "may still reach a non-cancelled terminal status", matches saga semantics. A cancel before the pivot compensates, and a cancel after it is ignored while the saga runs forward to `completed`.

## The harness, not the engine, owns order, approval and outcome

The engine choice matters less than it first appears, because five of the six engines leave the same three things to the author: the order of the undo, whether a compensation failure is visible, and what the caller is told. The real design work therefore moves into the harness. A saga tool for agents needs five parts that no engine or agent SDK supplies together:

1. per-step `compensate` functions with a persisted compensation log, MassTransit's idea, which ports to any engine;
2. a pivot declared in the plan, with every compensable step before it;
3. one approval over the whole plan, bound to its inputs and to the state it was computed from;
4. idempotency keys on every forward and compensating call;
5. the five-way typed outcome.

With those parts in place, Temporal or Durable Task becomes a replaceable durability layer, which suits this repo's rule that every component be removable. The agent itself stays simple. It proposes a plan, waits on an operation id, and reads back an outcome that tells it exactly what is true about the customer's order, money and inbox.
