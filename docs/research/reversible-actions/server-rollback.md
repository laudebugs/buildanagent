# Make every agent tool call commit once or not at all

- **Status:** research report for todo U5 (Round U), 2026-11-18. It asks how an API backend makes each agent tool call safe to fail, retry or reverse, with a .NET section.
- **Versions checked (as of November 2026):** EF Core 11.0.0 and 10.0.15, the Npgsql EF Core provider 10.0.3 (11.0.0-rc.3 is the newest prerelease), .NET 11.0.0 and 10.0.15, Marten 9.62.0, `KurrentDB.Client` 1.6.1, `prisma` 8.0.0-rc.34 with `@prisma/client` 7.10.1, `drizzle-orm` 0.45.4, Debezium 3.7.1.Final, PostgreSQL 18 and 19 RC 2, MCP revision 2026-07-28 and IETF `draft-ietf-httpapi-idempotency-key-header-08`. The SDK claims use the repo's pinned packages.
- **Evidence:** three research notes, [transactions and idempotency](notes/transactions-and-idempotency.md), [temporal tables and event sourcing](notes/temporal-tables-and-event-sourcing.md) and [tool results after a rollback](notes/tool-results-after-rollback.md). They cite Microsoft Learn, the Prisma, Drizzle, Stripe, Marten, Kurrent, Debezium and PostgreSQL docs, the IETF datatracker, the NuGet and npm registries, the providers' tool-use docs, and this repo's SDK mirrors and installed `.d.ts` files, all fetched on 2026-11-18. Corrections are logged in [fact-check-server-rollback.md](fact-check-server-rollback.md).
- **Verified:** every number, version, date, status and behavioural claim was re-read against its primary source on 2026-11-18. Nothing here ran code against a database or a model. The four-outcome taxonomy, the result shape and the .NET end-to-end flow are our synthesis and an unrun sketch, and the regeneration case for tool call ids is untested. Fetched pages were read as data, and any instructions they contained were not followed.

An agent that writes through an API backend will sooner or later see a tool call time out, fail halfway or need undoing, and a careless retry can charge a customer twice. The backend makes each call safe to fail, retry or reverse by treating it as one database transaction that also records the call's identity, its before-state and a composed result. Three mechanisms do the work. First, **one transaction per tool call** holds the idempotency row, and every irreversible side effect (email, payment, outbound HTTP) moves after commit or into a transactional outbox. Second, **an idempotency key derived from the tool call id** is scoped as `(tenant, session, branch, tool_call_id)` and stored with a hash of the arguments. A replayed call then returns the saved result, a changed payload gets 422 and a concurrent duplicate gets 409. Third, **history makes reversal a compensating write**, using SQL Server temporal tables, an EF Core audit interceptor, or Marten or KurrentDB event streams tagged with the tool call id as causation. None of these mechanisms is a rewind, and none reverses anything outside the database.

After a rollback, the model must be told what actually happened, and the wire formats barely help. Only Anthropic (`is_error`) and MCP (`isError`) carry an error flag, and no provider or SDK defines "rolled back", "partial" or "unknown outcome". So the backend should return one of four outcome kinds (`not_applied`, `compensated`, `partial`, `unknown`) in the result body, with a retry rule and a next action, and keep stack traces in the log. As of November 2026 the ORM pieces are mature, though each ORM hides a retry trap. In this report, I show that commodity parts suffice and that the tool call id is the weak link: **a regenerated model turn emits a new id for the same action, so only calls persisted before execution deduplicate.**

## One transaction per tool call works in all three ORMs, but each hides a retry trap

The unit of safety is the tool call, and every mainstream ORM can express it as a single scope that commits or rolls back. The traps sit in the retry and nesting rules, so this section covers those.

**EF Core** wraps each `SaveChanges` in a transaction and guarantees it "will either completely succeed, or leave the database unmodified if an error occurs" ([EF Core, Transactions](https://learn.microsoft.com/en-us/ef/core/saving/transactions)). A tool call that reads, decides and writes several times needs an explicit `BeginTransactionAsync`/`CommitAsync`, and that collides with resilience. **A user-initiated transaction under `EnableRetryOnFailure()` throws `InvalidOperationException`** unless the whole unit runs inside `db.Database.CreateExecutionStrategy().ExecuteAsync(...)`, which replays the entire delegate on a transient failure ([EF Core, Connection Resiliency](https://learn.microsoft.com/en-us/ef/core/miscellaneous/connection-resiliency)). The same page then states a harder problem. "If the connection is dropped while the transaction is being committed the resulting state of the transaction is unknown." By default the strategy retries as though the commit failed, which can duplicate rows with store-generated keys. Its fourth remedy is to insert a tracking row with a GUID in every transaction and, on a commit failure, check whether that row exists ([EF Core, Connection Resiliency](https://learn.microsoft.com/en-us/ef/core/miscellaneous/connection-resiliency)). That tracking row is an idempotency row under another name, and the tool call id can be the GUID. Inside an existing transaction, EF also creates a savepoint before each `SaveChanges` and rolls back to it on error, except on SQL Server with MARS enabled ([EF Core, Transactions](https://learn.microsoft.com/en-us/ef/core/saving/transactions)).

**Prisma** changed shape between majors. Prisma 7 (`@prisma/client` 7.10.1, October 2026) offers `$transaction([])` and interactive `$transaction(async tx => …)` with `maxWait` 2000 ms and `timeout` 5000 ms defaults, and warns against network requests inside the callback ([Prisma v7 transactions](https://www.prisma.io/docs/orm/v7/prisma-client/queries/transactions.md)). Prisma 8 replaces both with `db.transaction(async tx => …)`, drops `maxWait` and the array form, and leaves the transaction open as long as the callback runs unless you set a timeout. Two rules matter for tool handlers. First, **"Prisma ORM does not retry write conflicts for you"**: a conflict surfaces as `RUNTIME.TRANSACTION_COMMIT_FAILED` with SQLSTATE 40001 or 40P01 on `cause`, and the page supplies a `withRetry` wrapper. Second, **a nested `db.transaction` "does not nest"**: it is a separate transaction that the outer one cannot roll back, so you must pass `tx` down ([Prisma 8 transactions](https://www.prisma.io/docs/orm/prisma-client/queries/transactions)). A helper that opens its own transaction therefore silently breaks the tool call's atomicity. As of 18 November 2026, Prisma 8 is still a release candidate. The docs banner says "Prisma ORM 8 is here", but Prisma's own release-status page says it "has not reached general availability yet: npm still installs a release candidate under `latest`" ([Prisma, Release status](https://www.prisma.io/docs/orm/release-status)). That candidate is `prisma` `8.0.0-rc.34`, published 16 November 2026, while `@prisma/client` stays at 7.10.1 ([npm registry](https://registry.npmjs.org/prisma)).

**Drizzle** is the simplest. `db.transaction(async tx => …)` returns the callback's value, `tx.rollback()` throws to abort, and a nested `tx.transaction(...)` becomes a savepoint ([Drizzle transactions](https://orm.drizzle.team/docs/transactions)). The page documents no timeout and no automatic retry, so a conflict retry is again the caller's job. The stable release is `drizzle-orm` 0.45.4, while 1.0 is at `1.0.0-rc.5` ([npm registry](https://registry.npmjs.org/drizzle-orm)).

| ORM (as of Nov 2026) | Tool-call scope | Nested call | Conflict retry | Trap |
|---|---|---|---|---|
| EF Core 11.0.0 | `strategy.ExecuteAsync(() => BeginTransaction … Commit)` | Savepoint (not with MARS) | Execution strategy replays the delegate | Commit-unknown outcome; manual transactions need the strategy wrapper |
| Prisma 8 RC / 7.10.1 | `db.transaction(tx => …)` / `$transaction` | Prisma 8: **separate transaction** | None; wrap 40001/40P01 yourself | Calls through `db` instead of `tx` run outside the transaction |
| Drizzle 0.45.4 | `db.transaction(tx => …)` | Savepoint | None documented | No timeout documented |

No transaction reaches outside the database. Prisma puts it bluntly: "Database writes roll back; emails don't" ([Prisma 8 transactions](https://www.prisma.io/docs/orm/prisma-client/queries/transactions)). Its v7 page walks through a plan upgrade in which the Stripe subscription succeeds and the database update then fails. The customer is charged but gets no paid features, and a naive re-run either errors or **creates a second subscription** ([Prisma v7 transactions](https://www.prisma.io/docs/orm/v7/prisma-client/queries/transactions.md)). The standard fix is the transactional outbox. The handler writes the message to an outbox table inside the same transaction, and a relay sends it later, so messages go out "if and only if the database transaction commits". The relay can still deliver more than once, so consumers must be idempotent ([microservices.io, Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html)). Brandur Leach's Stripe-derived design draws the same line. Endpoints that touch only local ACID state get idempotency "by mapping requests to transactions"; endpoints with foreign mutations need idempotency keys, atomic phases and recovery points ([brandur.org](https://brandur.org/idempotency-keys), a personal blog, so secondary). For an agent backend this means a tool that both writes rows and calls a payment API is two tool phases, not one transaction.

## Tool call ids make good idempotency keys only after they are persisted and scoped

The idempotency design is settled outside the agent world. Stripe saves the status and body of the first request with a key and replays it on retries, "including 500 errors". It compares parameters and errors on a mismatch, saves nothing for validation failures or concurrent conflicts, and may prune keys after 24 hours in API v1. API v2 instead retries partially failed work to completion within a 30-day window ([Stripe, Idempotent requests](https://docs.stripe.com/api/idempotent_requests); [Stripe, Advanced error handling](https://docs.stripe.com/error-low-level)). Stripe also says to treat a 500 as indeterminate: "Don't retry with a new idempotency key until you've resolved the original outcome." Replays carry `Idempotent-Replayed: true` ([Stripe, Advanced error handling](https://docs.stripe.com/error-low-level)). The IETF `Idempotency-Key` header draft, **at revision -08 (22 October 2026) and still not an RFC**, standardises the same contract. A missing key gets 400, key reuse with a different payload gets **422**, and a retry while the original is still running gets **409**, all as RFC 9457 problem+json. Its security section recommends a composite key that combines the client's key "with other client specific attributes known only to the resource", because low-entropy keys can leak other clients' cached responses ([draft-08](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/)).

Agent vendors point at the tool call id as the natural key. Anthropic tool uses carry ids like `toolu_01A09q90qw90lq917835lq9` ([Claude docs, Implement tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/implement-tool-use)), and OpenAI function calls carry a `call_id` that the output must reference ([OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling.md)). The OpenAI Agents SDK (v0.21.0) is explicit: "If a tool has side effects, make it idempotent by call ID so an interrupted continuation cannot repeat the effect" ([repo mirror, models.mdx:209-213](../../reference/openai-agents-sdk/source/docs/src/content/docs/guides/models.mdx)). Cloudflare Agents retries an interrupted turn automatically after eviction and tells developers to "Persist idempotency keys or completion records before external side effects" ([repo mirror, chat-agents.md:645-653](../../reference/cloudflare-agents/source/agents/docs/agents/chat-agents.md)). LangGraph warns that interrupts re-run nodes, so side effects before `interrupt` should be idempotent ([repo mirror, interrupts.mdx:1365-1375](../../reference/langchain/source/src/oss/langgraph/interrupts.mdx)). Temporal adds the key point about placement: the idempotency key must be "enforced by the service you are calling from your Activity, not by the Activity itself" ([Temporal, Activity Definition](https://docs.temporal.io/activity-definition)). For our design, that service is the backend tool endpoint.

The id has limits that the vendors do not spell out. **No Anthropic or OpenAI page found states the uniqueness scope or lifetime of `toolu_` or `call_` ids.** The backend should therefore never treat a bare id as globally unique. Scope it by tenant and session, following the IETF composite-key advice and Brandur's `UNIQUE (user_id, idempotency_key)` index ([brandur.org](https://brandur.org/idempotency-keys)).

Three cases decide whether deduplication by tool call id works, and this part is our reasoning, not a vendor claim. If a resume replays a persisted assistant message, the same id returns and deduplication works; this is the crash-after-side-effect case the SDKs warn about. If a harness regenerates the model call, for example after a crash before the assistant message was saved, the model emits a fresh id for what may be the same action, and deduplication fails. If a forked or rewound session tree replays an old id on a new branch, a session-only scope cannot tell the branches apart. Each case has a mitigation. The harness should append the tool-call entry to the session log before executing it; our planned `SessionStore.append` is already "idempotent by id" with an expected-last-id check ([build-harness.md:294](../../plans/build-harness.md)). The branch or entry id belongs in the key. High-stakes tools add a business key such as "one refund per order", which is Stripe's advice to "derive the key from a user-attached object" ([Stripe, Advanced error handling](https://docs.stripe.com/error-low-level)). The regeneration case is untested, so a mock-model run in `verify/` should confirm it.

The endpoint's behaviour then maps onto the IETF statuses. Same key and same argument hash, already completed: replay the stored result. Same key, different hash: return 422, which the harness surfaces to the model as a non-retryable tool error. Same key still in progress, including the loser of a race on the unique index: return 409, which the harness retries with backoff under the same key. A 500 or a commit-unknown outcome: look up the idempotency row before re-executing, as in EF Core's tracking-row remedy. Off-the-shelf middleware does not change this picture. **Neither ASP.NET Core nor Express nor NestJS was found to ship idempotency middleware.** The community packages are small: `IdempotentAPI` has had no release since November 2024 ([NuGet](https://api.nuget.org/v3-flatcontainer/idempotentapi/index.json)), and `@node-idempotency/express` 1.1.0 dates from August 2026 ([npm](https://registry.npmjs.org/@node-idempotency/express)). Middleware that keeps its own store probably writes the key outside the handler's transaction, though this pass did not verify that against the packages' source. A hand-written table inside the tool call's own transaction is the safer default.

## Restoring earlier state is always a new write, whether history lives in rows or events

Reversal means "make the world look as it did before tool call X", and both history mechanisms do it by writing forward. Neither rewinds.

**SQL Server and Azure SQL temporal tables** keep the previous version of every updated or deleted row in a history table. The period timestamps are the **begin time of the current transaction**, so "all rows inserted within a single transaction have the same UTC time" ([Microsoft Learn, Temporal tables](https://learn.microsoft.com/en-us/sql/relational-databases/tables/temporal-tables?view=sql-server-ver17)). That rule makes one transaction per tool call a precondition for per-call restore: two tool calls in one transaction cannot be separated afterward. EF Core maps the feature with `ToTable("Employees", b => b.IsTemporal())`, queries it with `TemporalAsOf`, `TemporalAll` and three range operators, and documents the restore recipe directly. You read the old row with `TemporalAsOf(timestamp)`, `Add` it and call `SaveChangesAsync`, which creates a new current row while keeping the history intact ([EF Core, SQL Server temporal tables](https://learn.microsoft.com/en-us/ef/core/providers/sql-server/temporal-tables)). EF Core 11 adds CLR-mapped period columns ([What's new in EF Core 11](https://learn.microsoft.com/en-us/ef/core/what-is-new/ef-core-11.0/whatsnew)).

Temporal tables carry limits that shape a per-call undo. Every temporal table needs a primary key. History tables take no constraints and cannot be edited directly. `TRUNCATE` is blocked while versioning is on, and graph and FILESTREAM tables cannot be temporal ([limitations](https://learn.microsoft.com/en-us/sql/relational-databases/tables/temporal-table-considerations-and-limitations?view=sql-server-ver17)). Retention defaults to `INFINITE`, but a finite `HISTORY_RETENTION_PERIOD` bounds the undo window, and **a point-in-time database restore silently turns the retention flag off** ([retention](https://learn.microsoft.com/en-us/sql/relational-databases/tables/manage-retention-of-historical-data-in-system-versioned-temporal-tables?view=sql-server-ver17)). Outside SQL Server, MariaDB has equivalent native system versioning and can query `FOR SYSTEM_TIME AS OF TRANSACTION 12345` ([MariaDB docs](https://mariadb.com/docs/server/reference/sql-structure/temporal-tables/system-versioned-tables)).

**PostgreSQL has no native system-time versioning, even in PostgreSQL 19** (RC 2 on 12 November 2026). The new docs section says "PostgreSQL does not currently support system time, but it could be emulated using triggers" ([PostgreSQL devel docs 5.7](https://www.postgresql.org/docs/devel/ddl-temporal-tables.html)). PostgreSQL 18's `WITHOUT OVERLAPS` and `PERIOD` foreign keys are application-time features ([PG 18 release notes](https://www.postgresql.org/docs/18/release-18.html)). The extension options are `temporal_tables` (C, v1.2.2, its latest tag), the `periods` extension (advertised only for 9.5 to 15) and nearform's PL/pgSQL port for managed clouds that forbid C extensions ([arkhipov](https://raw.githubusercontent.com/arkhipov/temporal_tables/master/README.md); [xocolatl](https://raw.githubusercontent.com/xocolatl/periods/master/README.md); [nearform](https://raw.githubusercontent.com/nearform/temporal_tables/master/README.md)). None was confirmed against PG 18. On PostgreSQL, the practical choice is an application-level audit table or event sourcing.

The audit table is the lightest portable option. EF Core's `SaveChangesInterceptor` sees every `SaveChanges`, and Microsoft's own sample uses it to "create an independent audit record of the changes". The same page warns that the sample is "not intended to be a robust auditing solution" ([EF Core interceptors](https://learn.microsoft.com/en-us/ef/core/logging-events-diagnostics/interceptors)). Writing original and current values plus the tool call id per entity gives exactly the before-images an inverse operation needs. Bulk `ExecuteUpdate` and `ExecuteDelete` escape that interceptor, because Microsoft documents them as "a way to save data to the database without using EF's traditional change tracking and SaveChanges() method". They also open no transaction of their own, so a tool call that uses them must run them inside its explicit transaction ([EF Core, ExecuteUpdate and ExecuteDelete](https://learn.microsoft.com/en-us/ef/core/saving/execute-insert-update-delete)). Change data capture, by contrast, fits audit streams better than synchronous undo. SQL Server CDC has "a built-in latency" and keeps changes for **3 days by default** ([About CDC](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/about-change-data-capture-sql-server?view=sql-server-ver17)). Debezium (3.7.1.Final, the latest stable release as of November 2026) records committed row-level changes in a log that applications read afterward, so it is asynchronous by design ([Debezium releases](https://debezium.io/releases/); [Debezium FAQ](https://debezium.io/documentation/faq/)). Neither CDC nor Debezium knows the tool call id unless the application writes it into the row.

**Event sourcing** makes the tool call a first-class fact. Marten (9.62.0, on PostgreSQL) records correlation and causation ids per event once you opt in with `CausationIdEnabled`/`CorrelationIdEnabled`, and it takes them "automatically from any active OpenTelemetry span". So a span tagged with the tool call id labels every event the call produces ([Marten, Event Metadata](https://martendb.io/events/metadata.html)). `FetchForWriting<T>(id, expectedVersion)` throws `ConcurrencyException` if another writer moved the stream, and it checks again at `SaveChangesAsync` ([Marten, Command handler workflow](https://martendb.io/scenarios/command_handler_workflow.html)). `ArchiveStream` is a reversible soft delete, while `TombstoneStream` hard-deletes a stream and all its events, for example "to clean up after a plan or workflow that should leave nothing behind" ([Marten, Archiving](https://martendb.io/events/archiving.html)).

**KurrentDB**, formerly EventStoreDB, records the same causation metadata but deletes more bluntly. It reserves `$correlationId` and `$causationId` in event metadata, but "you cannot selectively delete events from the middle of a stream". Hard deletes stay visible in `$all` until a scavenge, and "Scavenging is destructive" ([Kurrent docs, Event streams](https://docs.kurrent.io/server/v26.0/features/streams.html); [Scavenging](https://docs.kurrent.io/server/v25.1/operations/scavenge.html)). Its licence also matters for build-versus-buy, because the repository ships under the source-available **Kurrent License v1**, which forbids offering it as a hosted service, and some features need a licence key ([LICENSE.md](https://raw.githubusercontent.com/kurrent-io/KurrentDB/master/LICENSE.md); [installation](https://docs.kurrent.io/server/latest/quick-start/installation.html)). Across the two stores, the word "tombstone" means three things: a failed-sequence placeholder in Marten's appending docs, a hard delete in Marten's archiving docs, and a `$streamDeleted` marker in KurrentDB.

Neither store offers an "undo" API, so undo in event sourcing is a compensating event (`PriceChangeReverted`) that references the event it reverses. The table below compares the three mechanisms; the restore column is our synthesis.

| Mechanism | Before-state source | Per-call restore | Concurrency guard | Fits |
|---|---|---|---|---|
| SQL Server temporal + EF Core | Engine history, keyed by transaction begin time | `TemporalAsOf(before)` → re-add, overwrite or remove | Check rowversion or the agent's period start before restoring | SQL Server/Azure SQL backends |
| EF Core interceptor audit table | Original values captured at save | Apply the stored inverse | Compare current row to the agent's after-image | Any provider, including PostgreSQL |
| Marten / KurrentDB events | The stream itself, causation = tool call id | Append compensating events | `FetchForWriting(id, versionAfterAgent)` / expected revision | Aggregates where history is the domain |

The guard column carries the most important rule. **Restoring a row to "as of T" silently overwrites every later change, human or agent.** A per-call undo must therefore first confirm that the current state is still what the tool wrote, and refuse or escalate if the state has moved on. In event sourcing that check comes almost free: append the compensation with the stream version the agent left behind, and a concurrent change aborts the undo. Two smaller hazards also follow. A cascade is recoverable only if every table in it is temporal, and restores must re-insert parents before children. Temporal queries map history through the current model, so a migration between the call and the undo loses dropped columns. A cheaper alternative is to have the agent write to its own proposal stream or draft rows, promoted only on approval. Undo is then an archive, not a compensation.

## After a rollback, tell the model one of four outcomes in the result body

The wire formats give little help. Anthropic's `tool_result` has `is_error`, "Set to `true` if the tool failed or the call was invalid". Every `tool_use` id must get a matching result, so **a rolled-back call cannot be silently dropped** ([Handle tool calls](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls.md)). MCP's `CallToolResult.isError` exists so that the model sees tool errors, because "Otherwise, the LLM would not be able to see that an error occurred and self-correct" ([MCP schema 2026-07-28](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/schema/2026-07-28/schema.ts)). OpenAI's `function_call_output` is a string whose "format is up to you" ([OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling.md)). Gemini suggests an `"error"` key in `functionResponse.response` ([Gemini API reference](https://ai.google.dev/api/caching.md.txt)). The SDKs diverge further. Copilot alone has a typed `resultType` beyond success and error (`success | failure | rejected | denied | timeout`). OpenAI Agents SDK can return a timeout as a model-visible result and by default replaces errors with "An error occurred while running the tool. Please try again." Claude Agent SDK, Google ADK, LangChain's default and Vercel pass the raw exception message to the model. Vercel's MCP adapter drops `isError` altogether (sources in the [tool-results notes](notes/tool-results-after-rollback.md), §2, read from the pinned packages in `verify/`). **None of the four wire formats and none of the eight SDKs has a "rolled back" or "partially applied" state.**

Two conclusions follow. A backend should never throw on rollback, because a thrown error leaks internals to the model in half the SDKs. And the outcome must live in the body, with the provider flag set where one exists and stated again in text, because some adapters lose the flag. Vendor guidance on wording is consistent. Anthropic asks for "what went wrong and what Claude should try next" ([Handle tool calls](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls.md)). Its engineering guide also asks for errors that are "specific and actionable … rather than opaque error codes or tracebacks" ([Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)). RFC 9457 says problem details "are not a debugging tool for the underlying implementation" ([RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.txt)). The repo's own guide adds that an error should say what not to do. Its evidence is practitioner reports from Hacker News, a secondary source, of agents inventing data after a failed tool ([agent.md §3](../../guides/agent.md#3-tools-deserve-more-design-effort-than-the-prompt-few-workflow-shaped-tools-identity-from-trusted-context-and-errors-that-say-what-to-do-next)).

The outcome taxonomy below comes from distributed-API practice, not from any agent vendor. AWS treats a timeout as a state that needs "reconciliation", fixed by a caller-provided token that is echoed back ([AWS Builders' Library](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)). Google AIP-194 says clients "should not automatically retry transactional requests" and that `ABORTED` should be retried "at a level higher" ([AIP-194](https://google.aip.dev/194)). AIP-193 gives stable `reason` codes in upper snake case, at most 63 characters ([AIP-193](https://google.aip.dev/193)). Stripe v2 shows a partial operation completed by an idempotent retry ([Stripe](https://docs.stripe.com/api/idempotent_requests)).

| Outcome | Meaning | Retry rule | Model must not |
|---|---|---|---|
| `not_applied` | Rejected before any effect: validation, policy, precondition, conflict | Safe after fixing the cause, same key | Claim the change happened |
| `compensated` | Applied, then undone; world matches pre-call state | New operation only, if the user still wants it | Hide observable effects (an email already sent) |
| `partial` | Some steps applied, compensation failed or skipped | Idempotent resume or human escalation | Present it as success |
| `unknown` | Timeout or lost response | Reconcile by operation id, or retry with the **same** key | Retry with a fresh key |

The result itself carries two channels. The model sees a composed sentence plus a small structured payload, and the session log gets the raw exception, provider codes, compensation trace and a link to the original `tool_use` id. Pi's `content`/`details`, Copilot's `textResultForLlm`/`sessionLog` and OpenAI's `customData` already split these two channels ([tool-results notes](notes/tool-results-after-rollback.md) §2). A proposed shape, with RFC 9457 names reusable as extension members:

```json
{
  "outcome": "compensated",
  "operation": "refund_create",
  "operation_id": "op_7Q2…",
  "applied": [], "reverted": ["refund"], "not_reversible": ["customer email sent"],
  "current_state": "Order 4417: no refund; status unchanged",
  "retry": "new_operation_only",
  "next_action": "Tell the requester the refund did not go through; do not say it was issued.",
  "reason": "PAYMENT_PROVIDER_DECLINED"
}
```

Typed `outcome` and `retry` fields let the harness act too, for example by blocking a fresh-key retry after `unknown`, in line with RFC 9457's rule that consumers should not parse `detail`. One conflict needs handling. In the Claude Agent SDK, a TypeScript `tool()` handler that sets `structuredContent` stops the text blocks from reaching Claude, and in the OpenAI Agents SDK, declaring an `outputSchema` disables the default error function. So the structured payload must itself be model-readable, or the error path must not declare an output schema. No published study measures how models respond to "rolled back" versus "failed" wording, so the eval suite has to test it.

## A .NET backend gets every piece from EF Core, temporal tables and Marten

The .NET stack covers all three mechanisms with first-party or mature packages. As of 18 November 2026 the choices are **.NET 10 LTS (10.0.15) or .NET 11 STS (GA 10 November 2026)**, both supported to 14 November 2028 ([.NET support policy](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)). EF Core is at 11.0.0 and 10.0.15, both published 10 November ([NuGet](https://api.nuget.org/v3-flatcontainer/microsoft.entityframeworkcore.sqlserver/index.json)), so 11.0.0 just clears the repo's one-week pin rule. The Npgsql provider is stable at 10.0.3, with 11.0 at RC 3 ([NuGet](https://api.nuget.org/v3-flatcontainer/npgsql.entityframeworkcore.postgresql/index.json)). PostgreSQL shops should therefore stay on EF Core 10 for now. Marten is at 9.62.0 (9.0 shipped May 2026). Marten 9.62.0 was published on 16 November, too recently for the pin rule, and Marten ships several releases a week, so a pin takes the newest one at least a week old. `KurrentDB.Client`, the .NET client for KurrentDB, `KurrentDB.Client` is at 1.6.1 ([Marten NuGet](https://api.nuget.org/v3-flatcontainer/marten/index.json); [KurrentDB.Client NuGet](https://api.nuget.org/v3-flatcontainer/kurrentdb.client/index.json)).

The end-to-end flow below is our synthesis of the cited APIs. Nobody has run it, so it should become a runnable example in `verify/` before anyone relies on it. The ASP.NET Core tool endpoint receives the tool call id, session and branch from the harness, and starts an OpenTelemetry `Activity` tagged with them, which Marten picks up as causation. Inside `CreateExecutionStrategy().ExecuteAsync`, it opens one transaction and inserts the `ToolCall` idempotency row (unique on tenant, session, branch and call id, with the argument hash). It captures `SYSUTCDATETIME()` as the restore point, performs the writes, adds any outbox messages, and commits. A `SaveChangesInterceptor` records the touched keys and before-images against the tool call id. On SQL Server, `IsTemporal()` tables keep the before-images, so the audit row needs only the keys and the time.

Reversal runs as a second tool call with its own transaction. On SQL Server, a second endpoint loads the recorded keys and checks that each current row still matches the agent's after-image. It then applies `TemporalAsOf(before)` or the stored inverse in one new transaction tagged with an undo causation id. The endpoint returns a `compensated` result, or `partial` if a row has moved on. On PostgreSQL, the interceptor's before-images serve the same role, or agent-writable aggregates live in Marten streams. There, reversal is a compensating event appended with `FetchForWriting(id, versionAfterAgent)`, and agent scratch streams are archived. Anything that left the database through the outbox gets its own compensating action, and the result lists it under `not_reversible` if none exists.

## Reversibility belongs in the tool contract, and the harness must enforce it

Reversibility is a property of the tool contract more than of the database. Transactions, idempotency rows and history tables are all commodity features in November 2026, yet no ORM, store, provider or SDK supplies the join between them. That join has two parts. The first is the tool call id, recorded before execution and used as both idempotency key and causation id. The second is an outcome vocabulary rich enough to tell the model that something was undone. The residual risk sits outside the transaction: a temporal table can bring back a deleted row but cannot unsend an email, and the model alone cannot resolve an `unknown` outcome. For anything irreversible, the safest agents therefore draft first and commit on approval.

The join is where our planned harness and backend meet, so it belongs in the shared `ToolResult` type and the session log design rather than in each tool. The backend must own the transaction, the idempotency row and the before-state. The harness must persist the tool-call entry before execution and put the branch in the key. Above all, the harness should enforce the `retry` field in code, refusing a fresh-key retry after an ambiguous result **instead of trusting the model to remember why it should not.**
