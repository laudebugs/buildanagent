## Verdict on the owner's hypothesis

### Takeaway
Mostly **wrong for ordinary edits, right for two narrow cases**. VS Code does keep "a copy", but the copy is the **before** state, not the proposed change: the agent's edits go straight into the real file's text buffer and are **saved to disk** when the edit stream ends; the copy (`originalModel`) is an in-memory snapshot of the pre-edit content. **Keep** just makes the snapshot catch up to the file; **Undo** writes the snapshot back over the file and saves again. It is "apply, then review, then optionally revert" (compensating write), not "stage, then commit". The hypothesis holds only for (a) **sensitive / outside-workspace edits**, where the tool call shows a diff and waits for **Allow** before anything is written, and (b) **terminal and other tool calls** that require approval before they run.

- Agent edits are applied to the **real buffer**: `_applyEdits` calls `this.modifiedModel.pushEditOperations(...)` with `_isEditFromUs = true` — [CE/chatEditingTextModelChangeService.ts L296-L318 (R)](https://github.com/microsoft/vscode/blob/1.147.0/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingTextModelChangeService.ts#L296-L318)

- The Copilot edit tools (`replace_string`, `create_file`, `apply_patch`) do not write files themselves; they stream edits to the chat response (`responseStream.textEdit(uri, edit)` … `textEdit(uri, true)` for "done"), which the session routes to `acceptAgentEdits` — [T/abstractReplaceStringTool.tsx L301-L314 (M)](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/extensions/copilot/src/extension/tools/node/abstractReplaceStringTool.tsx#L301-L314); [T/createFileTool.tsx L113-L126 (M)](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/extensions/copilot/src/extension/tools/node/createFileTool.tsx#L113-L126); [CE/chatEditingSession.ts L1033-L1034 (R)](https://github.com/microsoft/vscode/blob/1.147.0/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts#L1033-L1034)

### Inferences
- What the hypothesis calls "the copy of the transaction" corresponds in VS Code to a **before-image** (an undo log entry), not a redo log / staged write set. The file on disk is the working copy the agent writes to, so tests, builds and other processes see unreviewed changes immediately. This is the "apply-then-review (P1)" pattern from the repo's earlier notes, implemented as a compensating write.
- Undo is not a no-op discard; it is a **new write** to the file (and a save). If another process read the file in between, it saw the agent's version.

### Gaps
- I did not trace every path from the chat response stream into `_acceptEdits` (the participant/progress plumbing in `chatServiceImpl`); the claim that `textEdit` parts reach `acceptAgentEdits` rests on the session code at L555-L590 and the tool code, not on a full call-graph trace.

## Snapshots, checkpoints and request-level undo

### Takeaway
Above the per-file pending-edit state there is a **checkpoint timeline**: an epoch-ordered operation log (text edits, create, delete, rename) plus per-request checkpoints. "Restore checkpoint", "edit a previous request" and chat undo/redo navigate this log by **rewriting files on disk**; they are also compensating writes, persisted across restarts in workspace storage.

### Cited Findings
- `restoreSnapshot(requestId, stopId)` → `this._timeline.navigateToCheckpoint(checkpointId)`; `undoInteraction()` → `undoToLastCheckpoint()`; `redoInteraction()` → `redoToNextCheckpoint()` — [CE/chatEditingSession.ts L420-L425, L866-L872 (R)](https://github.com/microsoft/vscode/blob/1.147.0/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts#L420-L425)
- Navigation replays or reverses recorded `FileOperationType.Create / Delete / Rename` operations (`this._delegate.createFile/deleteFile/renameFile`), then reconstructs file contents for affected URIs from the baseline plus recorded text edits (`_reconstructAllFileContents`, `_applyTextEditsToContent`) — [CE/chatEditingCheckpointTimelineImpl.ts L281-L292, L672-L730 (M)](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingCheckpointTimelineImpl.ts#L672-L730)
- Navigating to the start of a request restores the captured **baseline**, "_not_ the result state from the prior request because there may have been user changes in the meantime" (code comment) — [CE/chatEditingCheckpointTimelineImpl.ts L265-L275 (M)](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingCheckpointTimelineImpl.ts#L265-L275)
- `recordFileOperation` refuses to record an operation at an epoch earlier than the current one, and recording after an undo truncates the redo branch (it pushes onto the visible operations only) — [CE/chatEditingCheckpointTimelineImpl.ts L300-L313 (M)](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingCheckpointTimelineImpl.ts#L300-L313)
- Per-entry snapshots (`createSnapshot`) record `original` (baseline) and `current` (file) text and the entry `state`; `restoreFromSnapshot(snapshot, restoreToDisk = true)` resets both models via `resetDocumentValues` (an undoable full-range edit on the real buffer, "not done via `setValue` so that the undo stack is preserved") — [CE/chatEditingModifiedDocumentEntry.ts L192-L220 (R)](https://github.com/microsoft/vscode/blob/1.147.0/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingModifiedDocumentEntry.ts#L192-L220); [CE/chatEditingTextModelChangeService.ts L344-L360 (R)](https://github.com/microsoft/vscode/blob/1.147.0/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingTextModelChangeService.ts#L344-L360)

- Settings: `chat.checkpoints.enabled` (default `true`), `chat.checkpoints.showFileChanges` (default `false`), `chat.editing.confirmEditRequestRemoval` and `chat.editing.confirmEditRequestRetry` (both default `true`: confirm before removing/retrying a request "and its associated edits") — [src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts L584-L595, L1162-L1170 (M)](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts#L584-L595)
- Docs: "Before processing each request, VS Code creates a snapshot of affected workspace files"; restore "removes subsequent requests from the conversation history and restores the workspace files"; editing a previous request "reverts file changes made by that request and subsequent requests, and then sends the updated request" — [VS Code: Review and revert agent changes](https://code.visualstudio.com/docs/copilot/chat/review-code-edits)

### Inferences
- Two independent mechanisms exist: per-file **review state** (`originalModel` vs real buffer, Keep/Undo) and per-request **time travel** (timeline). Both act by writing the real files; neither holds proposed changes back from disk.
- Because snapshots are persisted, Keep/Undo and checkpoint restore survive a window reload (inference from storage code; I did not test it).

### Gaps
- I did not read `_reconstructAllFileContents` in full, so how it handles a file the user edited after the checkpoint (beyond the baseline comment) is not settled.

### Takeaway
No setting makes VS Code hold edits off disk until Keep. `chat.editing.autoAcceptDelay` only auto-**Keeps** after N seconds; `chat.tools.edits.autoApprove` is the one switch that turns an edit into **confirm-before-write**, and by default it does so only for sensitive files.

## Confirm-before vs apply-then-review across tools

### Takeaway
VS Code mixes the two patterns by action type: **file edits** apply then review (except sensitive/outside-workspace paths, which confirm first with a diff); **terminal commands, MCP and extension tools, URL fetches** confirm before running unless auto-approved, and none of those are covered by Keep/Undo.

### Cited Findings
- `createEditConfirmation` runs in the tool's `prepareInvocation` (before `invoke`). If no URI needs confirmation it returns `{ presentation: 'hidden' }`; otherwise it returns `confirmationMessages` titled "Allow edits to sensitive files?" with a reason — "edit files you don't have permission to modify", "edit sensitive files", "edit files outside of your workspace" or "edit system files" — plus details from `generateConfirmationDetails` (a diff via `formatDiffAsUnified`) — [T/editFileToolUtils.tsx L806-L812, L962-L1018 (M)](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/extensions/copilot/src/extension/tools/node/editFileToolUtils.tsx#L962-L1018); [T/abstractReplaceStringTool.tsx L583-L596 (M)](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/extensions/copilot/src/extension/tools/node/abstractReplaceStringTool.tsx#L583-L596)
- Permission levels: Manual (default; "Actions that are not auto-approved require your confirmation"), Assisted (model-based reviewer, Copilot harness only), Allow all; Autopilot "Auto-approves all tools, like Allow all"; "Allow all and Autopilot skip confirmation for potentially destructive actions, including file edits, terminal commands, and external tool calls" — [VS Code: Manage approvals and permissions](https://code.visualstudio.com/docs/agents/run/approvals)
- Terminal: "By default, common read-only commands run automatically, while risky commands such as rm and del require approval"; rules in `chat.tools.terminal.autoApprove` match each subcommand and "a false rule takes precedence"; "Terminal auto-approval is a best-effort convenience, not a security boundary"; `chat.tools.terminal.blockDetectedFileWrites` (experimental) defaults to `outsideWorkspace` — [approvals page](https://code.visualstudio.com/docs/agents/run/approvals)
- Confirmation scopes: "Allow Once is the default action for terminal commands, web fetches, and file access requests"; session or "Always Allow" grants; tool approval is grouped by source (MCP server, extension) in "Chat: Manage Tool Approval" — [approvals page](https://code.visualstudio.com/docs/agents/run/approvals)
- "Generic and terminal tool confirmations are read-only. If a call needs different parameters, reject it and tell the agent what to change"; Local-harness and extension-tool confirmations can allow parameter editing — [VS Code: Use tools with agents](https://code.visualstudio.com/docs/agents/run/tools)
- The approvals overview lists `chat.tools.eligibleForAutoApproval` as controlling "Which tools require confirmation before or after they run" (i.e. pre-run and post-run/result confirmations exist) — [approvals page](https://code.visualstudio.com/docs/agents/run/approvals)
- URL fetches are a two-step confirm: request approval and response approval, configured by `chat.tools.urls.autoApprove` — [approvals page](https://code.visualstudio.com/docs/agents/run/approvals); default entries `https://code.visualstudio.com` and `https://github.com/microsoft/vscode/wiki/*` — [chat.shared.contribution.ts L919-L925 (M)](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts#L919-L925)
- Sandboxing restricts terminal file-system and network access "even after the commands are approved" and stays on under Allow all / Autopilot (Preview on macOS, Linux, WSL2; Experimental on Windows) — [approvals page](https://code.visualstudio.com/docs/agents/run/approvals)

### Inferences
- The split follows reversibility: local text edits are cheap to revert from a before-image, so they skip pre-approval; commands and external calls cannot be reverted by VS Code, so they get pre-approval and sandboxing. Sensitive files are the exception because writing them can itself execute code (dev containers, MCP config, hooks), so a later Undo would be too late.

### Gaps
- MCP-specific confirmation behaviour (e.g. annotations such as `readOnlyHint` affecting prompts) was not checked in source this round.

## External effects, file creation/deletion and notebooks

### Takeaway
Only tool-tracked writes join the working set. Terminal and script changes are invisible to Keep/Undo and to checkpoints, unless a tool brackets them with the proposed `externalEdit` API, which snapshots before and diffs after. File deletion and creation happen on disk immediately; Undo recreates or deletes the file. Notebooks follow the same apply-save-then-revert pattern.

### Cited Findings

## Is it transactional? Atomicity, concurrency and conflicts

### Takeaway
Not in the database sense. There is no atomic multi-file commit: files are written one by one as edits stream, and Keep/Undo across files runs per-file I/O in parallel and then flips UI state in one observable `transaction`. Concurrency is handled by **rebasing**: user edits during review are rebased onto the baseline so Undo removes only the agent's changes, falling back to treating overlapping user edits as part of the agent diff. The newer Agent Host (Copilot harness) path adds an optimistic version check.

### Cited Findings
- Keep All / Undo All: `_operateEntry` filters entries still `Modified` and not being streamed, runs `acceptDeferred`/`rejectDeferred` for all with `Promise.all` (errors are logged and swallowed per entry), then "Execute all state transitions atomically in a single transaction" — [CE/chatEditingSession.ts L433-L472 (R)](https://github.com/microsoft/vscode/blob/1.147.0/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts#L433-L472)
- Per-resource serialisation: `_streamingEditLocks = new SequencerByKey</* URI */ string>()` queues edit streams, external edits and deletions per file — [CE/chatEditingSession.ts L163-L164 (R)](https://github.com/microsoft/vscode/blob/1.147.0/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts#L163-L164)

### Inferences
- If the file changes on disk from another process while edits are pending, VS Code's normal file-watcher reload updates `modifiedModel`, which `_mirrorEdits` sees as a non-agent edit and rebases into the baseline (or folds into the agent diff if it overlaps). So an Undo restores "baseline + outside changes", not the pre-agent bytes. This is inferred from the code paths; not tested.
- Keep All / Undo All can partially fail (one file's write errors are logged and skipped), so cross-file atomicity is UI-level only.
- The Agent Host design (version-stamped Accept/Discard against a host-owned changeset) is the nearest thing to a transactional protocol, but it is still optimistic concurrency over already-written files, not deferred commit.
