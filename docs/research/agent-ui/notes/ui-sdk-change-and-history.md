## 1. Change callbacks: `details`, `cancel()`, timing, and what `act()` returns

### Takeaway
Every `on<Key>Change` callback runs **before** the state write, and `details.cancel()` stops that write and also hides the change from `observe` and history. Nothing is ever written and then rolled back. Because the bridge's `ok` only means "no bridge error", a cancelled agent value still returns `ok: true`. The truth is in the per-step `changes` (empty for that step) and in `values`, both of which are computed by diffing live state.

### Cited Findings
- `ChangeDetails` has exactly five members: `reason`, `event?`, `source: ChangeSource`, `cancel(): void` and `readonly canceled: boolean`. The comment on `cancel` reads "Stops the change. A controlled component ignores it, since the next value comes from you." — [details.ts:171–184](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/foundation/kernel/details.ts#L171-L184)
- `ChangeSource` is `"mouse" | "touch" | "pen" | "keyboard" | "virtual" | "programmatic" | "agent"`. — [details.ts:9–10](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/foundation/kernel/details.ts#L9-L10)
- Reasons come from a shared vocabulary of about 60 strings (e.g. `"item-press"`, `"input-change"`, `"drag"`, `"imperative"` = "A controller or `api` call", `"undo"`, `"redo"`, `"restore"`). Each component exports a subset as a union. — [details.ts:20–150](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/foundation/kernel/details.ts#L20-L150)
- The agent bridge runs each step's API call inside `withSource("agent", call)`, which is why callbacks see `source: "agent"`. — [agent.ts:716–723](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/agent/agent.ts#L716-L723)
- Order inside the change function: it returns `false` early when the value is unchanged. Otherwise it builds `details`, **calls the callback**, and only then runs `store.set(...)`, and only if `!callbackDetails.canceled && !isControlled && !askedInside`. — [change.ts:98–134](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/foundation/kernel/change.ts#L98-L134)
- After a cancel, the function returns `false` **before** `watchers.change?.(...)`. So the observe registry, which feeds `observe`, `agent.subscribe` and `createHistory`, never hears a cancelled change. — [change.ts:155–158](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/foundation/kernel/change.ts#L155-L158). The docs agree: "Changes canceled with `details.cancel()` aren't reported." — [observe-changes.mdx:54](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/observe-changes.mdx#L54)
- For a controlled key, a non-cancelled change is reported to watchers at once, and the bridge remembers the requested value until the owner passes it back. The docs warn: "the notification reports the requested change before the owner passes the value back. It isn't confirmation that the owner accepted it." — [change.ts:158–175](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/foundation/kernel/change.ts#L158-L175); [observe-changes.mdx:54](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/observe-changes.mdx#L54)
- The kernel docs say "Call `details.cancel()` to refuse an uncontrolled change. Calling `event.preventDefault()` alone doesn't cancel it. With controlled state, the app decides by passing a new value or keeping the old one." The setter returns `false` "if the value was already the same or the callback canceled it". — [handle-changes.mdx:308, 277](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/core/kernel/handle-changes.mdx#L277)
- Commits (`on<Value>Commit`) "can't be canceled". — [details.ts:202–215, CommitDetails](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/foundation/kernel/details.ts#L202-L215); [handle-changes.mdx:399](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/core/kernel/handle-changes.mdx#L399)
- The documented cancel example: `if (details.source === "agent" && value === "asia-pacific") { details.cancel() }`. — [permissions.mdx:111–125](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/permissions.mdx#L111-L125)
- `act()` returns `{ ok: !error, error?, steps: log, open?, appeared, values }`. `error` is set only when a step **throws**: an `allow` refusal, "Needs a person", a disabled target, a superseded restoration, or a bad ref or argument. — [agent.ts:1853–1905](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/agent/agent.ts#L1853-L1905); throws at [agent.ts:1310–1321](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/agent/agent.ts#L1310-L1321), [1696](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/agent/agent.ts#L1696), [1708–1712](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/agent/agent.ts#L1708-L1712)
- A step's `changes` comes from `since(prior, …)`, a diff of each component's state keys before and after the step. A cancelled value therefore produces no change entry. `values` is read from live state after the call. — [agent.ts:914–948, 867–910](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/agent/agent.ts#L867-L948)
- Documented field meaning: `ok` is "Whether every step ran without a bridge error." — [reference.mdx:127](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/reference.mdx#L127)
- Quote (gap): "A callback can also cancel a change without making the step fail, so `ok: true` doesn't mean every requested value was accepted." — [reference.mdx:136](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/reference.mdx#L136)
- Quote (gap): "Canceling a value change can leave `act` with `ok: true` and no change for that step." — [permissions.mdx:127](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/permissions.mdx#L127); and "`act` can return `ok: true` while a change callback cancelled a value. Check `result.values` or the DOM" — [agent-ready.md:133](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/skills/ui-sdk/references/agent-ready.md#L133)

### Inferences
- `cancel()` is a **pre-write veto**, not an undo. Nothing reaches the store, nothing reaches history, and nothing exists to revert. That is good for "never let the agent set X". It does nothing for "let the agent set X, then let the person decide".
- `details` carries no **reason for refusal** back to the agent. `cancel()` takes no argument, and the act result shows only the missing change. A model that wants to learn why must infer it from `values`. A UI that wants to tell the model why must return that text through its own channel (inferred from the `cancel: () => void` signature and the result shape).
- `details` carries no act/step/call id, so a callback cannot tell which `act` call or which step of a batch produced a change (from the five members listed above).
- For **controlled** components, `cancel()` is described as ignored. A controlled owner refuses by not passing the value back, and then `observe`/history have already heard the request. Undo built on history can then hold an entry for a value that never landed (inference from change.ts:158–175 plus observe-changes.mdx:54; the restore code guards against this with `same(current(step), step.value)`, see section 2).

### Gaps
- I did not trace every component's `api` for whether it surfaces the boolean from the change function. The bridge does not use it: `perform` neither throws nor flags on a `false` return. The docs say this directly at reference.mdx:136.
- I found no documented way for a change callback to attach a message the agent sees.

## 2. History: `createHistory`, `undoSource`, `seek`, `stageChanges`, `createUndoStack`

### Takeaway
`createHistory(agent)` is an in-memory, page-scoped log of component value changes, one entry per (component, key) change with its `source`. It offers editor-style `seek(n)` and a selective `undoSource("agent")` that reverts every applied agent entry while keeping other sources' later values. Restoration is itself a sequence of agent `act` calls, one per key, so it passes through `allow` and change callbacks and can be refused, and it reports what failed. It restores only recorded state keys (`value`, `checked`, `pressed` by default). It has no depth limit, no persistence, and no grouping by act call. `stageChanges` is a separate preview/revert primitive. `createUndoStack` is a generic snapshot stack for one component's own state.

### Cited Findings
**API (createHistory)**
- `createHistory(agent, { within?, keys?, coalesce? })` returns `entries()`, `position()`, `subscribe(listener)`, `seek(to)`, `undoSource(source)`, `clear()` and `destroy()`. — [history.ts:127–360](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/history/history.ts#L127-L360); docs [history-and-undo.mdx:12–113](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/history-and-undo.mdx#L12-L113)
- `HistoryEntry` = `{ id, ref, label, key, value, previous, source, reason, reverted?, redacted? }`. `source` holds "`agent`, or how a person did, like `pointer` or `keyboard`". (The code comment says `pointer`, but `ChangeSource` has no `"pointer"`. It has `mouse`/`touch`/`pen`. This is a small doc-comment inconsistency.) — [history.ts:14–33](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/history/history.ts#L14-L33) vs [details.ts:9–10](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/foundation/kernel/details.ts#L9-L10)

A wrapped `act` throws "createHistory requires an agent with the original act method returned by createAgent." — [history.ts:131–136](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/history/history.ts#L131-L136); test [history.test.ts:114–118](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/test/history.test.ts#L114-L118)
- Recording listens through `observe` (so cancelled changes never appear) and keeps only `keys` (default `["value", "checked", "pressed"]`). — [history.ts:137, 151–154, 197–200](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/history/history.ts#L137-L200)
- `describeEntry` renders "Agent set Region to Frankfurt" or "You set …". Every non-agent source is shown as "You". — [history.ts:83–85](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/history/history.ts#L83-L85)

**Granularity**
- One entry per (ref, key) change. With `coalesce` (default true), consecutive changes with the same ref, key, source and reason fold into one entry, except reasons `item-press` and `imperative`. A committed drag arrives as one entry because `observe` reports commits, not steps, unless `coalesce: false` sets `live: true`. — [history.ts:175–200](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/history/history.ts#L175-L200); [history-and-undo.mdx:103–111](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/history-and-undo.mdx#L103-L111)
- Scope is per page by default, narrowed to an element with `within`. — [history-and-undo.mdx:23–32](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/history-and-undo.mdx#L23-L32)
- Entries carry no act or step identifier (see the type above). A multi-step `act` produces several independent entries.

**seek (step back/forward)**
- `seek(to)` clamps the target. For every key touched between the current and target positions, it computes the value at the target, skipping reverted entries, and writes it back. It resolves with the steps it could not put back. If none went back and nothing new was recorded, the position reverts. — [history.ts:276–305](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/history/history.ts#L276-L305); [history-and-undo.mdx:54–67](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/history-and-undo.mdx#L54-L67)
- "A change made from the past drops the future it replaces" (truncating redo, like an editor). — [history.ts:175–176](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/history/history.ts#L175-L176); [history-and-undo.mdx:61](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/history-and-undo.mdx#L61)

**undoSource (undo by who made the change)**
- `undoSource(source)` walks applied entries. For each touched key it restores "its latest value from the other sources, or to its starting value if there isn't one"; reverted entries get `reverted: true` and stay in the list. — [history.ts:311–349](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/history/history.ts#L311-L349); [history-and-undo.mdx:69–79](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/history-and-undo.mdx#L69-L79)
- Quote: "if a person changes the project name after the agent does, that person's value stays." — [history-and-undo.mdx:77](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/history-and-undo.mdx#L77)
- It accepts any source string, e.g. `"keyboard"` or `"programmatic"`. — [history-and-undo.mdx:79](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/history-and-undo.mdx#L79)
- Source attribution leaks across `await`. A Button handler's change made after an `await` "is recorded as `"programmatic"` and `undoSource("agent")` leaves it", unless the app wraps it in `withSource(source, …)`. — [history-and-undo.mdx:81–101](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/history-and-undo.mdx#L81-L101)

**How restoration works, and why it may not be exact**
- Restoration goes "through `agent.act`, one control at a time, so current permissions, disabled state and change callbacks still apply, and a control that's refused or has left the page doesn't stop the others." — [history-and-undo.mdx:63](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/history-and-undo.mdx#L63)
- In code, `restore` calls the guarded internal `act` with one `set<Key>` step per key. A step counts as done only if `act(...).ok` **and** `same(current(step), step.value)`, with the comment "A change callback or a controlled owner can refuse a write the agent still calls done." So history, unlike a raw `act` caller, checks the live value. — [history.ts:205–251](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/history/history.ts#L205-L251)
- The guard: if a non-agent change hits a key while it is being restored, that key is dropped from the restore ("Anyone else's change is later than the restore, so it stays"), and the bridge throws "The restoration of … was superseded by a newer change." — [history.ts:141, 157–161, 209–217](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/history/history.ts#L141-L217); [agent.ts:1708–1712](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/agent/agent.ts#L1708-L1712)
- A refused undo keeps the entry applied and reports it: test "an undo a change callback refuses is reported, and its entry stays applied", and the matching test for `seek`. — [history.test.ts:46–70](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/test/history.test.ts#L46-L70)
- Redacted (password, card, OTP, `data-agent-secret`) entries are never restored and are reported as failed. — [history.ts:27–32, 218–227](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/history/history.ts#L27-L227); [history-and-undo.mdx:34](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/history-and-undo.mdx#L34)

- Restores need a settable key: "Restoring a key uses its `set<Key>` action… so choose keys the component can set through the bridge." — [history-and-undo.mdx:32](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/history-and-undo.mdx#L32)

**createUndoStack (per-component state undo)**
- A pure snapshot stack: `record(state, { group?, time? })`, `undo()`, `redo()`, `canUndo`, `canRedo`, `seal`, `map` and `reset`. The defaults are `limit` **100** and `groupDelay` **500 ms**. It has no notion of source. — [undo-stack.ts:9–111](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/foundation/kernel/undo-stack.ts#L9-L111)
- The docs point to it "For undo inside one component, like a drawing or a board". — [history-and-undo.mdx:8](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/history-and-undo.mdx#L8); [handle-changes.mdx:489–517](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/core/kernel/handle-changes.mdx#L489-L517)

### Inferences
- **Undo of an agent step is exact only for recorded, settable, non-secret value keys still on the page whose restore the policy accepts.** It does not cover open/closed state, presses (submit, delete, send), network side effects, removed rows, or keys outside `keys`. It can fail on a control marked `data-agent-confirm` when no `allow` exists, because restore steps go through `perform`, which throws "Needs a person" (agent.ts:1310–1314). That last point is inferred from the code path; the docs say only "current permissions… still apply".
- **Undo writes are agent writes.** Restore calls run inside `asAgent`, so change callbacks see `source: "agent"`. An app rule like "cancel agent changes to Asia Pacific" will also cancel an *undo* back to Asia Pacific, and an `allow` prompt can fire for an undo. The `details` passed to the callback cannot tell an undo from a fresh agent action: no distinct source or reason is set by `restore`. This is inferred from history.ts:229–238 and agent.ts:716–723; the docs do not discuss it.
- **No per-act undo.** `undoSource("agent")` reverts *all* applied agent entries in the history, and `seek(n)` reverts everyone's later changes. To undo just the last agent turn, an app would record `position()` before `act` and `seek` back to it, which also reverts interleaved human edits. Alternatively it could create a fresh history per turn, or use `stageChanges`. Coalescing can also merge two agent turns into one entry when they set the same field with the same non-`imperative` reason (inferred from history.ts:178–188; I did not confirm which reason a bridge `set<Key>` call reports).
- **Not persistent across reload.** The log lives in memory, and refs are only stable while a component stays mounted, so a stored log could not be replayed reliably after reload (inference).
- `stageChanges.revert()` overwrites a person's edits made during the preview, while `createHistory` preserves them. The two helpers disagree on conflict policy, and a UI must choose (from history-and-undo.mdx:77 vs :139).

### Gaps
- I did not run any code. Behaviour claims rest on source reading plus the repo's own tests, which I read but did not execute.
- I found no docs on history size limits, memory growth, or persistence, and no statement that they are planned.

## 4. Is multi-step `act({ steps })` atomic?

### Takeaway
No. Steps run sequentially, each written and rendered before the next. The call stops at the first throwing step and leaves earlier steps applied. Cancelled steps do not stop the call. No group id, transaction, or group-level undo exists.

### Cited Findings
- `act` loops over steps, `await perform(...)` each, logs that step's diff, and `break`s on the first thrown error. Nothing is undone after the break. — [agent.ts:1853–1887](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/agent/agent.ts#L1853-L1887)
- `perform` "Runs one step as the agent, once `allow` lets it, and waits for the page to render it". `allow` is asked per step, not per batch. — [agent.ts:1264–1324](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/agent/agent.ts#L1264-L1324)
- Docs: "Runs steps in order… Stops at the first step that fails, and says which." — [agent.ts:2078–2086](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/agent/agent.ts#L2078-L2086); "there is no rollback" — [reference.mdx:136](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/reference.mdx#L136)
- Calls on one bridge are serialized: "`act` and `query` calls on the same bridge are queued", and while a step waits on `allow`, "another call can't run, so an agent can't press that confirm itself." — [reference.mdx:138](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/reference.mdx#L138); [agent.ts:2041–2049](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/agent/agent.ts#L2041-L2049)
- The result includes `steps[].changes` and `gone`, so "a change that a later step undid or took off the page, like a removed row, still shows". — [agent.ts:1855–1882](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/agent/agent.ts#L1855-L1882)

### Inferences
- The serialization covers bridge calls only. A person can still edit the page between steps of one `act` (each step awaits rendering), so a batch is not isolated from human edits either. This is inferred from the awaits in `perform`; the history's supersede guard exists precisely for this interleaving.
- To reverse a batch as a group, the app must bracket it: record `history.position()` before the call and `seek` back on Revert, or run the batch through `stageChanges` and call `revert()`. Neither gives atomicity. Each can partially fail and reports what it couldn't put back.

### Gaps
- No docs discuss group undo for one `act` call.

## 5. What a UI must add for draft-then-commit (Keep/Revert) or an undo toast

### Takeaway
UI SDK supplies the parts: source-tagged change events, a source-filtered history with `seek` and `undoSource`, a stage/revert helper, and `elementOf(ref)` for highlighting. It does not supply a draft layer. Agent edits land on live state, and any backend write a component triggers is outside its reach. Keep/Revert and undo toasts are app-level work built on these parts.

### Cited Findings
- Available parts: `stageChanges` + `revert()` (preview on real controls, "If the person accepts the suggestion, leave the values in place"), `createHistory` + `undoSource("agent")`/`seek`, `subscribe` for a live list, `describeEntry` for toast text, and `elementOf(ref)` "for pointing at a component, like a highlight around what an agent just changed." — [history-and-undo.mdx:115–141](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/history-and-undo.mdx#L115-L141); [observe.ts:48–61](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/observe/observe.ts#L48-L61); [history.ts:83–85](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/history/history.ts#L83-L85)
- Pre-write vetoes exist: `allow` per step (5-minute default timeout) and `data-agent-confirm` hand-offs, plus `cancel()` in change callbacks. — [agent.ts:661–671](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/agent/agent.ts#L661-L671); [permissions.mdx:111–127](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/permissions.mdx#L111-L127)

### Inferences (all inferred from the mechanisms above; none of these are documented recipes)
- **Undo toast for an agent turn.** Create a history scoped to the edited region, snapshot `position()` before the model's `act`, and after it render `entries().slice(p)` with `describeEntry` in a toast. On Undo, call `seek(p)`, or `undoSource("agent")` if that history covers only this turn. Then show what `seek` returned as "couldn't undo". The app must also (a) keep side-effecting actions out of the undoable set, gating `press` on save/send/delete with `data-agent-confirm`/`allow`, because history cannot reverse them; (b) make sure its own change callbacks don't cancel the undo writes, which arrive as `source: "agent"`; and (c) wrap post-`await` handler writes in `withSource` so they are attributed correctly.
- **Draft-then-commit (Keep/Revert).** `stageChanges` is the closest built-in, but it writes to live controls, so any `onValueChange` that persists to a server commits the "draft" at once. A real draft needs the app to defer persistence. Options: buffer changes whose `details.source === "agent"` in a pending store and persist only on Keep; or keep the component controlled and show the agent's value as a suggestion without committing it, the pattern of the `suggestions.tsx` experiment. Revert must also decide the conflict policy: `stageChanges.revert()` clobbers the person's intervening edits, while `undoSource` keeps them.
- **Trust the live state, not `ok`.** Any Keep/Revert UI should list what actually changed using `steps[].changes`/`values`, or history entries (which exclude cancelled changes), not the requested steps. Requested-but-cancelled values would otherwise appear as pending edits.
- **Server-side state** (form saves, mutations triggered by `press`) needs its own compensation or soft-delete mechanism. UI SDK has none, and its docs exclude it explicitly (history-and-undo.mdx:63).

### Gaps
- I found no official example combining `createHistory` with a toast, or a documented Keep/Revert flow beyond the experimental `suggestions.tsx`, whose full logic I did not read line by line.
- I found no third-party write-up of building undo on UI SDK; the library was released around 2026-11-13 (secondary, per the existing notes).
