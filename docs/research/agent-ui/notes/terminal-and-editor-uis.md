## Claude Code: terminal UI stack, headless mode, SDK and IDE integrations

### Takeaway
Claude Code's terminal UI is a React renderer derived from Ink (Yoga-laid-out `ink-box`/`ink-text` nodes, inferred from strings in the shipped binary), with two renderers: a "classic" main-screen renderer and a "fullscreen" alternate-screen renderer that virtualizes the transcript. The same engine is driven headlessly by `claude -p` with `stream-json`, which the Agent SDK wraps, and the VS Code extension bundles a private copy of the CLI for its webview chat panel. As of v2.1.327, a public plugin "mods" API lets plugins draw UI as a surface-neutral element tree (`Box`, `Text`, `Button`) that renders on terminal, desktop, VS Code and mobile surfaces.

### Cited Findings
- **Two renderers.** "Fullscreen rendering is an alternative rendering path for the Claude Code CLI that eliminates flicker, keeps memory usage flat in long conversations, and adds mouse support. It draws the interface on the terminal's alternate screen buffer, like `vim` or `htop`, and only renders messages that are currently visible." It is a "research preview"; `/tui fullscreen` and `/tui default` switch renderers and relaunch "with your conversation intact" — [Fullscreen rendering](https://code.claude.com/docs/en/fullscreen.md)
- The flicker problem is worst "in terminal emulators where rendering throughput is the bottleneck, such as the VS Code integrated terminal, tmux, and iTerm2" — [Fullscreen rendering](https://code.claude.com/docs/en/fullscreen.md)
- Env switches: `CLAUDE_CODE_NO_FLICKER=1` enables fullscreen; `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1` or `CLAUDE_CODE_NO_FLICKER=0` forces classic; screen-reader mode always uses classic, except attached background sessions — [Fullscreen rendering](https://code.claude.com/docs/en/fullscreen.md)
- v2.1.327 changelog: "Added `/tui classic` as the name for the non-fullscreen renderer"; the changelog's recent entries are dominated by fullscreen fixes (pinned prompt, jump-to-bottom pill, collapsed tool groups with timers, transcript virtualization going blank on far jumps, mouse escape codes leaking after exit) — [CHANGELOG.md](https://github.com/anthropics/claude-code/blob/v2.1.327/CHANGELOG.md) (lines 12, 315-409)
- **Ink lineage (inferred from binary strings, not source).** The linux-x64 binary bundled with `@anthropic-ai/claude-agent-sdk` 0.3.327 (CLI 2.1.327, a Bun-compiled single file) contains Ink host-node names `ink-box`, `ink-text`, `ink-virtual-text`, `ink-link`, Yoga calls (`yogaNode.setMeasureFunc`, `getComputedHeight`), the string "mounted around every Ink root by src/ink.ts", "Ink instance not found - cannot pause rendering", and the CSI 2026 synchronized-output sequence `ESC[?2026h`. No `react-reconciler` or `yoga-layout` package-name strings appear, consistent with a vendored/forked Ink rather than the npm package. Method: `grep -a` on the binary in `node_modules/.pnpm/@anthropic-ai+claude-agent-sdk-linux-x64@0.3.327/` in this repo; the code was not run. SDK manifest: [docs/reference/claude-agent-sdk](../../../reference/claude-agent-sdk/) pin; [npm package](https://www.npmjs.com/package/@anthropic-ai/claude-agent-sdk)
- The binary also contains "Used by tools that previously rendered Ink JSX via setToolJSX with an onDone callback", suggesting tools historically rendered their own Ink JSX into the transcript (inferred from binary strings).
- **Plugin UI API (public types).** "A mod is a Claude Code plugin whose behaviour lives in a hooks module… `ui.render` answers, with the node Claude Code draws." The built-in `diff` mod implements `/diff`: "the session's uncommitted changes in a pane beside the transcript, file by file with their hunks, refreshed as Claude edits files and runs commands" — [mods/README.md](https://github.com/anthropics/claude-code/blob/v2.1.327/mods/README.md)
- `ui.render` "Fires when the engine is about to draw a component… `next(e)` resolves to the drawing: return it, wrap it, draw your own, or rewrite `props`. An invalid tree, or a throw while drawn, draws the engine's" — [mods/types/claude-code.d.ts](https://github.com/anthropics/claude-code/blob/v2.1.327/mods/types/claude-code.d.ts) (~line 4850)
- `RenderElement` is a union of `Box`, `Text`, `Button`, etc.; a `Button` renders "`[ label ]` on the terminal, a native button on a desktop"; JSX has "no intrinsic (string) tags", only constructors from `$.ui.resolve(e)`. Named overridable components include `Pane`, `ToolUse`, `AgentRow`, `ContextMenu`, `Backdrop`. Surfaces enumerated in examples: `terminal`, `desktop`, `vscode`, `mobile` — [claude-code.d.ts](https://github.com/anthropics/claude-code/blob/v2.1.327/mods/types/claude-code.d.ts) (lines ~51-58, 11985-11995, 19380-19400)
- **Headless mode.** `claude -p` is "the Agent SDK via the CLI". `--output-format` is `text` (default), `json` ("result, session ID, and metadata") or `stream-json` ("newline-delimited JSON for real-time streaming"); token streaming needs `--output-format stream-json --verbose --include-partial-messages`. `--bare` skips discovery of hooks, skills, plugins, MCP servers and CLAUDE.md. A `-p` session "shows no workspace trust dialog and no per-server approval prompt" — [Run Claude Code programmatically](https://code.claude.com/docs/en/headless.md)
- The Agent SDK spawns the CLI with `--output-format stream-json --verbose --input-format stream-json`; control requests (`can_use_tool`, `interrupt`, `elicitation`, …) share the stream — [interfaces-and-extensions.md §1, §3](../../agent-harness/notes/interfaces-and-extensions.md)
- **VS Code extension.** "The extension bundles its own copy of the CLI (command-line interface) for the chat panel." In Manual permission mode an edit "shows a side-by-side comparison of the original and proposed changes, then asks for permission. You can accept, reject, or tell Claude what to do instead"; per-change **Accept this change / Reject this change** buttons since v2.1.275, disabled for diffs with more than 100 changes. Plan mode "automatically opens the plan as a full Markdown document where you can add inline comments". Permission modes (Auto, Manual, Plan) are switched from an indicator under the prompt box — [VS Code](https://code.claude.com/docs/en/vs-code.md)
- CLI-in-terminal integration: running `claude` in the integrated terminal "connects automatically" to the installed extension; from an external terminal `/ide` connects — [VS Code](https://code.claude.com/docs/en/vs-code.md) (section "VS Code extension vs. Claude Code CLI")
- Zed runs Claude as an ACP "External Agent" via Zed's SDK adapter (`zed-industries/claude-agent-acp`) — [ACP agents list](https://github.com/agentclientprotocol/agent-client-protocol/blob/v1.19.0/docs/get-started/agents.mdx); [Zed external agents](https://zed.dev/docs/ai/external-agents)

### Inferences
- Claude Code's direction is a surface-neutral component tree (Box/Text/Button) that each surface draws natively, which lets one plugin UI target terminal, desktop, VS Code and mobile. The Ink-style `Box`/`Text` vocabulary of the mods API matches the internal renderer's node names.
- Fullscreen exists because main-screen Ink re-renders the whole live region and floods slow terminals; alternate-screen with viewport virtualization is the fix, at the cost of giving up native scrollback.

### Gaps
- The interactive renderer's source is not public, so the React version, reconciler, and whether Ink is forked or rewritten could only be inferred from binary strings.
- How the VS Code webview talks to its bundled CLI (stream-json over stdio is likely, given the SDK) is not documented on the pages read; mark as inference.
- JetBrains page fetched but not analysed in depth ([JetBrains](https://code.claude.com/docs/en/jetbrains.md)).

## OpenAI Codex CLI: ratatui TUI, app-server protocol, exec mode, approvals

### Takeaway
Codex's TUI is a Rust ratatui 0.30 + crossterm app that keeps the terminal's native scrollback for finished history (inserting rendered cells above an inline viewport via escape sequences) and renders only the live tail and the bottom pane through ratatui. It is a client of the app-server JSON-RPC protocol: by default it embeds the server in-process, but it can attach to a shared local daemon or a remote `ws://` app-server, and the same protocol powers the VS Code extension and desktop/mobile apps.

### Cited Findings
- **Stack.** `codex-tui` depends on `ratatui` 0.30.2 (workspace pin), `crossterm` 0.29 (patched to an `openai-oss-forks/crossterm` git rev), `pulldown-cmark` 0.10 (Markdown), `syntect` 5 (syntax highlighting), `diffy` 0.4.2 (diffs), `vt100` 0.16.2, `textwrap` — [codex-rs/tui/Cargo.toml](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/Cargo.toml); [codex-rs/Cargo.toml](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/Cargo.toml) (lines 389-686)
- **Scrollback-native transcript.** "Codex uses the terminal scrollback itself for finalized chat history, so inserting a history cell is an escape-sequence operation rather than a normal ratatui render." A `FullScreen` insertion mode exists for terminals where "partial scroll regions are unreliable" and for Zellij — [tui/src/insert_history.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/src/insert_history.rs) (lines 1-60)
- Terminal init: "inline viewport; history stays in normal scrollback"; the alternate screen is used only when "an overlay or the owned transcript" is active — [tui/src/tui.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/src/tui.rs) (lines 499, 727-744)
- **Transcript model.** "`ChatWidget` consumes protocol events, builds and updates history cells… The UI has both committed transcript cells (finalized `HistoryCell`s) and an in-flight active cell (`ChatWidget.active_cell`) that can mutate in place while streaming (often representing a coalesced exec/tool group). The transcript overlay (`Ctrl+T`) renders committed cells plus a cached, render-only live tail" — [tui/src/chatwidget.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/src/chatwidget.rs) (lines 1-17)
- **Streaming.** Markdown deltas are committed at newline boundaries (`MarkdownStreamCollector`); each stream has a "stable region (committed to scrollback via the animation queue)" and a mutable "tail region"; pipe tables are held back as mutable tail "so adding a row can reflow earlier table rows instead of committing a stale render to scrollback"; Mermaid fences become diagrams on close — [markdown_stream.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/src/markdown_stream.rs); [streaming/controller.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/src/streaming/controller.rs); [streaming/table_holdback.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/src/streaming/table_holdback.rs)
- Adaptive pacing: `ChunkingMode::Smooth` drains "one queued line… per baseline commit tick"; under queue pressure `CatchUp` "drains queued backlog immediately", with hysteresis — [streaming/chunking.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/src/streaming/chunking.rs)
- **Diffs.** `diff_render.rs` "Renders unified diffs with line numbers, gutter signs, and optional syntax highlighting"; backgrounds adapt to terminal lightness (dark `#212922`/`#3C170F`), with fixed palettes for truecolor/256/16 colours; each hunk is highlighted as one block to keep syntect parser state — [tui/src/diff_render.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/src/diff_render.rs) (lines 1-33)
- **Approvals in the UI.** The approval overlay "converts agent approval requests (exec/apply-patch/MCP elicitation) into a list-selection view with action-specific options"; "Selection always emits an explicit decision event"; Esc on MCP elicitation always means Cancel — [bottom_pane/approval_overlay.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/src/bottom_pane/approval_overlay.rs). Option labels include "Yes, just this once", "Yes, and don't ask again for commands that start with `…`", "Yes, and allow this host for this conversation", "No, and block this host in the future", "No, continue without running it", "No, and tell Codex what to do differently"; patch approvals offer "Yes, and don't ask again for these files" (same file, lines ~870-1077)
- Approval policies: `untrusted` (UnlessTrusted), `on-request` (alias `on-failure`), `Granular(...)` (per-category auto-allow or auto-reject), `never` — [codex-rs/protocol/src/protocol.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/protocol/src/protocol.rs) (lines ~1184-1205)
- The bottom pane owns the composer plus "a stack of transient `BottomPaneView`s (popups/modals)"; input goes only to the top of the stack — [bottom_pane/mod.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/src/bottom_pane/mod.rs)
- Subagents: `multi_agents.rs` owns "multi-agent history rows, `/subagents` picker entries, and the fast-switch keyboard shortcuts" — [tui/src/multi_agents.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/src/multi_agents.rs)
- **UI/core separation.** The TUI depends on `codex-app-server-client`, `codex-app-server-daemon` and `codex-app-server-protocol`; `app_server_session.rs` is the "App-server session facade… owns the typed JSON-RPC calls needed by the TUI" — [tui/Cargo.toml](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/Cargo.toml) (lines 34-36); [app_server_session.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/src/app_server_session.rs)
- Daemon vs embedded: "If an implicitly discovered daemon cannot initialize the connection, the TUI starts an embedded server instead. Explicit `--remote` endpoints remain authoritative"; the daemon backs "remote clients such as the desktop and mobile apps" (experimental) — [app-server-daemon/README.md](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-daemon/README.md)
- "Codex app-server is the interface Codex uses to power rich clients (for example, the Codex VS Code extension)." Transports: stdio JSONL (default), `ws://` ("experimental and unsupported"), `unix://`. "Remote terminal UI mode lets you run app-server on one machine and connect the Codex CLI terminal interface from another" — [Codex App Server docs](https://developers.openai.com/codex/app-server)
- Thread items the UI renders: `UserMessage`, `AgentMessage`, `Plan`, `Reasoning`, `CommandExecution`, `FileChange`, `McpToolCall`, `DynamicToolCall`, `CollabAgentToolCall`, `SubAgentActivity`, `ImageView`, `EnteredReviewMode`/`ExitedReviewMode`, `ContextCompaction` — [app-server-protocol/src/protocol/v2/item.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-protocol/src/protocol/v2/item.rs) (lines 319-515)
- **Exec mode.** `codex exec` defaults to a read-only sandbox; `--json` makes stdout JSONL with `thread.started`, `turn.started|completed|failed`, `item.*`, `error`; `--full-auto` "is no longer supported" (use `--sandbox workspace-write` or `--approve-for-me`) — [Non-interactive mode](https://developers.openai.com/codex/noninteractive). `codex exec` is itself an in-process app-server client — [interfaces-and-extensions.md §2](../../agent-harness/notes/interfaces-and-extensions.md)
- Zed drives Codex through the ACP adapter `agentclientprotocol/codex-acp` — [ACP agents list](https://github.com/agentclientprotocol/agent-client-protocol/blob/v1.19.0/docs/get-started/agents.mdx)

### Inferences
- Codex chose a hybrid "inline viewport + native scrollback" design, the opposite of Claude Code's fullscreen path: finished cells are immutable once written to scrollback, so everything that can still change (tables, active tool groups) must be held in the mutable tail.
- Because the TUI is just one app-server client, the TUI, VS Code extension, desktop app and remote TUI all see the same thread/turn/item model and approval server-requests.

### Gaps
- The VS Code extension's source is not in the repo; its use of app-server is from the official docs only.

## Pi: pi-tui differential renderer, RPC/JSON modes, extension UI

### Takeaway
Pi ships its own minimal TUI library, `@earendil-works/pi-tui` 1.5.2 (runtime deps only `marked`, `get-east-asian-width`, `marked-cjk-friendly`), built on a line-array `Component.render(width): string[]` contract with differential rendering, CSI 2026 synchronized output, and two interchangeable renderers (main-screen with native scrollback, alternate-screen with app-owned scrolling; fullscreen is the default). Extensions get a `ctx.ui` API whose dialog methods degrade to an `extension_ui_request` subprotocol in RPC mode, so the same extension works under a foreign frontend.

### Cited Findings
- "Minimal terminal UI framework with differential rendering and synchronized output for flicker-free interactive CLI applications"; features: interchangeable renderers, differential rendering ("Updates only changed lines or viewport rows"), CSI 2026, bracketed paste, Kitty/iTerm2 inline images — [packages/tui/README.md](https://github.com/earendil-works/pi/blob/v1.5.2/packages/tui/README.md) (lines 1-17)
- Renderers: "`TuiMainScreen` renders into the main terminal buffer and preserves terminal scrollback. `TuiAltScreen` renders a fixed-height viewport in the alternate terminal buffer with application-owned scrolling. When stopped, it restores the main buffer and prints the complete final document" — [packages/tui/README.md](https://github.com/earendil-works/pi/blob/v1.5.2/packages/tui/README.md) (lines 57-63)
- Main-screen strategy: first render prints all lines; on width change or "Change Above Viewport" it clears and fully re-renders; normal update moves "the cursor to the first changed line, clear to the end, and render changed lines". Alt-screen updates changed rows in place, follows streaming output at the bottom, supports mouse wheel, OSC 133 prompt jumps, OSC 8 links, OSC 52 copy-on-select — [packages/tui/README.md](https://github.com/earendil-works/pi/blob/v1.5.2/packages/tui/README.md) ("Rendering modes", lines 745-755)
- Component contract: `render(width): string[]`, each line "must not exceed `width` or the TUI will error"; optional `handleInput`, `handleMouse`, `invalidate()` — [packages/tui/README.md](https://github.com/earendil-works/pi/blob/v1.5.2/packages/tui/README.md) (lines 245-262)
- `pi --tui-mode <mode>`: "Uses `fullscreen` (default) or `regular` terminal mode" — [coding-agent/docs/cli.md](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/cli.md) (line 236)
- Extension UI integration points: `ctx.ui.select/confirm/input/editor` for dialogs, `notify`/`setStatus`, `setWidget` ("Persistent content near the editor"), header/footer/editor factories, `ctx.ui.custom()` for overlays, and "Custom rendering for a tool or session entry" via renderers; "Do not create a second terminal renderer inside an extension" — [coding-agent/docs/tui.md](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/tui.md)
- Tools can define `renderCall`/`renderResult`; overriding a built-in tool without renderers inherits "the built-in renderer… (syntax highlighting, diffs, etc.)"; `pi.registerMessageRenderer(customType, renderer)` — [coding-agent/docs/extensions.md](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/extensions.md) (lines 1622-1623, 1805, 2375)
- `ui_prompt_start`/`ui_prompt_end` events fire around blocking dialogs "so host/status integrations can report 'waiting for user'" — [extensions.md](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/extensions.md) (line 699)
- RPC extension UI: dialog methods "emit an `extension_ui_request` on stdout and block until the client sends back an `extension_ui_response`"; `notify`, `setStatus`, `setWidget`, `setTitle`, `set_editor_text` are fire-and-forget; `custom()` returns `undefined` and `setFooter`/`setHeader`/`setEditorComponent` are no-ops in RPC mode; guard TUI-only code with `ctx.mode === "tui"` — [coding-agent/docs/rpc-extension-ui.md](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/rpc-extension-ui.md)
- Modes: print, `--mode json` (JSONL events), `--mode rpc`; all share one `AgentSession` — [interfaces-and-extensions.md §1-3](../../agent-harness/notes/interfaces-and-extensions.md); [cli-integration.md](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/cli-integration.md)
- Third-party frontends: Pi reaches ACP clients via the community `svkozak/pi-acp` adapter — [ACP agents list](https://github.com/agentclientprotocol/agent-client-protocol/blob/v1.19.0/docs/get-started/agents.mdx); and AHP clients via `Qusic/pi-ahp` over WebSocket — [Agent Host Protocol README](https://github.com/microsoft/agent-host-protocol)

### Inferences
- Pi's line-array component model trades layout power (no flexbox) for predictable width handling and cheap line diffs; it is the smallest viable TUI architecture among the products studied.
- The RPC degradation table is a useful template: classify every UI call as blocking dialog, fire-and-forget, or terminal-only, so headless frontends know which they must implement.

### Gaps
- Pi has no first-party IDE extension; editor support is community adapters only (as found).

## OpenCode: TUI as a client of a local server, SDK, multiple frontends

### Takeaway
OpenCode 2.3.0 is client/server: a shared background server (Effect `HttpApi`, OpenAPI-described, SSE events) is started on demand, and the terminal UI (`@opencode/tui`, built on OpenTUI 0.8.4 with SolidJS 1.9.17), a web UI, an Electron desktop app, mobile pairing and `opencode acp` are all clients. The TUI talks to the server through the generated `@opencode/client`.

### Cited Findings
- `@opencode/tui` 2.3.0 depends on `@opentui/core`, `@opentui/keymap`, `@opentui/solid` and `solid-js`; root catalog pins `@opentui/*` 0.8.4 and `solid-js` 1.9.17 (with a local patch) — [packages/tui/package.json](https://github.com/sst/opencode/blob/910c423/packages/tui/package.json); [package.json](https://github.com/sst/opencode/blob/910c423/package.json) (lines 54-164)
- Other frontends: `@opencode/desktop` (Electron 44.9.1, Solid), `@opencode/app` (Solid web app), `@opencode/session-ui` (shared Solid session UI) — package.json files under [packages/](https://github.com/sst/opencode/tree/910c423/packages)
- The TUI imports `OpenCode` from `@opencode/client` and `createClientConnection` from `@opencode/client/solid` — [packages/tui/src/app.tsx](https://github.com/sst/opencode/blob/910c423/packages/tui/src/app.tsx) (lines 6-7); [packages/tui/src/context/client.tsx](https://github.com/sst/opencode/blob/910c423/packages/tui/src/context/client.tsx)
- `@opencode/client` is "Private generation target for clients derived directly from OpenCode's authoritative Effect `HttpApi`"; a zero-Effect Promise client using `fetch` plus an Effect client; "Custom transports such as the PTY WebSocket connection remain outside the generic HTTP client" — [packages/client/README.md](https://github.com/sst/opencode/blob/910c423/packages/client/README.md)
- Default command resolves a server connection, printing "Starting background server..." or "Restarting background server (version mismatch)..."; a `standalone` option exists — [packages/cli/src/commands/handlers/default.ts](https://github.com/sst/opencode/blob/910c423/packages/cli/src/commands/handlers/default.ts); server modes `default | service | stdio` — [packages/cli/src/server-process.ts](https://github.com/sst/opencode/blob/910c423/packages/cli/src/server-process.ts)
- Web UI is "available by default and password-protected"; `opencode pair` prints a one-time link/QR that signs a browser or the OpenCode app into the same server — [OpenCode Web docs](https://opencode.ai/docs/web)
- Protocol: OpenAPI 3.1 with an SSE `/api/event` stream; the SDK can run the HTTP router in memory — [interfaces-and-extensions.md §1-2](../../agent-harness/notes/interfaces-and-extensions.md)

## Agent Client Protocol (ACP): how editors drive external agents

### Takeaway
ACP is JSON-RPC 2.0 over the agent's stdio, launched as a subprocess by the editor, with a "UX-first" message set: streamed `session/update` notifications (message/thought chunks, tool calls with kinds, statuses and diff/terminal content, plans, modes, usage, compaction), a `session/request_permission` client request with four option kinds, and client-provided `fs/*` and `terminal/*` methods. Stable protocol version is 1 (repo v1.19.0); v2 is a draft that drops client fs/terminal APIs and adds subagent child sessions. Zed, JetBrains, Neovim, Emacs, many VS Code extensions and Obsidian are clients; Claude (via Zed's adapter), Codex (via `codex-acp`), Gemini CLI, OpenCode, Copilot CLI, Cursor, Junie, Cline and Pi (via adapter) are agents.

### Cited Findings
- Repo moved to the `agentclientprotocol` GitHub org; "The current stable ACP protocol version is `1`"; wire compatibility comes from `protocolVersion` in `initialize`, not crate/schema release versions — [README.md](https://github.com/agentclientprotocol/agent-client-protocol/blob/v1.19.0/README.md)
- Architecture: "the editor boots the agent sub-process on demand, and all communication happens over stdin/stdout. Each connection can support several concurrent sessions"; design principles "MCP-friendly" (reuses MCP types), "UX-first", "Trusted"; the editor passes its MCP server config to the agent and can proxy its own MCP tools back to itself — [docs/get-started/architecture.mdx](https://github.com/agentclientprotocol/agent-client-protocol/blob/v1.19.0/docs/get-started/architecture.mdx)
- v1 methods. Agent side: `initialize`, `authenticate`, `session/new`, `session/load`, `session/set_mode`, `session/set_config_option`, `session/prompt`, `session/cancel`, `session/list`, `session/delete`, `session/resume`, `session/close`, `logout`. Client side: `session/request_permission`, `session/update`, `fs/read_text_file`, `fs/write_text_file`, `terminal/create|output|release|wait_for_exit|kill`, `elicitation/create|complete`. Protocol: `$/cancel_request`. The unstable schema adds `providers/*` and `mcp/message` — [schema/v1/meta.json](https://github.com/agentclientprotocol/agent-client-protocol/blob/v1.19.0/schema/v1/meta.json); `meta.unstable.json`
- `SessionUpdate` variants (v1 schema): `user_message_chunk`, `agent_message_chunk`, `agent_thought_chunk`, `tool_call`, `tool_call_update`, `plan`, `available_commands_update`, `current_mode_update`, `config_option_update`, `session_info_update`, `usage_update`, `notice`, `compaction_update`, `compaction_summary_chunk` — [schema/v1/schema.json](https://github.com/agentclientprotocol/agent-client-protocol/blob/v1.19.0/schema/v1/schema.json)
- Tool calls: kinds `read`, `edit`, `delete`, `move`, `search`, `execute`, `think`, `fetch`, `switch_mode`, `other`; status `pending → in_progress → completed | failed`; content `content`, `diff`, `terminal`; updated via `tool_call_update` — [docs/protocol/v1/tool-calls.mdx](https://github.com/agentclientprotocol/agent-client-protocol/blob/v1.19.0/docs/protocol/v1/tool-calls.mdx); schema.json
- Permissions: the agent "MAY request permission from the user before executing a tool call by calling the `session/request_permission` method"; option kinds `allow_once`, `allow_always`, `reject_once`, `reject_always` — [tool-calls.mdx](https://github.com/agentclientprotocol/agent-client-protocol/blob/v1.19.0/docs/protocol/v1/tool-calls.mdx); schema.json
- Plans: `plan` update with entries whose status is `pending | in_progress | completed` and priority `high | medium | low` — [schema.json](https://github.com/agentclientprotocol/agent-client-protocol/blob/v1.19.0/schema/v1/schema.json); [docs/protocol/v1/agent-plan.mdx](https://github.com/agentclientprotocol/agent-client-protocol/blob/v1.19.0/docs/protocol/v1/agent-plan.mdx)
- v2 (draft): "a consolidation release. It redesigns the prompt lifecycle, unifies streaming and non-streaming updates… removes Client APIs that few implementations used"; "The Client file system, terminal execution, and session modes APIs are gone… Use client-provided MCP servers when the Agent needs Client-side tools"; "v2 as a whole is still labeled draft"; request IDs cannot be `null` and batches are not used — [docs/protocol/v2/migration.mdx](https://github.com/agentclientprotocol/agent-client-protocol/blob/v1.19.0/docs/protocol/v2/migration.mdx)
- v2 subagents: a child session with its own `sessionId` announced by `subagent_update`, which "Every Client MUST" handle; children's updates arrive as ordinary `session/update` — [docs/protocol/v2/subagents.mdx](https://github.com/agentclientprotocol/agent-client-protocol/blob/v1.19.0/docs/protocol/v2/subagents.mdx)
- Agents listed include Claude Agent "(via Zed's SDK adapter)", Codex CLI "(via ACP's adapter)", Cline, Cursor, Gemini CLI, GitHub Copilot ("in public preview"), Goose, Junie by JetBrains, Kiro CLI, Mistral Vibe, OpenCode, OpenHands, Pi "(via pi-acp adapter)", Qwen Code and many more — [docs/get-started/agents.mdx](https://github.com/agentclientprotocol/agent-client-protocol/blob/v1.19.0/docs/get-started/agents.mdx)
- Clients listed include Zed, JetBrains, Neovim (CodeCompanion, avante.nvim, agentic.nvim), Emacs (agent-shell.el), Qt Creator, Sublime Text, several VS Code extensions (e.g. "native Diff Editor approvals"), Obsidian plugins, and TUI clients such as a "Rust/ratatui terminal client" (Martty) — [docs/get-started/clients.mdx](https://github.com/agentclientprotocol/agent-client-protocol/blob/v1.19.0/docs/get-started/clients.mdx)
- Zed: "Zed hosts the thread in the Agent Panel and Threads Sidebar, while the External Agent usually owns its own runtime, auth, model selection, tools, and native configuration"; agents install from the ACP Registry; "Zed MCP servers May be forwarded over ACP"; "Tool permissions: Zed ACP/tool forwarding permissions may apply; native tool permissions depend on the agent" — [Zed External Agents](https://zed.dev/docs/ai/external-agents)

### Inferences
- ACP's message set is essentially a rendering contract for an agent transcript: chunks, tool-call cards with kind icons and status, diff and terminal content blocks, plan checklists and permission option buttons. A harness that emits these natively can be hosted by dozens of editors for free.
- v2 moves tool execution back into the agent (no client fs/terminal), keeping the editor as a renderer and approver; this matches the Codex/OpenCode server-owns-execution model.

### Gaps
- agentclientprotocol.com pages were not fetched; facts come from the docs source in the repo, which renders that site.

## Patterns across products

### Takeaway
Every product separates a protocol-speaking agent core from its renderers, and the UI converges on the same primitives: a transcript of streamed message chunks plus collapsible tool-call cards, inline or side-by-side diffs, approval prompts with once/always/reject options plus "tell the agent what to do instead", a plan or todo checklist, subagent rows or panes, and resumable sessions. The main split in terminal UIs is native scrollback (Codex, Pi regular, Claude classic, Gemini default) versus alternate-screen virtualized viewports (Claude fullscreen, Pi default, Gemini opt-in).

### Cited Findings
- Renderer split: Codex inline viewport + scrollback ([tui.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/src/tui.rs)); Claude classic vs fullscreen ([Fullscreen rendering](https://code.claude.com/docs/en/fullscreen.md)); Pi `TuiMainScreen` vs `TuiAltScreen`, fullscreen default ([pi-tui README](https://github.com/earendil-works/pi/blob/v1.5.2/packages/tui/README.md); [cli.md](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/cli.md)); Gemini `ui.useAlternateBuffer` default false ([settings.md](https://github.com/google-gemini/gemini-cli/blob/v0.68.0/docs/cli/settings.md))
- Synchronized output (CSI 2026) is used by Pi ([pi-tui README](https://github.com/earendil-works/pi/blob/v1.5.2/packages/tui/README.md)) and appears in the Claude binary (inferred, see Claude section)
- UI frameworks: React+Ink (Claude, inferred; Gemini, fork `@jrichman/ink`), ratatui (Codex), custom line-diff library (Pi), OpenTUI + Solid (OpenCode) or OpenTUI + React (Cline CLI) — sources in the sections above
- Approval option vocabularies: ACP `allow_once/allow_always/reject_once/reject_always` ([schema](https://github.com/agentclientprotocol/agent-client-protocol/blob/v1.19.0/schema/v1/schema.json)); OpenCode `once/always/reject` ([permission.tsx](https://github.com/sst/opencode/blob/910c423/packages/tui/src/routes/session/permission.tsx)); Codex "Yes, just this once … No, and tell Codex what to do differently" ([approval_overlay.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/src/bottom_pane/approval_overlay.rs)); Gemini "Allow once / for this session / all future sessions / Modify with external editor / No, suggest changes" ([components](https://github.com/google-gemini/gemini-cli/tree/v0.68.0/packages/cli/src/ui/components)); Claude VS Code "accept, reject, or tell Claude what to do instead" ([VS Code](https://code.claude.com/docs/en/vs-code.md))
- Diff previews: Codex syntax-highlighted unified diffs in terminal ([diff_render.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/src/diff_render.rs)); OpenCode `PatchDiff` in the permission prompt; Claude `/diff` side pane mod ([mods/README.md](https://github.com/anthropics/claude-code/blob/v2.1.327/mods/README.md)); editor-native diff via Gemini `openDiff` ([companion spec](https://github.com/google-gemini/gemini-cli/blob/v0.68.0/docs/ide-integration/ide-companion-spec.md)), Claude VS Code per-change accept/reject, ACP `diff` tool-call content, VS Code `ChatResponseMultiDiffPart` and AHP changesets
- Plans/todos: ACP `plan` entries; Codex `Plan` thread item and plan stream controller ([item.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-protocol/src/protocol/v2/item.rs); [controller.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/src/streaming/controller.rs)); Claude VS Code plan as Markdown document with inline comments; Gemini `ExitPlanModeDialog`; Cline `PLAN_MODE_RESPOND`
- Subagents/background: Codex `/subagents` picker and `SubAgentActivity` items; ACP v2 child sessions; Claude agent view / background sessions ([Fullscreen rendering](https://code.claude.com/docs/en/fullscreen.md) links agent-view); VS Code AHP multi-chat with forks and side chats ([agentHost/AGENTS.md](https://github.com/microsoft/vscode/blob/1d20abc/src/vs/platform/agentHost/AGENTS.md)); OpenCode `opencode/child-session-updates` ACP extension
- Session resume: Codex `thread/resume`, resume picker with transcript preview (`resume_picker_transcript_preview.rs` in [tui/src](https://github.com/openai/codex/tree/rust-v0.170.0/codex-rs/tui/src)); ACP `session/load` and `session/resume`; Claude `--resume` preview; OpenCode fork/timeline dialogs
- Headless JSONL output exists in all CLIs: Claude `stream-json`, Codex `exec --json`, Gemini `stream-json`, Pi `--mode json` — sources above

### Inferences
- For our harness: emit an event stream whose vocabulary maps one-to-one onto ACP `session/update` (chunks, tool_call with kind/status/diff content, plan) and treat approvals as server requests with once/always/reject plus a free-text "do this instead" reply; then an ACP adapter, a TUI and an IDE webview are all thin renderers.
- Pick native scrollback for the first TUI (simpler, accessible, works with screen readers and terminal search) and keep the mutable "live tail" small, as Codex does; add an alternate-screen virtualized mode later only if long-session memory or flicker becomes a problem, as Claude Code and Pi did.
- Keep diff rendering and approval UI as removable renderer components, not core logic, so editor frontends can replace them with native diff editors.

### Gaps
- No product publishes measurements of rendering cost (bytes written per frame, memory per transcript length) beyond qualitative docs claims.
- Accessibility behaviour (screen readers) was only touched on for Claude Code (classic renderer forced) and Codex (`screen_reader.rs` exists in tui/src but was not read).
