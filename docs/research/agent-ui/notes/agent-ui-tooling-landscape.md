# The landscape around Vercel Labs' UI SDK: headless behavior libraries and agent-facing UI tooling (as of November 2026)

Scope: what surrounds UI SDK (ui-sdk.dev, github.com/vercel-labs/ui), not UI SDK itself. All versions and dates are from the npm registry (`registry.npmjs.org/<pkg>`, fetched 2026-11-18) unless another source is cited. Prior repo research already covers AG-UI, A2UI's protocol details, CopilotKit's hooks and AI SDK UI; see `docs/research/agent-ui/notes/ui-protocols.md` and `web-ui-frameworks.md`. These notes do not repeat that material.

UI SDK itself, for orientation only: `@ui-sdk/core` 0.1.0-beta.10 (published 2026-11-18, first published 2026-11-12, Apache-2.0, repo vercel-labs/ui) — [npm @ui-sdk/core](https://registry.npmjs.org/@ui-sdk/core). Its llms.txt calls it "the layer underneath a UI library: how interfaces behave, written once in a framework-free TypeScript core", rendered in React, Vue, Svelte, Solid and web components, and has an "Agents" section covering "the agent bridge, WebMCP and our skills" — [ui-sdk.dev/llms.txt](https://ui-sdk.dev/llms.txt).

## (a) Headless behavior and primitive libraries: how they split behavior from rendering, versions, frameworks, licences, and agent marketing

### Takeaway
There are three ways to split behavior from rendering. Hooks or state machines return prop-getters that you spread onto your own markup: React Aria hooks, Zag.js, Melt UI builders, TanStack. Unstyled compound components own the DOM structure but no styles: Radix, Base UI, Headless UI, Ark UI, Bits UI, React Aria Components. UI SDK's framework-free "behaviors" belong to the first family. Only Zag.js already shares one behavior core across React, Vue, Solid and Svelte, and none of the incumbents ships Web Components as a first-class target. Agent marketing has become the norm among the larger libraries: React Aria/Spectrum and Ark UI ship MCP servers, React Aria ships Agent Skills, and Ark, Zag, Base UI and TanStack publish llms.txt. Radix, Headless UI and Melt UI show no agent-specific tooling in their primary sources.

### Inferences
- UI SDK's distinguishing claim is not headlessness. It is one framework-free core rendered in five targets, including Web Components, combined with agent-first docs (an agent bridge and WebMCP). Zag.js is the incumbent that comes closest: a shared core, four frameworks plus vanilla, and a mature 1.x line at 1.48. Ark UI already wraps Zag with an MCP server.
- Agent-facing docs have become table stakes (llms.txt, per-page markdown, an MCP server, Agent Skills). UI SDK competes on how good those materials are, not on having them.
- The prop-getter family (Zag, React Aria hooks, Melt, TanStack) suits agents that write markup, because the agent controls the elements while the library supplies the ARIA and keyboard wiring. The compound-component family hides more structure, so a coding agent has less to get wrong but also less control.

## (b) Agent-facing UI tooling: registries, app generators, generative-UI renderers, LLM docs and design-system MCP

### Takeaway
The tooling splits along the two uses. For coding agents there are distribution and context channels: the shadcn CLI, registry, MCP server and skill; the v0 API and MCP; library MCP servers; llms.txt; and Figma's MCP server. For runtime generative UI there are catalog renderers that constrain what a model can emit: json-render, A2UI, OpenUI Lang (the successor to Thesys C1) and CopilotKit's declarative tier. These sit alongside sandboxed open-ended HTML (CopilotKit Open Generative UI, MCP Apps) and streaming-text renderers (Streamdown). AI Elements has moved from the vercel/ai-elements repo into shadcn/ui as copy-in "patterns", so Vercel's chat UI components now live in the shadcn registry.

### Inferences
- Vercel now has a layered stack. UI SDK supplies behaviors, shadcn/ui supplies styled components and AI Elements patterns through a registry, json-render supplies a runtime catalog, Streamdown renders streaming text and v0 is the hosted agent. UI SDK sits below shadcn's current base options (Base UI, Radix, React Aria), and whether shadcn will add it as a fourth base is an open question.
- Runtime generative-UI frameworks are converging on one pattern: a developer-owned catalog with zod or schema props, a prompt generated from that catalog, and a streaming parser. json-render, OpenUI Lang and A2UI differ mainly in wire format (JSON patches, a compact DSL, adjacency-list JSON) and in renderer reach.

## Coding agents that write UI code vs runtime generative UI: where each tool fits, evidence on behaviors vs finished components vs raw HTML, and security and accessibility trade-offs

### Takeaway
I found no public benchmark that compares agents composing headless behaviors against agents using finished components or raw HTML. The closest evidence is indirect. Agentic accessibility benchmarks show that context injected at generation time (instructions, skills) raises pass rates sharply, which is the mechanism library MCP servers and skills use. Public UI arenas rank models by human preference for visual and functional output, not by library choice or accessibility. For runtime generative UI, the primary sources agree that the trust/expressiveness trade-off is the main design decision. Catalogs (json-render, A2UI, OpenUI) keep the agent's output inside developer-built, accessible components. Open-ended HTML has to be sandboxed and gives up accessibility guarantees.

### Cited Findings
- WebDev Arena: "Users submit a prompt, two LLMs generate web apps, and the community votes on which model performs better" (published 10 Mar 2025, updated 13 Jun 2025). It measures pairwise human preference over whole apps — [Arena blog: WebDev Arena](https://arena.ai/blog/webdev-arena). Current leaderboard figures came only from a search summary **[secondary, unverified]**: about 1.03M votes and 161 models as of 2026-11-18, with Claude Fable 5.2 (xHigh) first — [WebDev Arena leaderboard](https://arena.ai/leaderboard/code/webdev)
- Design Arena calls itself "The largest crowdsourced benchmark for AI-generated design". It has separate leaderboards for Website (HTML, Non-Agentic), Website (Frontend, Agentic), UI Component, Image to Frontend and others — [designarena.ai](https://www.designarena.ai/). Specific standings came from search snippets and conflicted between sources, so they are not recorded here **[secondary, conflicting]**.
- DesignBench (arXiv 2506.06251) is a front-end benchmark covering React, Vue, Angular and vanilla HTML/CSS. It is not accessibility-focused and was seen only in a search result **[secondary; abstract not fetched]** — [arXiv 2506.06251](https://arxiv.org/abs/2506.06251)
- Arena also published "Interaction-as-a-Judge", which uses computer-use agents to evaluate generated apps; the related-articles teaser reports gains from 55.4% to 75.5% in inference-time scaling — [Arena blog page (related articles)](https://arena.ai/blog/webdev-arena)
- Security, runtime side: json-render is "Guardrailed - AI can only use components in your catalog" — [json-render README](https://raw.githubusercontent.com/vercel-labs/json-render/main/README.md). For A2UI, "No untrusted code is executed on the client" — [a2ui.org/llms.txt](https://a2ui.org/llms.txt). CopilotKit describes the open-ended tier as "hardest to guarantee accessibility / brand / security" — [CopilotKit overview](https://docs.copilotkit.ai/concepts/generative-ui-overview.md). Streamdown hardens rendered markdown with `rehype-harden` — [Streamdown README](https://raw.githubusercontent.com/vercel/streamdown/main/packages/streamdown/README.md)
- Security, coding-agent side: the shadcn MCP server installs third-party registry code into a project, and registries can require authentication — [shadcn MCP](https://ui.shadcn.com/docs/mcp.md), [shadcn llms.txt (registry authentication page)](https://ui.shadcn.com/llms.txt). The v0 API runs generated apps in "secure live previews … without exposing credentials to the browser" — [v0 API v2](https://v0.app/docs/api/v2.md)
- Accessibility, by design: Zag's machines "handle keyboard interactions, focus management, and ARIA attributes" per WAI-ARIA APG — [Zag README](https://raw.githubusercontent.com/chakra-ui/zag/main/README.md). Ark claims components "tested with real assistive technologies" — [Ark README](https://raw.githubusercontent.com/chakra-ui/ark/main/README.md). These are vendor claims, not independent audits.
- PACE (ASSETS '26) argues that failures in "reusable UI components within design systems and component libraries" can "propagate across many applications" — [PACE paper](https://faculty.washington.edu/wobbrock/pubs/assets-26.04.pdf)

### Inferences
- Coding agents: behavior libraries (UI SDK, Zag, React Aria hooks) give the agent correct ARIA, focus and keyboard handling while it writes the markup and styles. That is attractive because the evidence below shows ARIA is where models fail most. Finished components (shadcn, Ark styled, Spectrum) reduce what the agent writes further. Raw HTML is the worst case on accessibility. This ranking is reasoned from the accessibility studies, not measured.
- Runtime generative UI: a behavior library is not itself a runtime catalog, but it can be the accessible implementation layer underneath catalog components (json-render, A2UI, OpenUI). It does not fit the open-ended sandboxed-HTML tier unless the agent is allowed to load the library inside the sandbox. UI SDK's "agent bridge"/WebMCP angle is a third use, agents operating a rendered page, and another researcher covers it.

### Gaps
- No benchmark found comparing an agent using a component or behavior library against raw HTML on accessibility or task success. The search returned none; PACE and A11y LLM Eval vary prompts and instructions, not libraries.
- I could not get current WebDev Arena or Design Arena standings from a primary page fetch (both pages are client-rendered).
- I found no study of accessibility in runtime-generated (catalog-rendered) UI specifically.

## Accessibility evidence: studies and audits of accessibility in AI-generated UI code

### Takeaway
The evidence is consistent. LLMs and agents produce inaccessible UI by default, and they struggle most with ARIA and complex widgets. Accessibility guidance at generation time helps a lot: instructions, skills, feedback loops or RL alignment. Automated checks cover only part of WCAG, so manual testing is still needed.

### Cited Findings
- **A11y LLM Eval (Microsoft, open source):** every generation is "an agentic Copilot session" (GitHub Copilot SDK) in Docker, rendered with Playwright and checked with axe-core plus per-test assertions. A test passes only with "zero axe-core WCAG failures" and all requirement assertions passing, and the suite reports pass@k — [a11y-llm-eval README](https://raw.githubusercontent.com/microsoft/a11y-llm-eval/main/README.md)
- The latest report (blog post by the project's author, 2026-05-21 **[project-author blog, not peer-reviewed]**) covers 8 models × 32 prompt cases (1,280 control samples). The average control pass rate is "12%", with GPT-5.4 Mini leading at 25%. The "Basic instruction set lifts pass rates by +48.5pp to 60%". The two-turn "Building Accessible UI" skill reaches "86% pass rate (+74.6pp)", with the review turn costing "about 5.5× the input tokens of control". The hardest case (Shopping Home Page, React, dark theme) had a 0% pass rate with 15.55 average WCAG failures, and "Component density compounds the problem fast". The author cautions that 100% here "means the sample passed every check that was run, not that the page is WCAG conformant" — [dev.to: AI-generated accessibility, an update](https://dev.to/mfairchild365/ai-generated-accessibility-an-update-frontier-models-still-fail-but-skills-change-the-game-5629)
- **PACE** (Ma, Wobbrock, Gustafson, Fairchild, Devon, Mankoff, Potluri; ASSETS '26, Oct 2026, CC BY 4.0) is "a benchmarking testbed for controlled evaluation of accessibility in LLM-generated HTML form components". It covers 58 form components × 5 models × 3 system prompts × 3 request variants × 10 trials, n = 26,100 outputs. It finds "accessibility in LLM-generated code moved with prompt construction and with the circumstance around it (e.g., model, form component, and measure used". It cites the 2026 WebAIM Million's "1.1 percentage-point increase in pages with detectable accessibility failures" — [PACE paper](https://faculty.washington.edu/wobbrock/pubs/assets-26.04.pdf)
- **A11yn** (arXiv 2510.13914, Oct 2025): LLM-generated web UIs "frequently violate" WCAG. Using WCAG audits as an RL reward reduced "the inaccessibility rate by 87.5% and 58.1% under two independent WCAG auditors". The work releases the UIReq-6.8K dataset and the RealUIReq-300 benchmark — [arXiv 2510.13914](https://arxiv.org/abs/2510.13914)
- **Human or LLM?** (arXiv 2503.15885, Mar 2025): GPT-4o and Qwen2.5-Coder "often produce more accessible code" than human-written code on basics such as contrast and alt text, "but struggle with complex issues such as ARIA attributes". Prompting strategies give limited gains, while the feedback-driven FeedA11y (ReAct) "significantly outperforms" them — [arXiv 2503.15885](https://arxiv.org/abs/2503.15885)
- **CodeA11y** (arXiv 2502.10884, Feb 2025): a formative study with 16 developers found "failure to prompt AI for accessibility, omitting crucial manual steps like replacing placeholder attributes, and the inability to verify compliance". It cites "~96% of web pages that contain accessibility violations" — [arXiv 2502.10884](https://arxiv.org/abs/2502.10884)
- **From Code to Compliance** (arXiv 2501.03572) found that GPT-4o's default code often lacks compliance, and that structured feedback and visual aids improve it. This was seen only in a search summary **[secondary; abstract fetched but not read]** — [arXiv 2501.03572](https://arxiv.org/abs/2501.03572)
- **Aljedaani et al. 2024, "Does ChatGPT Generate Accessible Code?"**: a third-party summary reports 84% of ChatGPT-generated sites with violations across 88 developers **[secondary, unverified]**. The search tool's arXiv id (2412.08905) is wrong: it resolves to the Phi-4 Technical Report — [arXiv 2412.08905 (Phi-4, not the a11y paper)](https://export.arxiv.org/abs/2412.08905). PACE also summarises ChatGPT sites as having "missing form labels, absent alternative text, vague link descriptions, and poor contrast" — [PACE paper](https://faculty.washington.edu/wobbrock/pubs/assets-26.04.pdf)
- **LLM-Driven Accessible Interface** (arXiv 2601.06616, Jan 2026): LLMs refine "baseline accessible UI templates that conform to WCAG 2.2 and EN 301 549". This is an architectural precedent for "accessible base plus LLM adaptation" — [arXiv 2601.06616](https://arxiv.org/abs/2601.06616)

### Inferences
- The repeated finding that models "struggle … with ARIA attributes" and complex widgets (Human or LLM?, PACE's literature review) is the strongest argument that delegating ARIA, focus and keyboard behavior to a tested library (UI SDK, Zag, React Aria) should help. No study tests that directly.
- The A11y LLM Eval result (skills: 12% → 86%) suggests that library-shipped skills and MCP servers (React Aria, shadcn, Ark, A2UI, UI SDK) are a credible mechanism for improving agent output, at a token cost.

### Gaps
- No independent audit of the accessibility of any headless library's components (Radix, Base UI, Zag, React Aria, UI SDK) was found; the only claims are the vendors' own.
- I did not read PACE's per-model results tables (only the abstract and introduction).
