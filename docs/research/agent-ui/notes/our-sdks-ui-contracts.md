## What does a UI subscribe to, in what shape, and is it typed?

### Takeaway
Every SDK hands a UI a typed, discriminated event union, but at three different altitudes. Claude, Copilot and Pi emit a *runtime/session log* (dozens of event kinds, many unrelated to chat). OpenAI and ADK emit *run items/events* that a UI must fold into messages itself. Vercel AI SDK, and the two SDKs that reuse it (Cloudflare, and OpenAI via an adapter), emit a *UI-ready* chunk protocol (`UIMessageChunk`) that folds into a typed `UIMessage.parts[]` model. LangGraph sits between: graph-level `streamMode`s plus, newly, a typed "agent streaming protocol" (`@langchain/protocol`).

### Inferences
- Only Vercel's `UIMessage.parts` (shared by Cloudflare and reachable from OpenAI via the adapter) is a model designed *for rendering*: tool calls and their approval/result live on one part with one state field. Every other SDK makes the UI join a call event with a later result event by id (Claude `tool_use`/`tool_result` ids, Pi `toolCallId`, OpenAI `RunItem` call ids, ADK functionCall/functionResponse ids, Copilot `toolCallId`). LangGraph's `useStream.toolCalls` does that join client-side.
- Claude and Copilot event unions are huge because they expose a whole product runtime (hooks, tasks, MCP, plugins, rate limits); a UI must whitelist the kinds it renders and ignore the rest.

## How is a pending approval represented, rendered, answered, and does it survive a disconnect/reload?

### Takeaway
Three models: (1) **callback** — the SDK awaits a host function (Claude `canUseTool`, Copilot `onPermissionRequest`, Pi extension `ctx.ui.confirm`); the pending approval is an in-memory promise unless the host deliberately defers it. (2) **paused run state** — the run ends with interruptions that are serialised and resumed (OpenAI `RunState`, LangGraph `interrupt`+`Command`, ADK confirmation events in the session). (3) **message part state** — the approval *is* a part in the transcript (`approval-requested`) answered by a client call (Vercel `addToolApprovalResponse`, Cloudflare `cf_agent_tool_approval`). Models 2 and 3 survive reloads by construction if the store is durable; model 1 survives only in Copilot (`continuePendingWork`) and Claude's hosted bridge.

### Cited Findings
- **Claude.** `CanUseTool(toolName, input, { signal, suggestions?, blockedPath?, mcpServer?, decisionReason?, title?, displayName?, description?, … })` → `PermissionResult { behavior: 'allow', updatedInput?, updatedPermissions? } | { behavior: 'deny', message, interrupt? }` — `sdk.d.ts:244-300, 2719-2731`. `title`/`displayName`/`description` are UI-ready prompt strings ("Full permission prompt sentence rendered by the bridge … Use this as the primary prompt text") and flags `default_to_no`, `suppress_always_allow_rule` tell the UI how to render the buttons — `sdk.d.ts:270-300`, `sdk.d.ts:5253-5290`. Over the stdio control protocol this is a `control_request` with `subtype: 'can_use_tool'` — `sdk.d.ts:5253`. `AskUserQuestion` (clarifying questions) also routes through `canUseTool` — `docs/reference/claude-agent-sdk/guide.md:139`; [user-input.md](https://code.claude.com/docs/en/agent-sdk/user-input.md) sections "Handle tool approval requests", "Handle clarifying questions". Auto-denials surface as `system/permission_denied` — `sdk.d.ts:6066`. Session state flips to `requires_action` while waiting — `sdk.d.ts:6505`. Survival: in the local SDK the pending ask is a JS promise in the host (inference); in the hosted bridge, `resume_reason` documents a turn that "goes on from the answer to the permission prompt the new worker took over", and `sendControlCancelRequest` dismisses a prompt on claude.ai — `sdk.d.ts:3889-3910` (`resume_reason` doc), `bridge.d.ts:55-62`.
- **Pi.** No permission system: "Only an extension's `tool_call` handler can approve or block a call" — `docs/reference/pi/guide.md:90`. The handler can call `ctx.ui.confirm/select/input` — `pi-coding-agent/dist/core/extensions/types.d.ts:85-87`. Survival: tied to the live process (inference; nothing persists the pending dialog).
- **OpenAI.** Stream emits `run_item_stream_event` `tool_approval_requested`; the run stops with `result.interruptions: RunToolApprovalItem[]` — `agents-core/dist/result.d.ts:61-63, 148-150`. Survival: the approval lives in the messages array, so it survives a reload iff the app persists messages (inference from the stateless request model).

- **ADK.** `FunctionTool({ requireConfirmation })` pauses before the body runs and emits a long-running `adk_request_confirmation` function call (id in `event.longRunningToolIds`, details in `actions.requestedToolConfirmations: {[id]: ToolConfirmation{hint, confirmed, payload?}}`); the UI answers with a function response carrying `confirmed`; "The pause is stored as session events, so the answer can arrive in a later request"; unknown call ids run nothing [verified: 07] — `docs/reference/google-adk/guide.md:120-140`; `dist/types/tools/tool_confirmation.d.ts`; `event_actions.d.ts`. `IntentMismatchReason` (`unknown_original_call`, `arguments_mismatch`, …) validates responses — `tool_confirmation.d.ts`.

### Inferences
- For a web UI that must survive reload, the part-state model (Vercel/Cloudflare) is the least work: the transcript itself shows the pending prompt. Paused-state models (OpenAI, LangGraph, ADK) are equally durable but require the UI to read the interruption from a store and map its answer to a resume call. Callback models need the host to turn the callback into a durable record (Copilot's `no-result` pattern is the SDK-blessed version of that).
- Copilot's resume caveat means a reconnecting UI must re-read pending permissions itself (e.g. from persisted `permission.requested` events without a matching `permission.completed`), not wait for a re-emit.

### Gaps
- Whether Claude's local `query()` can defer a `canUseTool` answer across a process restart was not found in types or docs.
- No pending-permission list RPC was found for Copilot (only `listPendingRequests` for external tools, `generated/rpc.d.ts:45051`); how a UI enumerates pending permissions after resume is unconfirmed.

## Can a client reconnect to an in-flight stream?

### Takeaway
Built-in reconnect exists in Cloudflare (WebSocket resume handshake with SQLite-buffered chunks, zero config), Vercel (`resumeStream`/`reconnectToStream` with a pluggable store, e.g. Redis via `resumable-stream`), LangGraph's client stack (`joinStream(runId, lastEventId)`, `reconnectOnMount`, protocol `subscription.reconnect`) when a server implements it, and Claude's hosted bridge/browser SDK (SSE sequence numbers). OpenAI, Pi, ADK and Copilot have no in-flight stream resume; they offer resume-from-persisted-state after the fact.

### Cited Findings
- **Cloudflare.** Handshake: client sends `cf_agent_stream_resume_request {probeId?}` after its handler registers; server replies `cf_agent_stream_resuming` (or `_resume_none` with reason `idle`/`continuation-owned`, or `_pending` while the turn is queued); client sends `cf_agent_stream_resume_ack {id}`; server replays buffered chunks with `replay: true` then `replayComplete`, then live chunks; chunks carry `seq` and the client skips replayed continuation chunks at or below its high-water mark — `wire-types-Cv0iwjk5.d.ts:11-31, 60-80`; [resumable-streaming.md](https://github.com/cloudflare/agents/blob/agents@0.33.0/docs/agents/resumable-streaming.md) lines 5-90. Chunks are flushed to SQLite every 10; stale streams (>5 min) cleaned on restore; client abort is local-only by default, explicit `stop()` cancels — same page. Separately, Durable Object eviction recovery runs turns in a "recoverable fiber" and signals `cf_agent_chat_recovering` — same page line 5; `wire-types-Cv0iwjk5.d.ts:84-91`.
- **Vercel.** `ChatTransport.reconnectToStream({ chatId }) → ReadableStream<UIMessageChunk> | null`, `resumeStreamIsReplay` flag, `Chat.resumeStream()` — `ai/dist/index.d.ts:6181-6262, 6478, 6607-6620`. With `useChat({ resume: true })` the hook GETs `/api/chat/[id]/stream` on mount; the server uses `consumeSseStream` + `resumable-stream` + Redis and returns 204 if nothing is active; "client-side aborts are treated as disconnects" and stopping needs a dedicated endpoint — [chatbot-resume-streams.mdx](https://raw.githubusercontent.com/vercel/ai/2feaeecbd6a921a27123aafa75db6af34e1f246b/content/docs/04-ai-sdk-ui/03-chatbot-resume-streams.mdx) lines 8-20, 34-43, 91, 239-247. `WebSocketChatTransport.resumeStreamIsReplay = true` — `index.d.ts:6843`.
- **LangGraph.** `useStream({ reconnectOnMount })` and `joinStream(runId, lastEventId?)` — `langgraph-sdk/dist/ui/types.d.ts:856`, `react/types.d.ts:65`, `ui/orchestrator.d.ts:302`. Protocol: events carry `event_id` ("Unique ID for reconnection (maps to SSE id:)") and `seq`; `subscription.reconnect { run_id, last_event_id?, subscriptions? }` — `@langchain/protocol/protocol.ts:324-334, 529-543`. These need a server that buffers runs (LangGraph Platform/Agent Server, or a custom implementation); the OSS `graph.stream()` itself has no replay (inference).
- **Claude.** Local `query()` is a subprocess stream; resume is by session (`resume`, `resumeSessionAt`, `forkSession`, `getSessionMessages`) — `sdk.d.ts:905, 975, 2262-2275`. Hosted: `BridgeSessionHandle.getSequenceNum()` — "Persist this and pass back as `initialSequenceNum` on re-attach so the server resumes instead of replaying full history"; `reconnectTransport()` carries undelivered writes — `bridge.d.ts:33-38, 62-75, 115-122`; the browser SDK has `getSseLastSequenceNum`, `suspendSseStream`, `resumeSseStream` — `browser-sdk.d.ts:155-215`. Both are `@alpha`.
- **OpenAI.** No reconnect API on `StreamedRunResult` (`toStream`, `toTextStream`, `completed`, `cancel`-style members only) — `agents-core/dist/result.d.ts:172-230`; resume means `RunState.fromString()` of a paused run (inference: an interrupted, non-paused stream cannot be rejoined).
- **Pi.** RPC is stdin/stdout of a child process; no reconnect in the protocol — `rpc.md:50-95`. Recovery is by session file (JSONL tree, `switch_session`, `get_messages`, `get_tree`) — `rpc-types.d.ts:104-135`; [session-format.md](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/session-format.md) lines 1-60.
- **ADK.** `/run_sse` is a plain POST-SSE response — `api-server.md:223-232`. The "Resume stopped agents" page is tagged Python v1.16.0 and Kotlin only — [runtime/resume.md](https://github.com/google/adk-docs/blob/ff7a5f56469a81f3e43a8fc54668d8dc84300192/docs/runtime/resume.md) line 4 — yet `@google/adk` 2.5.0 has `Runner.resumabilityConfig?: ResumabilityConfig` ("pause an invocation upon a long-running function call … resume an invocation from the last event") — `runner/runner.d.ts:65-67, 129, 279`; `apps/resumability_config.d.ts`. This is invocation resume, not stream rejoin.
- **Copilot.** `resumeSession(id, config)` returns the stopped session; `getEvents()` returns history [verified: 06] — `docs/reference/copilot-sdk/guide.md:59`; ephemeral events (deltas, `session.idle`) are never written, so a late subscriber cannot recover them and should subscribe before create/resume returns — [streaming-events.md](https://github.com/github/copilot-sdk/blob/v1.0.31/docs/features/streaming-events.md) line 217. "Remote sessions" export read-only history to GitHub web/mobile, "not remote control" — [remote-sessions.md](https://github.com/github/copilot-sdk/blob/v1.0.31/docs/features/remote-sessions.md) line 3.

### Inferences
- Rejoin requires a server that owns the run independently of the HTTP/WebSocket connection and buffers its chunks with sequence ids. Cloudflare gets this free from Durable Objects; Vercel and LangGraph give the client half and a store interface; the in-process SDKs leave the whole server half to the host.
- Every rejoin design uses the same trick: monotonically sequenced chunks plus a replay-vs-continue flag (Cloudflare `seq`/`replay`, Vercel `resumeStreamIsReplay`, LangGraph `event_id`/`seq`, Claude bridge sequence numbers).

### Gaps
- Whether `@langchain/langgraph`'s `encoding: "text/event-stream"` output emits `id:` lines usable with `last_event_id` was not checked in source.
- Behavior of Vercel's `WebSocketChatTransport` reconnect against a server was not read beyond types.

## Is there shared state beyond the transcript?

### Takeaway
Only Cloudflare has bidirectional, broadcast, typed agent state as a first-class UI contract (`setState` ↔ `useAgent`). LangGraph exposes the full graph state to the UI (`values` stream, `useStream` state and `mutate`), ADK emits state changes as `stateDelta` on events (which AG-UI's "shared state" builds on), and Vercel offers one-way typed `data-*` parts. Claude, Pi, OpenAI and Copilot expose runtime status (todos, tasks, plan, queue, mode) as events but no app-defined shared state object.

### Cited Findings
- **Cloudflare.** `setState()` "saves to SQLite, broadcasts to connected clients and then calls `onStateChanged()`"; a new WebSocket client first receives current state then every update [verified: 01] — `docs/reference/cloudflare-agents/guide.md:34-52`. Clients may push state (`agent.setState` from `useAgent`, `AgentClient.setState`), servers can veto via `validateStateChange(nextState, source)` — [state.md](https://github.com/cloudflare/agents/blob/agents@0.33.0/docs/agents/state.md) lines 193-312. Readonly connections receive state but cannot set it — [readonly-connections.md](https://github.com/cloudflare/agents/blob/agents@0.33.0/docs/agents/readonly-connections.md) lines 1-12. Frames `cf_agent_state` / `cf_agent_state_error`; `@callable()` methods are RPC over the same socket (`rpc` frame) — `types-6Zo2zfoO.d.ts:5-13`.
- **LangGraph.** `values` mode streams full state after each step [verified: 08] — `docs/reference/langchain/guide.md:111`; `useStream` options include `threadId`, `initialValues`, and an optimistic `mutate(update)` in submit callbacks — `langgraph-sdk/dist/ui/types.d.ts:845-860`; protocol has `state` commands/results and a `values` channel — `@langchain/protocol/protocol.ts:303, 336, 474`. `custom` mode carries tool-written events — `guide.md:111`.
- **ADK.** `EventActions.stateDelta` and `artifactDelta` on every event; `runAsync` also accepts `stateDelta` from the caller — `event_actions.d.ts`; `runner.d.ts:171-179`. The ADK AG-UI page lists "Shared State" and "Generative UI" as features via CopilotKit — `ag-ui.md` headings lines 67-110.
- **Vercel.** `DataUIPart<DATA_TYPES>` (`data-<name>` chunks) typed by `dataPartSchemas`, and `messageMetadataSchema` for per-message metadata — `ai/dist/index.d.ts:2010, 6426`; server→client only (inference: no client→server state channel besides new messages).
- **Claude.** Runtime-state events, not app state: `session_state_changed`, task/todo progress, `commands_changed`, `background_tasks_changed` — `sdk.d.ts:3993-4040, 5866, 6502`.
- **Pi.** `queue_update{steering, followUp}`, `session_info_changed`, `thinking_level_changed`, `entry_appended`; extensions can push `setStatus`, `setWidget`, `setTitle` to the UI — `agent-session.d.ts:49-80`; `rpc-types.d.ts:434-458`.
- **OpenAI.** `RunContext` is local; nothing streams it; `agent_updated_stream_event` signals handoffs — `events.d.ts:41-52`.
- **Copilot.** `session.plan_changed`, `session.todos_changed`, `session.mode_changed`, `workspace_file_changed`, canvases with `CanvasDeclaration` and resume-time canvas rehydration — `session-events.d.ts:12`; `dist/types.d.ts:3050-3056`; `canvas.d.ts`.

### Inferences
- If the planned UI needs a live side panel (plan, todo list, artifacts) driven by the agent, Cloudflare's state sync is the only off-the-shelf bidirectional channel; elsewhere it must be built from custom/data events plus a separate write path.

### Gaps
- AG-UI's state-delta event schema itself was not examined (outside scope; no AG-UI package installed).

## How do the eight compare side by side?

### Takeaway
Vercel's UI message stream is the de-facto common denominator: Cloudflare is built on it and OpenAI ships an official adapter to it. LangChain is converging on its own typed protocol, ADK points to AG-UI via CopilotKit, and Claude/Copilot/Pi expose rich runtime logs that a custom UI must translate.
