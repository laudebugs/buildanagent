# Agent UIs render event logs, not chats

The chat transcript an agent shows is a rendering of a typed event stream, and the field has now agreed on that model (as of November 2026). Every serious agent product and SDK surveyed here does the same three things. It separates a protocol-speaking agent core from its renderers. It streams text, reasoning and tool-call deltas as discriminated events. And it renders tool calls as stateful cards with an approval step. The products differ on three harder questions. The first is whether the approval lives in the transcript, in a paused run, or in a host callback. The second is whether a client can rejoin a stream that is still running. The third is whether there is shared state beyond the message list. Above that common layer sit two kinds of open standard. Runtime protocols carry runs, messages, tool calls, state and interrupts: AG-UI 1.0, the Vercel AI SDK UI message stream, ACP, and Codex's app-server. Payload formats describe what UI to show, either as declarative data the host renders natively (A2UI, ChatKit widgets) or as sandboxed HTML (MCP Apps, which OpenAI's Apps SDK has now adopted as its primary standard). Of the eight SDKs this repository verifies, only Vercel's `UIMessage.parts` is a data model designed for rendering. Cloudflare is built on it, and OpenAI ships an official adapter to it. Claude, Copilot and Pi expose large runtime logs that a UI must filter and translate, while OpenAI, LangGraph and Google ADK expose run items or graph state that a UI must fold into messages itself. Beyond chat, the evidence favours structured surfaces: editable plans, canvases, generated UIs, inboxes and review-centred async task lists. Chat stays useful for underspecified intent and for steering.

## Every agent UI projects one sequenced event log

Each product, whatever its surface, keeps the agent behind a protocol and treats the UI as one client among several. Codex's terminal UI is a client of the app-server JSON-RPC protocol. It embeds the server in-process by default, but it can attach to a shared daemon or a remote `ws://` endpoint, and the same protocol "power[s] rich clients (for example, the Codex VS Code extension)" ([Codex App Server docs](https://developers.openai.com/codex/app-server); [app-server-daemon README](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-daemon/README.md)). OpenCode 2.3.0 goes further. A background server speaks an OpenAPI 3.1 API with an SSE event stream, and the OpenTUI/SolidJS terminal UI, a web UI, an Electron app, mobile pairing and `opencode acp` are all clients of it ([OpenCode client README](https://github.com/sst/opencode/blob/910c423/packages/client/README.md); [OpenCode Web docs](https://opencode.ai/docs/web)). Claude Code's `claude -p --output-format stream-json` is "the Agent SDK via the CLI" ([Claude Code headless docs](https://code.claude.com/docs/en/headless.md)). Its VS Code extension "bundles its own copy of the CLI" for the chat panel ([Claude Code VS Code docs](https://code.claude.com/docs/en/vs-code.md)). The Agent SDK package even ships an alpha `browser-sdk.d.ts`, whose `query()` reads the same `SDKMessage` stream over SSE from a `/v1/code/sessions/{id}/events/stream` URL ([`browser-sdk.d.ts`](../verify/claude-agent-sdk/node_modules/@anthropic-ai/claude-agent-sdk/browser-sdk.d.ts)). VS Code's own Copilot panel "now runs through the Agent Host Protocol" ([extensions/copilot/CONTRIBUTING.md](https://github.com/microsoft/vscode/blob/1d20abc/extensions/copilot/CONTRIBUTING.md)). AHP is "a synchronized, multi-client state protocol for AI agent sessions" built on "immutable state, pure reducers, and write-ahead reconciliation", and VS Code's reference server hosts **Copilot, Claude and Codex harnesses side by side** ([agent-host-protocol README](https://github.com/microsoft/agent-host-protocol); [agentHost/AGENTS.md](https://github.com/microsoft/vscode/blob/1d20abc/src/vs/platform/agentHost/AGENTS.md)).

The vocabulary of those event streams has converged too. ACP, the editor-to-agent protocol at stable version 1 (repo v1.19.0), is effectively a rendering contract. Its `session/update` notifications carry message and thought chunks, tool calls with a `kind` (read, edit, execute, fetch and others), a status that runs `pending → in_progress → completed | failed`, `diff` and `terminal` content, `plan` entries with priorities, mode and usage updates, and compaction. A separate `session/request_permission` request offers the four options `allow_once`, `allow_always`, `reject_once` and `reject_always` ([ACP v1 schema](https://github.com/agentclientprotocol/agent-client-protocol/blob/v1.19.0/schema/v1/schema.json); [ACP tool calls](https://github.com/agentclientprotocol/agent-client-protocol/blob/v1.19.0/docs/protocol/v1/tool-calls.mdx)). Codex's thread items name the same things: `AgentMessage`, `Plan`, `Reasoning`, `CommandExecution`, `FileChange`, `McpToolCall`, `SubAgentActivity` and `ContextCompaction` ([item.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/app-server-protocol/src/protocol/v2/item.rs)). On the web, AG-UI 1.0 freezes **31 event types in eight families**: runs and steps, text messages, tool calls, state snapshots and JSON Patch deltas, reasoning, activity, subagents, and raw/custom passthrough ([ag-ui README](https://raw.githubusercontent.com/ag-ui-protocol/ag-ui/main/README.md)). Vercel's UI message stream encodes nearly the same set as SSE chunks: `text-start/-delta/-end`, `reasoning-*`, `tool-input-start/-delta/-available`, `tool-approval-request`, `tool-output-available/-denied`, step markers and custom `data-*` parts ([AI SDK stream protocol](https://ai-sdk.dev/docs/ai-sdk-ui/stream-protocol)).

ACP's reach shows what a shared rendering contract buys. Zed, JetBrains, Neovim, Emacs, Qt Creator, Sublime Text, Obsidian and several VS Code extensions act as clients. Claude (through Zed's adapter), Codex (through `codex-acp`), Gemini CLI, OpenCode, Copilot CLI, Cursor, Junie, Cline and Pi (through `pi-acp`) act as agents ([ACP agents list](https://github.com/agentclientprotocol/agent-client-protocol/blob/v1.19.0/docs/get-started/agents.mdx); [ACP clients list](https://github.com/agentclientprotocol/agent-client-protocol/blob/v1.19.0/docs/get-started/clients.mdx)). The draft v2 removes the client file-system and terminal APIs and points agents to client-provided MCP servers instead ([ACP v2 migration](https://github.com/agentclientprotocol/agent-client-protocol/blob/v1.19.0/docs/protocol/v2/migration.mdx)). That leaves the editor as a renderer and approver, while the agent owns execution, as it already does in Codex and OpenCode.

### Terminal UIs split on who owns scrollback

Terminal agents use different stacks. Claude Code uses a React renderer derived from Ink; that comes from strings in the shipped binary, since the renderer's source is closed. Gemini CLI uses React 19.2.4 on an Ink fork. Codex uses ratatui 0.30 with crossterm. Pi uses its own line-diff library. OpenCode and the Cline CLI use OpenTUI ([codex-rs/tui/Cargo.toml](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/Cargo.toml); [gemini-cli package.json](https://github.com/google-gemini/gemini-cli/blob/v0.68.0/packages/cli/package.json); [pi-tui README](https://github.com/earendil-works/pi/blob/v1.5.2/packages/tui/README.md)). The design choice that matters more is where finished history lives. Codex "uses the terminal scrollback itself for finalized chat history" and draws only a mutable live tail through ratatui. It holds Markdown tables back in that tail "so adding a row can reflow earlier table rows instead of committing a stale render to scrollback" ([insert_history.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/src/insert_history.rs); [table_holdback.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/src/streaming/table_holdback.rs)). Claude Code went the other way. Its "fullscreen" research-preview renderer draws on the alternate screen and "only renders messages that are currently visible", which removes flicker that is worst in the VS Code terminal, tmux and iTerm2. Screen-reader mode forces the classic renderer ([Claude Code fullscreen rendering](https://code.claude.com/docs/en/fullscreen.md)). Pi ships both renderers and defaults to fullscreen. Gemini keeps `ui.useAlternateBuffer` off by default ([pi cli.md](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/cli.md); [Gemini settings](https://github.com/google-gemini/gemini-cli/blob/v0.68.0/docs/cli/settings.md)). The trade-off is consistent across all four. Native scrollback is simpler, searchable and accessible, but anything already committed to it is immutable. Alternate-screen virtualization fixes flicker and memory in long sessions, at the cost of app-owned scrolling.

The approval vocabularies have converged as well. Codex offers "Yes, just this once", "Yes, and don't ask again for commands that start with …" and "No, and tell Codex what to do differently" ([approval_overlay.rs](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/tui/src/bottom_pane/approval_overlay.rs)). Gemini offers "Allow once / for this session / all future sessions / Modify with external editor / No, suggest changes" ([Gemini UI components](https://github.com/google-gemini/gemini-cli/tree/v0.68.0/packages/cli/src/ui/components)). OpenCode replies `once`, `always` or `reject` beside a `PatchDiff` preview ([permission.tsx](https://github.com/sst/opencode/blob/910c423/packages/tui/src/routes/session/permission.tsx)). Claude's VS Code extension lets users "accept, reject, or tell Claude what to do instead" ([Claude Code VS Code docs](https://code.claude.com/docs/en/vs-code.md)). The shared pattern is **once/always/reject plus a free-text redirect**, and ACP has made it a standard.

Plugin UI in these products is moving toward surface-neutral component trees. Claude Code v2.1.327's public "mods" API lets a plugin answer `ui.render` with a `Box`/`Text`/`Button` element tree. A `Button` renders as "`[ label ]` on the terminal, a native button on a desktop", and the documented surfaces are terminal, desktop, VS Code and mobile ([claude-code.d.ts](https://github.com/anthropics/claude-code/blob/v2.1.327/mods/types/claude-code.d.ts); [mods README](https://github.com/anthropics/claude-code/blob/v2.1.327/mods/README.md)). Pi solves the same problem by degrading gracefully. An extension's `ctx.ui.confirm/select/input` becomes an `extension_ui_request` over RPC; `notify` and `setWidget` are fire-and-forget; and `custom()` returns `undefined` when there is no terminal ([rpc-extension-ui.md](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/rpc-extension-ui.md)). That three-way split of UI calls (blocking dialog, fire-and-forget, terminal-only) is a useful template for any headless frontend.

## Generative UI trades the agent's freedom against safety

Generative UI is not one technique but three, separated by how much of the UI the model controls. At the low end, the app maps a tool result to a pre-built component. Vercel defines generative UI as "connecting the results of a tool call to a React component" ([AI SDK generative UI](https://ai-sdk.dev/docs/ai-sdk-ui/generative-user-interfaces)). In the middle, the model composes a validated declarative spec from a catalogue. At the top, the model or a server ships arbitrary HTML rendered in a sandbox. CopilotKit's own docs name the same three levels "Controlled", "Declarative" and "Open-ended" ([CopilotKit docs](https://docs.copilotkit.ai/langgraph/shared-state)). It ships seven primitives across them: components as tools, tool-call rendering, state rendering, reasoning, A2UI, MCP Apps and "Open Generative UI" sandboxed HTML ([CopilotKit generative UI overview](https://docs.copilotkit.ai/concepts/generative-ui-overview.md)).

**A2UI** (Google, Apache-2.0) is the declarative standard. Spec v1.0 has been marked "Current" since 8 June 2026, and the renderer packages were at 0.15.0 as of November 2026 ([A2UI v1.0 spec](https://a2ui.org/specification/v1.0-a2ui/); [npm @a2ui/react](https://registry.npmjs.org/@a2ui/react)). "A2UI expresses UI using data, not code." The agent streams `createSurface`, `updateComponents`, `updateDataModel` and `deleteSurface` messages. Those messages describe a flat adjacency list of components that reference child ids, so components can arrive in any order and render progressively once a `root` exists. The client renders only from catalogues it declared, with "no fallback" ([A2UI README](https://raw.githubusercontent.com/google/A2UI/main/README.md); [A2UI v1.0 spec](https://a2ui.org/specification/v1.0-a2ui/)). OpenAI's ChatKit widgets work on the same principle. They are JSON trees rooted in a `Card` or `ListView`, with a built-in confirm/cancel `ActionConfig`, whose clicks become action payloads sent back to the server ([ChatKit widgets](https://developers.openai.com/api/docs/guides/chatkit-widgets.md)).

**MCP Apps** (SEP-1865, extension `io.modelcontextprotocol/ui`) is the sandboxed-code standard, and its 2026-01-26 revision is marked Stable ([MCP extensions overview](https://modelcontextprotocol.io/extensions/overview.md); [SEP-1865](https://modelcontextprotocol.io/seps/1865-mcp-apps-interactive-user-interfaces-for-mcp.md)). A tool's `_meta.ui.resourceUri` points to a `ui://` HTML resource. A web host must render it in an iframe behind a cross-origin sandbox proxy, with a CSP built from the declared domains. The View talks to the host in JSON-RPC over `postMessage`, using methods such as `ui/notifications/tool-input-partial` (streamed arguments), `tool-result`, `ui/message`, `ui/update-model-context` and `tools/call` ([MCP Apps spec 2026-01-26](https://raw.githubusercontent.com/modelcontextprotocol/ext-apps/main/specification/2026-01-26/apps.mdx)). It has become the convergence point for iframe UI. Claude, VS Code Copilot, Microsoft 365 Copilot, Goose and ChatGPT host it ([MCP Apps overview](https://modelcontextprotocol.io/extensions/apps/overview.md); [ext-apps README](https://raw.githubusercontent.com/modelcontextprotocol/ext-apps/main/README.md)). The community MCP-UI SDKs now implement it ([mcp-ui README](https://raw.githubusercontent.com/idosal/mcp-ui/main/README.md)). OpenAI's Apps SDK states that "ChatGPT implements the open MCP Apps standard". `window.openai` survives as compatibility aliases plus ChatGPT-only extensions such as checkout, file upload, modals and widget state, and "new UI should use the shared fields" ([OpenAI: Add UI to your MCP server](https://developers.openai.com/apps-sdk/build/chatgpt-ui.md)).

The trade-off is real, and the specs say so. A2UI's security case rests on "disallowing arbitrary executable code" ([A2UI README](https://raw.githubusercontent.com/google/A2UI/main/README.md)). MCP Apps lists malicious server HTML, sandbox escape, unauthorized tool execution, data exfiltration and phishing among its threats. It leaves user consent for View-initiated calls to the host ("MAY request user consent") ([MCP Apps spec](https://raw.githubusercontent.com/modelcontextprotocol/ext-apps/main/specification/2026-01-26/apps.mdx)). An inference worth acting on follows: because a View can feed text into the model through `ui/message` and `ui/update-model-context`, a compromised View is a prompt-injection channel. Its tool calls should pass through the same approval policy as the model's own calls. OpenAI's implementation shows two concrete mitigations. `_meta` reaches the widget but never the model. And since 27 May 2026, input for approval-gated tools reaches the widget only after the user approves ([Apps SDK reference](https://developers.openai.com/apps-sdk/reference.md); [Apps SDK changelog](https://developers.openai.com/apps-sdk/changelog.md)). Rendering is itself an exfiltration surface even without iframes: Simon Willison has catalogued many Markdown-image exfiltration attacks ([simonwillison.net](https://simonwillison.net/tags/markdown-exfiltration/), practitioner blog).

On whether generative UI is worth it, the evidence is promising but narrow. Chen et al. (ACL 2026 Findings) report "up to a 72% improvement in human preference" for generated interfaces over chat. They found an 84.0% win rate against a Claude 3.7 chat UI, 93.8% in data analysis, but only 50.0% for advanced AI/ML topics, and a lower preference for concise queries, where generative UI "may introduce unnecessary complexity" ([arXiv 2508.19227](https://arxiv.org/html/2508.19227)). Google Research reports that Gemini 3 Pro's generated pages were "strongly preferred", though generation "can sometimes take a minute or more" ([Google Research blog](https://research.google/blog/generative-ui-a-rich-custom-visual-interactive-user-experience-for-any-prompt/), vendor self-evaluation). Both are preference ratings, not task-success measures. No independent data on render-failure rates for A2UI or MCP Apps turned up.

## Runtime protocols and web frameworks divide on approval and resumption

The web stack has settled into two layers. A runtime protocol carries the run, and a payload format describes the UI. AG-UI says this outright: A2UI, MCP Apps and Open-JSON-UI "describe what UI an agent wants to show. AG-UI is the runtime protocol that carries those payloads." A2UI agrees and names AG-UI as its "standard transport binding" ([ag-ui README](https://raw.githubusercontent.com/ag-ui-protocol/ag-ui/main/README.md); [A2UI v1.0 spec](https://a2ui.org/specification/v1.0-a2ui/)). A2A 1.0 (Linux Foundation, March 2026) is agent-to-agent, not agent-to-UI. It carries UI only through extensions such as A2UI's, and it pauses with `TASK_STATE_INPUT_REQUIRED` ([A2A spec](https://a2a-protocol.org/latest/specification/)).

| Runtime protocol | Owner, status (as of Nov 2026) | Transport | Human-in-the-loop model | Resumption |
|---|---|---|---|---|
| AG-UI 1.0 | CopilotKit-led, MIT; frozen spec 17 Sep 2026 | HTTP POST + SSE; Protobuf binding | Run ends with `outcome: interrupt`; new run sends `resume[]` with same `threadId` | Not in protocol; CopilotKit Intelligence records events (paid hosted layer) |
| Vercel UI message stream v1 | Vercel, Apache-2.0 | SSE (`x-vercel-ai-ui-message-stream: v1`); WebSocket and in-process transports in v7 | In-stream `tool-approval-request` part answered by the client | `resumeStream` with app-supplied store (Redis via `resumable-stream`) |
| ACP v1 | Zed-originated, open | JSON-RPC over agent stdio | `session/request_permission` client request | `session/load`, `session/resume` |
| Codex app-server | OpenAI | stdio JSONL; experimental `ws://`, `unix://` | Server requests rendered as approval overlay | `thread/resume`; remote TUI |
| ChatKit server | OpenAI product protocol | Event iterator from `ChatKitServer.respond` | Widget confirm/cancel; client tool outputs | Server-side thread store |

Sources: [AG-UI interrupts](https://docs.ag-ui.com/concepts/interrupts.md); [AG-UI HTTP+SSE](https://docs.ag-ui.com/spec/1.0/basic/transports/http-sse.md); [CopilotKit AG-UI Streams](https://docs.copilotkit.ai/AG-UI-Streams.md); [AI SDK transport @ ai@7.0.162](https://github.com/vercel/ai/blob/ai@7.0.162/content/docs/04-ai-sdk-ui/21-transport.mdx); [AI SDK resume streams](https://github.com/vercel/ai/blob/ai@7.0.162/content/docs/04-ai-sdk-ui/03-chatbot-resume-streams.mdx); [ACP v1 meta](https://github.com/agentclientprotocol/agent-client-protocol/blob/v1.19.0/schema/v1/meta.json); [Codex App Server](https://developers.openai.com/codex/app-server); [Custom ChatKit](https://developers.openai.com/api/docs/guides/custom-chatkit.md).

The deepest split is how a run waits for a human. Vercel keeps the approval inside the message stream as a part the client answers. AG-UI and A2A end the run and start a new one that carries the answer. AG-UI's `Interrupt` carries a `responseSchema` and an `expiresAt`, and a resume must address every open interrupt ([AG-UI interrupts](https://docs.ag-ui.com/concepts/interrupts.md)). The terminating model fits stateless, checkpointed harnesses such as LangGraph or the OpenAI Agents SDK's `RunState`. The in-stream model fits a chat transcript that is itself the store. Translating between the two is mechanical.

The web frameworks are mostly opinions about where the source of truth lives:

- **Vercel AI SDK UI** holds `UIMessage[]` on the client and leaves persistence and resumption to the app. With resume enabled, "client-side aborts are treated as disconnects", so a real stop needs its own endpoint ([AI SDK resume streams](https://github.com/vercel/ai/blob/ai@7.0.162/content/docs/04-ai-sdk-ui/03-chatbot-resume-streams.mdx)). Its RSC `streamUI` path is still "experimental", and Vercel recommends "migrating to AI SDK UI" ([RSC overview](https://github.com/vercel/ai/blob/ai@7.0.162/content/docs/05-ai-sdk-rsc/01-overview.mdx)).
- **LangGraph's `useStream`**, now in `@langchain/react`, binds the UI to a server-checkpointed thread. It exposes typed graph state, `stream.interrupt`, checkpoint history for branching and time travel, and a native rejoin, where `disconnect()` leaves the run going and `stop()` cancels it ([LangChain frontend overview](https://docs.langchain.com/oss/javascript/langchain/frontend/overview.md); [Join & rejoin](https://docs.langchain.com/oss/javascript/langchain/frontend/join-rejoin.md)). Its generative UI is pushed by the server: `push_ui_message` sends components that the platform bundles and `LoadExternalComponent` mounts in a shadow DOM ([LangSmith generative UI](https://docs.langchain.com/langsmith/generative-ui-react.md)).
- **Cloudflare's `useAgentChat`** layers the AI SDK message model over a Durable Object WebSocket. Messages and stream chunks persist to SQLite, so resume needs no Redis ([Cloudflare chat agents @ agents@0.33.0](https://github.com/cloudflare/agents/blob/agents@0.33.0/docs/agents/chat-agents.md)).
- **CopilotKit** speaks AG-UI to LangGraph, ADK, Mastra and custom backends. It separates `useHumanInTheLoop` (the LLM calls a client tool) from `useInterrupt` (graph code such as LangGraph `interrupt()` pauses) ([CopilotKit HITL](https://docs.copilotkit.ai/human-in-the-loop.md)).
- **assistant-ui** defines no wire format. Its swappable "runtime" owns thread state, including branching, editing and regeneration, and first-party adapters map the AI SDK, LangGraph, `useStream`, ADK, A2A and AG-UI onto one message-part model ([assistant-ui runtimes](https://www.assistant-ui.com/docs/runtimes/pick-a-runtime.md)).
- **Google's `adk web`** is explicitly "not meant for use in production". It is a debugging UI over raw ADK `Event`s from `/run_sse`, with session-state editing, an event log, traces, eval sets and an agent graph. For production, ADK points to AG-UI and CopilotKit ([ADK web interface](https://github.com/google/adk-docs/blob/ff7a5f56469a81f3e43a8fc54668d8dc84300192/docs/runtime/web-interface/index.md); [ADK AG-UI](https://github.com/google/adk-docs/blob/ff7a5f56469a81f3e43a8fc54668d8dc84300192/docs/integrations/ag-ui.md)).

Python app builders take a looser route: Gradio puts tool activity into `ChatMessage.metadata` with a `title`, which renders as a collapsible accordion ([Gradio agents guide](https://www.gradio.app/guides/agents-and-tool-usage)).

## The eight verified SDKs expose three altitudes of UI contract

The eight SDKs this repository verifies all give a UI a typed, discriminated event union, but at three different altitudes. The findings below come from the installed type declarations and mirrored docs at the pinned versions. Marks of **[verified]** refer to the repo's offline behavioural examples, and nothing ran against a real model.

The first altitude is the **runtime log**: the event stream of a whole product. The Claude Agent SDK 0.3.327 yields a **40-member** `SDKMessage` union. Token deltas are opt-in raw Anthropic `stream_event`s, tool calls are `tool_use` blocks joined to later `tool_result` blocks by id, and a `session_state_changed` event reports `idle`, `running` or `requires_action` ([`sdk.d.ts`](../verify/claude-agent-sdk/node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts); [streaming-output](https://code.claude.com/docs/en/agent-sdk/streaming-output.md)). The GitHub Copilot SDK 1.0.31 emits a generated union of about **170** `SessionEvent` types. Each has an `{id, parentId, ephemeral?}` envelope. Deltas are ephemeral and never persisted **[verified]**, and ten `model.*` events sit outside the typed union **[verified]** ([Copilot streaming events](https://github.com/github/copilot-sdk/blob/v1.0.31/docs/features/streaming-events.md); [repo guide](../docs/reference/copilot-sdk/guide.md)). Pi 1.5.2's `AgentSessionEvent` adds queue, compaction and session-tree events to the core loop events. Its JSON and RPC modes write the stream as LF-delimited JSONL, with the cumulative `partial` snapshot stripped ([Pi rpc.md](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/rpc.md)). A UI on any of these three must whitelist the kinds it renders.

The second altitude is **run items and events** that a UI folds into messages. The OpenAI Agents SDK 0.21.0 streams raw Responses events, `run_item_stream_event`s (`tool_called`, `tool_output`, `handoff_occurred`, `tool_approval_requested` and others) and agent-updated events ([`events.d.ts`](../verify/openai-agents-sdk/node_modules/@openai/agents-core/dist/events.d.ts)). Google ADK 2.5.0 yields genai `Content.parts` with `functionCall` and `functionResponse`, plus `actions.stateDelta` on every event. Token streaming needs `StreamingMode.SSE` ([ADK API server](https://github.com/google/adk-docs/blob/ff7a5f56469a81f3e43a8fc54668d8dc84300192/docs/runtime/api-server.md)). LangGraph 1.6 sits between the second and third altitudes. It has eight `streamMode`s, a new `streamEvents` v3 with typed projections recommended "for most application and frontend use cases", and a types-only `@langchain/protocol` package. That package defines sequenced events and an `input.requested`/`input.respond` pair ([LangChain event streaming](https://github.com/langchain-ai/docs/blob/9d9747d0cf241e086c616a16d5ce230ad8f8f31d/src/oss/langchain/event-streaming.mdx)).

The third altitude is a **UI-ready part model**, and only Vercel has one. In AI SDK 7.0.162, `UIMessage.parts` puts a tool call, its approval and its result on one part with a single state field: `input-streaming → input-available → (approval-requested → approval-responded) → output-available | output-error | output-denied` ([Vercel chatbot tool usage](https://github.com/vercel/ai/blob/ai@7.0.162/content/docs/04-ai-sdk-ui/03-chatbot-tool-usage.mdx)). Cloudflare Agents 0.33.0 adopts that model wholesale inside `cf_agent_*` WebSocket frames. OpenAI's `@openai/agents-extensions/ai-sdk-ui` converts a run stream into the same chunks ([OpenAI AI SDK extension](https://github.com/openai/openai-agents-js/blob/v0.21.0/docs/src/content/docs/extensions/ai-sdk.mdx)). Every other SDK makes the UI join a call event to a result event by id.

### Approvals wait in a callback, a paused run or a message part

How a pending approval is stored decides whether it survives a reload. In the **callback** model, the SDK awaits a host function, so the pending prompt is an in-memory promise. Claude's `canUseTool` works this way, and it helpfully ships UI-ready `title`, `displayName` and `description` strings plus `default_to_no` hints ([`sdk.d.ts`](../verify/claude-agent-sdk/node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts)). Pi has no permission system at all: an extension's `tool_call` handler calls `ctx.ui.confirm` ([repo Pi guide](../docs/reference/pi/guide.md)). Copilot's `onPermissionRequest` is the exception that shows the fix. When the handler returns `{kind: "no-result"}`, the session emits `permission.requested` and waits for `handlePendingPermissionRequest` **[verified]**. Even then, `resumeSession` with `continuePendingWork` "does not re-emit restored permission requests", so a reconnecting UI must rebuild the pending list from the log ([repo Copilot guide](../docs/reference/copilot-sdk/guide.md)).

In the **paused-run** model, the run stops and its state is serialised. OpenAI's `result.interruptions` is answered with `state.approve/reject`; `RunState.toString()` survives a restart **[verified]**, and the docs warn that restored state is trusted, so browser UIs should keep it server-side ([repo OpenAI guide](../docs/reference/openai-agents-sdk/guide.md)). LangChain's `humanInTheLoopMiddleware` resumes with `Command({resume: {decisions}})` and offers approve, edit, reject and respond; "the pause lives in the checkpointer" **[verified]** ([repo LangChain guide](../docs/reference/langchain/guide.md)). ADK's `requireConfirmation` emits a long-running `adk_request_confirmation` call, stored as session events and validated against the original call id **[verified]** ([repo ADK guide](../docs/reference/google-adk/guide.md)).

In the **message-part** model, the approval is part of the transcript. Vercel answers it with `addToolApprovalResponse`, which survives a reload only if the app persists messages. Cloudflare sends a `cf_agent_tool_approval` frame against a part persisted in SQLite, so "the answer can arrive on a later connection" and the tool runs exactly once **[verified]** ([repo Cloudflare guide](../docs/reference/cloudflare-agents/guide.md)). For a web UI that must survive reloads, the part model is the least work, because the transcript itself shows the pending prompt.

### Only four SDKs can rejoin a stream that is still running

Rejoining a running stream needs a server that owns the run independently of the connection and buffers its chunks with sequence ids. Every design that works uses the same mechanism: monotonic sequence numbers plus a replay-or-continue flag. Cloudflare provides it with zero configuration. A `cf_agent_stream_resume_request` → `resuming` → `ack` handshake replays SQLite-buffered chunks flagged `replay: true`, deduplicated by `seq` ([Cloudflare resumable streaming](https://github.com/cloudflare/agents/blob/agents@0.33.0/docs/agents/resumable-streaming.md)). Vercel provides the client half (`reconnectToStream`, `resumeStreamIsReplay`) plus a store interface ([AI SDK resume streams](https://github.com/vercel/ai/blob/ai@7.0.162/content/docs/04-ai-sdk-ui/03-chatbot-resume-streams.mdx)). LangGraph's client stack has `joinStream(runId, lastEventId)` and protocol-level `event_id`/`seq`, but these need a server that buffers runs, such as LangGraph Platform ([`@langchain/protocol`](../node_modules/.pnpm/@langchain+protocol@0.0.20/node_modules/@langchain/protocol/README.md)). Claude has it only in the hosted bridge and browser SDK, through SSE sequence numbers marked `@alpha`. OpenAI, Pi, ADK and Copilot offer resume from persisted state after the fact, not rejoin.

### Only Cloudflare syncs app state in both directions

Shared state beyond the transcript is where the SDKs differ most. Cloudflare's `setState()` "saves to SQLite, broadcasts to connected clients and then calls `onStateChanged()`" **[verified]**. Clients can push state back, subject to `validateStateChange` ([Cloudflare state docs](https://github.com/cloudflare/agents/blob/agents@0.33.0/docs/agents/state.md)). LangGraph exposes full graph state through the `values` stream and `useStream`. ADK emits `stateDelta`, which AG-UI's shared state builds on. Vercel offers one-way typed `data-*` parts. Claude, Pi, OpenAI and Copilot expose runtime status (todos, plans, queues, modes, Copilot's experimental canvases) but no app-defined state object.

## Beyond chat, the plan and the review surface matter most

The critique of chat as the only interface has been steady since 2023. Nielsen calls intent-based outcome specification a paradigm that "completely reverses the locus of control", and he expects hybrid UIs that keep GUI elements ([NN/g](https://www.nngroup.com/articles/ai-paradigm/)). Wattenberger argues that chat lacks a "working buffer", so after successive rewrites "it's laborious to figure out what concretely has changed" ([Wattenberger essay](https://wattenberger.com/thoughts/boo-chatbots), opinion). Henley calls natural language as the only interface "lazy", and Appleton calls chat "flexible, familiar, and easy to implement" but "the lazy solution" ([Henley](https://austinhenley.com/blog/naturallanguageui.html); [Appleton](https://maggieappleton.com/lm-sketchbook), both opinion). Products have answered with four structures, and each moves the unit of interaction off the transcript.

**Canvases and artifacts** pair the chat rail with a persistent object. By November 2026, Claude's artifacts can read and write connected apps, store data between sessions (default 100 MB and 25,000 documents) and let viewers interact with Claude through them. Artifacts made before 16 September 2026 are now "legacy" ([Claude Help Center](https://support.claude.com/en/articles/9487310-what-are-artifacts-and-how-do-i-use-them)). The artifact has thus become a stateful mini-app that overlaps with generative UI.

**Background agents** make a branch or PR the deliverable and demote the transcript to a log. Examples are Claude Code cloud sessions that "keep running after you close your laptop", Copilot sessions that "continue seamlessly" across app, IDE, mobile and CLI, Cursor Cloud Agents that produce "merge-ready PRs with artifacts" (screenshots, videos, logs) with remote-desktop takeover, and Jules plans approved "before any code changes are made" ([Claude Code on the web](https://code.claude.com/docs/en/claude-code-on-the-web); [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent); [Cursor Cloud Agents](https://cursor.com/docs/cloud-agent); [Jules docs](https://jules.google/docs/)). The binding constraint is human review. In the repo's Hacker News corpus, about 190 authors name review burden as the most widely shared cost, and successful users cap themselves at **about two to six parallel sessions** ([what-fails note](../docs/research/practitioners/notes/what-fails.md); [what-works note](../docs/research/practitioners/notes/what-works.md)).

**Inboxes** serve ambient agents that react to events and surface only to notify, ask or request review ([LangChain blog](https://blog.langchain.com/introducing-ambient-agents/), vendor). LangChain's Agent Inbox types each interrupt with `allow_accept`, `allow_edit`, `allow_respond` and `allow_ignore` ([agent-inbox README](https://github.com/langchain-ai/agent-inbox)). That is the same decision set as `humanInTheLoopMiddleware` and close to ACP's options, which suggests approval decisions are becoming a portable schema.

**Editable plans** have the strongest evidence. On GAIA, Magentic-UI's co-planning, co-tasking and action guards raised task completion from **30.3% to 51.9%** with a simulated user who was asked for help in only 10% of tasks ([arXiv 2507.22358](https://arxiv.org/html/2507.22358)). Cocoa's notebook-style plans "enabled steerability without sacrificing ease-of-use" (n=16) ([arXiv 2412.10999](https://arxiv.org/abs/2412.10999)). About 400 HN authors describe writing the plan to a file, annotating it and reusing it as a progress log ([what-works note](../docs/research/practitioners/notes/what-works.md)). The counterweight comes from a CHI 2025 study (N=248), which found users "can easily mistrust the LLM agents with plans that seem plausible" ([arXiv 2502.01390](https://arxiv.org/abs/2502.01390)). A plan review should therefore surface risks and assumptions, not only steps.

Transparency still matters inside these structures. About 45 practitioners object to hidden reads and opaque subagents ("there's no observability into subagents and you just get a summary"), while others find "almost no value in watching the stream". A screen-reader user notes that collapsed output means no information at all ([docs-and-dx note](../docs/research/practitioners/notes/docs-and-dx.md)). The reconciliation is a summary-first surface over a complete, linear, accessible log. None of these surfaces has controlled data on canvas versus chat or on inbox approval accuracy. The case for them rests on preference studies, a few HCI experiments and practitioner convergence.

## Conclusion

The question is no longer whether to render a chat. It is which projections of the event log a UI needs, and which part of the stack owns the log. The transcript, the tool cards, the plan checklist, the approval inbox, the artifact and the PR review are all views over one ordered, append-only stream. The hard engineering sits beneath them. A server must own the run apart from any connection. Chunks must carry sequence numbers so clients can rejoin. Pending approvals must be durable records rather than in-memory promises. App state needs a write path back from the UI. Cloudflare comes closest to providing all four out of the box. Vercel's part model is the best rendering contract. AG-UI and ACP are the best portability bets for web and editors respectively.

For this repository's harness, the practical recommendation is to treat the session event log (architecture layer 3) as the UI contract itself. That means four things. Emit events whose vocabulary maps one-to-one onto ACP `session/update` and AG-UI. Ship translators to the Vercel UI message stream, of the kind OpenAI's adapter already shows, to get off-the-shelf React frontends. Model every approval as a persisted request with once/always/reject/redirect decisions, so that the in-stream, terminating and MCP-App View paths all funnel into one approval policy. Finally, treat generative UI as a permission question as much as a rendering one: declarative catalogues (A2UI) by default, and sandboxed MCP Apps for third-party tools, with View-initiated calls gated like model-initiated calls.
