# Copilot writes first and keeps the undo copy

- **Status:** research report for todo U8 (Round U), 2026-11-18. It answers the owner's question about Copilot's diff review and builds on the [undo report](undo-agent-edits.md) (U4) and the [agent UI synthesis](agent-ui-research.md) (U1).
- **Versions checked (as of November 2026):** VS Code release `1.147.0` and `main` at commit [`25cbb2e`](https://github.com/microsoft/vscode/tree/25cbb2e79c4601f32cd52d93847c62210a0072cd) (2026-11-18, version `1.148.0`, pre-release), which also holds the Copilot extension under `extensions/copilot/`; `@github/copilot-sdk` `1.0.31`, which bundles Copilot runtime `1.0.109`.
- **Evidence:** two research notes, [VS Code chat editing at source level](notes/vscode-chat-editing.md) and [Copilot's other surfaces and other agents](notes/copilot-surfaces-and-comparison.md). They cite the VS Code source at that commit, the SDK's `.d.ts` files, code.visualstudio.com, docs.github.com, learn.microsoft.com, and the Claude Code, Cline, Zed and Cursor docs, all fetched on 2026-11-18. Corrections are logged in [fact-check.md](fact-check.md#copilot-diff-review-report-2026-11-18).
- **Verified:** every behavioural, version, date and setting claim was re-read against its primary source on 2026-11-18. The VS Code source and the SDK types were read, not built or run, and this repo's harness never lets a mock model call the runtime's built-in write tool, so the `write` permission flow is read from types and source, not observed. Repo content and docs pages were read as data, and the agent instructions they contain were not followed.

The owner asked whether GitHub Copilot, like a database transaction, keeps a copy of a change it is about to commit and lets the user confirm or reject that diff. For the surface most people use, the answer is no. When Copilot in VS Code shows a diff of agent edits with Keep and Undo buttons, **the edits are already in the real file and already saved to disk**: "Pending edits are already saved to disk, so running your application or tests uses the changed files" ([VS Code: Review and revert agent changes](https://code.visualstudio.com/docs/copilot/chat/review-code-edits)). The copy VS Code keeps is a snapshot of the file *before* the agent touched it, and Undo is a new write that puts that snapshot back. In database terms, VS Code keeps an undo log and reverses with a compensating write; it never stages a write set for commit. Visual Studio and JetBrains agent modes also write first and review after.

The hypothesis holds in three narrower places, all as of November 2026. First, the **Copilot runtime** behind the CLI, the SDK and VS Code's default harness builds each proposed file write (a unified diff plus full before and after text) and runs it only after approval, but one tool call on one file at a time. Second, VS Code uses that confirm-first path by default only for **sensitive or outside-workspace files**. Third, the **cloud agent** puts the whole task on a branch in a draft pull request that a human must merge. It is the only Copilot surface that commits a held copy of the entire change in one step. In this report, I trace where each Copilot surface keeps the change before you decide, from VS Code's source to the cloud agent, and show that every local surface lets tests, builds and other processes see unreviewed agent edits, while none reviews what shell commands or external calls did.

## VS Code applies, saves, then lets you revert from a before-image

VS Code runs Copilot through two harnesses, and both write first. The default **Copilot harness** runs "the Copilot SDK" in a separate Agent Host process, while the deprecated **Local harness**, due for removal in February 2027, runs VS Code's own agent in the extension host ([VS Code: Agent harnesses](https://code.visualstudio.com/docs/agents/run/agent-harnesses)). The review docs cover both: "When you use Copilot and Local harness sessions in the editor window, supported file edits are tracked as pending review (working set)", and pending edits are already on disk ([VS Code review page](https://code.visualstudio.com/docs/copilot/chat/review-code-edits)). The Local harness shows the mechanism most plainly, so I trace it first, then show how the Copilot harness differs.

### The Local harness keeps the before-image in memory

In the Local harness, the review mechanism sits in VS Code core, not in Copilot's tools. The edit tools (`replace_string`, `create_file`, `apply_patch`) never write files; they stream text edits into the chat response, and the chat editing session applies them ([abstractReplaceStringTool.tsx L301-L314](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/extensions/copilot/src/extension/tools/node/abstractReplaceStringTool.tsx#L301-L314); [chatEditingSession.ts L1033-L1034](https://github.com/microsoft/vscode/blob/1.147.0/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts#L1033-L1034)). Each edited file then gets two text models. **`modifiedModel` is the real file's editor buffer**, and `originalModel` is a new in-memory model that holds a snapshot of the file at first touch, under a synthetic `chatEditingModel` URI scheme ([chatEditingModifiedDocumentEntry.ts L124-L136](https://github.com/microsoft/vscode/blob/1.147.0/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingModifiedDocumentEntry.ts#L124-L136)). Agent edits go into the real buffer through `pushEditOperations` ([chatEditingTextModelChangeService.ts L296-L318](https://github.com/microsoft/vscode/blob/1.147.0/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingTextModelChangeService.ts#L296-L318)). When the last edit of a stream arrives, VS Code **saves the file to disk with `SaveReason.AUTO`, without waiting for Keep**, for any file that is not untitled ([chatEditingModifiedDocumentEntry.ts L260-L281](https://github.com/microsoft/vscode/blob/1.147.0/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingModifiedDocumentEntry.ts#L260-L281)). The files `chatEditingModifiedDocumentEntry.ts`, `chatEditingTextModelChangeService.ts` and `chatEditingSession.ts` are byte-identical at tag 1.147.0 and at commit `25cbb2e`, so their line references hold for the stable release.

The diff you see is therefore `originalModel` against the live file. **Keep** sets `originalModel` to the current file so the diff empties. If the user does not auto-save, or the file is clean, Keep then saves explicitly so that the formatters the automatic save skipped can run. **Undo** replaces the whole real buffer with the snapshot as one editor-undo step, and it saves again only if every edit in the file came from the agent ([chatEditingTextModelChangeService.ts L321-L335](https://github.com/microsoft/vscode/blob/1.147.0/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingTextModelChangeService.ts#L321-L335); [chatEditingModifiedDocumentEntry.ts L284-L322](https://github.com/microsoft/vscode/blob/1.147.0/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingModifiedDocumentEntry.ts#L284-L322)). Per-hunk Keep and Undo copy single hunks between the two models ([L409-L450](https://github.com/microsoft/vscode/blob/1.147.0/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingTextModelChangeService.ts#L409-L450)). Creation and deletion follow the same apply-first rule. A created file exists on disk at once and Undo deletes it; a deleted file leaves the disk at once, and VS Code keeps its content so Undo can write it back ([chatEditingSession.ts L600-L662](https://github.com/microsoft/vscode/blob/1.147.0/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts#L600-L662); [chatEditingDeletedFileEntry.ts L244-L253](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingDeletedFileEntry.ts#L244-L253)). Notebooks use the same pattern ([chatEditingModifiedNotebookEntry.ts L416-L456](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingModifiedNotebookEntry.ts#L416-L456)).

Above the per-file review state sits a second mechanism, **request-level checkpoints**. An epoch-ordered timeline records text edits, creates, deletes and renames. "Restore checkpoint", or editing an earlier prompt, moves along that timeline by rewriting files on disk, and the timeline persists in workspace storage across restarts ([chatEditingCheckpointTimelineImpl.ts L672-L730](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingCheckpointTimelineImpl.ts#L672-L730); [chatEditingSessionStorage.ts L60-L72](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSessionStorage.ts#L60-L72)). Neither mechanism holds a proposed change back from disk, and **no setting does either**: `chat.editing.autoAcceptDelay`, which the docs scope to the Local harness, only Keeps edits automatically after a countdown ([chat.shared.contribution.ts L577-L583](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts#L577-L583)).

### The Copilot harness keeps the review in the Agent Host

The Copilot harness moves the same review into the Agent Host. VS Code's side of it says "the agent host writes files itself", and the editor's Keep and Undo become requests to the host, whose Working Set changeset "holds the tool edits the user hasn't kept" ([agentHostSnapshotController.ts L33-L72](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostSnapshotController.ts#L33-L72); [agentHostEditReview.ts L232-L247](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostEditReview.ts#L232-L247)). Each Accept or Discard names "the version of the changes the editor showed", and a stale one fails with "The changes were updated in the meantime. Try again." Before a Discard, VS Code first saves any unsaved text in the editor, because "The agent host reverts the changes on disk" (same file, L776-L871). That version check is optimistic concurrency, the nearest thing to a transaction protocol in VS Code, but it still operates on files the agent has already written.

### Sensitive files are VS Code's one confirm-before-write path

Both harnesses make one deliberate exception. The setting `chat.tools.edits.autoApprove` maps globs to booleans. By default it approves every edit except those to files that can trigger side effects when written, such as `.git/**`, `package.json`, lockfiles, `.env`, `Cargo.toml`, `.npmrc` and project files ([chatSettings.ts L138-L149](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/src/vs/platform/chat/common/chatSettings.ts#L138-L149)). A second list, `ALWAYS_CHECKED_EDIT_PATTERNS`, covers paths "whose executable side effects require confirmation regardless of user configuration", such as `.mcp.json`, `.vscode/*.json`, dev-container configs, and agent and hook folders ([chatSettings.ts L117-L135](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/src/vs/platform/chat/common/chatSettings.ts#L117-L135)). The docs confirm the ordering: "Sensitive-file approval happens before the agent saves an edit, rather than during review" ([VS Code review page](https://code.visualstudio.com/docs/copilot/chat/review-code-edits)).

The two harnesses enforce the exception in different code. In the Local harness, the edit tool's `prepareInvocation` returns an "Allow edits to sensitive files?" confirmation, with a unified diff, *before* the edit runs ([editFileToolUtils.tsx L962-L1018](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/extensions/copilot/src/extension/tools/node/editFileToolUtils.tsx#L962-L1018)). In the Copilot harness, VS Code forwards the same setting to the Agent Host ([chat.shared.contribution.ts L906-L918](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/src/vs/workbench/contrib/chat/browser/chat.shared.contribution.ts#L906-L918)). The host checks each runtime `write` permission request against those patterns and `ALWAYS_CHECKED_EDIT_PATTERNS` ([sessionPermissions.ts L264-L399, L880-L895](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/src/vs/platform/agentHost/node/sessionPermissions.ts#L264-L399)). It attaches the request's `diff` to the pending confirmation ([copilotAgentSession.ts L9231-L9235](https://github.com/microsoft/vscode/blob/25cbb2e79c4601f32cd52d93847c62210a0072cd/src/vs/platform/agentHost/node/copilot/copilotAgentSession.ts#L9231-L9235)). Setting `{"**/*": false}` should therefore make every edit ask first with a diff, the closest VS Code comes to the hypothesis. After Allow, however, the edit is still applied, saved and then reviewed as pending (my inference from the code; not tested).

The split follows reversibility. Text edits are cheap to revert, so they skip pre-approval. While "common read-only commands run automatically" by default, VS Code confirms risky terminal commands, MCP tools and URL fetches before they run ([VS Code: Manage approvals and permissions](https://code.visualstudio.com/docs/agents/run/approvals)). It confirms files whose mere writing can execute code for the same reason: a before-image cannot undo what those actions set off.

## The Copilot runtime holds one proposed write until you approve it

The Copilot CLI is the surface that best fits the hypothesis, one tool call at a time. In the default manual approval mode, Copilot "asks for your approval when a tool request isn't already allowed", which "can include tools that modify or execute files". The prompt offers "Yes", "Yes, and approve TOOL for the rest of the running session" and "No, and tell Copilot what to do differently"; on No, "Copilot will not run the command" ([About Copilot CLI](https://docs.github.com/en/copilot/concepts/agents/about-copilot-cli); [Using Copilot CLI](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/use-copilot-cli)). The runtime's types show what the prompt carries. The SDK's upstream README says it "exposes the same engine behind Copilot CLI", and in `@github/copilot-sdk` 1.0.31 (runtime 1.0.109) a `PermissionRequestWrite` has four content fields. They are `fileName`, a human-readable `intention`, a required `diff` ("Unified diff showing the proposed changes"), and an optional `fileEdits` array of "Complete before/after text previews captured while planning this request". In each entry, `before` is content "read while planning the operation" and `after` is the "Complete file content the operation plans to write" (`dist/generated/session-events.d.ts:11359-11444` in [@github/copilot-sdk 1.0.31](https://www.npmjs.com/package/@github/copilot-sdk/v/1.0.31)). For writes the sandbox would block, `requestSandboxBypass` is "a request, not a grant: the write happens unsandboxed only if the user approves this permission request" (same file, `:11394-11397`). Decisions range from `approve-once` and `approve-for-session` to `approve-permanently` and `reject` (`dist/generated/rpc.d.ts:25391-25856`).

That request is a genuine held copy of a proposed change. The runtime has planned the edit, the tool body has not run, and the host can render the diff, hold the request pending, and approve or reject it. VS Code's Copilot harness is one such host, since it passes the request's `diff` to its confirmation, as the previous section showed. Our harness verified the ordering for custom tools: the runtime asks `onPermissionRequest` before the handler runs, and a declined call "never runs" ([Copilot SDK guide](../../reference/copilot-sdk/guide.md), examples 02 and 09). By policy, though, it never let the mock model call the built-in write or shell tools, so the runtime behaviour of the `write` kind comes from types and source, not observation. The CLI docs also never say in words that the prompt displays the diff; that is a strong inference from the payload.

Two further limits matter. First, the unit is **one tool call on one file**: a multi-file change arrives as several requests, each approved and applied on its own, and no API commits several held edits together. Second, the confirm step erodes in practice. Session approval, `--allow-tool='write'`, `--allow-all-tools` and `/yolo` remove it, and the CLI then becomes apply-then-review through `/diff` and `/rewind` ([CLI command reference](https://docs.github.com/en/copilot/reference/cli-command-reference)). So the CLI README's "nothing happens without your explicit approval" holds only in manual mode ([github/copilot-cli](https://github.com/github/copilot-cli)).

The CLI's undo layer reaches further than VS Code's but is explicitly not transactional. With "Conversation + files", `/rewind` restores files "to their pre-change contents, skipping any you have since edited yourself"; "File changes are tracked per turn across editing tools, shell commands, and sub-agents, so Git is not required. A rewind cannot be undone" ([CLI command reference](https://docs.github.com/en/copilot/reference/cli-command-reference)). The SDK's `history.rewind` JSDoc is franker: "Not crash-atomic: file restore and conversation truncation are separate stores, applied in that order… There is no recovery journal". Its outcomes include `files-rolled-back` and `rollback-incomplete`, and its skip reasons include `user-modified` and `skipped-capture` ("A faithful preimage was not captured") (`dist/generated/rpc.d.ts:3171-3247, 45632` in [@github/copilot-sdk 1.0.31](https://www.npmjs.com/package/@github/copilot-sdk/v/1.0.31)). Plan mode blocks project-file edits but calls itself "a safety net, not a guarantee". It lets through MCP tools and shell commands whose effect "can't be clearly determined in advance" ([CLI command reference](https://docs.github.com/en/copilot/reference/cli-command-reference)).

## Visual Studio and JetBrains review after the write; the cloud agent reviews before the merge

Visual Studio agent mode "makes code edits, runs terminal commands, invokes tools, and applies changes across your codebase". It asks first only before "running a terminal command or using a tool that isn't built in" ([Visual Studio: Copilot agent mode](https://learn.microsoft.com/en-us/visualstudio/ide/copilot-agent-mode), updated 2026-10-13). Review comes afterwards. You keep or undo everything in Total changes, per file or per chunk, and Keep or Undo there covers "all edits made since the last time that you selected Keep or Undo". To roll back, you restore the checkpoint before a prompt, because the agent "doesn't support stepwise undo or redo" (same page). The older **Copilot Edits** flow comes closer to the hypothesis. Its proposed changes "appear as a diff in the code editor", Tab accepts and Alt+Delete rejects, and you "accept the proposed changes to commit them" ([Visual Studio: Copilot Edits](https://learn.microsoft.com/en-us/visualstudio/ide/copilot-edits), updated 2026-10-14). That "commit" is UI language, not Git or a transaction, and neither Visual Studio page says whether pending edits reach the disk before Keep.

In JetBrains agent mode, "Copilot streams the edits in the editor, updates the working set", and the next step is "Review the changes", while the user confirms terminal commands before they run ([Using agent mode in your IDE](https://docs.github.com/en/copilot/how-tos/copilot-in-your-ide/use-copilot-agents/use-agent-mode), JetBrains tab). JetBrains **edit mode** offers "controlled edits across multiple files that you review and accept individually", with Accept or Discard per file ([Asking Copilot questions in your IDE](https://docs.github.com/en/copilot/how-tos/chat-with-copilot/chat-in-ide)). GitHub's JetBrains docs cover none of three details: checkpoints, per-hunk review in agent mode, or whether pending edits are saved. Those details remain unknown.

The **cloud coding agent**, now called "Copilot cloud agent", is where the analogy holds best. It "only has the ability to push to a single branch", which is a new `copilot/` branch unless it was invoked on an existing pull request. Its draft pull requests "must be reviewed and merged by a human", and it "cannot mark its pull requests as 'Ready for review' and cannot approve or merge" them. By default, workflows wait until a user with write access approves them, and the person who asked for the pull request cannot approve it ([Risks and mitigations for Copilot cloud agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)). The branch is the held copy, the pull request diff is the review, and the merge commits the whole task atomically at the Git level. A rejected pull request still leaves in place whatever the agent did outside the branch during the run: network calls its firewall allowed, MCP calls, or workflow runs someone approved.

## The transaction analogy breaks in six places

A database transaction has three parts: a private copy, a review, and an atomic commit or abort. The analogy fits only where all three exist, and across Copilot's surfaces they rarely do. The table shows which parts each surface has.

| Surface (Nov 2026) | Where the change lives before you decide | Your decision does | Unit |
|---|---|---|---|
| VS Code agent, Copilot or Local harness | Real file, saved to disk; before-image in the Agent Host or in memory | Keep drops the before-image; Undo writes it back | File or hunk; checkpoint per request |
| VS Code sensitive files | Planned edit and diff in the tool confirmation | Allow runs the write; Deny skips it | One tool call |
| Copilot CLI (manual) and SDK runtime | Planned diff and before/after text in the permission request | Approve runs the write; reject skips it | One tool call, one file |
| CLI with session or global approval | On disk | `/rewind` restores per turn, best effort | Turn |
| Visual Studio agent mode | In the files (disk state undocumented) | Keep or Undo; checkpoint Restore | Chunk, file, all |
| Visual Studio Copilot Edits; JetBrains edit mode | Proposal diff in the editor | Accept or reject | Chunk or file |
| JetBrains agent mode | Streamed into the editor | Review the changes | Not documented |
| Cloud agent | A `copilot/` branch and draft pull request | Merge or close | Whole task |

The first break is **direction**. The default local copy is a before-image, so the file on disk holds the agent's version until you object, and VS Code's Undo is itself a write that any process may have raced. The second break is **granularity**. Where Copilot does hold a proposed change, it holds one tool call on one file, and approving that call does not wait for the rest of the task. The third break is **defaults drift**: session approvals, `/yolo`, and VS Code's Allow all and Autopilot turn confirm-first into apply-first. VS Code says the last two "skip confirmation for potentially destructive actions, including file edits, terminal commands, and external tool calls" ([VS Code approvals](https://code.visualstudio.com/docs/agents/run/approvals)).

The fourth break is **shell commands**. A prompt shows the command text, not its effect, and VS Code's working set "only tracks changes from supported agent edit tools", so a `sed -i` or a build never passes through a diff. The CLI's `/rewind` does track the file changes that shell commands make ([VS Code review page](https://code.visualstudio.com/docs/copilot/chat/review-code-edits); [CLI command reference](https://docs.github.com/en/copilot/reference/cli-command-reference)). The fifth break is **external effects**: VS Code checkpoints leave in place "completed terminal commands, network requests, deployments, or changes that tools made to external services" ([VS Code review page](https://code.visualstudio.com/docs/copilot/chat/review-code-edits)).

The sixth break is **atomicity and isolation**. In the Local harness, Keep All runs the per-file writes in parallel and logs and swallows any one that fails. Only then does it flip the UI state "atomically in a single transaction", so its cross-file atomicity is cosmetic ([chatEditingSession.ts L433-L472](https://github.com/microsoft/vscode/blob/1.147.0/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingSession.ts#L433-L472)). The same harness handles concurrency by rebasing. When the user edits a file during review, VS Code folds the edit into the baseline, so Undo removes only the agent's change; if the edit overlaps the agent's, VS Code composes it into the agent diff instead ([chatEditingTextModelChangeService.ts L362-L408](https://github.com/microsoft/vscode/blob/1.147.0/src/vs/workbench/contrib/chat/browser/chatEditing/chatEditingTextModelChangeService.ts#L362-L408)). The Copilot harness rejects a stale Accept or Discard instead, and the CLI's rewind skips files you edited. No Copilot doc says whether an approved write rechecks that the file still matches the previewed `before`.

## Other agents split the same way, and none commits a task

Copilot is typical of local agents: they confirm per tool call or review after the write. Two agents, Claude Code and Cline, confirm edits before writing them. **Claude Code in VS Code, in Manual mode**, confirms before it applies, with a real pre-write diff: "it shows a side-by-side comparison of the original and proposed changes, then asks for permission. You can accept, reject, or tell Claude what to do instead". Its `acceptEdits` mode removes that step ([Claude Code in VS Code](https://code.claude.com/docs/en/vs-code.md); [Claude Code permissions](https://code.claude.com/docs/en/permissions.md)). Its `/rewind` restores only files its own edit tools have touched, and "A file that only Bash commands changed isn't tracked" ([Claude Code checkpointing](https://code.claude.com/docs/en/checkpointing.md)). **Cline** says "every edit shows up as a diff you can review, modify, or revert". In its Act mode every edit and command needs approval unless auto-approve, "evaluated per tool call", is on ([cline/cline](https://github.com/cline/cline); [Cline Auto Approve](https://docs.cline.bot/features/auto-approve.md)).

Zed and Cursor, by contrast, review after the write. After **Zed**'s agent writes, its Review Changes view lets you "accept or reject each individual change hunk, or the whole set" ([Zed agent panel](https://zed.dev/docs/ai/agent-panel.md)). **Cursor** relies on checkpoints, and "Restoring a checkpoint reverts files only" ([Cursor agent overview](https://cursor.com/docs/agent/overview.md)); we found no primary documentation of its Keep and Undo diff UI as of November 2026. Every local agent therefore works per tool call or per file, and every one leaves shell and external side effects out of review. Only pull-request agents, such as Copilot's cloud agent, commit a whole task in one step.

## Conclusion: build a per-call gate and a task-level staging area on purpose

Copilot's review diff is usually a *receipt*, not a *proposal*. In VS Code, Visual Studio and JetBrains agent mode, the change has already happened, and the diff shows what you can still revert. Copilot holds a proposal only where reverting would come too late: sensitive config files that execute on write, and the runtime's manual mode, which needs no editor to revert in. Even then the proposal covers one tool call. The vendors choose undo over pre-approval for text edits because a before-image makes text edits cheap to reverse, and they keep pre-approval for the actions a before-image cannot reverse.

For our harness, those choices suggest building both layers deliberately instead of borrowing the word "transaction". The runtime's `write` request, with its diff and before and after snapshots, is the right shape for a per-call confirm gate. A true task-level commit needs a staging area that the agent writes into, such as a branch, a worktree or an overlay, followed by a single merge, which is what the cloud agent already does. Anything that escapes the staging area, from shell side effects to network calls, needs its own confirmation, because no rewind in any product reviewed here reverses it.
