# Make agent edits undoable by tracking who wrote what

An AI agent that edits a form, a document or a codebase will sometimes be wrong, and the person beside it needs to take back the agent's edits without losing their own. A UI that gets this right does three things. First, it tags every write with its actor and turn. Second, it keeps the agent's writes away from anything irreversible until a person commits them. Third, it reverts by inverse operations that leave other people's later edits alone. As of November 2026, no single library does all three.

Each layer of the stack covers part of the problem. Vercel Labs' UI SDK (`0.1.0-beta.10`) supplies the tagging, because every change callback sees `source: "agent"`, and an experimental history that can undo by source. Its `details.cancel()`, however, is a veto applied before the write, not an undo, and its multi-step `act()` has "no rollback". Among state libraries, only **Yjs `UndoManager` gives safe per-actor undo under interleaved edits**, because it reverts by CRDT item IDs rather than array positions. Patch stacks such as Immer's misfire once a human has shifted the same arrays, and snapshot stores cannot undo one actor at all. Products pair a Keep/Undo review layer with automatic checkpoints, and every vendor admits that neither layer reverses shell commands, network calls or external writes.

That shared limit sets the design. In this report, I show that an agent UI should **record agent edits as a tagged, grouped draft, list what actually changed rather than what was requested, revert by inverse operations, and gate irreversible side effects behind confirmation or a deferred commit in the style of Gmail's Undo Send.**

## UI SDK's `cancel()` refuses a write, and nothing exists to roll back

UI SDK's change callbacks answer "who is changing this?" but not "can I take it back?". `ChangeDetails` has exactly five members: `reason`, `event`, `source`, `cancel()` and `canceled`. Its `source` is one of `"mouse" | "touch" | "pen" | "keyboard" | "virtual" | "programmatic" | "agent"` ([details.ts](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/foundation/kernel/details.ts#L9-L184)). Callbacks learn the source because the agent bridge runs each step inside `withSource("agent", call)` ([agent.ts](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/agent/agent.ts#L716-L723)). The order of operations then decides what `cancel()` can do. The change function builds `details`, **calls the callback, and only then writes to the store**, and only if the change was not cancelled. A cancelled change returns before it notifies watchers, so `observe`, `agent.subscribe` and the history never hear of it ([change.ts](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/foundation/kernel/change.ts#L98-L158)). The documented example vetoes one value: `if (details.source === "agent" && value === "asia-pacific") details.cancel()` ([permissions.mdx](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/permissions.mdx#L111-L127)). A veto suits "never let the agent set X". It cannot serve "let the agent set X, then let the person decide", because nothing was written that could be undone.

The bridge's result hides cancels, and its batches are not atomic; the docs state both gaps. First, **`ok` only means "no bridge error"**. `act()` returns `{ ok: !error, … }`, and `error` is set only when a step throws: an `allow` refusal, "Needs a person", a disabled target or a bad reference ([agent.ts](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/agent/agent.ts#L1853-L1905)). The bridge reference says so directly: "A callback can also cancel a change without making the step fail, so `ok: true` doesn't mean every requested value was accepted. Inspect each step's `changes` and the returned `values`" ([reference.mdx](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/reference.mdx#L136)). The bridge computes `steps[].changes` by diffing live state before and after each step, so a cancelled value produces no entry there. Second, **multi-step `act({ steps })` is not atomic**: "A failed step stops the call. Earlier steps stay applied; there is no rollback" ([reference.mdx](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/reference.mdx#L136)). Each step is written and rendered before the next, and `allow` is asked per step, not per batch ([agent.ts](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/agent/agent.ts#L1264-L1324)). Because each step awaits rendering, a person can edit the page between steps, so the batch is not isolated from human edits either.

Three more limits of `cancel()` matter for undo. First, `cancel()` takes no argument, so it cannot send the agent a reason. Second, `details` carries no act or step ID, so a callback cannot tell which turn produced a change. Third, a controlled component ignores `cancel()` for the value itself, because its owner decides the next value. A change it does not cancel is reported at once, and that notification "isn't confirmation that the owner accepted it" ([observe-changes.mdx](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/observe-changes.mdx#L54)).

## UI SDK's history undoes "everything the agent did", not "the agent's last turn"

UI SDK keeps a person's edits when it undoes the agent's, which is the right conflict policy for a mixed human and agent page. The undo machinery sits in a separate, **experimental** module. `createHistory(agent, { within?, keys?, coalesce? })` keeps an in-memory log with one entry per changed (component, key) pair. Each entry records `{ id, ref, label, key, value, previous, source, reason, reverted?, redacted? }`. The log offers `seek(n)` for editor-style stepping and `undoSource(source)` for undoing by actor ([history.ts](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/history/history.ts#L14-L360); [history-and-undo.mdx](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/history-and-undo.mdx#L12-L113)). `undoSource("agent")` restores each touched key to "its latest value from the other sources", so "if a person changes the project name after the agent does, that person's value stays" ([history-and-undo.mdx](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/history-and-undo.mdx#L69-L79)). Unlike a raw `act` caller, the restore code also checks the live value: a step counts as done only if `act(...).ok` **and** the current value equals the target. If a person edits a key while the history restores it, the history drops that key ("Anyone else's change is later than the restore, so it stays"). A refused undo keeps its entry applied and is reported back ([history.ts](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/history/history.ts#L205-L251)).

The history's scope is narrow, and the docs say so: it "doesn't undo a network request, recreate a removed component or reverse an action such as saving a form". It records only value keys (`value`, `checked` and `pressed` by default), restores them through each component's setter, and never restores secret fields ([history-and-undo.mdx](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/history-and-undo.mdx#L32-L63)). The source shows four more limits that the docs do not discuss. **No per-turn undo exists.** Entries carry no act ID, so `undoSource("agent")` reverts every agent entry in the log, and `seek(position)` also reverts interleaved human edits. **Restore writes are agent writes.** They run inside the agent source, so an app rule that cancels agent changes to "Asia Pacific" will also cancel an undo back to "Asia Pacific", and `allow` prompts can fire during an undo. **Nothing persists.** The log is an uncapped in-closure array, and refs are stable only while a component stays mounted ([agent.ts](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/agent/agent.ts#L37)). **Attribution leaks across `await`.** The history records a handler's change made after an `await` as `"programmatic"` unless the app wraps it in `withSource` ([history-and-undo.mdx](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/history-and-undo.mdx#L81-L101)).

The closest built-in to draft-then-commit is `stageChanges(agent, changes)`, which returns `{ applied, revert() }`, but it is not a true draft. Its source frames it as "an agent's suggestion shown on the real control while a person looks at it" ([stage.ts](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/history/stage.ts#L1-L102)). Because it writes to live controls, any `onValueChange` that saves to a server commits the "draft" at once. Its `applied` list trusts `result.ok`, which the docs admit "doesn't prove a controlled owner accepted the value". And `revert()` "attempts to restore the captured values even if the person has edited those controls since the preview", the opposite of `undoSource`'s conflict policy ([history-and-undo.mdx](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/apps/docs/content/docs/agents/connect-an-agent/history-and-undo.mdx#L115-L139)). UI SDK thus supplies the parts: source-tagged events, a source-filtered history, `describeEntry` for toast text such as "Agent set Region to Frankfurt", and `elementOf(ref)` for highlights. The Keep/Undo layer and the undo toast remain app work ([history.ts](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/history/history.ts#L83-L85); [observe.ts](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/packages/core/src/page/observe/observe.ts#L48-L61)).

## Only Yjs reverts one actor safely; patches drift and snapshots clobber

Undo libraries for client state use one of three mechanisms, and the mechanism decides whether one actor's edits can be undone alone. **Yjs** reverts by CRDT item IDs. An `UndoManager` captures a transaction only if its `origin` is in `trackedOrigins`, which defaults to `new Set([null])`, meaning local, untagged edits ([UndoManager.js v13.6.33](https://github.com/yjs/yjs/blob/v13.6.33/src/utils/UndoManager.js); [Yjs docs](https://docs.yjs.dev/api/undo-manager)). An app can wrap every agent write in `doc.transact(fn, agentOrigin)` and give the agent its own manager with `trackedOrigins: new Set([agentOrigin])`. The agent then gets its own undo stack, and an undo deletes only the items the agent inserted, so a human's interleaved characters survive. By default, the manager "will never overwrite remote changes". Changes inside `captureTimeout` (default **500 ms**) merge into one `StackItem`, and `stopCapturing()` forces a boundary, so an app can bracket one agent turn as one undo unit. Each `StackItem` also carries a `meta` map that can hold the turn ID for a label ([UndoManager.js](https://github.com/yjs/yjs/blob/v13.6.33/src/utils/UndoManager.js)). The stacks live in memory only. The two-manager pattern is my inference from the tracking rule, not a documented recipe.

**Patch-based tools** tag and group easily but drift under concurrency. Immer's `produceWithPatches` returns `[nextState, patches, inversePatches]`, and the docs name undo/redo as a use case ([Immer patches](https://github.com/immerjs/immer/blob/v11.2.10/website/docs/patches.mdx)). Immer promises correct patches only when they are applied "to an equal base object", and its array patches are positional, because `generateArrayPatches` compares index by index ([patches.ts](https://github.com/immerjs/immer/blob/v11.2.10/src/plugins/patches.ts)). If a human inserts a row after the agent's edit, the agent's inverse patches target stale indices. ngrx-wieder 17.0.0 brings Immer patches to NgRx Store. Its `mergeActionTypes`, `BREAK_MERGE` action and `segmentationOverride` (separate stacks per key) could route agent actions to their own stack, but the same index caveat applies ([ngrx-wieder README](https://github.com/nilsmehlhorn/ngrx-wieder/blob/master/README.md)). For ordinary state, mobx-state-tree's `UndoManager` comes nearest to Yjs. It offers `startGroup`/`stopGroup` and `withoutUndo`, and "Multiple concurrent processes only undo their own changes" ([mst-middlewares README](https://github.com/coolsoftwaretyler/mst-middlewares/blob/main/README.md)).

**Snapshot tools** cannot undo one actor at all. NgRx SignalStore's `watchState` exists because "undo/redo require tracking all SignalStore's state changes without coalescing" ([NgRx state tracking](https://github.com/ngrx/platform/blob/22.0.1/projects/www/src/app/pages/guide/signals/signal-store/state-tracking.md)). ngrx-toolkit's `withUndoRedo` 22.0.0 uses it to push a whole snapshot of the tracked keys on every change, with no origin, pause or group API. Its `maxStackSize` check tests `redoStack.length` right after the redo stack is emptied and then calls `unshift()` with no arguments, so the limit is never enforced. Its docs also import from the wrong package name, `@ngrx-toolkit/core` ([with-undo-redo.ts](https://github.com/angular-architects/ngrx-toolkit/blob/main/libs/ngrx-toolkit/src/lib/undo-redo/with-undo-redo.ts); [docs](https://github.com/angular-architects/ngrx-toolkit/blob/main/docs/docs/with-undo-redo.md)). redux-undo's `groupBy` can fold an agent run into one entry. zundo's `pause()` cannot, because changes made while paused are never recorded, so the state before the run is lost unless the app saves it. Either way, restoring a snapshot reverts everything since then ([zundo README](https://github.com/charkour/zundo/blob/main/README.md); [redux-undo README](https://github.com/omnidan/redux-undo/blob/master/README.md)).

**TanStack Query** solves a different problem: rolling back an optimistic write when the server says no. In the cache approach, `onMutate` snapshots the query data and writes the optimistic value, and `onError` restores the snapshot. In the UI approach, the app renders pending `variables`, and "the item will also disappear" on error, so "you don't need to handle rollbacks at all" ([TanStack optimistic updates, 5.108.0](https://github.com/TanStack/query/blob/%40tanstack/query-core%405.108.0/docs/framework/react/guides/optimistic-updates.md)). Because the snapshot rollback restores the whole key, a failed agent mutation would erase a human's concurrent optimistic item until the refetch repairs it. The app can prevent that by giving the mutations one `scope.id`, which runs them serially ([mutations guide](https://github.com/TanStack/query/blob/%40tanstack/query-core%405.108.0/docs/framework/react/guides/mutations.md)). Undoing a *successful* agent mutation needs a compensating mutation on the server, which TanStack Query does not provide.

| Library (version, Nov 2026) | Mechanism | Tag by actor | Undo one actor only | Group an agent turn |
|---|---|---|---|---|
| Yjs `UndoManager` 13.6.33 | Inverse ops on CRDT item IDs | `origin` + `trackedOrigins` | Yes, safe under interleaving | `captureTimeout`, `stopCapturing()`, `meta` |
| Immer 11.2.10 | Inverse patches | App metadata | Unsafe after overlapping array edits | Concatenate patches |
| ngrx-wieder 17.0.0 | Immer patches in a meta-reducer | Action type, segments | Partial (Immer caveat) | `mergeActionTypes`, `BREAK_MERGE` |
| MST `UndoManager` (mst-middlewares 6.1.0) | Patches per action | `withoutUndo` | Partial, documented for concurrent processes | `startGroup`/`stopGroup` |
| ngrx-toolkit `withUndoRedo` 22.0.0 | Snapshots via `watchState` | No | No | No |
| zundo 2.3.0, redux-undo 1.1.0 | Snapshots | Filter only | No | redux-undo `groupBy`; zundo `pause` drops the run from history |
| TanStack Query 5.108.0 | Snapshot rollback on error | `mutationKey`, `meta` | Rollback clobbers concurrent writes | `scope.id` serialises |

Two of these versions sit near the repo's one-week age rule: Immer 11.2.10 (2026-11-10) meets it, while TanStack Query 5.108.0 (2026-11-17) is too new, so code should pin 5.107.1, the newest release at least a week old ([npm immer](https://registry.npmjs.org/immer); [npm @tanstack/query-core](https://registry.npmjs.org/@tanstack/query-core)).

## Products pair a Keep/Undo working set with automatic checkpoints

Coding agents have converged on two independent layers. The first is **review state**. VS Code's working set, an experimental feature of its Copilot-harness sessions in the editor window, writes edits to disk but marks them pending: "Keep retains the changes and clears their pending-review state. Undo reverts them without rewinding the agent conversation." Keep and Undo work per change, per file or for all files, and staging an edit in Source Control keeps it. "Pending edits are already saved to disk", so tests run against them. Sessions on the Claude or Codex harness, in the Agents window or in the cloud get diffs to compare instead of Keep and Undo ([VS Code: review agent changes](https://code.visualstudio.com/docs/copilot/chat/review-code-edits)). Zed lets the user "accept or reject each individual change hunk, or the whole set" ([Zed Agent Panel](https://zed.dev/docs/ai/agent-panel.md)). Windsurf, whose docs now call it Devin Desktop, puts accept and reject controls on each hunk of its diff zones ([Windsurf advanced](https://docs.windsurf.com/windsurf/advanced)), and JetBrains Junie offers Rollback per file or for all files ([Junie help](https://www.jetbrains.com/help/ai-assistant/junie-agent.html)). Claude Code's VS Code extension in Manual mode shows the diff *before* writing it, with Accept or Reject per change, though "A diff with more than 100 changes opens without the per-change buttons" ([Claude Code VS Code](https://code.claude.com/docs/en/vs-code.md)).

The second layer is **time travel**, and its unit varies by product. Claude Code "captures the state of your code before each prompt", keeps file snapshots for the 100 most recent checkpoints in a session, and `/rewind` can restore code, conversation or both ([Claude Code checkpointing](https://code.claude.com/docs/en/checkpointing.md)). Cline snapshots more finely, "Every time Cline modifies a file or runs a command", in a shadow Git repo ([Cline checkpoints](https://docs.cline.bot/core-workflows/checkpoints.md)). Cursor's restore "reverts files only; it does not remove messages" ([Cursor Agent](https://cursor.com/docs/agent/overview.md)). Windsurf's Cascade page, now marked legacy, warns that "Reverts are currently irreversible" ([Windsurf Cascade](https://docs.windsurf.com/windsurf/cascade/cascade)). The vendors agree on the limit. VS Code checkpoints do not reverse "completed terminal commands, network requests, deployments, or changes that tools made to external services", and the docs tell users to "Use an external service's recovery controls". Claude Code's checkpoints skip files changed only by Bash and are "Not a replacement for version control" ([VS Code](https://code.visualstudio.com/docs/copilot/chat/review-code-edits); [Claude Code](https://code.claude.com/docs/en/checkpointing.md)).

Document tools lean on the host application's own undo. Google Sheets' Gemini shows an "Action preview card"; once the user clicks Apply, "the Settings and Undo buttons show", and Undo stays available "until you make further changes" ([Gemini in Sheets](https://support.google.com/docs/answer/14356410?hl=en)). Of the products surveyed, Sheets has the clearest preview-then-undo card. Excel's Copilot edit mode "edits your workbook directly", and to revert, Microsoft says "you can undo changes or view prior versions" ([Excel Copilot FAQ](https://support.microsoft.com/en-gb/office/frequently-asked-questions-about-agent-mode-in-excel-1cfd906d-40b4-46be-8e2d-65b893e28a02)). Word's rewrite flow, by contrast, shows the result first and lets the user choose Replace, Insert below or Regenerate ([Copilot in Word: edit and rewrite](https://support.microsoft.com/en-us/word/copilot/edit-rewrite-content)). For irreversible writes, Notion's agent asks for confirmation before Gmail actions such as sending ([Notion Agent](https://www.notion.com/help/notion-agent)). The undo-toast pattern descends from **Gmail's Undo Send**, which offers a 5, 10, 20 or 30 second cancellation window ([Gmail help](https://support.google.com/mail/answer/2819488?hl=en)). Undo Send works only because Gmail actually delays the send. A toast over an action that has already happened promises an undo it cannot deliver.

Design guidance backs the shift from confirm-first to apply-then-undo for reversible work. Nielsen advises "Do not use confirmation dialogs for routine actions", reserves them for "actions with serious consequences", and urges teams to "go to great lengths to provide undo" ([NN/g](https://www.nngroup.com/articles/confirmation-dialog/)). Microsoft's HAX pattern 9C says to "undo the AI system's actions" when the system "proactively and automatically alters the user's input" ([HAX 9C](https://www.microsoft.com/en-us/haxtoolkit/pattern/g9-c-undo-automated-actions/)). Cline argues, as a vendor, that "Checkpoints make auto-approve practical" ([Cline](https://docs.cline.bot/core-workflows/checkpoints.md)). Against this, people under-review AI output. Perry et al. found that participants with an AI assistant "wrote significantly less secure code" yet "were more likely to believe they wrote secure code" ([arXiv 2211.03622](https://arxiv.org/abs/2211.03622)). Undo must therefore stay available after Keep, not only before it. This research found no study comparing undo-first with confirm-first for agent actions, and no telemetry on how often users Keep or Undo.

## A recommended design: a tagged draft, inverse-op revert and gated side effects

The design that fits this evidence has five parts, and each maps onto a mechanism shown above. **First, give every write an actor and a turn ID.** In UI SDK, read `details.source` and wrap post-`await` handler writes in `withSource`. Because `details` has no turn ID, mint one around each `act()` call and keep it in app state. In Yjs, use a per-agent `origin` object and store the turn ID in `stackItem.meta`. In Immer or MST, put `{actor, turnId}` on each history entry.

**Second, make the draft real.** A true draft keeps agent edits from reaching persistence until Keep. In UI SDK, one option holds the agent's proposed values in a list outside the controls and writes each one only on Accept, as the experimental `suggestions.tsx` panel does. The other buffers changes whose source is `"agent"` in a pending store and flushes it on Keep. The panel still previews a suggestion by writing it to the live control with `stageChanges`, so a control that saves on change would save the preview ([suggestions.tsx](https://github.com/vercel-labs/ui/blob/63df19ae09452fb185d54275404da044f0addda2/examples/experiments/react/suggestions.tsx#L138-L165)). On the server side, the TanStack variables approach plays the same role, because pending agent mutations render independently and need no snapshot rollback.

**Third, list what changed, not what was asked for.** Build the Keep/Undo list from `steps[].changes`, `values` or history entries, never from the requested steps, because `ok: true` can hide a cancel. Show the list per field and per turn, as VS Code and Zed do per hunk.

**Fourth, revert by inverse operations that preserve later human edits.** Where the surface can be a CRDT, use Yjs with a separate agent `UndoManager`. Elsewhere, key agent-editable state by entity ID rather than array index, record each turn's patches as one entry, and refuse or warn on "undo agent turn" when a later human entry touched overlapping paths. In UI SDK, prefer `undoSource`'s keep-the-human policy over the overwrite in `stageChanges.revert()`, and run a fresh `createHistory` per turn so that `undoSource("agent")` means "this turn". Because restore writes arrive as `source: "agent"`, make sure the app's own cancel rules recognise them. Report every key that could not be restored rather than claiming success.

**Fifth, split actions by reversibility before they run.** Saves, sends, deletes and deployments sit outside every undo layer surveyed, UI SDK's history included. Gate them with `data-agent-confirm` or `allow`, or give them a real deferred commit with a visible countdown in Gmail's manner. Undoing them after the fact needs a compensating server operation. For coding surfaces, keep review state and checkpoints as separate records in the session event log, scope checkpoints to tool-tracked writes, and say that scope in the UI.

| Edit class | Before it lands | After it lands | Mechanism |
|---|---|---|---|
| Local, reversible field or document edits | Optional suggestion or draft | Keep/Undo per field, per turn, or all; undo stays available after Keep | Source-tagged history, Yjs per-origin `UndoManager`, ID-keyed patches |
| Multi-step agent turn | One turn ID | Revert the turn as a group and report partial failures | Fresh history per turn, or `stopCapturing()` brackets |
| Server mutation the agent triggers | Pending render (TanStack variables) | Compensating mutation | App-defined inverse endpoint |
| Irreversible external action | Confirmation, or a deferred commit with an undo toast | None | `allow`, `data-agent-confirm`, delayed send |

## A turn ID and an undo reason would make agent undo one query

The hard part of agent undo is behavioural as well as technical. Products offer auto-keep timers, as in VS Code's deprecated Local harness, and pitch auto-approve with checkpoints as a safety net, as Cline does. Meanwhile, the evidence on overreliance suggests that many users will never open the review. Two properties therefore matter more than the Keep button itself: whether undo still works after acceptance, and whether the system refuses to act irreversibly without a person.

Agent undo turns on who owns the revert and what happens to everyone else's edits when it runs. Libraries that keep later human edits (Yjs by item ID, UI SDK's `undoSource` by keeping later human values) make agent undo safe on shared surfaces. Snapshot stacks, which fit single-user editors, become a liability once an agent and a person edit the same state. UI SDK has the right primitive, source tagging on every change, but places its only veto before the write and has no per-turn grouping. The most valuable addition to it, or to our own harness, is a turn ID on every change event and a distinct `reason: "undo"` on restore writes. With those two fields, Keep/Undo lists, undo toasts and per-turn rewind become queries over one event log. Our next step is to build those two fields into the harness's event log and add three checks to the eval suite: undo after Keep, a refusal to act irreversibly without a person, and runnable two-manager Yjs and Immer stale-index tests that would turn this report's "safe" and "unsafe" verdicts into **[verified]** claims.
