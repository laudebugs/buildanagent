# Hashbrown turns components into typed model output

They cite the source at both commits, `hashbrown.dev/llms-full.txt`, the npm and NuGet registries and npm download counts, all fetched on 2026-11-18. Corrections are logged in [fact-check.md](fact-check.md#hashbrown-report-2026-11-18).
- **Verified:** every number, version, date, status and behavioural claim was re-read on 2026-11-18 against the v0.8.3 source, `llms-full.txt`, the npm registry, the NuGet registration index and the npm downloads API. Hashbrown (hashbrown.dev, `liveloveapp/hashbrown`) is an MIT-licensed, headless TypeScript framework from LiveLoveApp that lets a model compose an app's own React or Angular components. The model never writes code. Instead, it returns structured output that names trusted components and fills in their props. As of November 2026 the latest release is **0.8.3** (26 October 2026), and `main` already carries an unreleased 0.9.0. Hashbrown matters to this repository because it answers a question the [agent UI synthesis](agent-ui-research.md) left open: how to give a model control over layout without giving it a UI protocol or an iframe.

The framework has four parts: a framework-agnostic core, thin React and Angular bindings, six server-side provider adapters, and experimental in-browser model transports. The core holds a small Redux-style store, a hand-rolled schema language called Skillet, a streaming JSON parser and a QuickJS sandbox. The adapters (OpenAI, Azure, Anthropic, Bedrock, Google, Ollama) turn each vendor's streaming API into **AG-UI 1.0** events. Generative UI runs on one mechanism. Each exposed component compiles into a strict JSON Schema branch shaped `{ ComponentName: { props, children } }`, the provider's structured-output mode enforces that schema, and the browser parses the answer incrementally and renders only registered components. That mechanism puts hashbrown at the constrained end of the **declarative** tier of generative UI, beside A2UI and json-render. Its costs are youth and churn: every minor release from 0.6 to 0.8 broke the API, it has no MCP or A2UI support, and its npm downloads are about 1% of CopilotKit's. In this report, I trace hashbrown from its store to its server contract and place it among the agent UI libraries surveyed so far. I show that **its lasting idea is to use the provider's strict structured-output mode as the generative-UI safety boundary**, and that our harness should copy that idea rather than depend on the framework.

## Ten npm packages ship in lockstep, and every recent minor breaks the API

Hashbrown ships as ten npm packages that always share one version, from an Nx monorepo that also holds a .NET and a Python package. At v0.8.3 the repo's `packages/` folder holds `core`, `react`, `angular`, the six provider adapters and `typesafe` ([packages at v0.8.3](https://github.com/liveloveapp/hashbrown/tree/v0.8.3/packages)). `main` adds `dotnet` (the ASP.NET Core library) and the Python `pydantic-ai` package ([packages at `3da245d`](https://github.com/liveloveapp/hashbrown/tree/3da245d12d65a378095755b65448b5d9e985db47/packages)). All ten npm packages are at **0.8.3**, published **2026-10-26**, and Mike Ryan (`mikeryan52`) and Brian Love (`blove`) maintain them. The Writer adapter, `@hashbrownai/writer`, stopped at 0.5.0 when 0.6 removed it. Core has had **38 published versions** since its first publish on 2025-05-01 ([npm @hashbrownai/core](https://registry.npmjs.org/@hashbrownai/core); [npm @hashbrownai/writer](https://registry.npmjs.org/@hashbrownai/writer)). The README sorts the packages into three kinds. `@hashbrownai/core` holds the framework-agnostic primitives, Skillet and the streaming parser. `@hashbrownai/react` and `@hashbrownai/angular` hold hooks, resources and components, and each `@hashbrownai/<provider>` package is a Node adapter ([README](https://github.com/liveloveapp/hashbrown/blob/3da245d12d65a378095755b65448b5d9e985db47/README.md)).

The release history explains the present architecture, because each of the last three minors removed a layer the framework once owned. Hashbrown launched in June 2025 as a frontend LLM toolkit that encoded provider streams into its own binary frames ([launch post](https://github.com/liveloveapp/hashbrown/blob/3da245d12d65a378095755b65448b5d9e985db47/www/content/blog/2025-06-25-hashbrown-launch.md)). **v0.6** (23 September 2026) removed that frame transport ("servers must speak AG-UI"), moved model selection to the server, and dropped the adapters' `loadThread`/`saveThread` storage and the Writer provider. It also renamed `fryHashbrown` to `createChatRuntime` and `sizzle()` to `start()`. **v0.7** (8 October) moved to AG-UI 1.0 and began publishing one module per source file, which cut a CopilotKit renderer bundle "from 244 KB to 117 KB minified". **v0.8** (22 October) moved the run-input extension to `forwardedProps.hashbrown`, removed few-shot `<ui>` examples and the `prompt` template, and switched OpenAI and Azure to the Responses API, warning that "client and server must upgrade together" ([CHANGELOG v0.8.3](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/CHANGELOG.md)). The unreleased **0.9** renames "Magic Text" streaming Markdown to "prose" with "no deprecated exports" ([prose migration](https://hashbrown.dev/docs/react/migrations/prose)). Readers of the docs should know that hashbrown.dev renders `main`. Parts of it therefore describe 0.9 APIs that npm does not yet ship, such as `ProseRenderer` and the NuGet `0.1.0-preview.2` pairing ([.NET page](https://hashbrown.dev/docs/react/platform/dotnet)).

## A micro-NgRx store feeds a schema-driven render loop

### Chat state is a Redux clone exposed as signals

The core of hashbrown is a small in-house state container, not a model wrapper. `micro-ngrx.ts` describes itself as "a minimal Redux-like store". It has `dispatch`, `dispatchAndWait`, `select`, `when`/`whenOnce`, `createSignal`, `runEffects` and a trampoline scheduler, which shows the maintainers' NgRx lineage ([micro-ngrx.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/utils/micro-ngrx.ts)). `createChatRuntime()` builds a store from twelve reducers: `recovery`, `interrupts`, `agentState`, `agUiMessages`, `config`, `generationOwnership`, `messages`, `status`, `streamingMessage`, `toolCalls`, `tools` and `thread`. Effects such as `generate-message`, `tool-turn-coordinator`, `tool-turn-executor` and `logical-run-retry-policy` drive the run, and they start only after `start()` ([reducers](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/reducers/index.ts); [effects](https://github.com/liveloveapp/hashbrown/tree/v0.8.3/packages/core/src/effects); [chat-runtime.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/chat-runtime.ts)). The store keeps the canonical history as a list of **AG-UI messages** and projects them into view messages. v0.8 added a `role: 'activity'` variant for display-only AG-UI activity events.

The bindings only bridge the store's signals into each framework, so the store is the real product. The resulting `ChatRuntime` exposes read-only `StateSignal`s, among them `messages`, `error`, `isReceiving`, `isSending`, `isRunningToolCalls`, `isLoading`, `exhaustedRetries`, shared `state`/`setState`, `pendingInterrupts`/`resume()`, `recovery` and `lastRunResult`. Its options are `system`, `tools`, `responseSchema`, `debounce`, `retries`, `transport`, `ui` and `threadId`, and since v0.6 it has no `model` option ([chat-runtime.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/chat-runtime.ts)). React's `useHashbrownSignal` bridges each signal through `useSyncExternalStore` with deep-equality deduplication. Angular's `chatResource` converts each signal with `toNgSignal` and re-syncs options in an `effect()` ([use-hashbrown-signal.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/react/src/hooks/use-hashbrown-signal.ts); [chat-resource.fn.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/angular/src/resources/chat-resource.fn.ts)). On top sits a ladder of hooks with increasing structure. `useChat`, `useStructuredChat` and `useUiChat` handle conversations; `useCompletion`, `useStructuredCompletion` and `useUiCompletion` work on single inputs; and `useDecision`/`useUiDecision` pick among named options. Angular has a `*Resource` twin for each ([Choosing an API](https://hashbrown.dev/docs/react/start/overview)). Even `useUiChat` is a thin layer: it calls `useStructuredChat({ ...options, schema: ui, ui: true })` and adds a UI-kit renderer ([use-ui-chat.tsx](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/react/src/hooks/use-ui-chat.tsx)). A Vue or Svelte binding would therefore need only a signal bridge and a renderer. That last point is my inference, since no such binding is documented.

### Generative UI compiles components into an `anyOf` schema

The generative UI pipeline has four stages, and none of them lets the model emit code. **First**, the developer registers a component with `exposeComponent(Component, { name, description, props, children })`. `props` is a Skillet or Standard JSON Schema, and the docs say that a prop type that does not match the component "is a build error". `children` is `false` (flat), `'text'`, `'any'` (recursive) or an explicit list of allowed child components, and an optional `fallback` component renders while props are incomplete ([expose-component.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/ui/expose-component.ts); [Generative UI with React components](https://hashbrown.dev/docs/react/concept/components)). Angular's version takes `input` instead of `props` and derives the name with `reflectComponentType` ([Angular expose-component](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/angular/src/utils/expose-component.fn.ts)).

**Second**, `createComponentSchema` turns each component into `s.streaming.object(description, { [name]: { props: s.node(s.object(...)), children } })` and joins the catalog with `s.anyOf(...)`. `createUiKit` then wraps the result as `{ ui: s.streaming.array('List of elements', node) }` ([expose-component.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/ui/expose-component.ts); [ui-kit.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/ui/ui-kit.ts)). **Third**, the browser sends that schema to the server as `forwardedProps.hashbrown.responseSchema`, and the adapter maps it to the provider's strict structured output. For OpenAI, the adapter sets `text.format = { type: 'json_schema', strict: true }` on the Responses API ([openai-request.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/openai/src/stream/openai-request.ts)). The answer streams back as ordinary assistant text events.

**Fourth**, core parses the growing text with Cacheplane's streaming parser, resolves it against the schema and hands each assistant message a `ui` field. React's `renderUiNodes` looks up every tag in the registry and throws `Unknown element type` for an unregistered one. While a node's `props.value` is missing it renders the `fallback` (or nothing), and otherwise it calls `createElement(component, { ...props.value, children })` recursively ([ui-kit.helpers.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/react/src/hooks/ui-kit.helpers.ts); [use-ui-kit.tsx](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/react/src/hooks/use-ui-kit.tsx)). Angular renders through `*ngComponentOutlet` in `<hb-render-message>` ([render-message.component.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/angular/src/components/render-message.component.ts)).

The source shows a property the docs do not state: **a registered component never receives half-formed props**. Each component's `props` is a non-streaming `s.object`, and Skillet resolves a non-streaming value only once it has closed, so `props.value` stays empty until the whole props object has arrived ([base.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/schema/base.ts)). Streaming therefore comes from new sibling nodes appearing in the `s.streaming.array` and from `'text'` children, not from props filling in live. Partial props reach only the optional `fallback`, through its `partialProps`. This design is also the security story. The docs say "the model cannot inject component code or HTML", and add that "a component catalog constrains the interface the model can request; it does not authorize a refund, account change, or database write" ([llms-full.txt](https://hashbrown.dev/llms-full.txt)). Two practical features follow from the catalog design. `useUiChat` keeps every component it has ever offered in its render registry, so earlier answers still render after `setComponents` narrows the request schema. And `createUiJsonSchema()` (v0.7) exports a UI kit's schema for "an agent Hashbrown doesn't run (CopilotKit, LangGraph, your own server)" ([use-ui-chat.tsx](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/react/src/hooks/use-ui-chat.tsx); [CHANGELOG](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/CHANGELOG.md)).

### Skillet trades Zod's expressiveness for strict, streamable schemas

Skillet gives up most of Zod's vocabulary in exchange for schemas that strict decoding accepts and a parser can resolve mid-stream. Exported as `s`, it calls itself "an LLM-optimized streaming JSON Parser" ([base.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/schema/base.ts)). Its public surface is deliberately small: `string`, `number`, `integer`, `boolean`, `literal`, `enumeration`, `object`, `array`, `anyOf`, `nullish`, `node`, the `streaming.{string,object,array}` variants, and nine string formats ([public_api.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/schema/public_api.ts)). Each type implements four operations: `toJsonSchema`, `toTypeScript`, `validate` and `fromJsonAst`. The constructors for strings, numbers, integers, booleans, enumerations, objects and arrays, streaming variants included, also **require a description**, which becomes both a JSON Schema `description` the model reads and the name of any `$defs` entry. Schema authoring thus doubles as prompt engineering. (`literal`, `anyOf`, `node` and `nullish` take no description.)

`toJsonSchema` emits exactly what strict structured-output modes demand. All properties are required, `additionalProperties` is false, repeated nodes are hoisted into `$defs`, root recursion uses `$ref: '#'`, and a non-object root is wrapped in a `__wrappedPrimitive` object ([to-json-schema.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/schema/to-json-schema.ts)). The `streaming` flag is what Zod lacks. A streaming string resolves to its buffer while still open, a non-streaming value resolves only when complete, and `anyOf` returns the first branch that matches the partial AST ([base.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/schema/base.ts)). Zod and ArkType schemas enter only through the Standard JSON Schema `~standard.jsonSchema` converter (draft-07), and "unsupported keywords throw at runtime" ([standard-json-schema.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/schema/standard-json-schema.ts); [Tool calling](https://hashbrown.dev/docs/react/concept/functions)). Refinements and transforms therefore do not survive the conversion. I infer that from the code path; the docs do not say it. The parser itself, `@cacheplane/json-stream`, replaced hashbrown's own parser in v0.6, and it also works standalone with no model attached ([resolve-with-schema.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/utils/resolve-with-schema.ts); [Streaming JSON parser](https://hashbrown.dev/docs/react/recipes/json-parser)).

## The browser owns the loop, the tools and a QuickJS sandbox

### Client tools run in the browser between stateless server steps

Hashbrown splits the agent loop down the middle: the server runs one model step per request, and the browser runs the tools. A tool is a browser function, `useTool({ name, description, schema, handler, deps })` in React or `createTool` in Angular, whose JSON Schema travels in `RunAgentInput.tools` ([use-tool.tsx](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/react/src/hooks/use-tool.tsx)). When the model calls it, the AG-UI tool-call events stream back. The executor then parses the arguments (double-parsing stringified JSON if needed), validates them against the Skillet schema, and runs the batch concurrently with `Promise.all`, racing each handler against abort. An unknown name rejects with `Tool ${name} not found`. The coordinator settles the turn with `continue` or `stop` ([tool-turn-executor.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/effects/tool-turn-executor.ts); [tool-turn-coordinator.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/effects/tool-turn-coordinator.ts)). To continue, hashbrown "sends that result in a continuation request" ([Tool calling](https://hashbrown.dev/docs/react/concept/functions)). The server thus stays stateless, but every tool turn re-sends the whole transcript, since "Hashbrown supplies the complete canonical transcript on each run" ([llms-full.txt](https://hashbrown.dev/llms-full.txt)). Server-executed tools, such as provider web search or tools an agent framework runs, appear read-only on assistant messages as `serverToolCalls` with labels, outcomes, timing and sources ([CHANGELOG](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/CHANGELOG.md)).

Browser tools have **no approval gate**: a handler runs as soon as the model calls it. Human-in-the-loop follows AG-UI's terminating interrupt model instead. An agent ends its run with interrupts, the client reads `pendingInterrupts` and answers the whole batch with `resume()` in a new run. The docs insist that "a direct provider adapter does not add approval checkpoints", so a real AG-UI agent server must create and validate them ([Interrupt and resume](https://hashbrown.dev/docs/react/concept/interrupt-and-resume)). Interrupts and resume are present in the v0.8.3 runtime ([chat-runtime.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/chat-runtime.ts)). Without such a server, the docs model approval as application UI: a generated card is "a proposal", and the workbench enables **Accept plan** only after a completed response passes the app's own rules ([Generative UI with React components](https://hashbrown.dev/docs/react/concept/components)).

### The JavaScript runtime is isolated but thinly guarded

`createRuntime`/`useRuntime` is hashbrown's answer to "executing LLM-generated code in the browser", one of the problems its launch post named. Each `run()` dynamically imports `quickjs-emscripten-core` and an asyncify WASM build. It then creates a fresh runtime whose interrupt handler fires when the signal aborts or `performance.now()` passes the deadline, installs a minimal `Intl` proxy, attaches the registered host functions, evaluates the code and disposes the context ([create-runtime-impl.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/runtime/create-runtime-impl.ts)). Host functions are attached with `newAsyncifiedFunction`, so async handlers look synchronous to the guest, and every value crosses the boundary through `JSON.stringify`/`JSON.parse` ([attach-function-to-context.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/runtime/attach-function-to-context.ts)). `describe()` renders each host function as a TypeScript signature for the prompt, and `useToolJavaScript` wraps the whole runtime as a chat tool named `javascript` that takes a streaming `code` string ([use-tool-javascript.tsx](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/react/src/hooks/use-tool-javascript.tsx)). The guest has "no browser `window`, `document`, or `fetch`" ([JS runtime](https://hashbrown.dev/docs/react/concept/runtime)).

The docs state the runtime's limits plainly, and the source adds three discrepancies. Per the docs, a deadline "does not roll back a host side effect or impose a memory limit", and a function's schema "does **not automatically validate arguments or results**" ([JS runtime](https://hashbrown.dev/docs/react/concept/runtime)). In the source, first, the JSDoc states a default timeout of `10000` ms, but the code defaults to `1_000`. Second, the tool description tells the model it runs "in a stateful JavaScript environment", while each call actually gets a fresh context. That prompt invites the model to reuse variables that no longer exist. Third, the WASM variant is a *debug* asyncify build, instantiated again on every call, which likely costs latency; I infer that and did not measure it ([create-runtime-impl.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/runtime/create-runtime-impl.ts); [use-tool-javascript.tsx](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/react/src/hooks/use-tool-javascript.tsx)). The realistic risk is therefore an over-broad host function, whose handler runs outside the sandbox and unvalidated, rather than a WASM escape.

## AG-UI over SSE is the whole server contract

### The browser posts `RunAgentInput` and reads AG-UI events

Since v0.6 the wire format is standard AG-UI 1.0 over HTTP and SSE, plus one extension field. `HttpTransport` POSTs `JSON.stringify(RunAgentInput)` to `/run` by default with `Accept: text/event-stream`. It lets middleware rewrite the `RequestInit` (for example to add auth headers), and it rejects any response that is not an event stream. The one hashbrown-specific field is `forwardedProps.hashbrown = { responseSchema?, ui? }`, which uses "AG-UI's extension point for values an agent reads and intermediaries pass through untouched" ([http-transport.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/transport/http-transport.ts); [hashbrown-run-agent-input.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/transport/hashbrown-run-agent-input.ts)). Transports are pluggable through a `{ name, send(request) }` interface. The experimental `experimental_chrome`, `experimental_edge`, `experimental_local` and `experimental_webllm` transports run models inside the browser with "no automatic hosted fallback" ([transport.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/core/src/transport/transport.ts); [Local models](https://hashbrown.dev/docs/react/recipes/local-models)). Those transports are immature. In the maintainers' qualification snapshot, reviewed on 6 November 2026, Chrome's default Nano model passed a no-tool smoke test 6/6, but "tool-session creation failed".

A server is a short route. The sketch below is condensed from the React quickstart ([React quickstart](https://hashbrown.dev/docs/react/start/quick); [llms-full.txt](https://hashbrown.dev/llms-full.txt)):

```ts
app.post("/api/chat", express.json({ limit: "1mb" }), async (req, res) => {
  const controller = new AbortController();
  res.once("close", () => controller.abort());            // browser disconnect cancels the provider call
  const encoder = new EventEncoder();                      // from @ag-ui/encoder
  res.setHeader("Content-Type", encoder.getContentType());
  const stream = HashbrownOpenAI.stream.text({
    apiKey: process.env.OPENAI_API_KEY!,
    model: process.env.OPENAI_MODEL!,                      // the model lives on the server since v0.6
    input: req.body as RunAgentInput,
    signal: controller.signal,
  });
  for await (const event of stream) res.write(encoder.encodeSSE(event));
  res.end();
});
```

The client side is equally small. A `<HashbrownProvider url="/api/chat">` (React) points the hooks at the route, a `useUiChat` call supplies the system prompt, exposed components and tools, and the app renders `message.ui` for each assistant message ([README](https://github.com/liveloveapp/hashbrown/blob/3da245d12d65a378095755b65448b5d9e985db47/README.md); [Generative UI with React components](https://hashbrown.dev/docs/react/concept/components)).

That simplicity carries the framework's central security caveat: by default **the browser supplies the system prompt, the tool declarations and the response schema**. The quickstart route forwards `req.body` untouched, so an unprotected endpoint is an open relay for any prompt, tool list and schema. The docs say so plainly. The endpoint "is for local development", "request transformation is not authorization", and "browser-supplied schemas and tool declarations do not grant server permissions", and a dedicated recipe covers securing a public endpoint ([React quickstart](https://hashbrown.dev/docs/react/start/quick); [Securing a public endpoint](https://hashbrown.dev/docs/react/recipes/public-endpoint); [llms-full.txt](https://hashbrown.dev/llms-full.txt)). Hashbrown itself enforces nothing on the server. Pinning the schema (for example with v0.8's `markdownComponent`) and allowlisting tools are the app's job.

### Six adapters map vendor APIs onto one event stream

Every adapter has the same shape, `Hashbrown<Provider>.stream.text({ ..., input: RunAgentInput, signal })`, which returns `AsyncIterable<AGUIEvent>` and accepts a `transformRequestOptions` hook. The docs warn that "an adapter does not add a missing model capability" ([Platforms](https://hashbrown.dev/docs/react/start/platforms); [Request transformation](https://hashbrown.dev/docs/react/concept/transform-request-options)). The adapters differ in which native features they map:

- **OpenAI and Azure** build stateless Responses API requests (`store: false`), so "an OpenAI-compatible Chat Completions endpoint alone is not enough". They map client tools to `strict: true` functions and replay encrypted reasoning statelessly ([openai-request.ts](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/packages/openai/src/stream/openai-request.ts); [CHANGELOG](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/CHANGELOG.md)).
- **Anthropic** uses the streaming Messages API. It maps thinking and redacted thinking to AG-UI reasoning, passes unsupported native events through as `RAW`, and exposes server-side web search, fetch and code execution ([Anthropic](https://hashbrown.dev/docs/react/platform/anthropic)).
- **Bedrock** maps to ConverseStream, with Nova web grounding ([Bedrock](https://hashbrown.dev/docs/react/platform/bedrock)).
- **Google** accepts either a Gemini API key or Vertex AI with Application Default Credentials ([Google](https://hashbrown.dev/docs/react/platform/google)).
- **Ollama** is only partly qualified. In the maintainers' own run with `qwen2.5:14b`, it passed **7/10** provider cases and **12/20** framework cases, and "schema-plus-tools cases omitted required lookups" ([Ollama](https://hashbrown.dev/docs/react/platform/ollama)).

Since v0.8 all six adapters report a normalized `lastRunFinishReason` and `lastRunUsage` ([CHANGELOG](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/CHANGELOG.md)).

Because the contract is just AG-UI, the six adapters are a convenience, not the boundary: any AG-UI server can drive a hashbrown front end. The project publishes versioned, "partial" qualifications at that boundary across ten capability families ([Framework compatibility](https://hashbrown.dev/docs/react/platform/compatibility)). As of November 2026, three frameworks had qualified profiles. LangGraph (`@ag-ui/langgraph` 0.0.45) and Mastra (`@ag-ui/mastra` 2.0.1) were last qualified on 30 October 2026, and two Pydantic AI ASGI profiles on 31 October and 3 November. Broader Pydantic AI coverage and eight other candidates remain `not-tested`. They include Google ADK, CrewAI, Microsoft Agent Framework and the Vercel AI SDK, whose entry reads "Bridge/transport investigation required". Plain chat and tool display work against any AG-UI server. Generative UI and structured output also need the agent to honor `forwardedProps.hashbrown` or to adopt the schema from `createUiJsonSchema()`, which I infer from the contract. The .NET path uses .NET 10, Microsoft Agent Framework and the upstream AG-UI SDK ([.NET](https://hashbrown.dev/docs/react/platform/dotnet)). Durable recovery comes from a separate product, b4.run, backed by Postgres ([b4.run](https://hashbrown.dev/docs/react/platform/b4run)).

### Hashbrown implements AG-UI fully, but not MCP or A2UI

Hashbrown uses AG-UI end to end: run input, text and tool events, `REASONING_*`, shared state, interrupts, `ACTIVITY_*` and, in 0.9, subagent child runs ([CHANGELOG](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/CHANGELOG.md); [main CHANGELOG](https://github.com/liveloveapp/hashbrown/blob/3da245d12d65a378095755b65448b5d9e985db47/CHANGELOG.md)). It implements none of the other protocols this space has converged on. The README still says of client tools, "Connect MCP servers too". Yet no file in `packages/*/src` at v0.8.3 mentions MCP, `llms-full.txt` never uses the word, and MCP appears only in changelog entries from 0.3.0 to the 0.5.0 betas. The README claim is therefore stale. MCP tools must be bridged by a server-side agent (as `serverToolCalls`) or hand-wrapped as `useTool`s ([README](https://github.com/liveloveapp/hashbrown/blob/3da245d12d65a378095755b65448b5d9e985db47/README.md); [packages](https://github.com/liveloveapp/hashbrown/tree/v0.8.3/packages)). A2UI appears only in a .NET recipe, which states that "A2UI surfaces… do not replace Hashbrown's text-JSON output contract", and the docs never mention MCP Apps ([llms-full.txt](https://hashbrown.dev/llms-full.txt)).

### Persistence is left to the app

Hashbrown keeps no conversation state of its own. A `threadId` "does not save messages or create a durable checkpoint", and the threads recipe's storage helper "is not a Hashbrown storage API". Stream reconnect is `not-tested` in the compatibility matrix ([How Hashbrown works](https://hashbrown.dev/docs/react/start/how-it-works); [Persist and resume threads](https://hashbrown.dev/docs/react/recipes/threads); [Framework compatibility](https://hashbrown.dev/docs/react/platform/compatibility)). Persistence, durable approvals and stream rejoin thus belong to the app or to an AG-UI agent server.

## Hashbrown occupies the declarative tier's trusted-component corner

Generative UI comes in three tiers that differ in how much the model controls, and hashbrown sits low in the middle one. In the **controlled** tier, the app maps a tool result to a pre-built component, which is how the AI SDK defines generative UI: "connecting the results of a tool call to a React component" ([AI SDK generative UI](https://ai-sdk.dev/docs/ai-sdk-ui/generative-user-interfaces)). In the **declarative** tier, the model composes a validated spec from a catalog. In the **open-ended** tier, the model ships HTML into a sandbox. CopilotKit's docs name the same three levels ([CopilotKit generative UI overview](https://docs.copilotkit.ai/concepts/generative-ui-overview.md)). Hashbrown sits one notch above the controlled tier, because the *final answer itself* is a nested component tree and the model chooses the layout. It reaches the open-ended tier only for computation, through the QuickJS tool, whose results are data, never markup.

Hashbrown stops short of A2UI in four ways, all my inference from the sources above. First, its catalog is the app's own framework components, not a cross-platform standard catalog. Second, the spec is the model's structured-output response, not a separate agent-to-UI message stream such as A2UI's `createSurface`/`updateDataModel` ([A2UI v1.0 spec](https://a2ui.org/specification/v1.0-a2ui/)). Third, it has no separate data model or bindings. Fourth, its format is not a published, renderer-neutral spec. Its nearest relative is Vercel Labs' json-render, whose rule is that "AI can only use components in your catalog" ([json-render README](https://raw.githubusercontent.com/vercel-labs/json-render/main/README.md)). Hashbrown differs by generating the schema from typed components and enforcing it through provider-side strict decoding.

Against **CopilotKit**, hashbrown is the narrower, lighter AG-UI client. Both speak AG-UI. CopilotKit adds prebuilt chat, A2UI and MCP Apps renderers, sandboxed HTML, and the split between `useHumanInTheLoop` and `useInterrupt`. Hashbrown instead offers browser-run tools without an agent framework, adapters that call providers directly, typed partial-JSON streaming and an Angular-native API. The two can also combine, since `createUiJsonSchema()` exists so that CopilotKit or LangGraph agents can emit hashbrown UI kits ([CHANGELOG](https://github.com/liveloveapp/hashbrown/blob/v0.8.3/CHANGELOG.md)).

Against the other libraries, hashbrown gives up state machinery to let the model choose components. Unlike **assistant-ui**, it has no thread model with branching or edit-and-regenerate, and it leaves persistence to the app. Compared with **AI SDK UI**, it trades the `UIMessage.parts` state machine, the in-stream `tool-approval-request` and `resumeStream` for terminating AG-UI interrupts and no stream rejoin. In return, the model, not a tool-to-component map, chooses the component. **Vercel Labs' UI SDK** complements hashbrown rather than competing with it. UI SDK provides accessible behaviors and a permissioned bridge that lets agents *operate* an existing UI through `snapshot`/`act`/`query`, while hashbrown lets a model *choose* which trusted components to show. A hashbrown catalog built from UI SDK primitives could therefore answer the accessibility question that model-composed UI leaves open. That pairing is my inference; neither project mentions the other.

Adoption is the weakest part of the case. From 18 October to 17 November 2026, `@hashbrownai/core` had **27,075** npm downloads against **2,873,035** for `@copilotkit/react-core`, about **0.9%** ([npm downloads: hashbrown](https://api.npmjs.org/downloads/point/2026-10-18:2026-11-17/@hashbrownai/core); [npm downloads: CopilotKit](https://api.npmjs.org/downloads/point/2026-10-18:2026-11-17/@copilotkit/react-core)). Angular downloads (16,105) exceed React's (9,989) by about 60%, which suggests that hashbrown's real niche is Angular, where generative-UI options are scarce ([npm downloads: angular](https://api.npmjs.org/downloads/point/2026-10-18:2026-11-17/@hashbrownai/angular); [npm downloads: react](https://api.npmjs.org/downloads/point/2026-10-18:2026-11-17/@hashbrownai/react)). No independent production case study turned up. The showcase is the maintainers' own `atc` app, an air-traffic assistant built in both Angular and React on one framework-free core ([building-atc post](https://github.com/liveloveapp/hashbrown/blob/3da245d12d65a378095755b65448b5d9e985db47/www/content/blog/2026-10-10-building-atc.md)). GitHub star and contributor counts could not be collected, and no head-to-head benchmark of bundle size, latency or render failure rates against CopilotKit, A2UI renderers or the AI SDK exists.

## Strict structured output can be the generative-UI boundary

Hashbrown's lasting contribution is to show that **the provider's strict structured-output mode can serve as the generative-UI safety boundary**. The recipe has three steps: generate a JSON Schema from typed, trusted components, let constrained decoding guarantee the shape, and stream-parse the answer against that same schema. In the common case where an app renders its own components, this recipe removes the need for a separate UI protocol such as A2UI, or for iframes. Its price is a UI contract private to hashbrown and tied to providers that support strict JSON Schema, which is why `createUiJsonSchema` exists for agents hashbrown does not run. Constrained decoding also guarantees only the shape, not the judgment, as Ollama's weak qualification numbers show. The second lesson concerns layering. Hashbrown dropped its own transport for AG-UI in a single minor release and kept persistence, durable approvals and stream rejoin out of the framework. Its history is evidence that AG-UI is becoming the default UI runtime protocol and that the hard state belongs on the server.

For this repository's harness, the conclusions are specific. Hashbrown's approach is a strong default for the declarative-tier generative UI that the [agent UI synthesis](agent-ui-research.md) recommends: a server-pinned UI schema, generated from a typed component catalog, emitted as structured output and carried over AG-UI. Our harness should therefore emit AG-UI-compatible events and honor a `forwardedProps`-style schema extension, but pin schemas and tools on the server instead of trusting the browser as hashbrown's default route does. We should also copy Skillet's two best ideas into our own schema tooling: mandatory descriptions and per-node streaming flags. Hashbrown itself is too young to depend on, with a breaking minor about every two weeks since September 2026, no MCP, and docs that run ahead of npm. Any adoption should pin exact versions and upgrade client and server together.
