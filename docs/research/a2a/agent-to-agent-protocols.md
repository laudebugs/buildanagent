# A2A 1.0 standardizes handing a task to an agent we cannot see inside, and our agents should use it only across an ownership boundary

Section T37 of the book must teach agent-to-agent protocols, but our repository mentions A2A only in passing: no plan, decision or todo outside the book uses it ([our-plans notes](notes/our-plans.md)). The protocol has matured faster than our plans. A2A 1.0.0 was tagged on 12 March 2026, and in August 2026 the project joined the Agentic AI Foundation beside MCP ([releases](https://github.com/a2aproject/A2A/releases); [AAIF proposal #37](https://github.com/aaif/project-proposals/issues/37)). Yet the SDKs we use lag behind. Of our eight SDKs, only Google ADK ships A2A in its released TypeScript package, and ADK still speaks protocol 0.3, which a 1.0-only server must reject ([SDK notes](notes/sdk-support.md)).

Five findings answer the research question, with every version and status as of November 2026. First, A2A 1.0 standardizes an Agent Card for discovery, eleven operations over three bindings, and a `Task` with nine states that can stream, call back and pause for input or authorization. It leaves identity, registries and prompt injection to the implementer. Second, MCP 2026-07-28 gave tools the same long-running, pausable shape through its tasks extension and `input_required`, so the line between the two protocols is who plans the work, not how long it takes. Third, in TypeScript only ADK ships both roles, on 0.3, while the official `@a2a-js/sdk` 1.3.0 speaks 1.0 and can talk to 0.3 peers; four other SDKs have A2A work only outside their released packages. Fourth, an agent should call another agent over A2A only when someone else owns that agent and its plan, and expose one only when an outside caller needs to delegate to it; inside one codebase, a function, a tool or an in-process subagent is cheaper. Fifth, a remote agent's card and replies are untrusted input, as 2026's measurements of card manipulation, name collisions and unchecked peer claims show. This report traces each finding to its sources, then turns them into what Section T37 should teach, one recommended example and seven proposed plan changes. Its thesis is that A2A is the standard way to hand a task to an agent we neither own nor can see inside, and that our agents should use it only across that ownership boundary, treating every card and reply as untrusted.

## Eleven terms are used one way throughout

An **agent** here is a program that runs a model in a loop with tools. An **A2A client** sends A2A requests, and an **A2A server**, or **remote agent**, answers them; one agent can be both, and either side calls the other its **peer**. **Calling** an agent means acting as its client, and **exposing** an agent means serving it over A2A. The **Agent Card** is the JSON document in which a server describes itself. A **task** is A2A's server-owned unit of work, and an **artifact** is a task's output. An **in-process subagent** is a child agent that runs inside the caller's own harness, as Chapter T17's example will show. An SDK **ships** a feature when its released npm package contains it; branches, examples and hosted services do not count. One name clash needs a warning: the ACP that merged into A2A in August 2025 is IBM's Agent Communication Protocol, not the Agent Client Protocol that the Strands CLI speaks ([ecosystem notes](notes/ecosystem-and-papers.md#1-governance-and-history); [Strands report](../external-designs/strands-harness-sdk.md)).

## A2A 1.0 standardizes the task, the Agent Card and three bindings, and leaves identity, registries and prompt injection to the implementer

**A2A 1.0.0 is a released standard under multi-vendor governance, and its 1.0.1 patch changes no protocol behaviour.** The Linux Foundation's `a2aproject/A2A` repository tagged v1.0.0 on 12 March 2026 and v1.0.1 on 28 May 2026, the latest release as of November 2026 ([releases](https://github.com/a2aproject/A2A/releases)). The text at the v1.0.0 tag still calls itself "Release Candidate v1.0" and names 0.3.0 as the latest release; the v1.0.1 text corrects both ([spec at v1.0.0](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/specification.md), lines 1 and 3; [spec at v1.0.1](https://github.com/a2aproject/A2A/blob/v1.0.1/docs/specification.md)). The patch prefers the `application/a2a+json` media type, remaps several HTTP error codes and spells task states in full. Because "Patch version numbers … do not affect protocol compatibility", both tags define protocol version 1.0 ([spec v1.0.0 §3.6](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/specification.md#36-versioning)). An eight-seat Technical Steering Committee governs the project, with seats held by Google, Microsoft, Cisco, AWS, Salesforce, ServiceNow, SAP and IBM Research ([GOVERNANCE.md at v1.0.1](https://github.com/a2aproject/A2A/blob/v1.0.1/GOVERNANCE.md)).

**The specification has three layers, and only the bottom one changes from transport to transport.** A protocol-neutral data model comes first, written in Protocol Buffers; `a2a.proto` is "the single authoritative normative definition of all protocol data objects" ([spec §1.3–1.4](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/specification.md#13-specification-structure)). Above it sit eleven abstract operations, the RPCs of the proto's `A2AService`: send a message, send a streaming message, get, list, cancel and subscribe to a task, four push-notification calls, and get the extended Agent Card ([a2a.proto at v1.0.0](https://github.com/a2aproject/A2A/blob/v1.0.0/specification/a2a.proto), lines 19–131). Three official bindings map those operations onto JSON-RPC 2.0 with Server-Sent Events, gRPC, and HTTP+JSON/REST. An agent that offers more than one binding must give them "Identical Functionality", the same errors and the same authentication ([spec §5.1, §5.3, §9.1](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/specification.md#5-protocol-binding-requirements-and-interoperability)).

**Five objects carry every exchange, and the `Task` is the one that makes A2A more than a remote function call.** A client sends a `Message` with the role user, made of `Part`s. Each part holds text, raw bytes, a URL or a JSON value, together with an optional media type and filename ([a2a.proto](https://github.com/a2aproject/A2A/blob/v1.0.0/specification/a2a.proto), lines 224–252). The server answers either with a direct `Message`, "for simple interactions that don't require task tracking", or with a `Task` whose ID the server generates ([spec §3.1.1, §3.4.2](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/specification.md#311-send-message)). A task moves through nine states. Four are terminal (completed, failed, canceled and rejected), and two are interrupted (input required and auth required), so a remote agent can pause and ask its caller for something ([a2a.proto](https://github.com/a2aproject/A2A/blob/v1.0.0/specification/a2a.proto), lines 187–208). Results belong in `Artifact`s, because "Messages SHOULD NOT be used to deliver task outputs" and "MUST NOT be considered a reliable delivery mechanism for critical information" ([spec §3.7](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/specification.md#37-messages-and-artifacts)). A `contextId` groups related tasks into one conversation, and the spec lets agents expire contexts as long as they document the policy ([spec §3.4.1](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/specification.md#341-context-identifier-semantics)).

**A caller can wait, poll, stream or be called back, so one protocol covers seconds-long and days-long work.** `SendMessage` blocks by default until the task ends or is interrupted, and `return_immediately: true` hands back the task at once ([spec §3.2.2](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/specification.md#322-sendmessageconfiguration)). A blocked or returned task can then be polled with `GetTask`, followed over a stream that "MUST begin with the Task object" and closes at a terminal state, or reported to a webhook by HTTP POST ([spec §3.1.2, §3.5.1](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/specification.md#351-overview-of-update-mechanisms)). Webhook delivery is at least once, and clients "SHOULD process notifications idempotently, as duplicate deliveries may occur" ([spec §4.3.3](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/specification.md#433-push-notification-payload)). For more input, the caller sends a new message with the same `taskId` and `contextId` ([spec §3.4.3](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/specification.md#343-multi-turn-conversation-patterns)). Authorization can chain the same way: an agent that is itself serving a task may pass an auth-required request up to its own caller, "forming a chain of Tasks" ([spec §7.6.2](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/specification.md#762-in-task-authorization-client-responsibilities)).

**The Agent Card tells a caller what a remote agent offers and how to reach it, and 1.0 moved the protocol version into each interface.** Every A2A server "MUST make an Agent Card available", usually at `https://{server_domain}/.well-known/agent-card.json` ([spec §8.1–8.2](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/specification.md#8-agent-discovery-the-agent-card)). The card's required fields name, describe and version the agent, list its skills, input and output modes and capabilities, and give one or more `supportedInterfaces`, each with a URL, a binding and a `Major.Minor` protocol version ([a2a.proto](https://github.com/a2aproject/A2A/blob/v1.0.0/specification/a2a.proto), lines 336–393). Clients send an `A2A-Version` header, and a server "MUST interpret empty value as 0.3 version", so one server can serve 0.3 and 1.0 clients from separate interfaces ([spec §3.6](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/specification.md#36-versioning)). Version 1.0 broke the 0.3 wire format in several places. It renamed `message/send` to `SendMessage`, replaced kebab-case enums with `TASK_STATE_*` names, removed the `kind` discriminator and moved the card's `url` and `protocolVersion` into `supportedInterfaces` ([What's new in v1.0](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/whats-new-v1.md)). A server with no 0.3 interface must answer a 0.3 client with `VersionNotSupportedError`, so the two cannot work together without an upgrade on one side ([spec §3.6.2](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/specification.md#362-server-responsibilities)).

**Identity, discovery registries and prompt injection stay outside the standard, and those gaps are where an implementer's work lies.** For identity, A2A relies on "established web security practices". A card declares schemes (API key, HTTP auth, OAuth 2.0, OpenID Connect or mutual TLS), the client obtains credentials "out-of-band", and the server must authenticate every request and scope every task query to the caller before it touches storage ([spec §4.5, §7, §13.1](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/specification.md#7-authentication-and-authorization)). Cards "MAY be digitally signed" with JWS over a JCS-canonicalized body, and clients "SHOULD verify at least one signature before trusting an Agent Card" ([spec §8.4](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/specification.md#84-agent-card-signing)). Discovery beyond the well-known URL is left open: "The current A2A specification does not prescribe a standard API for curated registries" ([agent discovery](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/topics/agent-discovery.md)). Injection gets one generic line, "Implementations MUST sanitize user-provided content to prevent injection attacks", in the media-type registration ([spec §14.1](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/specification.md#141-media-type-registration)). The word "prompt" never appears in the spec, so nothing in it addresses a remote agent's reply steering the model that called it.

## MCP hands an agent tools to drive, and A2A hands it peers that plan for themselves

**Both protocols now live in one foundation, and the A2A side describes them as layers of one stack.** The Linux Foundation formed the Agentic AI Foundation (AAIF) on 9 December 2025 with MCP among its founding projects ([LF press release](https://www.linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation)). A2A joined it as a Growth Stage project: the proposal closed as approved on 4 August 2026, and AAIF announced the move on 17 August, saying A2A is "backed by over 150 organizations" ([AAIF proposal #37](https://github.com/aaif/project-proposals/issues/37); [AAIF blog](https://aaif.io/blog/a2a-joins-aaif)). A2A's 1.0 announcement sums up the split as "MCP inside agents, A2A between agents" ([announcing 1.0, 2026-03-12](https://github.com/a2aproject/A2A/blob/5f931b8a25fe66789f987ec4a55fc16ee9fe41ee/docs/blog/posts/announcing-1.0.md)). Its current topic page calls MCP "vertical", because "It deepens a single agent", and A2A "horizontal", because "It connects agents across that boundary" to another team, department or partner ([A2A and MCP](https://a2a-protocol.org/latest/topics/a2a-and-mcp/)). The framing comes from one side only. We found no mention of A2A in MCP's specification repository at tag 2026-07-28, in its `llms-full.txt` or on its blog ([ecosystem notes](notes/ecosystem-and-papers.md#2-the-mcp-side)).

**MCP 2026-07-28 gave tools the long-running, pausable shape that once set A2A apart, so duration no longer separates the two.** The revision moved tasks out of the core protocol into an official extension, `io.modelcontextprotocol/tasks`, with polling through `tasks/get` and client input through `tasks/update`. It also replaced server-initiated requests with Multi Round-Trip Requests, in which a server returns `resultType: "input_required"` and the client retries with the answers ([MCP 2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog), major changes 6 and 7). MCP's own tasks proposal cites agents talking to agents: in one of Amazon's internal multi-agent systems, "When agents communicate through MCP, slow agents cause cascading delays" ([SEP-1686](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/2026-07-28/seps/1686-tasks.md)). MCP also moved away from servers that act as agents. Sampling, which "allows servers to implement agentic behaviors" by calling the client's model, is deprecated, and "New implementations **SHOULD NOT** adopt it" ([MCP 2026-07-28 sampling](https://modelcontextprotocol.io/specification/2026-07-28/client/sampling)). As of November 2026, then, an MCP tool call and an A2A task can both run for hours and both stop to ask for input.

**The difference that remains is who plans the work, and it decides which protocol fits.** In MCP the calling model picks a named tool, fills its input schema and receives the result; the planning stays with the caller. In A2A the caller sends a message in prose or data parts, and the remote agent decides how to do the work, keeps its own context and returns artifacts. Its internals stay hidden, because agents collaborate "without needing to share their internal thoughts, plans, or tool implementations" ([spec §1.2](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/specification.md#12-guiding-principles)). The Agent Card advertises skills as prose with tags and examples, not as input schemas ([a2a.proto](https://github.com/a2aproject/A2A/blob/v1.0.0/specification/a2a.proto), lines 430–447). The A2A project draws the same line, defining tools as "primitives with well-defined, structured inputs and outputs" and agents as systems that "reason, plan, use multiple tools, maintain state" ([A2A and MCP at v1.0.0](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/topics/a2a-and-mcp.md)). Our rule follows from that line. When the caller knows the inputs a capability needs, the capability is a tool and belongs behind MCP or a function. When the caller can state only the goal, and someone else owns the plan, the capability is an agent and belongs behind A2A.

**To the calling model, a remote A2A agent still looks like a tool, because every framework that consumes A2A wraps it as one.** Google ADK says that once the connection is set up, "interacting with the remote agent feels just like interacting with a local tool or function" ([ADK A2A intro](../../reference/google-adk/source/adk-docs/docs/a2a/intro.md), line 85). Microsoft Agent Framework offers a `get_a2a_tool` factory, and Microsoft Foundry Agent Service has an `a2a` tool type, generally available for A2A 1.0 as of November 2026 ([Agent Framework, A2A agent](https://learn.microsoft.com/en-us/agent-framework/integrations/by-component/agent-services/a2a); [Foundry, A2A tool](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/agent-to-agent)). In our design reading of the two specs, the task lifecycle therefore lands in the harness, not in the model. Our harness would have to hold a call open across `TASK_STATE_INPUT_REQUIRED` and `TASK_STATE_AUTH_REQUIRED`, as it must hold an MCP `tools/call` open across `input_required`. Microsoft adds the rule that follows from opacity: "Treat responses from the remote agent as untrusted application input" ([Agent Framework, A2A agent](https://learn.microsoft.com/en-us/agent-framework/integrations/by-component/agent-services/a2a)).

## Call another agent over A2A only when someone else owns it, and expose one only when an outside caller needs it

**Delegation must pay for itself before any protocol matters, and the evidence says it pays only on broad, parallel work.** Anthropic's multi-agent research system beat a single Opus 4 agent "by 90.2% on our internal research eval", but multi-agent systems used "about 15× more tokens than chats" (vendor, [Anthropic, multi-agent research system](https://www.anthropic.com/research/multi-agent-research-system), June 2025). Anthropic's January 2026 guidance names "three situations where multiple agents consistently outperform a single agent": context pollution, parallel tasks and specialization. Outside them, "the coordination costs typically exceed the benefits", at "3-10x more tokens" (vendor, [Claude blog, when to use multi-agent systems](https://claude.com/resources/articles/building-multi-agent-systems-when-and-how-to-use-them)). Kim et al. measured 260 configurations, and multi-agent results ranged "from +80.8% on decomposable financial reasoning to -70.0% on sequential planning". Tasks on which a single agent already "exceeds 45% accuracy experience negative returns from additional agents" ([arXiv 2512.08296v3](https://arxiv.org/abs/2512.08296)). With reasoning tokens held equal, single agents "consistently match or outperform" multi-agent systems on multi-hop reasoning ([arXiv 2604.02460v2](https://arxiv.org/abs/2604.02460)). Our agent guide already asks the right question last: is the work "broad, parallel, too large for one context and valuable enough to pay for it? Only then consider subagents" ([agent guide](../../guides/agent.md)).

**Once delegation pays, ownership decides between an in-process subagent and A2A, while network cost barely enters.** Google ADK's guidance lists four cases for A2A: the other agent is "a separate, standalone service", it "is maintained by a different team or organization", it is written in "different programming languages or agent frameworks", or the system needs "a strong, formal contract". The same page prefers local sub-agents for internal code, for low-latency work, for shared memory and for "Simple Helper Functions" ([ADK A2A intro](../../reference/google-adk/source/adk-docs/docs/a2a/intro.md), lines 20–62). The hop itself costs little next to a model call. A 2026 benchmark found a lighter protocol "8.4-9.6x faster than the baseline A2A SDK implementation" for bare coordination. Yet "where LLM inference dominates, the protocols are near parity", with the gap coming from connection setup ([arXiv 2610.04053v1](https://arxiv.org/abs/2610.04053)). The reasons to avoid A2A inside one codebase are therefore the ones ADK gives, shared context and simplicity, rather than speed.

**Five rules, ordered from cheapest to most costly, settle when our agents should call or expose another agent; the order is our synthesis.**
1. **A function or workflow step** when code can do the work, because "If you can write a function to handle the task, do that instead of using an AI agent" ([Microsoft Agent Framework overview](https://learn.microsoft.com/en-us/agent-framework/overview/)).
2. **A tool**, over MCP when someone else hosts it, when the caller knows the inputs the capability needs.
3. **An in-process subagent** when we own the agent and want a separate context or parallel branches, as Chapter T17's example will show ([T42](../../todos/done/T42-example-subagent.md)).
4. **An A2A client call** when another team, organization or framework owns the agent, its plan and tools stay hidden from us, and the task may run long or pause for input.
5. **An A2A server** only when an outside caller needs to delegate to our agent. Such callers already exist in hosted products: Gemini Enterprise can register A2A agents (in preview), Foundry Agent Service calls them through its `a2a` tool, and Bedrock AgentCore Runtime hosts A2A servers ([Gemini Enterprise](https://docs.cloud.google.com/gemini/enterprise/docs/register-and-manage-an-a2a-agent); [Foundry](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/agent-to-agent); [AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-a2a.html)).

**Exposing an agent costs more than calling one, because the server carries the spec's duties and the work the spec leaves open.** The spec requires a server to publish and version a card, authenticate every request, and scope every task operation to the caller "before any database queries" ([spec §13.1](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/specification.md#131-data-access-and-authorization-scoping)). The spec requires no durable task store, but we infer that a server needs one if a webhook or a later `GetTask` is to find a task after a restart. If it offers push notifications, it should validate webhook URLs against server-side request forgery, rejecting private ranges such as 10.0.0.0/8 ([spec §13.2](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/specification.md#132-push-notification-security)). On our agent platform, which serves many users, every one of these duties is a tenant-isolation duty as well ([ADR 0037](../../decisions/0037-multi-user-agent-platform.md)). The coding agent, which serves one owner, has no outside caller yet, so rule 5 gives it no reason to expose anything.

## One of our eight SDKs ships A2A in TypeScript, and it speaks 0.3, not 1.0

**As of November 2026, Google ADK is the only one of our eight SDKs with A2A in its released TypeScript package, and it speaks protocol 0.3.** The table reads the pinned versions in `verify/` and their installed files on 19 November 2026, and checks each SDK's newest npm release as well. The details, with file paths and line numbers, are in the [SDK notes](notes/sdk-support.md). Four SDKs have A2A work outside their released packages: an example, an unreleased branch, a hosted server or a community provider. None of that work can stand in for released SDK support, and the book should say so.

**ADK covers both roles, and its 0.3 types leak into its public API, so its move to 1.0 will break callers.** `toA2a(agent, options)` returns `Promise<express.Application>`, serving the card plus JSON-RPC and REST endpoints, and it "fails closed" unless the caller supplies authentication or sets `allowUnauthenticated: true` (installed `dist/types/a2a/agent_to_a2a.d.ts`, lines 71–94). Its generated card declares `protocolVersion: "0.3.0"` (`dist/esm/a2a/agent_card.js`, line 178). `RemoteA2AAgent` is an ordinary `BaseAgent`, so a parent agent delegates to it as it would to an in-process subagent. It imports the 0.3 type names, such as `MessageSendParams`, from `@a2a-js/sdk` ([SDK notes](notes/sdk-support.md#google-adk-googleadk-250)). An open issue says adk-js "only speaks A2A 0.3", and an open pull request moves it to `@a2a-js/sdk` `^1.3.0` with a 0.3 compatibility layer, as a breaking change because "adk-js accepts and exposes `@a2a-js/sdk` types" ([adk-js #1364](https://github.com/google/adk-js/issues/1364); [#1365](https://github.com/google/adk-js/pull/1365), both opened 2026-11-17).

**Three details of ADK's A2A code matter to a caller, and the 2.5.0 agents guide mentions none of them.** First, ADK maps the task lifecycle onto its own events: a server-side tool call that ADK marks long-running becomes an `input-required` status, and the client treats `input-required` like a terminal state that ends its turn (`event_processor_utils.js`, lines 70–95; `event_converter_utils.js`, line 163). Second, cancelling is missing, because the executor's `cancelTask` throws "Task cancellation is not supported yet." (`agent_executor.js`, line 148). Third, the installed typings drift from the code. `ToA2aOptions.basePath` documents a default of `"a2a"`, but the code uses `options.basePath || ""`, so the endpoints mount at the root.

**The official TypeScript SDK already speaks 1.0, and it is what any of our SDKs would build on.** `@a2a-js/sdk` 1.3.0 (29 September 2026, the `latest` tag as of November 2026) declares `A2A_PROTOCOL_VERSION = '1.0'` and generates its types from the spec repository at `ref: v1.0.0` ([a2a-js at v1.3.0](https://github.com/a2aproject/a2a-js/tree/v1.3.0), `src/constants.ts` and `src/types/buf.gen.yaml`). It implements all three bindings, although gRPC needs Node. A `legacyCompat: { enabled: true }` option lets a 1.x client call 0.3 agents and a 1.x server accept 0.3 clients, with documented losses: `ListTasks` against a 0.3 peer returns `UnsupportedOperationError` ([a2a-js notes](notes/a2a-js-sdk.md)). Express is the only server framework it ships, but its core and client entry points are tested on Cloudflare Workers, and 1.3.0 added database-backed task stores whose docs cover D1 through a community Kysely dialect (`vitest.edge.config.ts`; `docs/persistent-stores.md`). Its npm count of 8,104,700 downloads in the week to 18 November 2026 says little about direct use, because every ADK install pulls in a 0.3 copy (npm downloads API; [a2a-js notes](notes/a2a-js-sdk.md)).

**An offline A2A test is practical in our harness today only through ADK, or through `@a2a-js/sdk` alone.** ADK should be able to run both ends in one process, a route we read from its typings and code but have not yet run. `toA2a` would listen on `127.0.0.1` with the `ScriptedLlm` our harness already uses, and a `RemoteA2AAgent` would read its card from the loopback URL; plain HTTP is allowed on loopback, and the card's host must match the fetch origin ([SDK notes](notes/sdk-support.md#google-adk-googleadk-250); `verify/google-adk/examples/lib/check.ts`). With `@a2a-js/sdk` 1.3.0, a scratch test type-checked and ran a server and client in one process, both over loopback Express and over a fetch shim of about ten lines that calls the JSON-RPC handler with no socket at all ([a2a-js notes](notes/a2a-js-sdk.md)). Either route needs `@a2a-js/sdk` as a direct dependency of the harness, because it is only a transitive one today.

## A remote agent's card and reply are untrusted input, and 2026's measurements show where that bites

**The 2026 security papers moved from threat models to measurements, and the broadest of them reports eleven vulnerabilities that a specification-compliant adversary can exploit.** None of the papers below states a venue except the Agent Card study (an ACSAC 2026 workshop) and the injection paper (an ICML 2026 workshop), so the rest are preprints. A2ABreak formalized the specification into "37 states and 76 transitions" and reports "11 new vulnerabilities, each exploitable by a specification-compliant adversary". Among them are "cross-client context injection through unprotected context identifiers" and "credential harvesting via multi-hop identity loss in delegation chains" ([arXiv 2609.10871v3](https://arxiv.org/abs/2609.10871)). The abstract does not say whether it modelled 0.3 or 1.0, so its findings should be cited as risks to check, not as proven flaws in 1.0.0.

**The card itself is an attack surface, because a calling model reads its prose before it calls anyone.** Agent Cards "contain attacker-controllable natural-language fields that may influence agent selection before a provider is invoked". The authors probed 36.1 million domains, collected 310 deployed cards, and found that nine LLM judges caught card manipulation with recall "from 25.8% to 92.3%" ([arXiv 2611.18887v1](https://arxiv.org/abs/2611.18887), AIDC'26 at ACSAC). Names fail the same way. "A2A defines the card's name as human-readable metadata, not as a stable identity", and in tests of seven open-source projects, six client-style integrations routed a request addressed to a trusted peer's name to an attacker-controlled peer. The authors call this an implementation flaw, "not a universal A2A protocol exploit" ([arXiv 2609.27624v1](https://arxiv.org/abs/2609.27624)). We therefore recommend that a caller pin each peer by its card URL, and ideally by a verified card signature (spec §8.4), never by its display name.

**Delegation chains and peers' claims need checks that no participant runs by default.** In a test of multi-hop delegation, 14 of 15 adversarial conditions were rejected, but an isolated test exposed "the absence of semantic authority attenuation": nothing narrowed what a sub-delegate could do ([arXiv 2611.07050v1](https://arxiv.org/abs/2611.07050)). Across more than 2,500 runs of agents with private state, "no agent verifies a peer's factual claim on its own initiative". Such a system "inherits the reliability of its least reliable participant unless the protocol or mechanism performs the check" ([arXiv 2610.19342v2](https://arxiv.org/abs/2610.19342)). A defence architecture tested at an ICML 2026 workshop cut injection success across agents "from 31.2% to 4.2%", with message signing and provenance tracking reducing inter-agent injection by 91% ([arXiv 2609.22949v1](https://arxiv.org/abs/2609.22949)).

**For our harness, those findings reduce to one setting and three checks.** Our tool registry marks each tool's output as trusted or untrusted, and the default is `"untrusted"` only for `mcp:*` tools ([harness plan §3.3](../../plans/build-harness.md#33-context-policy-and-tool-registry-apis)). An A2A tool should take the same default, so a remote agent's artifacts carry the taint that the untrusted-source decision proposed in [plan review 2](../../plans/reviews/plan-review-2.md#6-eleven-owner-actions-are-still-open-and-only-one-a-test-project-for-n50-touches-waves-15) (HD16) attaches to MCP output. The three checks follow from the papers. First, pin peers by card URL and verify a signature where one exists. Second, never forward our own credentials in band, because the spec warns that in-band exchange exposes them "to each agent participating in the chain" ([spec §7.6.3](https://github.com/a2aproject/A2A/blob/v1.0.0/docs/specification.md#763-in-task-authorization-security-considerations)). Third, check a remote agent's factual claims before acting on them, as Chapter T36 teaches for recalled memory.

## Section T37 should teach A2A as delegation to an opaque peer, in five steps, and stay one section

**One section of Chapter T21 is enough, because A2A adds one idea to a chapter that already teaches tools and MCP.** The book plan placed A2A in T21 because "it belongs in the chapter that already explains MCP" ([book plan §4.3](../../plans/build-book.md#43-four-topics-need-research-before-they-are-written)), and T37 asks to propose a chapter only if the research shows the topic needs one ([T37](../../todos/done/T37-section-a2a.md)). It does not. None of our plans builds on A2A, ADK is the only one of our SDKs that ships it, and the decision a reader must make fits the five rules above. The section should teach these five steps, in this order:
1. **What A2A standardizes:** a card at `/.well-known/agent-card.json`, `SendMessage`, a `Task` with nine states, and results as artifacts, delivered by blocking, polling, streaming or webhook. Its version should be stated as of November 2026: 1.0.0, patched as 1.0.1.
2. **How it divides work with MCP:** duration no longer separates them after MCP 2026-07-28, so the line is who plans the work. This step belongs right after the chapter's MCP section, which already teaches `input_required`.
3. **When to delegate at all:** the cost figures (3–10x tokens) and the five rules, ending with exposure only for an outside caller.
4. **What ships in TypeScript:** ADK's `toA2a` and `RemoteA2AAgent` on protocol 0.3, the official SDK on 1.0, and the `A2A-Version` rule that keeps the two apart.
5. **What to distrust:** the card's prose, the card's name and every reply, with the `outputTrust` default as the fix.

**The purchase-order analogy holds, but it needs a second break note beside the one T37 records.** A purchase order fits A2A's core well. The buyer states what it wants without saying how to make it, the supplier owns the process, and the delivery note corresponds to an artifact. T37's break note is right: an A2A task "can stream updates and ask for more input, which a purchase order never does" ([T37](../../todos/done/T37-section-a2a.md)). A second break matters more for safety. A firm checks a supplier before it signs, whereas an Agent Card is self-description that the calling model reads as prose, and nine LLM judges caught manipulated cards with recall as low as 25.8% ([arXiv 2611.18887v1](https://arxiv.org/abs/2611.18887)). The section should keep the analogy and add that second note.

## One new example, on ADK, would give T37 its listing, and a 1.0 example should wait for a release

**A new `verify/google-adk/examples/09-a2a-delegation.ts` should run both ends of A2A in one process, offline, and assert five behaviours with `check()`, because ADK is the only SDK whose released code can show both ends.** A listing from Cloudflare's example or OpenAI's branch would teach code that no pinned package of ours runs. It would expose a "billing" agent driven by `ScriptedLlm` through `toA2a` on `127.0.0.1` with `bearerTokenUserBuilder`. A parent agent would then delegate to it through a `RemoteA2AAgent` that reads the loopback card. Five checks follow:
1. the card is served at `/.well-known/agent-card.json` with `protocolVersion: "0.3.0"` and two interfaces, JSON-RPC and HTTP+JSON;
2. the parent's run yields the remote agent's reply as an event, through the same interface as an in-process subagent;
3. a request without the bearer token never reaches the agent, which ADK documents as surfacing "as an HTTP 500 rather than a 401";
4. `toA2a` with neither authentication nor `allowUnauthenticated: true` refuses to mount the server;
5. a remote tool marked long-running ends the turn with an `input-required` status, the pause that T37's break note describes.

The example needs `@a2a-js/sdk` 0.3.14 as a direct dependency of `verify/google-adk`, because pnpm does not hoist the transitive copy ([AGENTS.md](../../../AGENTS.md#coding-standards)). The version is already in the lockfile, but adding the direct dependency still needs the owner's approval. Checks 2 and 5 read compiled code and have not been run, so the todo should confirm both before T37 cites them.

**A 1.0 example should wait until an SDK we pin releases 1.0 support.** ADK's pull request #1365 would move it to `@a2a-js/sdk` `^1.3.0`, and OpenAI's `@openai/agents/a2a` exists only on a branch. Once either ships, our weekly SDK-update workflow will open the upgrade pull request ([AGENTS.md](../../../AGENTS.md#layout)), and a follow-up todo can then assert the `A2A-Version: 1.0` header, `TASK_STATE_*` names and the 0.3 fallback. Until then, T37 should name 1.0 as the standard and 0.3 as what ships in ADK, and it should not show `@a2a-js/sdk` 1.3.0 code that no harness runs.

## A2A is the contract for delegating across a boundary, and our agents should cross it only when someone else owns the other side

As of November 2026, A2A 1.0 is a settled standard with a neutral home. It gives an agent a card to discover a peer, a task to track work that may run for days, and pauses that let a remote agent ask its caller for input or authorization. MCP now offers long-running, pausable tools too, so the choice between the two turns on who plans the work. A tool takes the inputs its caller chose, while an agent takes a goal and keeps its plan to itself. Our eight SDKs mostly lag the standard: ADK ships both roles on 0.3, and the official TypeScript SDK already speaks 1.0. The rule for our agents follows. Use a function, a tool or an in-process subagent while we own both sides, call over A2A when someone else owns the agent, and expose over A2A only when an outside caller needs it. Every card and every reply is untrusted input. Section T37 can teach all of this in one section, with one ADK example that runs both ends offline, and the owner approved all seven proposed changes on 2026-11-19 to make that the plan.
