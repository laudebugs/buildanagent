## 1. Protocol version per line (0.3.14 vs 1.3.0)

Takeaway. 0.3.14 implements A2A spec v0.3. Its main types were generated from a JSON schema fetched from an unpinned `main` branch, plus a vendored proto in package `a2a.v1`. 1.3.0 implements A2A spec v1.0. Its types are generated with ts-proto from `specification/` of the A2A repo at tag `v1.0.0` (not v1.0.1), proto package `lf.a2a.v1`. The SDK advertises the protocol as `'1.0'` (Major.Minor), and its opt-in compat layer accepts `'0.3'` as the legacy version. Version 1.0.0 was a large breaking release, and the repo ships a migration guide.

## 2. Transports, server integrations, runtime portability, client API (1.3.0)

Takeaway. 1.3.0 supports JSON-RPC, HTTP+JSON/REST and gRPC on both client and server, and all three can share one `DefaultRequestHandler`. gRPC is Node-only. The only shipped HTTP framework integration is Express (`@a2a-js/sdk/server/express`). No Hono, Fastify or Fetch-handler adapter ships. However, the core, client, server-core and compat subpaths are built and tested as Workers-safe (esbuild `--platform=neutral`, plus a vitest suite under `@cloudflare/vitest-pool-workers`). A framework-agnostic `JsonRpcTransportHandler` is exported from `@a2a-js/sdk/server`. The v1.0 `RestTransportHandler` exists in source but is not exported publicly. Only the legacy v0.3 REST handler is public, via `compat/v0_3/server`. So a non-Express runtime can serve JSON-RPC with roughly 20 lines of glue, but REST would need the Express adapter or a reimplementation. The client resolves the card from `/.well-known/agent-card.json`, and `ClientFactory` picks a transport from `supportedInterfaces` and `preferredTransports`. The default factories are JSON-RPC and REST, and every HTTP transport accepts a `fetchImpl`.

## 3. Server API (1.3.0)

Takeaway. Application code implements `AgentExecutor` (`execute`, `cancelTask`), reads a `RequestContext` (the full `SendMessageRequest`, plus `taskId`, `contextId`, `task` and `ServerCallContext`), and publishes `AgentEvent.*`-wrapped events to an `EventTarget`-based `ExecutionEventBus`. `DefaultRequestHandler` takes nine positional constructor arguments: card, task store, executor, bus manager, push store, push sender, extended-card provider, card-signature generator and options. The stores are `InMemoryTaskStore`, plus durable Kysely-backed `DatabaseTaskStore` and `DatabasePushNotificationStore` since 1.3.0 (PostgreSQL, MySQL, SQLite, Cloudflare D1), with an `a2a-db` migration CLI. Signed agent cards (JWS via `jose`), extensions (`A2A-Extensions` header, executor decorators) and multi-tenancy (`tenant` on interfaces, requests and context; stores scoped by tenant and owner) are all present. There is no agent-card builder class. Cards are plain proto-shaped objects.

## 4. Backward compatibility with v0.3

Takeaway. Yes. 1.x ships an opt-in, per-handler and per-transport-factory v0.3 compat layer (`legacyCompat: { enabled: true }`) across JSON-RPC, REST, gRPC, agent-card resolution and push notifications, in six `compat/v0_3*` subpaths. A 1.x client with the flag on can talk to 0.3 agents, and a 1.x server can accept 0.3 clients. It is lossy in documented ways: `ListTasks` is unavailable against v0.3, OAuth `deviceCode` is dropped, `final` is computed, and `blocking`/`returnImmediately` are inverted. Requests without a version are treated as v0.3.

Cited findings:
- [repo@1.3.0] README: "A v1.0 server can transparently accept v0.3 clients (and a v1.0 client can transparently talk to v0.3 servers) by opting into the compat layer with `legacyCompat: { enabled: true }` on the relevant transport / handler."
- [docs@1.3.0] `docs/compatibility-v0_3.md`: "The opt-in is **per handler and per transport factory** — there's no project-level switch." The client example uses `new DefaultAgentCardResolver({ legacyCompat: { enabled: true } })` and `new JsonRpcTransportFactory({ legacyCompat: { enabled: true } })` (likewise for REST and gRPC). "`ClientFactory` itself does not take a `legacyCompat` option".
- [docs@1.3.0] same file, detection: the JSON-RPC handler routes on method name (PascalCase goes to v1.0, everything else to v0.3, "spec §3.6.2 default-to-v0.3"). REST v0.3 routes live under `/v1/...`. gRPC uses separate descriptors (`A2AService` vs `LegacyA2AService`), and "the v1.0 gRPC factory has no `legacyCompat` flag". The agent card uses the `A2A-Version` header, defaulting to `'0.3'`, with `Vary: A2A-Version`.
- [docs@1.3.0] same file, caveats: "A v1.0 client calling `client.listTasks(...)` against a v0.3 server fails with `UnsupportedOperationError` (JSON-RPC code `-32004`)". "`OAuthFlows.deviceCode` (v1.0 only) **Silently dropped.**" "Going v1.0 → v0.3 the `final` flag is **computed** from the status state". "Inverted polarity (v1.0 `returnImmediately: true` ↔ v0.3 `blocking: false`...)". The translators in `src/compat/v0_3/translate/` "are intentionally internal and may change without a major-version bump."
- [npm] exports include `./compat/v0_3`, `./compat/v0_3/client`, `./compat/v0_3/server`, `./compat/v0_3/client/grpc`, `./compat/v0_3/server/grpc`, `./compat/v0_3/server/express`.

## 6. Offline test feasibility

Takeaway. Feasible both ways, and I verified both. (a) Loopback: an Express app on `127.0.0.1:0` with `jsonRpcHandler` and `restHandler`, driven by `ClientFactory.createFromUrl`, works in one Node process. This is the repo's own e2e pattern (`app.listen()` with an ephemeral port; gRPC uses `bindAsync('localhost:0')`). (b) No sockets at all: hand `JsonRpcTransportFactory({ fetchImpl })` a fetch function that calls `JsonRpcTransportHandler.handle()` directly and wraps streaming results as SSE with the exported `formatSSEEvent`/`SSE_HEADERS`. Both `sendMessage` and `sendMessageStream` worked. The SDK ships no in-memory transport. The `fetchImpl` shim is about 10 lines.
