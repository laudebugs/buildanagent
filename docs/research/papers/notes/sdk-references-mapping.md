# U22 against the SDK references, the comparison docs and the build guides

Working note, 2026-11-19. It maps the findings of [the U22 survey](../agent-research-papers.md) onto the eight SDK references in `docs/reference/`, the comparison docs in `docs/comparison/` and the three build guides in `docs/guides/`. It changes no file. Every proposal below is for the owner to accept or reject. An accepted proposal still goes through the repo's five document steps: draft, fact-check, review, fix and re-check.

Method: I read each reference's `guide.md` in full and searched each `fact-check.md` for every U22 angle (computer-use or browser tools, permission or capability checks, session logs and provenance, evals and benchmarks, multi-agent and handoffs, self-improvement). I read the relevant sections of the comparison docs and the three guides, and I checked each proposed citation against U22's own fact-check log (`../fact-check-agent-research-papers.md`). A ✅ row there means U22 read the arXiv abstract page directly. A ⚠️ row means U22 marked the claim a secondary summary, and any proposal that relies on such a row must say so.

The SDK references document SDK behavior, which they verify against pinned packages. U22 is about agent research, so it studies no SDK's internals. Unlike U18 and U19, it records no SDK typings, so it gives no reason to append a findings section to any reference's `fact-check.md`. No reference makes a claim that U22 contradicts. For example, no reference claims that some SDK checks a tool's code against its description.

## SDK references

### claude-agent-sdk: no change needed
The guide's safety material (the six-step permission order, `canUseTool`, `PreToolUse`, `readOnlyHint` used only to schedule parallel calls, and subagents) describes what the CLI does with a declared tool. It makes no claim that U22 contradicts. ACaM's point, that a declared contract can hide what the code does, applies to every SDK equally. It belongs in our own build guides (see agent.md §3 below), not in one vendor's reference. The fact-check's findings (F1–F5) concern doc accuracy and the inherited environment, which U22 does not cover.

### pi: no change needed
§6 already says project trust "is no security boundary" and that extensions run with the process's permissions. That statement agrees with SkillCFI and needs no support from it. The guide documents skills only as a resource that `DefaultResourceLoader` discovers. SkillCFI's finding is a design lesson for our harness (see agent-harness.md §7 below), not a fact about Pi 1.5.2. The fact-check is about doc accuracy only.

### openai-agents-sdk: no change needed
Handoffs (§6), tool guardrails that run "across handoffs" (§7) and `needsApproval` (§8) touch U22's multi-agent and tool-security themes only in general terms. U22's multi-agent papers (concealment in teams, resource underuse) study model behavior, not handoff mechanics, and U22 itself files the concealment study "for awareness only". The computer-use tool is listed in §5, but U22 leaves browser and computer use to U15 and adds nothing on it. The fact-check is about doc accuracy, plus U18's memory findings.

### vercel-ai-sdk: no change needed
`toolApproval`, the OPA policy package and `experimental_toolApprovalSecret` (§7) decide on the tool name and its input. The guide makes no claim about capability checking that U22 would revise. Subagents (§11) are one bullet. The fact-check findings F1–F8 concern doc drift.

### langchain: no change needed
The guide mentions its multi-agent patterns and skills in one bullet each (§11), with no design claims. `wrapToolCall` and `humanInTheLoopMiddleware` gate on the tool name and its arguments, which nothing in U22 contradicts. The fact-check is about doc accuracy and U18's store findings.

### cloudflare-agents: no change needed
Nothing in the guide (Durable Objects, Think's workspace tools, `needsApproval`, MCP, Workflows) bears on U22 closely. Browser Rendering appears only in the fact-check's list of skipped examples.

### google-adk: no change needed (one angle considered and rejected)
The parity list in §14 names three features with a U22 counterpart: "reflect-and-retry plugins" (Reflexion's pattern), planners (plan-then-execute) and, under "Missing from TypeScript", evaluation user simulation (τ-bench's simulated user). Each appears only as a name in a list. A U22 citation beside it would be a citation by reflex, because it would tell an ADK reader nothing about the ADK feature. If a later round documents ADK's evaluation or reflect-and-retry plugins, U22's τ-bench and Reflexion material becomes the right context. The fact-check is about doc accuracy plus U18 and U19.

### copilot-sdk: no change needed
The permission kinds (§5), `availableTools` (§6) and the hooks (§7) gate on the tool name and the kind of operation, and the `task` sub-agent tool appears only as a warning. Nothing in U22 contradicts or extends these claims. The fact-check is about doc accuracy plus U18.

## Build guides

### docs/guides/agent-sdk.md: no change needed

### docs/guides/agent-harness.md: propose four additions
None of U22's findings contradicts a claim here. Four paragraphs would gain primary evidence that U22 verified directly (✅ rows).

1. **§5, paragraph "Practitioners add path-based ask rules for the checks an agent can weaken."** The paragraph adds default `ask` rules for edits that touch hooks, CI config and rules files. It admits that this rule "rests on view 4 more than on" a single secondhand anecdote. The addition: Staron measured the same distinction at scale ([arXiv:2611.23251](https://arxiv.org/abs/2611.23251); U22, "Our permission pipeline checks what a tool call asks to do"; U22 fact-check rows 77–80, ✅). Across 932,791 pull requests from five coding agents in the AIDev dataset, control-plane changes (CI/CD workflows, permission settings) carried a far higher mean joint cost-and-governance penalty than data-plane changes. The gap between agents held after the authors controlled for cost and merge rate, and the classifier scored κ = 0.72 on a 34-PR check. The study gives the CI-config `ask` rule a measured basis beyond practitioner opinion. It also backs U22's proposal 3, which asks for a stricter review path for control-plane diffs.

2. **§7, paragraph "A trust gate controls what loads, not what runs, and two vendors say so." (or the following paragraph on content-hash pinning).** The guide already says that trust gates loading, not execution, and it adds content-hash pinning for extensions. The addition: SkillCFI is the first measurement of how far a loaded skill's possible steps diverge from its advertised ones ([arXiv:2611.24185](https://arxiv.org/abs/2611.24185); U22 fact-check rows 65–69, ✅). Its runtime control-flow contract blocked all 240 test violations that a plain permission allowlist admitted, with legitimate tasks completing almost as often. None of the 53 public skills the authors tested passed as written. A hash pin checks a skill's identity, not its behavior while it runs. The addition should say plainly that no current todo enforces a skill's control flow at run time (U22 proposal 1, against N22 and N23), so that a reader does not mistake the hash pin for that control.

3. **§10, paragraph "Public benchmarks are a weak guide, and the figures behind that claim are still disputed."** The paragraph rests its conclusion on OpenAI's SWE-bench Verified decision, whose framing it rightly calls unverified, plus practitioner opinion. The addition: two primary papers reach the same conclusion without OpenAI's posts (U22, "A trustworthy eval suite needs its own fresh tasks"; fact-check rows 27–28, ✅). "The SWE-Bench Illusion" found models locating a bug's file at up to 76% on SWE-bench tasks with no repository in context, against up to 53% on repositories outside SWE-bench, and read the gap as memorization ([arXiv:2506.12286](https://arxiv.org/abs/2506.12286)). The Agentic Benchmark Checklist found SWE-bench Verified's tests too thin to prove a patch correct, and τ-bench's grader counting an empty response as a pass ([arXiv:2507.02825](https://arxiv.org/abs/2507.02825); U22's fact-check says the 38% figure comes from a search summary of the paper, so cite it as such). The sentence on OpenAI's posts should stay as it is: U22's own account of them, that contamination was the cause, is also marked [secondary], so the dispute stands.

4. **§10, paragraph "Completion is checked in code, not taken from the model.", and §13 decision 10 ("Completion check").** The addition: Truthgate checks a coding agent's "done" claim against hidden host-side tests and against a signed tool-call log written outside the agent's sandbox. It found that a deterministic check over that record and an LLM judge catch different cheating cases, so the record is "evidence a judge should read, not a replacement for one" ([arXiv:2611.23335](https://arxiv.org/abs/2611.23335); U22 fact-check row 145, ✏️ corrected and then confirmed). On its 180-task impossible-task set, Claude Sonnet 5.5 passed 39 tasks by special-casing its code, a 21.7% false-pass rate. Decision 10's "settle it" line can then name both mechanisms: tune the deterministic check on replayed false claims, and keep a judge pass over the same log entry. This supports U22's note on N32, which says to keep both a log-based check and a judge rather than either alone.

Considered and not proposed: §2 (session log), because Wong's ledger and Hou et al.'s Atm only corroborate a design the guide already argues from stronger evidence, and their U22 rows are ⚠️. §11 (removability), because GUARD's automated, regret-gated self-editing is a gap that U22 names without any todo or proposal. Adding it to a build guide would present an unadopted direction as plan. If the owner adopts it, the natural home is a new open decision in §13.

### docs/guides/agent.md: propose one correction and three additions

1. **Correction: §2 ("Choose the least autonomy the task allows…"), the cost table, row "ReAct → reflection", column "Measured gain", which reads "not benchmarked".** Reflexion's own paper reports a measured gain: 91% pass@1 on HumanEval, against 80% for GPT-4 ([arXiv:2303.11366](https://arxiv.org/abs/2303.11366); U22 §1 ¶2; U22 fact-check rows 4–5, ✅ quoted from the abstract). The cell should become something like "91% vs 80% pass@1 on HumanEval in the original paper, against a GPT-4 baseline rather than a ReAct one". The "Pays when: unclear" cell stands, because that comparison sets no cost and no ReAct baseline. The paper body also compares ReAct with ReAct plus Reflexion on ALFWorld, but U22 did not verify that figure, so re-check the paper before using it. The same cell sits in `docs/research/agent/agent-research.md` §1, and agent fact-check R1 row 36 keeps "Not benchmarked" in place. The correction therefore needs its own row in that fact-check too, as the repo's correction rule requires.

2. **Addition: §3, paragraph "The contract is tested offline before any eval runs."** The static lint described there (todo A3) checks a contract's shape: description length, "when not to use" text, names, collisions and identity-shaped parameters. The addition: ACaM found Description-Code Inconsistency in real agents ([arXiv:2611.23507](https://arxiv.org/abs/2611.23507); U22 fact-check rows 72–76, ✅). A tool's code reaches capabilities its description never mentions ("capability laundering"). ACaM's static analysis found this across 43 real agents, at 98.3% macro-F1 against 24 hand-annotated ones, with ten exploits confirmed by working proofs of concept. A shape lint cannot catch it, which is U22's proposal 2 for A3. The same evidence also supports §5's rule that "Tiers come from the worst call an attacker … could make, not from the tool author's annotations". One clause there could cite ACaM beside the MCP specification's warning.

3. **Addition: §6, paragraph "Outcome graders on final state beat trajectory graders…" and the grader table's "LLM judge" row.** Two additions:
   - **An empty answer can pass an end-state grader.** The Agentic Benchmark Checklist found that τ-bench's grader counts an empty response as a pass ([arXiv:2507.02825](https://arxiv.org/abs/2507.02825); fact-check row 28, ✅, with the 38% trivial-pass figure from a search summary). The section models its final-state grading on τ-bench. The countermeasure, our inference rather than the paper's, is to run a do-nothing agent over the suite and treat any task it passes as a grader bug. Pairing such tasks with a check that the agent acted where action was required, as the "Must escalate" slice already does, also helps.
   - **One holistic judge score measures one impression.** For the LLM judge, Ali, Siddiqui and Zahid found that demo-based panel scores across nine dimensions moved together as one "halo" ([arXiv:2611.24039](https://arxiv.org/abs/2611.24039)). VFM and Gandalf score many narrow criteria separately, at lower cost ([arXiv:2611.23074](https://arxiv.org/abs/2611.23074), [arXiv:2611.22841](https://arxiv.org/abs/2611.22841)). Together they argue for scoring the summary rubric criterion by criterion rather than holistically, which is U22's proposal 4 for A17 and F4. All three papers' rows in U22's fact-check are ⚠️ (secondary summary, a tooling limit), so the addition must mark them so.

4. **Addition with a narrowing: §7 ("Ship in four stages…"), paragraph "The rollout evidence is thin and mostly practitioner writing", and the sentence "Shadow mode suits approval-gated agents…; no primary source describes it, so it is our inference."** Masoero reports a deployed multi-agent documentation-maintenance system, TriAgent, run for 43 days in shadow mode: 499 tickets triaged, 92 documentation gaps found, 81.1% of verifiable assertions judged correct, and agent and human replies complementary ([arXiv:2611.23142](https://arxiv.org/abs/2611.23142); U22 "Trustworthy agent provenance" ¶4). This is the first paper-level account of a support-style agent in shadow mode in our corpus, and a data point for the length of a shadow stage beside our proposed two weeks (and §10 decision 7). The record-and-deny approver that turns each human decision into a label remains our inference. The sentence should therefore say that no primary source describes *that pattern*, not shadow mode in general. U22's fact-check marks rows 103–104 ⚠️ (secondary summary), so re-read the paper before the edit, or attribute the claim to U22's summary.

Considered and not proposed: §5's reader, planner and drafter split against the team-concealment paper, which U22 itself files "for awareness only" and which studies one steered neuron in a 4B model. Also §4's frozen prompt against the values paper, whose finding concerns a self-improving agent revising its own instruction file, not the fixed bundle this guide builds.

## Summary
Of the eight SDK references and three build guides, 2 have proposed changes (agent-harness.md: four additions; agent.md: one correction and three additions) and 9 have none; the three comparison docs also need no change.
