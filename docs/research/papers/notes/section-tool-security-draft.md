## Our permission pipeline checks what a tool call asks to do, but not what the tool's code or a loaded skill actually does

Three papers from the 17-18 November 2026 arXiv window move tool-use security past the prompt-injection boundary that [`browser-use.md`](../../browser-use/browser-use.md#prompt-injection-stays-unsolved-so-the-network-and-the-credential-are-the-boundary) already covers (the lethal trifecta, Meta's Rule of Two, CaMeL, and the WASP/AgentDojo benchmarks) and into a question that literature does not ask: once a tool or skill is registered and the model is allowed to call it, does its code do what its contract says, and does it stay inside the control flow its author wrote? SkillCFI, ACaM and Staron's CI/CD study each answer no for a different layer — a skill's execution, a tool's description, and an agent's own authority — and each points to a gap in our planned permission pipeline ([N12](../../../todos/done/N12-permission-pipeline.md)), tool-contract lint ([A3](../../../todos/ready/A3-tool-contract-lint.md)) and generated-code gate ([ADR 0039](../../../decisions/0039-check-and-deploy-gate.md)). We do not repeat the foundational tool-injection literature here; this section covers only what these three papers add.

SkillCFI treats an agent skill as a program whose control flow has moved into prompt text, and borrows classical control-flow integrity to put it back under a fixed graph (Ruan et al., [arXiv:2611.24185](https://arxiv.org/abs/2611.24185), 18 November 2026). The authors compile a skill into agent instructions plus an executable contract, then enforce that contract at runtime: a deterministic checker admits a tool request only on evidence the model cannot fabricate, and refuses any unmediated channel, such as an inline script a skill tries to run directly. Against a 240-violation test set, SkillCFI blocked every one that a plain permission allowlist would have admitted, legitimate tasks completed almost as often as with no enforcement, and listing the next legal step in a refusal lifted the model's recovery rate from 21% to 65%. Most strikingly for us, none of 53 public skills the authors tested passed as written — each needed a rewrite to satisfy a fixed control-flow graph. Our skills todo ([N23](../../../todos/ready/N23-skills-context-files.md)) advertises skills by name, description and path and records each load, and our extensions todo ([N22](../../../todos/ready/N22-in-process-extensions.md)) gates project-supplied extensions by trust tier and a content-hash pin. Both check identity and provenance before a skill loads; neither constrains what the skill can cause the agent to do once it has loaded. SkillCFI's result argues that a skill's *advertised* steps and its *possible* steps diverge often enough that a hash pin on the skill file is not a control on the agent's behavior while it runs.

ACaM attacks the matching problem one layer down, at the individual tool rather than the skill (Santra et al., [arXiv:2611.23507](https://arxiv.org/abs/2611.23507), 17 November 2026). Agent platforms grant tools access to credentials, private data, and external services on the strength of a natural-language description, but the authors find no step anywhere that checks whether the implementing code can do only what the description claims. They name the resulting gap Description-Code Inconsistency, and the exploit it enables "capability laundering": a tool's code carries dangerous behavior its description never mentions, so a reviewer or a permission system that reads only the description misses it. ACaM derives a tool's real capabilities from its code with static analysis, using an LLM only to supply behavioral meaning for what the analysis finds, then builds an Agent Capability Property Graph to trace multi-tool threat chains. Across 43 real-world agents it reached 98.3% macro-F1 against 24 hand-annotated agents, and surfaced hundreds of structural vulnerabilities, ten confirmed with working proofs of concept. Our tool-contract lint ([A3](../../../todos/ready/A3-tool-contract-lint.md)) fails the build on a weak contract — missing error types, an underspecified schema — and our permission pipeline ([N12](../../../todos/done/N12-permission-pipeline.md)) decides each call from the contract's declared risk tier. Both trust what the contract says about the tool, which is exactly the trust ACaM shows is misplaced. A tool written against our registry could declare a narrow, low-risk contract while its implementation reaches a wider scope, and nothing in A3 or N12 as planned would catch that, because both check the declaration's shape, not the code's behavior.

Staron's study measures the same authority question at the scale of a running fleet of coding agents, across 932,791 pull requests from the AIDev dataset spanning five agents (Staron, [arXiv:2611.23251](https://arxiv.org/abs/2611.23251), submitted 24 September 2026). The paper defines a joint penalty that combines execution cost with governance risk, then classifies each pull request's changes as control-plane (CI/CD workflows, permission settings) or data-plane (ordinary code). Control-plane changes carried a far higher mean penalty than data-plane ones, and the gap in governance risk between agent implementations held even after the authors controlled for execution cost and merge rate — a manual check of 34 pull requests gave the authority-scope classifier a Cohen's kappa of 0.72. The paper's label for this behavior, escalating authority through the pipeline that is supposed to constrain the agent, is exactly the failure our architecture is built to foreclose: the loop runs outside the sandbox and treats the owner's pull-request merge as the one commit point ([ADR 0036](../../../decisions/0036-loop-outside-sandbox-and-pr-approval.md)), and the platform's generated-code gate signs a report for an exact commit and lets no deploy proceed without one ([ADR 0039](../../../decisions/0039-check-and-deploy-gate.md)). Neither decision, however, currently says that a diff touching CI/CD configuration itself should be scored or approved differently from a diff touching application code. Staron's empirical gap between control-plane and data-plane risk gives that distinction a measured basis, and our security review ([F15](../../../todos/ready/F15-security-review.md)) and generated-code isolation work ([F11](../../../todos/ready/F11-generated-code-isolation.md)) should flag a workflow-file or permission-setting change for the stricter path rather than scoring it like any other commit.

None of the three papers changes the network-and-credential boundary that the browser-use security review already settled on; they instead argue that the boundary we draw around a tool's *declared* authority is only as good as a check on what the tool's code can actually do, and that a CI/CD pipeline is itself a tool an agent can quietly widen. Extending A3's lint and N12's pipeline with a static, code-level capability check in ACaM's style, and treating control-plane diffs as a distinct, higher-scrutiny class in F15 and ADR 0039's gate, would close gaps that the current contract-and-tier design does not reach.
