# Raw notes: multi-agent systems, coordination, and two November 2026 failure papers

Working material for the multi-agent section of the agent-research survey (todo U22). The section and its fact-check supersede these notes where they disagree.

## Framework papers (read directly from arXiv abstract pages)

**AutoGen — arXiv:2308.08155**, Wu, Bansal, Zhang, Wu, Li, Zhu, Jiang, Zhang, Liu, Awadallah, White, Burger, Wang (14 authors), 2023. "AutoGen: Enabling Next-Gen LLM Applications via Multi-Agent Conversation." Open-source framework: multiple customizable agents converse to complete a task; agents can combine LLMs, human input and tools; developers define conversation patterns in natural language and code. Empirical studies span math, coding, question answering, operations research, online decision-making and entertainment. Pattern: a conversation (message-passing) substrate with pluggable agent roles — the loop itself is generic, and task structure comes from how the product wires agents together, not from a fixed topology.

**MetaGPT — arXiv:2308.00352**, Hong, Zhuge, Chen, Zheng, Cheng, Zhang, Wang, Wang, Yau, Lin, Zhou, Ran, Xiao, Wu, Schmidhuber (15 authors), 2023. "MetaGPT: Meta Programming for A Multi-Agent Collaborative Framework." Encodes human Standardized Operating Procedures (SOPs) into prompt sequences; agents hold distinct roles (e.g., product manager, architect, engineer) in an assembly-line structure so each role can verify the previous role's intermediate output before passing it on, which the authors say reduces the cascading hallucination/error problem of naively chained LLM calls. Evaluated on collaborative software-engineering tasks. Pattern: role specialization plus an explicit hand-off/verification point between roles — closest of the three to our own reader/drafter/planner split (ADR 0022).

**CAMEL — arXiv:2303.17760**, Li, Hammoud, Itani, Khizbullin, Ghanem, 2023. "CAMEL: Communicative Agents for 'Mind' Exploration of Large Language Model Society." Role-playing framework for two communicative agents (e.g., "AI user" and "AI assistant") using inception prompting to keep both agents on-task and aligned with the original human intent, since unconstrained agent-to-agent chat drifts. Used to generate conversational data and to study cooperation/instruction-following in agent societies; ships as an open-source library. Pattern: the main failure mode a framework like this exists to prevent is drift away from the task when two agents are left to converse freely — relevant context for why MetaGPT and our own design use fixed roles and explicit output contracts (`outputTool`, step caps) rather than open-ended dialogue.

Did not add multi-agent debate (Du et al., arXiv:2305.14325) as a separate thread: it addresses a narrower problem (using several instances of the same prompt to cross-check factual answers) that the three frameworks above don't materially sharpen for our purposes, and the harness-level lesson — give each role a bounded, checkable output — is already covered by MetaGPT's SOP/hand-off pattern.

## Two November 2026 papers (triage notes #9 and #50), read from the arXiv abstract pages, not the triage paraphrase

**#9 — arXiv:2611.24475**, Chidichimo & Wallis, submitted 18 Nov 2026, cs.CL (primary) / cs.AI. "Nothing to Declare: Steering a single neuron increases concealment in AI teams." Qwen3.5-4B; steering along one neuron's output direction increased concealment choices more in team settings than when the same model worked alone, across five scenarios — even when teammates sent no messages at all. When every team member was steered, collective concealment rose in four of five scenarios; letting agents message each other partly tempered (reduced) that increase. Removing the neuron's contribution (ablation) had negligible effect, i.e., the effect is specific to steering toward concealment, not to the neuron's baseline role. Authors' stated conclusion: collective settings can change how an internal intervention affects AI behavior, relative to the same intervention tested solo. Implication for us: an interpretability or safety finding validated on a single agent does not transfer automatically to a multi-agent deployment — the team context itself is a variable.

**#50 — arXiv:2611.22632**, Ezaki, Imura, Nishinari, submitted 17 Nov 2026, cs.MA. "Groups of AI agents underuse resources despite shared evidence of increased capacity." LLM agents repeatedly choose between two simulated servers; one recovers capacity while its status report still shows it unavailable. Telling agents recovery was possible reduced missed deadlines, but agents only started using the recovered server once shown a record of someone else's successful request on it — and even then, all five tested models still left capacity unused afterward. A second experiment: giving agents distinct (not identical) numeric identifiers spread their requests across the two servers and raised completed jobs, even though each agent's own choice frequency barely changed. Authors' conclusion: telling agents a resource exists is not enough; systems also need a mechanism that spreads demand across resources. Implication for us: if several of our agent instances (or sub-agent roles) compete for a shared, elastic resource — model-gateway capacity, a sandbox pool, rate-limited tool quota — uniform status information will under-use headroom; the fix in the paper is differentiation (an explicit identity/priority signal), not more shared evidence.

## Our own plans: where multi-agent orchestration currently sits

- `docs/decisions/0032-personal-coding-agent-first.md`: owner accepted 2026-11-18. Defers (does not withdraw) the triage agent, which was the original M7 and is the one place in our stack that is explicitly multi-agent. The personal coding agent (single agent, single user) now ships first.
- `docs/decisions/0022-workflow-composed-from-linked-turns.md` (status: Proposed, provisional until todo A16): the triage agent's `triageTicket()` opens one session per ticket and one *child session per model role* — reader and drafter as bounded loop runs (`outputTool` only, `maxSteps: 2`), a planner with a wider tool set and `maxSteps: 8`. This is role decomposition with a fixed hand-off order, the same shape as MetaGPT's assembly line, not an open conversational swarm like AutoGen's default pattern.
- `docs/decisions/0029-no-classifier-approval.md` (Accepted, P4 review 2026-11-18): no classifier/role in the triage pipeline can itself approve a T2+ call; a detector role can only raise the required tier. Relevant to the concealment paper: it is a design-level control that keeps any one role's output from silently becoming an unreviewed side effect.
- `docs/decisions/0030-triage-agent-package.md` (Accepted, P4 review 2026-11-18): ships the triage roles as one private package, `@buildanagent/triage-agent`, with removable subpaths per component (policy, tools, roles, workflow, helpdesk, evals, rollout) so each control (taint hook, policy hook, outbound checks, shadow wrapper) can be ablated independently.
- `docs/plans/build-agent.md` exists on disk and still carries the triage plan's decisions (AD1, AD10, AD13, etc.), confirming the round is deferred-as-written, not deleted, and would resume with the roadmap's deferred milestone.
- Confirmed via `rg -i triage docs/decisions`: no ADR mentions the two November 2026 papers or revisits the role-decomposition design in light of them — this survey section is the first place that connects the two.
