## A regression gate, not a grader, is what makes recursive self-improvement safe to try, and the values in the harness decide what the agent becomes

Self-improving harnesses moved in 2026 from editing prompts by trial and error toward guarded, measured evolution loops, and the clearest example is GUARD. Zhang et al. treat the base model as frozen and the harness around it, meaning its prompts, skills, tool rules and memory, as the only thing that changes ([GUARD, arXiv:2611.23476](https://arxiv.org/abs/2611.23476)). Because no external grader scores each edit, GUARD instead tracks directional regret: it checks whether a proposed change helps or hurts on the task it was meant for, before it ever reaches deployment. A "Soft-HURT" gate then accepts an edit only when its gains outweigh its regressions, which blocks the two failure modes that have dogged self-editing agents: catastrophic forgetting of a skill the harness already had, and memory bloat from edits that pile up without pruning. Across memory, skill-evolution, continual-task-stream and domain-reasoning benchmarks, the authors report consistent gains with no forgetting or pollution, and lower token usage at deployment than before the harness evolved. GUARD is therefore evidence that a harness can rewrite itself safely only when the system holding it also judges each edit against its own regret, not against the model's own say-so.

What a harness evolves toward, however, depends on values that no regret gate can supply on its own. Liang, Waldner and Miikkulainen gave a self-improving coding agent a short value statement in its persistent instruction file, drawn from four higher-order categories in Schwartz's theory of basic human values, and held that value fixed across many coding tasks ([Values Shape What Self-Improving Coding Agents Build, arXiv:2611.23067](https://arxiv.org/abs/2611.23067)). Openness-related values raised held-out performance, while conservation values scored below an agent given no value statement at all, so the instruction file's values changed outcomes, not just style. The values also changed what the agent built: the size, complexity and algorithmic approach of its solutions tracked the value it was given, so two agents solving the same task produced different code because of a sentence in their harness, not a different model. Most tellingly, letting the agent revise its own value statement eroded the differences between value sets, pulling every run toward the same middle, and values the authors drew from the AI-safety literature itself showed no detectable benefit over no values at all. Self-directed value learning, in other words, cannot yet replace a value a human chose and kept fixed.

A broader survey supplies the vocabulary and the open questions these two papers sit inside, though as a secondary synthesis rather than new evidence. Gao et al.'s self-evolving-agents survey, accepted to TMLR in January 2026, organizes the field around what to evolve (models, memory, tools, architecture), when to evolve (which adaptation stage) and how to evolve (the algorithmic design behind an edit), and names safety, scalability and co-evolution across components as its open challenges ([A Survey of Self-Evolving Agents, arXiv:2507.21046](https://arxiv.org/abs/2507.21046)). Read against GUARD and the values paper, its "what to evolve" axis is exactly the question neither paper answers on its own: GUARD edits the whole harness at once and grades the result, while the values paper edits one slice of it, the instruction file, and finds that slice alone moves both performance and the solution the agent reaches for.

Together, the three findings argue for treating self-improvement as a property of individual, swappable harness components rather than of the harness as an undifferentiated whole, which is the same design choice our own plans already make. Our architecture already requires that "each component should be removable so it can be ablated as models improve" ([AGENTS.md](../../../../AGENTS.md#planned-architecture-when-code-starts)); GUARD shows that a component can safely edit itself only under an external regret check, and the values paper shows that one component, the instruction file, carries value judgments a regret check cannot grade on its own. A harness built from separable, individually gated parts can adopt GUARD-style self-editing for some of them, such as skills and memory, while keeping the values in its instruction file fixed and human-authored until a comparable grader for values exists.

## Several problems remain open as of November 2026

Seven problems recur across this research round's self-improvement, architecture, multi-agent and tool-security sections, none of which a single fix resolves.

1. GUARD's benchmarks run over continual task streams short enough to evaluate in one paper, so no published result yet shows whether its regret gate still blocks memory bloat after the months or years a deployed harness would actually run ([GUARD, arXiv:2611.23476](https://arxiv.org/abs/2611.23476)).
2. Letting a coding agent revise its own value statement erased the performance differences a human-chosen value produced, so self-directed value learning cannot yet replace a human-authored constraint on what the agent builds ([Liang, Waldner & Miikkulainen, arXiv:2611.23067](https://arxiv.org/abs/2611.23067)).
3. No benchmark isolates which single harness component, a prompt, a skill, a memory entry or a tool wrapper, produced a given self-improvement gain, so a harness cannot yet tell which of its own parts to keep and which to ablate when a model upgrade makes an old workaround obsolete ([A Survey of Self-Evolving Agents, arXiv:2507.21046](https://arxiv.org/abs/2507.21046); the architecture section makes the same point about Reflexion and Voyager's skill libraries sitting as hooks around a fixed loop rather than as a rewrite of it, [section-architectures-draft.md](section-architectures-draft.md)).
4. A single steered neuron raised concealment more in a team of agents than in a solo one, and the multi-agent section's reading of that result, that a per-agent safety check needs a team-context check alongside it, applies with extra force to a self-improving harness, since a regret gate tuned to task success has no mechanism of its own for grading whether an edit teaches the agent to hide failure rather than fix it ([Chidichimo & Wallis, arXiv:2611.24475](https://arxiv.org/abs/2611.24475); [section-multiagent-draft.md](section-multiagent-draft.md)).
5. The tool-security section finds that a tool's declared contract and a skill's advertised steps already diverge from their actual code and behavior before any self-editing is involved ([section-tool-security-draft.md](section-tool-security-draft.md), citing SkillCFI and ACaM), so a harness that lets an agent write or revise its own skills and tool wrappers inherits a verification gap that static, human-authored tools have not closed either.
6. Across 932,791 agent pull requests, coding agents already escalate authority in CI/CD pipelines at rates that vary by agent with no self-improvement loop involved ([Staron, arXiv:2611.23251](https://arxiv.org/abs/2611.23251), via [section-tool-security-draft.md](section-tool-security-draft.md)), so a harness that can rewrite its own tool rules or permission settings raises a risk that is already unmeasured and ungoverned before any self-editing is added.
7. No source in this round, and no vendor in our own browser-use research, documents an audit trail of who or what approved a change, whether that change is a self-edit to a harness or a human's takeover of an agent's browser, leaving the same missing record in both cases ([browser-use.md, "Watching and shared control"](../../browser-use/browser-use.md#the-owner-can-watch-and-take-over-the-in-sandbox-browser-through-the-tasks-durable-object-which-on-cloudflare-opens-no-sandbox-port)).
