# Seven seams let our harness deploy anywhere

Our SDK already runs on every target the owner named, because the planned gateway uses only `fetch`, Web Streams and Web Crypto behind an injectable `Transport`. The harness is the part tied to one host, and it is tied in six places: the JSONL session store, the lock file with its pid check, the file key ring, the spawned `srt` and Docker sandboxes, the loopback credential proxy, and the Node-stream stdio transport. Seven adapter seams fix that without touching the loop. Two already exist in the plan as interfaces with only a file implementation: a `SessionLock`, and a `KeyStore` whose `rotate()` must become optional. Five are new: a `Scheduler` (wake-at), a `SecretSource` for the bring-your-own model key, remote `SandboxClient` backends that resume by id, an `EgressPolicy` compiled per backend, and a transport typed over Web streams. Cloudflare (from 2 October 2026) and Vercel (from 19 October 2026) each shipped this same adapter layer for third-party harnesses, which is the strongest evidence that these seams are the right ones ([Cloudflare changelog](https://developers.cloudflare.com/changelog/); [Cloudflare Agents harnesses](https://developers.cloudflare.com/agents/harnesses/); [Vercel blog, 19 October 2026](https://vercel.com/blog/making-every-harness-durable); [Vercel agent harnesses](https://vercel.com/docs/agent-harnesses)).

The same research covers three more questions, with every figure as of November 2026. A cloud coding agent like Claude Code on the web needs about seven components our plans do not have: a control plane, an environment build-and-snapshot cache, a GitHub App identity, PR delivery with webhook follow-ups, triggers, a network transport with multi-client attach, and notifications. Among hosted sandboxes, E2B, Vercel, Cloudflare and Daytona (Tier 3 and above) meet our three hard rules: fail closed, no credentials inside the sandbox, and a network allowlist. Browser sandboxes such as WebContainers are worth having only as an interactive, cost-saving backend that the harness drives over its protocol. They cannot enforce a network allowlist or write roots, and their results can be forged. We therefore recommend adding the seven seams, supporting E2B first, Cloudflare Sandbox second and Vercel Sandbox third, and keeping the browser as a relayed backend.

## Runtimes split into an isolate tier and a process tier

"Deploy anywhere" means two different things, because the five first-class targets offer two kinds of compute. The **isolate tier** covers Cloudflare Workers and Durable Objects and the Vercel Edge runtime. Only the SDK and a harness backed by an external store can run there. The **process tier** covers containers (Cloud Run, Fargate, Azure Container Apps, Fly Machines, Kubernetes), Lambda and Vercel's Node functions. The full harness runs there, but no local disk survives an instance unless a volume is attached, such as a Fly volume or a Kubernetes persistent volume; Fargate's 20–200 GiB task storage is ephemeral ([Fargate task storage](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/fargate-task-storage.html)). Cloudflare, AWS, Vercel and Azure each ship a durable-wait primitive, and Cloud Run has none built in, so a long approval wait is portable only if the pause is plain data that any trigger can resume.

On Cloudflare, an HTTP-triggered Worker has **no hard wall-clock limit while the client stays connected**. CPU time is 30 s by default on the Paid plan and configurable to 5 minutes, and time spent waiting on `fetch()` does not count. Cron Triggers, alarms and queue consumers stop at 15 minutes, and `ctx.waitUntil()` buys only 30 s after the response ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)). Memory is **128 MB per isolate**, and the bundle limit is 64 MiB uncompressed. The Workflows limits page still quotes 3 MB and 10 MB script sizes, so the two Cloudflare pages disagree, and the Workers page should be treated as authoritative ([Workflows limits](https://developers.cloudflare.com/workflows/reference/limits/)). The decisive restriction for our harness is that **`node:child_process` is an import-only stub with no working implementation**, and that `/tmp` is writable but "not persistent and are unique to each request" ([Node.js compatibility](https://developers.cloudflare.com/workers/runtime-apis/nodejs/); [Workers node:fs](https://developers.cloudflare.com/workers/runtime-apis/nodejs/fs/)).

Durable Objects, Workflows and Containers supply what Workers lack: state, durable waits and a process to spawn. Each object gets SQLite storage of up to 10 GB, rows of up to 8 MB, CPU that resets with every request or WebSocket message, at-least-once alarms, and WebSocket hibernation that keeps clients connected while the object is out of memory ([DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/); [DO Alarms](https://developers.cloudflare.com/durable-objects/api/alarms/); [DO WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)). Workflows add `step.waitForEvent`, whose default timeout is 24 hours, and `step.sleep` for up to 365 days ([Workflows events](https://developers.cloudflare.com/workflows/build/events-and-parameters/); [Workflows limits](https://developers.cloudflare.com/workflows/reference/limits/)). Containers and the Sandbox SDK run Firecracker microVMs that a Durable Object controls ([Sandbox overview](https://developers.cloudflare.com/sandbox/); [Containers docs](https://developers.cloudflare.com/containers/llms-full.txt)).

AWS Lambda stops at **900 s**, except that Lambda Managed Instances allow 90 minutes for async invocations. It gives up to 10 GB of `/tmp` per execution environment and streams responses on Node through function URLs ([Lambda quotas](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html); [response streaming](https://docs.aws.amazon.com/lambda/latest/dg/configuration-response-streaming.html)). Lambda durable functions run "for up to one year" by checkpoint and replay. Their waits bill no compute, and AWS names human-in-the-loop as the use case ([Lambda durable functions](https://docs.aws.amazon.com/lambda/latest/dg/durable-functions.html)). Vercel Functions cap duration at 300 s by default and 800 s at most, with 1,800 s in beta. Native WebSockets are in public beta and close when the function reaches its maximum duration. Vercel points to Workflows for "unlimited execution time" ([Vercel Functions limits](https://vercel.com/docs/functions/limitations); [Vercel KB: WebSockets](https://vercel.com/kb/guide/do-vercel-serverless-functions-support-websocket-connections)). Cloud Run allows a request of up to 60 minutes and job tasks of up to 7 days, but its writable file system lives in memory ([request timeout](https://cloud.google.com/run/docs/configuring/request-timeout); [task timeout](https://cloud.google.com/run/docs/configuring/task-timeout); [container contract](https://cloud.google.com/run/docs/container-contract)). On Azure, Container Apps ingress times a request out at 240 s, an HTTP-triggered Function must respond within 230 s whatever its timeout setting, and Durable Functions wait on `waitForExternalEvent("Approval")` ([ACA ingress](https://learn.microsoft.com/en-us/azure/container-apps/ingress-overview); [Functions hosting](https://learn.microsoft.com/en-us/azure/azure-functions/functions-scale); [Durable Functions external events](https://learn.microsoft.com/en-us/azure/azure-functions/durable/durable-functions-external-events)).

| Runtime | Longest single run | Durable wait | Local disk | Subprocess |
| --- | --- | --- | --- | --- |
| Cloudflare Workers | unlimited while connected; CPU ≤ 5 min; alarms 15 min | DO alarms; Workflows (24 h default event wait, 365 d sleep) | per-request `/tmp` | no |
| Durable Objects | unlimited while I/O is in flight | alarms, SQLite 10 GB | none | no |
| Cloudflare Containers / Sandbox | microVM driven by a DO | via the DO | 2–20 GB | yes |
| AWS Lambda | 15 min (90 min Managed Instances) | durable functions, Step Functions (1 yr each) | `/tmp` ≤ 10 GB, ephemeral | yes |
| Vercel Functions | 300 s / 800 s / 1,800 s beta | Vercel Workflows hooks | not researched | not researched |
| Cloud Run | 60 min request; 7 d job | none built in | in memory | yes |

Two smaller findings shape the target list. **Deno Deploy "will be sunset in April 2027"**, so it should not be a first-class target, although Deno as a runtime inside containers still matters ([Deno Deploy docs](https://docs.deno.com/deploy/)). And `AsyncLocalStorage` plus trace flushing are the recurring sharp edges on isolates. OpenAI's Agents SDK gives Workers only "limited support", with traces that must be flushed by hand and some that are inaccurate because of `AsyncLocalStorage` limits ([OpenAI Agents JS troubleshooting, v0.21.0](https://github.com/openai/openai-agents-js/blob/v0.21.0/docs/src/content/docs/guides/troubleshooting.mdx)). LangGraph ships a separate `./web` entry for runtimes without async context, by our inspection of the installed package.

## The SDK travels; the harness is bound to one host in six places

The other frameworks show where portability comes from. The portable ones keep the loop pure and push durability into a pluggable store or a separate engine. The Workflow SDK runs the same code "locally..., on Vercel..., or on any infrastructure using **Worlds**, which are pluggable adapters that handle storage, queuing, and communication" ([Workflow SDK deploying](https://workflow-sdk.dev/docs/deploying)). Cloudflare's `PiHarness` gives Pi storage in the Durable Object's SQLite and replaces Pi's in-memory scheduler, which "an evicted object has none" of, with a heartbeat driven by Pi's `wake()`. Cloudflare's harnesses page runs Claude Code and Codex in a "Linux container driven by a Durable Object", where "container loss fails or retries the turn" ([Cloudflare Pi harness](https://developers.cloudflare.com/agents/harnesses/pi/); [Cloudflare harnesses](https://developers.cloudflare.com/agents/harnesses/)). Vercel's beta durable harness resumes Pi, OpenCode, Claude Code and Codex "from the session's log" after a crash, timeout or redeploy ([Vercel agent harnesses](https://vercel.com/docs/agent-harnesses)). Process-based SDKs reach isolate hosts only as a container driven by a coordinator: the Claude Agent SDK "spawns and supervises a `claude` CLI subprocess that owns a shell, a working directory, and session files on disk" ([Claude Agent SDK hosting](https://code.claude.com/docs/en/agent-sdk/hosting.md)). Every one of these adapters uses the same three seams: a transcript store, a wake or schedule mechanism that replaces in-memory timers, and a sandbox that may be remote. None of them changed the loop.

Measured against those seams, the SDK plan is already portable. Its gateway "has no runtime dependencies", calls `type Transport = (request: Request) => Promise<Response>`, and exposes `clock`, `idGenerator` and `random` as public seams ([SDK plan §3.1–3.4](../../plans/build-sdk.md#31-two-packages-under-a-new-top-level-packages-directory)). Three SDK details still need attention. First, the default `ephemeralSigner()` from D5 strands every pause on any serverless host, because isolates and Lambda environments recycle between pause and resume ([SDK plan D5](../../plans/build-sdk.md#d5-a-pluggable-signer-with-key-ids-an-ephemeral-default-and-no-unsigned-resume-accepted-with-hd5)). Second, D7's pi-schema declares `node >=22.19.0`, and nobody has tested whether it loads in workerd; `@cfworker/json-schema` is the known-good fallback ([SDK plan §2](../../plans/build-sdk.md#2-decisions)). Third, the OTel observer must take its context explicitly rather than from ambient `AsyncLocalStorage`, and expose a `flush()` that a host can hand to `waitUntil`.

The harness plan is bound to one host by its own decisions, and its non-goals say so. HD2's lock creates `<session>.lock` with `open(path, "wx")`, renews it every 10 s, and treats it as stale only when the lease has lapsed and the pid is gone on the same host. The plan rejects an actor per session because that "suits a server, which is a non-goal" ([HD2](../../plans/build-harness.md#hd2-a-lock-file-with-a-renewed-lease-on-local-disk-only-provisional)). HD4's backends spawn the `srt` and `docker` binaries. HD5 assumes "one host process per session" with a key ring at `$XDG_STATE_HOME/agent-speak/keys.json`. HD15's proxy listens on `http://127.0.0.1:<port>`, which on a remote sandbox is the sandbox's own loopback. And `stdioTransport` takes `NodeJS.ReadableStream` ([harness plan §1–3](../../plans/build-harness.md#1-goal-and-non-goals)). The table maps each part to the adapter it needs. All adapters here are our design, and none has been built or tested.

| Plan part | Runs on Workers as planned? | Adapter needed |
| --- | --- | --- |
| Gateway, loop, tools, retries (B4–B14) | yes; CPU, the six-connections-awaiting-headers cap and the subrequest count are the limits | none beyond `Transport`; a workerd smoke test in B10 |
| Signed pauses (B15, D5) | the signature yes, the ephemeral key no | the plan's `KeyStore` with `rotate()` and `prune()` made optional, backed by a Worker secret, Secrets Store, Secrets Manager, Key Vault or Vercel secret |
| `SessionStore` (N2, N3) | interface yes, `jsonlStore` no | `doSqliteStore`, `d1Store`, `dynamoStore` (conditional put on `seq`), `postgresStore`, object-store segments; N3's conformance suite runs against each |
| HD2 lock (N4) | no pid, no host, no persistent file | more implementations of the plan's `SessionLock` (today only `fileLock`): a DO single writer, a DynamoDB, Cosmos or Postgres lease; off-host staleness becomes lease-only |
| Lease renewal and timers | `setInterval` dies when the request ends | `Scheduler.wake(at)`, backed by DO alarms (one per object, multiplexed through storage) or a queue's delayed message |
| HD4 sandboxes (N15–N19) | no | remote `SandboxClient` backends with `resume(id)` and a snapshot capability flag |
| HD15 credential proxy (N20) | no | `EgressPolicy { allow, routes }` compiled per backend, replacing a URL from `startEgressProxy()` |
| Transports (N26–N30), stdio MCP (N24), CLI, evals | dispatcher yes; stdio and CLI process tier only | `stdioTransport` over Web `ReadableStream`/`WritableStream`; a WebSocket transport (DO hibernation, Vercel WS beta) |
| Extensions, skills, trust store (N22, N23) | reads from disk | read from `/bundle` or an object store; writes through a store adapter |

Our signed pause needs no new design for long waits. A run ends in `awaiting_approval`, the `approval_requested` entry is written before any client is asked, and resume re-runs the permission pipeline ([HD5](../../plans/build-harness.md#hd5-the-harness-always-passes-hmacsigner-over-a-persistent-key-ring-accepted-with-sdk-d5)). The pause needs only a durable store, a persistent key and any trigger that can call `continueRun`, so it maps onto every engine as an adapter. On a Durable Object, the entry goes into SQLite, an optional alarm enforces the deadline, and the approver's message reaches the same object by session id. The Durable Object is the closest fit, and close to Cloudflare Agents' own `needsApproval` flow.

Workflow engines need one more rule, because they replay code. The engines are Cloudflare Workflows, Lambda durable functions, Step Functions, Vercel Workflows and Durable Functions. Our loop is not deterministic across model calls, so an engine should hold only the wait and the wake, with **one engine step per `continueRun` and never the inner loop**, and with entry ids rather than transcripts in the payload, since Workflows caps event payloads and step results at 1 MiB ([Workflows limits](https://developers.cloudflare.com/workflows/reference/limits/)). At-least-once alarms and replayed steps make idempotency mandatory. The rule from our server-rollback research applies directly: a tool call id deduplicates only after it is persisted before execution and scoped to `(tenant, session, branch, tool_call_id)` ([server rollback report](../../research/reversible-actions/server-rollback.md#tool-call-ids-make-good-idempotency-keys-only-after-they-are-persisted-and-scoped)). Vercel's 300–1,800 s function limits and Azure's 230 s HTTP limit also rule out `blockingApprovals()` on those hosts, which the harness already refuses to use.

| --- | --- | --- | --- | --- |
| Cloudflare (Workers + DO) | DO SQLite, one object per session; the object is the single writer; D1 or R2 for listing | Cloudflare Sandbox microVM | Worker secret or Secrets Store; `outboundByHost` handler | DO entry + alarm, or Workflows `waitForEvent` |
| AWS (Lambda, Fargate) | DynamoDB with a conditional write on `seq` and a lease row | Fargate task as the sandbox, or a hosted microVM; never from Lambda itself | Secrets Manager through the Lambda extension or ECS `secrets`; HD15 proxy as a Fargate sidecar | DynamoDB entry + function-URL resume; durable functions or a Step Functions task token |
| GCP (Cloud Run) | Firestore or Cloud SQL Postgres; advisory-lock or transaction lease | Cloud Run job or GKE Sandbox, or a hosted microVM | Secret Manager as env var or volume; proxy as a sidecar | store + new request |

The bring-your-own-key requirement fits one rule. The model key belongs to the gateway in the host process. The plan's `ProviderConfig` already takes `apiKey` as a string, and a `SecretSource` would let the host fetch and refresh it ([SDK plan §3.2](../../plans/build-sdk.md#32-gateway-api)). It arrives through a `SecretSource` passed into `createModel`, never read from `process.env` inside the SDK, and never reaches the sandbox. Each target has a native source: Worker secrets and the account-level Secrets Store on Cloudflare, Secrets Manager injected as ECS task `secrets` on AWS, Secret Manager on Cloud Run, Key Vault references through a managed identity on Azure, and write-only Secret env vars on Vercel ([Workers secrets](https://developers.cloudflare.com/workers/configuration/secrets/); [Secrets Store with Workers](https://developers.cloudflare.com/secrets-store/integrations/workers/); [ECS sensitive data](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/specifying-sensitive-data-secrets.html); [Cloud Run secrets](https://cloud.google.com/run/docs/configuring/services/secrets); [Container Apps secrets](https://learn.microsoft.com/en-us/azure/container-apps/manage-secrets); [Vercel sensitive env vars](https://vercel.com/docs/environment-variables/sensitive-environment-variables)). Env-var secrets are read-only, so key-ring rotation needs the optional `rotate()` half of `KeyStore`. Vercel redacts Secret values only in build logs and only at 32 characters or more, so `scrubSecrets` stays necessary before every append.

## Cloud coding agents are a control plane around a disposable VM

Six products, Claude Code on the web, Codex Cloud, Copilot in the cloud, Jules, Cursor Cloud Agents and Devin, converge on one shape. A control plane owns the session and the credentials. Each task or session runs in an isolated Linux VM booted from a cached snapshot of "base image plus setup script". A host-side egress proxy enforces an allowlist. The output is a branch or pull request, and a human merge is the only commit point. Claude gives "each session... a fresh virtual machine (VM) running Ubuntu 24.04", with ceilings of about 4 vCPUs, 16 GB RAM and 30 GB disk. After a setup script that finishes in roughly five minutes, "Anthropic snapshots the filesystem and reuses that snapshot"; the snapshot keeps disk state, not running processes, and rebuilds after about seven days ([Configure cloud environments](https://code.claude.com/docs/en/cloud-environments)). An idle VM pauses with its files saved. A reclaimed one comes back as a fresh VM that restores the conversation but not running shells or subagents ([Configure cloud environments](https://code.claude.com/docs/en/cloud-environments); [Claude Code on the web](https://code.claude.com/docs/en/claude-code-on-the-web)). Cursor names its substrate, "Firecracker-based microVM infrastructure" in a separate AWS account, and spells out a six-step lifecycle: start, provision, run, persist, hand off as a PR, recycle ([Cursor security overview](https://cursor.com/docs/cloud-agent/security)). Devin splits a stateless "Brain" in Cognition's cloud from a "Devbox" VM per session ([Devin deployment](https://docs.devin.ai/enterprise/deployment/overview)). The products differ mainly in where secrets live and in how long a sandbox lives.

The credential split is the design choice that matters most for us. Anthropic, OpenAI and LangChain's Open SWE keep secrets outside the VM and substitute them at a proxy. Claude's "GitHub credentials stay encrypted on Anthropic's servers and never enter a session's VM", `GH_TOKEN` reads as the placeholder `proxy-injected`, and network secrets are added "after each request leaves the session's VM" ([Claude Code on the web](https://code.claude.com/docs/en/claude-code-on-the-web); [Configure cloud environments](https://code.claude.com/docs/en/cloud-environments)). In Codex, "Programs receive a placeholder; the proxy substitutes the real value for allowed destinations" ([Codex cloud environments](https://developers.openai.com/codex/environments/cloud-environments)). Cursor and Devin instead put secrets into the VM as environment variables and redact them from output: Cursor's Runtime Secrets are redacted in transcripts but "still visible to users interacting with the agent's environment via the Terminal" ([Cursor secrets and network](https://cursor.com/docs/cloud-agent/security-network); [Devin secrets](https://docs.devin.ai/product-guides/secrets)). The proxy model is our HD15. The in-VM model leaks to anything the agent runs. Every vendor's network control also has a documented hole. GitHub says its firewall covers only processes started through the agent's Bash tool and that "Sophisticated attacks may bypass the firewall". Anthropic's GitHub proxy "doesn't limit which branches a push can update" ([Copilot firewall](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/customize-the-agent-firewall); [Configure cloud environments](https://code.claude.com/docs/en/cloud-environments)). Branch scope is therefore the git host's job, through rulesets, not the proxy's.

The open-source projects show two placements of the loop. OpenHands V1 runs the whole loop in an in-container agent server and streams events over WebSocket. It split from V0 because "the sandbox for tools might crash while the agent continued (or vice versa), leading to corrupted sessions". Its event-sourced log recovers from a crash in under 20 ms, and in a 15-day production comparison V1 cut system-attributable failures by 61% against V0 ([Wang et al., arXiv 2511.03690](https://arxiv.org/html/2511.03690)). mini-swe-agent and Open SWE keep the loop outside and send each command in. mini-swe-agent's environment is "literally just switch out `subprocess.run` with `docker exec`" ([mini-swe-agent README](https://github.com/SWE-agent/mini-swe-agent/blob/04d809ceab9df28f9adaed044884180159172930/README.md)). Open SWE's coding sandboxes "rely on the LangSmith proxy for the real credentials", but the proxy token "is minted at runtime from the GitHub App installation credentials", so its scope is the installation's, which is the common scope weakness ([Open SWE CUSTOMIZATION.md](https://github.com/langchain-ai/open-swe/blob/1965cd136a1ba6b02ea486e8caee04fde7c2e858/docs/CUSTOMIZATION.md)). For us, **the loop belongs in a runner next to the sandbox, not inside it**. A runner outside the box keeps HD15 and the model key off it, makes a sandbox crash recoverable from the log, and matches Cursor and Devin. Cursor's self-hosted workers receive tool calls over an outbound connection while "the agent loop, inference, and planning" stay with Cursor ([Cursor self-hosted machines](https://cursor.com/docs/cloud-agent/self-hosted)).

Our harness plan already covers the inside of the box: the sandbox interface and Docker backend, a default-deny proxy with sentinels, a log that is the only source of truth with second-process resume, a JSON-RPC protocol with reconnect, completion checks, and evals against mini-swe-agent. A cloud agent adds the outside of the box. The table lists each outside part, what the plan covers today and what we would add.

| Cloud-agent component | Plan coverage | What we would add |
| --- | --- | --- |
| Control plane | none | session registry, task queue, runner claim with a per-owner lock, autoscaler; Claude's self-hosted model places sessions on a queue that a runner claims ([self-hosted environments](https://code.claude.com/docs/en/self-hosted-environments)) |
| Environment build and cache | none | setup-script runner, snapshot store keyed on image, script and allowlist, invalidation rules, a per-session start hook (Claude's setup script versus SessionStart hook; Codex's install script versus start skill) |
| Remote sandbox | N15 interface only | hosted microVM adapter with `pause`, `resume` and `snapshot`, as in OpenHands' `BaseWorkspace` |

| Credential proxy and egress | HD15, N20 | GitHub as a first-class route (Basic for git over HTTPS, Bearer for the API); a "never attach" list; live policy updates; method filters such as Codex's GET, HEAD and OPTIONS mode ([Codex internet access](https://developers.openai.com/codex/cloud/internet-access)); blocked-request reports in the PR |

| Protocol and clients | stdio first; network a non-goal | WebSocket or HTTP transport, multi-client attach, follow-ups queued while provisioning, per-client auth |
| Triggers | none | GitHub App webhooks, Slack, Linear, schedules; accept only users with write access and strip hidden HTML, as Copilot does |
| PR delivery and follow-up | none | draft PR, webhook subscription, auto-fix loop, explicit handling of base-branch conflicts, which emit no webhook ([Claude Code on the web](https://code.claude.com/docs/en/claude-code-on-the-web)) |
| Notifications, tenancy, cost | HD9 session cap | push, email or Slack on "needs input", "done" and "failed"; per-tenant budgets, concurrency caps and per-vCPU-second compute metering beside model cost |

Two of these deserve ADRs before code. The snapshot cache is the largest new design. The GitHub identity, meaning installation-token scope and push rules, is second. Triggers overlap with the ingress gap that our 12-factor report already found ("we have no design for how ticket and approval events reach the agent"), so one ingress design with at-least-once deduplication should serve both the triage agent and a coding agent ([12-factor report](../../research/external-designs/twelve-factor-agents.md#five-small-changes-follow-led-by-an-ingress-design)). Our Copilot report adds the delivery rule: the cloud agent's draft PR is the only Copilot surface that holds the whole change for one human decision, so the PR, not a per-call prompt, is the natural commit point for a coding agent ([Copilot diff review report](../../research/agent-ui/copilot-diff-review.md)). Evals need a cloud mode that counts provisioning time and infra failures, because sandbox start and snapshot hits dominate wall time and no vendor publishes them.

## Four hosted sandboxes meet our three hard rules, and E2B should come first

Almost every serious hosted option now isolates each sandbox in a VM. **E2B, Vercel, Cloudflare and Fly use Firecracker**; Northflank uses Cloud Hypervisor or gVisor, by its marketing page; Modal uses gVisor or a VM; Azure dynamic sessions use Hyper-V ([E2B restrict public access](https://docs.e2b.dev/network/restrict-public-access); [Vercel security model](https://vercel.com/docs/sandbox/concepts/security); [Cloudflare Containers](https://developers.cloudflare.com/containers/llms-full.txt); [Fly architecture](https://fly.io/docs/reference/architecture/); [Northflank sandboxes](https://northflank.com/product/sandboxes); [Modal Sandboxes](https://modal.com/docs/guide/sandboxes); [ACA dynamic sessions](https://learn.microsoft.com/en-us/azure/container-apps/sessions)). Our harness guide's tier table lists "Firecracker (E2B, Vercel)" and should add Cloudflare and Fly.

**Daytona is the exception, and this corrects an earlier fix in our own log.** Round R1 of the harness fact-check changed "27–90 ms on containers" to say each Daytona sandbox has "a dedicated kernel", citing Daytona's docs overview and landing page ([agent-harness fact-check, R1](../../research/agent-harness/fact-check.md)). Daytona's Isolation page now says the default **Container** class is an "Isolated container with dedicated namespaces and enforced resource limits". Only the Linux VM and Windows classes are a "Full virtual machine with its own kernel", and only they support pause, resume, fork and memory snapshots. GPU sandboxes are containers too ([Daytona docs, llms-full.txt generated 2026-11-17](https://www.daytona.io/docs/llms-full.txt)). The docs overview and the landing page still say each sandbox gets "a dedicated kernel", which explains the R1 error. The original "on containers" was right for the default class, so R1 now has a superseding ✏️ row: Daytona's default class shares the host kernel, and its `tier` in our interface depends on the class ([agent-harness fact-check, U11](../../research/agent-harness/fact-check.md#daytona-isolation-re-checked-u11-2026-11-18)). Daytona has also moved: "As of June 2026, Daytona's core development has moved to a private codebase", with AGPL-3.0 at v0.190.0 as the last public licence, so new Daytona code is closed and reaches users only through the hosted service ([daytonaio/daytona README](https://raw.githubusercontent.com/daytonaio/daytona/main/README.md)).

The R1 prices stand, but they omitted memory, which both providers bill separately. E2B charges $0.0000045 per GiB-second, and Daytona $0.0162 per GiB-hour plus storage ([E2B pricing](https://e2b.dev/pricing); [Daytona pricing](https://www.daytona.io/pricing)). Change 12 below adds both figures to the harness guide.

Providers split sharply on egress control, which decides fit with our interface. `SandboxClient` promises `tier`, `stops`, and a `provision(manifest, policy)` that throws `SandboxUnavailableError` rather than run unsandboxed. Its conformance suite requires network denied unless allowlisted and an environment holding only `spawnEnv` names ([harness plan §3.4](../../plans/build-harness.md#34-permission-approval-and-sandbox-apis)). `exec`, `readFile`, `writeFile` and `dispose` map onto every TypeScript SDK. The adapter work sits in translating `SandboxPolicy.network` to each vendor's allowlist, killing on `signal`, and producing a typed denial, which no vendor reports.

Four hosted providers now ship HD15's pattern natively, in two variants, and Modal ships it in beta. Daytona's is closest to ours: "the sandbox holds an opaque placeholder token", swapped only when "the request goes to a host you have allowed". Cloudflare's outbound handlers "run in the Workers runtime — outside the sandbox — they can hold secrets that the sandbox itself never sees", and the documented credential example sends plain HTTP to the handler with no CA. Cloudflare's handler is HD15's reverse-proxy route almost verbatim, and it can check the method as HD15 does. For HTTPS, Containers can also intercept with an ephemeral Cloudflare CA. E2B, Vercel and Modal inject by intercepting TLS with a CA the vendor issues, which HD15 chose to avoid locally. Of these, Vercel's rule matchers can also check the method ([Vercel firewall](https://vercel.com/docs/sandbox/concepts/firewall)). The vendor owns that CA, though, so we do not build it ([Daytona secrets](https://www.daytona.io/docs/llms-full.txt); [E2B secrets](https://docs.e2b.dev/secrets)).

Each native injector leaves a scope gap that our adapter must close. E2B injects into "every process in the sandbox that sends an HTTPS request to that host" and silently omits a header whose secret fails to resolve. Daytona substitutes "A secret without an allowlist... for every host", so the adapter must always set hosts. Vercel's `subnets.allow` bypasses brokering and leaves DNS open ([E2B inject](https://docs.e2b.dev/secrets/inject)). Where method scoping matters, the adapter should front the provider with our own proxy, through E2B's fail-closed BYOP, Daytona's `outboundProxyUrl` or a Modal sidecar. Two more rules follow. The adapter should read back the effective network policy after `provision` and throw on a mismatch, which catches Daytona's org-level overrides. It should also compute `stops` from the policy it applied: a microVM with open egress stops `hostile_process` but not `exfiltration`. The sandbox provider's own API key is a second secret. OpenAI's docs record that its `VercelSandboxClient` keeps the Vercel token in serialized session state, a concrete leak path into N3's store ([OpenAI sandbox clients, v0.21.0](../../reference/openai-agents-sdk/source/docs/src/content/docs/guides/sandbox-agents/clients.mdx)).

The support order follows from fit and portability, and it is our recommendation. **E2B comes first** among hosted backends. It has the richest egress and secret model, Apache-2.0 infrastructure for self-hosting or BYOC, workload-identity tokens for short-lived cloud credentials, and an SDK that is documented to run even in browsers, which suggests it will run from any of our targets ([E2B workload identity](https://docs.e2b.dev/iam/workload-identity); [E2B streaming](https://docs.e2b.dev/commands/streaming)). E2B Pro costs $150 a month with a 24-hour continuous runtime, and a paused sandbox "is kept indefinitely" ([E2B billing](https://docs.e2b.dev/billing)). **Cloudflare Sandbox comes second**, as the native backend for a Workers-hosted harness, because "If your application runs outside of the Workers ecosystem, it cannot interact with sandboxes directly". **Vercel Sandbox comes third**: persistent by default, 24-hour sessions on Pro, and billed on active CPU at $0.128 an hour plus provisioned memory at $0.0212 per GB-hour ([Vercel Sandbox pricing](https://vercel.com/docs/sandbox/pricing)). Defer Daytona for its tier-gated allowlists and closed source, and Modal for its beta allowlist and open DNS. Use Azure dynamic sessions and Cloud Run sandboxes only as no-network code interpreters.

Two practical constraints shape the first adapters. First, AWS and GCP have no native backend that meets the allowlist rule on the pages read, so their first-class adapter is a Fargate task or Cloud Run job running our Docker-style image with the HD15 proxy as a sidecar. This sidecar design is our inference, not a documented pattern. Second, pinning: `e2b` 2.64.0 and `@vercel/sandbox` 4.0.0 were under a week old on 2026-11-18, so a verify harness must pin the previous release of each, 2.63.0 and 3.9.1, to satisfy the one-week rule in AGENTS.md. The Vercel pin is a major version back.

## Browser sandboxes save compute but cannot hold the credential boundary

WebContainers give an agent a Node.js runtime inside a browser tab: a file system, `npm` and `pnpm` installs, spawned processes with a pseudo-terminal, and dev servers with preview URLs. "WebContainers can only execute languages that are natively supported on the Web, including JavaScript and WebAssembly", and native addons are disabled ([Troubleshooting](https://webcontainers.io/guides/troubleshooting)). The `@webcontainer/api` 1.6.4 client is MIT, but the runtime is "hosted on StackBlitz" and closed. "Licensing is required for production usage of the API in a commercial, for-profit setting", and no price is published ([API support](https://webcontainers.io/guides/api-support); [npm](https://registry.npmjs.org/@webcontainer/api); [Commercial usage](https://webcontainers.io/enterprise)). "Only a single instance of WebContainer can be booted concurrently", the page must be cross-origin isolated with COOP and COEP headers, and support is "desktop Chromium-based browsers out of the box", with Safari and Firefox in beta ([API reference](https://webcontainers.io/api); [Configuring headers](https://webcontainers.io/guides/configuring-headers); [Browser support](https://webcontainers.io/guides/browser-support)). Third-party cookie blocking breaks the per-project Service Worker ([Browser configuration](https://webcontainers.io/guides/browser-config)). bolt.new's open-source snapshot shows the reference architecture. The API key stays on the server in a Remix app on Cloudflare, the server streams `file` and `shell` actions with `toolChoice: 'none'`, and the tab applies them with `webcontainer.spawn('jsh', ['-c', ...])`. Its prompt tells the model "Git is NOT available" and that there is "NO `pip` support" ([bolt.new api.chat.ts](https://github.com/stackblitz/bolt.new/blob/main/app/routes/api.chat.ts); [action-runner.ts](https://github.com/stackblitz/bolt.new/blob/main/app/lib/runtime/action-runner.ts); [prompts.ts](https://github.com/stackblitz/bolt.new/blob/main/app/lib/.server/llm/prompts.ts)). bolt.new's design is a one-shot stream rather than a tool loop: command output never flows back to the model inside a turn.

The alternatives trade capability against licence. BrowserPod 4.1.0 is the only in-browser option that ships Node 22 together with git, bash, npm and pnpm, persists to IndexedDB or OPFS, and as of its Community Licence of 13 November 2026 is "free for any use — personal, commercial and production — as long as you credit it". Its runtime loads from Leaning Technologies' CDN. CORS-free egress needs the separate BrowserPod Edge service, which works under an allowlist, and custom allowlists need the paid Edge Pro plan ([BrowserPod LICENSE](https://unpkg.com/browserpod@4.1.0/LICENSE.txt); [BrowserPod README](https://unpkg.com/browserpod@4.1.0/README.md); [BrowserPod AGENTS.md](https://unpkg.com/browserpod@4.1.0/AGENTS.md)). These are vendor claims, and we tested none. Nodebox is under a Sustainable Use License and has not been published since 2023 ([Nodebox LICENSE](https://unpkg.com/@codesandbox/nodebox@0.1.9/LICENSE); [npm](https://registry.npmjs.org/@codesandbox/nodebox)). CheerpX, behind WebVM, allows businesses only "technical evaluation and testing" without a commercial licence ([CheerpX LICENSE](https://unpkg.com/@leaningtech/cheerpx@1.4.0/LICENSE.txt)). The permissive options do less. Pyodide (MPL-2.0) imports `multiprocessing`, `threading` and `sockets` but they "are not functional", v86 (BSD-2-Clause) emulates x86, and QuickJS in Wasm (MIT) runs model-written JavaScript with no `fetch` ([Pyodide constraints](https://pyodide.org/en/stable/usage/wasm-constraints.html); [v86](https://registry.npmjs.org/v86); [our hashbrown report](../../research/agent-ui/hashbrown.md)).

The browser is a strong boundary against a hostile process reaching the user's machine and a weak one against exfiltration. Egress is the page's `fetch` under CORS, which blocks many hosts but is not default-deny: any CORS-permissive endpoint is an open channel. StackBlitz's CORS proxy, which redirects external requests "to a proxy", effectively opens arbitrary hosts for paying editor users ([StackBlitz CORS proxy](https://blog.stackblitz.com/posts/cors-proxy)). `setPreviewScript` gives the embedder code execution in every preview origin, and `auth.init` hands the tab the signed-in user's private npm access ([API reference](https://webcontainers.io/api)). Five risks follow for us. First, no secret may sit in the page, so the model key, approval keys and the log stay server-side, and any per-user token goes through a server-side HD15 route. Second, WebContainers cannot pass our conformance rules, because they offer neither `writeRoots` nor a network allowlist. Third, results from the tab are untrusted input that the user, or code in the tab, can forge, so `completion_check` cannot be graded there. Fourth, the tab must stay open, which rules out headless runs and evals. Fifth, the runtime is fetched from a vendor CDN at boot, so our pinning rules cannot pin it.

The browser therefore fits only as a **relayed backend**. The harness keeps the loop, permissions, approvals, log and keys. A `browserSandbox()` client's `provision` waits for a connected client that advertises a sandbox capability, and `exec` and the file operations travel as the protocol's existing server-to-client `tool/call` requests ([HD6](../../plans/build-harness.md#hd6-strict-json-rpc-20-with-the-jsonrpc-field-and-twelve-v1-methods)). It needs a new tier value, `"browser"`, with `stops: ["hostile_process"]`, so that any policy requiring `exfiltration` refuses it. The new tier follows the guide's honest-tiers rule. It fails closed naturally: no tab, no exec. Moving the whole loop into the browser behind a server-side model proxy, the hashbrown and WebVM shape, would make the user's browser the host and break HD5's host-only key ring, so it suits a playground, not this harness. The browser's value is cost and latency, not isolation. Licensing makes BrowserPod the lower-friction candidate if the owner wants one, and WebContainers a poor default.

## Conclusion

Portability turns out to be mostly a storage-and-wake problem, not a compute problem. Every adapter Cloudflare, Vercel and the Workflow SDK built for someone else's harness reduces to a transcript store, a wake mechanism and a remote sandbox, and our signed pause already makes approvals plain data that any of them can resume. The real cost of "deploy anywhere" therefore sits in three local-host decisions: HD2's pid-checked lock file, HD5's file key ring and HD15's loopback proxy. Each was right for one machine, and each needs new implementations or a new interface rather than a rewrite. The credential boundary travels better than expected. Hosted sandboxes have converged on HD15's idea of keeping credentials outside the sandbox and injecting them at egress, and Cloudflare's outbound handler reproduces it almost exactly. Our boundary thus becomes a policy we compile per provider rather than a proxy we must host everywhere.

A cloud coding agent is a larger commitment than the harness itself. The parts that make Claude Code on the web or Cursor useful (the queue, snapshot cache, GitHub identity and PR follow-up loop) sit outside the loop, and so does the main security hole every vendor admits: a firewall that covers only some processes and a git token broader than one branch. If we build one, the evidence favours keeping the loop in a runner outside the VM and treating the PR as the commit point, so that a reclaimed VM costs a resume rather than a session. The two ADRs to write first are the snapshot cache and the GitHub identity. The questions that remain are measurable: cold-start and snapshot timings for each provider, whether pi-schema and the MCP client load in workerd, and AgentCore's network modes. Each has a change above that settles it, so the owner's next step is to choose which of the fifteen changes to adopt.
