# Runtime portability for a TypeScript agent SDK and harness (as of November 2026)

> **Fact-checked 2026-11-18.** This note keeps its original text. Corrections are logged in [fact-check-portable-agents.md](../fact-check-portable-agents.md) and applied in [the report](../portable-agents.md), which supersede this note where they disagree.

Scope: what each target runtime allows an agent workload to do, how existing agent frameworks handle portability, which parts of our SDK (P1, `docs/plans/build-sdk.md`) and harness (P2, `docs/plans/build-harness.md`) are runtime-bound, and how long human-approval waits fit short-lived runtimes. All pages below were fetched on 2026-11-18 with `curl -sSL --max-time 30`; Cloudflare pages were fetched as their `/index.md` Markdown variants. Pages that carry a "last updated" date are noted where it matters. Pinned package versions come from this repo's lockfile.

## Q1. Per-runtime capability matrix: time limits, streaming and WebSockets, timers and durable waiting, filesystem, subprocesses, Node compatibility, bundle and memory, durable storage, secrets

### Takeaway
Only container-style runtimes (Cloud Run, Fargate, Container Apps, Fly Machines, Kubernetes, Lambda's container images in a limited way) can spawn `srt`/`docker`, keep a writable local disk and run a stdio CLI. Workers, Vercel Functions, Lambda and Deno Deploy all cap or cut off work that outlives a request, have no persistent local disk, and in Workers' case cannot spawn processes at all. Every serverless platform now ships its own durable-wait primitive (Durable Object alarms, Cloudflare Workflows `waitForEvent`, Lambda durable functions, Step Functions task tokens, Vercel Workflows hooks), so a long approval wait is portable only if the pause is plain data that any trigger can resume.

### Cited Findings

**Cloudflare Workers (isolates)**
- CPU time per HTTP request: 10 ms on Free; on Paid 30 s by default, configurable up to 5 min (300,000 ms) via `limits.cpu_ms`. Waiting on `fetch()`, KV reads or database queries does not count toward CPU time. Cron Triggers on Paid get 15 min CPU for intervals of 1 hour or more — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- Wall-clock duration: "There is no hard limit on duration for HTTP-triggered Workers. As long as the client remains connected"; Cron Triggers, Durable Object alarms and Queue consumers are capped at 15 min. `ctx.waitUntil()` "can extend execution for up to 30 seconds after the response is sent or the client disconnects" — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- Runtime updates give in-flight requests, streaming responses and WebSockets up to 20 minutes to finish; "Crashes, resource pressure, and shutdowns can interrupt work earlier. Design long-running applications to handle disconnections and safely retry interrupted work" — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- Memory 128 MB per isolate (Free and Paid). Worker size 64 MiB uncompressed on both plans, "There is no compressed size limit". Startup time 1 s. Env vars 64 (Free) / 128 (Paid) per Worker, 5 KB each — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/). **Conflict:** the Workflows limits page still says "3MB max script size" (Free) / "10MB" (Paid) per Worker size limits — [Workflows limits](https://developers.cloudflare.com/workflows/reference/limits/). The report should cite the Workers limits page and flag the discrepancy.
- Outbound fetch: subrequests 50/request (Free), 10,000/request default on Paid, configurable up to 10M; "no set time limit on individual subrequests"; at most six connections "simultaneously waiting for response headers" per invocation (a connection stops counting once headers arrive) — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- Node compatibility: for compatibility dates of `2026-08-04` or later, `nodejs_compat` and `nodejs_compat_v2` are on by default; for dates `2024-09-23` through `2026-08-03` add the `nodejs_compat` flag. `AsyncLocalStorage`, `fs` and `net` are listed as supported. `node:child_process` is a **non-functional stub** (enabled as an import-only stub from compatibility date `2026-03-17`) — "can be imported or required, but does not provide a working implementation"; unsupported APIs are polyfilled by Wrangler via unenv — [Node.js compatibility](https://developers.cloudflare.com/workers/runtime-apis/nodejs/)
- Filesystem: `node:fs` gives a memory-based virtual file system; `/bundle` is read-only bundle modules; `/tmp` is writable but "not persistent and are unique to each request" — [Workers node:fs](https://developers.cloudflare.com/workers/runtime-apis/nodejs/fs/)
- Secrets: "Secrets are a type of binding that allow you to attach encrypted text values to your Worker", read like env vars through `env` or `import { env } from "cloudflare:workers"` — [Workers secrets](https://developers.cloudflare.com/workers/configuration/secrets/). An account-level Secrets Store "securely reusable across your account" also exists — [Secrets Store](https://developers.cloudflare.com/secrets-store/)
- Outbound WebSockets: "Cloudflare Workers and other workerd runtimes cannot open outbound WebSockets using the global `WebSocket` constructor"; a `fetch()` with `Upgrade: websocket` is required (secondary: stated by the OpenAI Agents SDK docs, not Cloudflare) — [OpenAI Agents JS, Cloudflare extension, v0.21.0 mirror](https://github.com/openai/openai-agents-js/blob/v0.21.0/docs/src/content/docs/extensions/cloudflare.mdx)

**Durable Objects (DO)**
- SQLite-backed DO: 10 GB storage per object, unlimited objects, key+value ≤ 8 MB, SQL row/BLOB ≤ 8 MB, statement ≤ 100 KB, 100 bound parameters; received WebSocket message ≤ 32 MiB; CPU 30 s default per request, configurable to 5 min, and "Each incoming HTTP request or WebSocket *message* resets the remaining available CPU time"; outbound HTTP request body 100 MiB — [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/)
- Wall time for DO RPC/HTTP: "No hard limit while the caller stays connected... Durable Objects remain active while a request, RPC call, response stream, WebSocket, or pending I/O is in flight"; alarm handlers 15 min — [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/)
- Alarms: one alarm per object at a time; "guaranteed at-least-once execution"; retried with exponential backoff from 2 s for up to 6 retries; docs recommend catching errors and rescheduling to retry indefinitely; multiple schedules are kept in storage and the handler reschedules itself — [DO Alarms API](https://developers.cloudflare.com/durable-objects/api/alarms/)
- WebSocket Hibernation API: "Clients remain connected while the Durable Object is not in memory" and duration charges do not accrue during hibernation — [DO WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)
- D1: 10 GB per database (Paid), 1,000 queries per invocation (Paid), row ≤ 2 MB, 30-day Time Travel — [D1 limits](https://developers.cloudflare.com/d1/platform/limits/)

**Cloudflare Queues, Workflows, Containers, Sandbox**
- Queues: message 128 KB, 100 retries, retention up to 14 days, consumer wall time 15 min, `delaySeconds` up to 24 h, pull `visibilityTimeout` 12 h — [Queues limits](https://developers.cloudflare.com/queues/platform/limits/)
- Workflows: per-step wall clock unlimited, per-step CPU 30 s default / 5 min max; step result ≤ 1 MiB; event payload ≤ 1 MiB; persisted state per instance 1 GB (Paid); `step.sleep` up to 365 days; 10,000 steps default (up to 25,000); 50,000 concurrent instances per account (Paid); completed-state retention 7 days default, up to 30 — [Workflows limits](https://developers.cloudflare.com/workflows/reference/limits/)
- `step.waitForEvent({ type, timeout })` pauses a running instance until `instance.sendEvent({ type, payload })` arrives via the Workers binding or HTTP; the default timeout is 24 hours; `type` allows letters, digits, `-` and `_` only — [Workflows events](https://developers.cloudflare.com/workflows/build/events-and-parameters/)
- Containers (page last updated Nov 12, 2026): instance types from `lite` (1/16 vCPU, 256 MiB, 2 GB disk) to `standard-4` (4 vCPU, 12 GiB, 20 GB); custom types allowed; account max per instance 4 vCPU / 12 GiB / 20 GB; outbound HTTP bodies through an outbound handler 100 MiB — [Containers limits](https://developers.cloudflare.com/containers/platform-details/limits/). Containers are started and controlled from a Durable Object with `ctx.container` — [Containers overview](https://developers.cloudflare.com/containers/)
- Sandbox: two environments. Containers: "Each instance is a microVM with its own kernel and network"; the sandbox uses the DO scheduling policy, "which is in public beta"; Workers Paid only. Dynamic Workers: load untrusted JS/Python/Wasm as a new Worker with `globalOutbound: null` to block egress — [Sandbox overview](https://developers.cloudflare.com/sandbox/)

**AWS Lambda, Step Functions, Fargate**
- Timeout 900 s (15 min); Lambda Managed Instances allow 5,400 s (90 min) for async and most event-source invocations. Memory 128–10,240 MB (one vCPU equivalent at 1,769 MB). `/tmp` 512–10,240 MB. Env vars 4 KB aggregate. Payload 6 MB sync request/response, 200 MB streamed response. Zip package 250 MB unzipped; container image 10 GB. 1,024 file descriptors and 1,024 processes/threads — [Lambda quotas](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html). The same page's banner names "Lambda MicroVMs" and "Lambda Web Functions"; these were not researched further.
- Response streaming works through function URLs, `InvokeWithResponseStream`, or API Gateway proxy integration; natively on Node.js managed runtimes only; first 6 MB uncapped then 2 MBps; "streamed responses are not interrupted or stopped when the invoking client connection is broken" and are billed for full duration — [Lambda response streaming](https://docs.aws.amazon.com/lambda/latest/dg/configuration-response-streaming.html)
- Lambda durable functions: executions "for up to one year" via checkpoint and replay; "waits suspend execution without incurring compute charges, making them ideal for... human-in-the-loop workflows"; on resume "your code runs from the beginning but skips over completed checkpoints"; SDK in JS/TS, Python, Java, Go, C# — [Lambda durable functions](https://docs.aws.amazon.com/lambda/latest/dg/durable-functions.html)
- Step Functions Standard: max execution 1 year, history 25,000 events; Express: 5 minutes — [Step Functions quotas](https://docs.aws.amazon.com/step-functions/latest/dg/service-quotas.html). `.waitForTaskToken` pauses until `SendTaskSuccess`/`SendTaskFailure` returns the token — [Step Functions service integration patterns](https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html)
- Secrets: the "AWS parameters and secrets Lambda extension" is "runtime-agnostic" with an HTTP interface and a local cache — [Lambda with Secrets Manager](https://docs.aws.amazon.com/lambda/latest/dg/with-secrets-manager.html)
- Fargate (platform 1.4.0+): at least 20 GiB ephemeral storage, up to 200 GiB — [Fargate task storage](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/fargate-task-storage.html). An ALB closes connections after an idle timeout and AWS advises sending "at least 1 byte of data before each idle timeout period elapses" — [ALB attributes](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-load-balancer-attributes.html)

**Vercel Functions and Fluid compute**
- Max duration: Hobby 300 s; Pro/Enterprise 300 s default, 800 s max (GA), 1,800 s extended max (beta). Memory: Hobby 2 GB, Pro/Ent 4 GB. Bundle 250 MB uncompressed (Python 500 MB; "large functions" up to 5 GB, beta, needs Fluid compute). Request/response body 4.5 MB (streamed responses exempt). 1,024 file descriptors shared across concurrent executions. For "unlimited execution time, use Vercel Workflows" — [Vercel Functions limits](https://vercel.com/docs/functions/limitations)
- Edge runtime: must start responding within 25 s and can stream up to 300 s; code size 1/2/4 MB gzipped (Hobby/Pro/Ent); `eval`/`new Function` not allowed; Vercel says "We recommend migrating from edge to Node.js" — [Edge runtime](https://vercel.com/docs/functions/runtimes/edge)
- Fluid compute: default for new projects since April 23, 2025; multiple invocations share one instance (Node.js and Python); `waitUntil` for background work; runtimes Node.js, Python, Edge, Bun — [Fluid compute](https://vercel.com/docs/fluid-compute). "Promises passed to `waitUntil()` will have the same timeout as the function itself" — [@vercel/functions reference](https://vercel.com/docs/functions/functions-api-reference/vercel-functions-package)
- WebSockets: native, "in public beta on all plans and runs on Fluid Compute"; a connection is pinned to one instance and "closes when the function reaches its maximum duration, so every client needs reconnect logic" — [Vercel KB: WebSockets](https://vercel.com/kb/guide/do-vercel-serverless-functions-support-websocket-connections)
- Vercel Sandbox: "isolated Linux microVMs"; default image includes Node LTS, Python 3.14 and coding agents; billed on active CPU — [Vercel Sandbox](https://vercel.com/docs/vercel-sandbox). Timeout and persistence are separate controls; `persistent: true` is the default and a resume continues "from the last snapshot" — [Vercel KB: Sandbox duration and persistence](https://vercel.com/kb/guide/vercel-sandbox-duration-and-persistence)
- Vercel Workflows: durable code with `'use workflow'`/`'use step'`, "Pause for minutes or months", hooks for external events and approval — [Vercel Workflows](https://vercel.com/docs/workflow)

**Deno Deploy**
- "Deno Deploy will be sunset in April 2027. Your existing applications keep running until then" (banner on the docs, page last updated November 12, 2026) — [Deno Deploy docs](https://docs.deno.com/deploy/)
- Limits page: deployment size ≤ 1 GB; memory 512 MB per application; TLS termination required for outgoing port 443 — [Deno Deploy pricing and limits](https://docs.deno.com/deploy/pricing_and_limits/)
- Deno KV still requires `--unstable-kv` and "may change" — [Deno KV](https://docs.deno.com/deploy/kv/manual/)
- Deno runtime: "As of Deno 2.8, over 75% of Node's own test suite passes"; `node:` built-ins "nearly every module is implemented"; npm via `npm:` or `package.json` — [Deno Node compatibility](https://docs.deno.com/runtime/fundamentals/node/)

**Bun (a runtime, not a host)**
- `node:fs` "Fully implemented. 98% of Node.js's test suite passes"; diagnostics_channel partial — [Bun Node.js compatibility](https://bun.com/docs/runtime/nodejs-compat). Subprocesses via `Bun.spawn`/`Bun.spawnSync` — [Bun child processes](https://bun.com/docs/runtime/child-process). Vercel runs Bun functions with large-function and extended-duration support — [Vercel Functions limits](https://vercel.com/docs/functions/limitations)

**Google Cloud Run**
- Request timeout 5 min default, up to 60 min; a timeout closes the connection with 504 but "doesn't terminate the container instance"; above 15 min, make clients tolerant to reconnects — [Cloud Run request timeout](https://cloud.google.com/run/docs/configuring/request-timeout). WebSockets are subject to the same timeout; use session affinity and reconnects — [Cloud Run WebSockets](https://cloud.google.com/run/docs/triggering/websockets)
- Jobs: task timeout 10 min default, up to 168 hours (7 days) — [Cloud Run task timeout](https://cloud.google.com/run/docs/configuring/task-timeout)
- Container filesystem is writable but "an in-memory file system", so writes consume instance memory; CPU is always allocated while processing a request, idle-CPU depends on billing settings; SIGTERM before shutdown — [Cloud Run container contract](https://cloud.google.com/run/docs/container-contract)

**Azure Container Apps**
- Ingress supports HTTP/1.1, HTTP/2, WebSocket and gRPC; "Request time out is 240 seconds" — [ACA ingress](https://learn.microsoft.com/en-us/azure/container-apps/ingress-overview)
- Jobs set `replicaTimeout` (docs examples use 1,800 s) — [ACA jobs](https://learn.microsoft.com/en-us/azure/container-apps/jobs)
- Dynamic sessions: prewarmed pools, "Hyper-V isolation and optional network controls", auto-deprovision after a cooldown; aimed at running untrusted or LLM code — [ACA dynamic sessions](https://learn.microsoft.com/en-us/azure/container-apps/sessions)

**Azure Functions and Durable Functions**
- Plans: Flex Consumption (recommended serverless plan; scales out to 1,000 instances; memory sizes 512 MB, 2,048 MB or 4,096 MB; always-ready instances), Premium, Dedicated, Container Apps, and the legacy Consumption plan; Linux Consumption hosting retires 30 September 2028 — [Azure Functions hosting options](https://learn.microsoft.com/en-us/azure/azure-functions/functions-scale)
- `functionTimeout` default/maximum in minutes: Flex Consumption 30/unbounded, Premium 30/unbounded, Dedicated 30/unbounded (Always On), Container Apps 30/unbounded, Consumption 5/10. "Regardless of the function app timeout setting, 230 seconds is the maximum amount of time that an HTTP triggered function can take to respond to a request" (Azure Load Balancer idle timeout); unbounded executions still get only a 60-minute grace period at scale-in (Flex/Premium) and 10 minutes at platform updates — [Azure Functions hosting options](https://learn.microsoft.com/en-us/azure/azure-functions/functions-scale)
- Durable Functions support JavaScript and TypeScript; recommended backend is the Durable Task Scheduler — [Durable Functions overview](https://learn.microsoft.com/en-us/azure/azure-functions/durable/durable-functions-overview). Human approval uses `context.df.waitForExternalEvent("Approval")` (JS) and an external `raiseEvent` — [Durable Functions external events](https://learn.microsoft.com/en-us/azure/azure-functions/durable/durable-functions-external-events)
- Secrets: Key Vault references can be used "as values in app settings" for App Service, Functions and Logic Apps — [Key Vault references](https://learn.microsoft.com/en-us/azure/app-service/app-service-key-vault-references)

**Google Cloud secrets**
- Cloud Run services can consume Secret Manager secrets as environment variables or mounted volumes — [Cloud Run secrets](https://cloud.google.com/run/docs/configuring/services/secrets) (page headings "Environment variables" and volumes; details not extracted)

**Fly.io Machines**
- Fly Proxy can stop, suspend and start Machines by traffic (`auto_stop_machines`, `auto_start_machines`, `min_machines_running`) — [Fly autostop/autostart](https://fly.io/docs/launch/autostop-autostart/)
- Root filesystem is "ephemeral storage, a blank slate on every startup"; persistent state belongs in Volumes — [Fly Machines](https://fly.io/docs/machines/overview/); [Fly Volumes](https://fly.io/docs/volumes/overview/)
- Secrets live in "an encrypted vault"; setting one restarts the Machine and resets its ephemeral file system — [Fly secrets](https://fly.io/docs/apps/secrets/)

### Inferences
- A compact matrix for the report (all values as of November 2026, from the findings above):

| Runtime | Longest single run | Streaming / WS | Durable wait | Local FS | Subprocess | Memory / bundle |
| --- | --- | --- | --- | --- | --- | --- |
| Workers | HTTP: unlimited while connected, CPU ≤ 5 min; cron/queue/alarm 15 min; `waitUntil` +30 s | SSE yes; inbound WS yes; outbound WS only via fetch upgrade | DO alarms, Workflows (`sleep` 365 d, `waitForEvent` default 24 h) | per-request `/tmp` only | no (`child_process` stub) | 128 MB / 64 MiB |

| CF Containers / Sandbox | microVM driven by a DO | via Worker | via DO | instance disk 2–20 GB | yes | up to 12 GiB |
| Lambda | 15 min (90 min Managed Instances async) | streaming on Node via function URL; 200 MB | durable functions (1 yr), Step Functions (1 yr) | `/tmp` ≤ 10 GB, per environment | yes (1,024 procs) | 10 GB / 250 MB zip, 10 GB image |
| Vercel Functions | 300 s / 800 s / 1,800 s beta | SSE yes; WS beta, closes at max duration | Vercel Workflows | not researched (gap) | not researched (gap) | 2–4 GB / 250 MB (5 GB beta) |
| Cloud Run | 60 min request; jobs 7 d | SSE, WS (timeout-bound) | external | in-memory FS | yes | container |
| ACA | 240 s ingress request; jobs by `replicaTimeout` | WS, HTTP/2 | external | container | yes | container |
| Azure Functions (Flex) | HTTP response ≤ 230 s; executions 30 min default, unbounded max (60 min scale-in grace) | not researched | Durable Functions `waitForExternalEvent` | not researched | not researched | 0.5/2/4 GB |

| Deno Deploy | not found | not researched | KV (unstable) | not researched | not researched | 512 MB / 1 GB; **sunset April 2027** |

- "Deploy anywhere" therefore splits into two tiers: an isolate tier (Workers/DO, Vercel Edge, Deno Deploy) where only the SDK and a store-backed harness can run, and a process tier (Node/Bun/Deno in containers, Lambda, Vercel Node functions) where the full harness runs but without durable local disk except on Fargate/Fly volumes/k8s PVs.
- Deno Deploy's announced April 2027 sunset makes it a poor first-class target; Deno as a *runtime* (in containers) still matters.

## Q2. How agent frameworks achieve (or fail at) portability

### Takeaway
Frameworks that are portable keep the loop pure (fetch + Web APIs, no host tools) and push durability into a pluggable store or a separate workflow engine; the process-based SDKs (Claude Agent SDK, Copilot) and full coding harnesses (Pi coding agent) are portable only by being placed in a container that a durable coordinator drives. In November 2026 both Cloudflare and Vercel shipped exactly that adapter layer for third-party harnesses (Pi, OpenCode, Claude Code, Codex), which is strong evidence for the interfaces we need.

### Cited Findings
- **OpenAI Agents SDK (v0.21.0):** supported on Node.js 22+, Deno 2.35+, Bun 1.2.5+; Cloudflare Workers has "limited support": requires `nodejs_compat`, traces must be flushed manually, `AsyncLocalStorage` limits make some traces inaccurate, outbound WebSockets need a fetch-based upgrade; v8 isolates "have not been extensively tested" — [troubleshooting.mdx at v0.21.0](https://github.com/openai/openai-agents-js/blob/v0.21.0/docs/src/content/docs/guides/troubleshooting.mdx). Sandbox agents use `UnixLocalSandboxClient` (host processes, no isolation), `DockerSandboxClient` or hosted clients — [sandbox-agents.mdx at v0.21.0](https://github.com/openai/openai-agents-js/blob/v0.21.0/docs/src/content/docs/guides/sandbox-agents.mdx). The installed `@openai/agents-core@0.21.0` dist imports `node:child_process` (8 sites), `node:fs` and `node:path`; it declares no `engines` (local inspection of `node_modules`, this repo's lockfile).
- **Vercel AI SDK (`ai@7.0.162`):** declares `engines.node >=22` and its dist imports `node:async_hooks`, `node:diagnostics_channel` and `node:http` (local inspection). Code mode "requires Node.js 22 or newer and is not available in browser or edge runtimes" — [AI SDK docs mirror at ai@7.0.162](https://github.com/vercel/ai/blob/ai@7.0.162/content/docs/03-ai-sdk-core/18-code-mode.mdx). Durability is a separate package: `WorkflowAgent` from `@ai-sdk/workflow` runs the tool loop inside a workflow so "each tool execution is a durable step"; a `ToolLoopAgent` is "Lost on crash" — [AI SDK WorkflowAgent](https://ai-sdk.dev/docs/agents/workflow-agent)
- **Workflow SDK ("Worlds"):** "The same workflow code can run locally..., on Vercel..., or on any infrastructure using **Worlds**, which are pluggable adapters that handle storage, queuing, and communication"; Local World stores data in `.workflow-data/`; official Postgres world (`WORKFLOW_TARGET_WORLD=@workflow/world-postgres`); "community-maintained Worlds or build your own" — [Workflow SDK deploying](https://workflow-sdk.dev/docs/deploying). Hooks generate "a unique token that external systems can use to send data back" for approvals — [Workflow SDK hooks](https://workflow-sdk.dev/docs/foundations/hooks). npm `workflow` latest 5.6.1, Apache-2.0 (npm registry, 2026-11-18).
- **Vercel durable-harness (beta):** "Run Pi, fx, OpenCode, eve, Claude Code, and Codex on Vercel. When a crash, a function timeout, or a redeploy stops a turn, a new function resumes it from the session's log" — [Vercel agent harnesses](https://vercel.com/docs/agent-harnesses). npm `durable-harness` latest 0.0.2, Apache-2.0 (npm registry, 2026-11-18).
- **LangGraph.js (`@langchain/langgraph@1.6.0`):** `engines.node >=18`; exports a `./web` entry point alongside the default entry, whose `dist/node.js` imports `AsyncLocalStorage` from `node:async_hooks` (local inspection), i.e. a separate entry for runtimes without async context. Hosted deployment is "LangSmith Agent Server" ("LangSmith Deployment is now LangSmith Agent Server"), on Cloud, BYOC/hybrid, self-hosted (Enterprise) or standalone — [LangSmith deployment overview](https://docs.langchain.com/langsmith/deploy-overview). Standalone servers run in Docker/Compose/Kubernetes with PostgreSQL and Redis and need `LANGGRAPH_CLOUD_LICENSE_KEY` — [Standalone server](https://docs.langchain.com/langsmith/deploy-standalone-server)
- **Mastra:** "can be deployed to any Node.js-compatible environment", Node v22.13.0+; a Hono-powered Mastra server for "long-running processes, or WebSocket connections"; optional deployers for Vercel, Netlify and Cloudflare; workflow runners Inngest and Temporal for durable execution — [Mastra deployment overview](https://mastra.ai/docs/deployment/overview). `@mastra/deployer-cloudflare` generates `wrangler.jsonc`; "Cloudflare Workers use an ephemeral filesystem, so any storage you configure... must be hosted externally" (switch `LibSQLStore` file URLs to a remote DB) — [Mastra Cloudflare deployer](https://mastra.ai/integrations/deploy/cloudflare)
- **Cloudflare Agents (`agents@0.33.0`):** "each agent has a durable identity, local SQL storage, real-time connections, scheduled work, and recoverable execution"; the runtime is a Durable Object — [Agents overview](https://developers.cloudflare.com/agents/). `Agent` extends `Server` from `partyserver` — [Agents internals, repo mirror](../../../reference/cloudflare-agents/source/cloudflare-docs/src/content/docs/agents/agent-class/internals.mdx); this repo's guide: "An Agent needs the Workers runtime, so a Node test can't construct one" — [our Cloudflare Agents guide, testing section](../../../reference/cloudflare-agents/guide.md). There is no non-Cloudflare host: the hosted PartyKit platform "is shutting down. Deploys stop on 16 October and the platform shuts down on 23 October 2026" — [PartyKit docs](https://docs.partykit.io/). Local dev runs in workerd (Miniflare/Vitest plugin), per our guide.
- **Cloudflare harness adapters:** the Harnesses page lists Pi and Flue in "Durable Objects via the Agents SDK" with automatic resume; OpenCode in DOs; Claude Code and Codex (experimental) in a "Linux container driven by a Durable Object", which "Reattaches after object restart; container loss fails or retries the turn"; "Claude Code and Codex keep their records in a SQLite-backed `HarnessStore`" — [Cloudflare Agents harnesses](https://developers.cloudflare.com/agents/harnesses/)

Locally, `@earendil-works/pi-agent-core@1.5.2`'s dist imports no `node:` module at all, while `pi-ai` imports `node:http`, `node:crypto`, `node:fs`, `node:readline`, and `pi-coding-agent` declares `engines.node >=22.19.0` (local inspection).
- **Claude Agent SDK (0.3.327):** "spawns and supervises a `claude` CLI subprocess that owns a shell, a working directory, and session files on disk. Hosting it is not like hosting a stateless API wrapper"; patterns: ephemeral, long-running, hybrid (hydrate from a `SessionStore`), multi-agent container; size ~1 GiB RAM, 5 GiB disk, 1 CPU per agent; route model calls through `ANTHROPIC_BASE_URL` to a key-injecting proxy — [Claude Agent SDK hosting, mirror](https://code.claude.com/docs/en/agent-sdk/hosting.md) (source URL `https://code.claude.com/docs/en/agent-sdk/hosting.md`)
- **Strands:** deployment guides cover Lambda ("short-lived agent interactions and batch processing"), Fargate, App Runner, EKS, EC2 and Bedrock AgentCore — [Strands operating in production](https://strandsagents.com/latest/documentation/docs/user-guide/deploy/operating-agents-in-production/). The Lambda example "does not implement response streaming"; use Fargate for streaming — [Strands Lambda guide](https://strandsagents.com/latest/documentation/docs/user-guide/deploy/deploy_to_aws_lambda/). Our U10 report: Strands' `abstract class Sandbox` exposes `executeStreaming`, `readFile`, `writeFile`, etc.; AWS coupling sits "in the defaults and dependencies, not in the architecture" — [Strands harness SDK report](../../../research/external-designs/strands-harness-sdk.md)

### Inferences
- The common recipe across Pi-on-DO, Claude/Codex-on-DO, Vercel durable-harness and Workflow Worlds is the same three seams: (1) a session/transcript store interface, (2) a wake/schedule interface that replaces in-memory timers, (3) a sandbox/exec interface that may be remote. None of them needed the loop itself to change; Pi needed `pi-durable` only because its scheduler and storage were in-process.
- Process-based SDKs fail at isolate portability by design; they reach Workers/Vercel only as "container driven by a coordinator", and lose work when the container dies.
- `AsyncLocalStorage` and tracing flush are the recurring sharp edges in isolate runtimes (OpenAI's Workers notes, LangGraph's `./web` entry); our OTel observer should take explicit context, not ambient ALS, and expose an explicit `flush()` for `waitUntil`.

### Gaps
- The AI SDK has no single "supported runtimes" page in our mirror; Node/Edge/Workers support for `ai@7` is inferred from package metadata and prior knowledge, not a primary statement.
- Mastra's Lambda/Azure guides and its Cloudflare deployer's exact limitations (beyond storage) were not read.
- Flue, OpenCode-on-DO and Vercel durable-harness internals (store schema, resume semantics) were not inspected.
- Strands TypeScript's runtime support statement (Node only? browser?) was not found on the fetched quickstart.

## Q3. What in our SDK and harness plans is runtime-bound, and the adapter each part needs

### Takeaway
The SDK (P1) is already isolate-portable by design: the gateway uses only `fetch`, Web Streams and Web Crypto with an injectable `Transport`, and the validators avoid `eval`. The harness (P2) is Node-host-bound in five places: the JSONL store, the lock file, the file key ring, the spawned `srt`/Docker sandboxes with a loopback credential proxy, and the stdio/CLI transports plus stdio MCP. Each already sits behind an interface except the lock, the timers and the transport stream types.

### Cited Findings (our plans)
- Gateway "has no runtime dependencies, and it uses `fetch`, Web Streams and Web Crypto from Node 22"; `type Transport = (request: Request) => Promise<Response>; // defaults to globalThis.fetch` — [SDK plan §3.1–3.2](../../../plans/build-sdk.md#31-two-packages-under-a-new-top-level-packages-directory)
- D2: "Each adapter calls `fetch` through an injectable `Transport` and uses no vendor SDK" — [SDK plan D2](../../../plans/build-sdk.md#d2-anthropic-messages-and-openai-compatible-chat-completions-first-accepted)
- D5: pluggable `ApprovalSigner`, "a per-process ephemeral key by default"; D7: pi-schema 1.5.2 with `@cfworker/json-schema` 4.1.6 as fallback, the latter "exists because Workers lack `eval`"; pi-schema declares `node >=22.19.0` — [SDK plan §2](../../../plans/build-sdk.md#2-decisions)
- Determinism seams `clock`, `idGenerator`, `random` are public — [SDK plan §3.4](../../../plans/build-sdk.md#34-the-seams-p2-consumes)
- HD1: one `message_block` entry per content block, deltas never persisted; `SessionStore { append(key, entries, { expectedLastId }), load(key, { fromSeq }), list(), delete() }`, `memoryStore()`, `jsonlStore({ dir, maxEntryBytes })` (default 64 KiB) — [harness plan HD1, §3.2](../../../plans/build-harness.md#32-session-log-api)
- HD2: `open(path, "wx")` lock with `{ pid, host, token, leaseUntil }`, renewed every 10 s for a 30 s lease; stale only when the lease lapsed and the pid is gone on the same host; "local disk only", NFS unsupported; "An actor per session suits a server, which is a non-goal" — [harness plan HD2](../../../plans/build-harness.md#hd2-a-lock-file-with-a-renewed-lease-on-local-disk-only-provisional)
- HD4: `srt` for interactive runs, Docker (`--cap-drop ALL --read-only --network none`) for headless; backends "spawn the `srt` and `docker` binaries"; `SandboxClient { tier: "none"|"os"|"container"|"gvisor"|"microvm"; provision(manifest, policy) }`, `Sandbox { exec, readFile, writeFile, dispose }`; hosted backends are a non-goal but "the `SandboxClient` interface leaves room for them" — [harness plan HD4, §3.4, §1](../../../plans/build-harness.md#hd4-srt-for-interactive-runs-and-docker-for-headless-runs-accepted)
- HD5: "one host process per session"; key ring in a `KeyStore` at `$XDG_STATE_HOME/agent-speak/keys.json` mode `0600`; every `ask` ends the run in `awaiting_approval` and is written as an `approval_requested` entry first; resume re-runs the permission pipeline — [harness plan HD5](../../../plans/build-harness.md#hd5-the-harness-always-passes-hmacsigner-over-a-persistent-key-ring-accepted-with-sdk-d5)
- HD15: tools talk to `http://127.0.0.1:<port>/<route>/…` on a host-side reverse proxy that adds the credential; everything else leaves through a default-deny `CONNECT` proxy; `startEgressProxy()` returns a `url` "given to the sandbox as HTTP(S)_PROXY" — [harness plan HD15, §3.4](../../../plans/build-harness.md#hd15-the-credential-proxy-injects-on-reverse-proxy-routes-not-by-intercepting-tls)
- Transports: `stdioTransport(dispatcher, io: { stdin: NodeJS.ReadableStream; stdout: NodeJS.WritableStream })`; "A WebSocket or HTTP-with-SSE transport" is a non-goal; MCP over stdio (N24) and streamable HTTP (N25) — [harness plan §3.5, §1, §4.5](../../../plans/build-harness.md#1-goal-and-non-goals)
- Cloudflare's own Containers expose an "outbound handler" through which a Container's outbound HTTP passes (100 MiB body limit) — [Containers limits](https://developers.cloudflare.com/containers/platform-details/limits/); Dynamic Workers take `globalOutbound: null` — [Sandbox overview](https://developers.cloudflare.com/sandbox/)

### Inferences (part-by-part, Workers as planned → adapter needed)
- **Gateway, adapters, retries (B4, B8, B9): runs on Workers as planned.** Watch the six-connections-waiting-for-headers cap for parallel subagents, and subrequest counts (10,000 default) for long runs. Retry backoff via `setTimeout` is fine inside a live request. No adapter beyond `Transport`.
- **Loop, tools, interceptors, budget (B10–B14): runs as planned.** CPU is the only limit (30 s default, 5 min max per request/DO message; network waits excluded), and model waits dominate. D7's pi-schema declares `node >=22.19.0` in `engines`; whether it loads in workerd is untested, and `@cfworker/json-schema` is the known-good fallback. B10 should add a workerd smoke test.
- **Signed pauses (B15, D5): portable, but the ephemeral default is wrong on any serverless host** because isolates and Lambda environments recycle between pause and resume. Needs a `KeyStore` adapter backed by a Workers secret / Secrets Store, AWS Secrets Manager (via the extension), Vercel/Fly env secrets. Rotation (`rotate()`, `prune()`) needs write access, which env-var secrets don't give; split `KeyStore` into read-only `load()` and an optional admin `rotate()`.
- **OTel observer (B17, N31): portable if it never depends on ambient `AsyncLocalStorage`** and exposes `flush()` so hosts can hand it to `ctx.waitUntil` (Workers, 30 s) or Vercel `waitUntil` (same timeout as the function).
- **HD1 entries + `SessionStore` (N2, N3): the interface is portable; `jsonlStore` is not.** Workers `/tmp` is per-request; Cloud Run's FS is in-memory; Fly and Lambda FS are ephemeral. Adapters: `doSqliteStore` (row per entry; `expectedLastId` CAS inside the DO's single-threaded transaction; 64 KiB bound is far under the 8 MB row limit), `d1Store` (2 MB rows), `r2`/`s3` segment store, `dynamoStore` (conditional put on `seq`), `postgresStore`. A conformance suite already exists in N3's plan and should run against each.
- **HD2 lock (N4): cannot run on Workers as planned** (no pid, no host, no persistent `wx` file). Needs a `SessionLock` interface: `acquire(key) → token | "would_block"`, `renew`, `release`. Implementations: file lease (today), DO (the object *is* the single writer, so lock is a no-op or a lease row), DynamoDB/Postgres lease with conditional write. The pid-liveness rule must become lease-only off-host.
- **Lease renewal and any background timers:** a 10 s `setInterval` renew dies when a Worker request ends; on DOs, use alarms (one per object; multiplex via storage). Add a `Scheduler`/`wake(at)` seam like Pi's `wake()` used by `PiHarness`.
- **HD4 sandbox (N15–N19): `none`/`srt`/Docker cannot run on Workers** (`child_process` is a stub) nor on Vercel/Lambda in any isolating way. The `SandboxClient`/`Sandbox` shape already fits remote backends: add `cloudflareSandbox` (microVM via DO, `tier: "microvm"`), `vercelSandbox` (microVM), `acaDynamicSessions` (Hyper-V), and optionally `dynamicWorker` for JS-only code (`globalOutbound: null`). Needs: async `provision` that can resume an existing sandbox by id after the coordinator restarts (Cloudflare docs say container loss fails or retries the turn), and a `snapshot/restore` or "persistent workspace" capability flag.
- **HD15 credential proxy (N20): loopback reverse proxy is host-bound.** On Cloudflare the Container outbound handler (a Worker) is the natural injection point; on Dynamic Workers, a binding-based fetch with `globalOutbound` set to a controlled service. Interface: `EgressPolicy { allow, routes }` compiled per backend rather than `startEgressProxy()` returning a URL. Vercel Sandbox / ACA network controls were not researched (gap).
- **HD5 KeyStore file:** host-bound; see signed pauses above.
- **Protocol/dispatcher (N26–N28): portable**, but `stdioTransport` types Node streams; type it over Web `ReadableStream`/`WritableStream` so Deno/Bun/Workers can reuse it, and add a WebSocket transport (DO Hibernation or Vercel WS beta) when a server host is needed. The plan's non-goal blocks that today.
- **CLI (N30), stdio MCP (N24), evals (N36–N39), completion checks via `package.json` scripts (N32): Node/Bun/Deno process tier only.** MCP streamable HTTP (N25) is portable.
- **Extensions, skills, context files (N22, N23):** read from disk; on Workers they must come from `/bundle` (read-only) or an object store; `TrustStore`/`extensions.lock.json` writes need a store adapter.
- **Per first-class provider (owner's scope: Cloudflare, AWS, GCP, Azure, Vercel), the harness adapters would be** (all inferences from the findings above; none built or tested):

## Q4. Patterns for long waits (human approval) on short-lived runtimes, and how our signed pause fits

### Takeaway
Every platform offers a durable-wait primitive, but they differ in who owns control flow: workflow engines (Cloudflare Workflows, Lambda durable functions, Vercel Workflows, Step Functions) replay your code and hold the wait, while DO alarms and plain stores just let you sleep and be woken. Our signed pause (pause as an `approval_requested` entry, resume via `continueRun` with re-evaluation) is engine-neutral: it needs only a durable store, a persistent signing key and any trigger that can call `continueRun`, so it maps onto all of them as an adapter rather than depending on one.

### Cited Findings
- Cloudflare Workflows: `step.waitForEvent` with default 24 h timeout, `sendEvent` via binding or HTTP; `step.sleep` up to 365 days; instance state up to 1 GB; completed state retained 7–30 days — [Workflows events](https://developers.cloudflare.com/workflows/build/events-and-parameters/); [Workflows limits](https://developers.cloudflare.com/workflows/reference/limits/)
- Durable Objects: alarms with at-least-once execution and 6 retries; WebSocket hibernation keeps clients connected while the object is out of memory — [DO Alarms](https://developers.cloudflare.com/durable-objects/api/alarms/); [DO WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/). Our Cloudflare guide verified `schedule()` callbacks firing through a DO alarm in workerd — [our Cloudflare Agents guide §6](../../../reference/cloudflare-agents/guide.md#6-scheduling-runs-callbacks-on-durable-object-alarms)
- Lambda durable functions: up to one year; waits don't bill compute; resume replays from the start, skipping completed checkpoints — [Lambda durable functions](https://docs.aws.amazon.com/lambda/latest/dg/durable-functions.html). Step Functions Standard: 1 year, 25,000 history events, `.waitForTaskToken` — [quotas](https://docs.aws.amazon.com/step-functions/latest/dg/service-quotas.html); [integration patterns](https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html)
- Vercel Workflows / Workflow SDK: "Pause for minutes or months"; hooks yield a token for external resume ("Waiting for approval from a user or admin"); Chat SDK + Workflows "pause for human approval" — [Vercel Workflows](https://vercel.com/docs/workflow); [Workflow SDK hooks](https://workflow-sdk.dev/docs/foundations/hooks)
- Cloudflare Queues: `delaySeconds` ≤ 24 h, retention ≤ 14 days — usable for reminders/timeouts, not as the wait itself — [Queues limits](https://developers.cloudflare.com/queues/platform/limits/)
- Our design: SDK `awaiting_approval` "as a signed log state, a blocking wrapper that writes first"; harness writes the `SignedPendingRequest` as an entry before asking any client, never uses `blockingApprovals()`, and re-evaluates policy on resume — [SDK plan §1 table](../../../plans/build-sdk.md#1-goal-and-non-goals); [harness plan HD5](../../../plans/build-harness.md#hd5-the-harness-always-passes-hmacsigner-over-a-persistent-key-ring-accepted-with-sdk-d5)
- Our guide's rationale: "Pauses must be entries because a callback dies with its process, and approvals in production wait minutes or hours" — [harness plan HD5 evidence](../../../plans/build-harness.md#hd5-the-harness-always-passes-hmacsigner-over-a-persistent-key-ring-accepted-with-sdk-d5)

### Inferences
- **Fit per platform:**
  - *DO (Cloudflare):* run ends with `awaiting_approval` → entry appended to DO SQLite → optional alarm for an approval deadline → approver's HTTP/WebSocket message hits the same DO by session id → `continueRun`. No workflow engine needed; this is the closest to our design and to Cloudflare Agents' own `needsApproval` flow.
  - *Cloudflare Workflows:* wrap each turn as a step; on `awaiting_approval`, `step.waitForEvent({ type: "approval", timeout })`; the event payload carries the signed resolution. Caveats: 1 MiB event/step-result limits mean pass entry ids, not transcripts; replay semantics mean the turn step must be idempotent (our entries are idempotent by id).
  - *Lambda:* durable functions or Step Functions task token hold the wait; or simply persist to DynamoDB and let an API Gateway/function-URL request call `continueRun` — no compute while waiting either way.
  - *Vercel:* Workflow SDK hook token = our pending request id; or store + new function invocation. Function max duration (300–1,800 s) means `blockingApprovals()` is unusable there.
  - *Containers (Cloud Run/Fargate/Fly/k8s):* our current design as written (store + persistent key ring), with the store moved off local disk if instances scale to zero.
- Workflow engines replay code; our loop is not deterministic across model calls unless each model call is a step whose result is checkpointed. The cleaner fit is to treat the engine only as the *wait-and-wake* mechanism and keep the session log as the source of truth — i.e. one engine step per `continueRun`, never the inner loop.
- The ephemeral-key default and the "one host process per session" assumption are the two parts of the pause design that break on serverless; the signature, entry-first write and re-evaluation on resume all carry over unchanged.

### Gaps
- No primary source compares wait costs across these engines; pricing was not researched.
- Lambda durable functions' external-callback API (name, payload limits, max wait for a single callback) was not fetched.
- Whether Cloudflare Agents' built-in approval flow can resume across a deploy that changes the Agent class was not checked.
