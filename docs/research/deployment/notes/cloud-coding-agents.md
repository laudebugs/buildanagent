# How cloud coding agents are built (as of November 2026)

> **Fact-checked 2026-11-18.** This note keeps its original text. Corrections are logged in [fact-check-portable-agents.md](../fact-check-portable-agents.md) and applied in [the report](../portable-agents.md), which supersede this note where they disagree.

All vendor pages were fetched on 2026-11-18 with `curl -sSL`; repositories were shallow-cloned the same day at the commits listed under each. Quotes are verbatim and under 25 words. "Inference" marks my own reading; nothing here comes from search summaries unless marked.

## Per product: execution environment, repo access, network, secrets, output, steering, persistence, parallelism, limits, and the harness inside

### Takeaway
All six products converge on one shape: a control plane that owns the session and the credentials, a per-task (or per-session) isolated Linux VM built from a cached snapshot of "base image + setup script", a host-side egress proxy with an allowlist, and a branch or pull request as the output, with a human merge as the only commit point. They differ mainly in where secrets live (outside the VM via proxy substitution at Anthropic, OpenAI and for Claude/Open SWE GitHub tokens; inside the VM as redacted env vars at Cursor and Devin) and in how long a sandbox lives (ephemeral per task at Jules/Copilot-on-Actions; pause-and-resume VMs with snapshots at Claude, Copilot cloud sandboxes, Cursor, Codex).

### Cited Findings

**Claude Code on the web (cloud sessions)**
- A cloud session "runs on cloud infrastructure instead of on your machine", on Anthropic-managed infrastructure or an organization's self-hosted environment; it keeps running after the laptop closes. — [Claude Code docs: Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)
- Start surfaces: web, mobile, Desktop (Cloud environment), terminal (`claude --cloud`, formerly `--remote`), and cloud scheduled tasks ("routines"); "projects" start and track many sessions. — [same page](https://code.claude.com/docs/en/claude-code-on-the-web)
- Execution environment: "each session gets a fresh virtual machine (VM) running Ubuntu 24.04 on x86_64", repo cloned, common toolchains pre-installed; approximate ceilings 4 vCPUs, 16 GB RAM, 30 GB disk. — [Claude Code docs: Configure cloud environments](https://code.claude.com/docs/en/cloud-environments)
- Setup and caching: a setup script runs as root before Claude Code launches; when it finishes in roughly five minutes, "Anthropic snapshots the filesystem and reuses that snapshot" for later sessions; the snapshot keeps disk state, not running processes; it rebuilds when the script or allowed hosts change and after roughly seven days. SessionStart hooks run after launch on every session, including resumed ones. — [Configure cloud environments](https://code.claude.com/docs/en/cloud-environments)
- Idle and resume: after a few minutes idle "a session's VM pauses with its files saved"; a paused VM can be reclaimed, and reopening provisions a fresh VM that restores conversation history but not running shell commands, subagents or session-scoped scheduled tasks. — [Configure cloud environments](https://code.claude.com/docs/en/cloud-environments); [Environment expired](https://code.claude.com/docs/en/claude-code-on-the-web)
- Network: per-environment levels None, Limited (default allowlist of registries, GitHub, cloud SDKs, plus listed domains) and Full; changes reach running sessions within about a minute. GitHub, network-secret hosts and the Anthropic API bypass the allowlist via separate paths. All outbound traffic passes an HTTP/HTTPS security proxy. — [Configure cloud environments](https://code.claude.com/docs/en/cloud-environments)
- Credentials stay outside the VM: "your GitHub credentials stay encrypted on Anthropic's servers and never enter a session's VM"; the git client uses a scoped credential that the GitHub proxy "verifies and swaps for your actual GitHub token". `GH_TOKEN` reads as the placeholder `proxy-injected`. — [Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web); [Configure cloud environments](https://code.claude.com/docs/en/cloud-environments)
- GitHub proxy policy: rejects branch deletions and tag pushes but "doesn't limit which branches a push can update"; serves API requests only for repositories attached to the session (403 otherwise); rejects GraphQL. — [Configure cloud environments](https://code.claude.com/docs/en/cloud-environments)
- Network secrets: an API key stored on the environment that "Anthropic's agent proxy adds ... to requests for the hosts you list, after each request leaves the session's VM"; never attached to GitHub, the Anthropic API, public registries, or setup-script requests (the proxy connects only after setup). Environment variables, by contrast, are readable by anyone using the environment. — [Configure cloud environments](https://code.claude.com/docs/en/cloud-environments)
- Repo access: Claude GitHub App or `/web-setup` (uploads the local `gh` token to the Claude account); `--cloud` clones the GitHub remote at the current branch, or uploads a git bundle (<100 MB, falling back to current branch then a squashed snapshot) when there is no remote or no app. Non-GitHub hosts work only via bundle or self-hosted. — [Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)
- Output: Claude pushes to a branch; a Changes card shows the diff; the user creates a PR from claude.ai/code or teleports. Auto-fix subscribes to PR webhooks (CI failures, review comments) and pushes clear fixes; GitHub emits no webhook for base-branch conflicts, so auto-fix cannot react to them. — [Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)
- Steering and handoff: permission mode is chosen at creation and while running; `claude -p "msg" --cloud <session-id>` queues a follow-up from any logged-in machine; `--teleport` pulls a session into the terminal (one-way: "you can't push an existing terminal session to the cloud"), requires a clean tree and a pushed branch, and gives the terminal its own copy of the session. — [Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)
- Harness inside: the VM runs Claude Code itself (commands such as `/fast` need "Claude Code v2.1.271 or later in the session's environment"; cloud sessions set `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`; the Bash tool's 2-minute default and 10-minute max timeouts apply). — [Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web); [Configure cloud environments](https://code.claude.com/docs/en/cloud-environments)
- Self-hosted: environment → runner → session; Anthropic's control plane "places the session on your environment's queue, where a runner claims it, clones the repository ... and starts" a Claude Code process; a runner locks to one owner; an autoscaling orchestrator is optional; session content still goes to `api.anthropic.com`; self-hosted environments have no network secrets. Public beta, Team and Enterprise. — [Claude Code docs: Self-hosted environments](https://code.claude.com/docs/en/self-hosted-environments)
- Limits: cloud sessions share account rate limits; parallel tasks consume them proportionately. Availability: Pro, Max, Ultra, Team, and Enterprise premium seats; not for ZDR or HIPAA orgs. — [Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)

**OpenAI Codex Cloud**
- Two generations as of Nov 2026: the current "Codex Cloud" (web, mobile, desktop via "Work in > Cloud") and "Codex Cloud (Legacy)", which still serves Code Review and the Linear/GitHub integrations and which OpenAI plans to deprecate. — [OpenAI Developers: Cloud environments](https://developers.openai.com/codex/environments/cloud-environments)
- Current flow: "Each cloud task runs in its own workspace"; a reusable environment is created by letting Codex inspect repos, install dependencies and record an "Install script" and a "Start skill"; "Publishing captures the prepared filesystem for new tasks". New tasks start from that filesystem; existing tasks keep their own saved files, including uncommitted changes; repository refresh runs in the background preserving caches. — [Cloud environments](https://developers.openai.com/codex/environments/cloud-environments)
- Secrets, current: a network secret's "Programs receive a placeholder; the proxy substitutes the real value for allowed destinations", HTTPS on port 443 only, during setup and tasks; saving one adds its domains to restricted internet access. A personal vault holds per-user values. — [Cloud environments](https://developers.openai.com/codex/environments/cloud-environments)
- Legacy flow (still documented): Codex "creates a container and checks out your repo at the selected branch or commit SHA", runs the setup script (and an optional maintenance script on cached resume), applies internet settings, then "The agent runs terminal commands in a loop"; it ends with an answer and a diff, and the user opens a PR. — [OpenAI Developers: Codex cloud environments (legacy)](https://developers.openai.com/codex/cloud/environments)
- Legacy image and caching: default image `universal` (reference Dockerfile at `openai/codex-universal`); container state cached "for up to 12 hours"; cache invalidated on changes to setup/maintenance script, env vars or secrets; Business/Enterprise caches are shared across the environment's users. Legacy secrets "are only available to setup scripts" and are removed before the agent phase. — [Codex cloud environments (legacy)](https://developers.openai.com/codex/cloud/environments)
- Network (legacy page): setup scripts have internet; agent-phase internet is off by default, configurable to a domain allowlist (None / Common dependencies / All) and to GET, HEAD, OPTIONS only; all traffic goes through an HTTP/HTTPS proxy. The page walks through a prompt-injection exfiltration example via an issue body. — [OpenAI Developers: Agent internet access](https://developers.openai.com/codex/cloud/internet-access)
- Execution substrate: "tasks run in VM-backed sandboxes" on shared OpenAI-managed infrastructure, and Work Cloud "uses the Codex task-execution harness". — [OpenAI Developers: ChatGPT Work cloud security](https://developers.openai.com/codex/enterprise/chatgpt-work-cloud-security) (Inference: the legacy page says "container" and the newer page says "VM-backed sandboxes"; likely containers inside VMs, unconfirmed.)
- Model: the overview page's mock UI shows a model picker; I did not find a primary statement naming the cloud model as of Nov 2026. — [Codex Cloud overview](https://developers.openai.com/codex/cloud)

**GitHub Copilot cloud agent / "Copilot in the cloud"**
- Since 2026-10-28 paid users get "Copilot in the cloud": a session (conversation and activity) runs in an environment that is a cloud sandbox, a GitHub Actions runner, or a "Remote" custom environment; cloud-sandbox sessions "continue seamlessly" across the Copilot app, IDE, mobile and CLI. — [GitHub Docs: About Copilot on GitHub.com and Mobile / cloud agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent)
- Cloud sandbox: "an isolated Linux environment that GitHub creates for a Copilot session"; it clones each repo; while stopped it "keeps a snapshot of its state"; environment (Cloud vs Actions) is fixed at session start. Billing meters: $0.000024 per vCPU-second, $0.000003 per GiB-second, $0.005 per GiB-month of snapshot storage. — [GitHub Docs: About cloud sandboxes](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/about-cloud-sandboxes)
- Actions-based sessions: setup via `.github/workflows/copilot-setup-steps.yml` with a single `copilot-setup-steps` job (only certain keys honored, `timeout-minutes` max 59); checkout `fetch-depth` is overridden; failed setup steps are skipped rather than fatal; supports larger and self-hosted runners and Windows. Each Actions session has "a maximum execution time of 59 minutes". Cloud sandboxes support none of the Actions customizations but can span repos in one org. — [GitHub Docs: Configure the development environment](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/customize-the-agent-environment); [About cloud agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent)
- Firewall: on by default with a recommended allowlist; org/repo custom allowlists; blocked requests are reported in the PR body or a comment. Limits stated plainly: applies only to processes started through the agent's Bash tool (and, in cloud sandboxes, the Playwright MCP browser), and "Sophisticated attacks may bypass the firewall". Allowlist changes don't reach running sandbox sessions. — [GitHub Docs: Customizing the firewall](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/customize-the-agent-firewall); [About cloud sandboxes](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/about-cloud-sandboxes)
- Output and guardrails: pushes to a single branch (`copilot/` or the PR's branch); "cannot directly run git push"; draft PRs need human review and merge; it cannot mark ready, approve or merge; workflows wait for an "Approve and run workflows" click by default; the requester cannot approve; commits are authored by Copilot, co-authored by the requester, signed, and link the session log. Only users with write access can trigger it; HTML comments are filtered before reaching the agent. Before finishing it runs security checks, secret scanning and Copilot code review on its own code. — [GitHub Docs: Risks and mitigations](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)
- Post-PR: "Agent Merge" watches a PR and works on failed workflows and merge conflicts; automations run the agent on schedules or events with a chosen tool set. — [About cloud agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent); [Risks and mitigations](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)
- Billing: cloud and Actions compute draw on a monthly GitHub account allowance "separate from AI credits"; model choice depends on plan and how the task starts. — [About cloud agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent)

**Google Jules**
- "Jules runs each task inside a secure, short-lived virtual machine (VM)"; "Each task runs in a fresh virtual machine where Jules clones your repo"; Ubuntu with many toolchains and Docker preinstalled. — [Jules docs: Environment](https://jules.google/docs/environment/); [Jules FAQ](https://jules.google/docs/faq/)
- Setup: without a script Jules infers setup from the repo, AGENTS.md or README; "Run and Snapshot" runs the setup script and snapshots the environment for future tasks on that repo; long-running processes (dev servers) are not supported in setup scripts. — [Jules docs: Environment](https://jules.google/docs/environment/); [FAQ](https://jules.google/docs/faq/)
- Network and security: the VM has internet access; the FAQ puts responsibility on the user ("You are responsible for the code you run") rather than describing an allowlist or credential proxy. — [Jules FAQ](https://jules.google/docs/faq/)
- Flow: pick repo and base branch; Jules generates a plan the user approves "before any code changes are made"; mid-task feedback can trigger a replan; a pause button stops work; on completion, "Create branch" pushes changes, and a PR is opened from that branch (issue-triggered tasks link a PR). Failed tasks retry automatically, then notify. — [Jules docs: Getting started](https://jules.google/docs/); [Running tasks](https://jules.google/docs/running-tasks/); [FAQ](https://jules.google/docs/faq/)
- Limits: 15 / 100 / 300 daily tasks (rolling 24 h) and 3 / 15 / 60 concurrent tasks for Jules / Pro / Ultra; models listed as Gemini 2.5 Pro and "starting with Gemini 3 Pro". Still "Public Beta". — [Jules docs: Usage limits](https://jules.google/docs/usage-limits/) (Inference: the model names and tool versions on these pages look dated relative to Nov 2026; treat as possibly stale.)

**Cursor Cloud Agents (formerly Background Agents)**
- Run lifecycle, stated by Cursor: Start (web, IDE, CLI, API, Slack, issue/PR) → Provision ("an isolated VM for that agent", repo cloned) → Run (streams progress and artifacts) → Persist (conversation, metadata, artifacts) → Hand off ("pushes its branch and opens a pull request"; ready for review unless a draft is asked for) → Recycle ("hibernated and then deleted on lifecycle timers"). — [Cursor Docs: Cloud Agents security overview](https://cursor.com/docs/cloud-agent/security)
- Isolation: per-agent VMs, "Firecracker-based microVM infrastructure", in a separate AWS account; per-agent AES-256 keys; CMEK for Enterprise. — [Security overview](https://cursor.com/docs/cloud-agent/security)
- Environment: Ubuntu machines configured by agent-led setup, a saved snapshot, or a Dockerfile in `.cursor/environment.json`, plus an install script; "Builds" prepare environments in the background; resolution order personal saved env → team saved env → committed file; multi-repo environments; `repositoryDependencies` adds same-owner repos to git credentials. — [Cursor Docs: Cloud environment setup](https://cursor.com/docs/cloud-agent/setup); [Cloud Agents](https://cursor.com/docs/cloud-agent)
- Snapshots: "Encrypted point-in-time copies of the virtual machine disk" used to start or resume without recloning; kept up to 30 days of inactivity; conversation history kept indefinitely by default. — [Cursor Docs: Secrets & Network](https://cursor.com/docs/cloud-agent/security-network)
- Secrets live inside the VM: Environment Variables (visible to the agent), Runtime Secrets (env vars whose values are redacted to `[REDACTED]` in tool results, transcript and commits, but visible in the terminal), Build Secrets (Docker build only); OIDC tokens minted from a local socket are recommended for cloud roles. — [Secrets & Network](https://cursor.com/docs/cloud-agent/security-network)
- Network: "The agent has internet access by default"; egress controls restrict domains per user, team or environment; auto-runs all terminal commands, which Cursor names as an exfiltration risk. — [Secrets & Network](https://cursor.com/docs/cloud-agent/security-network); [Security overview](https://cursor.com/docs/cloud-agent/security)
- Repo access via the Cursor GitHub/GitLab app plus per-user account connection; "Access is inherited, never widened". Commits are signed with an HSM-backed Ed25519 key, authored as `Cursor Agent`, with a `Co-authored-by` trailer for the starter. — [Security overview](https://cursor.com/docs/cloud-agent/security); [Secrets & Network](https://cursor.com/docs/cloud-agent/security-network)
- Extras: artifacts (screenshots, videos, logs) as proof of work; remote desktop takeover and hand-back; repo hooks from `.cursor/hooks.json` run in the cloud (not during read-only exploratory turns); MCP over HTTP and stdio; a built-in Cloud MCP exposes transcripts and run events; "as many agents as you want in parallel". Billing at the selected model's rate; Premium plan and above. — [Cursor Docs: Cloud Agents](https://cursor.com/docs/cloud-agent)
- Self-Hosted Machines: Cursor keeps "the agent loop, inference, and planning"; a worker started with `agent worker start` holds an outbound HTTPS connection over which "Cursor sends agent tool calls"; no inbound ports; My Machines vs Team Pools; partner hosts include Modal, Daytona, E2B, Vercel, Cloudflare. — [Cursor Docs: Self-Hosted Machines](https://cursor.com/docs/cloud-agent/self-hosted)

**Devin (Cognition)**
- Architecture: "The Brain", a "stateless, cloud-based service" always in Cognition's cloud, and "The Devbox", a VM where Devin executes code; Enterprise Cloud (multi-tenant, "Each Devin session runs on its own isolated machine") or Customer Dedicated (single-tenant VPC over PrivateLink/IPSec). The workspace has a shell, browser and editor. — [Devin docs: Enterprise Deployment](https://docs.devin.ai/enterprise/deployment/overview)
- Environment: declarative "blueprints" (enterprise → org → repo, additive) with `initialize`, `maintenance`, `knowledge`, `post-build`, `clone`; builds produce a bootable snapshot, rerun on save and about every 24 hours; "Every session boots a fresh copy. Session changes don't persist back to the snapshot." — [Devin docs: Blueprints](https://docs.devin.ai/onboard-devin/environment/blueprints); [Enterprise environment overview](https://docs.devin.ai/enterprise/environment-management/overview)
- Secrets: org, personal, repo and session scopes; redaction on by default; "For shell commands, it binds secrets as environment variables whenever needed" (not exported into every shell). — [Devin docs: Secrets & Site Cookies](https://docs.devin.ai/product-guides/secrets)
- Access and steering: web, Slack, API; `devin --cloud` streams a cloud session to the terminal, `-r` resumes from any surface, `/handoff` moves a local session to the cloud and `/pickup` checks out the session's PR branch locally; `devin ssh` opens a shell on the VM; a cloud session can request access to the user's local machine. — [Devin docs: Devin Cloud in the CLI](https://docs.devin.ai/cli/cloud); [SSH](https://docs.devin.ai/cli/ssh)
- Cost unit: ACUs with budgets and per-user limits. — [Devin docs index (llms.txt): Usage policies](https://docs.devin.ai/llms.txt) (title and summary only; page not fetched)

### Inferences
- The control plane, not the sandbox, is the product: the session record, queue, credentials, and the GitHub integration live outside the VM everywhere. Cursor and Devin say so outright ("Brain" vs "Devbox"; self-hosted workers receive tool calls), and Claude's self-hosted runners only claim queued sessions. The sandbox is cattle that can be paused, snapshotted, reclaimed and rebuilt.
- Two credential models exist. Proxy substitution with a placeholder in the VM (Claude network secrets and GitHub proxy; Codex current network secrets; Open SWE's LangSmith GitHub proxy below) versus in-VM env vars with output redaction (Cursor Runtime Secrets, Devin). The first matches our harness's HD15; the second leaks to anything the agent runs.
- Setup splits into a cached "build" phase (setup script, snapshot) and a per-session "start" phase (SessionStart hook, Codex start skill, Devin maintenance, Cursor install). Everyone caches a filesystem snapshot, and everyone notes that background processes do not survive it.
- Every vendor names prompt injection plus agent egress as the main threat, and every vendor's network control is a proxy that covers only some processes (Copilot says so explicitly).
- Session portability is implemented as "same server-side session, different clients" (Copilot cloud sandboxes, Devin `-r`) or as "copy out" (Claude `--teleport` gives the terminal its own copy).

### Gaps
- No vendor publishes its sandbox technology except Cursor (Firecracker) and OpenAI ("VM-backed sandboxes"); Anthropic, GitHub, Google and Cognition say "VM" without naming the hypervisor.
- Default branch naming for Claude, Codex, Jules and Cursor cloud branches was not found in the fetched pages (Copilot's `copilot/` prefix is the only documented one).
- Clone depth: only Copilot documents that it overrides `fetch-depth`; the others don't state depth.
- Per-task wall-clock limits are documented only for Copilot on Actions (59 min); I found none for Claude, Codex, Cursor or Devin beyond idle-pause and command timeouts.
- Codex cloud's model and current resource ceilings, and Devin's per-session VM specs, were not found in primary pages.
- Jules' docs appear partly stale (Gemini 2.5/3 Pro, mid-2025 tool versions); a newer Jules API or CLI may exist that I did not fetch.

## Open-source implementations: how OpenHands, SWE-agent / mini-swe-agent and Open SWE separate the loop from the sandbox

### Takeaway
The open-source projects show two placements of the agent loop. OpenHands V1 and SWE-ReX put a small server inside the sandbox (OpenHands runs the whole agent loop in an in-container "agent server"; SWE-ReX runs only a shell server), while mini-swe-agent and Open SWE keep the loop outside and send each command in (`docker exec`, or a LangSmith sandbox API). The trend is toward an event-sourced, append-only log as the single source of truth, a pluggable workspace/sandbox interface, and a credential proxy in front of the sandbox.

### Cited Findings

**OpenHands (as of 2026-11-18)**
- The `OpenHands/OpenHands` repository is now "Agent Canvas", a "self-hosted developer control center" that runs OpenHands or any ACP agent (Claude Code, Codex, Gemini, Pi, OpenCode) on local, Docker, VM or cloud backends; it is "powered by the OpenHands Agent Server". — [OpenHands README @ 31c57c2](https://github.com/OpenHands/OpenHands/blob/31c57c207be72d0a228ea7a7e68a3a81bc98bdd5/README.md)
- The agent core moved to `OpenHands/software-agent-sdk` (version 1.62.0, MIT): four packages `openhands-sdk`, `openhands-tools`, `openhands-workspace`, `openhands-agent-server`; it is "the engine behind" the OpenHands CLI and OpenHands Cloud. — [software-agent-sdk README @ a6b92c2](https://github.com/OpenHands/software-agent-sdk/blob/a6b92c222aa1ee1ac9f1e08105493dd444a0b031/README.md)
- Design (paper, MLSys 2026): an "event-sourcing pattern treating all interactions as immutable events appended to a log"; agents, tools and LLMs are immutable, and `ConversationState` is "the only stateful component"; events persist as individual JSON files; crash recovery under 20 ms; V1 cut system-attributable failures by 61% versus V0 over 15 days. — [Wang et al., The OpenHands Software Agent SDK, arXiv 2511.03690](https://arxiv.org/abs/2511.03690) ([HTML](https://arxiv.org/html/2511.03690))
- Why V0 was split: in V0 "the sandbox for tools might crash while the agent continued (or vice versa), leading to corrupted sessions", and one user's heavy actions could crash other agents sharing the application. — [arXiv 2511.03690 HTML](https://arxiv.org/html/2511.03690)
- Loop placement: with a `RemoteWorkspace`, `Conversation` becomes a `RemoteConversation` that "serializes the agent configuration and delegates execution to an agent server over HTTP and WebSocket"; "the server executes using SDK components inside the container and streams events via WebSocket". The official image bundles the API server, VS Code Web, VNC desktop and Chromium; "Each agent instance runs in an independent container". — [arXiv 2511.03690 HTML](https://arxiv.org/html/2511.03690)
- Workspace backends in code: `docker`, `apptainer`, `cloud`, `remote_api`, `agent_sandbox`; `BaseWorkspace` exposes `execute_command`, `file_upload`, `file_download`, `git_changes`, `git_diff`, `pause`, `resume`; default image `ghcr.io/openhands/agent-server:latest-python`. — [openhands-workspace @ a6b92c2](https://github.com/OpenHands/software-agent-sdk/tree/a6b92c222aa1ee1ac9f1e08105493dd444a0b031/openhands-workspace/openhands/workspace); [sdk/workspace/base.py](https://github.com/OpenHands/software-agent-sdk/blob/a6b92c222aa1ee1ac9f1e08105493dd444a0b031/openhands-sdk/openhands/sdk/workspace/base.py)
- Agent server: REST + WebSocket, file-based storage of conversations and events, optional session API key, webhooks; `OH_CONVERSATION_RUNTIME` `local` or `docker` ("isolated per-conversation containers"); idle conversations suspend after 1200 s by default; `OH_SECRET_KEY` encrypts stored secrets. — [agent_server README @ a6b92c2](https://github.com/OpenHands/software-agent-sdk/blob/a6b92c222aa1ee1ac9f1e08105493dd444a0b031/openhands-agent-server/openhands/agent_server/README.md)
- Secrets and approvals: `SecretRegistry` is per-conversation and "late-bound"; tools read secrets only at execution time and outputs are masked; a `SecurityAnalyzer` rates calls low/medium/high/unknown and a `ConfirmationPolicy` pauses in `WAITING_FOR_CONFIRMATION`. — [arXiv 2511.03690 HTML](https://arxiv.org/html/2511.03690)
- Benchmark badge: SWE-bench 77.6 (README badge, linked to a spreadsheet; not independently checked). — [software-agent-sdk README](https://github.com/OpenHands/software-agent-sdk/blob/a6b92c222aa1ee1ac9f1e08105493dd444a0b031/README.md)

**SWE-agent, SWE-ReX and mini-swe-agent**
- SWE-agent (1.1.0 at commit 3ea751c, 2026-07-16) now says "Our general recommendation is to use mini-SWE-agent instead of SWE-agent going forward." — [SWE-agent README](https://github.com/SWE-agent/SWE-agent/blob/3ea751c087f32b16e039a2233dd6eefecef325d5/README.md)
- SWE-ReX (1.4.0 at 5c995c3) is "a runtime interface for interacting with sandboxed shell environments"; it keeps stateful shell sessions, runs many in parallel, and has deployments for local, Docker, Modal, Fargate, Daytona and remote; the split is `deployment/` (start the sandbox) versus `runtime/` (talk to it). — [SWE-ReX README and source](https://github.com/SWE-agent/SWE-ReX/tree/5c995c365dfb1fd5bc56fda688be5d8538f9931f)
- mini-swe-agent (2.4.6 at 04d809c): "some 100 lines of python for the agent class"; bash only, no tool-calling interface; "Executes actions with `subprocess.run` — every action is completely independent", which makes sandboxing "literally just switch out `subprocess.run` with `docker exec`". — [mini-swe-agent README @ 04d809c](https://github.com/SWE-agent/mini-swe-agent/blob/04d809ceab9df28f9adaed044884180159172930/README.md)

**LangChain Open SWE (now "Robin")**

Triggers: dashboard, GitHub issues and PR conversations, Slack, Linear, schedules; `/baby-sit` monitors PR CI. — [README](https://github.com/langchain-ai/open-swe/blob/1965cd136a1ba6b02ea486e8caee04fde7c2e858/README.md); [langgraph.json](https://github.com/langchain-ai/open-swe/blob/1965cd136a1ba6b02ea486e8caee04fde7c2e858/langgraph.json)

Defaults: 4 vCPUs, 16 GiB, 128 GiB snapshot FS, 2 h idle TTL, delete 7 days after stop. — [README](https://github.com/langchain-ai/open-swe/blob/1965cd136a1ba6b02ea486e8caee04fde7c2e858/README.md); [docs/CUSTOMIZATION.md §1](https://github.com/langchain-ai/open-swe/blob/1965cd136a1ba6b02ea486e8caee04fde7c2e858/docs/CUSTOMIZATION.md)

### Inferences
- Loop outside the sandbox (mini-swe-agent, Open SWE, Cursor self-hosted, Devin "Brain") keeps model keys and session state off the box and makes a sandbox crash recoverable; loop inside (OpenHands agent server, Claude Code in the VM, Codex) gives low-latency tools and lets the whole session move with the box. OpenHands' V0 lesson argues that whichever you pick, the session log must outlive the sandbox.
- mini-swe-agent's stateless `docker exec` per action is the cheapest sandbox contract to satisfy and is exactly what our N15 `exec` shape needs to emulate for the baseline.
- Open SWE shows that even an open project converges on proxy-injected GitHub credentials, and also shows the common weakness: installation-wide scope by default.

### Gaps
- I did not read OpenHands Cloud's hosted control plane (the multi-tenant scheduler), which lives outside these repos; its queueing and sandbox provider are undocumented here.
- Open SWE's AGENTS.md promises an "architecture inventory" that I could not find at this commit.
- No independent benchmark of these frameworks as cloud agents (vs SWE-bench scores) was found.

## Common components, and where products leave gaps

### Takeaway
A cloud coding agent is about twelve components, and only about four are the "agent": trigger intake, session/queue control plane, sandbox provider, environment build and snapshot cache, repo checkout and push identity, credential proxy and egress policy, the agent loop and its log, checkpoint/pause/resume, verification (tests, linters, code review, artifacts), PR delivery and post-PR follow-up, notifications and multi-client streaming, and observability/evals. The weak spots are the same across vendors: firewalls that cover only some processes, broad git token scope, no reaction to merge conflicts, and loss of in-flight background work when a VM is reclaimed.

### Cited Findings
- Triggers: web/mobile/desktop/CLI and scheduled routines (Claude); issues, PR `@copilot` mentions, automations on schedules or events (Copilot); Slack, `@cursor` on GitHub/Bitbucket, API, linked issues (Cursor); web, Slack, API (Devin); dashboard, GitHub, Slack, Linear, schedules (Open SWE). — [Claude](https://code.claude.com/docs/en/claude-code-on-the-web); [Copilot risks](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations); [Cursor](https://cursor.com/docs/cloud-agent); [Devin](https://docs.devin.ai/enterprise/deployment/overview); [Open SWE](https://github.com/langchain-ai/open-swe/blob/1965cd136a1ba6b02ea486e8caee04fde7c2e858/README.md)
- Queue and claim: Claude self-hosted places sessions on an environment queue that runners claim, with an optional autoscaling orchestrator. — [Self-hosted environments](https://code.claude.com/docs/en/self-hosted-environments)
- Environment build and cache: Claude snapshot after a ≤~5-minute setup script, ~7-day expiry; Codex legacy 12-hour container cache, current "publish" of a prepared filesystem; Jules "Run and Snapshot"; Cursor Builds and 30-day snapshots; Devin blueprint builds ~every 24 h. — sources above per product.
- Two-phase setup: Claude setup script vs SessionStart hook; Codex install script vs start skill (and legacy setup vs maintenance); Devin `initialize` vs `maintenance`. — [Claude](https://code.claude.com/docs/en/cloud-environments); [Codex](https://developers.openai.com/codex/environments/cloud-environments); [Devin](https://docs.devin.ai/onboard-devin/environment/blueprints)
- Verification evidence: Copilot runs security checks, secret scanning and Copilot code review before completing; Cursor produces screenshots, videos and logs; Codex "edits code, runs checks, and tries to validate its work" using AGENTS.md commands. — [Copilot risks](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations); [Cursor](https://cursor.com/docs/cloud-agent); [Codex legacy](https://developers.openai.com/codex/cloud/environments)
- Post-PR loops: Claude auto-fix via GitHub webhooks; Copilot Agent Merge; Open SWE `/baby-sit`. Gap named by Anthropic: no webhook when the base branch advances into a conflict. — [Claude](https://code.claude.com/docs/en/claude-code-on-the-web); [Copilot](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent); [Open SWE](https://github.com/langchain-ai/open-swe/blob/1965cd136a1ba6b02ea486e8caee04fde7c2e858/README.md)
- Attribution and audit: Copilot signed commits with session-log links; Cursor HSM-signed commits and co-author trailer; Claude labels GitHub replies as coming from Claude Code; Claude warns that its replies can trigger `issue_comment` automation such as Atlantis. — [Copilot risks](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations); [Cursor](https://cursor.com/docs/cloud-agent/security-network); [Claude](https://code.claude.com/docs/en/claude-code-on-the-web)
- Observability: Cursor's built-in Cloud MCP exposes transcripts, run events, environment details and setup logs; Copilot session logs and audit events; OpenHands agent server telemetry exporters. — [Cursor](https://cursor.com/docs/cloud-agent); [Copilot risks](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations); [agent_server README](https://github.com/OpenHands/software-agent-sdk/blob/a6b92c222aa1ee1ac9f1e08105493dd444a0b031/openhands-agent-server/openhands/agent_server/README.md)
- Evals: mini-swe-agent is the harness behind the SWE-bench "bash only" leaderboard; SWE-ReX was built for "massively parallel" benchmark runs. — [mini-swe-agent README](https://github.com/SWE-agent/mini-swe-agent/blob/04d809ceab9df28f9adaed044884180159172930/README.md); [SWE-ReX README](https://github.com/SWE-agent/SWE-ReX/blob/5c995c365dfb1fd5bc56fda688be5d8538f9931f/README.md)

### Inferences
- The minimal product is: trigger → control-plane session record → queue → sandbox from a cached snapshot → harness loop writing the session log outside the sandbox → completion checks → push via an identity the proxy holds → PR → webhook-driven follow-ups → notification.
- Verification is becoming the product differentiator (Copilot's self-review, Cursor's artifacts, Codex's AGENTS.md-driven checks), consistent with practitioners' review-capacity bottleneck.
- Branch-scope enforcement belongs to the git host (rulesets), not the proxy: Anthropic says its proxy "doesn't limit which branches a push can update".

### Gaps
- No vendor documents its scheduler, queue semantics, retry policy for infra failures, or how many concurrent sessions a single account may run (except Jules' 3/15/60 and Cursor's 10,000 self-hosted workers per user/team).
- No vendor publishes merge rates or task success rates for its cloud agent that I could fetch.

## Mapping onto our harness plan: what the plan covers and what a cloud coding agent needs beyond it

### Takeaway
The planned harness already covers the inside of the box well: the sandbox interface and Docker backend (N15/N17), a default-deny egress proxy with sentinel credentials (N20, HD15), sandboxed built-in tools (N21), the session log as the only source of truth with second-process resume (N2–N7, N35), a JSON-RPC protocol with reconnect (N26–N30), and completion checks and evals against mini-swe-agent (N32, N36–N38). What a cloud coding agent adds is the outside of the box: a multi-tenant control plane (session registry, queue, runner claim), a remote sandbox provider with snapshot/pause/resume, an environment build-and-cache pipeline, a GitHub App identity with a git-aware proxy and PR delivery, webhook-driven follow-ups, a network transport for the protocol with multi-client attach, notifications, and per-tenant cost/limits.

### Cited Findings
- Plan scope: §6 sandbox and credentials covers "separate sandbox and approval policies ... launched by the host, cleared env, default-deny egress proxy with host-scoped sentinels" (N15–N21); §8 protocol is "stdio JSONL first" (N26–N30); §10 evals "Inspect bridge, mini-swe-agent baseline, cost beside pass^k" (N32, N36–N39). — [build-harness.md §1](../../../plans/build-harness.md)
- HD4: `srt` for interactive runs and Docker for headless runs; HD15: "The credential proxy injects on reverse-proxy routes, not by intercepting TLS". — [build-harness.md §2](../../../plans/build-harness.md)
- HD8 seed suite: 30 tasks, k = 5, each trial 2 vCPUs, 4 GiB, 30-minute kill, $3 cap ("mini-swe-agent's default `cost_limit`"); infra failures scored apart. — [build-harness.md HD8](../../../plans/build-harness.md); matches `cost_limit: float = 3.0` in [mini-swe-agent default.py](https://github.com/SWE-agent/mini-swe-agent/blob/04d809ceab9df28f9adaed044884180159172930/src/minisweagent/agents/default.py)
- Harness guide: Docker with `--cap-drop ALL --read-only --network none`, and gVisor, Firecracker and hosted vendors as adapters chosen by threat model; hosted microVMs at about $0.05 per vCPU-hour (E2B, Daytona). — [agent-harness.md §6](../../../guides/agent-harness.md)
- Harness guide: OpenAI's `SandboxClient` separates a workspace manifest from the compute provider; Claude's `strictAllowlist` does not gate in-process tools such as WebFetch. — [agent-harness.md §6](../../../guides/agent-harness.md)
- Prior repo research: session portability "requires the session to be a server-side object with an event log, not a client-held transcript". — [beyond-chat-patterns note, background agents](../../../research/agent-ui/notes/beyond-chat-patterns.md)

### Inferences
- The harness should keep its "host launches the sandbox" rule; in the cloud the "host" becomes a runner process next to the sandbox, which holds the proxy and the log writer, while the loop can sit either in the runner (our default, like Cursor and Devin) or in the sandbox (like Claude Code and OpenHands). Keeping the loop in the runner preserves HD15 and keeps model keys out of the box.
- mini-swe-agent's bash-only, `docker exec`-per-action contract is the natural first remote backend test: if N15 can run mini-swe-agent's trajectories on a remote provider, the baseline (N37) works in the cloud too.
- The biggest new design decision is the snapshot/cache layer; the second is the GitHub identity (installation token scope and push rules). Both deserve ADRs before code.

### Gaps
- The plan has no todo for a network transport, a multi-tenant store, or GitHub App integration; whether those belong in Round N or a new round is an owner decision.
- I did not measure remote-provider cold starts; N19 measures only `srt` and Docker.
- Whether HD2's local-disk lock can be replaced by a remote lease without breaking HD1/HD2's guarantees was not analyzed here.
