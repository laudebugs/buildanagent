# Sandbox and credential providers for a pluggable harness sandbox (as of November 2026)

> **Fact-checked 2026-11-18.** This note keeps its original text. Corrections are logged in [fact-check-portable-agents.md](../fact-check-portable-agents.md) and applied in [the report](../portable-agents.md), which supersede this note where they disagree.

Scope: hosted and self-hosted backends a harness could plug in behind `SandboxClient` (plan §3, N15), and how each keeps API keys and repo tokens out of the sandbox, compared with HD15/N20. All pages were fetched on 2026-11-18 with `curl -sSL --max-time 30` unless noted. Prices are list prices as of November 2026. "Inference" marks my own reasoning; "secondary" marks claims not from the vendor's own page. GitHub's API was not reachable from this session (403 from the session's GitHub gate), so licences come from npm registry metadata or raw `LICENSE` files.

## Per provider: isolation, API surface, limits, persistence, network controls, regions, SDK and pricing

### Takeaway
Every serious hosted option now runs each sandbox in a VM boundary: Firecracker for E2B, Vercel, Cloudflare and Fly; Cloud Hypervisor or gVisor for Northflank; gVisor or a VM for Modal; Hyper-V for Azure. Daytona is the exception, because its default class is a namespaced container and only its VM classes get their own kernel. The providers split sharply on egress control. E2B, Vercel, Cloudflare, Daytona (Tier 3+) and Modal (beta) offer per-sandbox domain allowlists. Azure dynamic sessions and Cloud Run sandboxes offer only an on/off switch.

### Cited Findings

**E2B**
- Isolation: each sandbox is a Firecracker microVM. E2B blocks egress to private and link-local ranges "outside the guest… and cannot be disabled", and `169.254.169.254` answers from "the sandbox's own Firecracker metadata service", not a cloud metadata service. — [E2B docs, Restrict public access](https://docs.e2b.dev/network/restrict-public-access) (via [llms-full.txt](https://e2b.dev/docs/llms-full.txt))
- Plans: Hobby $0/month with $100 one-time credit, 8 vCPU / 8 GiB max, 10 GiB disk, **1 hour** max continuous runtime, 10 concurrent sandboxes, 1 create/s. Pro is $150/month, with **24 hours** max continuous runtime, 100 to 1,100 concurrent (add-ons of 500 slots at $500/month) and 5 creates/s. Secrets per project: 10 on Hobby, 100 on Pro. "Max continuous runtime is the time a sandbox can run **without being paused**… a paused sandbox is kept indefinitely with no time-to-live." — [E2B docs, Billing](https://docs.e2b.dev/billing)
- Usage price: vCPU $0.000014/s per vCPU ($0.0504/h; 2 vCPU is the default), RAM $0.0000045/s per GiB ($0.0162/GiB-h), "We charge per second of a running sandbox." — [E2B pricing](https://e2b.dev/pricing)
- API surface (JS SDK reference v2.64.0): commands (foreground, background, streaming), filesystem read/write/upload/download/watch, pre-signed upload and download URLs, public URL for ports, pause/resume, snapshots and fork ("snapshotted in place — paused, captured with its full filesystem and memory state, and resumed"), volumes, and lifecycle webhooks. — [E2B docs, commands](https://docs.e2b.dev/commands), [filesystem](https://docs.e2b.dev/filesystem), [fork](https://docs.e2b.dev/sandbox/fork), [persistence](https://docs.e2b.dev/sandbox/persistence), [volumes](https://docs.e2b.dev/volumes)
- Pause and resume timing (re-confirmed from prior R1): pause about 4 s per GiB of RAM, resume about 1 s. — [E2B persistence](https://e2b.dev/docs/sandbox/persistence); prior row in `docs/research/agent-harness/fact-check.md` R1
- Network: "Every sandbox has outbound internet access by default." `allowInternetAccess: false` equals `denyOut: ['0.0.0.0/0']`. `network.allowOut` / `denyOut` accept IPs, CIDRs and domain names. — [E2B, Internet access](https://docs.e2b.dev/network/internet-access)
- Bring-your-own SOCKS5 egress proxy: "Egress fails closed. If the proxy is unreachable… outbound connections from the sandbox fail instead of falling back to a direct connection." Allow and deny lists are evaluated first, on the host. E2B offers no static egress IPs on any plan. BYOP is not available in deployments built from the open-source `e2b-dev/runtime` repo. — [E2B, Bring your own proxy](https://docs.e2b.dev/network/byop)
- Self-host / BYOC: E2B offers BYOC deployments, plus the open-source `e2b-dev/runtime` repo and "E2B Embed". — [E2B, BYOP §Self-hosted deployments](https://docs.e2b.dev/network/byop); [E2B workload identity](https://docs.e2b.dev/iam/workload-identity) (BYOC mentions)
- Licence: `e2b-dev/infra` is Apache-2.0 ([raw LICENSE](https://raw.githubusercontent.com/e2b-dev/infra/main/LICENSE)). The `e2b` npm package 2.64.0 is MIT, published 2026-11-13; `@e2b/code-interpreter` 2.9.1 is MIT. — [npm registry: e2b](https://registry.npmjs.org/e2b)
- Browser use of the SDK is documented: input streaming needs streaming request bodies (Chromium over HTTP/2 only); in other browsers use `commands.sendStdin()`. — [E2B, Streaming](https://docs.e2b.dev/commands/streaming)

**Daytona**
- **Isolation, corrected.** The docs' Isolation page says the **Container** class is an "Isolated container with dedicated namespaces and enforced resource limits". **VM sandboxes (Linux VM and Windows)** are a "Full virtual machine with its own kernel", and only they support pause/resume, fork and hot (memory) snapshots. GPU sandboxes are isolated containers. The same docs' landing text still says sandboxes have "a dedicated kernel". — [Daytona llms-full.txt (generated 2026-11-17), Isolation and Overview](https://www.daytona.io/docs/llms-full.txt). This contradicts the prior R1 correction (below).
- Creation: "spinning up in under 90ms" (vendor claim). — [Daytona docs overview](https://www.daytona.io/docs/llms-full.txt)
- Pricing: vCPU $0.0504/h, memory $0.0162/GiB-h, storage $0.000108/GiB-h after the first 5 GiB free, Windows $0.0858/vCPU/h. "All billing is calculated per second." "$200 in free compute included." — [Daytona pricing](https://www.daytona.io/pricing)
- Lifecycle: the auto-stop interval defaults to **15 minutes** and "triggers even if there are internal processes running" (0 disables it). There are also auto-archive and auto-delete intervals, plus ephemeral sandboxes (auto-delete 0). Warm pools are limited to one per snapshot per region. — [Daytona sandboxes and snapshots (llms-full.txt)](https://www.daytona.io/docs/llms-full.txt)
- Network: a per-sandbox firewall with `networkAllowList` (IPv4 CIDR), `domainAllowList` (domains and wildcards), `networkBlockAll` and `outboundProxyUrl` (create-time only). The three filters are mutually exclusive, a conflict returns 400, and they can be updated while the sandbox runs. **Tier 1 and 2:** "Network access is restricted and cannot be overridden at the sandbox level." **Tier 3 and 4:** full internet by default, and a sandbox-level list "replaces the default policy… only destinations you list are allowed", including blocking "essential services" such as GitHub, npm and PyPI unless listed. — [Daytona, Network Limits (Firewall)](https://www.daytona.io/docs/llms-full.txt)
- Ingress: preview URLs need a token unless the sandbox is `public`. SSH tokens expire after 60 minutes by default. — [Daytona, Preview / SSH Access](https://www.daytona.io/docs/llms-full.txt)
- Regions: shared regions are `us` and `eu`. — [Daytona, Regions](https://www.daytona.io/docs/llms-full.txt)
- **Open source status:** "As of June 2026, Daytona's core development has moved to a private codebase. This repository will receive no further updates." The last public licence is AGPL-3.0 at v0.190.0. — [daytonaio/daytona README](https://raw.githubusercontent.com/daytonaio/daytona/main/README.md); [LICENSE at v0.190.0](https://raw.githubusercontent.com/daytonaio/daytona/v0.190.0/LICENSE)
- SDK: `@daytona/sdk` 0.232.0 (Apache-2.0, published 2026-11-16) and the same version under `@daytonaio/sdk`. — [npm registry](https://registry.npmjs.org/@daytona/sdk)

**Modal Sandboxes**
- Runtimes: gVisor, or a VM "with its own Linux kernel". "leave unset to let Modal choose for you". GPU sandboxes are gVisor only. Docker inside a sandbox needs the VM runtime. — [Modal Sandboxes guide](https://modal.com/docs/guide/sandboxes), Runtimes
- Lifetime: "default maximum lifetime of 5 minutes… a timeout of up to 24 hours"; beyond that, Modal recommends Filesystem Snapshots and restoring into a new sandbox. An `idle_timeout` is also available. — [Modal Sandboxes guide](https://modal.com/docs/guide/sandboxes), Timeouts
- API: `exec(argv[], {timeoutMs})` in Python, JS and Go, tunnels for ports, readiness probes, named sandboxes, tags and OIDC identity tokens (section listed in the guide's table of contents; content not extracted). — [Modal Sandboxes guide](https://modal.com/docs/guide/sandboxes)
- Network: outbound is open by default. Options are `block_network=True`, `outbound_cidr_allowlist`, and `outbound_domain_allowlist` (**Beta**), which "Only allows TLS traffic (port 443)". CIDR and domain lists combine additively. "Currently, DNS traffic is allowed without restriction except when all outbound traffic is blocked." The experimental `proxy_traffic_via_sidecar` routes port-443 traffic through a sidecar, whose controls replace the sandbox's own for that port. — [Modal Sandbox networking](https://modal.com/docs/guide/sandbox-networking)
- Pricing: "Sandboxes are billed at non-preemptible rates of 3x list price": $0.00003942/core/s CPU and $0.00000667/GiB/s memory. Functions list rates are $0.0000131/core/s and $0.00000222/GiB/s. The page has a "Region selection" multiplier section (not extracted). — [Modal pricing](https://modal.com/pricing). The prior R1 conversion stands: one core is 2 vCPUs, so $0.14/core-h equals $0.071/vCPU-h.
- SDK: npm `modal` 0.11.2 (Apache-2.0, 2026-11-17); PyPI `modal` 1.6.4. — [npm registry](https://registry.npmjs.org/modal), [PyPI](https://pypi.org/pypi/modal/json)

**Cloudflare Sandbox SDK / Containers**
- Isolation: "Each container instance runs in a Firecracker microVM with its own kernel and network. No other workload on the Cloudflare network shares that kernel." — [Cloudflare Containers llms-full.txt](https://developers.cloudflare.com/containers/llms-full.txt); Sandbox docs: "Each instance is a microVM with its own kernel and network" — [Cloudflare Sandbox llms-full.txt](https://developers.cloudflare.com/sandbox/llms-full.txt)
- Runtime coupling: "The Sandbox SDK is designed for use within Cloudflare Workers. If your application runs outside of the Workers ecosystem, it cannot interact with sandboxes directly." Each sandbox is a Durable Object with a container. — [Cloudflare Sandbox docs](https://developers.cloudflare.com/sandbox/llms-full.txt)
- API: `exec`, `execStream`, file APIs, `exposePort` (preview URLs), `mountBucket` (R2 and S3-compatible), directory backups to R2, `keepAlive`, and `sleepAfter` (default `"10m"`). — [Cloudflare Sandbox docs](https://developers.cloudflare.com/sandbox/llms-full.txt)
- Cold start: "Container cold starts can often be in the 1-3 second range, but this is dependent on image size". — [Cloudflare Containers architecture](https://developers.cloudflare.com/containers/llms-full.txt)
- Instance types (vCPU / memory / disk): lite 1/16 / 256 MiB / 2 GB; basic 1/4 / 1 GiB / 4 GB; standard-1 1/2 / 4 GiB / 8 GB; standard-2 1 / 6 GiB / 12 GB; standard-3 2 / 8 GiB / 16 GB; standard-4 4 / 12 GiB / 20 GB. Custom types are allowed under the `durable_object` scheduling policy. — [Containers limits](https://developers.cloudflare.com/containers/platform-details/limits/) (page last updated 2026-11-12)
- Pricing: billed "for every 10ms that they are actively running", inside the $5/month Workers Paid plan. Beyond the included usage, $0.0000025 per GiB-second memory, $0.000020 per vCPU-second and $0.00000007 per GB-second disk. Egress is priced per region at $0.025, $0.05 or $0.04 per GB (region mapping not extracted). — [Containers pricing](https://developers.cloudflare.com/containers/pricing/) (page last updated 2026-11-13)
- Network: class fields `enableInternet = false`, `allowedHosts`, `deniedHosts` (hosts or CIDRs), and **outbound handlers** (`outbound`, `outboundByHost`), which are "programmable egress proxies that run on the same machine as the sandbox. They have access to all Workers bindings." Hosts can be changed at runtime (`setOutboundByHost`, `removeOutboundByHost`). `deniedHosts`/`allowedHosts` are evaluated before handlers. — [Sandbox outbound traffic docs](https://developers.cloudflare.com/sandbox/llms-full.txt)
- HTTPS interception: `interceptOutboundHttps()` needs the container to trust `/etc/cloudflare/certs/cloudflare-containers-ca.crt`. "The CA is ephemeral and only exists at runtime", so it must be installed from the entrypoint. A container has 128 intercept entries. — [Containers outbound traffic / API](https://developers.cloudflare.com/containers/llms-full.txt)
- SDK: `@cloudflare/sandbox` 1.0.3 (Apache-2.0, 2026-10-22). — [npm registry](https://registry.npmjs.org/@cloudflare/sandbox). The session's skill list also names an "SDK 1.0 preview" `@cloudflare/sandbox@next` (not fetched).

**Vercel Sandbox**
- Isolation: "Each sandbox runs in its own Firecracker microVM with a dedicated kernel". `sudo`, Docker, VPN clients and FUSE work inside. — [Vercel Sandbox security model](https://vercel.com/docs/sandbox/concepts/security)
- Pricing (iad1): Active CPU $0.128/h ("Time spent waiting for I/O… does not count"), provisioned memory $0.0212/GB-h (billed in 1-minute minimum increments), creations $0.60 per 1M, snapshot storage $0.08/GB-month, drive storage $0.05/GB-month. ### Inferences
- Hosted CPU list prices cluster at $0.05–0.13 per vCPU-hour. Vercel ($0.128 per Active-CPU hour) and AgentCore (CPU billed net of I/O wait) charge only for busy CPU, which favours agent workloads that mostly wait on the model. Cost comparisons must therefore model utilisation, not just list rates.
- Pinning: AGENTS.md requires releases at least one week old. As of 2026-11-18, `e2b` 2.64.0 (5 days), `@vercel/sandbox` 4.0.0 (6 days), `@daytona/sdk` 0.232.0 (2 days) and `modal` 0.11.2 (1 day) are too new to pin, so a verify harness would pin the previous release of each.
- Daytona's move to a private codebase removes the self-host path for new versions. Treat it as hosted-only.

## Credentials: how each provider or pattern keeps API keys and repo tokens out of the sandbox, compared with HD15/N20

### Takeaway
Four hosted providers now ship the HD15 pattern natively, in two variants. Daytona's is closest to ours: an opaque placeholder in the sandbox env, swapped by an outbound proxy only for allowlisted hosts. E2B, Vercel and Cloudflare instead keep a reference in the network config and inject headers by intercepting TLS with a per-sandbox CA, which HD15 deliberately avoided. The provider owns that CA, though, so we do not have to build it. Cloudflare's `outboundByHost` over plain HTTP to a pseudo-host is almost exactly HD15's reverse-proxy route with no CA. Azure and Cloud Run offer no injection, so credentials there must stay entirely outside, with egress disabled.

### Cited Findings
- **HD15 (ours):** a tool calls `http://127.0.0.1:<port>/<route>/…`, and the host-side proxy forwards to the route's HTTPS host, "adding the credential header when the sentinel in the request matches and the method is allowed". Everything else leaves only through `CONNECT` to allowlisted names that resolve outside loopback, link-local and metadata ranges. There is no TLS interception, because "a CA inside every sandbox image is work the first consumers do not need". — `docs/plans/build-harness.md` HD15; signatures `CredentialRoute { route, host, methods, header, secret }`, `startEgressProxy`, `scrubSecrets` in §3
- **Daytona Secrets:** "the sandbox holds an opaque placeholder token" (`dtn_secret_<random>`) mapped to an env var. The proxy swaps it "only when the request goes to a host you have allowed". For other hosts "the placeholder is forwarded unchanged", and "A secret without an allowlist is substituted for every host." Substitution covers HTTPS headers only, never plain HTTP, bodies, query strings or transformed placeholders; Basic auth is decoded first. — [Daytona Secrets](https://www.daytona.io/docs/llms-full.txt)
- **E2B Secrets:** values are write-only through the API, and the "egress proxy injects the real value into matching outbound HTTPS requests outside the sandbox". A rule's `transform.headers` uses `Secret.fill('name')`. Plain HTTP gets no injection. Clients with their own CA bundle must trust the egress proxy. "Injection is keyed on the destination host. Every process in the sandbox that sends an HTTPS request to that host gets the secret". If a secret fails to resolve, the header is omitted ("fail-open… silent for traffic"). Deleting a secret "does not revoke the credential at its provider". Rotation needs no sandbox restart. Keep the E2B API key itself outside the sandbox. — [E2B Secrets](https://docs.e2b.dev/secrets), [inject](https://docs.e2b.dev/secrets/inject), [delete](https://docs.e2b.dev/secrets/delete)
- **E2B Workload Identity:** "Give sandbox workloads short-lived identity tokens instead of long-lived secrets". It mints JWT-SVIDs (SPIFFE) for an audience such as `sts.amazonaws.com`, which the egress proxy injects into requests. It is generally available on E2B Cloud and in BYOC on request. — [E2B workload identity](https://docs.e2b.dev/iam/workload-identity)
- **Vercel credentials brokering:** "The credential stays outside the sandbox. The sandbox firewall adds it to matching requests as they leave". The only managed credential is npm today. Arbitrary injection goes through firewall `transform` rules. For transform, forward and direct-response domains, "the firewall decrypts HTTPS traffic… re-encrypts it with a certificate signed by a certificate authority (CA) unique to your sandbox", and Vercel installs that CA in the system trust store and sets `CURL_CA_BUNDLE`, `GIT_SSL_CAINFO` and others. — [Vercel Sandbox credentials](https://vercel.com/docs/sandbox/credentials); [security model](https://vercel.com/docs/sandbox/concepts/security); [firewall](https://vercel.com/docs/sandbox/concepts/firewall)
- **Cloudflare outbound handlers:** "Because outbound handlers run in the Workers runtime — outside the sandbox — they can hold secrets that the sandbox itself never sees. The sandbox makes a plain HTTP request, and the handler attaches the credential". The example sets `x-auth-token` from `env.SECRET` for `github.com`, and plain HTTP to the handler "remain[s] secure because they run on the same machine as the sandbox". HTTPS interception needs the ephemeral CA. — [Cloudflare Sandbox outbound traffic](https://developers.cloudflare.com/sandbox/llms-full.txt); [Containers outbound traffic](https://developers.cloudflare.com/containers/llms-full.txt)
- **Modal:** offers no stored-secret injection at egress on the fetched pages. HTTPS can be relayed through a sidecar (`proxy_traffic_via_sidecar`, experimental), where our own proxy could run, and OIDC identity tokens are listed. — [Modal networking](https://modal.com/docs/guide/sandbox-networking); [Sandboxes guide](https://modal.com/docs/guide/sandboxes)
- **Northflank:** advertises "Secrets at egress", "model API key injected at egress". — [Northflank sandboxes](https://northflank.com/product/sandboxes) (marketing; not verified in docs)
- **Azure:** offers no injection. Its guidance is to assume untrusted code has "full access to the container, including its environment variables, secrets, and files". — [Session pools](https://learn.microsoft.com/en-us/azure/container-apps/session-pool)
- **Cloud Run sandboxes:** by default they get no parent env vars, secrets or metadata server, but offer no injection. — [Code execution in Cloud Run](https://cloud.google.com/run/docs/code-execution)
- **Fly:** scoped, expiring, revocable tokens (app-scoped deploy, SSH, machine-exec) cover the control plane only. — [Fly tokens](https://fly.io/docs/security/tokens/)
- **Prior repo findings still relevant:** OpenAI rejects credential-bearing mounts whose helper runs in the sandbox. Vercel's sandbox client token persists in serialized session state. — `docs/research/agent-harness/notes/permissions-and-sandboxing.md` (OAIDOC clients.mdx:166, 170)

### Inferences
- **HD15 transfers to remote sandboxes in three ways.** For a remote sandbox, `127.0.0.1` is the sandbox's own loopback, so the host-side proxy cannot be reached as written.
  1. Use the provider's native injection: Daytona placeholders map 1:1 to our `sentinels`, and E2B `rules`, Vercel `transform` and Cloudflare `outboundByHost` map to `CredentialRoute`.
  2. Point the provider's upstream-proxy option at our proxy, run as a reachable, authenticated service: E2B BYOP (SOCKS5, fails closed), Daytona `outboundProxyUrl`, or a Modal sidecar.
  3. Run our proxy as a sidecar inside the VM boundary but outside the agent's process. This only helps if the provider separates the two, as Modal's sidecars do.

  Option 1 is cheapest. It moves trust to the vendor, and on E2B and Vercel it brings TLS interception, which HD15 chose to avoid locally.
- **Scope gaps against HD15's per-host, per-method rule.** E2B keys injection on host only: "every process" sending to that host gets it, with no method filter documented. Daytona substitutes an un-allowlisted secret for every host, so the adapter must always set `hosts`. Vercel's `subnets.allow` bypasses brokering. Cloudflare handlers can check `request.method` themselves, as the docs' GET-only example shows. Only Cloudflare reproduces our method check natively, so the E2B, Daytona and Vercel adapters lose method scoping unless we front them with our own proxy.
- **Short-lived repo tokens:** E2B Workload Identity (OIDC to AWS STS) and Modal OIDC tokens make per-sandbox federation possible. For GitHub, the usual pattern is a GitHub App installation token minted host-side and injected at egress. I could not confirm the token's lifetime from the fetched docs (see Gaps).

### Gaps
- GitHub App installation-token lifetime: the docs source fetched uses template variables, and the "expires after one hour" figure was not found in text. It is commonly stated as one hour (unverified here).
- Whether E2B or Vercel rules can match on HTTP method or path is not documented on the pages read.
- Northflank's egress-secret mechanism is described only on a marketing page.

## Mapping each provider onto the planned `SandboxClient` interface (N15), and which cannot meet fail-closed, no-credentials-inside, network-allowlist

### Takeaway
`exec`, `readFile`, `writeFile` and `dispose` map directly onto every TypeScript SDK. The adapter work is in `provision` (translating `SandboxPolicy.network` to each vendor's allowlist, and uploading the `WorkspaceManifest`), in `signal` and `timeoutMs` (kill on abort), and in producing a typed `{ denied: SandboxDenial }`, which no vendor reports. E2B, Vercel, Cloudflare and Daytona (Tier 3+) meet all three hard requirements, and Modal meets them with beta caveats. Azure dynamic sessions and Cloud Run sandboxes fail the allowlist requirement, because egress is on/off only. Fly Machines offers no documented allowlist.

### Cited Findings
- Interface to match: `SandboxClient { tier: "none"|"os"|"container"|"gvisor"|"microvm"; stops: ("mistakes"|"exfiltration"|"hostile_process")[]; provision(manifest, policy): Promise<Sandbox> /* throws SandboxUnavailableError */ }`, `Sandbox { exec(command: string[], { cwd?, env, signal, timeoutMs? }): Promise<ExecResult>; readFile; writeFile; dispose }`, `SandboxPolicy { readRoots; writeRoots; network: { allow; deny } }`. The conformance suite requires that writes outside `writeRoots` are denied, network is denied unless allowlisted, env holds only `spawnEnv` names, and an unavailable backend throws rather than running unsandboxed. — `docs/plans/build-harness.md` §3 and the conformance bullet
- Exec shapes: Modal takes argv arrays (`sb.exec(["python","-c",…], {timeoutMs})`) ([Modal](https://modal.com/docs/guide/sandboxes)). Cloudflare takes a command string (`sandbox.exec("npm run build")`, `execStream`) ([CF Sandbox](https://developers.cloudflare.com/sandbox/llms-full.txt)). E2B runs commands with streaming and background modes ([E2B commands](https://docs.e2b.dev/commands)). Daytona passes env per command (`WithCommandEnv`) ([Daytona](https://www.daytona.io/docs/llms-full.txt)). Vercel `runCommand()` takes `sudo: true` ([Vercel security](https://vercel.com/docs/sandbox/concepts/security)). Azure code interpreter takes a POST of code to an executions endpoint, limited to 220 s ([Azure](https://learn.microsoft.com/en-us/azure/container-apps/sessions-code-interpreter)). Cloud Run runs a local `sandbox do -- <argv>` binary ([Cloud Run](https://cloud.google.com/run/docs/code-execution)).
- Default-open egress that the adapter must override: E2B ([source](https://docs.e2b.dev/network/internet-access)), Modal ([source](https://modal.com/docs/guide/sandbox-networking)), Vercel (`allow-all`, [source](https://vercel.com/docs/sandbox/concepts/firewall)), Daytona Tier 3+ ([source](https://www.daytona.io/docs/llms-full.txt)). Default-closed: Azure (`EgressDisabled`, [source](https://learn.microsoft.com/en-us/azure/container-apps/session-pool)) and Cloud Run sandboxes ([source](https://cloud.google.com/run/docs/code-execution)).
- Fail-closed primitives: E2B BYOP fails closed when the proxy is unreachable ([source](https://docs.e2b.dev/network/byop)), and Vercel's empty policy is `deny-all` ([source](https://vercel.com/docs/sandbox/concepts/firewall)). Two fail-open edges: E2B silently omits an unresolved secret header ([source](https://docs.e2b.dev/secrets/inject)), and Modal allows DNS unless all traffic is blocked ([source](https://modal.com/docs/guide/sandbox-networking)). Vercel `subnets.allow` also leaves DNS open ([source](https://vercel.com/docs/sandbox/concepts/firewall)).
- Daytona Tier 1/2 organisations cannot set sandbox-level lists: "Organization-level network restrictions take precedence". — [Daytona Network Limits](https://www.daytona.io/docs/llms-full.txt)

**Mapping table (inference from the findings above)**

| Provider | `tier` | `exec` | read/write | `dispose` | `network.allow` (names) | No creds inside | Verdict |
|---|---|---|---|---|---|---|---|
| E2B | microvm | direct (argv joined or via shell; adapter maps `signal` to kill) | direct | kill | `allowOut` domains plus `denyOut: [allTraffic]` | native Secrets or BYOP to our proxy | **Meets all three** |
| Vercel | microvm | `runCommand` | direct | stop; set `persistent: false` | user-defined policy (SNI, so domain fronting is possible) | `transform` brokering | **Meets all three**; ban `subnets.allow` in the adapter |
| Cloudflare Sandbox | microvm | string command (adapter shell-quotes argv) | direct | destroy | `enableInternet=false` plus `allowedHosts` | `outboundByHost` in the Worker | **Meets all three**, but the harness must run in Workers |
| Daytona | container by default; microvm for VM class | direct, per-command env | direct | delete; ephemeral | `domainAllowList` (Tier 3+ only) | placeholder Secrets with `hosts` | Meets all three on Tier 3+ only; the tier label depends on class |
| Modal | gvisor or VM; adapter must set `runtime` explicitly | argv native | direct | terminate | `outbound_domain_allowlist` (beta, 443 only, DNS open) | no native injection; sidecar proxy | Meets with caveats |
| AgentCore Code Interpreter | unclear (docs say "containerized", pricing says "microVM") | session API | direct (100 MB inline) | stop session | not confirmed (network modes gap) | none documented | Unverified |
| Azure dynamic sessions | VM (Hyper-V) | HTTP code execution, 220 s cap; custom containers differ | file API | cooldown or deallocate | **on/off only** | none | **Fails allowlist** (usable only with `EgressDisabled`, i.e. no network at all) |
| Cloud Run sandboxes (Preview) | unknown nested boundary inside a gen2 microVM | local `sandbox do` | bind mounts | process exit | **on/off only** (`--allow-egress` reaches all the resource can) | env, secrets and metadata hidden by default | **Fails allowlist**; it is also in-container, so the harness must run on Cloud Run |
| Fly Machines | microvm | Machines exec API | via exec | destroy | none documented | none native | **Fails** unless we add our own egress proxy in the image |
| Docker (self-host) | container | `docker exec` | `docker cp` | rm | `--network none` plus our proxy | our HD15 proxy | Meets (planned N17) |
| gVisor / Firecracker (self-host) | gvisor / microvm | our agent | our agent | our code | our proxy | HD15 | Meets; we build the orchestration |

### Inferences
- **`stops` honesty:** microVM providers can claim `["mistakes","exfiltration","hostile_process"]` only with an allowlist set. With default-open egress they stop only `hostile_process` against the host, not exfiltration. The adapter should compute `stops` from the policy it actually applied.
- **`SandboxDenial`:** no vendor returns a structured "denied by sandbox" result. Network denials show up as connection errors and file-root violations as EACCES. To keep the escalation state machine (N18) working, the adapter would have to enforce `writeRoots` itself (mounting or chmod) and infer denials from proxy logs, which is easiest with our own proxy or the Cloudflare handler, where we see every request.
- **Fail-closed `provision`:** the adapter should read back the effective network config after create (E2B, Daytona and Vercel can all update policy at runtime), compare it with the requested `SandboxPolicy`, and throw `SandboxUnavailableError` on mismatch. That covers Daytona Tier 1/2 org overrides and Modal `runtime` left unset.
- **`readRoots`/`writeRoots`:** hosted VMs give the agent root over the whole guest, so roots are advisory unless enforced in-guest (`--read-only` style mounts). The trust boundary becomes the VM plus egress, not the file roots.
- **First backends (inference):** after `srt` and Docker, **E2B** first among hosted options: the richest egress and secret model, Apache-2.0 infra for self-host, and a framework-neutral TS SDK. **Cloudflare Sandbox** comes next for a Workers-hosted harness, because `outboundByHost` is HD15 almost verbatim. **Vercel** is third. Defer Daytona (tier-gated allowlists, container default, no longer open source) and Modal (beta domain allowlist, DNS open). Reject Azure dynamic sessions and Cloud Run sandboxes for tool execution that needs any network. Both remain usable for no-network code interpreters.

### Gaps
- Whether E2B, Daytona, Modal and Vercel SDKs run inside Cloudflare Workers or other edge runtimes is not documented on any page fetched. Only Cloudflare states its SDK is Workers-only. E2B documents browser support with streaming caveats, which suggests a fetch-based client (inference). Modal's JS client was not examined. All need a workerd smoke test.
- No vendor documents an abort/kill latency guarantee for in-flight commands, which our `signal` semantics need.

## "Bring your own API key" for the model: how keys are supplied per runtime and kept out of logs and sandboxes

### Takeaway
The model key belongs to layer 1 (the gateway) in the host process. It comes from a Worker secret binding on Cloudflare, or from env or a secret manager on Node, and it never goes to the sandbox. If agent code inside the sandbox must call the model itself (for example, running a CLI agent inside), give it a placeholder and let egress injection add the real key for the model host only. Daytona, E2B, Vercel `transform`, Cloudflare handlers and Northflank all support this, and the harness's `scrubSecrets` must still run before every log append.

### Cited Findings
- **Secret stores on the first-class clouds:**
  - **Cloudflare:** per-Worker secrets are encrypted bindings read via `env` ([Workers secrets](https://developers.cloudflare.com/workers/configuration/secrets/)). Secrets Store is "a secure, centralized location in which account-level secrets are stored and managed… across all Cloudflare data centers". It binds to Workers through `secrets_store_secrets` (`binding`, `store_id`, `secret_name`) ([Secrets Store with Workers](https://developers.cloudflare.com/secrets-store/integrations/workers/)).
  - **AWS:** ECS and Fargate inject secrets "from AWS Secrets Manager and Amazon EC2 Systems Manager Parameter Store", referenced as environment variables (`secrets`) or as log-driver `secretOptions` ([ECS sensitive data](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/specifying-sensitive-data-secrets.html)). The Secrets Manager price is per secret per month plus per 10,000 API calls; the page renders the figures client-side, so no numbers were extracted ([Secrets Manager pricing](https://aws.amazon.com/secrets-manager/pricing/)). AgentCore Identity offers "identity and credential management for agent applications" with credential providers; details were not extracted ([AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html)).
  - **GCP:** Secret Manager has IAM access control, versions, replication policies and rotation schedules ([Secret Manager overview](https://cloud.google.com/secret-manager/docs/overview)). Cloud Run exposes secrets as environment variables or volume mounts ([Cloud Run secrets](https://cloud.google.com/run/docs/configuring/services/secrets)).
  - **Azure:** Key Vault stores "tokens, passwords, certificates, API keys, and other secrets", and its Premium tier uses HSM-protected keys ([Key Vault overview](https://learn.microsoft.com/en-us/azure/key-vault/general/overview)). Container Apps secrets can reference Key Vault through a managed identity, and the docs advise against inline values in production ([Container Apps secrets](https://learn.microsoft.com/en-us/azure/container-apps/manage-secrets)).
  - **Vercel:** "**Secret** values are write-only after saving. Use them for passwords, API keys, and tokens". Build logs replace Secret values of 32+ characters with `[REDACTED]` ([Vercel sensitive environment variables](https://vercel.com/docs/environment-variables/sensitive-environment-variables)).
- Cloudflare Workers: "Secrets are a type of binding that allow you to attach encrypted text values to your Worker". They are read via `env.NAME` or `import { env } from "cloudflare:workers"`. — [Workers secrets](https://developers.cloudflare.com/workers/configuration/secrets/)
- In Cloudflare Sandbox, outbound handlers "have access to all Workers bindings", so a model key held as a Worker secret can be attached on egress without entering the container. — [CF Sandbox outbound](https://developers.cloudflare.com/sandbox/llms-full.txt)
- Daytona's docs name "an LLM API key" as the motivating secret for placeholder injection. — [Daytona Secrets](https://www.daytona.io/docs/llms-full.txt). Northflank shows "model API key injected at egress". — [Northflank](https://northflank.com/product/sandboxes)
- E2B: keep the E2B API key in "your trusted application… outside the sandbox". Secret values are never returned by reads, lists or errors. — [E2B Secrets](https://docs.e2b.dev/secrets)
- Repo design: "Model gateway keys stay in layer 1, outside the sandbox, and secrets stay out of the session log". The harness takes API keys or proxy-injected credentials, "never consumer-subscription OAuth". — `docs/guides/agent-harness.md` §6. `scrubSecrets(entry, secrets)` is "applied before every append" (N20). — `docs/plans/build-harness.md` §3
- Inherited environments are the main leak path: Codex inherits all variables by default, and Claude's CLI inherited the verify harness's environment until it received an allowlisted `env`. — `docs/guides/agent-harness.md` §6. Azure tells users to assume sandboxed code can read env vars and secrets. — [Azure session pools](https://learn.microsoft.com/en-us/azure/container-apps/session-pool)

### Inferences
- Per runtime: Node or CLI harnesses read the key from env or a secret manager once into the gateway and pass `spawnEnv` (allowlist) to sandbox exec. A Workers harness uses a secret binding or a Secrets Store binding; AWS uses Secrets Manager injected as task `secrets`; GCP uses Secret Manager as an env var or volume; Azure uses Key Vault references through managed identity; Vercel uses Secret-type env vars. In every case the key lands in the harness process, and `spawnEnv` keeps it out of sandbox exec. Hosted sandboxes never receive the key in `env`; they get only a placeholder or a route.
- The sandbox provider's own API key (E2B, Daytona, Vercel token) is a second secret. It must stay with the harness, never in the sandbox or in serialized session state. Vercel's token persisting in serialized state (prior note) is a concrete risk for N5's session store.
- Placeholder values (Daytona's `dtn_secret_…`, our sentinels) are safe to log. Real values must be added to `scrubSecrets`' list as soon as they are loaded, because tool output can echo headers.

### Gaps
- Secrets Manager, Secret Manager and Key Vault prices were not extracted (client-rendered or not fetched). Rotation behaviour was not read in detail.
- Vercel redacts Secret values only in build logs and only at 32 characters or longer. Shorter keys, and runtime logs, are not covered by that rule, so the harness's `scrubSecrets` remains necessary.
- No provider documents redacting injected values from its own request logs. Whether E2B, Vercel or Daytona log transformed headers is unknown.
