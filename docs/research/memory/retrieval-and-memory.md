# Agents should carry a small core, search for the rest, and keep long-term memory as sourced records that expire

Chapter T36 of the book must teach retrieval and long-term memory, and our plans say little about either: "just-in-time retrieval by reference" in layer 5 and "File-based memory first" in layer 6 ([main report](../agent-sdks-and-harness-design.md); [AGENTS.md](../../../AGENTS.md#planned-architecture-when-code-starts)). The evidence gathered on 19 November 2026 supports both phrases and supplies the rules they leave out. Carrying everything fails early, because long inputs degrade well before the advertised window: on NoLiMa, 11 of 13 models fell below half their short-input score at 32K tokens ([arXiv 2502.05167v3](https://arxiv.org/abs/2502.05167)). Indexing everything is no safe default either, because carrying a stable, cached prefix costs a tenth of the base input price or less as of November 2026 ([Claude pricing](https://platform.claude.com/docs/en/about-claude/pricing)). Memory adds a third risk. An attacker who only sends queries can plant a record in memory, which MINJA did in 98.2% of attempts, and later sessions then obeyed it in 76.8% ([arXiv 2503.03704v5](https://arxiv.org/abs/2503.03704)).

Five findings answer the research question, with every version, price and status as of November 2026. First, an agent should carry only a small, stable core (instructions, an index of what it remembers and its few most-used tools) and fetch everything else through tools when a step needs it. Second, the first retriever should be keyword search, grep over files or BM25 over a corpus, with embeddings added only after a measured miss and then fused with the keyword list. Third, every retrieved chunk and every stored memory is untrusted input, so access control runs before ranking and memory writes carry their source. Fourth, memory that outlives a task works best as small, typed records in files, written through an explicit tool and recalled through a short index plus search. Each record is checked against its source before use and forgotten by an expiry that only a successful check renews. Fifth, all eight of our SDKs can retrieve through tools, six ship a long-term memory primitive of their own, and none expires a memory inside the process, so expiry and deletion are ours to build. This report traces each finding to its sources, then turns them into what Chapter T36 should teach, the examples it needs and proposed plan changes. Its thesis is that an agent should carry pointers, search with keywords first, and keep long-term memory as sourced records that it checks before trusting and forgets unless a check renews them.

## Nine terms are used one way throughout

**Carrying context** means putting text into every model request, whether the model needs it on that step or not; the papers call carrying a whole corpus **long context**. **Retrieval** means fetching text into the request only when a step needs it, through a tool call or a search the harness runs. **Keyword search** ranks text by the words it shares with the query, as grep and BM25 do. **Vector search** ranks text by the distance between embeddings, and **hybrid search** fuses a keyword list and a vector list into one ranking. **Long-term memory** is anything the agent writes during one task and reads in a later one; the session log of a single task (Chapter T15's subject) is excluded. A **memory record** is one stored item of long-term memory, and **forgetting** is any rule that stops a record from reaching the model, whether by expiry, supersession or deletion.

## Carry the small, stable core, and retrieve the rest when a step needs it

**Long inputs degrade before the window fills, so carrying everything costs quality as well as money.** Liu et al. found that models use the middle of a long input worst. GPT-3.5-Turbo lost more than 20% on multi-document QA, and with 20 or 30 documents it scored below its closed-book 56.1% ([Lost in the Middle, arXiv 2307.03172v3](https://arxiv.org/abs/2307.03172)). RULER tested 17 models that claim 32K tokens or more, and only half held "satisfactory performance" at 32K ([arXiv 2404.06654v3](https://arxiv.org/abs/2404.06654)). When the word overlap between question and answer was removed in NoLiMa, GPT-4o fell from 99.3% to 69.7% at 32K ([arXiv 2502.05167v3](https://arxiv.org/abs/2502.05167)). Chroma, which sells "open-source search infrastructure for AI" and so has a stake in retrieval, saw all 18 models it tested degrade as input grew. On LongMemEval questions every model scored much higher on a focused prompt of about 300 tokens than on the full prompt of about 113,000 ([Chroma, Context Rot](https://research.trychroma.com/context-rot)). Anthropic calls the effect "context rot" and treats context as "a finite resource with diminishing marginal returns" ([Anthropic, context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

**Retrieval has its own failure, though, so neither side wins everywhere.** When the budget allowed, long context beat naive retrieval on average, by 7.6% for Gemini-1.5-Pro, 13.1% for GPT-4o and 3.6% for GPT-3.5-Turbo. Yet the two gave the same prediction on over 60% of queries, so the Self-Route method answered from retrieved chunks first and fell back to long context only when the model judged them insufficient. That routing cut cost by 65% for Gemini-1.5-Pro and 39% for GPT-4o while keeping comparable quality ([arXiv 2407.16833v2](https://arxiv.org/abs/2407.16833)). More retrieved passages help only up to a point: output quality rose and then fell as passages were added, because retrieved "hard negatives" distracted the model ([arXiv 2410.05983v1](https://arxiv.org/abs/2410.05983)). LaRA's title gives its verdict, "No Silver Bullet": the better choice depends on model size, context length, task type and the retrieved chunks ([arXiv 2502.09977v2](https://arxiv.org/abs/2502.09977)). For a static knowledge base under about 200,000 tokens, Anthropic's 2024 advice was to skip retrieval and put the whole base in a cached prompt ([Anthropic, Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)). That advice predates the models of 2026, and no newer statement of it was found.

**Prompt caching makes a stable prefix cheap to carry, but only while it stays stable.** As of November 2026 Anthropic charges 1.25 times the base input price for a 5-minute cache write and 0.1 times for a read on most models, falling to 0.05 times on Opus 5.5 and Sonnet 5.5, so a 5-minute write pays for itself "after one cache read" ([Claude pricing](https://platform.claude.com/docs/en/about-claude/pricing)). OpenAI's ratios for GPT-5.6 and later are similar: 1.25 times for a 30-minute write and 0.1 times for most reads ([OpenAI, prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)). Caching lowers the price of carried tokens, not their cost to attention. It also breaks on any edit, because "changing any block at or before the breakpoint produces a different hash" ([Claude, prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)).

**Anthropic's own agents therefore carry a small core and fetch the rest through tools.** Its guidance keeps "lightweight identifiers (file paths, stored queries, web links, etc.)" in context and loads the data behind them "at runtime using tools". Claude Code is the hybrid case: "CLAUDE.md files are naively dropped into context up front, while primitives like glob and grep allow it to navigate its environment and retrieve files just-in-time." The guidance also names the price, since "runtime exploration is slower than retrieving pre-computed data" ([Anthropic, context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Anthropic's memory post of 6 November 2026 keeps the same shape: only a small top layer is injected, because "an incorrect note can be carried into every session", and Claude Code loads just the first 200 lines or 25 KB of its `MEMORY.md` index ([Anthropic, components of agent memory](https://www.anthropic.com/engineering/components-of-agent-memory)). Tool definitions follow the rule too. With deferred tools and a search tool, Anthropic measured 85% fewer tokens and MCP-eval accuracy rising from 49% to 74% on Opus 4, a vendor result on its own evaluation, and it advises keeping three to five tools always loaded ([Anthropic, advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)).

**A four-part rule follows from this evidence, and it is our synthesis rather than any source's.** Carry a body of text only when all four conditions hold:
1. it stays unchanged for the cache's lifetime;
2. it is small, which for hard lookups means well under the 32K tokens where RULER and NoLiMa show losses;
3. most requests need much of it, as in comparisons across documents, where long context beat retrieval;
4. it is reused often enough to repay the cache write.

Retrieve everything else, keeping a pointer in context instead of the payload. When the line is unclear, route as Self-Route does: retrieve first and escalate to long context only when the retrieved chunks fall short.

**Our harness plan already applies this rule in three places, so the book can teach it from our own design.** Layer 1 caps tool output at 64 KiB and spills the full text to a file the agent "can re-read by path" ([harness guide §3](../../guides/agent-harness.md#3-context-policy-should-run-five-removable-layers-cheapest-first-and-keep-every-compaction-visible-and-reversible); [HD3](../../plans/build-harness.md#hd3-layers-1-2-3-and-5-on-by-default-and-a-budget-capped-at-200k-tokens-provisional)). The tool registry can mark a tool `"deferred"`, and MCP tools default to it ([harness plan §3.3](../../plans/build-harness.md#33-context-policy-and-tool-registry-apis)). Skills appear in the system prompt as a name, a description and a path, with the body loaded through `read` ([N23](../../todos/ready/N23-skills-context-files.md)). Each is a pointer carried in place of a payload, which is the habit Chapter T36 should open with.

## Start with keyword search, and add vectors only after a measured miss

**BM25 remains the baseline that most dense retrievers fail to beat outside their training domain.** BEIR ran ten systems over 18 zero-shot datasets and found "BM25 is a robust baseline". Measured by nDCG@10 relative to BM25, DPR averaged −47.7% and TAS-B −2.8%, while BM25 followed by a cross-encoder reranker gained 11% and won on 16 of the 18 datasets ([BEIR, arXiv 2104.08663v4](https://arxiv.org/abs/2104.08663)). Dense retrieval wins where it was trained. DPR's top-20 accuracy on Natural Questions was 78.4% against BM25's 59.1%, yet on SQuAD, whose questions share words with their passages, BM25 won with 68.8% against 63.2% ([DPR, arXiv 2004.04906v3](https://arxiv.org/abs/2004.04906)). No embedding model wins everywhere either: MTEB found that "no particular text embedding method dominates across all tasks" ([arXiv 2210.07316v3](https://arxiv.org/abs/2210.07316)).

**Keyword and vector search fail on different queries, so the second retriever should be fused with the first rather than replace it.** Weller et al. proved that one embedding vector can return only a limited number of distinct top-k sets, bounded by its dimension. On their deliberately simple LIMIT task, embedding models stayed under 20% recall@100 while BM25 came "close to perfect". Their second version adds the reverse failure: with words swapped for synonyms, BM25 dropped by more than 89% against 38.9% for a Qwen3 embedder ([arXiv 2508.21038v2](https://arxiv.org/abs/2508.21038)). Reciprocal rank fusion (RRF) merges the two lists by rank alone, scoring each document as the sum of 1/(k + rank) over the lists. Its authors fixed k = 60 and found the choice "not critical" ([Cormack, Clarke and Büttcher, SIGIR 2009](https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf)). In Anthropic's tests over code, fiction and papers, the failure rate of top-20 retrieval fell from 5.7% to 2.9% with contextual embeddings plus contextual BM25, and to 1.9% with a reranker on top ([Anthropic, Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)). Cloudflare AI Search turns hybrid search on by default and fuses with RRF (vendor docs, [Cloudflare, hybrid search](https://developers.cloudflare.com/ai-search/configuration/indexing/hybrid-search/)).

**Coding agents disagree on embeddings, most of the evidence on either side comes from vendors, and the one independent study finds that the harness matters more.** Claude Code's early versions indexed code with Voyage embeddings. Boris Cherny, who created it, said agentic grep "outperformed everything. By a lot", then added: "This was just vibes ... There's some internal benchmarks also" ([Latent Space podcast transcript, 2025-05-07](https://www.latent.space/p/claude-code)). Anthropic's own post gives the design reason, that glob and grep avoid "stale indexing" ([Anthropic, context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Cursor reports the opposite result on its own dataset: semantic search added to grep raised answer accuracy by 12.5% on average, and code retention rose 2.6% on repositories of 1,000 files or more ([Cursor, semantic search](https://cursor.com/blog/semsearch)). An independent 2026 paper ran 116 LongMemEval questions through four harnesses. Inline grep beat inline vector retrieval for every pairing of harness and model, but the harness moved scores more than the retriever: the same Opus 4.6 scored 93.1% in one harness and 76.7% in Claude Code ([arXiv 2605.15184v1](https://arxiv.org/abs/2605.15184)). A retriever benchmark therefore says little about our harness until we run it there.

**Retrieval should be measured as its own component, on a small labelled set, before the answer is graded.** BEIR reports nDCG@10 because it rewards graded, rank-aware relevance, while recall@k says whether the needed text reached the request at all and MRR says how high the first hit ranked ([BEIR v4](https://arxiv.org/pdf/2104.08663v4)). Anthropic's eval guidance sizes the set: "20-50 simple tasks drawn from real failures is a great start", with cases where a behaviour should occur and cases where it should not ([Anthropic, demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Agents need the check, because logged agent trajectories missed every gold file in 27–35% of samples on a 2026 repository benchmark ([Agent Retrieval Bench, arXiv 2607.24882v1](https://arxiv.org/abs/2607.24882)). A labelled set for our agents should include exact identifiers, paraphrases, queries that should return nothing and queries from a second tenant.

**Every part of this runs offline in TypeScript without an embedding API.** SQLite's FTS5 ranks with a built-in `bm25()` whose constants are fixed at k1 = 1.2 and b = 0.75 ([SQLite FTS5](https://www.sqlite.org/fts5.html)), and Cloudflare lists FTS5 among the extensions that D1 and Durable Object SQLite support ([Durable Objects SQLite API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)). In process, `minisearch` 7.2.0 (MIT, about 6.4 million weekly downloads as of November 2026) exposes BM25 parameters ([npm registry](https://registry.npmjs.org/minisearch)). On the vector side, `ai` 7.0.162 exports `MockEmbeddingModelV4` from `ai/test`, and `@langchain/core` 1.3.4 ships `SyntheticEmbeddings`, which derives a fixed vector from the text (installed typings `ai/dist/test/index.d.ts` and `@langchain/core/dist/utils/testing/embeddings.d.ts`; [SDK notes](notes/sdks-claude-openai-vercel-langchain.md)). A hashed or synthetic vector keeps a test deterministic, but it captures no meaning, so an example that uses one must call it a stand-in for semantic search.

## Retrieved text and stored memory are untrusted input, so filter before ranking and record each record's source

**OWASP lists the vector store as an attack surface of its own, and most of its fixes concern access rather than ranking.** LLM08:2025, "Vector and Embedding Weaknesses", names five risks: unauthorized access and data leakage, cross-context leaks between tenants, embedding inversion, data poisoning and changed model behaviour. Its four prevention strategies are "permission-aware vector and embedding stores" with "strict logical and access partitioning", validated and authenticated sources, tagging and classifying combined data, and "detailed immutable logs of retrieval activities" ([OWASP LLM08:2025](https://genai.owasp.org/llmrisk/llm082025-vector-and-embedding-weaknesses/)). The Top 10 for Agentic Applications, published on 9 December 2025, extends the same concern to memory. Its ASI06, "Memory & Context Poisoning", covers "summaries, embeddings, and RAG stores" and "persistent corruption of agent memory and retrievable context that propagates across sessions" ([OWASP Agentic Top 10](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/)).

**A handful of planted texts is enough to steer retrieval, and memory makes the effect last.** PoisonedRAG reached a 90% attack success rate by "injecting five malicious texts for each target question into a knowledge database with millions of texts" ([arXiv 2402.07867v3](https://arxiv.org/abs/2402.07867)). BadRAG's ten passages, 0.04% of the corpus, were retrieved for 98.2% of triggered queries ([arXiv 2406.00083v3](https://arxiv.org/abs/2406.00083)). Greshake et al. showed that "processing retrieved prompts can act as arbitrary code execution" ([arXiv 2302.12173v2](https://arxiv.org/abs/2302.12173)). Long-term memory turns one injection into a standing order. AgentPoison exceeded 80% attack success while poisoning under 0.1% of a memory or RAG store ([arXiv 2407.12784v1](https://arxiv.org/abs/2407.12784)), and MINJA, using queries alone, reached 76.8% attack success ([arXiv 2503.03704v5](https://arxiv.org/abs/2503.03704)). In 2024 Johann Rehberger planted instructions in ChatGPT's memory from an untrusted website, so that later conversations were sent to him, until OpenAI fixed the macOS app in version 1.2024.247 ([Embrace The Red, SpAIware](https://embracethered.com/blog/posts/2024/chatgpt-macos-app-persistent-data-exfiltration/)).

**Access control must run inside the retriever, before ranking, or the top-k leaks across tenants.** Cloudflare Vectorize documents that a metadata "filter is applied first, and the topK results are taken from the filtered set", and that namespace filtering also runs before the search (vendor docs, [Vectorize metadata filtering](https://developers.cloudflare.com/vectorize/reference/metadata-filtering/)). For AI Search, Cloudflare recommends one instance per tenant, so that "one tenant can never retrieve another tenant's documents" ([Cloudflare, per-tenant search](https://developers.cloudflare.com/ai-search/how-to/per-tenant-search/)). OWASP's ASI06 describes the failure: "Near-duplicate content seeded by an attacker exploits loose namespace filters, pulling another tenant's sensitive chunk into retrieval by high cosine similarity" ([OWASP Agentic Top 10](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/)). For keyword search the same rule is a `WHERE tenant_id = ?` clause in the query itself, never a filter applied to the results.

**Embeddings expose their source text, so they need the same protection and the same deletion as the documents.** Vec2text recovered 92% of 32-token inputs exactly from their embeddings, and it recovered full names from embedded clinical notes ([arXiv 2310.06816v1](https://arxiv.org/abs/2310.06816)). We found no regulator statement that embeddings in an agent's memory are personal data. The EDPB's opinion on AI models judges anonymity case by case and does not mention vector stores ([EDPB Opinion 28/2024](https://www.edpb.europa.eu/system/files/2024-12/edpb_opinion_202428_ai-models_en.pdf)). Treating embeddings as personal data is therefore our inference from the inversion results, and a cautious one.

**OWASP's memory mitigations double as a design for writing and forgetting.** ASI06 asks systems to "Scan all new memory writes and model outputs (rules + AI) for malicious or sensitive content before commit", to "Require source attribution", and to "Prevent automatic re-ingestion of an agent's own generated outputs into trusted memory" to avoid "bootstrap poisoning". It also asks for per-tenant namespaces, "snapshots/rollback and version control", and "Expire unverified memory to limit poison persistence" ([OWASP Agentic Top 10](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/)). The next section builds its write and forget rules on these six requirements.

## Long-term memory works best as sourced records in files, written through a tool, recalled through an index and forgotten by expiry

The research names the kinds of memory, and the products of 2026 agree on how to handle them. CoALA splits an agent's memory into working, episodic, semantic and procedural memory, and warns that writing procedural memory, the agent's own instructions or code, "is significantly riskier than writing to episodic or semantic memory" ([CoALA, arXiv 2309.02427v3](https://arxiv.org/abs/2309.02427)). The three subsections below take writing, recall and forgetting in turn, and each ends with the rule we draw for our agents.

### Write small, sourced records through a tool, and consolidate them in the background

**Every major memory product now writes in two ways: during the task through a tool, and afterwards in a background pass.** LangChain's LangMem guide states the trade-off. Writing "in the hot path" lets the agent choose what to store, but "it adds perceptible latency to user interactions", while a background pass after the conversation "is perfect for ensuring higher recall of extracted information" ([LangMem concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)). Anthropic's memory tool is the hot-path design: Claude issues `view`, `create`, `str_replace`, `insert`, `delete` and `rename` commands on paths under `/memories`, and "Your application runs each request against storage you control" ([Claude, memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)). GitHub Copilot writes through a `store_memory` tool whose records hold a subject, a fact, citations such as `src/client/sdk/constants.ts:12` and a reason ([GitHub, agentic memory](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)). Letta's "dreaming" runs background subagents on a step count or at compaction, and Cloudflare's Agent Memory, in private beta as of November 2026, extracts memories at compaction and also gives the model `remember`, `recall`, `forget` and `list` tools ([Letta, memory](https://docs.letta.com/agent-sdk/memory/index.md); [Letta, memory and dreaming](https://docs.letta.com/configuration/memory/index.md); [Cloudflare, Agent Memory](https://blog.cloudflare.com/introducing-agent-memory/)).

**The records themselves are small, typed and sourced, and the writer decides on each one whether to add, change or drop it.** Mem0's update step retrieves similar memories for each new fact and picks one of four operations: ADD, UPDATE, DELETE for "memories contradicted by new information", or NOOP ([Mem0, arXiv 2504.19413v1](https://arxiv.org/abs/2504.19413)). Claude Code's auto memory types each note as `user`, `feedback`, `project` or `reference`, records a `modified` timestamp on each write, and "skips anything it can derive from the codebase" ([Claude Code, memory](https://code.claude.com/docs/en/memory)). Cloudflare's ingestion classifies items as facts, events, instructions or tasks and keys each fact by a "normalized topic key" ([Cloudflare, Agent Memory](https://blog.cloudflare.com/introducing-agent-memory/)).

**Our rule for writing:** the agent writes one record per durable fact through an explicit memory tool, and each record carries a subject, the fact, a source (a `file:line`, a URL or the user's own words), a type, a created date and a last-validated date. A background pass at compaction or session end merges duplicates and retires contradicted records, and its edits appear in the session log like any other write. Records derived from untrusted tool output are marked low-trust. Nothing the agent concluded on its own enters memory as trusted, which follows ASI06's ban on re-ingesting the agent's own outputs. No untrusted input may write procedural memory, which follows CoALA's warning.

### Recall a short index every session, search for the rest, and check each record before acting on it

**The common recall design loads a short index into every session and leaves the rest to search.** Claude Code loads "The first 200 lines of `MEMORY.md`, or the first 25KB, whichever comes first" and reads topic files "on demand" ([Claude Code, memory](https://code.claude.com/docs/en/memory)). Letta's file-based memory "does not include a semantic or vector index by default", so its agents find memories "with normal file-search and read tools" ([Letta, MemFS](https://docs.letta.com/concepts/memfs/index.md)). Anthropic's memory tool injects a system prompt that begins "IMPORTANT: ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE" ([Claude, memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)). On a corpus of about 420 million tokens, Anthropic found that search plus a maintained wiki scored 61% against 53% for search alone and saved about 20,000 tokens a question, but gave "no clear gain" where one text search of one document sufficed (vendor eval, [Anthropic, components of agent memory](https://www.anthropic.com/engineering/components-of-agent-memory)). The older research ranks memories by a score instead: Generative Agents summed recency, importance and relevance with every weight set to 1 and decayed recency by 0.995 per game hour ([arXiv 2304.03442v2](https://arxiv.org/abs/2304.03442)).

**A recalled memory is a claim about the past, so Copilot checks it against the present before acting on it.** Before applying a memory, Copilot's agent is "prompted to verify its accuracy and relevance by checking the cited code locations", and it stores a corrected version when the code disagrees. GitHub reports a pull-request merge rate of 90% with memory against 83% without, a vendor measurement ([GitHub, agentic memory](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)). GitHub's docs still warn that "a stored fact should not be relied on as a rule that will always be followed" ([GitHub Docs, Copilot Memory](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)). Unchecked memory goes stale in measurable ways. On LongMemEval, ChatGPT and Coze lost 37% and 64% of their offline-reading accuracy, and the authors found that "ChatGPT tended to overwrite crucial information as the chat continues" ([LongMemEval, arXiv 2410.10813v2](https://arxiv.org/abs/2410.10813)).

**Our rule for recall:** each session starts with the memory index, capped at 200 lines or 25 KB, and the agent searches topic files with the same keyword tools it uses for code. Before a recalled record changes what the agent does, the agent re-reads the record's source; a record whose source has changed or vanished is rewritten or deleted, not obeyed.

### Forget by an expiry that only a successful check renews, and delete from every copy

**Shipped systems forget in five ways, and the strongest combines expiry with validation.** The five are:
1. expiry after a set time, as in AWS AgentCore's event expiry of up to 3,650 days ([AgentCore CreateMemory](https://docs.aws.amazon.com/bedrock-agentcore-control/latest/APIReference/API_CreateMemory.html));
2. decay that lowers a record's rank without deleting it, as in MemoryBank's forgetting curve R = e^(−t/S) and Mem0's score multiplier of 0.3 to 1.5 ([arXiv 2305.10250v3](https://arxiv.org/abs/2305.10250); [Mem0, memory decay](https://docs.mem0.ai/platform/features/memory-decay));
3. supersession, which keeps the old record but marks it invalid, as Zep's bi-temporal graph does ([Zep, arXiv 2501.13956v1](https://arxiv.org/abs/2501.13956));
4. explicit deletion, as in the memory tool's `delete` and its advice to "Periodically delete memory files that haven't been accessed in a long time" ([Claude, memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool));
5. validation at read time, as in Copilot's citation check.

Copilot joins the first and the fifth. Its memories expire after 90 days by default, an owner can set repository facts to anything from 7 to 180 days, and the period resets only when Copilot upvotes a memory it has validated. "Simply retrieving a memory does not reset this period" ([GitHub Docs, Copilot Memory](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)). The launch announcement of 15 January 2026 had said 28 days, so the figure has changed once already ([GitHub changelog](https://github.blog/changelog/2026-01-15-agentic-memory-for-github-copilot-is-in-public-preview/)).

**Deleting a memory record does not delete what was copied from it, and the vendors' own docs say so.** Zep warns that deleting an episode "does not regenerate the names or summaries of nodes shared with other episodes", so "This episode information may still exist within these nodes" ([Zep, deleting data](https://help.getzep.com/v4/deleting-data-from-the-graph.md)). Claude Code deletes old transcripts after `cleanupPeriodDays`, but its memory files are excluded from that sweep and "stay until you or Claude edits or deletes them" ([Claude Code, memory](https://code.claude.com/docs/en/memory)). Our own harness keeps session logs with "No automatic deletion by default" ([HD11](../../plans/build-harness.md#hd11-keep-transcripts-until-the-owner-sets-a-retention-period-and-keep-the-entry-base-stable-accepted)), so a fact deleted from memory would still sit in the log entry that recorded its write. The GDPR's Article 17 obliges a controller to erase personal data "without undue delay" on valid request, which in our reading reaches every such copy (text read from a reproduction because EUR-Lex refused the fetch, [gdpr-info.eu, secondary](https://gdpr-info.eu/art-17-gdpr/)).

**Our rule for forgetting:** project facts expire 90 days after their last successful validation, task records expire when the session ends, and a user's stated preferences last until the user changes them. A delete removes the record, its index line and any embedding of it in one step, and it also marks the session-log entries that carry the fact, so that HD11's archive or purge, or a targeted purge, can reach them.

## A file is enough for one agent and one user, and a service earns its price at many users or temporal questions

**For the owner's coding agent, a directory of memory files meets every rule above.** Anthropic's memory tool, Claude Code's auto memory and Letta's MemFS all store memory as files, and Letta adds that "Every memory edit is committed to the MemFS git repository" ([Letta, MemFS](https://docs.letta.com/concepts/memfs/index.md)). Git history gives ASI06's rollback for free, a diff shows every write, and keyword search over a few hundred records needs no index. The main report's rule, "Buy a memory service only when you need cross-user personalization" ([main report](../agent-sdks-and-harness-design.md#planning-should-start-as-react-and-earn-every-extra-agent)), holds, and the evidence adds three signals that a service is worth its price:
1. many end users each need an isolated profile;
2. recall must span thousands of records, where keyword search over files starts to miss;
3. users ask temporal questions such as "what did I prefer before March?", which Zep's bi-temporal edges and Cloudflare's version chains answer.

The multi-user agent platform shows the first signal from its first tenant.

**The published benchmarks cannot choose a vendor, because the vendors dispute each other's runs.** LoCoMo's conversations average about 9,000 tokens, small enough to fit in one request ([arXiv 2402.17753v1](https://arxiv.org/abs/2402.17753)), and in Mem0's own table full context scored 72.90% against 68.44% for Mem0's graph variant and 66.88% for Mem0 ([arXiv 2504.19413v1](https://arxiv.org/abs/2504.19413)). Zep first claimed 84%; Mem0's chief technology officer answered that the correct figure is 58.44% ([getzep/zep-papers#5](https://github.com/getzep/zep-papers/issues/5)), and Zep then published a corrected score of 75.14% ([Zep blog](https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)). LongMemEval is the better test for our rules, because it scores knowledge updates and abstention, the abilities that forgetting must protect ([arXiv 2410.10813v2](https://arxiv.org/abs/2410.10813)).

## Chapter T36 should teach four rules, one per planned section, and add retrieval measurement

**The four sections the book plan gives Chapter T36 fit the evidence, and each can be taught as one rule with one failure beside it.** The plan lists just-in-time retrieval, vector and keyword search with their failure modes, long-term memory across runs, and when to buy a memory service ([book plan §4.2, row 12](../../plans/build-book.md#42-part-ii-in-depth-for-experienced-builders)). For each section, the chapter should teach the following:
1. **Just-in-time retrieval:** the four-part carry rule, taught through our harness's three pointers (a spilled file path, a deferred tool and a skill's path). The failure to show beside it is a long input that degrades, with NoLiMa's GPT-4o falling from 99.3% to 69.7% at 32K as the number to remember.
2. **Keyword and vector search:** BM25 as the first retriever, LIMIT's two opposite failures as the reason to fuse, RRF as the fusion, and access control before ranking. This section should also teach measurement (recall@k on 20 to 50 labelled queries, including queries that should return nothing), which the plan's rationale promises but no section names ([book plan §4.3](../../plans/build-book.md#43-four-topics-need-research-before-they-are-written)). The failure to show is a planted document ranked first.
3. **Long-term memory:** the record schema and the three rules for writing, recall and forgetting, with Copilot's citation check as the worked case. The failure to show is a stale record obeyed without a check.
4. **Buying a service:** the file-based default, the three signals that a service is worth its price, and the benchmark dispute as the reason to measure on our own tasks.

**The three analogies the owner approved hold up against the evidence, and each break note names a real failure.** The reference librarian's break, that "a wrong ranking looks just as confident", is what PoisonedRAG and LIMIT measure. The card file's break, that "a model may write a wrong card and later trust it", is MINJA's attack and the reason for Copilot's check. The shredding schedule's break, that deleting a fact "does not delete it from logs or caches unless the harness does", matches Zep's own warning and our HD11 default ([T36](../../todos/ongoing/T36-chapter-retrieval-and-long-term-memory.md)). The chapter needs no new analogy.

**The chapter's exercise needs expiry that no SDK provides, so the example must build it and say so.** The exercise asks the reader to "Store a fact in one run, recall it in the next, then expire it and show it is gone" ([T36](../../todos/ongoing/T36-chapter-retrieval-and-long-term-memory.md)). None of the eight SDKs expires a memory in the process, so the example should store an expiry time in the record, read time from an injected clock, and filter expired records in the recall tool. A last step should then show that the expired fact still sits in the session log, which teaches the shredding schedule's break by running it.

**Two figures in this report will age fastest, and every vendor score needs a label.** Copilot's expiry moved from 28 days in January 2026 to 90 days by November 2026, and Cloudflare's Agent Memory was still in private beta in November 2026. Every vendor score in the chapter should carry the word "vendor", because the Mem0 and Zep figures for the same system differ by 17 points depending on who ran the test.

## Three new examples would give the chapter its listings, led by T41's keyword search

**T41 should build keyword search with BM25 written inside the example, because that needs no new dependency and makes the strongest baseline.** T41 asks for "keyword search or a vector index with deterministic embeddings" in `verify/vercel-ai-sdk/` and forbids a new dependency without the owner's approval ([T41](../../todos/done/T41-example-retrieval.md)). BM25 fits in a few dozen lines of TypeScript and is deterministic, and the `minisearch` package would be the dependency to propose if hand-written scoring proved too long. The example should search a fixture of about ten short documents in `fixtures/` and assert four behaviours with `check()`:
1. an exact identifier, such as an error code, ranks its document first;
2. a paraphrase with no shared words misses, which is keyword search's failure;
3. a tenant filter inside the query keeps another tenant's near-duplicate out of the top results;
4. a planted document ranked first misleads the scripted model, the failure T41 already asks for.

A hybrid variant, which fuses the BM25 list with cosine scores from `MockEmbeddingModelV4` using RRF at k = 60, is optional. If T41 writes it, the example must label the mock vectors as a stand-in for semantic search.

**A second example should run the chapter's exercise on LangChain's store, which T36 already cites.** `verify/langchain/examples/09-long-term-store.ts` writes and reads a fact inside one run ([09-long-term-store.ts](../../../verify/langchain/examples/09-long-term-store.ts)). **A third example should prove on Cloudflare that memory survives eviction and stays inside one agent.** A new `verify/cloudflare-agents/examples/10-context-memory.ts` would declare a writable memory block and an FTS5 search block, have the mock model call `set_context` and `search_context`, evict the Durable Object and assert that both survive, then show that a second agent name sees nothing. **Four smaller examples would close reference gaps but are not needed for the chapter.** The SDK notes propose a Claude example that shows `settingSources` gating `CLAUDE.md` while auto memory still loads, an ADK example of `InMemoryMemoryService` with its whole-word miss, a Copilot example of the `storeMemory` callback (Linux only) and a Pi example of a memory extension. Each would turn a finding of this report into a checked behaviour, and none blocks T36.

## Retrieval and memory are one discipline: carry pointers, search, and check before trusting

The evidence of November 2026 turns our plans' two phrases into rules an agent can follow. An agent carries a small, stable core and keeps pointers to everything else, because long inputs degrade and a cached prefix is cheap only while it stays unchanged. It searches with keywords first and adds vectors only after a measured miss, because each retriever fails where the other succeeds. It treats retrieved text and its own memories as untrusted, so access control runs before ranking and every record carries its source. Its long-term memory is a set of small records in files, written through a tool, loaded through a short index and checked against its source before it changes what the agent does. A record expires unless a check renews it, and its deletion reaches every copy, including the session log. Our eight SDKs supply the retrieval and some of the storage, but none supplies that expiry, so it belongs in our harness. The owner approved all twelve proposed changes on 2026-11-19, so T41's form and the harness memory extension in change 5, on which the book's listings and our own agents both depend, are now in the plans.
