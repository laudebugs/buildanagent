## Write: what gets stored, when, and by whom

### Takeaway
There are two write policies, and every serious system now ships both. In the hot path, the agent calls a tool such as `memory`, `store_memory` or `remember` during the task. That is cheap to build and keeps memory explicit, but it adds latency and gives the model one more decision to make. In the background, a separate pass extracts memories from a transcript after the session, on compaction, or every N steps. That raises recall and keeps the main loop clean, but you pay for extra model calls and get writes nobody watched. Research gives the vocabulary: CoALA's working, episodic, semantic and procedural memory; Generative Agents' observation stream plus reflection; MemGPT's self-editing core memory. CoALA warns that writing procedural memory (the agent's own instructions or code) is "significantly riskier" than writing facts or episodes. Product designs converge on four record types: facts, events/episodes, instructions/procedures and short-lived tasks. They also converge on one rule: store small, atomic, sourced items, not transcripts.

### Cited Findings

**Research designs**
- Generative Agents (Park et al.; v1 2023-04-07, v2 2023-08-06; UIST '23). The "memory stream" stores "a complete record of the agent's experiences using natural language". Reflections are a second memory type: "higher-level, more abstract thoughts generated by the agent". They are generated "when the sum of the importance scores for the latest events perceived by the agents exceeds a threshold (150 in our implementation)", which came to roughly two or three times a day. Each reflection stores "pointers to the memory objects that were cited". Importance is set at write time by asking the LLM to rate poignancy "On the scale of 1 to 10". — [arXiv 2304.03442v2](https://arxiv.org/abs/2304.03442)
- MemGPT (Packer et al.; v1 2023-10-12, v2 2024-02-12). This is "virtual context management" modelled on OS memory hierarchies. Main context holds read-only system instructions, a "fixed-size read/write block of unstructured text" called working context ("writeable only via MemGPT function calls") and a FIFO message queue. External context holds recall storage (the message database) and archival storage ("a read/write database storing arbitrary length text objects"). At a "warning token count" ("e.g. 70% of the context window") the queue manager inserts a "memory pressure" warning so the LLM can save important items. At the flush count ("e.g. 100%") it evicts messages (e.g. 50% of the window) into a recursive summary. Evicted messages "are stored indefinitely in recall storage". — [arXiv 2310.08560v2](https://arxiv.org/abs/2310.08560)
- CoALA, "Cognitive Architectures for Language Agents" (Sumers, Yao et al.; v1 2023-09-05, v3 2024-03-15, TMLR). Working memory "persists across LLM calls". Episodic memory "stores experience from earlier decision cycles". Semantic memory "stores an agent's knowledge about the world and itself". Procedural memory is the LLM weights plus agent code. Writing procedural memory "is significantly riskier than writing to episodic or semantic memory, as it can easily introduce bugs or allow an agent to subvert its designers' intentions". The paper also says "modifying and deleting (a case of 'unlearning') are understudied in recent language agents". — [arXiv 2309.02427v3](https://arxiv.org/abs/2309.02427)
- Reflexion (Shinn et al.; v1 2023-03-20, v4 2023-10-10). Agents "verbally reflect on task feedback signals, then maintain their own reflective text in an episodic memory buffer". The paper reports 91% pass@1 on HumanEval against GPT-4's 80%. — [arXiv 2303.11366v4](https://arxiv.org/abs/2303.11366)
- A-MEM (Xu et al.; v1 2025-02-17, v11 2025-10-08, NeurIPS 2025). Writes follow the Zettelkasten method: each new memory becomes a note with "contextual descriptions, keywords, and tags", gets linked to related notes, and can trigger "memory evolution" that updates the attributes of existing notes. — [arXiv 2502.12110v11](https://arxiv.org/abs/2502.12110)
- Mem0 (Chhikara et al.; v1 2025-04-28, the only version). Extraction is followed by an update phase. For each candidate fact the system retrieves the top-s similar memories, and an LLM tool call picks one of four operations: "ADD for creation of new memories when no semantically equivalent memory exists; UPDATE for augmentation of existing memories with complementary information; DELETE for removal of memories contradicted by new information; and NOOP". A graph variant (Mem0g) adds entity-relation memory. — [arXiv 2504.19413v1](https://arxiv.org/abs/2504.19413)
- Sleep-time Compute (Lin et al., Letta/UC Berkeley; v1 2025-04-17, the only version). Models "think" offline about context before queries arrive. Test-time compute needed for the same accuracy falls "by ~ 5x" on Stateful GSM-Symbolic and Stateful AIME. Scaling sleep-time compute raises accuracy "by up to 13%" and "18%" respectively, and amortizing across related queries cuts "average cost per query by 2.5x". Efficacy correlates with how predictable the user's query is. — [arXiv 2504.13171v1](https://arxiv.org/abs/2504.13171)
- Survey, "Memory in the Age of AI Agents" (Zhang et al.; v1 2025-12-15, v2 2026-01-13). It classifies memory by form (token-level, parametric, latent), function (factual, experiential, working) and dynamics (formed, evolved, retrieved), and argues that "long/short-term memory have proven insufficient" as a taxonomy. Only the abstract was read. — [arXiv 2512.13564v2](https://arxiv.org/abs/2512.13564). An earlier survey is [arXiv 2404.13501v1](https://arxiv.org/abs/2404.13501) (2024-04-21).

**Hot path versus background (product docs)**
- LangMem conceptual guide (LangChain; undated, read 2026-11-19). It names the two policies. Hot path ("Conscious Formation"): "This approach is easy to implement and lets the agent itself choose how to store and update its memory. However, it adds perceptible latency to user interactions, and it adds one more obstacle to the agent's ability to satisfy the user's needs." Background ("Subconscious Formation"): an LLM reflects "on a conversation after it occurs (or after it has been inactive for some period)… This approach is perfect for ensuring higher recall of extracted information." Memory types: semantic (stored as a profile or a collection), episodic ("Few-shot examples; Summaries of past conversations") and procedural ("Prompt rules"). On collections: "If the system over-extracts, this could lead to reduced precision… If it under-extracts, this could lead to low recall." — [LangMem concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- Anthropic memory tool, `memory_20250818` (platform docs, undated, read 2026-11-19). It is a hot-path design and runs client-side: "Claude only requests memory operations. The tool entry `{"type": "memory_20250818", "name": "memory"}` "is the entire configuration", and the memory tool itself "doesn't require a beta header". The API auto-injects this system prompt: "IMPORTANT: ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE. … ASSUME INTERRUPTION: Your context window might be reset at any moment, so you risk losing any progress that is not recorded in your memory directory." Optional reinforcement text: "You can rename or delete files that are no longer relevant. Do not create new files unless necessary." The docs say the tool is "available on every model and eligible for zero data retention and HIPAA readiness". The TypeScript helper `betaMemoryTool` ships in `@anthropic-ai/sdk/helpers/beta/memory`, and Python and TypeScript both ship `BetaLocalFilesystemMemoryTool`. — [Claude Platform, Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- The same page describes a multi-session pattern. An initializer session writes "a progress log … a feature checklist … and a reference to any startup or initialization script", and each session ends by updating the progress log. "Mark a feature complete only after end-to-end verification confirms it works". — [Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Claude Code (code.claude.com docs, undated, read 2026-11-19) has two memory systems. CLAUDE.md is written by you; auto memory is written by Claude. Auto memory saves four types, recorded in frontmatter: `user`, `feedback`, `project` and `reference`. "Claude skips anything it can derive from the codebase, such as architecture, file paths, or debugging fixes." Storage is `~/.claude/projects/<project>/memory/`, holding a `MEMORY.md` index ("one line per memory") plus one topic file per memory. It is machine-local and shared across the worktrees of one repo. A `modified` ISO 8601 timestamp is recorded on each write. CLAUDE.md resolves through a managed-policy, user, project and local (`CLAUDE.local.md`) hierarchy. Files are concatenated, not overridden, ordered from the filesystem root down to the working directory. `@path` imports recurse to "a maximum depth of four hops". Target size: "under 200 lines per CLAUDE.md file". — [Claude Code, How Claude remembers your project](https://code.claude.com/docs/en/memory)
- GitHub Copilot Memory (engineering blog, 2026-01-15). It writes in the hot path: "We implemented memory creation as a tool that agents can invoke when they discover something that's likely to have actionable implications for future tasks." The example record has `subject`, `fact`, `citations: ["src/client/sdk/constants.ts:12", …]` and `reason`. The tool is named "store_memory". — [GitHub Blog, Building an agentic memory system for GitHub Copilot](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)
- GitHub docs (read 2026-11-19). Copilot sorts memories into "repository-level facts" (shared with collaborators, citing code) and "user-level preferences" ("clearly stated, non-sensitive preferences", citing "direct quotes of what you said"). "If your intent is ambiguous, Copilot asks you to clarify the scope rather than guessing." — [GitHub Docs, About Copilot Memory](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)
- Letta (docs, read 2026-11-19; Letta is the company behind MemGPT). Memory now lives in "MemFS", "a git repository that belongs to the agent". Files at the memory root (older agents: `system/`) are in the system prompt every turn. Other directories are reached through `MEMORY.md` indexes. "Every memory edit is committed to the MemFS git repository." Background writing is called "dreaming": "background subagents to review recent conversations, consolidate lessons, and update memory without interrupting active work". It is configured with `trigger: "step-count" | "compaction-event" | "off"` and `behavior: "reminder" | "auto-launch"`; the example uses `stepCount: 25`. An optional "Agent reviews before applying" mode runs a second background review that "does not ask you for approval". — [Letta, Memory](https://docs.letta.com/agent-sdk/memory/index.md); [Letta, MemFS](https://docs.letta.com/concepts/memfs/index.md); [Letta, Memory & dreaming](https://docs.letta.com/configuration/memory/index.md)
- Cloudflare Agent Memory (blog 2026-04-17, private beta) offers both paths. "Bulk ingestion at compaction" extracts "facts, events, instructions, and tasks", and model tools `remember`, `recall`, `forget` and `list` cover the rest. "The primary agent should never burn context on storage strategy." Ingestion verifies items ("passed, corrected, or dropped"), classifies them, keys facts and instructions by "normalized topic key", and dedupes with `INSERT OR IGNORE`. "Raw conversation messages are always stored verbatim alongside extracted memories." Cloudflare argues that "Tighter ingestion and retrieval pipelines are superior to giving agents raw filesystem access." That is a vendor position opposite to Anthropic's and Letta's file-based designs. — [Cloudflare Blog, Agents that remember](https://blog.cloudflare.com/introducing-agent-memory/); [Cloudflare docs, How Agent Memory works](https://developers.cloudflare.com/agent-memory/concepts/how-agent-memory-works/) (dateModified 2026-06-02)
- AWS Bedrock AgentCore Memory (docs, read 2026-11-19). It writes in the background through "strategies" run on raw events: built-in semantic, user preference, summary and episodic. Built-in steps are "Extraction", "Consolidation" ("Determines whether to write useful information to a new record or an existing record") and "Reflection" ("Insights are generated across episodes"). "If no strategies are specified, long-term memory records will not be extracted." The episodic strategy "automatically detects episode completion" and records "situation, intent, assessment, justification, and episode-level reflection". — [AgentCore, Memory](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory.html); [Memory strategies](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-strategies.html); [Episodic strategy](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/episodic-memory-strategy.md)
- Google Memory Bank (now part of "Gemini Enterprise Agent Platform"; docs last updated 2026-11-19). Generation has two steps. Extraction keeps only information matching configured "memory topics". By default these are managed topics such as `USER_PERSONAL_INFO` and `USER_PREFERENCES`. Consolidation "Identifies if existing memories with the same scope should be deleted or updated". "For production agents, you generally want to run memory generation in the background" (`wait_for_completion: False`). The default generation model is `gemini-3.5-flash`. — [Generate memories](https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/memory-bank/generate-memories); [Set up Memory Bank](https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/memory-bank/setup)

## Recall: getting the right memory back into context

### Takeaway
The classic recall score comes from Generative Agents: recency plus importance plus relevance, each min-max normalised and weighted equally. Products have moved toward hybrid retrieval: keyword plus vector plus exact topic key, fused with RRF and broken on ties by recency. Small, always-loaded indexes are the other common pattern (Claude Code's 200-line/25KB `MEMORY.md`, Letta's root files, Copilot's "most recent memories"), with detail read on demand. GitHub adds the most transferable idea: treat a stored memory as a claim with citations, and check it against the current state before acting on it. Retrieval-time verification is cheap because "Information retrieval is an asymmetrical problem: It's hard to solve, but easy to verify."

### Cited Findings
- Generative Agents recall: recency is "an exponential decay function over the number of sandbox game hours since the memory was last retrieved. Our decay factor is 0.995"; importance is the LLM's 1–10 rating; relevance is cosine similarity of embeddings. "score = α_recency · recency + α_importance · importance + α_relevance · relevance. In our implementation, all αs are set to 1." "The top-ranked memories that fit within the language model's context window are included in the prompt." — [arXiv 2304.03442v2](https://arxiv.org/abs/2304.03442)
- MemGPT recall: the LLM pages data back with function calls such as `archival_storage.search(...)`. It can chain calls with `request_heartbeat=true`, which "is what allows MemGPT to perform multi-step retrieval". — [arXiv 2310.08560v2](https://arxiv.org/abs/2310.08560)
- LongMemEval's design recommendations, from the benchmark paper: "session decomposition for value granularity, fact-augmented key expansion for indexing, and time-aware query expansion". Key expansion gave "9.4% higher recall@k" and "5.4% higher accuracy". Time-aware query expansion improved temporal reasoning "by 6.8%∼11.3% when a strong LLM is employed". — [arXiv 2410.10813v2](https://arxiv.org/abs/2410.10813)
- LangMem: "memory relevance is more than just semantic similarity. Recall should combine similarity with 'importance' of the memory, as well as the memory's 'strength', which is a function of how recently/frequently it was used." — [LangMem concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- Claude Code: "The first 200 lines of `MEMORY.md`, or the first 25KB, whichever comes first, are loaded at the start of every conversation." Topic files are not loaded at startup; Claude "reads them on demand". If `MEMORY.md` is over a limit, "the write still succeeds, but Claude Code returns an error telling Claude to rewrite the index, because everything past the limit is dropped on the next load". CLAUDE.md files load whole up to 4 MiB. Auto memory is not loaded into subagents, except forks. — [Claude Code memory](https://code.claude.com/docs/en/memory)
- Anthropic memory tool: Claude "automatically checks its memory directory before starting a task". The docs recommend capping `view` output and letting Claude page with `view_range`. This is a just-in-time pattern: "Rather than loading all relevant information up front, an agent records what it learns in memory files and reads them back on demand." — [Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Copilot recall and verification (2026-01-15): "When an agent starts a new session, we retrieve the most recent memories for the target repository and include them in the prompt." "Before applying any memory, the agent is prompted to verify its accuracy and relevance by checking the cited code locations. If the code contradicts the memory, or if the citations are invalid … the agent is encouraged to store a corrected version". Verification "boils down to a small number of simple read operations, adding no significant latency". — [GitHub Blog](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/). The current docs add caveats: "Because this is a judgment Copilot makes, rather than a guarantee enforced by the system, a stored fact should not be relied on as a rule that will always be followed." Retrieval now favours memories with more upvotes: "Upvoted memories are more likely to be sent." — [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)
- Copilot measured impact (vendor, 2026-01-15): coding agent PR merge rate 90% with memory against 83% without ("7% increase"); code review positive feedback 77% against 75%; "p-value <0.00001". In offline tests seeded with noisy memories from abandoned branches, code review precision rose 3% and recall 4%. — [GitHub Blog](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)
- Cloudflare recall (vendor, 2026-04-17): five channels (fact-key match, full text, HyDE vectors, direct vectors, raw messages) are merged with Reciprocal Rank Fusion. "Fact-key matches get the highest weight". "Ties are broken by recency". `recall()` returns a synthesized answer, and "If no memories match the query, `recall()` returns an empty answer rather than hallucinating a response." — [Cloudflare Blog](https://blog.cloudflare.com/introducing-agent-memory/); [How Agent Memory works](https://developers.cloudflare.com/agent-memory/concepts/how-agent-memory-works/)
- Letta MemFS: "MemFS does not include a semantic or vector index by default. Agents find memory in its Markdown files with normal file-search and read tools." Semantic search is an optional mod (`@letta-ai/memfs-search`). — [Letta MemFS](https://docs.letta.com/concepts/memfs/index.md)
- Anthropic context editing (beta header `context-management-2025-06-27`). `clear_tool_uses_20250919` clears old tool results. Defaults: `trigger` 100,000 input tokens, `keep` 3 tool uses; plus `clear_at_least`, `exclude_tools` and `clear_tool_inputs`. With the memory tool, "Claude receives an automatic warning to preserve important information" before clearing (compare MemGPT's memory-pressure warning). Clearing invalidates cached prompt prefixes. — [Claude Platform, Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)
- Anthropic's published numbers (vendor, 2025-09-29). On "an internal evaluation set for agentic search", "combining the memory tool with context editing improved performance by 39% over baseline. Context editing alone delivered a 29% improvement. In a 100-turn web search evaluation, context editing enabled agents to complete workflows that would otherwise fail due to context exhaustion—while reducing token consumption by 84%." — [Claude, Managing context on the Claude Developer Platform](https://claude.com/blog/context-management) (anthropic.com/news/context-management redirects there)

## Forget: decay, expiry, supersession and deletion

### Takeaway
Shipped systems use six forgetting mechanisms, often in combination:
1. TTL or expiry: AgentCore events (3 or 7 to 3650 days; the API page gives both minimums), Memory Bank revisions (365-day default; memories themselves default to no TTL), Copilot (90-day default as of November 2026, down-voted memories retired).
2. Decay as a ranking bias, not deletion: Generative Agents' 0.995 per game-hour, MemoryBank's Ebbinghaus curve, Mem0's 0.3×–1.5× multiplier.
3. Supersede or invalidate instead of delete, keeping history: Zep's bi-temporal edges, Cloudflare's version chain, Mem0's Dream "Supersede", Supermemory's `isLatest`.
4. LLM-chosen DELETE on contradiction (Mem0's paper).
5. Explicit delete tools and user controls (Anthropic `delete`, Cloudflare `forget`, Copilot settings pages).
6. Validation at read time against ground truth (Copilot's citations).

Expiry that resets only on validated use, not on mere retrieval, is the sharpest design: Copilot says "Simply retrieving a memory does not reset this period." Supersession keeps the past, which helps temporal questions and audit but conflicts with erasure duties (see Attacks and privacy).

### Cited Findings
- MemoryBank (Zhong et al.; v1 2023-05-17, v3 2023-05-21). Forgetting follows the Ebbinghaus curve "R = e^(−t/S)". S "is initialize[d] … with 1 upon its first mention". When a memory is recalled, "We increase S by 1 and reset t to 0, hence forget it with a lower probability." The authors call it "an exploratory and highly simplified memory updating model". — [arXiv 2305.10250v3](https://arxiv.org/abs/2305.10250)
- Zep/Graphiti (Rasmussen et al.; v1 2025-01-20, the only version). Bi-temporal model: "timeline T represents the chronological ordering of events, and timeline T′ represents the transactional order of Zep's data ingestion". Four timestamps per edge: t′created, t′expired, t_valid, t_invalid. On contradiction "it invalidates the affected edges by setting their t_invalid to the t_valid of the invalidating edge… Graphiti consistently prioritizes new information". The result maintains "both current relationship states and historical records". — [arXiv 2501.13956v1](https://arxiv.org/abs/2501.13956). Current docs expose `valid_at`, `invalid_at` and `expired_at`. Their example: a user who loved Adidas then states a preference for Puma, so "Zep attempts to invalidate the fact that Kendra loves Adidas shoes". — [Zep v4, Facts](https://help.getzep.com/v4/facts.md)
- Zep deletion caveat (docs, read 2026-11-19): "Deleting an episode does not regenerate the names or summaries of nodes shared with other episodes. This episode information may still exist within these nodes. If an episode invalidates a fact, and the episode is deleted, the fact will remain marked as invalidated." Edges and nodes survive if other episodes reference them, and node deletion cascades to edges. — [Zep v4, Deleting data](https://help.getzep.com/v4/deleting-data-from-the-graph.md)
- Mem0 Platform (docs, read 2026-11-19). "Memory Decay" is "a soft ranking bias, never a filter… at worst it scales its score by `0.3×`", with a ceiling of 1.5×. It is off by default and opt-in per project. Each search result gets a "fire-and-forget reinforcement", with access history "capped at the most recent 20 touches". "Dream" has three actions: "Synthesis" (opt-in, Pro and above; pattern memories linking back to their sources) plus "Supersede" ("Marks an older fact as outdated when a newer one contradicts it") and "Merge", which are "Always on, all plans". A separate "Memory Expiration" feature lets a memory "stop surfacing after a known date without being deleted". — [Mem0, Memory Decay](https://docs.mem0.ai/platform/features/memory-decay); [Mem0, Dream](https://docs.mem0.ai/platform/features/dream); [Mem0 docs index](https://docs.mem0.ai/llms.txt)
- Cloudflare Agent Memory: "when a new memory has the same key as an existing one, the old memory is superseded rather than deleted. This creates a version chain with a forward pointer from the old memory to the new memory." Tasks "are ephemeral by design", are excluded from the vector index and "deprioritized after the session ends". The model's `forget` tool marks "a memory as no longer important or true". — [Cloudflare Blog](https://blog.cloudflare.com/introducing-agent-memory/); [How Agent Memory works](https://developers.cloudflare.com/agent-memory/concepts/how-agent-memory-works/)
- Supermemory (docs, read 2026-11-19). "Automatic forgetting" works three ways: "Time-based — temporary facts drop after they expire ('exam tomorrow', 'meeting at 3pm today')"; "Contradiction — updates win for 'what's true now'"; and "Noise filtering". An `isLatest` flag keeps "retrieval on the current fact without erasing the past". — [Supermemory, Graph memory](https://supermemory.ai/docs/concepts/graph-memory.md)
- GitHub Copilot Memory, the key forgetting design. Two dated statements conflict:
  - 2026-01-15 changelog (public preview): memories are "validated against the current codebase before use" and "Automatically expired after 28 days to prevent stale information". — [GitHub Changelog](https://github.blog/changelog/2026-01-15-agentic-memory-for-github-copilot-is-in-public-preview/)
  - Current docs (read 2026-11-19): "The default expiry period is 90 days. Enterprise and organization owners can configure the expiry period for repository-level facts to any value between 7 and 180 days (inclusive)." User-level preferences always use the default. "The expiry period starts when a memory is created and resets when Copilot upvotes it. Simply retrieving a memory does not reset this period." "Downvoting a memory does not alter the period remaining". "Memories that are downvoted past a threshold are no longer used and will be deleted after a period of disuse." Hidden memories "can remain stored until they expire. A memory disappearing from the list does not necessarily mean it has been deleted." — [GitHub Docs, About Copilot Memory](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)
  - So the 28-day figure is the January 2026 launch value. As of November 2026 the documented default is 90 days, configurable from 7 to 180. A secondary ITNEXT article also reported 90 days ([ITNEXT, secondary](https://itnext.io/github-copilot-memory-dreaming-code-search-9e16e1492bba)).
- Anthropic memory tool, "Memory expiration": "Periodically delete memory files that haven't been accessed in a long time." Deletion is otherwise explicit (`delete`) and left to the application. — [Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Claude Code: transcripts are deleted after `cleanupPeriodDays`, but memory files are excluded from that sweep. "`MEMORY.md` and topic files stay until you or Claude edits or deletes them." Near the size limit, Claude is reminded to "merge or drop stale entries". The documented forgetting is therefore size pressure plus manual edits, with no TTL. — [Claude Code memory](https://code.claude.com/docs/en/memory)
- AWS AgentCore: `eventExpiryDuration` is "The number of days after which memory events expire, between 7 and 3650 days", but the same page lists the "Valid Range: Minimum value of 3. Maximum value of 3650". Short-term storage is billed "over their time to live (TTL)". — [AgentCore Control API, CreateMemory](https://docs.aws.amazon.com/bedrock-agentcore-control/latest/APIReference/API_CreateMemory.html); [AgentCore pricing](https://aws.amazon.com/bedrock/agentcore/pricing/)
- Google Memory Bank TTL configuration "Defaults to no TTL". A sample sets "Default TTL for memory revisions is 365 days". Consolidation can delete memories, and fetching a DELETED memory returns 404. — [Set up Memory Bank](https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/memory-bank/setup); [Generate memories](https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/memory-bank/generate-memories)

## Attacks and privacy

### Takeaway
Memory turns a one-shot prompt injection into a persistent one. An attacker writes once (through a web page, document or crafted query) and every later session obeys. Measured attack success is high: MINJA injects malicious records 98.2% of the time with query-only access; AgentPoison exceeds 80% with under 0.1% poisoned entries. SpAIware showed real exfiltration that persisted across ChatGPT sessions. OWASP ASI06's mitigations map directly onto forgetting design: provenance, expiry of unverified memory, rollback, per-tenant namespaces, and no automatic re-ingestion of the agent's own outputs. Copilot's citation check is one tested defence (vendor claim). Privacy is the other edge. Supersession and "verbatim raw messages" preserve exactly what an erasure request needs gone. Embeddings can be inverted (92% exact recovery of 32-token inputs), so vector stores must be in scope for deletion. No regulator statement found says in so many words that embeddings in agent memory are personal data; that conclusion is an inference from the research plus the EDPB's case-by-case anonymity test.

### Cited Findings
- MINJA (Dong et al.; v1 2025-03-05 titled "A Practical Memory Injection Attack against LLM Agents"; v5 2026-02-12 titled "Memory Injection Attacks on LLM Agents via Query-Only Interaction"). The attacker needs no direct access to the memory bank, only "interacting with the agent via queries and output observations". It uses "bridging steps" and an "indication prompt" with "progressive shortening". Across three agents (EHR, RAP/Webshop, QA): "average success rate of 98.2% for injecting malicious records into the memory, and a high average attack success rate of 76.8%". Per-setting attack success ranges from 57.0% (EHR/MIMIC-III, GPT-4) to 98.9% (RAP/Webshop, GPT-4o). — [arXiv 2503.03704v5](https://arxiv.org/abs/2503.03704)
- AgentPoison (Chen et al.; v1 2024-07-17, the only version). A backdoor trigger optimized so that triggered queries retrieve poisoned demonstrations from memory or a RAG store. "average attack success rate higher than 80% with minimal impact on benign performance (less than 1%) with a poison rate less than 0.1%", tested on autonomous-driving, QA and EHR agents. — [arXiv 2407.12784v1](https://arxiv.org/abs/2407.12784)
- Johann Rehberger, "ChatGPT: Hacking Memories with Prompt Injection" (2024-05-22): fake memories can be planted through connected apps, uploaded images and browsing, and the "Memory updated" notice "is the primary indicator that something unwanted might have happened". — [Embrace The Red](https://embracethered.com/blog/posts/2024/chatgpt-hacking-memories/)
- Rehberger, SpAIware (2024-09-20). A prompt injection from an untrusted site writes spyware instructions into ChatGPT's memory, so "all new conversation going forward will contain the attackers instructions and continuously send all chat conversation messages, and replies, to the attacker" through image-URL exfiltration (macOS app). Timeline: memory injection reported May 2024 and "closed as a model safety issue, not a security concern"; end-to-end exploit reported June 2024; fixed in ChatGPT 1.2024.247 in September 2024. Advice: "review your ChatGPTs memories regularly". — [Embrace The Red, SpAIware](https://embracethered.com/blog/posts/2024/chatgpt-macos-app-persistent-data-exfiltration/)
- OWASP Top 10 for Agentic Applications 2026 (published 2025-12-09), ASI06 Memory & Context Poisoning. Context "includes any information an agent retains, retrieves, or reuses, such as summaries, embeddings, and RAG stores". The entry "focuses on persistent corruption of agent memory and retrievable context that propagates across sessions". Examples include "Long-term memory drift", "Cross-agent propagation" and "Cross-tenant vector bleed". Mitigations include: "Scan all new memory writes … before commit"; "Memory segmentation"; "minimize retention by data sensitivity"; "Require source attribution"; "Prevent automatic re-ingestion of an agent's own generated outputs into trusted memory to avoid … 'bootstrap poisoning'"; "use snapshots/rollback and version control"; "decaying or expiring unverified memory over time and supporting rollback/quarantine"; "Expire unverified memory to limit poison persistence"; and "Require two factors to surface high-impact memory (e.g., provenance score plus human-verified tag)". — [OWASP GenAI, Agentic Top 10 2026](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/) (PDF pp. 24–25)
- GitHub adversarial test (vendor, 2026-01-15). The team "deliberately seeded repositories with adversarial memories–facts that contradicted the codebase–with citations pointing to irrelevant or nonexistent code locations. Across all test cases, agents consistently verified citations, discovered contradictions, and updated incorrect memories." No numbers are given. — [GitHub Blog](https://github.blog/ai-and-ml/github-copilot/building-an-agentic-memory-system-for-github-copilot/)
- Anthropic memory tool security notes. "A malicious path such as `/memories/../../secrets.env` can reach files outside the `/memories` directory. Your implementation must validate every path in every command". The listed safeguards: check that paths start with `/memories`, canonicalize paths, reject `../` and `..\\`, "Watch for URL-encoded traversal sequences (`%2e%2e%2f`)", and use `pathlib.Path.resolve()`/`relative_to()`. On sensitive data: "Claude usually refuses to write sensitive information to memory files. For stronger guarantees, add validation that strips sensitive data before your handler writes the file." Also: "cap how large a file can grow". — [Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- Claude Code trust boundaries. External `@` imports in project files show "an approval dialog", "to protect you from files other people commit to a shared project". An `autoMemoryDirectory` set in repository settings is honoured only under workspace trust. — [Claude Code memory](https://code.claude.com/docs/en/memory)
- GDPR Article 17(1) (Regulation (EU) 2016/679): "The data subject shall have the right to obtain from the controller the erasure of personal data concerning him or her without undue delay and the controller shall have the obligation to erase personal data without undue delay where one of the following grounds applies", including that the data "are no longer necessary" and that consent is withdrawn. Article 17(2) requires "reasonable steps, including technical measures" to inform other controllers when data were made public. — EUR-Lex primary not fetchable (HTTP 202 bot challenge): [EUR-Lex 32016R0679](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:32016R0679); text taken from the [gdpr-info.eu reproduction (secondary)](https://gdpr-info.eu/art-17-gdpr/)
- Inference, not regulator text: for agent memory, erasure has to reach every derived copy: the extracted memory, its superseded versions and revisions (Zep `invalid_at` edges, Cloudflare version chains, Memory Bank revisions with a 365-day default TTL, Mem0 superseded facts), verbatim raw messages (Cloudflare and Zep episodes), node summaries that absorbed the fact (Zep's own deletion caveat above), vector embeddings, caches, logs (OpenAI retains deleted-memory logs up to 30 days, secondary), and backups (Letta MemFS git history keeps every commit).
- Embedding inversion. Vec2Text (Morris et al.; v1 2023-10-10): "a multi-step method that iteratively corrects and re-embeds text is able to recover 92% of 32-token text inputs exactly", and it "can recover important personal information (full names) from a dataset of clinical notes". — [arXiv 2310.06816v1](https://arxiv.org/abs/2310.06816)
- EDPB Opinion 28/2024 on AI models (2024-12-17) addresses trained models, not vector stores. Whether a model is anonymous must be assessed case by case, looking at extraction, "regurgitation" and "model inversion" risks. No passage on embeddings or vector databases was found (grep of the PDF for "embedding" and "vector" returned none). — [EDPB Opinion 28/2024 (PDF)](https://www.edpb.europa.eu/system/files/2024-12/edpb_opinion_202428_ai-models_en.pdf). An EDPB-commissioned expert report (Barberá, "AI Privacy Risks & Mitigations – LLMs", February/March 2025; "views … do not necessarily reflect the official position of the EDPB") lists agent "Memory (data storage and retention)" risks. Its mitigations: "Allow users to manage stored data (e.g., delete, edit)" and "Limit retention periods and implement automated deletion policies for sensitive data". — [EDPB SPE report (PDF)](https://www.edpb.europa.eu/system/files/2025-04/ai-privacy-risks-and-mitigations-in-llms.pdf)
- Copilot privacy scoping. Repository facts are "not pooled across an organization's repositories". Forks do not copy memories. On Business and Enterprise plans, user-level preferences are "owned by the billing entity", and administrators "can export or delete user-level preferences for their members". — [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)

## Benchmarks

### Takeaway
LoCoMo is the benchmark vendors fight over. It is small enough (about 9K to 26K tokens per conversation) that full context beats every memory system in Mem0's own table: 72.90% J against Mem0g's 68.44%. Memory systems win there on latency and tokens, not accuracy. LongMemEval is harder (about 115K tokens; a 1.5M-token variant) and names the abilities that matter for forgetting: knowledge updates, temporal reasoning and abstention. Commercial assistants lost 30–64% accuracy on it. The Zep–Mem0 dispute shows that vendor LoCoMo numbers depend on the vendor's own harness. Treat every vendor score as vendor-reported.

### Cited Findings
- LoCoMo (Maharana et al.; v1 2024-02-27, the only version): conversations of "300 turns and 9K tokens on avg., over up to 35 sessions", grounded on personas and temporal event graphs. Tasks: QA, event summarization and multimodal dialogue. Long-context LLMs and RAG "still substantially lag behind human performance". — [arXiv 2402.17753v1](https://arxiv.org/abs/2402.17753)
- LongMemEval (Wu et al.; v1 2024-10-14, v2 2025-03-04, ICLR 2025). It has 500 questions testing five abilities. The two most relevant to forgetting are "Knowledge Updates (KU): Ability to recognize the changes in the user's personal information and update the knowledge of the user dynamically over time" and "Abstention (ABS): … answer 'I don't know'". Variants are LongMemEval_S (~115k tokens per question) and _M (500 sessions, ~1.5M tokens). The headline is a "30% accuracy drop". GPT-4o falls from 0.870 (oracle evidence only) to 0.606 on S (30.3%↓); Llama 3.1 70B falls 55.1%. Online commercial systems tested on histories about 10x shorter than S: ChatGPT (GPT-4o) scored 0.5773 against 0.9184 offline reading, and Coze (GPT-4o) 0.3299 ("37% and 64% performance drop"). "ChatGPT tended to overwrite crucial information as the chat continues, while Coze often failed to record indirectly provided user information." — [arXiv 2410.10813v2](https://arxiv.org/abs/2410.10813)
- Mem0's LoCoMo results (vendor, 2025-04-28), overall LLM-as-judge J: Full-context 72.90% (p95 total latency 17.117 s, ~26K tokens); Mem0g 68.44% (2.590 s); Mem0 66.88% (1.440 s, 1,764 memory tokens); Zep 65.99%; best RAG 60.97%; LangMem 58.10% (p95 search 59.82 s); OpenAI 52.90%; A-Mem 48.38%. Headlines: "26% relative improvements in the LLM-as-a-Judge metric over OpenAI", "91% lower p95 latency and saves more than 90% token cost" against full context. — [arXiv 2504.19413v1](https://arxiv.org/abs/2504.19413)
- Zep's paper (vendor, 2025-01-20). On DMR it scored 94.8% against MemGPT's 93.4% (gpt-4-turbo). Zep itself notes DMR conversations have "only 60 messages, easily fitting within current LLM context windows", and its own full-conversation baseline scored 94.4%. On LongMemEval_S: gpt-4o-mini 63.8% against 55.4% full context; gpt-4o 71.2% against 60.2%; context of 1.6k tokens against 115k; latency 2.58 s against 28.9 s for gpt-4o. Knowledge-update accuracy fell with gpt-4o-mini (76.9% → 74.4%) but rose with gpt-4o (78.2% → 83.3%). — [arXiv 2501.13956v1](https://arxiv.org/abs/2501.13956)
- Zep's blog rebuttal (vendor; 2025-05-06, "Updated Jun 03, 2026"), "Lies, Damn Lies, & Statistics: Is Mem0 Really SOTA in Agent Memory?". Zep says Mem0 implemented Zep incorrectly, including running searches sequentially instead of concurrently. It gives a "corrected result is 75.14% +/- 0.17, with Zep outperforming Mem0 by 10%" and a p95 search time of 0.632 s. It calls LoCoMo flawed, noting that "a simple full-context baseline … achieved a J score of ~73%, compared to Mem0's best score of ~68%". The page's subtitle says "outperforms it by 24%" while the body says 10%, and its banner announces "80% at <200ms latency" (dated "December 9, 2015", apparently a typo). — [Zep Blog](https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)
- Mem0's response (vendor; GitHub issue opened 2025-05-08 by Mem0's co-founder and CTO, now closed), "Revisiting Zep's 84% LoCoMo Claim: Corrected Evaluation & 58.44% Accuracy". It says Zep's calculation included adversarial category 5 answers in the numerator while excluding category 5 from the denominator, and that Zep altered the shared `system_prompt` and retrieval template. — [getzep/zep-papers#5](https://github.com/getzep/zep-papers/issues/5)
- Secondary: later self-reported LoCoMo scores (Mem0 92.5%, Zep 94.7%) use different models and setups and are not comparable. An independent "locomo-audit" repository exists but was not read. — [Mem0 blog (vendor, secondary)](https://mem0.ai/blog/locomo-benchmark); [locomo-audit (not read)](https://github.com/dial481/locomo-audit)

## Implications for our agents and the book

- **Default to a file-based memory with an index.** Use a directory of Markdown files with YAML frontmatter, plus a `MEMORY.md` index capped at about 200 lines (Claude Code's 200 lines/25KB; Letta's root-plus-index layout). Load only the index at session start and read topic files on demand. This matches Anthropic's memory tool, Claude Code and Letta MemFS, needs no vector store at small scale, and is inspectable and diffable. Put it under git (as Letta does) so poisoning can be rolled back, which OWASP ASI06 recommends.
- **Write in the hot path for explicit, high-value items; consolidate in the background.** Use a tool call (`create`/`str_replace`) when the user states a preference or correction, or when the agent discovers a durable fact. Run a background pass at compaction or session end (Letta dreaming, Cloudflare ingest at compaction, Memory Bank asynchronous generation) to merge duplicates and retire contradicted entries. Keep the background pass's edits visible and reviewable: Letta's "Agent reviews before applying" mode still "does not ask you for approval".
- **Make every record a sourced claim.** Store `subject`, `fact`, `source` (file:line, URL, or a quote of the user's words), `type` (user/feedback/project/reference, or fact/event/instruction/task), `created` and `last_validated`. Before acting on a memory, re-check its source, as Copilot does. If the check fails, rewrite or delete the memory. This is the cheapest stale-memory and poisoning defence on record (vendor claim, with merge rate 90% vs 83%).
- **Forget by expiry that resets only on successful validation, not on read.** Copilot's rule ("Simply retrieving a memory does not reset this period"; 90-day default, 7–180 configurable) is a good default. Apply it to `project` facts. Exempt explicit user preferences until the user changes them. Expire `task` items at session end. Use supersession (keep the old version with an `invalid_at` date) only where temporal questions matter, and make sure a hard delete reaches all versions.
- **Never store raw transcripts or the agent's own unverified conclusions as trusted memory.** OWASP warns against "bootstrap poisoning". Label anything derived from untrusted tool output (web pages, emails, issues) as low-trust. Low-trust items need validation or human confirmation before they can change behaviour, and they expire fastest. Never write procedural memory (instructions to self) from untrusted input. CoALA calls that the riskiest write.
- **Harden the handler.** Validate paths (canonicalize, reject `..` and its URL-encoded forms), cap file and index sizes, strip secrets before write, scope per user/tenant, and show the user when memory changes ("Memory updated" was the only tell in SpAIware). Treat a shared or committed memory file as untrusted input, as Claude Code does with external imports.
- **Design deletion as a first-class path.** Provide `forget`/`delete` to the user and the agent. On a GDPR erasure request, delete from files, git history or backups (or document a retention window), caches, logs and any embeddings. Inversion research means embeddings cannot be assumed anonymous; that is an inference, since no regulator statement says so for agent memory.
- **Buy a service when the problem stops being "one agent, one user, a few hundred facts".** The signals: many end users needing isolated profiles; recall across thousands of memories where keyword search over files fails; temporal questions ("what did they prefer before March?"), where Zep's bi-temporal graph or Cloudflare/Mem0 supersession helps; or a team that cannot run a background extraction pipeline. Costs as of November 2026 are low at small scale (AgentCore's worked example comes to $18.97/month; Cloudflare is free in beta), while Zep's paid tiers start at $125/month. Check that the service exports everything (Cloudflare promises this), supports hard delete across revisions, and has a maintained TypeScript client.
- **For the book, treat LoCoMo numbers as marketing.** Full context beats every memory system on LoCoMo, and the Zep and Mem0 numbers for the same system differ by 58% versus 75% (or 84%) depending on who ran the harness. Cite LongMemEval's knowledge-update and abstention abilities as the right tests for forgetting, and say plainly that the 30–64% commercial accuracy drops are 2024 measurements.

## Gaps

- **TypeScript versus Python.** LangMem has no npm package (only PyPI `langmem` 0.0.30); LangGraph.js 1.7.5 has stores but no LangMem extraction or consolidation. Graphiti (Zep's open-source engine) is Python-only (`graphiti-core` 0.31.2; no npm package); TS users get only the hosted `@getzep/zep-cloud`. Google Memory Bank samples are Python (`agentplatform`), and no Memory Bank-specific TS client was found. Mem0's self-hosted Node build (`mem0ai/oss`) lacks some Platform-only features, per its docs. Anthropic's memory helpers exist in TS (`betaMemoryTool`, `BetaLocalFilesystemMemoryTool`), but Go and Ruby have none. AgentCore has a generated TS client (`@aws-sdk/client-bedrock-agentcore`), but its higher-level memory helpers ship in the Python `bedrock-agentcore` package; this was not verified for TS.
- **Copilot expiry conflict.** The 28-day value (changelog, 2026-01-15) and the 90-day value (docs, read 2026-11-19) conflict. No changelog entry recording the change was found.
- **Pricing gaps.** The Mem0 pricing page contradicts itself (Free/Custom tiles against a $19/$249 FAQ). Google's per-1,000-memories SKU is unverified (PDF not fetched). Cloudflare Agent Memory has no price yet.
- **OpenAI ChatGPT memory controls** come only from search summaries (help page 403). Saved-memory capacity limits were not captured.
- **No regulator or EDPB statement found** that classifies vector embeddings in agent memory stores as personal data. The EDPB opinion covers trained models. The claim in this note rests on Vec2Text plus inference.
- **Letta's legacy "memory blocks" API and the original sleep-time agents announcement** were not fetched. Current docs describe MemFS (labels become Markdown files) and "dreaming". The mapping to the older core/archival/recall terms comes from the MemGPT paper only.
- **No independent replication was read** of the Mem0, Zep, Cloudflare or Copilot numbers. The locomo-audit repository and the A-MEM and MINJA defence evaluations were not read in full. Only the abstracts of A-MEM, the 2025-12 survey and Sleep-time Compute were read.
- **Attack success against file-based memory tools** such as Anthropic's memory tool, Claude Code auto memory and Letta MemFS has no published measurement that was found. MINJA and AgentPoison target retrieval-based memory banks.
