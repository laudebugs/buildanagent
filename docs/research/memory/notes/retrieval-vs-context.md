## Anthropic's position: just-in-time retrieval, lightweight identifiers, hybrid strategy

### Takeaway
Anthropic treats context as a finite "attention budget" that loses value with every token it holds ("context rot"). Its September 2025 guidance has three parts. Keep lightweight references (paths, queries, links) in context. Load the data behind them through tools only when it is needed. Pre-load only a small, stable core, which is what Claude Code does: it loads CLAUDE.md up front and uses glob and grep just in time. Anthropic also names the cost: runtime exploration is slower than reading pre-computed data. Its November 2026 memory post keeps the same structure. A small injected layer, an index of what the agent knows, loads into every session, and everything below that layer is searched for when needed.

### Cited Findings
- 2025-09-29, context rot: "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases." Context "must be treated as a finite resource with diminishing marginal returns." LLMs "have an 'attention budget' that they draw on when parsing large volumes of context. Every new token introduced depletes this budget by some amount". Anthropic traces the cause to the n² pairwise attention relationships and to training data in which short sequences dominate. Degradation is "a performance gradient rather than a hard cliff". — [Anthropic, Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- 2025-09-29, guiding principle: "good context engineering means finding the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome." — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- 2025-09-29, the shift from pre-inference retrieval to just-in-time retrieval: "many AI-native applications employ some form of embedding-based pre-inference time retrieval ... we increasingly see teams augmenting these retrieval systems with 'just in time' context strategies." Also: "Rather than pre-processing all relevant data up front, agents built with the 'just in time' approach maintain lightweight identifiers (file paths, stored queries, web links, etc.) and use these references to dynamically load data into context at runtime using tools." Claude Code "can write targeted queries, store results, and leverage Bash commands like head and tail to analyze large volumes of data without ever loading the full data objects into context." — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- 2025-09-29, progressive disclosure: metadata such as folder hierarchy, naming and timestamps act as signals. "file sizes suggest complexity; naming conventions hint at purpose; timestamps can be a proxy for relevance." — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- 2025-09-29, the trade-off: "runtime exploration is slower than retrieving pre-computed data ... Without proper guidance, an agent can waste context by misusing tools, chasing dead-ends, or failing to identify key information." — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- 2025-09-29, hybrid strategy and Claude Code: "the most effective agents might employ a hybrid strategy, retrieving some data up front for speed, and pursuing further autonomous exploration at its discretion ... Claude Code is an agent that employs this hybrid model: CLAUDE.md files are naively dropped into context up front, while primitives like glob and grep allow it to navigate its environment and retrieve files just-in-time, effectively bypassing the issues of stale indexing and complex syntax trees." The post adds: "The hybrid strategy might be better suited for contexts with less dynamic content, such as legal or finance work." Its default advice: "do the simplest thing that works". — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- 2025-09-29, related techniques: compaction (Claude Code continues "with this compressed context plus the five most recently accessed files"), structured note-taking, and sub-agents that explore with "tens of thousands of tokens or more" and return "a condensed, distilled summary of its work (often 1,000-2,000 tokens)". — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- 2025-09-29 (vendor), context management launch. On an internal agentic-search evaluation, "combining the memory tool with context editing improved performance by 39% over baseline. Context editing alone delivered a 29% improvement." In a 100-turn web search evaluation, context editing reduced "token consumption by 84%". — [Anthropic, Managing context on the Claude Developer Platform](https://www.anthropic.com/news/context-management)
- 2026-11-06 (vendor), "The components of agent memory": "the agent harness can preemptively load them into Claude's context at the start of every session ... This means Claude doesn't need to search for them". The post warns: "Injected memories use up valuable tokens, and an incorrect note can be carried into every session ... So the top layer of the memory hierarchy has to stay relatively small". Claude Code auto memory "loads only the first 200 lines or 25 KB of MEMORY.md. This header serves as an index". — [Anthropic, The components of agent memory](https://www.anthropic.com/engineering/components-of-agent-memory)
- 2026-11-06 (vendor), search combined with a built representation, on a corpus of "about 350,000 files, roughly 420M tokens" with 25 questions. Search plus wiki scored 54% rising to 61% as the wiki grew. Search alone scored 53%; wiki alone peaked at 48%. "Using search and the wiki also saved about 20,000 tokens per question." On a merger task needing several documents, the wiki scored 87% and search alone 73%. On a LAB brief task, where criteria "could be retrieved with a text search from a single document", the wiki showed "no clear gain". — [Anthropic](https://www.anthropic.com/engineering/components-of-agent-memory)
- Claude Code docs (undated, read 2026-11-19): "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence. Move instructions that matter for only part of the codebase into path-scoped rules, which load only when Claude works with matching files." "The first 200 lines of MEMORY.md, or the first 25KB, whichever comes first, are loaded at the start of every conversation." — [Claude Code docs, memory](https://code.claude.com/docs/en/memory)

## Anthropic Contextual Retrieval: "under 200K tokens, just put it in the prompt"

### Takeaway
For a static knowledge base below about 200,000 tokens, Anthropic's September 2024 advice is to skip RAG and put the whole corpus in a cached prompt. Above that size, hybrid retrieval works best: BM25 plus embeddings, with chunk-level context prepended, a reranker, and the top 20 chunks passed to the model. In Anthropic's tests that stack cut top-20 retrieval failures by 67%.

### Cited Findings
- 2024-09-19: "If your knowledge base is smaller than 200,000 tokens (about 500 pages of material), you can just include the entire knowledge base in the prompt that you give the model, with no need for RAG or similar methods." Prompt caching makes this approach "significantly faster and more cost-effective", "reducing latency by > 2x and costs by up to 90%". "However, as your knowledge base grows, you'll need a more scalable solution." — [Anthropic, Introducing Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)
- 2024-09-19, why hybrid: embeddings "can miss crucial exact matches". BM25 is "particularly effective for queries that include unique identifiers or technical terms". The example: "Error code TS-999". — [Anthropic](https://www.anthropic.com/news/contextual-retrieval)
- 2024-09-19 (vendor eval). Metric: 1 minus recall@20. Data: codebases, fiction, arXiv papers and science papers, using Gemini Text 004 embeddings. "Contextual Embeddings reduced the top-20-chunk retrieval failure rate by 35% (5.7% → 3.7%)." "Combining Contextual Embeddings and Contextual BM25 reduced the top-20-chunk retrieval failure rate by 49% (5.7% → 2.9%)." "Reranked Contextual Embedding and Contextual BM25 reduced the top-20-chunk retrieval failure rate by 67% (5.7% → 1.9%)." The reranker (Cohere) scored the top 150 chunks and kept the top 20. — [Anthropic](https://www.anthropic.com/news/contextual-retrieval)
- 2024-09-19, number of chunks: "more information can be distracting for models so there's a limit to this. We tried delivering 5, 10, and 20 chunks, and found using 20 to be the most performant". The added context per chunk is "usually 50-100 tokens". The one-time contextualization cost, with caching, is "$1.02 per million document tokens" (2024 Claude 3 Haiku prices). — [Anthropic](https://www.anthropic.com/news/contextual-retrieval)

## Claude Code's choice of agentic search (grep/glob) over a vector index

### Takeaway
Boris Cherny, who created Claude Code, said on the Latent Space podcast (May 2025) that early Claude Code used off-the-shelf RAG with Voyage embeddings. The team replaced it with agentic search, meaning glob and grep in a loop. He gave three reasons: better results ("mostly vibes", plus some internal benchmarks), no index that drifts out of sync, and no index stored somewhere it could leak. The stated cost was latency and tokens. Anthropic's own September 2025 post confirms the design: glob and grep avoid "stale indexing". No Anthropic paper or benchmark for the decision was found.

### Cited Findings
- 2025-05-07, podcast transcript (Anthropic staff speaking, published by Latent Space): "very, very early versions of Claude actually used RAG. So we, like, indexed the code base, and I think we were just using Voyage ... eventually, we landed on just agentic search ... one is it outperformed everything. By a lot. By a lot. And this was surprising. In what benchmark? This was just vibes, so internal vibes. There's some internal benchmarks also, but mostly vibes." — [Latent Space, Claude Code podcast](https://www.latent.space/p/claude-code)
- Same transcript: "Just using regular code searching, you know, glob, grep ... there was this whole, like, indexing step that you have to do for RAG ... the code drifts out of sync. And then there's security issues because this index has to live somewhere ... agentic search just sidesteps all of that. So essentially, at the cost of latency and tokens, you now have really awesome search without security downsides." — [Latent Space](https://www.latent.space/p/claude-code)
- 2025-09-29, Anthropic's primary statement of the design: glob and grep let Claude Code "retrieve files just-in-time, effectively bypassing the issues of stale indexing and complex syntax trees." — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Secondary: blog posts repeat the account and add a "bitter lesson" rationale and the line "Early versions of Claude Code used RAG + a local vector db", reportedly said by Cherny on X or Hacker News. Neither the wording nor the venue was verified — [smartscope.blog (secondary)](https://smartscope.blog/en/ai-development/practices/rag-debate-agentic-search-code-exploration/); [ahkarimi.github.io (secondary)](https://ahkarimi.github.io/blog/2026/rag-failed-in-production/)

## Cursor: semantic search added to grep

### Takeaway
Cursor (vendor eval, November 2025) reports the opposite design choice for its own agent. Semantic search added to grep raised offline accuracy by 12.5% on average, and grep together with semantic search gave its best results. The online effect was small overall and larger on big repositories. The evidence that semantic retrieval helps on large codebases is therefore a vendor eval on a vendor dataset, against an Anthropic decision backed mostly by "vibes".

### Cited Findings
- 2025-11-06 (vendor eval, Cursor Context Bench, which is Cursor's own dataset): semantic search gives "on average 12.5% higher accuracy in answering questions (6.5%–23.5% depending on the model)" and increases "accuracy across all models we tested". — [Cursor, Improving agent with semantic search](https://cursor.com/blog/semsearch)
- 2025-11-06 (vendor online A/B test, same model in both arms): "agent code retention increases by 0.3% when semantic search is available. This effect increases to 2.6% on large codebases with 1,000 files or more." "We observed a 2.2% increase in dissatisfied follow-up user requests when semantic search was not available." — [Cursor](https://cursor.com/blog/semsearch)
- 2025-11-06: the embedding model is trained on agent traces, where an LLM ranks "what content would have been most helpful at each step". Conclusion: "Semantic search is currently necessary to achieve the best results, especially in large codebases. Our agent makes heavy use of grep as well as semantic search, and the combination of these two leads to the best outcomes." — [Cursor](https://cursor.com/blog/semsearch)

## Papers: long context versus RAG

### Takeaway
The papers agree on three points. (1) Long-context models use the middle of a long input poorly and degrade well before their advertised window. (2) When budget allows, long context beats naive RAG on average, but RAG is far cheaper and gives the same answer on most queries, so routing between them captures most of the benefit. (3) Adding retrieved passages helps at first and then hurts, because hard negatives distract the model. No method wins everywhere (LaRA, 2025: "No Silver Bullet").

### Cited Findings
- Lewis et al., RAG (arXiv 2005.11401v4, 2021-04-12; v1 2020-05-22; NeurIPS 2020). This paper coined the term: a seq2seq generator ("parametric memory") paired with "a dense vector index of Wikipedia" ("non-parametric memory"). It set the state of the art on three open-domain QA tasks and found that RAG produces "more specific, diverse and factual language". — [arXiv 2005.11401](https://arxiv.org/abs/2005.11401)
- Liu et al., Lost in the Middle (arXiv 2307.03172v3, 2023-11-20; TACL). "performance is often highest when relevant information occurs at the beginning or end of the input context, and significantly degrades when models must access relevant information in the middle". "GPT-3.5-Turbo's multi-document QA performance can drop by more than 20%—in the worst case, performance in 20- and 30-document settings is lower than performance without any input documents (i.e., closedbook performance; 56.1%)." — [arXiv 2307.03172](https://arxiv.org/abs/2307.03172)
- Xu et al., Retrieval meets Long Context LLMs (arXiv 2310.03025v2, 2024-01-23; ICLR 2024). "LLM with 4K context window using simple retrieval-augmentation at generation can achieve comparable performance to finetuned LLM with 16K context window ... while taking much less computation." Also, "retrieval can significantly improve the performance of LLMs regardless of their extended context window sizes." Retrieval-augmented Llama2-70B-32k beat GPT-3.5-turbo-16k and its own non-retrieval baseline across nine long-context tasks. — [arXiv 2310.03025](https://arxiv.org/abs/2310.03025)
- Hsieh et al., RULER (arXiv 2404.06654v3, 2024-08-06; COLM 2024). 17 models, 13 tasks. Despite "nearly perfect accuracy in the vanilla NIAH test, almost all models exhibit large performance drops as the context length increases. While these models all claim context sizes of 32K tokens or greater, only half of them can maintain satisfactory performance at the length of 32K." — [arXiv 2404.06654](https://arxiv.org/abs/2404.06654)
- Li et al., RAG or Long-Context? Self-Route (arXiv 2407.16833v2, 2024-10-17; EMNLP 2024 industry track). "when resourced sufficiently, LC consistently outperforms RAG in terms of average performance. However, RAG's significantly lower cost remains a distinct advantage." On average LC beats RAG "by 7.6% for Gemini-1.5-Pro, 13.1% for GPT-4O, and 3.6% for GPT-3.5-Turbo". "the predictions from LC and RAG are identical for over 60% of queries." Self-Route, in which the model judges whether retrieved chunks can answer the query and falls back to LC if not, cut cost "by 65% for Gemini-1.5-Pro and 39% for GPT-4O" while keeping performance comparable to LC. On synthetic PassKey, RAG scored 80.34% against LC's 65.25%. Reworded, the same task dropped RAG to 4.58% while LC held at 69.32%. — [arXiv 2407.16833](https://arxiv.org/abs/2407.16833); numbers from [full text v2](https://arxiv.org/html/2407.16833v2)
- Jin et al., Long-Context LLMs Meet RAG (arXiv 2410.05983v1, 2024-10-08; only v1 exists). "the quality of generated output initially improves first, but then subsequently declines as the number of retrieved passages increases". The authors attribute this to retrieved "hard negatives". With a strong retriever the curve is an "inverted-U pattern". The training-free fix is "retrieval reordering", which places the highest-scored passages at the start and end of the input. — [arXiv 2410.05983](https://arxiv.org/abs/2410.05983)
- Li et al., LaRA (arXiv 2502.09977v2, 2025-03-05). 2,326 test cases, 4 QA categories, 3 kinds of long text, 11 LLMs. "the optimal choice between RAG and LC depends on a complex interplay of factors, including the model's parameter size, long-text capabilities, context length, task type, and the characteristics of the retrieved chunks." Secondary (search summary, not checked against the paper's tables): LC does better on reasoning and comparison tasks and at 32K, and RAG gains ground at 128K, especially for weaker models. — [arXiv 2502.09977](https://arxiv.org/abs/2502.09977)
- Modarressi et al., NoLiMa (arXiv 2502.05167v3, 2025-07-09; ICML 2025). Needles share minimal lexical overlap with the question. 13 LLMs that claim 128K or more. "At 32K, for instance, 11 models drop below 50% of their strong short-length baselines. Even GPT-4o ... experiences a reduction from an almost-perfect baseline of 99.3% to 69.7%." Reasoning models and CoT "struggle to maintain performance in long contexts". — [arXiv 2502.05167](https://arxiv.org/abs/2502.05167)

## Chroma "Context Rot" technical report

### Takeaway
Chroma, a vector database vendor and so not neutral on this question, held task difficulty fixed and varied only input length across 18 models. Performance fell as input grew, and fell faster when the question and the needle were semantically distant or distractors were present. The finding most relevant to memory comes from LongMemEval. Every model did much better on a focused prompt of about 300 tokens than on the full prompt of about 113,000 tokens. Retrieving first and then reasoning beats asking the model to do both over raw history.

### Cited Findings
- 2025-07-14 (vendor technical report, Hong, Troynikov and Huber): 18 LLMs including GPT-4.1, Claude 4, Gemini 2.5 and Qwen3, with 8 input lengths and 11 needle positions per condition. 194,480 LLM calls, of which 69 (0.035%) were refusals. Findings: "Across all experiments, model performance consistently degrades with increasing input length." "Lower similarity needle-question pairs increases the rate of performance degradation." Distractors have a "non-uniform impact". Haystack structure "consistently shows an impact". — [Chroma, Context Rot](https://research.trychroma.com/context-rot)
- 2025-07-14, LongMemEval: 306 prompts averaging "~113k tokens" (full) against "~300 tokens" (focused). "Across all models, we see significantly higher performance on focused prompts compared to full prompts." Claude models showed "the most pronounced gap", "largely driven by abstentions". Thinking modes narrow the gap but do not close it. — [Chroma](https://research.trychroma.com/context-rot)
- 2025-07-14, conclusion: "Whether relevant information is present in a model's context is not all that matters; what matters more is how that information is presented." — [Chroma](https://research.trychroma.com/context-rot)

## Prompt caching economics (as of November 2026)

### Takeaway
Caching makes a stable pre-loaded prefix cheap to re-read. Cache reads cost 0.1x base input on most Anthropic models and 0.05x on Opus 5.5 and Sonnet 5.5. A 5-minute write costs 1.25x, so it pays back after one read. This strengthens "carry it" for content that is stable and reused within the cache lifetime. It does nothing for the attention cost of long context (context rot), and caching breaks if anything before the breakpoint changes. OpenAI's ratios are similar.

### Cited Findings
- Anthropic pricing docs (undated, read 2026-11-19, as of November 2026): "5-minute cache write 1.25x base input price"; "1-hour cache write 2x base input price"; "Cache read (hit) 0.1x base input price on most models". "5-minute duration (1.25x write): after one cache read; 1-hour duration (2x write): after two cache reads". The cache-hit multiplier is model-specific: Fable 5.2 / Mythos 5.2 0.025x ($0.20/MTok), Opus 5.5 0.05x ($0.20/MTok), Sonnet 5.5 0.05x ($0.10/MTok), "All other models 0.1x". Base input as of November 2026: Opus 5.5 $4/MTok, Sonnet 5.5 $2/MTok, Haiku 5.5 $0.10/MTok for prompts up to 100,000 tokens and $0.50/MTok above that. "Claude 4.7 and later models ... use a newer tokenizer ... approximately 30% more tokens for the same text." — [Claude docs, Pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Anthropic prompt caching docs (as of November 2026): the minimum cacheable prompt is 512 tokens for the 5.x family including Opus 5.5, Sonnet 5.5 and Haiku 5.5, 1,024 for Opus 4.8 / Sonnet 4.6, and 4,096 for Haiku 4.5 and Opus 4.5/4.6. Shorter prompts are "processed without caching, and no error is returned". A breakpoint has a 20-block lookback, and "changing any block at or before the breakpoint produces a different hash". — [Claude docs, Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- OpenAI prompt caching guide (undated, read 2026-11-19, as of November 2026): caching is "enabled by default"; reused tokens are "discounted up to 95%". For GPT-5.6 and later, "cache writes cost 1.25× the standard, uncached input-token rate for the default 30-minute lifetime", or 2.5× for a 12-hour lifetime in the Responses API. "Subsequent reads cost 0.1× the ordinary input rate on most of these models and 0.05× on GPT-6.2 Astra, GPT-6.2 Sol, GPT-6.1 Sol, and GPT-6.1 Terra". Worked example: "one write and nine full reads cost 2.15× at that rate, compared with 10× without caching." The minimum cacheable length is 1,024 tokens. Older models have "No additional cache-write charge". Per-model prices were not verified because the pricing page returned 403. — [OpenAI, Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)

## Retrieval applied to tools: tool search, defer_loading, code execution with MCP

### Takeaway
The same rule applies to tool definitions. Loading every definition up front can cost 55K–134K tokens and lowers tool-selection accuracy. Deferring definitions and letting the model search for them saved 85% of tokens and raised accuracy on Anthropic's MCP evals. Presenting tools as files the agent browses ("code execution with MCP") cut one workflow from 150,000 to 2,000 tokens. All of these are vendor measurements.

### Cited Findings
- 2025-11-04 (vendor): with code execution, the agent lists `./servers/` and reads only the tool files it needs. "This reduces the token usage from 150,000 tokens to 2,000 tokens—a time and cost saving of 98.7%." Passing intermediate results through the model costs extra: a 2-hour meeting transcript "could mean processing an additional 50,000 tokens". Code execution "requires a secure execution environment with appropriate sandboxing". — [Anthropic, Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)
- 2025-11-24 (vendor): five MCP servers carry "58 tools consuming approximately 55K tokens before the conversation even starts". "At Anthropic, we've seen tool definitions consume 134K tokens before optimization." With the Tool Search Tool, about 8.7K tokens in total are used against about 77K, "an 85% reduction in token usage". On MCP evals, "Opus 4 improved from 49% to 74%, and Opus 4.5 improved from 79.5% to 88.1%". Deferred tools "are excluded from the initial prompt entirely", so caching is not broken. Use it when "Tool definitions consuming >10K tokens". "Keep your three to five most-used tools always loaded, defer the rest." Programmatic tool calling cut average usage "from 43,588 to 27,297 tokens, a 37% reduction". — [Anthropic, Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)
- Tool search docs (as of November 2026): regex and BM25 variants (`tool_search_tool_regex_20251119`, `tool_search_tool_bm25_20251119`) are listed for models from Opus 4.7 through Fable 5.2. "Maximum deferred tools: 10,000 tools with defer_loading: true for each request". "Tool search typically reduces this by over 85 percent, loading only the 3–5 tools Claude needs for a given request." — [Claude docs, Tool search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)

## 2026 updates: grep versus vectors inside agent loops

### Takeaway
Two 2026 papers sharpen the debate without settling it. On conversational memory (LongMemEval), inline grep beat inline vector retrieval for every harness and model pair tested. However, the harness and the way results are delivered (inline or in a file) moved scores more than the choice of retriever. On repository file retrieval, no retriever family dominated, and logged agent trajectories missed every gold file in 27–35% of samples.

### Cited Findings
- 2026-05-14, "Is Grep All You Need? How Agent Harnesses Reshape Agentic Search" (arXiv 2605.15184v1; v1 is the only version). 116 LongMemEval questions run on a custom harness (Chronos) and on Claude Code, Codex and Gemini CLI. "inline grep exceeding inline vector for every harness-model pair we evaluate". On Chronos, "inline grep spans 83.6–93.1% across backbones, whereas inline vector spans 62.9–83.6%." "The same Claude Opus 4.6 backbone reaches 93.1% under Chronos but 76.7% under Claude Code". Delivering results as files reverses some comparisons: Codex/GPT-5.4 fell "from 93.1% under inline grep to 55.2% under programmatic grep". Conclusion: "file-based delivery and provider CLI shells able to invert or erase the lexical advantage". — [arXiv 2605.15184](https://arxiv.org/abs/2605.15184); numbers from [full text v1](https://arxiv.org/html/2605.15184v1)
- 2026-07-27, Agent Retrieval Bench (arXiv 2607.24882v1). 427 samples, 25 repositories, 392,000 files, 7.9M chunks. "No single retrieval family dominates: Qwen3-Embedding-4B has the best sample-weighted MRR on positive samples, Qwen3-Embedding-8B the best Recall@20, and RepoMap the best budgeted context yield at 8K tokens". "Logged trajectories also miss every gold file on 27-35 percent of samples." — [arXiv 2607.24882](https://arxiv.org/abs/2607.24882)
- 2026-11-06 (vendor): Anthropic's memory post, summarized in the first section, is the newest Anthropic primary on the question. Search with a maintained index (a wiki) beat search alone on multi-document questions and saved about 20K tokens per question. It gave no gain where a text search of one document was enough. — [Anthropic](https://www.anthropic.com/engineering/components-of-agent-memory)
- Secondary: a CORE-Bench (June 2026) code retrieval funnel and a Turbopuffer talk (AI Engineer Europe 2026) report roughly equal recall for windowed reads with or without semantic search on 50 tasks. Neither was read — [codex.danielvaughan.com (secondary)](https://codex.danielvaughan.com/2026/08/01/core-bench-code-retrieval-agentic-coding-codex-cli-grep-embedding-search-retrieval-funnel/); [ai.engineer (secondary)](https://ai.engineer/talks/zKk7sDMGDEQ-benchmarking-semantic-code-retrieval-on-claude)

## Implications for our agents and the book

- **Carry the small, stable, always-relevant core.** That means instructions, a memory index and the 3–5 most-used tools, kept under about 200 lines or 25 KB, as Claude Code does. Caching makes re-reading it nearly free: a 5-minute write at 1.25x pays back after one read at 0.05–0.1x. Every carried token still draws on the attention budget, and an incorrect note gets carried into every session.
- **Retrieve everything else just in time, and keep pointers in context.** Pointers are file paths, IDs, URLs and stored queries, not the payloads behind them. This applies to tool definitions too: defer them when they exceed about 10K tokens.
- **Decision rule supported by the evidence.** Carry the whole corpus only when all four conditions hold. (a) It is static within the cache lifetime. (b) It is small, roughly under 200K tokens for a 2024 Claude model and well under the window where RULER and NoLiMa show degradation (often 32K for hard tasks). (c) Most queries need much of it, as in reasoning or comparison across documents, where LC beats RAG. (d) You will reuse it often enough to amortize the cache write. Otherwise retrieve. When in doubt, use a Self-Route-style fallback: try retrieval first and escalate to long context only when the model says the chunks are insufficient. Self-Route kept LC-level quality at 39–65% lower cost.
- **For memory over conversation history, retrieve, then reason.** Chroma's 113K-token prompts against roughly 300-token focused prompts, and the LongMemEval grep results, both say not to replay raw history. Search it, and inject only the hits.
- **Start with lexical search (grep or BM25) and add embeddings only after measuring.** Lexical search is exact on identifiers, needs no index that can go stale, and keeps data local. It won on conversational memory in 2026. Add semantic search when queries are conceptual and the corpus is large: Cursor saw +12.5% offline and its biggest online gains on repositories of 1,000 files or more (vendor eval). If you index, use hybrid BM25 plus embeddings with a reranker and top-20 chunks, and order the strongest passages at the edges.
- **Measure retrieval inside your own harness.** The 2026 papers show that the harness and the delivery path (inline result or file) can move accuracy by 15–38 points with the same retriever, so a retriever benchmark does not transfer to our TypeScript harness.
- **Cap the number of retrieved chunks.** Returns invert after a point because hard negatives distract, so more retrieval is not automatically better. Delegate broad exploration to sub-agents that return 1–2K-token summaries.

## Gaps

- No Anthropic paper or published benchmark backs Claude Code's switch from RAG to grep. The primary account is a podcast transcript, and it says "mostly vibes". The exact wording of Cherny's X or Hacker News post was not found.
- Cursor's numbers come from a vendor dataset (Cursor Context Bench) that is not public. Its A/B effect sizes come without confidence intervals.
- The 200K-token rule of thumb dates from September 2024 and Claude 3-era models. No 2026 Anthropic restatement for current context windows (or the roughly 30% larger 4.7+ tokenizer) was found, and current context window sizes were not checked.
- The OpenAI pricing page returned 403, so per-model cached-input dollar prices are unverified. Only the ratios from the caching guide are recorded.
- LaRA's per-length numbers come from a search summary and were not checked against its tables. LongBench v2 was not reviewed.
- Most long-context papers test 2023–2025 models. No independent 2026 RULER or NoLiMa-style results for the Claude 5.x or GPT-6.x families were found.
- TypeScript-specific gaps: no source measures retrieval for TypeScript or JavaScript codebases specifically. That includes grep versus embeddings on TS monorepos, or whether type-aware tools (tsserver/LSP "go to definition") beat both. The 2026 grep paper used conversational data, not code. Whether `@anthropic-ai/sdk` or the Agent SDK sets `defer_loading` or cache breakpoints automatically in TypeScript was not checked.
