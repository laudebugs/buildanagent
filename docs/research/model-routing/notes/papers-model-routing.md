## 1. Repo context tested, not repeated

The repo already says (agent-sdk.md ~line 47; agent.md §8, ~lines 225-235): about 45 HN authors route by role; changing model or effort mid-session busts the cache; gateway offers a per-subagent model setting, no automatic per-request router. agent-research-papers.md already covers Zhou et al., "Reducing Inference Cost of Coding Agents with Timeout Cascades" (arXiv:2611.24324) and Hou et al. (Atm, routing decisions as records). I re-read the timeout-cascade paper; corrections to the repo's summary are in 2.13.

Test results in one place (details below):
1. "Changing effort mid-session busts the cache": still true for a top-level change, but both big vendors now document a cache-preserving per-message effort change (Anthropic beta; OpenAI `configuration_update`). The repo statement needs a qualifier. See 3.2, 3.1.
2. "Changing the model busts the cache": true by construction (caches are per model), and OpenRouter's own auto router is built around it: "Switching models rebuilds the prompt cache, so the router changes effort first and switches models only when the gain justifies it." So the practitioner constraint is reproduced by a vendor router.
3. "Route by role, not per request": supported by Anthropic's own measured guidance (orchestrator/subagent wins in only two situations; otherwise lower effort on one model won). But 2026 research (Switchcraft, TwinRouterBench, AgentRouter, MTRouter) reports per-step routing savings even under cache accounting, on small, partly vendor-affiliated, simulated or single-benchmark setups. The disagreement is real and unresolved. See 5.
4. No pre-2026 paper models caching at all (FrugalGPT through Router-R1: nothing found by grep for cache in the ones I checked). Cache-aware evidence exists only in 2604-2609 papers.

## 2. Papers

Format per paper: citation/URL/version; method; models; data; headline numbers with location; baselines; stated limitations; builder takeaway.

### 2.1 FrugalGPT (Chen, Zaharia, Zou)
- https://arxiv.org/abs/2305.05176 ; I read v1 (9 May 2023). arXiv listing of later TMLR 2024 version is cited by AgentRouter as "Transactions on Machine Learning Research, 2024"; I did not read a later version.
- Method (§3, Strategy 3): LLM cascade = ordered list of m APIs, a scoring function g(q,a) in [0,1] and a per-stage threshold; return the first answer whose score >= threshold. Learn list L and thresholds by constrained optimisation under a budget (mixed-integer; they prune lists with low disagreement and interpolate). Also describes prompt adaptation and LLM approximation (completion cache, fine-tuned small model).
- Models: 12 commercial APIs from 5 providers (Table 1). Cascade length 3. Scorer: DistilBERT regression (§4).
- Data: HEADLINES (finance, 10000 examples), OVERRULING (law, 2400), COQA (reading, 7982) (Table 2). Random train/test split. One split; no run variance reported that I found.
- Headline: "match the performance of the best individual LLM (e.g. GPT-4) with up to 98% cost reduction or improve the accuracy over GPT-4 by 4% with the same cost" (abstract). Table 3 (cost to reach same accuracy): HEADLINES GPT-4 33.1 vs FrugalGPT 0.6, 98.3% savings; OVERRULING GPT-4 9.7 vs 2.6, 73.3%; COQA best is GPT-3, 72.5 vs 29.6, 59.2%. Case study Fig. 3: HEADLINES, budget $6.5 = one-fifth of GPT-4's cost; chain GPT-J (accept if score > 0.96) -> J1-L (accept if > 0.37) -> GPT-4; "cost is reduced by 80%, while the accuracy is even 1.5% higher". Fig. 4: max-performance-improvement matrix shows the cheap models are right where GPT-4 is wrong on a minority of items: "13% of data points where GPT-4 makes an error, but GPT-3 provides the correct answer" on COQA.
- Baselines: individual LLMs only; no other routers (2023).
- Limitations (§5): needs labelled examples drawn from the same or similar distribution as test; cascade learning costs resources (one-time); latency, fairness, privacy not studied. Fig. 5(c) example: all LLMs in the chain give the same answer but scorer is unsure, so every stage is paid; "Identifying how to avoid such cases remains an open problem."
- Builder: the original cascade-with-a-learned-verifier. Savings are large on easy classification tasks with a short answer; the scorer is trained per dataset. Models are 2023 GPT-3/J1/GPT-4 era with 100x price spread.

### 2.2 RouteLLM (Ong et al.)
- https://arxiv.org/abs/2406.18665 ; v4, 23 Feb 2025; PDF prints "Published as a conference paper at ICLR 2025".
- Method (§3-4): binary router between a strong and weak model; routers trained on 80k Chatbot Arena preference battles (label sparsity addressed by clustering models into tiers, §4.1), plus data augmentation with golden-label MMLU validation split (~1500 samples) or GPT-4-as-judge labels. Four routers: similarity-weighted (SW) ranking, matrix factorisation, BERT classifier, causal-LLM classifier. Metrics: CPT(x%) = fraction of strong-model calls needed to reach x% of the gap closed; APGR.
- Models: strong gpt-4-1106-preview, weak Mixtral 8x7B (main). Transfer test Table 4: Claude 3 Opus / Claude 3 Sonnet, Llama 3.1 70B / 8B with the same routers (not retrained).
- Data: MT Bench (160 open-ended, LLM judge), MMLU (14,042 questions, 5-shot), GSM8K (>1,000, 8-shot); contamination check against training sets (§5.1).
- Headline: abstract "reduce costs by over 2 times without sacrificing response quality". Table 1 (MT Bench): trained on Arena+judge data, matrix factorisation CPT(50%) = 13.40% (random 49.03%), CPT(80%) 31.31%, APGR 0.802 (+60.4%); note "MT Bench score at CPT(50%), 8.8, is 95% that of GPT-4's score (9.3)". Tables 2-3: trained on Arena only the routers are about random on MMLU/GSM8K (e.g. BERT MMLU CPT(50%) 49.43% vs random 50.07%); adding ~1500 in-domain golden-label samples gives "approximately 20% less GPT-4 calls than random" on MMLU. Table 6 cost saving ratio over random at CPT(50%): MT Bench 3.66x (95% GPT-4 quality), MMLU 1.41x (92%), GSM8K 1.49x (87%). Table 7 router overhead: SW ranking $39.26 per million requests at 2.9 req/s; matrix factorisation $3.32/M at 155 req/s; "adds an extra cost of no more than 0.4%" of GPT-4 generation. Cost basis §5.4: GPT-4 $24.7 per million tokens, Mixtral $0.24.
- Baselines: random router; commercial routers compared in Appendix E (not read).
- Limitations (§6): real-world distributions may differ from benchmarks; two-model only; "performance between different routers trained on the same dataset can vary widely on the same benchmark without a clear explanation". Table 5 similarity score between training set and benchmark predicts router gain.
- Builder: a router trained on generic preference data does not transfer to a new task distribution (MMLU/GSM8K ~ random); ~1.5k in-domain labels changed that. Savings quoted are vs a random router at matched quality, not vs "always weak". Models are 2024 GPT-4 vs Mixtral.

### 2.3 Hybrid LLM (Ding et al.)
- https://arxiv.org/abs/2404.14618 ; v1, 22 Apr 2024 (PDF does not print venue; ICLR 2024 per brief).
- Method (§3): router predicts query difficulty = probability that small model's response quality (BART score) is >= large model's, trained with DeBERTa-v3-large; three variants: deterministic (r_det), probabilistic (r_prob, sample multiple responses), and probabilistic with data transformation (r_trans: relax the label with a threshold t chosen by grid search). Threshold tunable at test time. One LLM call per query (no cascade).
- Models: FLAN-T5 800m/11b, Llama-2 7b/13b, GPT-3.5-turbo, in pairs of small/medium/large quality gap.
- Data: MixInstruct (four public datasets; 10k train examples, 5k test, §4.1).
- Headline: abstract "up to 40% fewer calls to the large model, with no drop in response quality" (their "cost advantage" = fraction of queries sent to the small model, not dollars, §2.3). Table 1 quality drop vs all-at-large: Llama-2 7b vs 13b: 40% cost advantage -> 0.0-0.2% drop; Llama-2 13b vs GPT-3.5-turbo: 20% -> 0.8-1.0% (r_prob/r_det), 40% -> 2.9-3.5%; FLAN-T5 800m vs Llama-2 13b (large gap): 40% -> 10.3-13.8% drop. Fig. 1: 22% fewer GPT-3.5 calls with 1% BART drop. §4.4 router latency measured against open models (DeBERTa router much faster; GPT-3.5 latency not measured).
- Baselines: random routing, all-at-large, all-at-small.
- Limitations (§5): routes on query text alone; fixed model pair and distribution; OOD generalisation and N-model routing left to future work. Fig. 8: transfer to unseen model pairs works when quality gaps correlate (r=0.76) and not when they don't (r=0.06).
- Builder: "up to 40%" holds only when the pair is close; with a big gap the router is near random. Quality metric is BART score, a similarity metric, not task correctness.

### 2.4 AutoMix (Aggarwal et al.)
- https://arxiv.org/abs/2310.12963 ; v5, 19 Jan 2025 (NeurIPS 2024 per brief).
- Method (§3-4): small model answers; same small model self-verifies the answer few-shot against the context (entailment-style), producing a noisy confidence; a POMDP router (or simple threshold) decides whether to call a larger model. Black-box, no weights, no trained verifier. Metric IBC (incremental benefit per cost) and Delta-IBC vs the linear mix of SLM and LLM (§5.1).
- Models: SLMs Mistral-7B, Llama-2-13B, GPT-3.5; larger model GPT-4 (relative cost 1 for SLM vs 60/100/200 for LLM, §5.1; "five language models").
- Data: QASPER, QUALITY, COQA, MUTUAL, DIPLOMAT (context-grounded QA/dialogue); validation splits; identical prompts across models.
- Headline: abstract "reducing computational cost by over 50% for comparable performance". Table 1 Delta-IBC: AutoMix+POMDP e.g. Mistral-7B DIPLOMAT 156.8, MUTUAL 46.7, COQA 12.4, QASPER 69.3, QUALITY 51.6; FrugalGPT 16.8/20.3/-16.7/7.7/8.1; HybridLLM 67.1/3.4/10.5/0.4/2.7. Text: AutoMix-POMDP "is the only method that yields positive gains across all configurations"; with 50 training examples "maintains 15% Delta-IBC and beats the baselines by more than absolute 20%" (§5.4). Baselines were charged zero routing cost "due to their lower operational costs" while AutoMix's verifier cost is charged (§5.2).
- Limitations (end of §6): "designed with a dialogue-related or context-grounded reasoning setup in mind for effective self-verification, which does not include tasks like factual question-answering and commonsense reasoning."
- Builder: a self-verifier can work without training data, but only where the answer can be checked against supplied context; the "50%" is the abstract's claim; the table gives IBC lift, not a dollar saving. Not an agent setting.

### 2.5 RouterBench (Hu et al.; Martian authors)
- https://arxiv.org/abs/2403.12031 ; v2, 28 Mar 2024. Authors include Martian staff (code under github.com/withmartian/routerbench): treat as vendor-affiliated.
- Method: benchmark with precomputed outputs, §3 framework with cost-quality convex hull and AIQ (average improvement in quality over a cost range); "Zero router" baseline = best convex combination of single models that ignores the query. Routers tested (§5.1-5.2): KNN, MLP predictive routers (trained 70% / tested 30%), and a cascading router with a simulated judge having error rate p (§5.2, "error parameter").
- Data: 405,467 samples, 11 models, 8 datasets, 64 tasks (§4.2): MMLU, Hellaswag, Winogrande, ARC, GSM8K, MBPP, MT-Bench, plus a RAG set. Models include GPT-4, GPT-3.5, Claude V1/V2/Instant, Llama 70B, Mixtral 8x7B, Yi 34B, Mistral 7B, Code Llama 34B, WizardLM 13B.
- Headline (§5.3, quoted): KNN/MLP routers "achieve the level of performance to the best individual LLMs with lower or similar costs ... However, none of the routing algorithms significantly outperform the baseline Zero router"; the oracle "consistently exceeds all other routers and LLMs". Cascading (Fig. 5): with judge error 0 the cascade nears the oracle; "as the judge's error rates increase, the performance of the cascading router may deteriorate rapidly, particularly when the error rate exceeds 0.2"; strong gains only "when the router's judge has an error rate of up to 0.1". RAG set (§5.4, Fig. 6): all routers beat the zero router; routers learn time-sensitive features (e.g. "2024") and send them to online-retrieval models.
- Limitations (§6): only cost and quality (no latency, throughput); limited models/tasks; cascades evaluated with a simulated (not real) judge, so the paper itself calls the result "a simulated upper limit".
- Builder: the strongest sceptical primary result in the older literature: on public benchmarks simple routers barely beat "pick a model on the cost-quality frontier and ignore the query". And a cascade is only as good as its judge; error above ~0.2 erases the gain.

### 2.6 A Unified Approach to Routing and Cascading for LLMs (Dekoninck, Baader, Vechev)
- https://arxiv.org/abs/2410.10347 ; PDF header "v5 ... 26 Oct 2026". I read v5 text. (ICML 2025 per brief; v5 may differ from the version most papers cite; table numbers below are v5's.)
- Method (§3-4): derive an optimal cascading strategy (adding to a proof that quality-minus-lambda-cost routing is optimal), and "cascade routing": at each step re-route to any remaining model using updated quality estimates, combining ex-ante (before running) and post-hoc (after running) quality estimates. States "good quality estimators as the critical factor".
- Data/models: RouterBench with 3, 5, 11 models and injected Gaussian noise on quality/cost estimates (§5.1); SWE-Bench (10 models, quality via ground-truth tests = post-hoc, cost = latency); Minerva Math + LiveCodeBench (Qwen2.5 Math/Coder, ex-ante accurate); ARC-Challenge, MMLU-Pro, MixEval, GSM8k with Llama and Gemma families using log-probability-feature quality estimators (after Gupta et al.) (§5.2).
- Headline: abstract/§1 "improving performance by up to 8% on the RouterBench benchmark and by 14% on the SWE-Bench benchmark". Text §5.1: "gains between 1% to 4%, which measured relatively to the naive linear interpolation baseline means that cascade routing improves by 13% to 80% over the baselines." Real-world classification/open-form (Table 2 right): "much narrower margins reaching up to 1.2%" because estimates are noisy. SWE-Bench (Table 2 left): routing "does not outperform the trivial baseline" because ex-ante estimates are insufficient; baseline cascade also does poorly because of binary feedback (threshold admits all or only correct).
- Limitations: stated implicitly in §5.2: with realistic noisy quality estimators the gain over baselines is about 1%.
- Builder: theory says routing helps when you can predict quality before running (e.g. you know the task type), cascading helps when you can check after running (tests), and with only a noisy classifier there is little to gain. For agents the useful estimator is post-hoc: tests, schema validation, compile.

### 2.7 Language Model Cascades: Token-level uncertainty and beyond (Gupta et al.)
- https://arxiv.org/abs/2404.10136 ; v1, 15 Apr 2024 (ICLR 2024 per brief).
- Method (§2-3): deferral rules for generative cascades. Chow-Sum (sum of token log-probs) suffers length bias; Chow-Average over-corrects (defers short outputs); Chow-Quantile uses a quantile of the per-token probability vector; learned post-hoc deferral rule (5-layer MLP) on quantiles, plus optional embeddings from small and large models. Metric: area under the deferral curve (AUC-DF).
- Models/data: FLAN-T5 Small/Base/Large/XL; MNLI, ANLI, TriviaQA, NaturalQA, TyDiQA (ID/SW/FI), Lambada, SQuAD, WMT translation pairs (§3.5); 5 random runs averaged (Table 1/4 caption).
- Headline: post-hoc rule "consistently performs the best; in scenarios where other methods are better, the difference is minimal" (§4.3); no single quantile works across datasets (§1); using the larger model's intermediate embeddings gives further gains, "particularly for classification tasks" (needs access to larger model internals, not possible with APIs).
- Limitations (§5): encoder-decoder FLAN-T5 only, "we believe insights ... should generalize to decoder-only" untested; RLHF models are known to be uncalibrated; verbalised confidence not evaluated.
- Builder: token-probability confidence is length-biased and needs logprobs; many hosted frontier APIs do not expose them. For agents, a deferral signal must come from somewhere else.

### 2.8 GraphRouter (Feng, Shen, You)
- https://arxiv.org/abs/2410.03834 ; v2, 17 Mar 2025; PDF prints "Published as a conference paper at ICLR 2025".
- Method (§2): heterogeneous graph with task, query and LLM nodes; GNN (2-layer GAT, 32-dim) predicts edge attributes (response quality and cost) for candidate LLMs; inductive: new LLMs added via few-shot interaction data (80 queries) with LLM descriptions embedded.
- Models: 10 LLMs through Together API (Table 3); first six observed, last four "new" in generalisation test.
- Data: Alpaca, GSM8K, SQuAD, Multi-News, 600 cases each = 2,400 queries (Table 2), split 70/10/20.
- Headline: abstract "minimum performance improvement of 12.3%" and "at least 9.5% boost" on new LLMs. Table 4 reward under three performance/cost weightings; "Performance First": GraphRouter 0.539 vs Hybrid LLM 0.510, FrugalGPT 0.517, Oracle 0.588; "Cost First" reward 0.064 vs FrugalGPT 0.057, Oracle 0.072; Largest LLM reward -0.701. Text §4.1: "at least 88.89% of the optimal solution". Table 5: vs C2MAB-V few-shot, reward +9.52%, time cost -99.45%.
- Limitations (conclusion): "primarily serves as exploratory work"; richer graph signals (paths, model taxonomy) left out. Future work mentions multi-agent per-module selection.
- Builder: tiny dataset (2,400), single-turn tasks; the improvement is in a weighted reward (performance minus cost) not dollars saved. Useful idea: describe each model with embeddings so a new model can be added without retraining; Router-R1 reuses it.

### 2.9 Router-R1 (Zhang, Feng, You)
- https://arxiv.org/abs/2506.09033 ; v3, 24 Oct 2025.
- Method (§3): the router is itself an LLM (Qwen2.5-3B-Instruct or Llama-3.2-3B-Instruct) trained with PPO to interleave "think" and "route" actions over multiple rounds, integrating each routed model's reply into its context; reward = format + final outcome (exact match) + cost reward (normalised by output tokens and model price tier, App. A.1). Conditions only on model descriptors (price, latency, example performance), so it can route to unseen models.
- Models: pool of six, e.g. Qwen2.5-7B, Llama-3.1-8B/70B, Mistral-7B, Mixtral-8x22B, Gemma-2-27B (§4); pricing from Together.
- Data: trained on 7K NQ + 7K HotpotQA; evaluated on seven QA sets (NQ, TriviaQA, PopQA, HotpotQA, 2WikiMultiHopQA, Musique, Bamboogle).
- Headline: Table 1 average exact match "Router-R1-Qwen 0.416; Router-R1-Llama 0.409"; beats Prompt LLM, KNN router, GraphRouter, RouterDC, Search-R1. Fig. 3 (cost coefficient 0.6-0.9): "as the cost coefficient increases, overall performance gradually declines" while cost reward rises; emergent behaviour "prefers to query smaller models first and only escalates to larger models when necessary". Fig. 4a: more routed calls on multi-hop than single-hop sets.
- Limitations (Appendix, "Limitations"): task scope QA only; simple reward; "its multi-round nature introduces inference latency ... may limit its suitability for time-sensitive applications"; generalisation to unseen LLMs depends on descriptors like price and latency.
- Builder: shows a learned router can discover a small-first-then-escalate cascade itself, but it is a QA/RAG setting with exact-match reward, and the router is an LLM that adds calls and latency. No headline dollar saving figure (I did not find one).

### 2.10 RouterEval (Huang et al.)
- https://arxiv.org/abs/2503.10657 ; v2, 20 May 2025.
- Content: benchmark of "over 200,000,000 performance records for 12 popular LLM evaluations ... based on over 8,500 various LLMs" (mostly open models with published leaderboard results, many small).
- Headline: "a capable router can significantly enhance the performance ... as the number of candidates increases. This improvement can even surpass the performance of the best single model in the pool" (abstract, §3); "even with only 3 ~ 10 candidates, the performance can obtain strong performance" (§3, finding 3). Evaluation of existing routers: "most still have significant room for improvement" (abstract; Tables 1-2 not read in detail).
- Limitations (end): data volume still "cannot produce an excellent router"; benchmark records mostly closed, expensive; cost-effectiveness best at 3-10 candidates.
- Note: the scaling result is about accuracy with an oracle-like router (oracle router r_o and a router with accuracy p, §3.1), not about dollars. "Cost" appears as a future objective.
- Builder: the promise (a pool of weak models beats one strong one) rests on an oracle router; real routers are far from it.

### 2.11 MasRouter (Yue, Zhang et al.)
- https://arxiv.org/abs/2502.11133 ; v1, 16 Feb 2025 (PDF does not print a venue).
- Method (§4): cascaded controller network chooses a collaboration mode (CoT, reflection, self-consistency, debate, MacNet chain/complete), agent roles (pool of 26), and the LLM per agent, trained with a cost penalty lambda in {5,15,25}.
- Pool: gpt-4o-mini-0718, claude-3.5-haiku, gemini-1.5-flash, llama-3.1-70b (all cheap-tier; deepseek-v3 used for the inductive test) (§5.1). Data: MBPP, HumanEval, GSM8K, MATH (519 problems), MMLU.
- Headline: abstract "1.8% ~ 8.2% improvement over the state-of-the-art method on MBPP", "reducing overhead by up to 52.07% compared to SOTA methods on HumanEval", plug-in to MAD/MacNet "reducing overhead by 17.21% ~ 28.17%" (Table 2); Table 1 "outperforming RouterDC ... by 3.51% on average"; HumanEval cost $0.363 -> $0.185 in intro; training cost savings 69.57%/83.51% vs GPTSwarm/AFlow on MMLU (Table 12).
- Limitations: no limitations section found by grep. All pool models are small/cheap, so "cost" gains are mostly from collapsing the number and structure of agents, not from swapping a frontier model for a cheap one.
- Builder: much of "multi-agent routing" saving is topology selection (fewer agents), not model selection; separate the two when quoting.

### 2.12 Reducing Inference Cost of Coding Agents with Timeout Cascades (Zhou, Sviridov, Ustiugov, Javaid; AMD Singapore / NTU)
- https://arxiv.org/abs/2611.24324 ; read the PDF text (version not printed in the text I extracted; repo cites submission 18 Nov 2026).
- Method (§IV-G, H): small-model-first cascade. Task first goes to GLM-4.7-Flash under a timeout (swept 0-120 min); if the run times out, produces an empty patch, a syntax error, or "fails the tests" it escalates to GLM-4.7 which "restarts from the original task state" (cold restart). Compared with an "oracle-style" difficulty router (simulated from ground-truth difficulty labels).
- Data: SWE-bench Verified with mini-swe-agent; 36 open-weight models evaluated (§V-A, Fig. 1); hybrid simulations use the 466 tasks (190 easy, 238 medium, 38 hard) with recorded trajectories from both models (§IV-C/E). Single run per model-task pair.
- Headline (§V-C): "On easy tasks, GPU-hour cost drops from 821 to 546 GPU-hours, a 33.5% reduction. Across all tasks, it drops from 2585 to 2160 GPU-hours, a 16.4% reduction." Oracle-style router: 2585 -> 2122, 17.9% (§V-D); "an additional gain of only 1.5%". At 0% router accuracy cost rises to 2623 GPU-hours, above large-only 2585. Resolve rate stays at or slightly above the 71.2% large-model baseline.
- Corrections to how the repo summarises it: (a) the "up to 33%" is the easy-task slice only; the all-task figure is 16.4%. (b) The cost is GPU-hours for self-hosted open-weight models, not API dollars. (c) The cascade's escalation trigger includes "fails the tests" - i.e. ground-truth test outcome, which a real deployment may not have for every task (SWE-bench-style tasks with a reproducing test do). (d) The hybrid results are "simulations" assembled from recorded trajectories, not a live two-model run. (e) Restart is cold: a live system using an API with caching would also lose cached context on escalation. (f) Authors: "single-run evaluations, one primary model pair, and one benchmark", 91% of tasks easy/medium; if the workload is mostly hard, "the cascade would approach a large-model-only system with extra overhead". They suggest "asynchronous workflows".
- Builder: an in-loop signal (timeout) plus a verifier (tests) gave most of the benefit of an oracle router. Strongest paper-side evidence for "cascade with a verifier beats router".

### 2.13 Switchcraft: AI Model Router for Agentic Tool Calling (Agarwal et al., Microsoft Research)
- https://arxiv.org/abs/2605.07112 ; v2, 30 Oct 2026 (I read v2). Industry authors; the paper reports interviews with "a dozen enterprise teams".
- Method (§3): fine-tuned DistilBERT classifier predicts per-model probability that a tool call is correct; Platt-calibrated; picks lowest-profiled-cost model above a reliability threshold, abstains if none likely; runs on every agent turn within a 20 ms budget (§4.5; T4 GPU; routing cost "at most $1.57 per million queries").
- Models: 8 candidates including GPT-5-nano, GPT-5-mini, GPT-5.4(-mini/-nano), GPT-5.3-chat, Kimi-K2.5, Qwen-3.5-9B (per-model results Table 3).
- Data: six function-calling benchmarks (BFCL v3 etc.), 99,125 in-distribution labelled queries, held-out test 9,746 queries (Table 3), plus one benchmark held out entirely (OOD).
- Headline: abstract "78.3% answer accuracy (86.4% when correct abstentions are credited) at 59% lower cost than the best individual model (75.6%), saving over $3,800 per million queries"; "larger models do not consistently outperform smaller ones on tool-use tasks, and nominally cheaper models can incur higher total cost due to token-intensive output" (Finding 1: GPT-5.3-chat 75.63% beats newer GPT-5.4 74.62% at 58% of its cost; GPT-5.4 "over-elaborates, producing verbose chain-of-thought that occasionally corrupts the structured tool-call output"). Routes 74% of queries to GPT-5-nano on OOD benchmark (§4.3). Label cost: "Labeling our 99,125 in-distribution queries with all eight models cost about $2,300 at list prices"; pays back "after about 600,000 routed queries" (§4.5).
- Multi-turn and caching (§4.6, Appendix P, Tables 37-38): execution-with-recovery on BFCL multi-turn: Switchcraft 72.7% vs GPT-5.4 77.3% at 3.8x cost. KV-cache replay: "Switching models between turns forfeits cached prompt prefixes. We replay consecutive multi-turn test turns of 20 seeds with a KV cache per model and published cache-read prices, which discount cached input by 90% for OpenAI models and 83% for Kimi-K2.5". Result: "Caching cuts per-turn routing's cost by 65%. Keeping the current model while it stays predicted-correct costs 7.3% more at similar accuracy, and routing only the first turn saves 19% but loses 5.7 pp of accuracy". App. P table 38: per-turn routing 40.68 (x10^-4 $) with cache vs 115.10 without; sticky 43.64; first-turn-only 32.88 at 67.85% accuracy vs 73.59%.
- Cache-accounting assumptions (App. P, "Cache accounting"): "a separate cache for each model per conversation ... On turn 3, A can reuse the matching prefix cached on turn 1"; no TTL expiry modelled that I could find; no cache-write premium (OpenAI-style); Qwen has no cached price so uncached rate used. The multi-turn subset is small (BFCL multi-turn: 1,490 per-turn records, 150 in the test set; "multi-turn queries (1.5%) make up 69% of Switchcraft's spend", §4.8). Anthropic's 1.25x/2x write premium and 5-minute TTL would change the arithmetic. This is the main published counter to "switching mid-session busts the cache => do not route per turn", and it depends on those assumptions.
- Limitations: labels score each call given ground-truth history (no cross-turn recovery credited, App. E/F); harness requires a tool call every request; realised cost exceeds budget because "Ranking models by average profiled cost cannot see that a long multi-turn query costs far more than average" (§4.8).
- Builder: per-call routing on tool-call correctness (a checkable property) with a calibrated classifier and abstention is the most agent-specific design in the literature; savings are large because many tool calls are easy and because the "best single model" is not the biggest one.

### 2.14 Task- and Session-Level Model Routing: Common-Interface Hybrid Evaluation of Four Open-Source Routers (Kumar, Saminathan)
- https://arxiv.org/abs/2608.14641 ; v1, 28 Jul 2026. Small, independent authors (Indiana University / independent). I read abstract, intro, task selection, results §6, most of the discussion.
- Method: one adapter interface; four routers: RouteLLM (matrix factorisation), LiteLLM Router (rules/fallbacks, no content inspection), vLLM Semantic Router and Aurelio Semantic Router (embedding similarity). Benchmarks: RouterBench (replayed), BFCL v4 (single-turn simple only), tau2-bench (retail only), WebArena (gitlab + shopping only). 290 frozen tasks; 3 candidates x 3 replicates = 2,610 candidate outcomes; prompt-output cache disabled between replicates. Sample sizes 30 (BFCL), 60 (RouterBench), 100 (tau2, WebArena), "set in advance based on API cost constraints rather than a power calculation". Routers pick one model "per task or session"; per-step routing is explicitly not evaluated.
- Headline (abstract): "Three routers emit constant or near-constant tier assignments; only vLLM Semantic Router varies materially with prompt content, and it has the highest observed success rate on none of the four benchmarks. Always-Mid matches Aurelio exactly on three benchmarks and within 0.003 on the fourth ... observed gains track selected-tier composition more closely than demonstrated task-specific targeting." Table 3 candidate tiers: mid-general at least double cheap-small on RouterBench/WebArena, about 1.5x on tau2; mid->strong increment smaller than cheap->mid (0.117 vs 0.283 on RouterBench), zero on WebArena, slightly negative on tau2; BFCL v4: cheap-small best. Cost: Aurelio costs "42.2x more per task than the cheap-only routers on WebArena and 54.5x on tau2-bench on candidate cost alone".
- Correction to a search-summary claim: the "~16x" figure is a pool-swap/price propagation result (Table 18): LiteLLM and RouteLLM per-task cost went "$0.000038 -> $0.000618" when the cheap slot's model was replaced, with success unchanged, i.e. static routers locked to a slot inherit a price change; it is not "routers cost 16x more with no gain".
- Limitations: configurations are partly the authors' adapter choices (Aurelio utterances, RouteLLM threshold applied to a pair it was not calibrated on); "the findings are scoped to these configurations, candidate pool, and frozen benchmark samples, not to routing paradigms in general."
- Builder: control for fixed-tier baselines and selected-tier mix before crediting a router. Small n.

### 2.15 AgentRouter: Heterogeneous Model Routing for Cost-Optimal Multi-Step Agentic Workflows (Paul, Nandy)
- https://arxiv.org/abs/2609.22951 ; v1, 19 Sep 2026; PDF header says "Proceedings of the 43rd International Conference on Machine Learning, Seoul ... PMLR 306, 2026". 25 KB text; read all of it.
- Method (§3): 12M-parameter classifier (task-type tagger + MLP) maps each trajectory step to one of four tiers using five features: inferred task type (PLAN/REASON/RETRIEVE/GENERATE/FORMAT/VERIFY), reasoning depth, tool-use count, output format, context utilisation. Asymmetric loss penalises under-provisioning more than over-provisioning (lambda 0.3). "Dependency-aware" labels assume earlier steps ran on their minimum adequate tier. Fallback: if end-to-end quality < Qmin, re-run failed steps on the frontier model (fires on <4% of trajectories); in evaluation Qactual uses ground-truth labels, "in production deployment, a lightweight LLM-as-a-judge proxy replaces the ground-truth evaluator".
- Data/models: 50,000 step annotations from 6,250 trajectories (4 domains), 2,400 held-out trajectories (600/domain, 4-12 steps, 18,720 step decisions). Pool: GPT-4o ($15/M out), GPT-4o-mini, Llama-3-70B, Llama-3-8B (prices Feb 2026). Authors' own benchmark; "Implementation details ... supplementary materials" (not available to me).
- Headline: abstract/Table 1: 71.8% cost reduction at 97.3% of frontier-only quality, overhead 4.7 ms; RouteLLM per-step 31.4%/94.2%; FrugalGPT cascade 44.1%/96.8% with 48 ms overhead; DAAO 36.2%/98.1%; Budget-Aware 52.7%/95.6%. Table 2: only 14.2% of steps need Tier 1 yet use 48.3% of cost; per-tier accuracy 76.4-91.2%, overall 84.6%. §4.4 ablation: task type is the dominant feature (-12.3 accuracy points when removed). Cost reduction by domain: document 76.4%, data 74.1%, research 69.2%, code 63.8% (code needs Tier 1 on 26.3% of steps).
- Stated limitations (§5): trained on LangGraph/CrewAI; on AutoGen "6-9% accuracy degradation, though cost reduction still reaches 58%"; model tiers tied to Feb-2026 pricing; "assumes the step sequence is known or estimable at routing time ... Fully online agentic scenarios ... fall outside the current scope"; median 3.2 tier transitions per trajectory (95th percentile 7 for 8-step trajectories) and a note that providers charging per-call overhead may see that matter. No prompt-cache accounting found (grep for "cach" returned nothing).
- Weaknesses to flag: intro claims "60-80% of their inference budget" wasted and "55-70% of agent trajectory steps require no frontier-model capability" are anecdotal ("every production agent system we have operated"), no source. Self-built benchmark, GPT-4o/Llama-3 era models. Treat as the most optimistic estimate and weakest evidence of the group.
- Builder: step-type is the useful signal (planning/reasoning vs formatting/extraction) - matches the role-based practice; the headline saving is unverified outside the authors' setup.

### 2.16 MTRouter: Cost-Aware Multi-Turn LLM Routing with History-Model Joint Embeddings (Zhang et al.)
- https://arxiv.org/abs/2604.23530 ; v1, 26 Apr 2026.
- Method: joint embedding of interaction history and candidate model; outcome estimator trained on logged trajectories predicts turn-level utility; chooses model each turn under a fixed budget. Pool of 6 with OpenRouter prices (Table 2).
- Data: ScienceWorld (text environment, 50-step horizon; 13 task types ID, held-out types OOD) and Humanity's Last Exam with tools (search/browse/python; 30 steps).
- Headline (abstract, Table 3, mean over 3 runs): "on ScienceWorld, it surpasses GPT-5 while reducing total cost by 58.7%; on HLE, it achieves competitive accuracy while reducing total cost by 43.4% relative to GPT-5". HLE accuracy 26.0%. vs Router-R1: +11.7 points on ScienceWorld with 54.4% lower cost; HLE 32.7% lower cost. "makes fewer model switches" than prior multi-turn routers.
- OpenRouter auto router as baseline (§4.1): "OpenRouter produces negative scores on ScienceWorld because it underestimates task difficulty and over-relies on lightweight models" (§4.2); caveat: OpenRouter's pool is larger and not customisable (App. D) so the comparison is not like-for-like. The 2025-era OpenRouter auto router (Not Diamond-based) is the one tested; the 2026 router (see 3.5) has a different mechanism.
- Cache: no cache modelling found (grep "cach" gave no hit in the body).
- Builder: shows a cheap generic production router can fail badly in interactive agent tasks; learned per-turn routing found "fewer switches" are better.

### 2.17 TwinRouterBench (Yang et al., Gradient / Commonstack-affiliated)
- https://arxiv.org/abs/2605.18859 ; v5, 24 Oct 2026. Authors include Gradient; the benchmark repo is CommonstackAI/TwinRouterBench and the tested router UncommonRoute is Commonstack's, so vendor-affiliated.
- Method: step-level routing benchmark. Static track: 970 router-visible prefixes from 520 instances across SWE-bench, BFCL, mtRAG, QMSum, PinchBench, each with an execution-verified minimum tier from a "downgrade-and-cascade" search; scoring is arithmetic on labels, trajectory membership and token costs. Dynamic track: live SWE-bench Verified harness; at each LLM call the router picks a model "given the current prefix, available models, cache state, and budget"; reports official resolve rate and realised API spend.
- Cache accounting (§5.2): "prompt tokens are billed as cache_write on cold starts, tier switches, TTL expiry (5 minutes, matching provider defaults such as Anthropic's prompt-cache policy), or prefix deltas, and as cache_read on valid same-tier prefix hits"; "cache_write at high is 12.5x its cache_read" (App. Table A7).
- Headline (Table 3, locked 100 instances: 18 Astropy + 82 Django, "not a random sample of SWE-bench Verified"): Opus 4.6 no routing 74/100 resolved, API cost $54.73; UncommonRoute (trained) 75/100, $25.66 (53.1% lower, text §6.2); UncommonRoute (rule-based) 73/100, $172.56 (more than unrouted); SR-KNN router 75/100, $55.61. Static track: LLM-as-router test: Claude Opus 4.6 given the pool description predicts "high" for only 7 of 147 verified-high steps and fails all 40 SWE trajectories (Table A11/A12; "a case study of one frontier model under one prompt template").
- Limitations (§7): small static corpus; labels frozen to the model pool/prices; dynamic coverage only SWE-bench Verified subset; "Function-calling scores can reflect both task decisions and interface compliance".
- Builder: only live end-to-end evidence I found of per-step routing in a coding agent with realised cache-aware spend: ~53% lower cost at equal resolve on 100 tasks, but a rule-based router cost 3x MORE than no routing. The result depends on label supervision from execution-verified downgrades (n^m runs naive; they use greedy locking).

### 2.18 From Myopic Selection to Long-Horizon Awareness: Sequential LLM Routing for Multi-Turn Dialogue (DialRouter; Zhang et al.)
- https://arxiv.org/abs/2604.12385 ; v1, 14 Apr 2026.
- Method: MCTS over dialogue branches induced by different model choices; distils a lightweight routing policy with retrieval-based future-state approximation. Cost model with cache: "if the same model is used in consecutive turns, cached history tokens is charged at the lower cache cost ... if the model switches, all [input charged at the standard rate]" and footnote: "we consider the worst-case scenario for model switching, in which the KV cache is assumed to be completely invalidated."
- Data: ShareGPT, JDDC (e-commerce customer service), MedDG; Qwen and Llama candidate sets plus closed models (GPT-5.1, DeepSeek-V3.2 in Table 4/5).
- Headline: average success 83.31% (Qwen set), +5.67% over Qwen3-14B; 78.88% (Llama set); with a cost reward "approximately 80% reduction" in cost with SR 88.69%, "relative drop of about 1.4%" (Fig. 4; the baseline for the 80% figure is not clear from the text I read - treat as unverified). Routing patterns (App.) show "transition structure dominated by self-loops, indicating limited cross-model switching once a routing strategy is established".
- Builder: when the cost model charges for switching, the learned policy mostly sticks with one model. Dialogue, not tool-using agents.

### 2.19 Unified AI Gateway: Joint Model Routing and KV Cache Management (Lu, Zhang, Shao; Huawei)
- https://arxiv.org/abs/2609.06940 ; v1, 7 Sep 2026. Vision/system-design paper with an analytical simulation, no deployed system or real API measurements.
- Claim: "When routing switches the target model, the accumulated cache may be unavailable or incompatible, forcing the target model to repeat full-context prefill. This repeated work can outweigh the capability or price advantage of switching models." Simulation (Table 3-4 settings, Fig. 1): "TTFT speedups of 1.25x-13.28x and input-cost benefits of 1.20x-6.16x" across eight workload profiles; requires cross-model KV cache transfer/mapping which commercial APIs do not offer (it cites LMCache/Mooncake-style systems for self-hosted stacks). Cache read price uses 0.10x as in Anthropic's rate.
- Builder: only useful as a statement of the problem and for self-hosted stacks; the numbers are modelled, not measured.

### 2.20 COMPASS (Rezaei, Parsa; Invariant Tech)
- https://arxiv.org/abs/2610.27822 ; v1, 20 Oct 2026. Industry author.
- Agentic router: an LLM follows a routing recipe, calls tools to fetch evaluation records (performance/cost per model), optionally previews candidate answers, then selects a model. Evaluated on LLMRouterBench (69.85% accuracy at $139.57 vs RLCascadeRouter 69.14% at $180.22) and DeepSWE under 5-fold CV ("78.1% at $215, compared with 74.1% at $500 for the best single model"); per task, not per step.
- Own stated next step: "cache-aware multi-turn routing" (routing decisions should weigh caching costs). Unread beyond abstract, §1, and greps (partial read).

### 3.1 OpenAI

For the API: "we provide direct access to the thinking model, its mini version" plus a nano. The card does not say the router is exposed in the API. Signal: learned classifier trained on user feedback. Vendor claim, no numbers.
- Current state: the ChatGPT help article "GPT-5 in ChatGPT" (https://help.openai.com/en/articles/11909943-gpt-5-in-chatgpt, "Updated: 3 days ago") as returned by the fetch tool does not mention Auto/Fast or a router; it describes a Thinking slider (Instant, Medium, High, Extra High, Pro) and says "If you reach a Thinking limit, ChatGPT may continue with another available model." So by Nov 2026 the user-facing product is described as user-selected effort, plus a limit-based fallback. I cannot confirm from official text that the router was removed; press coverage in Aug 2025 (the-decoder, TechCrunch, Fortune, listed in search results, not fetched) reported a picker (Auto/Fast/Thinking) returning after backlash. Mark: ChatGPT router status = unclear in current docs.
- API-side controls: prompt caching guide (https://developers.openai.com/api/docs/guides/prompt-caching; no date on page): caching on by default; minimum 1,024 tokens for GPT-5.6 and later; retention 30 min minimum or 12 h via `prompt_cache_options.ttl` on GPT-5.6+; "discounted up to 95%"; cache reads 0.1x (0.05x on some GPT-6.x); "A different model can use different weights and caching behavior"; changing reasoning effort can "change model-side reasoning instructions"; "On supported GPT-6 and later models, you can append a `configuration_update` item to change effort while keeping the earlier prefix cacheable." (as returned by the fetch tool; exact item shape not verified).
- Signal summary: classifier on conversation (ChatGPT only), plus user/developer-set effort and model.

### 3.2 Anthropic
- Effort parameter (https://platform.claude.com/docs/en/build-with-claude/effort; page uses anthropic-version 2026-10-21): five levels low/medium/high/xhigh/max; "Effort is a behavioral signal, not a strict token budget"; "affects all tokens ... Text responses, tool calls and function arguments, thinking"; low "Simpler tasks that need the best speed and lowest costs, such as subagents". Haiku 5.5 "For high-volume, latency-sensitive tasks such as classification, extraction, and routing"; "In long agent prompts, the model is more likely to skip a search, stop early, or skip a check at `low`."
- Cache and effort: "Changing the top-level effort value between requests can invalidate all or part of the prompt cache, so vary it across workloads rather than within a conversation that relies on cache hits." New: per-message effort (https://platform.claude.com/docs/en/build-with-claude/effort-per-message, beta, header `mid-conversation-output-config-2026-07-01`): a `role: "system"` message carrying `output_config.effort` "leaves everything before it unchanged, so the cached prefix still matches." Limits: model support differs by platform (the page's tables are inconsistent about which models), not on Managed Agents ("Availability: Not available"), and some thinking modes (Sonnet 5.5 `between_tools`, Haiku 5.5 `disabled`) reject a mid-conversation change with a 400.
- Prompt-caching page (https://platform.claude.com/docs/en/build-with-claude/prompt-caching; first 100,000 of 155,417 chars read): hierarchy tools -> system -> messages; tool-definition changes invalidate everything; "The thinking configuration ... changing it always invalidates message blocks"; changing effort "can invalidate message blocks, and on some models tool and system caches too"; switching `speed` fast/standard "invalidates system and message caches". Default 5-minute TTL, 1-hour option; write 1.25x (5 min) or 2x (1 h) base input; reads 0.1x (0.05x for Opus 5.5 and Sonnet 5.5; 0.025x for Fable/Mythos 5.x). The page "does not say whether caches are shared across models"; I could not find that statement in the part I read.
- Model choice (https://platform.claude.com/docs/en/about-claude/models/choosing-a-model): "Tuning effort is often a better lever than switching models." Two starting strategies (efficiency-first from Haiku 5.5, or capability-first from Opus 5.5 then optimise down). "Combine models: Multimodel strategies pair a lower-cost model with a frontier model so that most tokens are billed at the lower rate. The two common patterns are an executor that escalates hard decisions to an advisor, and an orchestrator that delegates bulk work to lower-cost workers."
- Measured guidance (https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence; first 100,000 of 195,771 chars read; vendor-internal results, "directional"): "The page advises tuning one model first, then building a pairing only if it beats the single model's whole score-versus-spend curve." Advisor pattern: "An advisor can help only when the executor consults it"; Opus 5.5 at high + Fable 5.1 advisor scored 90.1%, "1.7 points over the executor alone, at the edge of run-to-run noise" at $2.92 per attempt, "about 2.1 times the executor alone"; on GPQA Diamond, Haiku 5.5/Sonnet 5.5 with an Opus 5.5 advisor were within noise of the executor and cost 12% / 25% more because the advisor was consulted on "none of the 198 questions"; Chartography: executor at low plus advisor scored 61.7, "7 points below the executor alone". Orchestrator pattern: delegation "came out ahead in only two situations": routine work with a long cost tail (easy slice of BrowseComp, earlier models) and work larger than one context window (internal defect search); for "a single dependent chain, or work that fits in one context without a long cost tail, the orchestrator's model alone at lower effort came out ahead in every case measured." Opus 5.5 with Sonnet 5.5 subagents "cost about a third less ... and scored about the same" (defect search); Haiku 5.5 subagents on coding tasks with Opus 5.5 at medium "cut cost per attempt by 32% and the pass rate by about 4 percentage points (95% interval 1.3 to 7.1)", described as "an alternative to lowering effort, not better". Caveats on the page: changing top-level effort mid-session "invalidates the cache and distorts the comparison"; "Switching speed mid-conversation misses the prompt cache"; recheck "at every model release, because releases move both the capability gap and the price ratio".
- Tooling: advisor tool (beta) and Managed Agents multiagent orchestration ("each with its own model", up to 25 concurrent subagents) = role-based routing offered as a product feature. No automatic per-request model router from Anthropic in the pages read.
- Signal summary: no classifier; the caller picks model and effort; the model itself may escalate (advisor consult) or the orchestrator delegates by role.

### 3.3 OpenRouter
- Auto Router (https://openrouter.ai/docs/guides/routing/routers/auto-router; as returned by the fetch tool; a search result page also states older docs said "powered by NotDiamond", and a January 2025 announcement described a Not Diamond meta model; the current page describes a different mechanism): narrow the pool (guardrails, ZDR, capabilities, allow/exclude lists) -> "A fast decision model rates eleven aspects of the request in one call" (task type, difficulty, speed needs, vision, codebase knowledge) -> policy "weighs that rating against live prices, cache status, and benchmark performance" within a `cost_tier` (low/medium/high) and picks model and effort -> normal provider routing. "No added fee. You pay the standard rate for whichever model is selected." Session stickiness: "Switching models rebuilds the prompt cache, so the router changes effort first and switches models only when the gain justifies it." Variants openrouter/auto, auto-code (coding agents), auto-beta. Deprecated parameters `cost_quality_tradeoff`, `pin_model`; 404 if restrictions leave no model; global data region only. Observability via `X-OpenRouter-Metadata: enabled`.
- Prompt-caching guide (https://openrouter.ai/docs/guides/best-practices/prompt-caching): "Subsequent requests for the same model are routed to the same provider, keeping your cache warm", sticky up to 60 minutes inactivity; not used with manual provider order; for router models the cached model is reused only best-effort, "so the router may select a different model on a later turn."
- Fallbacks/provider sort pages were not retrieved (the page I fetched did not contain them); no claim made here.
- Signal: LLM-rated request features + price + cache + benchmarks; fallback on provider health. Vendor claims, no savings numbers given on the page.

### 3.7 Vercel AI Gateway
- Model fallbacks (https://vercel.com/docs/ai-gateway/models-and-providers/model-fallbacks, last_updated 2026-10-02): `providerOptions.gateway.models` array tried in order "if the primary model fails or is unavailable"; combine with provider `order`/`only`; `modelAttempts` metadata. Failure-triggered.
- Decision fallbacks (https://vercel.com/docs/ai-gateway/models-and-providers/decision-fallbacks, last_updated 2026-10-08): for a "decision" request (structured classification via a native decision model such as `typesafe-ai/jev` or a language model) a conditional object `{ model, when: { question, confidenceBelow | probabilityBetween | any/all/atLeast } }` reruns the whole decision on a stronger model when the first answer is uncertain; "A triggered fallback executes and bills both the primary and fallback stages"; stages are sequential so latency adds; "runs at most two successful decision stages"; "Only native decision models report confidence. A language-model fallback ... Choice and Score answers have no `confidence`." This is a gateway-level cascade with a confidence verifier, but only for the Decisions API, not for chat/agent completions (the page: "Only decision requests accept a conditional object").
- Virtual models (https://vercel.com/docs/ai-gateway/models-and-providers/virtual-models, last_updated 2026-10-02): `vmc/<slug>` stores model + provider order/only + fallbacks + `sort` (e.g. "cost") + prompt caching + provider options (e.g. `{"anthropic": {"effort": "high"}}`) once; coding agents (Claude Code, Codex) can select it; updating the slug moves every agent at once. A "custom routing" page is linked ("Route across models with Custom Routing"), not fetched.
- Signal: failure, provider health/cost sort, or confidence threshold on decision requests.

### 3.8 LiteLLM
- Router (https://docs.litellm.ai/docs/routing): strategies `simple-shuffle` (default, "recommended for production"), `latency-based-routing`, `usage-based-routing-v2`, `least-busy`, `cost-based-routing` (lowest-cost healthy deployment), custom strategy; `fallbacks`, `context_window_fallbacks`, retries with backoff, cooldowns (default 5 s). These pick among deployments of the same model name for load/reliability, not between a strong and weak model by difficulty.
- Auto Routing (Beta, https://docs.litellm.ai/docs/proxy/auto_routing; "available since v1.94.0"): scores each request "across seven dimensions and maps the score to a tier" SIMPLE/MEDIUM/COMPLEX/REASONING with zero API calls in the default heuristic mode; alternative classifiers: small LLM, JEV (TypeSafe), keyword rules, custom plugin; tier can hold a list with `adaptive: true` (Thompson sampling); `session_affinity` off by default. Page limitations (quoted/paraphrased from the fetch): "Session affinity pins the whole session to its first-turn tier, so a hard opening question keeps later simple turns on an expensive model"; "Savings figures are estimates against a derived baseline and depend on cache-history evidence." Signal: heuristic or LLM classifier on request text.

## 5. Synthesis

### 5.1 Three designs compared
1. Per-request (or per-step) router: a classifier or LLM predicts, before running, which model will be good enough (RouteLLM, Hybrid LLM, GraphRouter, Switchcraft, AgentRouter, OpenRouter auto, LiteLLM auto routing, ChatGPT router). Needs an ex-ante quality estimate; helps when task type is predictive of difficulty. Unified-routing paper: routing is "useful when ex-ante quality estimates are accurate".
2. Per-role routing: the developer pins a model (and effort) to a role (planner, executor, reader, formatter, grader, subagent). No classifier, cache-friendly because the model changes only at context boundaries. Anthropic's advisor/orchestrator pages and Managed Agents are this pattern; Vercel virtual models and Cloudflare dynamic routes are config-level versions. Evidence is practitioner plus vendor-internal; AgentRouter's ablation (task type is the strongest feature, -12.3 accuracy points when removed) suggests role/step-type captures most of the signal a classifier uses.
3. Cascade with a verifier: run cheap first, escalate if a check fails (FrugalGPT, AutoMix, timeout cascade, Vercel decision fallbacks, RouterBench cascading router). Needs a trustworthy post-hoc check; best in agents where tests/validators exist (SWE-bench tests; schema-valid tool calls; compilation). Cost: wasted cheap attempt, added latency, and a cold restart that discards cache.

### 5.2 Signals that worked, and where
- Task or step type (planning vs formatting vs retrieval): AgentRouter ablation; TwinRouterBench step-role shares (upper tier 72.09% for test/verification/debugging vs 1.95% summarisation/answering, 0.79% tool/API).
- Executable verification: tests (timeout cascade; Unified routing's SWE-Bench), tool-call schema correctness (Switchcraft).
- Time/budget as implicit difficulty: timeout (2.12).
- Token log-probabilities: work for short outputs, length-biased (2.7); often unavailable from APIs.
- Self-verification by the small model: works for context-grounded QA only (2.4).
- Cheap generic similarity/heuristic routers: weakest evidence; independent evaluation found constant tiers; MTRouter found OpenRouter's older auto router "negative scores" on ScienceWorld.
- LLM-as-router with a frontier model: failed in TwinRouterBench's single case (7/147 high steps identified); Router-R1 trained a 3B router with RL and got good QA results, with latency caveat.
- Cost-aware features: price per model and live cache state used by OpenRouter's current router (vendor-described, not independently evaluated).

### 5.3 Reported savings and their conditions
- Largest numbers (FrugalGPT 98%, AgentRouter 71.8%, Switchcraft 59%, TwinRouterBench 53%, MTRouter 58.7%/43.4%) come from: easy-skewed workloads; a best-single-model baseline that is the largest model; a pool with a 100x price spread; labels for the exact distribution; small or self-built benchmarks. Timeout cascade shows what happens with a harder, standard benchmark and honest per-task accounting: 16.4% (all tasks) vs 17.9% for an oracle router.
- Savings against a "random router" (RouteLLM) or "linear interpolation" (Unified) baselines are not savings against "just use a mid-tier model". The independent evaluation (2.14) found Always-Mid matched the best router on three of four benchmarks, and RouterBench found a zero-information router on the cost-quality frontier is hard to beat.
- Savings available without any router: Anthropic: "Tuning effort is often a better lever than switching models"; Haiku-subagents cost -32% with -4 pp pass rate, "an alternative to lowering effort, not better". Prompt caching read prices of 0.1x or lower dominate input cost in long loops (repo's own agent.md §8: 95.9% of tau-bench agent cost is input tokens), so a router that breaks the cache can lose what the cheaper model gains.

### 5.4 Failure modes (with evidence)
- Router miscalibration: false confidence; cascades degrade fast when judge error exceeds 0.2 (RouterBench); Switchcraft: a fixed 0.5 threshold on raw outputs got 73.33%, below the best single model, calibrated thresholds plus abstention added 4.59 pp accuracy at 2.2x cost (§4.7); 62.7% misrouted when only one model is correct (§4.8).
- Distribution shift: RouteLLM Arena-only routers ~random on MMLU and GSM8K; Hybrid LLM transfer fails when quality gaps do not correlate (r=0.06); AgentRouter 6-9% accuracy drop on an unseen framework; retraining needed when the pool or prices change; model releases move "both the capability gap and the price ratio" (Anthropic).
- Cache invalidation: top-level effort change and model change forfeit cached prefix (Anthropic, OpenAI, OpenRouter docs). Counter-evidence: Switchcraft's replay finds per-turn routing still cheaper than sticky when each model keeps its own cache for the conversation; TwinRouterBench with 5-minute TTL and write premium still finds 53% saving; DialRouter's learned policy under a no-reuse assumption becomes self-loop dominated. The result depends on turn spacing vs TTL, write premiums, and whether you can switch back to a still-warm cache. Neither side tested Anthropic-style 1.25x/2x writes with live traffic that I could find.
- Inconsistent persona/format across models: AgentRouter notes cheap-model output "forces the frontier model at the next step to reason over corrupted context"; Switchcraft: a stronger model's chain-of-thought "occasionally corrupts the structured tool-call output"; TwinRouterBench lists "out-of-distribution behavior under mixed-model histories, and tool-format mismatch across model families" as concerns (they price some of them in and rely on execution-verified labels). Thinking blocks/preserved thinking are model-specific (Anthropic per-message effort page: moving or removing the system message invalidates thinking blocks on models with preserved thinking). No paper I read measured tone/persona drift directly.
- Router overhead and spend: LiteLLM page notes classifier calls "can add cost and egress"; Router-R1 latency; Aurelio cost 42.2-54.5x the cheap-only routers per task on candidate cost, with no success gain over Always-Mid; rule-based UncommonRoute cost $172.56 vs $54.73 unrouted on TwinRouterBench dynamic track.
- Evaluation cost and label cost: Switchcraft labelling 99,125 queries on 8 models ~$2,300; breakeven ~600,000 routed queries; TwinRouterBench notes exhaustive verification needs n^m runs; RouterEval notes performance records are expensive; RouterBench is static replay (no real judge); every router needs per-distribution re-evaluation after each model release.
- Verbosity cost inversion: "nominally cheaper models can incur higher total cost due to token-intensive output" (Switchcraft §4.4, Table 4 chattiness); GPT-5-nano hidden reasoning tokens.
- Overthinking on the big model: timeout-cascade authors and Switchcraft report the stronger model sometimes loses (GLM-4.7 over-engineered fix; GPT-5.4 vs 5.3-chat), so "escalate = better" is not guaranteed.

### 5.5 Where papers and practitioners disagree (and where they agree)
- Granularity: HN practitioners (per repo): route by role; 2026 papers (Switchcraft, AgentRouter, TwinRouterBench, MTRouter): route per step/turn. Evidence for the papers is simulation or small single-benchmark; evidence for practitioners is self-report of cache loss, not measured. Vendors split: Anthropic and OpenRouter recommend sticking to one model per session, changing effort first; OpenRouter's router itself is designed that way.
- Cache: practitioners say mid-session change busts the cache; docs confirm for top-level effort/model; but vendors now ship cache-preserving per-message effort (Anthropic beta) and `configuration_update` (OpenAI GPT-6+). This weakens the "effort changes are expensive" part of the practitioner claim for current models while leaving "model switch" intact. The repo's gateway could expose per-message effort instead of banning mid-session effort change (design option; I did not check what the repo's gateway currently supports).
- Learned routers vs defaults: papers report gains over random/linear baselines; independent tests and RouterBench show little gain over a fixed mid tier or zero router. Practitioners mostly pick a fixed model per role, consistent with the sceptical papers.
- Cascades vs routers: timeout-cascade paper and Unified-routing paper both favour post-hoc signals where a verifier exists; practitioners did not (in repo) discuss cascades with test verifiers; Anthropic's advisor pattern is a cascade whose escalation is decided by the small model itself and "can help only when the executor consults it" (consultation rate collapsed in their measurements).
- Effort vs model: Anthropic says effort is often the better lever; most router papers predate effort controls (2023-2025 data) and never compare routing to simply lowering effort. TwinRouterBench's trained-router win is against unrouted Opus 4.6, not Opus at lower effort. This comparison is missing from the literature I read.
- Agreement: all sources say measure on your own distribution; routing value depends on workload difficulty mix (timeout cascade §VI-D "Characterize the task distribution before training routers"; Anthropic "Having a good evaluation set is the most important step").

### 5.6 Implications for the repo's gateway claim (for the chapter author, not a recommendation of implementation)
- Defensible: "per-subagent model setting, no automatic per-request router" matches (a) Anthropic's measured role-based guidance, (b) the independent evaluation and RouterBench showing weak router gains over fixed tiers, (c) cache costs.
- Add: a cascade hook is a different thing from a router and has the strongest paper support in agents when a verifier exists (tests, schema validation); needs a design note on cold restart and cache loss.
- Update: mid-session effort change is no longer inherently cache-breaking where per-message effort / configuration_update exists; the repo statement should carry a model-and-date qualifier.
- Unverified in these notes: the HN counts (45 authors) and whether any HN threads discuss cascades; not re-checked.
