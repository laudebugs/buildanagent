# Agents should make fast calls by default and escalate on a check that code can run, not on a router's guess

Every model call in an agent loop spends money, time and cache, and our guides give one rule for all three: "route by role at step boundaries, not per request" ([agent guide §8](../../guides/agent.md#8-cost-is-set-by-the-cached-preamble-and-the-per-ticket-budget-and-it-is-measured-per-resolved-ticket)). The SDK guide adds that the gateway should offer "no automatic per-request router" ([agent SDK guide §2](../../guides/agent-sdk.md#2-the-model-gateway-should-expose-one-versioned-streaming-method-over-a-transcript-the-sdk-owns)). Two things have changed in 2026 that neither rule mentions. Vendors now sell fast "decision models" that return typed probabilities, and Anthropic and OpenAI now document ways to change effort without losing the prompt cache. The owner asked what System 1 and System 2 models are, which fast models exist, when an agent should use each, how to combine them and what that changes in our repo.

Five findings answer the question, with every price, version and status as of November 2026:

1. The papers use "System 1" in four incompatible ways, and the label's own defenders now prefer to avoid it. The book should define a **fast call** as one that emits no reasoning tokens before its answer, a **slow call** as one that does, and a **decision model** as a fast call that returns typed probabilities.
2. Published regular prices of decision models run from $0.038 to $0.24 per million input tokens, with no output charge. Anthropic's and OpenAI's small models start at $0.10, and Google's cheapest general model at $0.25. Nearly every speed and accuracy figure is the vendor's own.
3. The strongest rules are to make fast calls by default, to spend slow calls on plans and irreversible steps, to escalate on signals that code can observe and to lower effort before changing models.
4. Routers beat random baselines but rarely a fixed mid-tier model. A cascade checked by tests saved 16.4% of GPU-hours on a coding benchmark, close to the 17.9% saved by a router that knew each task's true difficulty.
5. Switching models still rebuilds the cache, but changing effort need not, which qualifies one clause of our rule.

We propose one new chapter that also names decision models; five offline examples; one edit each to the agent guide, the SDK guide and the harness guide; two plan items (a gateway design question and an SDK cascade example); and one edit to the book's model-choice section. The owner's six decisions are in the last section. An agent should make fast calls by default and escalate on a check that code can run, not on a router's guess.

Every claim below is logged in the [fact-check log](fact-check-system-1-system-2-and-model-routing.md), section by section.

## The book should define a fast call by what it emits, and a decision model as a fast call that returns typed probabilities

**The papers use "System 1" in four incompatible ways, so the book needs its own definition.** Talker-Reasoner defines the two systems by role: a fast Talker agent that converses and a slow Reasoner that plans and calls tools, with Gemini 1.5 Flash behind the Talker and CoT-prompted Gemini 1.5 Flash calls behind the Reasoner ([Christakopoulou et al., §3.2 and §4.2](https://arxiv.org/abs/2410.08328)). SwiftSage defines them by model: a 770M-parameter flan-t5-large fine-tuned by imitation, against prompted GPT-4 ([Lin et al., §3.2–3.3](https://arxiv.org/abs/2305.17390)). Yu et al. define them by tokens: System 1 produces "a response given an input, without generation of intermediate tokens", and System 2 is "any approach which generates intermediate tokens" ([§1 and §3.1](https://arxiv.org/abs/2407.06023)). AdaptThink, Thinkless and Qwen3 define them by a mode switch inside one model, with a thinking mode and a non-thinking mode chosen by a flag or a first token ([Qwen3 §4.3](https://arxiv.org/abs/2505.09388); [AdaptThink §3–4](https://arxiv.org/abs/2505.13417)). A fifth use comes from vendors, not papers: TypeSafe calls a model "System One" when it "returns typed answers and probabilities" and does not write replies ([TypeSafe, System One](https://docs.typesafe.ai/concepts/system-one.md)).

| Paper or vendor | System 1 is | System 2 is | What decides |
| --- | --- | --- | --- |
| Talker-Reasoner | the conversational agent | the planner that holds tools and a belief state | a hand-written rule on the coaching phase |
| SwiftSage | a small fine-tuned model | prompted GPT-4 | four rules on observations |
| Yu et al. | no intermediate tokens | intermediate tokens or traces | the training recipe |
| Qwen3; AdaptThink; Thinkless | the non-thinking mode | the thinking mode | the caller's flag, or the model's first token |
| TypeSafe; Cloudflare; OpenAI | a model that returns typed probabilities | a generative or reasoning model | the application's thresholds |

**The papers also warn that the metaphor is loose, which is a reason to define terms by observable output.** Talker-Reasoner itself says "most cognitive processes are a mix of both kinds of reasoning" ([§1](https://arxiv.org/abs/2410.08328)). A 2026 study of GUI agents calls the parallel "functional rather than mechanistic", about "observable input–output behaviour" and not "the underlying computation" ([Halimeh et al., §2](https://arxiv.org/abs/2609.19843)). A survey of reasoning models says current ones "struggle to maintain this balance" between fast and slow ([Li et al., §6.2](https://arxiv.org/abs/2502.17419)). Because hosted models now reason adaptively, a model's name no longer says which path a call takes. Claude Haiku 5.5, for example, is the fastest Claude model yet supports adaptive thinking with a default effort of `medium` ([Claude Haiku 5.5](https://platform.claude.com/docs/en/models/haiku-5-5/overview)).

**We recommend three terms, defined by what a call emits.** A **fast call** is a model call that emits no reasoning tokens before its answer, either because the model never reasons or because its effort is set to the lowest level. A **slow call** emits reasoning tokens first. A **decision model** is a fast call whose answer is a typed value with a probability for each allowed option and no generated text. This follows Yu et al.'s operational test, adds the vendors' typed output, and lets one model sit on either path. The book should use "fast call", "slow call" and "decision model", one term for each concept, and name the "System 1" and "System 2" metaphor only as the next section describes.

## Where the framing comes from, and what it says about when a fast judgment can be trusted

**The labels "System 1" and "System 2" came from a 2000 paper on individual differences, and their own defenders now prefer to avoid them.** Stanovich and West wrote that "the two systems have simply been generically labeled System 1 and System 2", chosen to emphasize a prototypical view of two-process theories ([Stanovich and West 2000](https://pages.ucsd.edu/~mckenzie/StanovichBBS.pdf)).

Kahneman's Nobel lecture credits them with the labels and lists "fast" among System 1's features ([Kahneman 2002](https://nobelprize.org/uploads/2018/06/kahnemann-lecture.pdf)). Keren and Schul had found in 2009 that two-system models "currently provide little scientific advance" (p. 533). They argue that System 2 reasoning cannot run without System 1's associations, so the two are not isolable systems (pp. 539–540), and that much of the supporting evidence is "not diagnostic" because a one-system model predicts it equally well (p. 542) ([Keren and Schul 2009](https://doi.org/10.1111/j.1745-6924.2009.01164.x)). Evans and Stanovich later wrote that they "now prefer to avoid this terminology as it suggests (falsely) that the two types of processes are located in just two specific cognitive or neurological systems" ([Evans and Stanovich 2013](https://doi.org/10.1177/1745691612460685)). Their Table 1 lists "fast" and "slow" only as "typical correlates", and they call the belief that Type 1 causes bad thinking and Type 2 "necessarily" leads to correct responses "perhaps the most persistent fallacy". Melnikoff and Bargh report that critics find the two-types framework "lacks empirical support, contradicts well-established findings, and is internally incoherent", and they side with the critics. They say its untested assumption of two types has the consequence of "systematically thwarting scientific progress" and that Evans and Stanovich's 2013 reply did not go far enough ([Melnikoff and Bargh 2018](https://acmelab.yale.edu/sites/default/files/melnikoff_bargh_2018_mythical_number_2_0.pdf), abstract and opening sections).

**The book therefore avoids "System 1" and "System 2" as its own vocabulary and keeps the pair for naming the metaphor.** A definition by speed or model size would inherit the fallacy before any evidence about models arrived, so "fast call", "slow call" and "decision model" describe only what a call emits. The book quotes vendors, such as TypeSafe's "System One", as vendors.

**Nothing measured on people is evidence about models, so the human work yields analogies, ranked here by strength.**

1. **Satisficing as a cascade's stopping rule is the strongest.** Simon wrote that satisficing criteria "provide a stop rule to terminate search", so that "as soon as a satisfactory alternative is found, it can be accepted", and that aspirations "adjust upward" when reached easily and downward when missed ([Simon, "Satisficing"](http://iiif.library.cmu.edu/file/Simon_box00070_fld05370_bdl0001_doc0001/Simon_box00070_fld05370_bdl0001_doc0001.pdf), McGraw-Hill Encyclopedia of Economics). A cascade accepts the cheap answer when a check passes, and the check is the aspiration level. The analogy breaks in three places. The check is an external verifier, and its validity decides the whole system (rule 6 below). Simon allows optimal search only "for relatively routine and repetitive choices", the regime of high-volume routing, so a learned router is the alternative he cautioned about. And retrying on another model shares blind spots, our inference.
2. **Kahneman and Klein's two conditions work as a per-task-type eval test and make no claim about model size.** Intuition is skilled only where the environment gives "adequately valid cues" and the judge had "prolonged practice and feedback that is both rapid and unequivocal", and "high subjective confidence is not a good indication of validity" ([Kahneman and Klein 2009](https://gwern.net/doc/psychology/cognitive-bias/illusion-of-depth/2009-kahneman.pdf)). In their 2010 interview Klein adds that most corporate decisions fall short of high validity, and Kahneman says confidence follows "the quality and coherence of the story", not its validity ([McKinsey interview](https://www.mckinsey.com/capabilities/strategy-and-corporate-finance/our-insights/strategic-decisions-when-can-you-trust-your-gut), pp. 3–4). For an agent, the test asks whether each task type has stable cues and labelled outcomes, and it warns against routing on a fluent answer's confidence. A deployed model does not learn from use, and "easy" does not mean "valid", so the evidence is your own eval on that task type.
3. **Ecological rationality suggests a simple rule before a learned router.** A heuristic that searched fewer than half the cues beat logistic regression on 236 airline applicants, with the advantage largest when learning data was scarce. In 1,728 simulated environments logistic regression predicted better on average only at 1,000 training cases ([Luan, Reb and Gigerenzer 2019, Study 1, Study 2 and Table 3](https://pure.mpg.de/rest/items/item_3172441_6/component/file_3184539/content)). The evidence is one real dataset plus simulation. Neither strategy passed 63% accuracy on the real data, and the authors limit the claim to two strategies and one criterion. It concerns fitting from small samples, which a pretrained model's behaviour is not.
4. **Cynefin offers a vocabulary for choosing a call, a workflow or a loop, and it classifies situations, not models.** Snowden and Boone prescribe "sense, categorize, and respond" for simple contexts, "sense, analyze, and respond" for complicated ones, and "probe first, then sense, and then respond" for complex ones ([Snowden and Boone 2007](https://www.systemswisdom.com/sites/default/files/Snowdon-and-Boone-A-Leader's-Framework-for-Decision-Making_0.pdf)). Mapping them to a call, a workflow and a loop is our proposal, and we read no test of the framework.
5. **The pre-mortem is a plausible verifier step before an irreversible action, and Klein's own account shows that its mechanism is social.** Kahneman and Klein (2009) describe teams imagining the plan has failed and writing down why, and Klein calls it "a sneaky way to get people to do contrarian, devil's advocate thinking", which changes the dynamic "from trying to avoid anything that might disrupt harmony to trying to surface potential problems" ([McKinsey interview](https://www.mckinsey.com/capabilities/strategy-and-corporate-finance/our-insights/strategic-decisions-when-can-you-trust-your-gut), p. 7). The interview's only outcome claim is Kahneman's "guess" that plans get tweaked, not abandoned (p. 7), and we found no outcome study. A model critiquing its own plan shares that plan's blind spots, our inference; Kahneman's point that independent judgments "decorrelate errors" (p. 8) favours a separate context or model.
6. **Vocabulary transfer is the weakest.** Reading "fast" as cheap and error-prone and "slow" as reliable repeats the fallacy above. One structure survives: Evans and Stanovich, with Kahneman, favour a default-interventionist form, in which fast processing supplies a default that slower processing may override. That matches "answer with the cheap call, escalate on a trigger". Keren and Schul doubt even this strict hierarchy (p. 540), and Evans and Stanovich say intervention "is a function of several factors, including the metacognitive feeling of rightness in the initial intuition", so no single measurable trigger carries over.

A general small model can still write, call tools and explain. A decision model cannot: TypeSafe says Jev "is not trained to generate text", and its own page on the model's limits lists numeric precision, date comparison, indirection and adversarial content as weak spots ([model jaggedness](https://docs.typesafe.ai/model-jaggedness.md)). Fast hosts change speed and not capability: Groq and Cerebras serve open models such as gpt-oss at 500 to 3000 tokens per second by their own figures, and neither page we read lists a time to first token.

## Use a fast call by default, a slow call for plans and irreversible steps, and a decision model for typed checks, and escalate on a signal code can observe

**Seven rules cover the choice, and each rests on evidence of a different strength.** The papers measure math puzzles, one text simulator and one web benchmark. The vendors measure their own workloads. Neither has tested a rule on our agents, so each rule below names its evidence and what to measure before adopting it.

1. **Ask a decision model a question only when it has a fixed answer set and a person could answer it in a second.** TypeSafe's guidance is to "ask for one snap judgment per question": "Does this message convey urgency?" fits, while "analyze this message and determine the best course of action" "needs slow reasoning" ([primitives](https://docs.typesafe.ai/primitives.md)). Act on the probability of the option your code will take, and set the threshold from labelled data, because TypeSafe's calibration "does not guarantee that an individual answer is correct" ([System One](https://docs.typesafe.ai/concepts/system-one.md)). Microsoft gives the same advice for Decision-1: validate calibration on your own data wherever confidence sets a threshold ([Microsoft](https://techcommunity.microsoft.com/blog/azure-ai-foundry-blog/introducing-microsoft-decision-1-in-microsoft-foundry-for-decision-and-classific/4562742)). The evidence is vendor guidance, with no independent test.
2. **Keep anything code can compute in code.** TypeSafe's list of failures starts with arithmetic and says "keep the arithmetic in code", and tells you to extract date parts with a question and compare them in code ([model jaggedness](https://docs.typesafe.ai/model-jaggedness.md)). Following the rule costs nothing and applies to every fast model.
3. **Use a slow call for plans, and for the step whose error you cannot undo.** SwiftSage hands control to GPT-4 when the next action is critical, such as the final answer. It scored 84.68 on ScienceWorld against 36.43 for ReAct with GPT-4, and used 757 tokens per action against 1,855 to 2,983 for its baselines ([Lin et al., Tables 1 and 4](https://arxiv.org/abs/2305.17390)). Talker-Reasoner's "snap judgement Talker" answered a request for a multi-step plan without its Reasoner and was wrong ([§4.4](https://arxiv.org/abs/2410.08328)). Both results come from one simulator or one coaching case, and both switch rules are hand-written.
4. **Make a fast call by default, and do not spend reasoning on easy inputs.** An o1-like model used 1,953% more tokens than a conventional one to answer "2 plus 3", and its first solution was correct in more than 92% of cases ([Chen et al., §1–2](https://arxiv.org/abs/2412.21187)). AdaptThink's pilot found non-thinking mode "comparable" on MATH levels 1 to 3 and slightly better on level 1 ([§3.2](https://arxiv.org/abs/2505.13417)). Snell et al. found that extra beam-search budget degraded easy questions and that on the hardest "no method makes much meaningful progress" ([§5.3](https://arxiv.org/abs/2408.03314)). The three studies measured math on single model families, so they show how reasoning behaves and do not show what an agent should do.
5. **In an agent loop, raise effort only where your evals show a gain.** Rule 3 names the steps to try a slow call on, and this rule asks your evals to confirm each one. Cuadron et al. scored 4,018 SWE-bench Verified trajectories and found that more overthinking, meaning internal simulation in place of acting, tracked lower resolution (R² 0.892 for reasoning models, Figure 1 and Table 1). Yet o1 at high effort resolved 29.1% against 21.0% at low effort, for $1,400 against $400 ([§1](https://arxiv.org/abs/2502.08235)). More effort helped on average and cost 3.5 times as much, so the question is which steps earn it. Anthropic's advice agrees: "Use xhigh or max only where your evals show a quality gain" ([effort](https://platform.claude.com/docs/en/build-with-claude/effort)).
6. **Escalate on a signal code can observe, and do not trust the cheap model's own confidence.** SwiftSage escalates when five steps in a row earn no reward, when an action is invalid, when an action is critical and when an observation shows an exception ([§3.4](https://arxiv.org/abs/2305.17390)). The timeout cascade escalates on a timeout, an empty patch, a syntax error or failing tests ([Zhou et al., §IV](https://arxiv.org/abs/2611.24324)). A schema check alone is weak: in TypeSafe's scheduling cascade, 72 of the cheap model's 74 wrong answers passed it ([cookbook](https://docs.typesafe.ai/cookbooks/sde_cascade.md)). A model's own consultation is weaker still: Anthropic's executor consulted its advisor on none of 198 GPQA questions ([Anthropic](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)).
7. **Lower the effort before you change the model.** Anthropic's choosing guide says "Tuning effort is often a better lever than switching models" ([choosing a model](https://platform.claude.com/docs/en/about-claude/models/choosing-a-model)). On a SWE-bench Pro subset, Opus 5.5 at `low` solved about the same share as Sonnet 5.5 at its default, for about 7% more per solved task. Haiku 5.5 subagents behind Opus 5.5 at `medium` cut cost by 32% and the pass rate by about 4 points, "an alternative to lowering effort, not better" ([Anthropic](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)). These are Anthropic-internal results, labelled "directional" on the page.

**Neither fast nor slow thinking makes an agent safe against manipulation, so a decision model is not a security boundary.** TypeSafe says that "text that argues for its own classification can move the answer" ([model jaggedness](https://docs.typesafe.ai/model-jaggedness.md)), and its banking example gave a hesitant "yeah, go ahead I guess" a 0.99 for `approve_transfer` ([probability routing](https://docs.typesafe.ai/patterns/probability-routing.md)). A probability states intent, not consent. A slow call changes the weakness and does not remove it. In 21,600 simulated shopping decisions by six models, high reasoning effort halved the odds that an agent took a preselected default (from about 92% to 86% of choices) and raised the odds that it took the socially endorsed option by a factor of 1.71 (from about 96% to 98%) ([Halimeh et al., §5.1 and Table 1](https://arxiv.org/abs/2609.19843)). Approvals, sandboxes and credentials stay the book's job in [the chapters that cover them](../../../apps/manual/src/content/chapters/approvals-guardrails-and-injection.md).

## Five integration patterns work, and each one fails in a way you can name

**A fast-first cascade pays when the cheap model is right most of the time and a check code can run catches its mistakes.** TypeSafe's cookbook sends 1,000 NATURAL PLAN scheduling tasks to `gpt-6-luna`, checks each answer with six Jev questions (one per rule, true meaning the rule was broken), and escalates to `gpt-6.1-sol` at high effort when any rule's probability of being broken exceeds a threshold or the schema fails. Luna alone scored 92.6% at $0.16 per 1,000 tasks and Sol alone 98.1% at $1.89. The threshold sets both the cost and the accuracy. In the cookbook's sweep, a threshold of 0.29 escalated 13% of tasks and reached 96.5% for $0.49, and 0.18 escalated 54% and matched Sol's 98.1% for $1.31; its default of 0.7 is not in the sweep. The checks cost $0.04 per 1,000 tasks. TypeSafe ran this itself, so the numbers are a vendor claim, and the page adds that "the verifier has to cost far less than the reasoning rung, or the cascade saves nothing" ([cookbook](https://docs.typesafe.ai/cookbooks/sde_cascade.md)).

A paper on coding agents found the same shape with tests as the check. It ran GLM-4.7-Flash first and restarted on GLM-4.7 after a timeout, an empty patch, a syntax error or failing tests. That cut GPU-hours by 33.5% on easy SWE-bench Verified tasks and 16.4% across all tasks, close to the 17.9% of a router given the true difficulty labels ([Zhou et al., §V-C and §V-D](https://arxiv.org/abs/2611.24324)).

Vercel's AI Gateway ships the pattern for decision requests: a conditional such as `confidenceBelow: 0.6` reruns the question on a stronger model, "executes and bills both" stages and adds their latencies ([decision fallbacks](https://vercel.com/docs/ai-gateway/models-and-providers/decision-fallbacks)).

**A cascade fails when the check errs, when most tasks are hard, or when the restart discards context.** RouterBench's simulated cascade lost its gains "particularly when the error rate exceeds 0.2" for its judge ([Hu et al., §5.2–5.3](https://arxiv.org/abs/2403.12031)). Zhou et al. restart the large model "from the original task state", so a live system loses its cache on escalation. They ran one pass over one model pair and one benchmark, with simulated hybrid runs, and warn that a workload dominated by hard tasks "would approach a large-model-only system with extra overhead" ([§IV and §VI](https://arxiv.org/abs/2611.24324)). FrugalGPT's 98.3% saving on its headline-classification dataset used 2023 models whose costs differ "by up to 2 orders of magnitudes" and a scorer trained on labelled examples from the test distribution ([Chen et al., §1, §5 and Table 3](https://arxiv.org/abs/2305.05176)).

**A slow planner with a fast executor saves tokens when the plan is stable, and loses when the executor needs the planner mid-step.** On WebArena's 812 tasks, CogniWeb's fine-tuned Phi-3-mini reached 43.96% success with 393.89 output tokens, while a gpt-4o agent that always reasoned and reflected reached 46.06% with 1,503.83, "nearly four times" the length for "this modest 2%" gain ([Liu et al., §4](https://arxiv.org/abs/2508.05081)). The paper is a preprint under review. SwiftSage gets its saving another way: one call to the slow model returns a buffer of about five actions, so one expensive call funds several cheap steps ([Lin et al., §4.3](https://arxiv.org/abs/2305.17390)). Talker-Reasoner's version, where the Reasoner writes a belief to memory and the Talker reads it, lets the Talker answer from a stale belief, and the authors list when to consult the Reasoner as an open problem ([§5](https://arxiv.org/abs/2410.08328)). Anthropic's measurements are narrower: delegation to cheaper subagents "came out ahead in only two situations", routine work with a long cost tail and work larger than one context window ([Anthropic](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)). On a single dependent chain, the orchestrator's model alone at lower effort won every case Anthropic measured, though those measurements were on earlier models (the harder BrowseComp set and DeepWideSearch).

**Per-role models give the same split without a classifier, and the evidence for them is practice and vendor measurement.** Cloudflare's own platform post describes the roles: "a fast, cheap model to classify a user's message; a large, reasoning model to plan its actions; and a lightweight model to execute individual tasks" ([Cloudflare](https://blog.cloudflare.com/ai-platform/)). Anthropic names two patterns, an executor that escalates to an advisor and an orchestrator that delegates to cheaper workers, and supports up to 25 subagents at a time ([Anthropic](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)). Our repo's own research reports that about 45 Hacker News authors route by role ([agent guide §8](../../guides/agent.md#8-cost-is-set-by-the-cached-preamble-and-the-per-ticket-budget-and-it-is-measured-per-resolved-ticket)). Role routing fails when a role's difficulty varies by input, as when a "reader" role meets one hard document, and nothing escalates it.

**One model with an effort or thinking budget is the cheapest change to try first.** Qwen3's `/think` and `/no_think` flags and its thinking budget put the choice in the caller's hands ([§4.3](https://arxiv.org/abs/2505.09388)). AdaptThink cut a 1.5B model's response length by 50.9% on GSM8K, 63.5% on MATH500 and 44.7% on AIME 2024 and raised accuracy by 4.1, 1.4 and 1.6 points ([§1](https://arxiv.org/abs/2505.13417)). Thinkless reports a reasoning mode used for only 25% of Minerva Algebra samples at about one-third of the tokens, within 1% of full accuracy, and says an external router "struggles to recognize" the difficulty of AIME for the model it routes to ([§4.2](https://arxiv.org/abs/2505.13379)). Both trained small models on math. Hosted models fail in other ways: Anthropic calls effort "a behavioral signal, not a strict token budget", and at `low` the model skips checks in long agent prompts ([effort](https://platform.claude.com/docs/en/build-with-claude/effort)).

**Distillation moves a slow method's output into a fast call when the task is a stable rewrite or judgment, and fails when the tokens are the computation.** Yu et al. fine-tuned Llama-2-70B-chat on its own filtered slow answers. Last-letter concatenation rose from 30.0% to 98.0% with 25.5 tokens, a judge's agreement with humans on OASST2 from 49.1% for the slow method to 58.4% distilled with four output tokens against 2,117.8, and chain-of-thought math on GSM8K collapsed from 52.77% to 7.13% ([Tables 1, 3 and 4](https://arxiv.org/abs/2407.06023)). The authors write that "System 2 Distillation of CoT does not work well". Perplexity trained its Decider Flash by distilling its larger Decider into a Qwen3.5-4B model, a vendor example of the same move ([Perplexity](https://www.perplexity.ai/hub/blog/perplexity-decider)).

## Routers beat random baselines but rarely beat a fixed mid-tier model or a cascade with a check, and cache accounting decides whether they pay

**The older papers measure routers against weak baselines, and the best ones say so.** RouteLLM cut GPT-4 calls to 1/3.66 of a random router's number at 95% of GPT-4's quality on MT Bench. On MMLU, its routers trained only on Chatbot Arena data performed "at the level of the random router" until about 1,500 labelled in-domain examples were added ([Ong et al., §5.3–5.4](https://arxiv.org/abs/2406.18665)). RouterBench found that "none of the routing algorithms significantly outperform the baseline Zero router", a fixed mix of models that ignores the query ([Hu et al., §5.3](https://arxiv.org/abs/2403.12031)). The unified routing and cascading paper reports gains up to 8% on RouterBench, but only "up to 1.2%" with noisy quality estimates on real classification tasks, and on SWE-bench "the routing strategy does not outperform the trivial baseline" ([Dekoninck et al., §5](https://arxiv.org/abs/2410.10347)). An independent 2026 test of four open-source routers on 290 frozen tasks found that three emitted near-constant tiers, and that "Always-Mid matches Aurelio exactly on three benchmarks and within 0.003 on the fourth" ([Kumar and Saminathan, abstract](https://arxiv.org/abs/2608.14641)). The sample was small, set by API budget and not by a power calculation, and the authors scope the finding to their configurations.

**Newer agent-specific routers report large savings on narrow, checkable tasks, and the largest numbers come from the weakest evidence.** Switchcraft routes each tool call with a calibrated DistilBERT classifier and reached 78.3% accuracy at 59% lower cost than the best single model on six function-calling benchmarks, partly because "larger models do not consistently outperform smaller ones on tool-use tasks" ([Agarwal et al., abstract and §4](https://arxiv.org/abs/2605.07112)). TwinRouterBench ran a trained per-step router in a live SWE-bench Verified harness: 75 of 100 tasks resolved for $25.66 in API cost against 74 for $54.73 without routing, while a rule-based router resolved 73 for $172.56, three times the unrouted cost ([Yang et al., Table 3](https://arxiv.org/abs/2605.18859)). The 100 tasks were 18 Astropy and 82 Django instances, "not a random sample", and the benchmark's repository belongs to Commonstack, which also publishes the router it tested. AgentRouter reports 71.8% lower cost at 97.3% of frontier quality, but on the authors' own benchmark with GPT-4o and Llama-3 models and, as far as we found, with no cache accounting ([Paul and Nandy, Table 1](https://arxiv.org/abs/2609.22951)). The cascade from the previous section had the most honest result: a router given the true difficulty labels saved 17.9%, against 16.4% for the cascade that only watched timeouts and tests ([Zhou et al., §V-D](https://arxiv.org/abs/2611.24324)).

**Three production routers pick by request text, and none publishes an independent test.** OpenRouter's Auto Router has "a fast decision model" rate eleven aspects of a request, then weighs the rating against price, cache status and benchmark results ([OpenRouter](https://openrouter.ai/docs/guides/routing/routers/auto-router)). LiteLLM's Auto Routing, in beta, scores a request on seven dimensions with zero API calls by default and can call a small model or Jev instead; its `session_affinity` option is off by default ([LiteLLM](https://docs.litellm.ai/docs/proxy/auto_routing)). Cloudflare's Auto Router, in public beta since 30 September 2026, classifies the recent messages into 14 task categories and rates complexity, ambiguity, stakes and context dependence from one to five. On Cloudflare's internal 97-task benchmark it scored 86.6% at $2.10, against 96.6% at $5.91 for Opus 5.5 and 84.2% at $2.64 for GPT-6 Sol ([Cloudflare](https://blog.cloudflare.com/auto-router/)). That is 35% of Opus's cost for ten points less success, a trade the router's owner should make knowingly, and the table is Cloudflare's own. Vercel's decision fallbacks, covered above, are the one gateway feature that escalates on a confidence threshold.

**Whether switching pays depends on the cache, and the vendors now document a split between effort and model.** Anthropic says that changing the top-level effort value between requests "can invalidate all or part of the prompt cache", and offers a beta per-message effort, a `role: "system"` message carrying `output_config.effort`, that "leaves everything before it unchanged, so the cached prefix still matches" ([effort](https://platform.claude.com/docs/en/build-with-claude/effort); [per-message effort](https://platform.claude.com/docs/en/build-with-claude/effort-per-message)). OpenAI offers the same on supported GPT-6 and later models through a `configuration_update` input item ([prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)). A model change still rebuilds the cache. OpenRouter says that switching models "costs extra while the new model rebuilds the prompt cache", so its router "favors a change in reasoning effort when that's enough" ([OpenRouter](https://openrouter.ai/docs/guides/routing/routers/auto-router)). Cloudflare says that switching models "throws the cache away" and charges a switching penalty that grows with context ([Cloudflare](https://blog.cloudflare.com/auto-router/)).

**Two papers price the cache and find that per-turn routing can still win, under assumptions a deployment must check.** Switchcraft replayed multi-turn tool-calling traces with a cache per model and published cache-read prices: a 90% discount for OpenAI models and 83% for Kimi-K2.5, with none assumed for Qwen-3.5-9B. Caching cut per-turn routing's cost by 65%, staying on the current model cost 7.3% more at similar accuracy, and routing only the first turn saved 19% but lost 5.7 points of accuracy ([Agarwal et al., §4.6](https://arxiv.org/abs/2605.07112)). Its replay assumes "a separate cache for each model per conversation", and the appendix we read prices cache reads only: we found no write premium or expiry in it. The multi-turn queries come from BFCL, 150 of them in the test set. TwinRouterBench bills cache writes on tier switches and after a five-minute expiry, and its trained router still came out 53.1% cheaper ([§5.2 and §6](https://arxiv.org/abs/2605.18859)). We found no paper that tests Anthropic's write premiums, 1.25 times for five minutes and 2 times for an hour, against live traffic ([prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). No paper we read compares routing with simply lowering effort, which is Anthropic's first recommendation.

## The repo's routing rule holds for model changes and needs one qualifier for effort changes

**Our guides say three things about routing, and the new evidence supports two of them as written.** The SDK guide says the gateway "should therefore offer a per-subagent model setting and no automatic per-request router", because about 45 Hacker News authors route by role and report that changing the model or effort mid-session busts the cache ([agent SDK guide §2](../../guides/agent-sdk.md)). The agent guide repeats it: "Route by role at step boundaries, not per request" ([agent guide §8](../../guides/agent.md#8-cost-is-set-by-the-cached-preamble-and-the-per-ticket-budget-and-it-is-measured-per-resolved-ticket)). The harness guide allows "effort changes, model changes and context edits" only "at session or subagent boundaries" ([harness guide §3](../../guides/agent-harness.md)). The rules against an automatic router and for roles hold: RouterBench, the independent four-router test and Anthropic's measured advice all point the same way, and the one live agent test with a large saving, TwinRouterBench, also found a rule-based router that tripled cost.

| Repo statement | Verdict | Evidence | Change to propose |
| --- | --- | --- | --- |
| No automatic per-request router in the gateway | Holds, with a scope | Routers rarely beat a fixed mid-tier model; per-call routing reports gains only on checkable tool calls (Switchcraft) and one live SWE-bench run | Keep the default. Say "measure before adding one", and name Switchcraft's conditions: a checkable property and a calibrated classifier |
| Route by role at step boundaries | Holds | Anthropic: delegation won in two situations; effort first otherwise | Add the cascade hook below as a third option, because role routing cannot escalate one hard input |
| Changing the model mid-session busts the cache | Holds | OpenRouter and Cloudflare both document a rebuild | None; add the sources |
| Changing effort mid-session busts the cache | Needs a qualifier | True for top-level effort. Anthropic's beta per-message effort and OpenAI's `configuration_update` keep the prefix | Say "top-level effort", and let the gateway express a per-message effort on models that support it |
| Effort and model change only at session or subagent boundaries | Too strict for effort | Per-message effort changes take effect from the next user turn without a rebuild | Allow it, logged like a model change, once the gateway can send it |
| Book: start with the most capable model, then try smaller ones | Holds, with a second option | Anthropic's guide gives two starts, efficiency-first from Haiku 5.5 and capability-first from Opus 5.5 | Add the effort step before the model swap (rule 7) |

**The qualifier on effort needs care, because it holds only on named models and platforms.** Anthropic's per-message effort is a beta that works on the latest Claude models, not on Managed Agents, and two settings reject a mid-conversation change with a 400 error: Sonnet 5.5 with `between_tools` thinking and Haiku 5.5 with thinking `disabled` ([per-message effort](https://platform.claude.com/docs/en/build-with-claude/effort-per-message)). Moving or removing the system message also invalidates thinking blocks on models with preserved thinking. OpenAI's item exists only "on supported GPT-6 and later models". The repo's rule should therefore read: change effort through the provider's cache-preserving mechanism where one exists, and otherwise only at a boundary.

**Our gateway cannot yet express the new mechanism, and our SDK can already switch models per call.** The gateway README documents `providerOptions.openaiChat.extraBody` for fields such as `reasoning_effort`, and a search of `packages/gateway/src` and `packages/sdk/src` found "effort" only in the OpenAI chat adapter, so a typed effort option and a per-message effort message do not exist. The SDK's `shouldStop` hook can turn a text answer into a re-ask with `{ continue }`, and its `beforeModelCall` hook may return a `model` from `createModel()` for that call, so a cascade needs no new SDK feature ([hook-checks.ts](../../../packages/sdk/src/hook-checks.ts)). The book already separates the two meanings of "router": [Choosing the shape](../../../apps/manual/src/content/chapters/choosing-the-shape.md) uses it for input routing to specialists, where a classifier or a regular expression picks a branch. The new chapter should call the other thing a **model router**, and call a check-then-escalate loop a **cascade**.

**Four additions follow, and the owner's decisions in the last section carry them.** The gateway design question is decision 4, the cascade example is the first todo of decision 2, the mention of decision models belongs to the chapter in decision 1, and the guide wording is decision 3. First, the gateway plan should list a typed `effort` option and per-message effort as a design question, with the model and platform limits above. Second, the SDK plan should list a cascade example on `shouldStop` and `beforeModelCall`, because Zhou et al. and TypeSafe both show the pattern works with a code-checkable verifier. Third, the tools chapter or the new chapter should name decision models as a way to answer fixed-set questions without an LLM loop, with the TypeSafe limits from rule 2. Fourth, the guides should replace "about 45 authors" with the measured evidence beside it, since the 45 are self-reports of cache loss that the vendors' documentation now confirms for model changes and partly contradicts for effort.

## One new Part II chapter should follow Events and hooks and teach the seven rules through five offline examples

**The chapter should be "Fast and slow calls: effort, decision models, cascades and when a router pays", placed after Events and hooks.** The chapter needs the gateway's cache model ([The model gateway](../../../apps/manual/src/content/chapters/the-model-gateway.md)) and the hook that can swap a model per call ([Events and hooks](../../../apps/manual/src/content/chapters/events-and-hooks.md)), so it cannot sit earlier in Part II. In `apps/manual/src/outline.ts`, the entry goes between `events-and-hooks` and `the-session-log-and-context`:

```ts
{
  slug: "fast-and-slow-calls",
  title: "Fast and slow calls: effort, decision models, cascades and when a router pays",
  opening: "scenario",
},
```

The neighbours open with `question` and `analogy`, so the `scenario` opening breaks no consecutive-type rule, and it would be the fourth `scenario` of 19 chapters, under the cap of five (a quarter of 19, rounded up). `check:book` enforces both rules ([outline.ts header](../../../apps/manual/src/outline.ts)).

**Five sections should carry the seven rules, each headed by its conclusion.**

1. **A call is fast or slow by what it emits, and a decision model is a fast call with typed answers.** The four uses of "System 1" in the papers, the three terms from this report and the Haiku 5.5 example of one model on both paths. Opens on a scenario: an agent spends a reasoning model's budget confirming a refund's order id.
2. **Lower the effort before you change the model, and change it without losing the cache.** Rules 4, 5 and 7, Anthropic's cost-per-solved-task measure, top-level against per-message effort, and the model and platform limits.
3. **Ask a decision model fixed-set questions, keep arithmetic and consent in code, and measure calibration on your own data.** Rules 1, 2 and the security paragraph, with TypeSafe, Clef and OpenAI's API as three wire shapes of one idea.
4. **A cascade escalates on a check that code can run, and a weak check costs more than it saves.** Rules 3 and 6, the TypeSafe and timeout-cascade numbers as vendor and paper evidence, and the planner-and-executor split.
5. **A router needs a baseline it can beat, a priced cache and a result on your own traffic.** The routing section above in one page, ending on the rule "pick a fixed tier first, then measure what a router adds".

Exercises ask the reader to change a threshold and predict which tasks escalate, as the gateway chapter does for its budget.

**Five worked examples would give the chapter its listings, each offline with scripted models and each stated as one todo.**

1. **`packages/sdk/examples/14-cascade-with-check.ts`: a cascade whose check decides what the cascade costs.** Run ten scripted scheduling tasks through a fast scripted model priced as Haiku 5.5 ($0.10 and $0.50 per million tokens) and a slow one priced as Sonnet 5.5 ($2 and $10), each task using 2,000 input and 200 output tokens, so a fast call costs $0.0003 and a slow call $0.006. The fast model gets seven answers right, two schema-invalid and one valid but wrong. A `shouldStop` hook runs the check on the fast model's text answer and, on a failure, returns `{ continue: <re-ask> }`. A `beforeModelCall` hook then returns the slow `model` with `messages` set to the original task only, so the slow call sends a fresh 2,000-input-token prompt and costs $0.006. The pair runs twice: with a schema-only check, it escalates two tasks, accepts the wrong answer and costs $0.015; with a schema-plus-rule check, it escalates three, ends ten of ten correct and costs $0.021, against $0.06 for slow-only. Done when the test asserts those counts and costs, and a comment says the scripted counts stand in for TypeSafe's 72 of 74 finding and prove no real model.
2. **`packages/sdk/examples/15-decision-gate.ts`: thresholds that scale with risk, over a decision-model stand-in.** Define a typed `DecideClient` with `predicate`, `choice` and `score` answers, implemented by a deterministic table, and gate three tool calls: a read-only lookup acts above 0.67, a refund acts above 0.93 and otherwise asks for confirmation, and a transfer always asks. Assert that a scripted 0.99 for "yeah, go ahead I guess" on the transfer still reaches the confirmation step, that a question referring to an earlier answer is rejected so the code must send a second request, and that a date comparison runs in code after the client extracts its parts. Done when a comment states that the table mimics the request shape of TypeSafe, Clef and OpenAI's Decisions API and measures nothing.
3. **`packages/gateway/examples/05-switch-or-stay.ts`: what a model switch costs under a per-model cache.** Price a ten-turn session that adds 2,000 input tokens a turn, with 200 output tokens a turn, at Sonnet 5.5's cache write ($2.50) and read ($0.10) rates and Haiku 5.5's ($0.125 and $0.01), with the output prices of the first example, one cache per model, no expiry, and output tokens kept out of the cached context. By this report's hand calculation the totals are $0.0790 for Sonnet throughout, $0.0044 for Haiku throughout, $0.0680 for Haiku for five turns then Sonnet, $0.0406 for Sonnet then Haiku, and $0.0616 alternating each turn, starting on Sonnet ($0.0671 when Haiku takes turn 1). A second run with a gap beyond the five-minute TTL before every turn must show every model rewriting its whole prefix. Done when the test reproduces these numbers from the catalog's rates and the comment names the Switchcraft assumption (a separate cache per model) so a reader sees that the alternation total depends on it and on which model takes turn 1.
4. **`packages/sdk/examples/16-cost-per-solved-task.ts`: rank candidates by cost per solved task and say "within noise".** Given scripted pass-fail results for 40 tasks on four candidates (Haiku 5.5, Sonnet 5.5, Opus 5.5 at `low`, Opus 5.5 at `medium`) with token counts and catalog prices, print cost per solved task and mark any pair whose paired pass-rate difference is under two standard errors as tied. Assert that a lower-effort large model beats a smaller model on cost per solved task when the scripted numbers say so, and that a tied pair is not ranked. Done when a comment says the example reproduces Anthropic's method and none of its numbers.
5. **`packages/sdk/examples/17-plan-buffer.ts`: a slow planner's buffer funds several fast steps, and a stuck rule takes control back.** A scripted slow model returns a buffer of five actions that a scripted fast executor runs as tool calls. Control returns to the slow model when the buffer empties, when an action is invalid or when three steps in a row earn no progress (a smaller K than SwiftSage's five, so the test stays short). Assert that a ten-step task uses two slow calls where step-by-step slow use needs ten, and that an injected invalid action triggers a third slow call. Done when a comment says SwiftSage's evidence is one simulator with hand-written rules.

## What this report could not confirm

**Six limits bound the evidence, and each is stated where it applies.**

1. Every decision-model latency, accuracy and cost figure comes from the vendor that sells the model, and the vendors' leaderboards contradict one another, so the book should present them as claims. No independent test of any decision model's calibration came to our attention.
2. No paper we read tests Anthropic's cache-write premiums with live traffic, and none compares routing with lowering effort.
3. We did not confirm a price for Perplexity's or Baseten's models, or whether TypeSafe offers open weights.
4. On the human research, we did not read Klein's 2007 pre-mortem article, so the pre-mortem rests on his interview and on Kahneman and Klein's paper. We read Keren and Schul (2009), the McKinsey interview and Wack's second 1985 article in full, from copies the owner supplied, and Wack's first article only as an abstract. The report leaves scenario planning out because it informs none of the chapter's decisions.
5. We read Boyd's 1976 paper, which contains no OODA loop, and none of his later briefings, so the report says nothing about OODA. We also read only the first half of the Stanford Encyclopedia entry on bounded rationality.
6. We read the long papers' appendices in part, so a claim that rests on an unread appendix is marked as unconfirmed in the fact-check log.
