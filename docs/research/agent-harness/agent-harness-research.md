# Build an agent harness around one tree-shaped log, three separate safety decisions and one protocol

- **Status:** research synthesis for todo G2a, 2026-11-18. The [build-guides plan](../../plans/build-guides.md) defines the scope; the guide G2b will be written from this file.
- **Versions checked (as of November 2026):** Pi `@earendil-works/pi-coding-agent` 1.5.2, `@anthropic-ai/claude-agent-sdk` 0.3.327, `@openai/agents-core` 0.21.0, `ai` 7.0.162, `langchain` 1.6.1 with `@langchain/langgraph` 1.6.0, and shallow clones of Codex `main` at `4389a52`, OpenHands software-agent-sdk 1.62.0 at `7dd877e`, Cloudflare `agents` 0.33.0 / `@cloudflare/think` 0.23.0 at `1a450e7`, OpenCode at `79bd2c6` and mini-swe-agent 2.4.6 at `04d809c`.
- **Sources:** five research notes in [`notes/`](notes/) cite file and line ranges in `verify/*/node_modules/`, in the clones, and URLs. I keep their citations or cite "(notes/<file>.md §N)" where the note holds the primary reference. Corrections are logged in [fact-check.md](fact-check.md).
- **Scope:** the harness layer as [build-guides §2](../../plans/build-guides.md) defines it: the runtime that hosts the loop for real work. The loop, tool schemas, the six interceptors and the test model belong to the SDK layer, and this file links to the [SDK synthesis](../agent-sdk/agent-sdk-research.md) for them rather than repeating them.

The harness is the part of an agent stack that moves results most. Harness choice moved Pass@1 by up to 24.3 points across seven harnesses on one model in Claw-SWE-Bench ([arXiv 2606.12344](https://arxiv.org/abs/2606.12344) v2, §6.2; the 27.4 points that the introduction of [arXiv 2610.04433](https://arxiv.org/html/2610.04433) cites are from v1), and with model, tasks and prices held fixed, harnesses differed by up to 3× in cost ([arXiv 2610.04433](https://arxiv.org/abs/2610.04433), abstract; notes/observability-and-evals.md §7). Our [SDK synthesis](../agent-sdk/agent-sdk-research.md) settled the loop: one in-process streaming function whose pauses are log states. This file answers the five G2a questions about what surrounds that loop: session formats (§1), compaction (§2), permissions, approvals and sandboxes (§3), interfaces and extensions (§4), and observability and evals (§5). Section 6 turns the evidence into eighteen design decisions, and §7 shows where they revise our [8-layer reference architecture](../agent-sdks-and-harness-design.md#a-reference-architecture-in-eight-swappable-layers) and the SDK synthesis. Sections 8 and 9 list the gaps and the questions Round P must settle. My conclusion is that our harness should keep one append-only, tree-shaped session log as its only source of truth. Around that log, it should add context layers from the cheapest upward, keep the permission pipeline, the sandbox and the credential boundary as three separate components, expose one typed protocol under every interface, and judge every change by cost per task as well as pass rate against mini-swe-agent.

## 1. Sessions belong in an append-only tree of typed entries, with HEAD, locks and pauses made explicit

**Five of the seven harnesses store sessions as an ordered log of typed entries, and four of them link the entries into a tree.** Pi, the Claude Agent SDK, OpenHands, Cloudflare and Codex all store model-visible items as an ordered log, and all but Codex link entries into a tree with `id` + `parentId`; Codex references entries by ordinal (notes/sessions-and-storage.md §1, §2, §5, §6, §7; `CX/codex-rs/protocol/src/protocol.rs:3534-3545`). Compaction summaries, branch summaries and context edits then become ordinary entries that a context builder interprets. LangGraph and OpenAI are the outliers. LangGraph stores a snapshot of every channel per super-step plus per-task pending writes (`LGC/base.d.ts:9-51`). OpenAI splits state into a flat, mutable `Session` item list and a versioned `RunState` blob for paused runs (`OA/agents-core/dist/memory/session.d.ts:22-80`; `runState.d.ts:20-80`).

| Harness | Storage unit | Branch in place | Resume point | Multi-process | Pending approval survives restart |
|---|---|---|---|---|---|
| Pi | JSONL line, `id` + `parentId` | yes (`/tree`) | any entry; leaf = last line | no lock | no (extension may store `custom` state) |
| Claude SDK | JSONL line, `uuid` + `parentUuid`; `last-prompt.leafUuid` as HEAD | no (truncating resume) | any chain uuid (`resumeSessionAt`) | none; store orders by commit time | `defer` only; `canUseTool` dies with the process |
| OpenAI | item list + `RunState` | no | paused run | optional transaction with suffix compare-and-swap | yes, in `RunState` |
| LangGraph | checkpoint + writes | `updateState` fork | super-step boundary | none in the interface | yes, as an interrupt write |
| Codex | rollout JSONL + SQLite index | no | turn; revert by new file | cross-process writer lock | no ("Transient, non-durable") |
| OpenHands | one file per event + state JSON | yes | event; unmatched actions | `flock` (unsafe on NFS) | yes (`waiting_for_confirmation`) |
| Cloudflare | Durable Object SQLite rows | yes | latest leaf | single writer per object | yes (`approval-requested` part) |

Sources: notes/sessions-and-storage.md §8 and the citations under §1–7.

**The tree is right, but Pi leaves three holes that other harnesses show how to close.** First, Pi does not persist HEAD: `_buildIndex` sets the leaf to the last entry in file order (`PI/session-manager.js:733-753`), so a `/tree` jump with no later append is lost on reload. OpenHands persists `leaf_event_id` instead (`OH/.../conversation/state.py:249-262`), and the Claude CLI writes `last-prompt` entries whose `leafUuid` names the current entry (notes/sessions-and-storage.md, Addendum). Second, Pi takes no lock on session files (`PI/session-manager.js` imports none), while Codex's `WriterLockCoordinator` returns `WouldBlock` to a second writer (`CX/codex-rs/rollout/src/writer_lock.rs:1-3, 20-46`) and OpenHands resyncs and rejects unknown parents under a file lock (`OH/.../event_store.py:315-378`). Third, Pi rewrites the original file when it migrates a version on load (`PI/session-manager.js:718-731`), whereas Codex stages, verifies and publishes a migrated history atomically with a `.pending` journal (`CX/.../thread-store/src/local/rollout_migration.rs:1-10`). No harness supports two concurrent writers on one session; every design assumes one writer, enforced by a lock or an actor (notes/sessions-and-storage.md, Unresolved gaps).

**Codex shows how to revert and fork without copying or truncating history.** Revert creates "a new immutable rollout file. Old rollouts stay intact. The new file references the retained prefix, and the only mutable cutover is the existing SQLite rollout-path pointer" (`CX/codex-rs/thread-store/src/local/revert_thread.rs:15-18`). Forks reference a parent prefix by ordinal (`CX/codex-rs/protocol/src/protocol.rs:3534-3545`). Codex's SQLite database is an index for paging and listing, not the log (`CX/codex-rs/state/migrations/0001_threads.sql:1-25`). Cloudflare's rows, by contrast, are mutable (`update`, `deleteMessages`), a choice driven by Durable Object pricing, where "rows written cost ~1000× rows read" (`CF/packages/agents/src/sessions/core.ts:6-9`).

**A real Claude Code transcript confirms the tree, the explicit HEAD and non-destructive compaction, and adds two details worth copying.** The sessions note inspected the structure of one CLI 2.1.327 transcript, recording field names, entry types and link counts only; the format is internal and undocumented, so this is one sample from one version (notes/sessions-and-storage.md, Addendum). Its `user`, `assistant`, `attachment` and `system` entries form a `uuid`/`parentUuid` tree with two roots, while `last-prompt`, `mode` and `queue-operation` entries are session-level bookkeeping. The only branching comes from parallel tool calls: the CLI writes one entry per content block, so an assistant `tool_use` entry has two children, the next `tool_use` block and its own `tool_result`. Compaction writes a `system` entry with subtype `compact_boundary`, `parentUuid: null` and a `logicalParentUuid` across the cut, with `compactMetadata` recording `trigger`, `preTokens`, `postTokens` and the preserved segment, and every earlier entry stays in the file. Each subagent writes its own `subagents/agent-<id>.jsonl` with `isSidechain: true` plus a `.meta.json` naming the spawning `toolUseId`, and large tool results spill to a `tool-results/` folder beside the transcript. Entries also record `cwd`, `gitBranch`, `permissionMode`, `sandboxed` and approval outcomes, so a resume can rebuild where and under which permissions each turn ran. I re-checked the entry types, the single `compact_boundary` with a null parent and a `logicalParentUuid`, the `leafUuid` targets and the `subagents/` and `tool-results/` folders on this session's transcript (see [fact-check.md](fact-check.md) row 23).

**Pauses must be entries, not callbacks, because a callback dies with its process.** Codex lists `ExecApprovalRequest`, `ApplyPatchApprovalRequest` and `RequestPermissions` as "Transient, non-durable events" (`CX/codex-rs/rollout/src/policy.rs:161-205`), and Claude's `canUseTool` is an in-process callback (notes/sessions-and-storage.md §2). OpenHands, Cloudflare and Claude's `defer` hook decision survive a restart because the pause is data (`OH/.../state.py:880-886`; `CF/packages/think/src/think.ts:16954-16960`; `CL:1071, 6429`). OpenAI binds approvals to "canonical invocation fingerprints" since `RunState` 1.18, and since 1.20 it checkpoints session appends made during approval resume, because history and run state live in two stores that can diverge (`runState.d.ts:56-75`). That divergence is the strongest argument for one store.

**Replay needs two named modes, because "time travel" in LangGraph re-executes.** Invoking LangGraph with an old checkpoint re-runs later nodes, and "LLM calls, API requests, and interrupts fire again and may return different results" (`LGD/use-time-travel.mdx:14-22`). A recorded log supports deterministic *playback* from stored entries and a separate *re-run from entry X*, which branches. Playback reproduces the exact prompt only if the log stores the model id, thinking level and system/tool checkpoint, as Pi's entries do (`docs/reference/pi/source/coding-agent/session-format.md:78-207`).

**Recommendation.** Use a JSONL file of typed entries with ids and parent ids as the only source of truth; persist HEAD; lock per session; migrate into a new file; store pauses as `approval_requested` and `approval_resolved` entries; bound entry size at write time (Codex truncates persisted tool output at 64 KiB, `CX/codex-rs/rollout/src/policy.rs:16-19`); and put the store behind a small interface modelled on Claude's `SessionStore` (`append` idempotent by entry id, `load`, `list`, `delete`, `CL:7266-7348`). Write the user entry durably before the first model call, because LangGraph cannot tell "never accepted" from "lost" (`LGD/checkpointers.mdx:690-696`).

## 2. Context policy works as cheap layers first, with summarization as the expensive fallback

**Pi, Cloudflare Think and Codex compact at more than one trigger point, and all three keep about 20,000 recent tokens verbatim.** Pi checks `contextTokens > contextWindow - reserveTokens` (16,384) before a prompt and after tool results, and retries once on overflow (`PI/compaction/compaction.js:55-56`; `PI/agent-session.js:478-486, 2529-2566`). Cloudflare Think compacts after an append, optionally before a step at 90% of `maxInputTokens`, and optionally once after an overflow error (`CF/packages/think/src/think.ts:3039-3100`). Codex compacts before a turn at 90% of the window by default and mid-turn after a sampling step (`CX/core/src/session/turn.rs:258-305, 787-818`; `CX/protocol/src/openai_models.rs:583-594`). Pi, Cloudflare and Codex (for user text) each keep about 20,000 recent tokens verbatim (`PI/compaction/compaction.js:56, 334-373`; `CF/.../compaction-helpers.ts:135-148`; `CX/core/src/compact.rs:69`).

| Harness | Between turns | Mid-turn | On provider overflow | Originals kept |
|---|---|---|---|---|
| Pi 1.5.2 | window − 16,384 | same check in `prepareNextTurn` | one compact-and-retry | yes, in the tree |
| Claude SDK 0.3.327 | CLI auto-compaction, policy window (e.g. 200K on 1M models) | not exposed | not documented | yes, on disk |
| Codex `4389a52` | 90% of window; async at 65% | after a sampling step | no retry on the main path | `CompactedItem` in the rollout |
| Cloudflare Think 0.23.0 | `compactAfter(threshold)` | opt-in at 90% | opt-in, one retry | yes, as overlays |
| OpenHands 1.62.0 | > 240 events or `max_tokens` | condenser on every step | `CondensationRequest` | yes, as a tombstone event |
| OpenAI 0.21.0 | ≥ 10 non-user items | no | no | **no**: session replaced |
| LangChain 1.6.1 | `beforeModel`, only if a trigger is set | same hook | no | **no**: `RemoveMessage(REMOVE_ALL_MESSAGES)` |

Sources: notes/context-and-compaction.md, first and fourth tables.

**A reactive overflow retry is common but not universal, which qualifies refinement 3 of our [earlier fact-check](../fact-check-2026-11-18.md#reference-architecture-review).** That refinement names three trigger points. Pi and Think implement all three, but Codex's main sampling path returns `ContextWindowExceeded` without retry (`CX/core/src/session/turn.rs:2148-2151`) and keeps compact-and-retry for its guardian path only (`:969-990`), relying on the 65% background threshold instead (`CX/core/src/config/mod.rs:247`). The three-point pattern is therefore common, not universal.

**The cheap layers carry most of the measured value.** Masking old observations "halves cost relative to the raw agent while matching, and sometimes slightly exceeding, the solve rate of LLM summarization" on SWE-bench Verified (Lindenbauer et al., [arXiv 2508.21433](https://arxiv.org/abs/2508.21433), abstract). In Anthropic's internal eval, context editing alone improved performance by 29% and cut tokens by 84% in a 100-turn search eval ([Managing context](https://claude.com/blog/context-management), vendor eval, as of September 2025). Anthropic calls tool-result clearing "one of the safest lightest touch forms of compaction" ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). LangChain's `ClearToolUsesEdit` copies the API defaults of 100,000 tokens and 3 kept tool uses (`LC/contextEditing.js:6-8`). Cloudflare truncates older tool output to 500 characters at read time and "does NOT mutate stored messages" (`CF/packages/agents/src/chat/truncate-older-messages.ts:1-21`).

**Summarizers differ in what they see, and two defaults lose information.** LangChain feeds its summarizer only the last 4,000 tokens of the span it discards (`LC/summarization.js:44, 566-580`), so a long history is summarized from its tail. LangChain's summarization also never fires without a configured trigger (`LC/summarization.js:318-345`). Pi's template is the strongest: fixed sections, "Preserve exact file paths, function names, and error messages", an iterative update of the previous summary, and cumulative read and modified file lists (`PI/compaction/compaction.js:16-35, 379-449, 712-714`). No harness summarizes the system prompt; Pi and LangChain prepend it unchanged and Codex re-renders it (notes/context-and-compaction.md, "Every summarizer keeps a verbatim recent tail").

| Harness | Summary writer | Tail kept | Template |
|---|---|---|---|
| Pi | the session model | ~20K tokens, cut at turn boundaries | Goal, Constraints, Progress, Key Decisions, Next Steps, Critical Context |
| Codex local | the turn's model | user messages up to 20K tokens; no assistant or tool tail | handoff summary "for another LLM" |
| Codex remote, OpenAI, Anthropic API | the provider's server | server-chosen | opaque (OpenAI output is encrypted) |
| OpenHands | condenser model, may differ | back half, plus the first 2 events | USER_CONTEXT, TASK_TRACKING, CODE_STATE, TESTS and more |
| LangChain | configured model | 20 messages | free-form extraction from the last 4,000 tokens |
| Cloudflare | session's compact function | 20K tokens | tool I/O sliced to 500 characters |

Sources: notes/context-and-compaction.md, "Summaries are written by a model" and "Every summarizer keeps a verbatim recent tail".

**Every compaction costs one prompt-cache rebuild, so the harness must ration prefix changes.** Think moves its truncation cutoff only every 8 messages, because "a cutoff that moved every turn rewrote a message near the end of that prefix on every turn" (`CF/packages/think/src/think.ts:304-313`). Pi disables cache writes on summary requests (`PI/compaction/compaction.js:478-482`), and the Claude CLI freezes the system prompt until compaction (`CSDK:2570-2577`). Anthropic's `clear_at_least` exists so each clear is worth its cache write ([Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)).

**The payoff of context management shrinks as windows grow, and compaction alone does not carry long tasks.** The context-management gain on SWE-bench fell from 35.7 to 2.7 points as the window grew from 32K to 128K (Fan et al., [arXiv 2609.20804](https://arxiv.org/html/2609.20804), §3.2, Tables 3-4; the Terminal-Bench gap fell from 9.5 to 2.8). Anthropic found that "compaction isn't sufficient" across windows and fixed it with an initializer that writes `init.sh`, a progress file, a JSON feature list and a git commit ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).

**Recommendation.** Build five removable layers, cheapest first: cap tool output at write time and spill the full text to a file; mask older tool results at read time in steps; summarize between turns with a 20K tail and a recall-first template; compact mid-turn at about 90%; retry once on overflow, then end the run with an in-band error (SDK decision 3). Store each compaction as an entry, never delete originals, and ablate layers 3 to 5 against the baseline before keeping them on 128K+ models (notes/context-and-compaction.md, implications 1-8).

## 3. Safety is three separate decisions: which call may run, what it can touch, and which secrets it sees

**Mature harnesses separate the permission pipeline, the sandbox and the credential boundary; the others implement at most the first.** Claude and Codex implement all three. Vercel, OpenAI and LangChain gate per tool and delegate isolation and secrets, and Pi implements none by default (notes/permissions-and-sandboxing.md, thesis). Our earlier fact-check split layer 7 into a sandbox policy and an approval policy ([refinement 2](../fact-check-2026-11-18.md#reference-architecture-review)); the evidence adds the credential boundary as a third, independent decision.

**The mature permission pipeline is ordered, deny-first and fail-closed.** Claude checks hooks, then deny rules, ask rules, the permission mode, allow rules and finally `canUseTool`, and a deny wins even in `bypassPermissions` (`docs/reference/claude-agent-sdk/guide.md:136-142`, verified by examples 03a–03f). Claude's gotcha shows the risk of silent steps: a bare tool name in `allowedTools` makes `canUseTool` unreachable with only a Node warning (`guide.md:152`). Codex derives `Skip`, `NeedsApproval` or `Forbidden` from `.rules` files and a dangerous-command list (`CDX src/exec_policy.rs:424-495, 893-905`), and it refuses to persist "always allow" prefixes that grant a whole interpreter, such as `bash -c` or `bun run` (`exec_policy.rs:64-80`). Defaults matter as much as order: Vercel's OPA policy treats no matching rule as allow unless the policy declares a default deny (`VDOC 03-agents/06-policy-tool-approvals.mdx:61`).

**Codex keeps the sandbox mode and the approval policy apart, and its `untrusted` value is no longer selectable.** The sandbox mode is `read-only | workspace-write | danger-full-access` (`CDX config.schema.json:4925-4930`). The approval schema offers `on-request`, `granular` and `never` (`config.schema.json:316-345`). A config that sets `approval_policy = "untrusted"` fails with "no longer supported; remove this setting", and Codex applies `UnlessTrusted` only as the derived default for a project marked untrusted (`CDX src/config/mod.rs:249-252, 4085-4101`). This corrects [harness-architectures.md](../harness-architectures.md), now marked in place and logged as [row 17](../fact-check-2026-11-18.md#corrections-from-the-verified-sdk-references-round-c-2026-11-18). Escalation is an explicit flow: run sandboxed, and on `SandboxErr::Denied` ask again unless a prior human or hook approval covers the retry; a Guardian approval never does (`CDX src/tools/orchestrator.rs:1-3, 406-580`).

**Pause-and-resume approvals need integrity checks that only Vercel ships, and only as an option.** Vercel warns that without a secret "a client that crafts a valid-looking approval for a schema-conforming input can bypass the human-in-the-loop step" (`VDOC 03-agents/06-tool-approvals.mdx:297`). `experimental_toolApprovalSecret` HMAC-signs the tool name, call id and input, and a server-side policy denial still wins over a valid signature (`:299-340`). OpenAI re-evaluates conditional approvals after restoring a `RunState` but does not sign it (OAI `tool.d.ts:23-39`; notes/permissions-and-sandboxing.md §2). LangChain's `when` predicate "runs again when the run resumes … If it returns `false` on resume, the reviewer's answer is skipped and the tool runs, even if they rejected it" (`LCM hitl.d.ts:20-23`).

| Harness | Gate shape | Where a pending approval lives | Integrity on resume |
|---|---|---|---|
| Claude | six ordered steps; synchronous `canUseTool` with an `AbortSignal` | CLI process (`defer` hook for a durable pause) | n/a in process |
| Codex | exec-policy rules plus approval policy; Guardian reviewer optional | in process; transient in the rollout | n/a in process |
| Pi | one extension `tool_call` handler returning `{block, reason}` | in process | n/a in process |
| OpenAI | per-tool `needsApproval`; tool guardrails | serialized `RunState` | policy re-evaluated, unsigned |
| Vercel | call-level `toolApproval` rules; optional OPA | client-held `messages` | HMAC when `experimental_toolApprovalSecret` is set |
| LangChain | `humanInTheLoopMiddleware` with `approve | edit | reject | respond` | checkpointer per `thread_id` | `when` predicate re-run; must be deterministic |

Sources: notes/permissions-and-sandboxing.md §1–2.

**Sandbox strength rises with cost, and the cheap tier shares the host kernel.** Anthropic's secure-deployment guide rates OS sandboxes "Good (secure defaults)" with "Very low" overhead, gVisor "Excellent (with correct setup)" with simple syscalls about 2× slower and heavy file open/close 10–200× slower, and microVMs "Excellent" with "High" overhead (`CDOC secure-deployment.md:74-77, 186-192`). Firecracker's own specification promises guest init within 125 ms and at most 5 MiB of VMM overhead ([SPECIFICATION.md](https://github.com/firecracker-microvm/firecracker/blob/main/SPECIFICATION.md)). Hosted prices, as of November 2026, are $0.0504 per vCPU-hour billed per second at both E2B ($0.000014/s) and Daytona, and $0.071 per vCPU-hour for Modal Sandboxes ($0.00003942 per physical core-second, one core being 2 vCPUs) ([E2B pricing](https://e2b.dev/pricing); [Daytona pricing](https://www.daytona.io/pricing); [Modal pricing](https://modal.com/pricing)). Daytona claims sandbox creation under 90 ms ([Daytona docs](https://www.daytona.io/docs/en/)); E2B's ~150 ms cold start still comes only from comparison blogs (secondary; notes/permissions-and-sandboxing.md §4). OpenAI's `UnixLocalSandboxClient` "adds no OS-level confinement", and Vercel's sandbox interface "does not sandbox the tool itself" (`OAIDOC sandbox-agents/clients.mdx:20, 33-37`; `VDOC 07-reference/01-ai-sdk-core/34-sandbox.mdx:14-19`).

| Tier | Example | Strength | Overhead | Where it runs |
|---|---|---|---|---|
| None (path checks in tools) | OpenAI `UnixLocalSandboxClient`; Vercel `experimental_sandbox` | none | zero | host |
| OS process sandbox | `srt` (Seatbelt, bubblewrap + seccomp); Codex Seatbelt, bwrap + seccomp | good, shares the host kernel | very low | host |
| Container | Docker with `--cap-drop ALL --read-only --network none` | setup-dependent | low | self-hosted |
| gVisor | `runsc` | excellent with correct setup | ~2× simple syscalls, 10–200× heavy file I/O | self-hosted or hosted |
| microVM | Firecracker (E2B, Vercel), Kata | excellent | ≤125 ms to guest init, ≤5 MiB VMM per VM (spec) | hosted |
| WASM alone | Pyodide interpreters | weak: host functions are the attack surface | low | host |

Sources: `CDOC secure-deployment.md:74-77, 113-138, 186-192`; Firecracker SPECIFICATION.md; the WASM row rests on the main report's [Cyera citation](../agent-sdks-and-harness-design.md#sandboxing-needs-two-boundaries-and-no-secrets-inside), not re-fetched (notes/permissions-and-sandboxing.md §4).

**Network isolation is a host-side proxy, and in-process tools often bypass it.** Anthropic's sandbox cut permission prompts by 84% and needs both filesystem and network isolation ([Claude Code sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing)). `srt` removes the network namespace on Linux, reaches HTTP and SOCKS proxies over Unix sockets, and refuses allowed names that resolve to loopback, link-local or metadata addresses ([sandbox-runtime README](https://github.com/anthropic-experimental/sandbox-runtime)). Claude's `strictAllowlist`, however, is "Enforced for sandboxed commands only — in-process tools such as WebFetch are not gated by this setting" (`CSDK:9489`). When the SDK `sandbox` option sets `enabled: true`, `failIfUnavailable` defaults to `true` and `query()` exits rather than run unsandboxed; the settings-file default is `false`, which warns and runs unsandboxed (`CSDK:2340-2345, 9468`). The permissions note records only the settings-file default (see [fact-check](fact-check.md) row 9).

**Secrets leak mostly through inherited environments.** Codex's default `ShellEnvironmentPolicy` inherits every variable with default excludes ignored, and a test pins that `API_KEY` and `SECRET_TOKEN` reach commands (`CDX src/exec_env_tests.rs:83-105`). Claude's CLI inherited our harness's environment until we passed an allowlisted `env` (`docs/reference/claude-agent-sdk/fact-check.md:94`). The better pattern injects credentials at the egress proxy: Claude's `sandbox.credentials` `mask` gives the sandbox a sentinel that "the host proxy swaps sentinel→real on egress", though `mask` degrades to `deny` on macOS and Windows (`CSDK:9554-9640`). OpenAI refuses credential-bearing mounts whose helper runs inside the sandbox (`OAIDOC sandbox-agents/clients.mdx:170`).

**Recommendation.** Build one ordered, deny-first pipeline whose no-match default is `ask` interactively and `deny` headless; keep a `SandboxPolicy` and an `ApprovalPolicy` separate, with Codex's escalate-and-re-approve flow as a tested state machine; sign every resumable approval and re-check current policy on resume; ship an OS sandbox and Docker backend that fail closed; route network through a default-deny proxy that also gates in-process fetch tools; and spawn every tool with a cleared, allowlisted environment.

## 4. A harness should be one typed protocol with thin transports, extended in three trust tiers

**Every mature harness has one protocol-shaped core, and its SDK, CLI, RPC and server are transports over it.** Codex's `exec` CLI is a client of an in-process app-server that keeps "the same JSON-RPC result envelope that `MessageProcessor` uses for stdio and websocket transports … rather than creating a second execution contract" (`CX/codex-rs/app-server/src/in_process.rs:19-24`; `exec/src/lib.rs:20-22`). OpenCode's SDK "executes Server's assembled HTTP router in memory, opening no listener" (`OC/packages/sdk/README.md:3`). Pi's four modes "use the same agent, sessions, resources, and tools" (`PIDOC/cli-integration.md:5`). The Claude Agent SDK is a thin client over the CLI's stream-json protocol (notes/interfaces-and-extensions.md §2). Wrappers such as Vercel's `HarnessAgent` adapt ten harnesses through whichever headless protocol each publishes (`VAI/05-harness-adapters.mdx:15-47`).

| Shape | Serves | Examples |
|---|---|---|
| In-process SDK | same-language hosts | Pi SDK; OpenCode `@opencode/sdk`; Codex `in_process.rs` |
| One-shot CLI with JSONL events | scripts, CI | `pi --mode json`; `codex exec --experimental-json` |
| Long-lived JSONL-over-stdio RPC | other languages, IDEs, SDK wrappers | Pi `--mode rpc`; Claude `stream-json`; Codex `stdio://` |
| Network server | desktop, web, remote sandboxes | Codex `ws://`; OpenCode OpenAPI + SSE; OpenHands WebSocket |

Sources: notes/interfaces-and-extensions.md §1.

**Every protocol carries three record families, and the hard parts are acceptance, cancellation and backpressure.** The families are client commands with correlated responses, uncorrelated events, and server-to-client requests for approvals, dialogs and client-hosted tools (notes/interfaces-and-extensions.md §3). Pi's `prompt` reply reports only a disposition, and clients must wait for `agent_settled`, because `agent_end` can be followed by retries, compaction or queued follow-ups (`PIDOC/rpc.md:58-71`). Claude lets either side withdraw one request with `control_cancel_request` (`CAS/sdk.d.ts:4185`). Codex bounds its queues at 128, rejects a full command queue with `-32001`, may drop notifications under load, and never silently abandons a server request, "so approval flows do not hang indefinitely" (`CX/.../app-server-transport/src/transport/mod.rs:24`; `in_process.rs:24-32`). Codex also omits the `jsonrpc` field on purpose: "We do not do true JSON-RPC 2.0" (`CX/codex-rs/app-server-protocol/src/rpc.rs:1-2`). Pi refuses Node `readline` because it splits on U+2028 and U+2029 inside JSON strings (`PI/dist/modes/rpc/jsonl.js:1-20`).

**Feature detection beats version numbers, and reconnecting clients need the pending set.** Claude has no protocol version field and tells clients to "treat absence as an older CLI" (`CAS/sdk.d.ts:435, 4877`). Codex combines `initialize` capabilities with per-field `#[experimental]` gates that reject a call unless the client opted in (`CX/codex-rs/app-server-protocol/src/experimental_api.rs:1-30`). Claude's `initialize` response lists pending permission requests so a joining client can re-arm them (`CAS/sdk.d.ts:435-443`), and OpenHands' event socket resumes `since` a timestamp (`OH/.../sockets.py:188-233`).

**Extensions split into three trust tiers, and a trust gate controls loading, not execution.** In-process plugins have full power and no isolation: a Pi extension "runs inside the Pi process with the same operating-system permissions", across 41 hook events (`PIDOC/extensions.md:7`; `PI/dist/core/extensions/types.d.ts:1229-1269`), and it can silently override a built-in tool by registering the same name (`PIDOC/extensions.md:2360`). MCP servers are isolated by the process boundary. Skills are files the model reads on demand, with only "name, description, and path" in the system prompt (`PIDOC/skills.md:41-53`). Pi's project trust keeps a folder from "silently loading executable extensions" yet "does not limit what tool calls can access" (`PIDOC/security.md:27-57`, `:33`). Claude's `skills` allowlist is likewise "a context filter, not a sandbox" (`CAS/sdk.d.ts:2463-2485`).

**The MCP client should namespace, defer and negotiate per server.** Pi names tools `mcp__<server>__<tool>` with hash suffixes on collision (`PIDOC/mcp.md:77`), while OpenAI prefixes nothing by default and throws `Duplicate tool names found across MCP servers` at runtime (`OAI/mcp.mjs:405, 430-432`). Pi exposes each server as `codemode`, `deferred`, `direct` or `hidden`, and appends server summaries to the conversation "so earlier messages stay cached" (`PIDOC/mcp.md:191-209`); Claude defers MCP tools behind tool search by default (`CAS/sdk.d.ts:1300-1303`). `@ai-sdk/mcp` 2.0.90 names `2026-07-28` its latest protocol, while `@modelcontextprotocol/core` 2.4.0 still sets `LATEST_PROTOCOL_VERSION = "2025-11-25"` but ships the new schemas (notes/interfaces-and-extensions.md §7). LangChain warns that mixing protocol eras in one aggregate client drops the whole fleet to legacy (`docs/reference/langchain/source/src/oss/langchain/mcp/connections.mdx:101-105`). Codex ships no MCP-server mode at `4389a52`: `git ls-tree` lists only `codex-mcp`, `rmcp-client` and `message-board-mcp`, and its CLI's `mcp` subcommand manages external servers (`CX/codex-rs/cli/src/main.rs:174`). The removal is inferred from absence, because the shallow clone has no history.

| MCP client | Transports | Tool names | Exposure |
|---|---|---|---|
| Pi | stdio, streamable HTTP; SSE rejected | `mcp__<server>__<tool>`, hash suffix on collision | `codemode` (default), `deferred`, `direct`, `hidden` |
| Claude | stdio, SSE, HTTP, in-process `sdk` | not checked in the notes | deferred behind tool search unless `alwaysLoad` |
| OpenAI | stdio, streamable HTTP, SSE, hosted | unprefixed by default; runtime error on duplicates | `toolFilter`, `cacheToolsList` |
| LangChain | per-server `ClientGroup` across protocol eras | `server_tool` prefix | not checked in the notes |

Sources: notes/interfaces-and-extensions.md §7.

**Recommendation.** Define one typed protocol package first, with commands, responses, events and server requests in a discriminated union, and generate TypeScript and JSON Schema from it. Implement the in-process API, then JSONL-over-stdio, then WebSocket or HTTP+SSE as transports over one dispatcher, with our own CLI as a client of the in-process transport. Make MCP a removable built-in extension, adopt the Agent Skills format unchanged, and defer an MCP-server facade until a consumer needs one.

## 5. Observability is a span tree projected from the log, and evals must report cost beside pass rate

**Every SDK except Pi emits the same three-level span tree under different names.** OTel GenAI defines `invoke_agent`, a model span and `execute_tool` (`SC/gen-ai-agent-spans.md:181-219`; `execute-tool.md:58-60`). Vercel follows those names, OpenAI uses `AgentSpan`/`TurnSpan`/`GenerationSpan`/`FunctionSpan`, Claude uses `claude_code.interaction`/`llm_request`/`tool`, and Pi instruments only model requests (notes/observability-and-evals.md §1). Only Claude splits permission wait from execution with a `tool.blocked_on_user` child span (`COBS:149`), so elsewhere tool latency mixes human think-time with machine time.

**The OTel GenAI conventions are Development-only, untagged and still renaming.** Every agent, inference and tool span is at Development status (`SC/README.md:7`). The conventions moved to `open-telemetry/semantic-conventions-genai`, which had no tags or releases on 2026-11-18, so a version means a commit SHA (notes/observability-and-evals.md §2). `@ai-sdk/otel` 1.0.162 shows the drift: it records the new `gen_ai.client.inference` histogram but writes span attributes under the older `gen_ai.client.operation.duration` name (`VOT:154-158, 251-271`). No convention defines cost; token counters only "serve as a proxy for cost approximation" (`SC/gen-ai-token-metrics.md:32-44`).

**Content capture must default to off, yet Vercel and OpenAI default it on.** The spec says instrumentations "SHOULD NOT capture them by default" and should record `*_ref` URIs in production (`SC/gen-ai-spans.md:466-500`). Vercel's attribute selector defaults inputs and outputs to recorded (`@ai-sdk/otel/src/select-telemetry-attributes.ts:39-63`). OpenAI sets `traceIncludeSensitiveData ?? true` (`OAC/run.mjs:121`) and registers an exporter to `api.openai.com/v1/traces/ingest` at import (`@openai/agents/dist/index.mjs:5`; `agents-openai/dist/openaiTracingExporter.mjs:6`). Claude records structure only until four opt-in variables are set, and Pi never records content (`COBS:47, 239-248`; `PIAT:73-101`).

| SDK | Telemetry default | Content default | Default destination |
|---|---|---|---|
| Vercel `ai` 7.0.162 | on once an integration is registered | **recorded** | the global OTel SDK |
| OpenAI Agents 0.21.0 | on in server runtimes, off under `NODE_ENV=test` | **recorded** | `api.openai.com/v1/traces/ingest`, registered at import |
| Claude Agent SDK 0.3.327 | off until `CLAUDE_CODE_ENABLE_TELEMETRY=1` | structure only; four opt-in variables | OTLP from the CLI; export errors silent by default |
| Pi 1.5.2 | no exporter shipped | never; char counts and tool names only | in-memory or SQLite store |
| LangSmith | on with `LANGSMITH_TRACING=true` | recorded; hide flags and anonymizers | LangSmith or OTLP |

Sources: notes/observability-and-evals.md §3–4.

**Cost accounting needs four input classes (uncached, cache read, 5-minute and 1-hour cache writes), one input convention and a provenance flag.** OTel's `input_tokens` "SHOULD include cached tokens" (`SC/client-inference.md:235`), while Pi's `input` is uncached tokens and Anthropic's raw `input_tokens` excludes cache (notes/observability-and-evals.md §6). Claude splits 5-minute and 1-hour cache writes and records `costBasis` (`CL:1568-1593`), and calls its costs "client-side estimates, not authoritative billing data" (`CCOST:17-25`). Budgets act after the fact: Claude's `maxBudgetUsd` stops after the crossing response (`docs/reference/claude-agent-sdk/guide.md:243`), and mini-swe-agent stops "after exceeding (!)" its $3 `cost_limit` (`MSWE/agents/default.py:28-29`).

**Eval evidence says cost resolves harness differences better than pass rate.** Among mature harnesses, swapping the harness "flips as many tasks as rerunning the same harness, 13% in both cases", and "45 tasks catch a 13-point gap only half the time … 447 tasks resolve 5 points" (arXiv 2610.04433, abstract). τ-bench's pass^k exposes inconsistency: gpt-4o retail scored above 60% pass^1 but below 25% pass^8 ([arXiv 2406.12045](https://arxiv.org/abs/2406.12045)). Infrastructure is a variable too: on Terminal-Bench 2.0, infra errors fell from 5.8% to 0.5% and success rose 6 points when resource caps were lifted ([Infrastructure noise](https://www.anthropic.com/engineering/infrastructure-noise)). Anthropic recommends 20–50 tasks from real failures, outcome graders, a clean environment per trial, and transcript reading, because grading bugs took Opus 4.5 from 42% to 95% on CORE-Bench once fixed ([Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

**Inspect and mini-swe-agent cover the runner and the baseline, so we need not write either.** Inspect's `sandbox_agent_bridge()` runs an unmodified harness and proxies its model calls, forwards generation settings only with `forward_generation_config=True`, and ships `pass_at_k` and `pass_k_k` reducers (`INS/agent-bridge.qmd:15, 291-298`; `INS/metrics.qmd:389-390`). mini-swe-agent writes a trajectory JSON with `instance_cost`, `api_calls` and `exit_status`, raises when a model's cost cannot be priced, and ships a `DeterministicModel` (`MSWE/agents/default.py:159-180`; `MSWE/models/litellm_model.py:108-126`; `MSWE/models/test_models.py:90-115`).

**Recommendation.** Emit `invoke_agent`, turn, model and `execute_tool` spans with a separate approval-wait span from one internal schema module stamped with the semconv commit; keep content off by default; export only to an explicitly configured OTLP endpoint; derive telemetry from usage and cost stored on log entries; and report pass rate, pass^k, cost, tokens, steps and preamble size per task beside a mini-swe-agent run with the same model, tasks, prices and resource limits.

## 6. Eighteen design decisions follow from the evidence

Each decision names its evidence and the [reference-architecture layer](../agent-sdks-and-harness-design.md#a-reference-architecture-in-eight-swappable-layers) it refines. Loop, tool-pipeline, interceptor and test-model decisions stay in the [SDK synthesis §6](../agent-sdk/agent-sdk-research.md#6-fourteen-design-decisions-follow-from-the-evidence); the harness builds on them.

1. **The session log is a JSONL tree of typed entries and the only source of truth (layer 3).** Entries carry `id`, `parentId`, `type` and `timestamp`; compaction, branch summaries, context edits, model and tool-loadout changes, usage and approvals are entries (§1; Pi `session-format.md:78-207`). Run state is rebuilt from the log, so no separate `RunState` blob exists, avoiding OpenAI's 1.20 divergence fix (`runState.d.ts:63-67`). Following the Claude transcript, write one entry per content block so parallel tool results interleave without ambiguity, give each subagent its own log file linked by the spawning tool-call id, and record cwd, permission mode and sandbox state on entries (notes/sessions-and-storage.md, Addendum).
2. **HEAD is persisted, and resume is exact (layer 3).** A `checkout` entry records every branch move, closing Pi's lost-`/tree`-jump hole (`PI/session-manager.js:733-753`; OpenHands `state.py:249-262`).
3. **One writer per session, enforced by an exclusive lock that fails fast (layer 3).** A second writer gets `WouldBlock`, as in Codex (`writer_lock.rs:20-46`). Readers stay lock-free and tolerate a torn last line, as Pi does (`PI/session-manager.js:314-324`), and our docs warn that `flock` is unsafe on NFS, as OpenHands' do (`event_store.py:45-56`).
4. **Files are immutable; revert and fork move a pointer (layer 3).** A file-level fork references its parent prefix, and migration writes a new file, verifies it and publishes atomically, rejecting unknown future versions (Codex `revert_thread.rs:15-18`, `rollout_migration.rs:1-10`; OpenAI `runState.mjs:2498-2501`).
5. **The store sits behind a `SessionStore` interface, with JSONL on disk and in memory first (layer 3).** `append` is idempotent by entry id, remote backends get an expected-suffix compare-and-swap, and SQLite arrives later as a projection for listing and search (Claude `CL:7266-7348`; OpenAI `session.d.ts:95-128`; Codex `0001_threads.sql`).
6. **Pauses are `approval_requested` and `approval_resolved` entries bound to an invocation fingerprint (layers 2 and 3).** This implements SDK decision 8 in storage: the pending entry carries the call id, tool, canonical-input hash and policy version, and a resumed run refuses any call without a matching resolution (§1, §3; OpenAI `runState.d.ts:56-75`; Vercel `06-tool-approvals.mdx:299-340`).
7. **Playback and re-run are separate, named replay modes (layers 3 and 8).** Playback rebuilds from stored entries with no calls; re-run branches from an entry (§1; LangGraph `use-time-travel.mdx:14-22`).
8. **Context policy is five removable layers, cheapest first (layer 5).** Write-time caps with spill-to-file, read-time masking in steps, threshold summarization, mid-turn compaction at about 90%, and one overflow retry (§2; notes/context-and-compaction.md, implications 1-5). The `transformContext` interceptor from SDK decision 12 is where layers 2 to 4 run.
9. **Summaries use a recall-first template over the whole discarded span (layer 5).** Use Pi's sections and exact-identifier rule, tool outputs truncated to about 2,000 characters each, iterative updates, cumulative file lists, a 20K tail that never splits a call from its result, and a fresh system prompt (Pi `compaction.js:253-266, 379-449`; avoid LangChain `summarization.js:44`).
10. **The gateway rations cache-prefix changes and records compaction cost (layers 1 and 5).** Freeze the system prompt until compaction, move masking cutoffs in steps, disable cache writes on summary calls, and count compaction calls in usage (Claude `CSDK:2570-2577`; Think `think.ts:304-313`; Pi `compaction.js:478-482`).
11. **Long tasks keep state in files, not summaries (layer 6).** An initializer writes a progress file, a JSON task list and a git commit, and each session re-reads them ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).
12. **One ordered, deny-first permission pipeline (new component between layers 2 and 7).** Hooks, deny, ask, mode, allow, host callback, as Claude orders them; an allow rule that shadows a registered callback is a startup error; no-match means `ask` interactively and `deny` headless (Claude `guide.md:136-152`; OPA `06-policy-tool-approvals.mdx:61`). The pipeline fills the "policy gate" slot of SDK decision 10.
13. **Sandbox policy and approval policy stay separate, with escalation as a tested state machine (layer 7).** Approval policy is `on-request | granular | never`; under `never`, denials return to the model; "always allow" never persists an interpreter prefix (Codex `orchestrator.rs:406-580`, `exec_policy.rs:64-80`, `config/mod.rs:4085-4101`).
14. **The sandbox is a pluggable client with honest tiers that fail closed (layer 7).** Ship `none` (labelled unsafe), an OS backend over `srt`, and Docker with `--cap-drop ALL --read-only --network none`; gVisor, Firecracker and hosted vendors come as adapters chosen by threat model (OpenAI `clients.mdx:41`; `secure-deployment.md:74-77, 113-138, 186-192`; Claude `CSDK:2340-2345`).
15. **No credentials inside the sandbox (layers 1 and 7).** Spawn tools with a cleared, allowlisted environment, inject API credentials at a default-deny egress proxy by host-scoped sentinel, gate in-process fetch tools by the same allowlist, and keep secrets out of the log (Codex `exec_env_tests.rs:83-105`; Claude `CSDK:9489, 9554-9640`; `AGENTS.md` "Running third-party code").
16. **One typed protocol under every interface, with stdio JSONL as the first remote transport (new interface layer).** Use JSON-RPC 2.0 framing with the `jsonrpc` field, `noun/verb` methods, a `trace` field, disposition plus a terminal `turn/settled`, per-request cancellation, bounded queues that never drop server requests, capability flags with `experimental` gates, and a pending set in `initialize` (§4; Codex `in_process.rs:19-32`, `rpc.rs:1-57`; Pi `rpc.md:58-71`; Claude `sdk.d.ts:435-443`).
17. **Three extension tiers behind one project-trust gate, and MCP as a removable built-in (layer 4 and a new extension layer).** In-process extensions get typed hooks with declared composition and need `override: true` to replace a built-in tool; MCP tools get canonical `mcp__<server>__<tool>` names checked at registration and a per-server exposure policy; skills use the Agent Skills format; headless trust defaults to skip (Pi `extensions.md:412-425, 2360`, `mcp.md:77, 191-209`, `security.md:59-82`).
18. **Telemetry is a projection of the log, and evals run on Inspect against mini-swe-agent (layer 8).** One schema module stamped with the semconv commit, content off by default, an approval-wait span, no default remote exporter, pre-emptive budget checks, and eval reports that pair pass rate and pass^k with cost, tokens, steps and preamble size per task, in a clean sandbox per trial with infra failures scored apart (§5; `SC/gen-ai-spans.md:466-500`; arXiv 2610.04433; [Infrastructure noise](https://www.anthropic.com/engineering/infrastructure-noise)).

## 7. The evidence revises the 8-layer architecture in six places and creates three tensions with the SDK synthesis

**Six revisions to the [reference architecture](../agent-sdks-and-harness-design.md#a-reference-architecture-in-eight-swappable-layers) and its [review](../fact-check-2026-11-18.md#reference-architecture-review):**

1. **Layer 3, "build schema; buy storage", is premature.** Every harness we read stores sessions on local disk or in the runtime's own database; none buys storage (§1). Build the schema and a JSONL backend, and make storage pluggable behind `SessionStore` (decision 5). The tree refinement (review item 1) holds, and the evidence adds persisted HEAD, a writer lock, immutable files and fingerprinted pause entries (decisions 2-6).
2. **Layer 5 gains write-time caps and stepped masking ahead of summarization, and the reactive retry is optional.** The main report already puts clearing first; the evidence adds write-time caps with spill files, makes masking the default ([Complexity Trap](https://arxiv.org/abs/2508.21433)), and shows that Codex works without a reactive retry, which qualifies review item 3 (§2).
3. **Layer 7 splits into three decisions, and the permission pipeline needs its own component.** The architecture table places "permission check" inside the layer-2 loop and the approval policy in layer 7. The evidence treats permissions, sandbox and credentials as three components, so the pipeline should be a component of its own that the loop calls (decisions 12-15). The main report's "Buy (or adopt OS sandbox)" becomes "adopt an OS sandbox and Docker; buy hosted microVMs through adapters".
4. **The architecture needs an interface layer.** Review item 5 adds stdio RPC "early"; the evidence makes the protocol the core's native contract, with every interface, including our own CLI, as a transport over it (§4; decision 16).
5. **The architecture needs an extension layer with a trust gate.** No layer covers in-process extensions, skills or project trust, yet every harness ships them and Pi and Claude both warn that trust gates loading, not execution (§4; decision 17).
6. **Layer 8 needs content-off defaults, a cost attribute of our own and pre-emptive budgets.** The main report's pinned-version advice holds, but "version" now means a commit SHA, cost has no convention, and both vendor budgets overshoot by one response (§5).

**Two corrections to earlier documents.** First, [harness-architectures.md](../harness-architectures.md) listed Codex's `untrusted` approval policy as selectable; it is now corrected in place and logged as [row 17](../fact-check-2026-11-18.md#corrections-from-the-verified-sdk-references-round-c-2026-11-18). Second, the same file lists "MCP client and server" in Codex's extension model, while Codex ships no MCP-server crate or subcommand at `4389a52` (§4). I left that row unchanged because the removal is inferred from absence; [fact-check.md](fact-check.md) row 17 records it as ⚠️ for a follow-up correction.

**Three tensions with the [SDK synthesis](../agent-sdk/agent-sdk-research.md):**
- **Token convention.** SDK open question 3 leaves "input" undecided, and SDK decision 5 stores uncached input plus cache classes. OTel requires `input_tokens` to include cache (`SC/client-inference.md:235`). Both can hold: the log stores the four classes separately, and the telemetry projection sums them for `gen_ai.usage.input_tokens`. Round P must still name the in-memory field.
- **Blocking gates.** SDK decision 8 keeps an in-memory blocking gate "as a convenience for CLIs and tests". The harness evidence shows a blocking pause dies with its process (§1), so the harness should accept a blocking gate only in the in-process transport and must write the `approval_requested` entry before it blocks, so a crash still leaves a resumable state.
- **Budget timing.** SDK decision 7 ends a run with a stop reason when its optional USD cap fires but does not say whether the cap is checked before or after a model call. Harness decision 18 asks for a pre-emptive check, because Claude's and mini-swe-agent's budgets act only after the crossing response (§5). Round P must decide which rule the SDK's cap follows (§9 question 9).

The decisions otherwise extend the SDK synthesis without conflict: its six interceptors host the context layers and the permission pipeline, its in-band errors carry sandbox denials back to the model, its built-in OTel observer (SDK decision 13) is where the log projection of decision 18 runs, and its base-URL-overridable gateway is what Inspect's bridge needs. This file also answers SDK open question 9: G2a owns the session log format (decisions 1-7) and the compaction layers and triggers (decisions 8-10), while the SDK defines the `transformContext` interceptor they run through.

## 8. Several decisions rest on secondary sources, absent code or unrun claims

- **Secondary or abstract-only figures.** The masking-versus-summarization result (arXiv 2508.21433), the 35.7 → 2.7 decay (arXiv 2609.20804) and the hosted-sandbox prices were re-checked against the papers and pricing pages on 2026-11-18 ([fact-check](fact-check.md), R1). E2B's cold start and Modal's sub-second start remain secondary because neither vendor page states a figure. The 2610.04433 figures come from its abstract, not its body, and the 27.4-point Claw-SWE-Bench figure is that paper's citation of arXiv 2606.12344, whose current abstract does not state it (notes/context-and-compaction.md §"Measured payoffs"; notes/permissions-and-sandboxing.md §4; notes/observability-and-evals.md, Unresolved gaps).
- **A disagreement between the notes and the main report.** The observability note's search summary says OpenAI audited 27.6% of SWE-bench Verified and found at least 59.4% of audited problems flawed, while the main report says "59.4% of 138 audited hard tasks" (`docs/research/agent-sdks-and-harness-design.md:119`). openai.com still returns 403 to this session (re-tried 2026-11-18), so neither framing is checked.
- **Unreachable specifications.** The MCP 2026-07-28 spec, the Agent Skills spec, cyera.com and gvisor.dev were unreachable; MCP facts come from `@modelcontextprotocol/core` 2.4.0, `@ai-sdk/mcp` 2.0.90 and LangChain docs (notes/interfaces-and-extensions.md, Unresolved gaps).
- **Code we did not read.** Codex's `linux-sandbox` and `execpolicy` crates were outside the sparse clone, so its Seatbelt and bwrap flags, `.rules` grammar and default `SandboxMode` are unchecked, including the "read-only (the default)" claim in [harness-architectures.md](../harness-architectures.md). Claude's on-disk format now rests on one structural sample of one CLI version (notes/sessions-and-storage.md, Addendum), not on documentation; `pi-durable`'s SQL schema is not in our install, and Codex's fsync behaviour was not read (notes/sessions-and-storage.md, Unresolved gaps).
- **Nothing here is [verified] by a runnable example.** No example in `verify/` exercises session stores, compaction, sandboxes, the RPC modes or telemetry; every claim comes from code or docs. The Claude `defer` resume flow is inferred, not run.
- **Unstudied areas.** ACP, OpenCode's SSE schema, OpenHands' REST surface, protocol latency overhead and our own `srt` and Docker cold starts are unmeasured.

## 9. Round P must settle nine questions before harness code starts

1. **Log granularity.** One JSONL line per stream delta, per content block or per completed item? The choice sets the unit that playback rebuilds from (decision 7), the point from which a reconnecting protocol client resumes (decision 16), and the file size budget.
2. **Lock primitive.** Lock file with PID and lease, `flock`, or an actor process per session, and what happens to a stale lock after a crash?
3. **Default context layers.** Which of the five layers are on by default for 128K+ models, given the decay result, and who runs the ablation?
4. **Default sandbox backend.** `srt`, Docker or `none` with a loud warning for local use, once we have measured cold starts on our hardware?
5. **Approval signing key.** This merges SDK open question 5: who owns the HMAC key, how it rotates, and whether an unsigned resume fails closed.
6. **Protocol framing.** Strict JSON-RPC 2.0 (decision 16) or Codex's field-less variant, and which methods ship in v1?
7. **Telemetry convention commit.** Which `semantic-conventions-genai` SHA we pin, and what our cost attribute is called until a convention exists.
8. **Eval suite seed.** Which 20–50 real-failure tasks form the first capability suite, at what k, with which resource guarantees and kill limits?
9. **Budget timing.** Does the SDK's USD cap (SDK decision 7) check before each model call, as decision 18 asks, or after the crossing response, as Claude and mini-swe-agent do (§7)?

## Conclusion: build the log first, then wrap policies and one protocol around it

The harnesses we read agree on the core of a harness design. Five of seven keep an ordered session log and four of those make it a tree; Pi, Codex and Think compact at several points with a 20K tail; the strong ones separate what may run from what it can touch and which secrets it sees; and every mature one puts its SDK, CLI and server over a single protocol. Their weaknesses are equally consistent: unpersisted HEADs, missing locks, approvals that die with a process, unsigned resumes, inherited environments, content recorded by default and budgets that overshoot. Our harness should take the shared design and close those holes in eighteen decisions, starting with the session log because the context layers, the approval pauses, replay and telemetry are all projections of it. The next step is G2b: write the harness guide from §6, then carry the nine open questions in §9 into Round P's implementation plan.
