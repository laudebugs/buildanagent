# Our agents should drive a logged-out browser inside the sandbox, with the loop and every credential outside it

Our agents can handle tasks that need a web browser without changing the architecture we already accepted. The loop stays in the Durable Object, the browser runs somewhere the model's keys never reach, and every page the browser loads leaves through the same egress allowlist as `bash` ([ADR 0036](../../decisions/0036-loop-outside-sandbox-and-pr-approval.md)). For the personal coding agent, the first browser should be a headless Chromium inside the task's existing hosted sandbox, pointed at the dev server on the sandbox's own localhost, logged out and holding no credentials. As of November 2026, Copilot, Jules, Codex Cloud, Cursor and Devin use a browser the same way: to check their own UI work and show the result as a screenshot or video. Copilot and Cursor attach it to the pull request ([GitHub changelog](https://github.blog/changelog/2025-07-02-copilot-coding-agent-now-has-its-own-web-browser/); [Cursor blog](https://cursor.com/blog/agent-computer-use)), while Jules, Codex and Devin send it to the user ([Jules changelog](https://jules.google/docs/changelog/2025-08-07); [Codex Browser](https://learn.chatgpt.com/docs/browser); [Devin docs](https://docs.devin.ai/work-with-devin/testing-and-recordings.md)). Browsing the open web, and the multi-user platform's browsing agents, need a hosted browser reached over a Chrome DevTools Protocol (CDP) WebSocket. Every hosted browser we checked hands one out, so a single `BrowserProvider` seam can cover Cloudflare, AWS and Vercel.

Five narrower findings support this, with every version, price and status as of November 2026. First, the model should see an accessibility snapshot, with screenshots only on request, and whether each action returns a full snapshot matters more to the token bill than the choice of MCP or CLI. Second, the cheapest hosted browser that needs no new vendor differs by target. Cloudflare Browser Run fits our Durable Object loop natively at $0.09 an hour, though Browser Use Cloud and Anchor charge less per hour. On AWS, AgentCore Browser costs about $0.04 an hour on our estimate and about $0.07 on AWS's own pricing example, and Vercel has no browser of its own, so Browser Run serves it over CDP. Third, Anthropic, OpenAI and Google all ship computer-use tools that the client executes, but they disagree on coordinates, batching and the safety handshake. Only three of our eight documented SDKs wrap the current vendor tools: LangChain.js wraps only the legacy ones, and Copilot bundles its own opt-in plugins. Fourth, prompt injection from web content remains unsolved, because adaptive attackers still succeed far more often than vendor figures suggest, so the boundary has to be the egress allowlist and the absence of credentials, not the model. Fifth, only self-hosted, deterministically graded suites such as WebArena-Verified can gate a release. We therefore propose seventeen changes to our plans, todos and ADRs for the owner to decide, led by a new ADR 0043 that places the coding agent's browser inside the sandbox and a fix to the Cloudflare sandbox backend without which no HTTPS page loads at all.

This report uses six terms throughout. A **browser tool** is any tool that lets the model drive a browser. An **in-sandbox browser** is Chromium running inside one of our `SandboxClient` sandboxes. A **hosted browser** is a browser service such as Browser Run or Browserbase. A **computer-use tool** is a model vendor's screenshot-and-action tool. The **egress allowlist** is the set of hosts our `EgressPolicy.allow` lets a sandbox reach. An **accessibility snapshot** is a text rendering of the page's accessibility tree in which every node carries a short ref that the next tool call passes back. The `"browser"` sandbox tier proposed in [portable-agents.md](../deployment/portable-agents.md#browser-sandboxes-save-compute-but-cannot-hold-the-credential-boundary) is a different idea, a sandbox that runs in the user's tab, and this report does not revisit it. For the storage and wake mechanics that any long browser task inherits, see [storage-and-wake.md](../deployment/storage-and-wake.md).

## Accessibility snapshots with refs won, and per-action output sets the token bill

By November 2026 the default page representation is the accessibility snapshot. Playwright MCP returns lines such as `- textbox "What needs to be done?" [ref=e5]`, and a ref stays valid "until the page changes"; a stale one fails with "Ref <ref> not found in the current page snapshot" ([Playwright MCP snapshots](https://playwright.dev/mcp/snapshots)). Chrome DevTools MCP tags nodes with a `uid` and tells the model to "Prefer taking a snapshot over taking a screenshot" ([chrome-devtools-mcp tool reference](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md)). Vercel Labs' agent-browser uses `@e1` refs, and Anthropic's new browser toolset targets elements as `{"type":"ref","ref":"ref_2"}` ([agent-browser README](https://github.com/vercel-labs/agent-browser/blob/main/README.md); [Claude browser use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/browser-use-tool)). Playwright's own comparison rates snapshots "Low — text only" in token cost and "Exact" in precision, against "High — image tokens" and "Approximate" for screenshots, though it publishes no measured numbers ([Playwright MCP snapshots](https://playwright.dev/mcp/snapshots)).

The other representations survive as fallbacks. Raw HTML is "often too large to be fed to LLMs" unfiltered, which is why Mind2Web filtered it with a small model first ([Mind2Web](https://arxiv.org/abs/2306.06070)). In SeeAct, set-of-mark prompting "turns out to be not effective for web agents", and its authors found grounding rather than planning to be the bottleneck ([SeeAct](https://arxiv.org/abs/2401.01614)). Pure screenshots remain, in our judgement, the only option for canvas, video and some cross-origin iframes; Anthropic's browser toolset likewise tells the model to "Fall back to coordinates for content the tree doesn't describe" ([Claude browser use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/browser-use-tool)). A 1920×1080 screenshot costs 2,691 visual tokens on Claude 4.7 and later models, which do not resize it, and 1,560 on older models, which downsize it to 1456×819 ([Claude vision docs](https://platform.claude.com/docs/en/build-with-claude/vision)). The production report "Building Browser Agents" reached about 85% on WebGames with "accessibility tree snapshots with selective vision", against about 50% for earlier agents and 95.7% for humans ([arXiv 2511.19477](https://arxiv.org/abs/2511.19477)). No peer-reviewed study compares HTML, accessibility snapshots, set-of-marks and pixels on 2026 models for both tokens and success, so the hybrid default rests on vendor convergence and 2023–2025 papers.

**The bigger token lever is whether each action returns a full snapshot.** Playwright MCP can snapshot one subtree, search the snapshot with `browser_find`, write it to a file, or turn off the snapshot that actions return (`--snapshot-mode none`); DevTools MCP returns a post-action snapshot only when `includeSnapshot` is set ([playwright-mcp README](https://github.com/microsoft/playwright-mcp/blob/main/README.md); [chrome-devtools-mcp tool reference](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md)). The same mechanism explains the CLI-versus-MCP debate. Microsoft says in both Playwright READMEs that CLI plus skills is "more token-efficient" because it avoids "loading large tool schemas and verbose accessibility trees", but gives no numbers ([playwright-cli README](https://github.com/microsoft/playwright-cli/blob/main/README.md)). Vercel's "93% less context" figure for agent-browser appears only in third-party write-ups, and we found no Vercel source for it ([paddo.dev, secondary](https://paddo.dev/blog/agent-browser-context-efficiency/)). Checkly, which says it is "heavily involved in the Playwright ecosystem", re-ran the comparison in July 2026. Its MCP sessions ended at about 48–50k tokens and its CLI sessions at about 45–48k. Checkly credits the near-tie to harnesses that defer MCP tool loading and to Playwright MCP now writing snapshots to disk, and it gives no tool versions ([Checkly](https://www.checklyhq.com/blog/mcp-vs-cli-token-efficiency/)). Our tool registry already defers tool schemas, so our harness gets the CLI's savings by returning file paths and on-request snapshots, whichever transport carries the tool.

CDP is the protocol every option speaks. WebDriver BiDi is still a W3C Working Draft, last updated 13 November 2026 ([W3C TR](https://www.w3.org/TR/webdriver-bidi/)), and even Puppeteer keeps CDP as Chrome's default "since not all CDP features are supported by WebDriver BiDi yet" ([Puppeteer docs](https://github.com/puppeteer/puppeteer/blob/main/docs/webdriver-bidi.md)). Playwright's `connectOverCDP` works with any Chromium endpoint but is "significantly lower fidelity" than its own `connect()` protocol, which needs a Playwright server on the far side ([Playwright BrowserType docs](https://github.com/microsoft/playwright/blob/main/docs/src/api/class-browsertype.md)). Playwright also exposes the snapshot machinery directly: `ariaSnapshot` has an `'ai'` mode that emits refs, and `Page.getByRef` (added in 1.64) resolves one ([Playwright release notes](https://github.com/microsoft/playwright/blob/main/docs/src/release-notes-js.md)). A TypeScript harness can therefore build its own ref tools on the library without adopting any agent framework.

## Every hosted browser hands out a CDP URL, so the loop can stay outside

Every hosted browser we checked returns a CDP WebSocket, or in AWS's case a WebSocket streaming endpoint, that a loop on Workers, Lambda or Vercel Functions connects to. The model's keys therefore never enter the browser, and the CDP URL itself becomes the one secret the host must hold. Steel says its connection URL "holds a token that controls the session", and Browser Use warns that "the credential-bearing CDP URL" can leak through transport errors ([Steel security](https://steel.dev/docs/platform/security-and-compliance); [Browser Use docs](https://docs.browser-use.com/llms-full.txt)). Live View URLs carry the same power over every logged-in account in the session, so Cloudflare says to treat them as credentials and, by default, gives a viewer five minutes to start a connection ([Cloudflare Live View](https://developers.cloudflare.com/browser-run/features/live-view/)).

**Cloudflare Browser Run fits our first target natively.** As of November 2026, the product formerly called Browser Rendering runs Chrome 152, offers stateless Quick Actions (`/markdown`, `/snapshot`, `/accessibilityTree` and others) and full Browser Sessions over Puppeteer, Playwright or raw CDP ([Browser Run overview](https://developers.cloudflare.com/browser-run/); [changelog](https://developers.cloudflare.com/browser-run/changelog/)). A Worker reaches it through a `browser` binding that needs no API token, while any other environment connects with a Bearer token to `wss://api.cloudflare.com/client/v4/accounts/{account_id}/browser-run/devtools/browser` ([CDP](https://developers.cloudflare.com/browser-run/cdp/); [binding API](https://developers.cloudflare.com/browser-run/reference/browser-binding-api/)). Our pinned `agents` 0.33.0 ships `agents/browser`, whose `browserTool` gives the model "one browser that stays open between turns" and lets it write CDP code that runs in Dynamic Workers; "The model never starts or closes the browser" ([Browse the Web, mirror at agents@0.33.0](../../reference/cloudflare-agents/source/agents/docs/agents/browse-the-web.md)). Two network controls sit outside the browser: Guardrails apply per-session hostname allowlists to Puppeteer, Playwright and CDP sessions but not to Quick Actions, and Outbound Workers route chosen hosts through a Worker that "can reach a private service, add authentication, or transform the response" ([Guardrails](https://developers.cloudflare.com/browser-run/features/guardrails/); [Outbound Workers](https://developers.cloudflare.com/browser-run/features/outbound-workers/)). A human handoff (`Cloudflare.handoff`, then `Cloudflare.handoffComplete`) covers MFA, CAPTCHAs and "sensitive credentials you do not want to pass to an automation script" ([Human in the Loop](https://developers.cloudflare.com/browser-run/features/human-in-the-loop/)).

Browser Run's limits shape how an agent must use it. An idle session closes after 60 seconds by default and 20 minutes at most, and sessions also close when Browser Run rolls out a release ([Limits](https://developers.cloudflare.com/browser-run/limits/)). It has no saved-profile product, no IP rotation and no CAPTCHA solving ([FAQ](https://developers.cloudflare.com/browser-run/faq/); [llms-full.txt, crawl section](https://developers.cloudflare.com/browser-run/llms-full.txt)). Cloudflare always labels its traffic as a bot, signed with Web Bot Auth, which as of November 2026 is an IETF working-group draft (`draft-ietf-webbotauth-httpsig-protocol-01`), not an RFC ([FAQ](https://developers.cloudflare.com/browser-run/faq/); [Automatic request headers](https://developers.cloudflare.com/browser-run/reference/automatic-request-headers/); [IETF datatracker](https://datatracker.ietf.org/wg/webbotauth/documents/)). Its docs recommend incognito contexts to separate tasks, offer a fresh browser for "full process-level isolation", and describe no per-session VM. Concurrency is also contested. The limits page, updated 14 October 2026, gives 200 concurrent browsers and 3 new browsers per second on Workers Paid, while a 15 April 2026 changelog entry says 120 and 1 ([Limits](https://developers.cloudflare.com/browser-run/limits/); [changelog](https://developers.cloudflare.com/browser-run/changelog/)). The newer page should win, but the conflict needs a recheck before we size anything on it. A task that outlives its browser must therefore keep any state it needs in Durable Object storage and re-create the browser on wake.

**AWS has a native option; Vercel has none.** AgentCore Browser runs each session in a container, with a 15-minute default and 8-hour maximum, an automation endpoint for Playwright, a Live View endpoint, and, for custom browsers, recordings written to the customer's own S3 bucket ([AgentCore Browser](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-tool.html); [AgentCore session recording](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-session-recording.html)). It bills $0.0895 per active vCPU-hour and $0.00945 per GB-hour, with CPU free during "I/O wait and idle time" but memory billed at its peak for the whole session ([AgentCore pricing](https://aws.amazon.com/bedrock/agentcore/pricing/)). AWS does not publish a session's vCPU and memory, so our figure of about $0.04 per hour, for one vCPU at 25% and 2 GB, is only an estimate; AWS's own pricing example, 2 vCPU and 4 GB at 80% I/O wait, comes to about $0.07 per hour. AWS lets you choose the network mode only when you create a custom browser, and a secondary source found no statement of the managed `aws.browser.v1`'s mode, so VPC egress control needs a custom browser ([AgentCore session management](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-resource-session-management.html); [hidekazu-konishi.com, secondary](https://hidekazu-konishi.com/entry/what_agentcore_browser_keeps_and_where_its_traffic_goes.html)). Vercel's docs only show headless Chromium inside a Function through `@sparticuz/chromium`, which wants 1,600 MB or more of memory ([Vercel Functions limitations](https://vercel.com/docs/functions/limitations)). Vercel Labs' agent-browser documents running inside Vercel Sandbox through its `@agent-browser/sandbox` package, though Vercel's own docs have no page for it ([agent-browser on Vercel](https://agent-browser.dev/next)). Because Browser Run accepts CDP from "any environment that supports WebSocket connections", one Browser Run account can serve the Vercel target too ([CDP](https://developers.cloudflare.com/browser-run/cdp/)).

**For a single owner, the cheapest path that needs no new vendor is Browser Run on Cloudflare, AgentCore on AWS and Browser Run over CDP from Vercel.** On AWS, AgentCore's estimated $0.04–0.07 an hour undercuts Browser Run's $0.09. Browser Use Cloud and Anchor charge less still, but each would add a vendor and one more holder of our session data. Change 13 puts this mapping behind one `BrowserProvider` seam.

For the platform, a vendor's own security matters as much as its price. Kernel disclosed on 4 November 2026 that an attacker used a compromised Kernel API key to reach a staff login at its logging provider on 27 October, and downloaded data holding some API keys and customers' third-party secrets. After Kernel detected the breach on 2 November, the attacker used a compromised hosting-provider credential on 3 November to reach four servers, three of which ran browser sessions ([Kernel notice](https://www.kernel.sh/blog/public-notice-of-security-incident-nov-4-2026)). Browserbase, for its part, records every session as video by default, with zero data retention only on Enterprise, though any plan can turn recording off per session ([Session replay](https://docs.browserbase.com/platform/browser/observability/session-replay); [ZDR](https://docs.browserbase.com/account/enterprise/zero-data-retention)).

**An in-sandbox browser sees the sandbox's localhost and reuses every sandbox seam.** A hosted browser cannot load `http://localhost:3000` inside our sandbox without an exposed preview URL, while Chromium in the same sandbox can. It also inherits the sandbox's `SandboxPolicy`, `EgressPolicy` and conformance suite, so it adds no seam ([harness plan §3.4](../../plans/build-harness.md#34-permission-approval-and-sandbox-apis)). Its own cost, Chromium's memory and image size inside the task's sandbox, is unmeasured, and change 12 measures it.

**As N46b is written, no HTTPS request leaves a Cloudflare sandbox.** [N46b](../../todos/ready/N46b-cloudflare-sandbox-backend.md) compiles `EgressPolicy` to `enableInternet = false` plus `allowedHosts` and an `outboundByHost` handler, in Sandbox SDK 0.x terms, and says nothing about interception. In SDK 0.x, outbound rules apply to HTTPS "only when your class sets `interceptHttps` to `true`", which installs an ephemeral CA at `/etc/cloudflare/certs/cloudflare-containers-ca.crt`. With interception off, HTTPS "reach[es] every host while `enableInternet` is `true`, and fail[s] while it is `false`" ([Sandbox SDK 0.x outbound traffic](https://developers.cloudflare.com/sandbox/sdk/guides/outbound-traffic/)). As written, then, no allowlisted HTTPS host would load in Chromium or anything else. SDK 1.0, npm's `latest` since 30 September 2026, drops these fields ([Move outbound rules](https://developers.cloudflare.com/sandbox/sdk/migrate/outbound-traffic/); [Containers outbound traffic](https://developers.cloudflare.com/containers/configuration/outbound-traffic/)). A 1.0 container started with `enableInternet: false` reaches only the hosts its Durable Object intercepts with `interceptOutboundHttps`, so on 1.0 too, HTTPS needs interception. Three questions remain open. The 0.x page does not say whether its rules apply to every process, though the Containers page states the 1.0 rule for the whole container. The runtime trusts the CA automatically for Node.js, curl, Python requests and Git, but names neither Chromium nor its own certificate store. And we have not checked whether E2B's and Vercel's firewalls cover a browser process at all. Change 2 fixes N46b and tests Chromium against the CA, and change 3 adds the conformance tests that settle the rest.

## Vendor computer-use tools need one adapter each, and only three of our SDKs wrap them

All three model vendors make the client execute every action, but their tools differ in five ways that a portable harness must absorb. Anthropic's GA `computer_toolset_20260801` sends each of its 17 actions as its own `tool_use` block tagged `"toolset_name": "computer"`, in ordered batches; after a failure the client answers every later action with "Not executed: an earlier computer action in this turn failed." ([Claude computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)). Its `browser_toolset_20260801` adds 31 browser actions, four of them off by default, that target refs from an accessibility snapshot and fall back to coordinates ([Claude browser use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/browser-use-tool)). **Opus 5.5 and Sonnet 5.5 return a 400 on the Claude API for the older `computer_20251124` tool**, so a legacy loop that reads `input.action` stops working on current models ([Claude computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool#earlier-tool-versions)). OpenAI's GA `computer` tool returns batched `actions[]` in one `computer_call`, the old `computer-use-preview` model is shut down, and for GPT-6 Astra OpenAI now recommends "code execution", a function tool whose script the application runs against a library such as Playwright or PyAutoGUI ([OpenAI computer use guide](https://developers.openai.com/api/docs/guides/tools-computer-use.md); [migration](https://developers.openai.com/api/docs/guides/tools-computer-use-integration.md)). Gemini made `computer_use` a built-in tool of mainline models with Gemini 3.5 Flash in June 2026, replacing a standalone 2.5 computer-use model, with coordinates on a normalised 0–999 grid ([Google blog](https://blog.google/innovation-and-ai/models-and-research/gemini-models/introducing-computer-use-gemini-3-5-flash/); [Gemini computer use docs](https://aistudio.google.com/docs/computer-use)).

| | Anthropic | OpenAI | Google |
| --- | --- | --- | --- |
| Coordinates | screenshot pixels; client resizes to the image limit | environment pixels; `detail: "original"` advised | 0–999 normalised grid |
| Batching | one `tool_use` per action, halt on failure | `actions[]` in one call | parallel function calls, a screenshot with each reply |
| Safety handshake | server-side classifiers, nothing to acknowledge | `pending_safety_checks` to acknowledge | `safety_decision`, answered with `safety_acknowledgement` |
| Structured page channel | browser toolset refs | `BrowserToolset` function tools or code execution | none |
| Toolset overhead | about 4,500 input tokens for the default computer members | not published | not published |

The vendor tools also reveal where the industry thinks safety lives. Anthropic's docs recommend a dedicated low-privilege VM, no credentials, a domain allowlist and human confirmation of consequential actions ([Claude computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)). OpenAI tells integrators to confirm purchases, destructive changes and data transmission, noting that "Typing sensitive information into a form counts as transmission" ([OpenAI guide](https://developers.openai.com/api/docs/guides/tools-computer-use.md)). Both Anthropic's and OpenAI's client SDKs now ship toolset base classes that take a driver the application supplies, with Browserbase, Browser Use, Daytona and E2B publishing drivers; Anthropic's classes are in beta as of November 2026 ([Claude SDK toolsets](https://platform.claude.com/docs/en/agents-and-tools/tool-use/browser-use-sdk); [OpenAI guide](https://developers.openai.com/api/docs/guides/tools-computer-use.md)). Published benchmark scores for these tools come from different harnesses and are mostly self-reported or secondary, such as a 78.4 OSWorld-Verified figure for Gemini 3.5 Flash that the blog shows only in a chart ([the-decoder, secondary](https://the-decoder.com/google-bakes-computer-control-directly-into-gemini-3-5-flash-letting-the-model-see-and-operate-your-screen/)). A portable harness needs one internal action model, in screenshot pixels with ordered batches and a provider-neutral safety record routed to the approval pipeline, plus a thin adapter per vendor.

## Coding agents use the browser to check their own work inside the sandbox

Most major cloud coding agents now ship a browser inside their own sandboxes, and they use it for the same four jobs: reproduce a bug, verify a UI change, run an end-to-end flow, and attach evidence. Copilot's coding agent got a Playwright MCP browser in July 2025 and "share[s] screenshots of what it has done in its pull request" ([GitHub changelog](https://github.blog/changelog/2025-07-02-copilot-coding-agent-now-has-its-own-web-browser/)). Jules added Playwright to its base image and sends "a screenshot of the front end along with any code changes" ([Jules changelog](https://jules.google/docs/changelog/2025-08-07)). Cursor's cloud agents run a full VM desktop and deliver PRs with videos, screenshots and logs; Devin records an annotated video of "the single most important end-to-end flow" after CI is green ([Cursor blog](https://cursor.com/blog/agent-computer-use); [Devin docs](https://docs.devin.ai/work-with-devin/testing-and-recordings.md)). Claude Code's cloud VMs preinstall Chrome for Testing with `CHROME_PATH` set, and do not support an interactive SSO login ([Claude Code cloud environments](https://code.claude.com/docs/en/cloud-environments)). Lovable tests selectively after faster checks, Replit only when it judges enough has changed, and Claude Code warns that always-on browser tools raise context use ([Lovable](https://docs.lovable.dev/features/browser-testing); [Replit](https://docs.replit.com/references/agent/app-testing.md); [Claude Code Chrome docs](https://code.claude.com/docs/en/chrome)).

Copilot is the only vendor we checked that documents its firewall covering the browser. In its cloud sandboxes the firewall applies to the built-in Playwright server and its browser processes, but not to repository-configured replacement MCP servers, and blocked requests are reported in the PR ([Copilot firewall](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-the-firewall)). Whether our own backends' firewalls cover a browser is still unchecked, so change 3 tests it on each one, and change 8 copies Copilot's habit of reporting blocked requests in the PR.

Our plans name no browser tool, so the coding agent needs one. They name no Playwright or screenshot anywhere either: the only web tool is N21's `fetch`, which runs through `EgressProxy.fetch` and must fail on a non-allowlisted host ([N21](../../todos/ready/N21-builtin-tools.md)), and [W2](../../todos/ready/W2-coding-tool-profile.md)'s tool profile adds git tools and the test command. The plans also leave one question open that a browser forces: whether browser actions inside the sandbox count as prompt-free "commands" under [CA6](../../plans/build-coding-agent.md#ca6-the-draft-pull-request-is-the-approval-point-accepted). Our coding agent therefore needs a headless Chromium in the sandbox with snapshot, screenshot, console and network tools, viewport presets, evidence attached to the draft PR, and egress rules that bind the browser process itself; driving the owner's logged-in browser and computer-use tools can wait.

## Prompt injection stays unsolved, so the network and the credential are the boundary

Every vendor that has shipped a browser agent calls prompt injection unsolved, and independent adaptive attacks still succeed far more often than vendor figures suggest. A browser is the textbook leg of Willison's lethal trifecta, an agent that combines "private data, untrusted content, and external communication", because any page load, form post or image request can carry data out ([Simon Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). Our harness already treats that outbound leg as the one to cut ([agent guide](../../guides/agent.md)). The evidence below supports cutting it in the network layer and keeping credentials out of reach, and treating every model-side defense as one layer among several.

### Vendor figures fell below 0.1% by November 2026, but adaptive attackers succeed far more often

Anthropic's figures fell sharply between 2025 and 2026. The Claude for Chrome pilot in August 2025 measured 23.6% attack success without mitigations and 11.2% with them across 123 test cases ([Claude blog](https://claude.com/blog/claude-for-chrome)). In November 2025 an internal best-of-N attacker with 100 attempts per environment succeeded 1.4–2.4% of the time against improved safeguards, against 8.0–13.8% for the models alone; Anthropic added that "A 1% attack success rate … still represents meaningful risk" ([Anthropic research](https://www.anthropic.com/research/prompt-injection-defenses)). Its support page, updated 16 November 2026, reports "less than 0.08%" for Claude Opus 4.8 in internal testing, with risk "still non-zero" ([Claude Help Center](https://support.claude.com/en/articles/12902428-use-claude-in-chrome-safely)). A circulating 0–0.3% figure for the Claude in Chrome launch appears only in secondary write-ups that name conflicting models, so we treat it as unverified ([kdpisda.in, secondary](https://kdpisda.in/claude-in-chrome-general-availability/)). OpenAI's CISO called prompt injection "a frontier, unsolved security problem" at the Atlas launch, and OpenAI later said it "is unlikely to ever be fully 'solved'"; that second quote comes from secondary coverage because OpenAI's post returned HTTP 403 ([Simon Willison](https://simonwillison.net/2025/Oct/22/openai-ciso-on-atlas/); [Techloy, secondary](https://www.techloy.com/openai-admits-prompt-injection-isnt-going-away-as-it-hardens-security-for-atlas/)).

Independent tests measure a different attacker. In January 2025 NIST CAISI found the strongest baseline attack on AgentDojo reached 11%, while attacks built for the target model reached 81%, and it recommends multi-attempt evaluation ([NIST CAISI](https://www.nist.gov/news-events/news/2025/01/technical-blog-strengthening-ai-agent-hijacking-evaluations)). BrowseSafe++ took attacks that "succeed on only a few percent of tasks" and, after revising them with agent feedback, reached up to 95.41% ([arXiv 2610.17457](https://arxiv.org/abs/2610.17457)). VPI-Bench deceived browser-use agents in up to 100% of cases on some platforms with visual injections, and WASP's injections in GitLab issues and Reddit posts partly succeeded in up to 86% of cases ([VPI-Bench](https://arxiv.org/abs/2506.02456); [WASP](https://arxiv.org/abs/2504.18575)). A Gray Swan competition sponsored by UK AISI, analysed with CAISI in a March 2026 paper, logged 272,000 attempts against 13 frontier models and found "All models proved vulnerable", from 0.5% for Claude Opus 4.5 to 8.5% for Gemini 2.5 Pro ([arXiv 2603.15714](https://arxiv.org/abs/2603.15714); [NIST CAISI](https://www.nist.gov/blogs/caisi-research-blog/insights-ai-agent-security-large-scale-red-teaming-competition)). WASP's setting matters most for us, because a coding agent that reads issue trackers is exactly its target. Brave's "unseeable" injections, faint text in screenshots that the model reads, show that text sanitising alone cannot protect a screenshot-driven agent ([Brave](https://brave.com/blog/unseeable-prompt-injections/)). We should plan for the adaptive number.

Detection classifiers help but leave gaps. BrowseSafe's fine-tuned detector reached an F1 of 0.904 in under a second, against 0.863 for Sonnet 4.5 at 23–36 seconds and 0.360 for PromptGuard-2 ([BrowseSafe](https://arxiv.org/html/2511.20597)). Its architecture is cheap to copy: treat all browser-tool output as untrusted, chunk large pages, run detection in parallel with planning, and replace flagged output with a placeholder. Google's Chrome design runs a similar page classifier "in parallel to the planning model's inference" ([Google blog](https://blog.google/security/architecting-security-for-agentic/)). In our pipeline such a detector runs as a hook, so it can deny or ask but never allow, because [ADR 0019](../../decisions/0019-permission-pipeline-and-approval-modes.md) lets a classifier allow only as the host callback.

### The designs that hold use a deterministic gate outside the model

The published designs converge on one rule: an agent that reads untrusted web content must not also hold private data and an outbound channel, unless a deterministic gate decides each consequential action. Meta's Rule of Two lets an agent combine at most two of untrusted input, sensitive access and external state change; its browsing research assistant avoids sensitive access by running "in a restrictive sandbox without preloaded session data" ([Meta AI](https://ai.meta.com/blog/practical-ai-agent-security/)). Google's Chrome agent adds a User Alignment Critic that "see[s] only metadata about the proposed action", and Origin Sets that split read-only origins from origins where the agent may act ([Google blog](https://blog.google/security/architecting-security-for-agentic/)). OpenAI's Atlas offers a "logged out mode" and reserves logged-in mode for "well-scoped actions on very trusted sites" ([Simon Willison quoting OpenAI](https://simonwillison.net/2025/Oct/22/openai-ciso-on-atlas/)). CaMeL shows the provable version: separating control flow from data flow, it solves 77% of AgentDojo tasks, against 84% for an undefended system ([CaMeL](https://arxiv.org/abs/2503.18813)). Our coding agent can follow this design cheaply: browsing runs with untrusted input and the sandbox's egress allowlist but no private data, while the git push takes no web input and goes through the GitHub App route, with the owner's merge as the confirmation ([CA4](../../plans/build-coding-agent.md#ca4-the-loop-runs-in-a-durable-object-outside-the-sandbox-accepted); [CA6](../../plans/build-coding-agent.md#ca6-the-draft-pull-request-is-the-approval-point-accepted)).

### Logins belong to the host, and a saved cookie jar is a credential

The consensus for logins is that the model never sees a secret. 1Password's agentic autofill fills a Browserbase session "if, and only if, the human approves", over an end-to-end encrypted channel that keeps raw credentials out of the model's context; Chrome's agent signs in through Google Password Manager; Steel says "Your code and your agent never need the password, and Steel never returns it" ([1Password](https://1password.com/blog/closing-the-credential-risk-gap-for-browser-use-ai-agents); [Google blog](https://blog.google/security/architecting-security-for-agentic/); [Steel credentials](https://steel.dev/docs/logins/credentials)). A persisted session is still a credential. Browserbase contexts keep cookies, local storage and autofill data until deleted, and its docs advise one context per site and login and `persist: false` for read-only reuse ([Browserbase contexts](https://docs.browserbase.com/features/contexts)). A prompt-injected agent inside a logged-in context can use the session without ever seeing a password, and no vendor documents a way to stop a filled session from navigating to an attacker's origin after login; Google's Chrome agent comes closest by restricting model-generated URLs to known public ones. Our order of preference is therefore an API or OAuth token injected at an egress route outside the sandbox ([HD15 in the harness plan](../../plans/build-harness.md#hd15-the-credential-proxy-injects-on-reverse-proxy-routes-not-by-intercepting-tls)), then an approval-gated fill by the host with the filled fields masked from later screenshots and snapshots, then a human handoff.

### Egress must be enforced below the browser

A browser that renders attacker pages is both an exfiltration channel and an SSRF primitive. Image loads and links leak data, as OWASP's scenario of an injected image URL shows, and the metadata address `169.254.169.254` can return cloud credentials to a request that reaches it ([OWASP LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/); [modpagespeed blog, secondary](https://modpagespeed.com/blog/air-gapped-headless-fetch-ssrf-pinning/)). Some clouds demand more than reaching the address. Google Cloud's metadata server denies a request without the `Metadata-Flavor: Google` header ([Google Cloud metadata docs](https://cloud.google.com/compute/docs/metadata/querying-metadata)), but an AWS instance accepts either IMDSv1 or IMDSv2 by default and needs IMDSv2's session token only if it is configured to require it ([AWS IMDS docs](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-instance-metadata-service.html)). Browser-level filters do not hold: Playwright MCP's `--allowed-origins` "*does not* serve as a security boundary", and browser-use calls its domain restrictions "a guard for an aligned model, not a sandbox" ([playwright-mcp README](https://github.com/microsoft/playwright-mcp/blob/main/README.md); [browser-use README](https://github.com/browser-use/browser-use/blob/main/README.md)). CVE-2026-5607 is an SSRF in `mcp-browser-agent` up to 0.8.0, which NVD confirms ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2026-5607)). Our N20 proxy must refuse allowlisted names that resolve to `127.0.0.1` or `169.254.169.254` ([N20](../../todos/ready/N20-credential-proxy.md)), and that check must also cover every subresource Chromium fetches. The rule follows: the browser's traffic leaves through the same egress allowlist as `bash`, the harness checks each navigation URL against that allowlist in a before-tool-call hook, and the proxy enforces it again by resolved address.

Method filters add a cheaper layer for read-only browsing, but only where the backend sees the request. Codex Cloud can "restrict network requests to `GET`, `HEAD`, and `OPTIONS`" ([Codex Cloud internet access](https://learn.chatgpt.com/docs/cloud/internet-access)), Vercel Sandbox firewall rules can match on "the path, method, query parameters, and headers" ([Vercel Sandbox firewall](https://vercel.com/docs/sandbox/concepts/firewall)), and a Cloudflare outbound handler reads each intercepted request's method ([Containers outbound traffic](https://developers.cloudflare.com/containers/configuration/outbound-traffic/)). HD15's `CONNECT` path, by contrast, filters HTTPS by name without intercepting TLS, so it cannot see methods; only HD15's credential routes check them ([HD15 in the harness plan](../../plans/build-harness.md#hd15-the-credential-proxy-injects-on-reverse-proxy-routes-not-by-intercepting-tls)). Change 16 offers a read-only research mode on the backends that can enforce it.

### Screenshots are tenant data with a retention cost

Screenshots and snapshots capture whatever the page shows, including personal data and session details. OpenAI keeps deleted ChatGPT agent screenshots for up to 90 days, according to a search summary of its help article, which returned HTTP 403 to us ([OpenAI Help, search summary](https://help.openai.com/articles/11752874)). Browserbase records video by default, Browser Run keeps rrweb recordings for 30 days when enabled, and AgentCore writes recordings to the customer's S3 ([Browserbase replay](https://docs.browserbase.com/platform/browser/observability/session-replay); [Browser Run recording](https://developers.cloudflare.com/browser-run/features/session-recording/); [AgentCore session recording](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-session-recording.html)). We found no vendor or standards guidance on redacting personal data in agent screenshots; Steel masks filled credentials in its snapshots but nothing broader ([Steel credentials](https://steel.dev/docs/logins/credentials)). Our telemetry should therefore reference screenshot and snapshot blobs rather than inline them, store the blobs encrypted with a short expiry, mask fields the host filled, and keep recording off unless the owner or a tenant turns it on.

## Only self-hosted, deterministically graded suites can gate a release

Browser benchmarks split into self-hosted suites with programmatic graders, which are reproducible, and live-web suites graded by a model, which drift. WebArena-Verified re-audits WebArena's 812 tasks, replaces model judges with deterministic comparison, ships Docker images for its GitLab, shopping and other sites, offers a 258-task Hard subset, and can re-grade offline from captured HAR files ([webarena-verified README](https://github.com/ServiceNow/webarena-verified)). REAL's 112 tasks run on deterministic site replicas, and BrowserGym wraps MiniWoB, WebArena and others behind one interface ([REAL](https://arxiv.org/abs/2504.11543); [BrowserGym](https://github.com/ServiceNow/BrowserGym)). A BrowserGym issue reports that its WebArena-Verified reward gives partial credit where the official harness does not, so scores from the two are not comparable ([BrowserGym issue #412](https://github.com/ServiceNow/BrowserGym/issues/412)). We found no official WebArena-Verified leaderboard and no confirmed Claude or GPT scores on it.

Live-web numbers mostly measure the judge and the scaffold. Online-Mind2Web's own authors showed a search-only agent scoring 51% on WebVoyager but 22% on their suite ([Online-Mind2Web](https://arxiv.org/html/2504.01382v4)). As of November 2026, Princeton's independent HAL board tops out near 42% on Online-Mind2Web, while vendor boards report about 97% with their own judges ([HAL](https://hal.cs.princeton.edu/online_mind2web); [Browser Use, self-reported](https://browser-use.com/posts/online-mind2web-benchmark)). On the desktop, the official OSWorld-Verified board lists scores up to 90.19% as of November 2026, above the 72.36% human baseline ([OSWorld-Verified](https://os-world.github.io/)); OSWorld 2.0's long tasks still hold the best official result to 44.33% as of November 2026, up from 20.6% in its paper ([OSWorld 2.0](https://osworld-v2.xlang.ai/)). An audit of 150 failure-scored trajectories found 15.3% of FAIL verdicts wrong, 10.7% from evaluator false negatives and 4.7% from broken tasks, and HAL found its own cost accounting double-counted nested spans by up to 2× ([arXiv 2607.28367](https://arxiv.org/abs/2607.28367); [HAL](https://hal.cs.princeton.edu/online_mind2web)). Both lessons apply to our OpenTelemetry spans and our eval reports.

Our eval tiers follow from this. A small fixture web app with seeded UI bugs, graded by code, can run in `pnpm test` against the mock model, provided the browser touches only that fixture inside the temp directory; our [mock-model rule](../../../AGENTS.md#process-for-documenting-an-sdk) allows read-only tools inside a temp directory but does not name a browser, so the todo should say so. The WebArena-Verified Hard subset, restricted to GitLab and shopping, can run nightly, with each step's action, snapshot, screenshot and HAR in the session log so it can be re-graded. Injection resistance needs its own suite, run CAISI's way with adaptive, multi-attempt attacks and success reported at k attempts; WASP's GitLab tasks and BrowseSafe-Bench are the closest ready-made candidates. Live-web suites and OSWorld belong only in occasional external comparisons, never in a gate.

## Seven problems remain open as of November 2026

Seven questions stay open after this research, ordered from the one that blocks [Round W](../../plans/build-coding-agent.md#52-round-w-builds-the-coding-agent) to the ones that only shape the platform. Each names the proposed change that would settle or contain it.

1. **Cloudflare egress for a browser.** We do not know whether Sandbox SDK 0.x's outbound rules cover every process (the Containers page says 1.0's cover the whole container), whether Chromium trusts the ephemeral interception CA, or whether E2B's and Vercel's firewalls cover a browser. Only a test on each backend will tell: changes 2 and 3.
2. **CDP latency.** Nobody has measured the latency of per-action CDP round trips from a Worker or Lambda to a hosted browser, which change 13's `BrowserProvider` will pay on every action.
3. **Tenant isolation in Browser Run.** Cloudflare documents no tenant isolation boundary for Browser Run beyond incognito contexts and a fresh browser's process-level isolation, which matters for tenants under [ADR 0042](../../decisions/0042-generated-code-isolation.md): change 14.
4. **Prompt injection.** It has no fix. The best BrowseSafe detector's recall of 0.841 misses about one injection in six ([BrowseSafe](https://arxiv.org/html/2511.20597)), and adaptive attackers succeed far more often than vendor figures: changes 10 and 11.
5. **Scoped logins.** No vendor lets us scope a filled login so that an injected agent cannot carry the session to another origin: change 17 defers logged-in browsing until one does.
6. **Screenshot redaction.** No guidance exists on redacting personal data from agent screenshots: changes 8 and 9.
7. **Representations and graders.** No study compares page representations on 2026 models, and benchmark verdicts are wrong often enough that our own graders need audits: change 11.

Bot walls are a known limit rather than an open question; see Browser Run's limits above.

Two scope calls belong with these changes. The coding agent's in-sandbox browser should ship before any hosted-browser seam, because it needs no new seam and covers the jobs most competitors ship. And the platform should not offer browsing until change 14's ADR and change 15's tests exist, because a tenant's browser combines untrusted pages with whatever the tenant connects to it.

## Browser use is a network problem, so ADR 0043 comes first

Browser use turns out to be a network problem far more than a model problem. Every vendor ships a capable driver, every hosted browser speaks CDP, and the coding agents we checked use the browser for the same narrow job of checking their own work. The part that decides safety is the layer below the browser: whether its traffic leaves through the egress allowlist, whether it can reach the metadata address, and whether anything it can touch holds a credential. Our accepted architecture already answers all three for `bash`, and the most urgent finding is that on Cloudflare it answers them for no HTTPS client until change 2 adds interception to N46b.

The owner's first decision is ADR 0043. Putting a logged-out Chromium inside the existing sandbox gives the coding agent verified UI changes and PR evidence with no new seam, no new vendor and no new credential path. The hosted-browser seam, logged-in browsing and the platform's browsing agents can then wait for a task that needs them, each behind its own ADR, with the injection suite from change 11 measuring the risk before any of them ships.
