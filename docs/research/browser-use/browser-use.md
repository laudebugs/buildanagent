# Our agents should drive a credential-free browser from outside the sandbox

Our agents can handle tasks that need a web browser without changing the architecture we already accepted. The loop stays in the Durable Object, the browser runs somewhere the model's keys never reach, and every page the browser loads leaves through the same egress allowlist as `bash` ([ADR 0036](../../decisions/0036-loop-outside-sandbox-and-pr-approval.md)). For the personal coding agent, the first browser should be a headless Chromium inside the task's existing hosted sandbox, pointed at the dev server on the sandbox's own localhost, logged out and holding no credentials. That is how Copilot, Jules, Codex Cloud, Cursor and Devin use a browser as of November 2026: to check their own UI work and attach a screenshot or video to the pull request ([GitHub changelog](https://github.blog/changelog/2025-07-02-copilot-coding-agent-now-has-its-own-web-browser/); [Jules changelog](https://jules.google/docs/changelog/2025-08-07); [Codex Browser](https://learn.chatgpt.com/docs/browser); [Cursor blog](https://cursor.com/blog/agent-computer-use); [Devin docs](https://docs.devin.ai/work-with-devin/testing-and-recordings.md)). Browsing the open web, and the multi-user platform's browsing agents, need a hosted browser reached over a Chrome DevTools Protocol (CDP) WebSocket. Every hosted browser we checked hands one out, so a single `BrowserProvider` seam can cover Cloudflare, AWS and Vercel.

The same research answers five narrower questions, with every version, price and status as of November 2026. The model should see an accessibility snapshot whose nodes carry short refs, with screenshots only on request, and most of the token bill depends on whether each action returns a full snapshot. Cloudflare Browser Run is the cheapest hosted browser and fits our Durable Object loop natively; AWS has AgentCore Browser; Vercel has no browser of its own. Anthropic, OpenAI and Google all ship computer-use tools that the client executes, but they disagree on coordinates, batching and the safety handshake, and only three of our eight documented SDKs wrap them. Prompt injection from web content remains unsolved: adaptive attackers still succeed far more often than vendor figures suggest, so the boundary has to be the network allowlist and the absence of credentials, not the model. Only self-hosted, deterministically graded suites such as WebArena-Verified can gate a release. We therefore propose seventeen changes to our plans, todos and ADRs, led by a new ADR 0043 that places the coding agent's browser inside the sandbox and a fix to the Cloudflare sandbox backend without which no HTTPS page loads at all.

This report uses four terms throughout. A **browser tool** is any tool that lets the model drive a browser. An **in-sandbox browser** is Chromium running inside one of our `SandboxClient` sandboxes. A **hosted browser** is a browser service such as Browser Run or Browserbase. A **computer-use tool** is a model vendor's screenshot-and-action tool. The `"browser"` sandbox tier proposed in [portable-agents.md](../deployment/portable-agents.md#browser-sandboxes-save-compute-but-cannot-hold-the-credential-boundary) is a different idea, a sandbox that runs in the user's tab, and this report does not revisit it. For the storage and wake mechanics that any long browser task inherits, see [storage-and-wake.md](../deployment/storage-and-wake.md).

## Accessibility snapshots with refs won, and per-action output sets the token bill

By November 2026 the default page representation is an accessibility-tree snapshot in which every node carries a short ref that the next tool call passes back. Playwright MCP returns lines such as `- textbox "What needs to be done?" [ref=e5]`, and a ref stays valid "until the page changes"; a stale one fails with "Ref <ref> not found in the current page snapshot" ([Playwright MCP snapshots](https://playwright.dev/mcp/snapshots)). Chrome DevTools MCP tags nodes with a `uid` and tells the model to "Prefer taking a snapshot over taking a screenshot" ([chrome-devtools-mcp tool reference](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md)). Vercel Labs' agent-browser uses `@e1` refs, and Anthropic's new browser toolset targets elements as `{"type":"ref","ref":"ref_2"}` ([agent-browser README](https://github.com/vercel-labs/agent-browser/blob/main/README.md); [Claude browser use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/browser-use-tool), read through a summarizing fetch). Playwright's own comparison rates snapshots "Low — text only" in token cost and "Exact" in precision, against "High — image tokens" and "Approximate" for screenshots, though it publishes no measured numbers ([Playwright MCP snapshots](https://playwright.dev/mcp/snapshots)).

The other representations survive as fallbacks. Raw HTML is "often too large to be fed to LLMs" unfiltered, which is why Mind2Web filtered it with a small model first ([Mind2Web](https://arxiv.org/abs/2306.06070)). Set-of-marks overlays "turn out to be not effective for web agents" in SeeAct, whose authors found grounding rather than planning to be the bottleneck ([SeeAct](https://arxiv.org/abs/2401.01614)). Pure screenshots remain the only option for canvas, video and some cross-origin iframes, and on Claude a 1920×1080 screenshot costs about 1,560 input tokens after the default resize, or 2,691 unresized ([Claude vision docs](https://platform.claude.com/docs/en/build-with-claude/vision)). The production report "Building Browser Agents" reached about 85% on WebGames with "accessibility tree snapshots with selective vision", against about 50% for earlier agents and 95.7% for humans ([arXiv 2511.19477](https://arxiv.org/abs/2511.19477)). No peer-reviewed study compares HTML, snapshots, set-of-marks and pixels on 2026 models for both tokens and success, so the hybrid default rests on vendor convergence and 2023–2025 papers.

**The bigger token lever is whether each action returns a full snapshot.** Playwright MCP can snapshot one subtree, search the snapshot with `browser_find`, write it to a file, or turn off the snapshot that actions return (`--snapshot-mode none`); DevTools MCP returns a post-action snapshot only when `includeSnapshot` is set ([playwright-mcp README](https://github.com/microsoft/playwright-mcp/blob/main/README.md); [chrome-devtools-mcp tool reference](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md)). The same mechanism explains the CLI-versus-MCP debate. Microsoft says in both Playwright READMEs that CLI plus skills is "more token-efficient" because it avoids "loading large tool schemas and verbose accessibility trees", but gives no numbers ([playwright-cli README](https://github.com/microsoft/playwright-cli/blob/main/README.md)). Vercel's "93% less context" figure for agent-browser appears only in third-party write-ups, and we found no Vercel source for it ([paddo.dev, secondary](https://paddo.dev/blog/agent-browser-context-efficiency/)). Checkly's independent re-run in July 2026 found MCP sessions ending at about 48–50k tokens and CLI sessions at about 45–48k, a gap that "largely closed" once harnesses deferred MCP tool loading and Playwright MCP wrote snapshots to disk (secondary write-up, no tool versions given) ([Checkly](https://www.checklyhq.com/blog/mcp-vs-cli-token-efficiency/)). Our tool registry already defers tool schemas, so our harness gets the CLI's savings by returning file paths and on-request snapshots, whichever transport carries the tool.

CDP is the protocol every option speaks. WebDriver BiDi is still a W3C Working Draft, last updated 13 November 2026 ([W3C TR](https://www.w3.org/TR/webdriver-bidi/)), and even Puppeteer keeps CDP as Chrome's default "since not all CDP features are supported by WebDriver BiDi yet" ([Puppeteer docs](https://github.com/puppeteer/puppeteer/blob/main/docs/webdriver-bidi.md)). Playwright's `connectOverCDP` works with any Chromium endpoint but is "significantly lower fidelity" than its own `connect()` protocol, which needs a Playwright server on the far side ([Playwright BrowserType docs](https://github.com/microsoft/playwright/blob/main/docs/src/api/class-browsertype.md)). Playwright also exposes the snapshot machinery directly: `ariaSnapshot` has an `'ai'` mode that emits refs, and `Page.getByRef` (added in 1.64) resolves one ([Playwright release notes](https://github.com/microsoft/playwright/blob/main/docs/src/release-notes-js.md)). A TypeScript harness can therefore build its own ref tools on the library without adopting any agent framework.

## Every hosted browser hands out a CDP URL, so the loop can stay outside

Every hosted browser we checked returns a CDP WebSocket, or in AWS's case a WebSocket streaming endpoint, that a loop on Workers, Lambda or Vercel Functions connects to. The model's keys therefore never enter the browser, and the CDP URL itself becomes the one secret the host must hold. Steel says its connection URL "holds a token that controls the session", and Browser Use warns that "the credential-bearing CDP URL" can leak through transport errors ([Steel security](https://steel.dev/docs/platform/security-and-compliance); [Browser Use docs](https://docs.browser-use.com/llms-full.txt)). Live View URLs carry the same power over every logged-in account in the session, which is why Cloudflare expires them after 5 minutes by default ([Cloudflare Live View](https://developers.cloudflare.com/browser-run/features/live-view/)).

**Cloudflare Browser Run fits our first target natively.** The product formerly called Browser Rendering now runs Chrome 152, offers stateless Quick Actions (`/markdown`, `/snapshot`, `/accessibilityTree` and others) and full Browser Sessions over Puppeteer, Playwright or raw CDP ([Browser Run overview](https://developers.cloudflare.com/browser-run/); [changelog](https://developers.cloudflare.com/browser-run/changelog/)). A Worker reaches it through a `browser` binding that needs no API token, while any other environment connects with a Bearer token to `wss://api.cloudflare.com/client/v4/accounts/{account_id}/browser-run/devtools/browser` ([CDP](https://developers.cloudflare.com/browser-run/cdp/); [binding API](https://developers.cloudflare.com/browser-run/reference/browser-binding-api/)). Our pinned `agents` 0.33.0 adds `agents/browser`, whose `browserTool` gives the model "one browser that stays open between turns" and lets it write CDP code that runs in Dynamic Workers; "The model never starts or closes the browser" ([Browse the Web, mirror at agents@0.33.0](../../reference/cloudflare-agents/source/agents/docs/agents/browse-the-web.md)). Two network controls sit outside the browser: Guardrails apply per-session hostname allowlists to Puppeteer, Playwright and CDP sessions but not to Quick Actions, and Outbound Workers route chosen hosts through a Worker that "can reach a private service, add authentication, or transform the response" ([Guardrails](https://developers.cloudflare.com/browser-run/features/guardrails/); [Outbound Workers](https://developers.cloudflare.com/browser-run/features/outbound-workers/)). A human handoff (`Cloudflare.handoff`, then `Cloudflare.handoffComplete`) covers MFA, CAPTCHAs and "sensitive credentials you do not want to pass to an automation script" ([Human in the Loop](https://developers.cloudflare.com/browser-run/features/human-in-the-loop/)).

Browser Run's limits shape how an agent must use it. An idle session closes after 60 seconds by default and 20 minutes at most, and sessions also close when Browser Run rolls out a release ([Limits](https://developers.cloudflare.com/browser-run/limits/)). It has no saved-profile product, no IP rotation and no CAPTCHA solving, and Cloudflare always labels its traffic as a bot, signed with Web Bot Auth ([FAQ](https://developers.cloudflare.com/browser-run/faq/)). Its docs recommend incognito contexts to separate tasks and describe no per-session VM. Concurrency is also contested: the limits page, updated 14 October 2026, gives 200 concurrent browsers and 3 new browsers per second on Workers Paid, while a 15 April 2026 changelog entry says 120 and 1; the newer page should win, but the conflict needs a recheck before we size anything on it ([Limits](https://developers.cloudflare.com/browser-run/limits/); [changelog](https://developers.cloudflare.com/browser-run/changelog/)). A task that outlives its browser must therefore keep any state it needs in Durable Object storage and re-create the browser on wake.

**AWS has a native option; Vercel has none.** AgentCore Browser runs each session in a container, with a 15-minute default and 8-hour maximum, an automation endpoint for Playwright, a Live View endpoint, and recordings written to the customer's own S3 bucket ([AgentCore Browser](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-tool.html)). It bills $0.0895 per active vCPU-hour and $0.00945 per GB-hour, with "I/O wait and idle time" free ([AgentCore pricing](https://aws.amazon.com/bedrock/agentcore/pricing/)). AWS does not publish a session's vCPU and memory, so our estimate of about $0.04 per hour for a 2 GB session at 25% CPU is only an estimate. A secondary source says the managed `aws.browser.v1` runs only in public network mode, so VPC egress control needs a custom browser ([hidekazu-konishi.com, secondary](https://hidekazu-konishi.com/entry/what_agentcore_browser_keeps_and_where_its_traffic_goes.html)). Vercel's docs only show headless Chromium inside a Function through `@sparticuz/chromium`, which wants 1,600 MB or more of memory ([Vercel Functions limitations](https://vercel.com/docs/functions/limitations)). Community guides run agent-browser inside Vercel Sandbox, but we found no official Vercel page for it ([skills.sh, secondary](https://skills.sh/vercel/vercel-plugin/vercel-sandbox)). Because Browser Run accepts CDP from "any environment that supports WebSocket connections", one Browser Run account can serve the Vercel target too ([CDP](https://developers.cloudflare.com/browser-run/cdp/)).

For a single owner, Browser Run on Cloudflare and AWS, and Browser Run over CDP from Vercel, is the cheapest path that needs no new vendor.

**An in-sandbox browser costs more but sees the sandbox's localhost.** A hosted browser cannot load `http://localhost:3000` inside our sandbox without an exposed preview URL, while Chromium in the same sandbox can. It also inherits the sandbox's `SandboxPolicy`, `EgressPolicy` and conformance suite, so it adds no seam ([harness plan §3.4](../../plans/build-harness.md)). The catch on Cloudflare is HTTPS. Cloudflare Sandbox's outbound rules apply to HTTPS "only when your class sets `interceptHttps` to `true`", which installs an ephemeral CA at `/etc/cloudflare/certs/cloudflare-containers-ca.crt`; with interception off, HTTPS "reach[es] every host while `enableInternet` is `true`, and fail[s] while it is `false`" ([Cloudflare Sandbox outbound traffic](https://developers.cloudflare.com/sandbox/guides/outbound-traffic/)). [N46b](../../todos/ready/N46b-cloudflare-sandbox-backend.md) today compiles `EgressPolicy` to `enableInternet = false` plus `allowedHosts` and says nothing about interception, so as written no allowlisted HTTPS host would load in Chromium or anything else. The page also does not say whether the rules apply to every process, and we have not checked whether Chromium trusts that CA through its own certificate store, or whether E2B's and Vercel's firewalls cover a browser process at all.

## Vendor computer-use tools need one adapter each, and only three of our SDKs wrap them

All three model vendors make the client execute every action, but their tools differ in five ways that a portable harness must absorb. Anthropic's GA `computer_toolset_20260801` sends each of its 17 actions as its own `tool_use` block tagged `"toolset_name": "computer"`, in ordered batches; after a failure the client answers every later action with "Not executed: an earlier computer action in this turn failed." ([Claude computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool), read through a summarizing fetch). Its `browser_toolset_20260801` adds 31 browser actions, four of them off by default, that target accessibility refs and fall back to coordinates ([Claude browser use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/browser-use-tool)). **Opus 5.5 and Sonnet 5.5 return a 400 on the Claude API for the older `computer_20251124` tool**, so a legacy loop that reads `input.action` stops working on current models ([Claude computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool#earlier-tool-versions)). OpenAI's GA `computer` tool returns batched `actions[]` in one `computer_call`, the old `computer-use-preview` model is shut down, and for GPT-6 Astra OpenAI now recommends "code execution", a function tool whose script the application runs against Playwright ([OpenAI computer use guide](https://developers.openai.com/api/docs/guides/tools-computer-use.md); [migration](https://developers.openai.com/api/docs/guides/tools-computer-use-integration.md)). Gemini made `computer_use` a built-in tool of mainline models from Gemini 3.5 Flash in June 2026, with coordinates on a normalised 0–999 grid ([Google blog](https://blog.google/innovation-and-ai/models-and-research/gemini-models/introducing-computer-use-gemini-3-5-flash/); [Gemini computer use docs](https://aistudio.google.com/docs/computer-use), read through a summarizing fetch).

| | Anthropic | OpenAI | Google |
| --- | --- | --- | --- |
| Coordinates | screenshot pixels; client resizes to the image limit | environment pixels; `detail: "original"` advised | 0–999 normalised grid |
| Batching | one `tool_use` per action, halt on failure | `actions[]` in one call | parallel function calls, a screenshot with each reply |
| Safety handshake | server-side classifiers, nothing to acknowledge | `pending_safety_checks` to acknowledge | `safety_decision`, answered with `safety_acknowledgement` |
| Structured page channel | browser toolset refs | `BrowserToolset` function tools or code execution | none |
| Toolset overhead | about 4,500 input tokens for the default computer members | not published | not published |

The vendor tools also reveal where the industry thinks safety lives. Anthropic's docs recommend a dedicated low-privilege VM, no credentials, a domain allowlist and human confirmation of consequential actions ([Claude computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)). OpenAI tells integrators to confirm purchases, destructive changes and data transmission, noting that "Typing sensitive information into a form counts as transmission" ([OpenAI guide](https://developers.openai.com/api/docs/guides/tools-computer-use.md)). Both Anthropic's and OpenAI's client SDKs now ship toolset base classes that take a driver the application supplies, with Browserbase, Browser Use, Daytona and E2B publishing drivers ([Claude SDK toolsets](https://platform.claude.com/docs/en/agents-and-tools/tool-use/browser-use-sdk); [OpenAI guide](https://developers.openai.com/api/docs/guides/tools-computer-use.md)). Published benchmark scores for these tools come from different harnesses and are mostly self-reported or secondary, such as a 78.4 OSWorld-Verified figure for Gemini 3.5 Flash that the blog shows only in a chart ([the-decoder, secondary](https://the-decoder.com/google-bakes-computer-control-directly-into-gemini-3-5-flash-letting-the-model-see-and-operate-your-screen/)). A portable harness needs one internal action model, in screenshot pixels with ordered batches and a provider-neutral safety record routed to the approval pipeline, plus a thin adapter per vendor.

## Coding agents use the browser to check their own work inside the sandbox

Every major cloud coding agent now ships a browser inside its own sandbox, and they use it for the same four jobs: reproduce a bug, verify a UI change, run an end-to-end flow, and attach evidence. Copilot's coding agent got a Playwright MCP browser in July 2025 and "share[s] screenshots of what it has done in its pull request" ([GitHub changelog](https://github.blog/changelog/2025-07-02-copilot-coding-agent-now-has-its-own-web-browser/)). Jules added Playwright to its base image and sends "a screenshot of the front end along with any code changes" ([Jules changelog](https://jules.google/docs/changelog/2025-08-07)). Cursor's cloud agents run a full VM desktop and deliver PRs with videos, screenshots and logs; Devin records an annotated video of "the single most important end-to-end flow" after CI is green ([Cursor blog](https://cursor.com/blog/agent-computer-use); [Devin docs](https://docs.devin.ai/work-with-devin/testing-and-recordings.md)). Claude Code's cloud VMs preinstall Chrome for Testing with `CHROME_PATH` set, and do not support an interactive SSO login ([Claude Code cloud environments](https://code.claude.com/docs/en/cloud-environments)). Lovable and Replit test selectively, after cheaper checks, and Claude Code warns that always-on browser tools raise context use ([Lovable](https://docs.lovable.dev/features/browser-testing); [Replit](https://docs.replit.com/references/agent/app-testing.md); [Claude Code Chrome docs](https://code.claude.com/docs/en/chrome)).

Copilot is also the only vendor that documents its firewall covering the browser. In its cloud sandboxes the firewall applies to the built-in Playwright server and its browser processes, but not to repository-configured replacement MCP servers, and blocked requests are reported in the PR ([Copilot firewall](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/customize-the-agent-firewall)). Our own plans name no browser, Playwright or screenshot anywhere: the only web tool is N21's `fetch`, which runs through `EgressProxy.fetch` and must fail on a non-allowlisted host ([N21](../../todos/ready/N21-builtin-tools.md)), and [W2](../../todos/ready/W2-coding-tool-profile.md)'s tool profile adds git tools and the test command. The plans also leave one question open that a browser forces: whether browser actions inside the sandbox count as prompt-free "commands" under [CA6](../../plans/build-coding-agent.md#ca6-the-draft-pull-request-is-the-approval-point-accepted). Our coding agent therefore needs a headless Chromium in the sandbox with snapshot, screenshot, console and network tools, viewport presets, evidence attached to the draft PR, and egress rules that bind the browser process itself; driving the owner's logged-in browser and full-desktop computer use can wait.

## Prompt injection stays unsolved, so the network and the credential are the boundary

Every vendor that has shipped a browser agent calls prompt injection unsolved, and independent adaptive attacks still succeed far more often than vendor figures suggest. A browser is the textbook leg of Willison's lethal trifecta, an agent that combines "private data, untrusted content, and external communication", because any page load, form post or image request can carry data out ([Simon Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). Our harness already treats that outbound leg as the one to cut ([agent guide](../../guides/agent.md)). The evidence below supports cutting it in the network layer and keeping credentials out of reach, and treating every model-side defense as one layer among several.

### Vendor figures fall to 1–2%, and adaptive attackers multiply them

Anthropic's figures fell sharply between 2025 and 2026. The Claude for Chrome pilot in August 2025 measured 23.6% attack success without mitigations and 11.2% with them across 123 test cases ([Claude blog](https://claude.com/blog/claude-for-chrome)). In November 2025 an internal best-of-N attacker with 100 attempts per environment succeeded 1.4–2.4% of the time against improved safeguards, against 8.0–13.8% for the models alone; Anthropic added that "A 1% attack success rate … still represents meaningful risk" ([Anthropic research](https://www.anthropic.com/research/prompt-injection-defenses)). Its current, undated support page reports "less than 0.08%" for Claude Opus 4.8 in internal testing, with risk "still non-zero" ([Claude Help Center](https://support.claude.com/en/articles/12902428-use-claude-in-chrome-safely)). A circulating 0–0.3% figure for the Claude in Chrome launch appears only in secondary write-ups that name conflicting models, so we treat it as unverified ([kdpisda.in, secondary](https://kdpisda.in/claude-in-chrome-general-availability/)). OpenAI's CISO called prompt injection "a frontier, unsolved security problem" at the Atlas launch, and OpenAI later said it "is unlikely to ever be fully 'solved'"; that second quote comes from secondary coverage because OpenAI's post returned HTTP 403 ([Simon Willison](https://simonwillison.net/2025/Oct/22/openai-ciso-on-atlas/); [TechInformed, secondary](https://techinformed.com/openai-hardens-chatgpt-atlas-against-prompt-injection-with-auto-attacker-red-team/)).

Independent tests measure a different attacker. NIST CAISI found the strongest baseline attack on AgentDojo reached 11%, while attacks built for the target model reached 81%, and it recommends multi-attempt evaluation ([NIST CAISI](https://www.nist.gov/blogs/caisi-research-blog/insights-ai-agent-security-large-scale-red-teaming-competition)). BrowseSafe++ took attacks that "succeed on only a few percent of tasks" and, after revising them with agent feedback, reached up to 95.41% ([arXiv 2610.17457](https://arxiv.org/abs/2610.17457)). VPI-Bench deceived browser-use agents in up to 100% of cases on some platforms with visual injections, and WASP's injections in GitLab and Reddit issues partly succeeded in up to 86% of cases ([VPI-Bench](https://arxiv.org/abs/2506.02456); [WASP](https://arxiv.org/abs/2504.18575)). The March 2026 Gray Swan, CAISI and UK AISI competition ran 272,000 attempts against 13 frontier models and found "All models proved vulnerable", from 0.5% for Claude Opus 4.5 to 8.5% for Gemini 2.5 Pro ([arXiv 2603.15714](https://arxiv.org/abs/2603.15714)). WASP's setting matters most for us, because a coding agent that reads issue trackers is exactly its target. Brave's "unseeable" injections, faint text in screenshots that the model reads, show that text sanitising alone cannot protect a screenshot-driven agent ([Brave](https://brave.com/blog/unseeable-prompt-injections/)). We should plan for the adaptive number.

Detection classifiers help but leave gaps. BrowseSafe's fine-tuned detector reached an F1 of 0.904 in under a second, against 0.863 for Sonnet 4.5 at 23–36 seconds and 0.360 for PromptGuard-2 ([BrowseSafe](https://arxiv.org/html/2511.20597)). Its architecture is cheap to copy: treat all browser-tool output as untrusted, chunk large pages, run detection in parallel with planning, and replace flagged output with a placeholder. Google's Chrome design runs a similar page classifier "in parallel to the planning model's inference" ([Google blog](https://blog.google/security/architecting-security-for-agentic/)). In our pipeline such a detector can deny or ask as a hook but never approve, which [ADR 0019](../../decisions/0019-permission-pipeline-and-approval-modes.md) already requires.

### The designs that hold use a deterministic gate outside the model

The published designs converge on one rule: an agent that reads untrusted web content must not also hold private data and an outbound channel, unless a deterministic gate decides each consequential action. Meta's Rule of Two lets an agent combine at most two of untrusted input, sensitive access and external state change; its browsing research assistant avoids sensitive access by running "in a tightly restricted sandbox with no pre-loaded session data" ([Meta AI](https://ai.meta.com/blog/practical-ai-agent-security/)). Google's Chrome agent adds a User Alignment Critic that "see[s] only metadata about the proposed action", and Origin Sets that split read-only origins from origins where the agent may act ([Google blog](https://blog.google/security/architecting-security-for-agentic/)). OpenAI's Atlas offers a "logged out mode" and reserves logged-in mode for "well-scoped actions on very trusted sites" ([Simon Willison quoting OpenAI](https://simonwillison.net/2025/Oct/22/openai-ciso-on-atlas/)). CaMeL shows the provable version, separating control flow from data flow at a cost of 77% against 84% task success on AgentDojo ([CaMeL](https://arxiv.org/abs/2503.18813)). Our coding agent can follow this design cheaply: browsing runs with untrusted input and the sandbox's outbound allowlist but no private data, while the git push takes no web input and goes through the GitHub App route, with the owner's merge as the confirmation ([CA4](../../plans/build-coding-agent.md#ca4-the-loop-runs-in-a-durable-object-outside-the-sandbox-accepted); [CA6](../../plans/build-coding-agent.md#ca6-the-draft-pull-request-is-the-approval-point-accepted)).

### Logins belong to the host, and a saved cookie jar is a credential

The consensus for logins is that the model never sees a secret. 1Password's agentic autofill fills a Browserbase session "if, and only if, the human approves", without Browserbase or the model seeing the value; Chrome's agent signs in through Google Password Manager; Steel "never returns the stored password, so your agent and your model never need it" ([1Password](https://1password.com/blog/closing-the-credential-risk-gap-for-browser-use-ai-agents); [Google blog](https://blog.google/security/architecting-security-for-agentic/); [Steel credentials](https://steel.dev/docs/logins/credentials)). A persisted session is still a credential. Browserbase contexts keep cookies, local storage and autofill data until deleted, and its docs advise one context per site and login and `persist: false` for read-only reuse ([Browserbase contexts](https://docs.browserbase.com/features/contexts)). A prompt-injected agent inside a logged-in context can use the session without ever seeing a password, and no vendor documents a way to stop a filled session from navigating to an attacker's origin after login. Web Bot Auth only identifies the operator; as of November 2026 it is an IETF working-group draft (`draft-ietf-webbotauth-httpsig-protocol-01`), not an RFC ([IETF datatracker](https://datatracker.ietf.org/wg/webbotauth/documents/)). Our order of preference is therefore an API or OAuth token injected at an egress route outside the sandbox ([HD15 in the harness plan](../../plans/build-harness.md)), then an approval-gated fill by the host with the filled fields masked from later screenshots and snapshots, then a human handoff.

### Egress must be enforced below the browser

A browser that renders attacker pages is both an exfiltration channel and an SSRF primitive. Image loads and links leak data, as OWASP's scenario of an injected image URL shows, and the metadata address `169.254.169.254` returns cloud credentials to any request that reaches it ([OWASP LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/); [modpagespeed blog, secondary](https://modpagespeed.com/blog/air-gapped-headless-fetch-ssrf-pinning/)). Browser-level filters do not hold: Playwright MCP's `--allowed-origins` "*does not* serve as a security boundary", and browser-use calls its domain restrictions "a guard for an aligned model, not a sandbox" ([playwright-mcp README](https://github.com/microsoft/playwright-mcp/blob/main/README.md); [browser-use README](https://github.com/browser-use/browser-use/blob/main/README.md)). A secondary source reports CVE-2026-5607, an SSRF in `mcp-browser-agent` up to 0.8.0, which we have not checked on NVD ([SentinelOne, secondary](https://www.sentinelone.com/vulnerability-database/cve-2026-5607/)). Our N20 proxy already refuses allowlisted names that resolve to `127.0.0.1` or `169.254.169.254` ([N20](../../todos/ready/N20-credential-proxy.md)), and that check must also cover every subresource Chromium fetches. The rule follows: the browser's traffic leaves through the same `EgressPolicy` as `bash`, the harness checks each navigation URL against that allowlist in a before-tool-call hook, and the proxy enforces it again by resolved address.

### Screenshots are tenant data with a retention cost

Screenshots and snapshots capture whatever the page shows, including personal data and session details. OpenAI keeps deleted ChatGPT agent screenshots for up to 90 days ([OpenAI Help](https://help.openai.com/articles/11752874)). Browserbase records video by default, Browser Run keeps rrweb recordings for 30 days when enabled, and AgentCore writes recordings to the customer's S3 ([Browserbase replay](https://docs.browserbase.com/platform/browser/observability/session-replay); [Browser Run recording](https://developers.cloudflare.com/browser-run/features/session-recording/); [AgentCore Browser](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-tool.html)). We found no vendor or standards guidance on redacting personal data in agent screenshots. Our telemetry should therefore reference screenshot and snapshot blobs rather than inline them, store the blobs encrypted with a short expiry, mask fields the host filled, and keep recording off unless the owner or a tenant turns it on.

## Only self-hosted, deterministically graded suites can gate a release

Browser benchmarks split into self-hosted suites with programmatic graders, which are reproducible, and live-web suites graded by a model, which drift. WebArena-Verified re-audits WebArena's 812 tasks, replaces model judges with deterministic comparison, ships Docker images for its GitLab, shopping and other sites, offers a 258-task Hard subset, and can re-grade offline from captured HAR files ([webarena-verified README](https://github.com/ServiceNow/webarena-verified)). REAL's 112 tasks run on deterministic site replicas, and BrowserGym wraps MiniWoB, WebArena and others behind one interface ([REAL](https://arxiv.org/abs/2504.11543); [BrowserGym](https://github.com/ServiceNow/BrowserGym)). A BrowserGym issue reports that its WebArena-Verified reward gives partial credit where the official harness does not, so scores from the two are not comparable (from a search summary) ([BrowserGym issue #412](https://github.com/ServiceNow/BrowserGym/issues/412)). We found no official WebArena-Verified leaderboard and no confirmed Claude or GPT scores on it.

Live-web numbers mostly measure the judge and the scaffold. Online-Mind2Web's own authors showed a search-only agent scoring 51% on WebVoyager but 22% on their suite ([Online-Mind2Web](https://arxiv.org/html/2504.01382v4)). Princeton's independent HAL board tops out near 42% on Online-Mind2Web, while vendor boards report about 97% with their own judges ([HAL](https://hal.cs.princeton.edu/online_mind2web); [Browser Use, self-reported](https://browser-use.com/posts/online-mind2web-benchmark)). On the desktop, aggregators report OSWorld-Verified scores above the 72.36% human baseline, but the official board could not be read, so those figures are secondary ([Presenc, secondary](https://presenc.ai/research/osworld-computer-use-leaderboard-2026)); OSWorld 2.0's long tasks still hold the best reported result to 20.6% ([OSWorld 2.0](https://osworld-v2.xlang.ai/)). An audit of 150 failure-scored trajectories found 15.3% of FAIL verdicts wrong, partly because trajectories omitted decisive visual evidence, and HAL found its own cost accounting double-counted nested spans by up to 2× ([arXiv 2607.28367](https://arxiv.org/abs/2607.28367); [HAL](https://hal.cs.princeton.edu/online_mind2web)). Both lessons apply to our OpenTelemetry spans and our eval reports.

Our eval tiers follow from this. A small fixture web app with seeded UI bugs, graded by code, can run in `pnpm test` against the mock model, provided the browser touches only that fixture inside the temp directory, which is what our [mock-model rule](../../../AGENTS.md#process-for-documenting-an-sdk) permits. The WebArena-Verified Hard subset, restricted to GitLab and shopping, can run nightly, with each step's action, snapshot, screenshot and HAR in the session log so it can be re-graded. Injection resistance needs its own suite, run CAISI's way with adaptive, multi-attempt attacks and success reported at k attempts; WASP's GitLab tasks and BrowseSafe-Bench are the closest ready-made candidates. Live-web suites and OSWorld belong only in occasional external comparisons, never in a gate.

## Seven problems remain open as of November 2026

Seven questions stay open after this research, ordered from the one that blocks Round W to the ones that only shape the platform. First, we do not know whether Cloudflare Sandbox's outbound rules apply to every process, whether Chromium trusts the ephemeral interception CA, or whether E2B's and Vercel's firewalls cover a browser; only a test on each backend will tell. Second, nobody has measured the latency of per-action CDP round trips from a Worker or Lambda to a hosted browser. Third, Cloudflare documents no per-session isolation boundary for Browser Run beyond incognito contexts, which matters for tenants under [ADR 0042](../../decisions/0042-generated-code-isolation.md). Fourth, prompt injection has no fix; the best BrowseSafe detector's recall of 0.841 misses about one injection in six ([BrowseSafe](https://arxiv.org/html/2511.20597)), and adaptive attackers multiply vendor rates. Fifth, no vendor lets us scope a filled login so that an injected agent cannot carry the session to another origin. Sixth, no guidance exists on redacting personal data from agent screenshots. Seventh, no study compares page representations on 2026 models, and benchmark verdicts are wrong often enough that our own graders need audits. Bot walls are a known limit rather than an open question: Browser Run always identifies as a bot and solves no CAPTCHAs, so hostile consumer sites will need a stealth vendor or a human.

## Conclusion

Browser use turns out to be a network problem far more than a model problem. Every vendor ships a capable driver, every hosted browser speaks CDP, and every coding agent uses the browser for the same narrow job of checking its own work. The part that decides safety is the layer below the browser: whether its traffic leaves through the allowlist, whether it can reach the metadata address, and whether anything it can touch holds a credential. Our accepted architecture already answers all three for `bash`, and the most urgent finding is that, on Cloudflare, it does not yet answer them for any HTTPS client until N46b turns interception on.

The owner's first decision is ADR 0043. Putting a logged-out Chromium inside the existing sandbox gives the coding agent verified UI changes and PR evidence with no new seam, no new vendor and no new credential path. The hosted-browser seam, logged-in browsing and the platform's browsing agents can then wait for a task that needs them, each behind its own ADR, with the injection suite from change 11 measuring the risk before any of them ships.
