## Q1. What tool profile does the coding agent plan define (W2), and is there any browser, web fetch or MCP plan?

### Takeaway
No plan, ADR or todo mentions a browser, Playwright, screenshots or computer use as a capability for our agents. The only web tool is the harness built-in `fetch` (N21), which runs through the egress proxy's allowlist. W2 adds git tools and a test-command completion check on top of N21. MCP is planned as a removable harness built-in (N24 stdio, N25 HTTP). The platform plan reaches integrations "through MCP servers the user names", and only by URL.

### Inferences
- A browser would be a new tool family. No plan section, todo or ADR covers it, so adding one needs at least a todo, and probably an ADR for placement.

## Q2. What hard rules must a browser capability satisfy?

### Takeaway
Seven rules bind any browser capability, and they are stricter on the platform. (1) The loop stays outside the sandbox and the sandbox holds no credentials (ADR 0036, HD15, CA4). (2) Egress is default-deny with an allowlist, compiled per backend as `EgressPolicy`, and in-process fetch is gated by the same allowlist. (3) Every tool, MCP included, passes the deny-first permission pipeline, and the model can never widen its sandbox. (4) Backends fail closed and state honestly what they stop. (5) MCP and tool output is untrusted by default. (6) On the platform, tenant code runs only in a fresh hosted sandbox with no stdio MCP commands, and no tenant credential enters a sandbox. (7) Tests run offline, and mock models never touch the host.

### Cited Findings
- **The loop stays outside the sandbox, and the sandbox holds no credentials.** "Keep the loop outside the sandbox, and keep credentials out of it ([ADR 0036](docs/decisions/0036-loop-outside-sandbox-and-pr-approval.md))." — `AGENTS.md` "Planned architecture (when code starts)". ADR 0036 Decision: "The loop runs in the task's Durable Object (or the target's equivalent host), and the sandbox only runs commands. The sandbox holds no credentials. Inside the sandbox and its allowlist, commands run without per-call prompts; any call outside those bounds becomes a signed pause. The owner's merge of the draft pull request is the commit point." — `docs/decisions/0036-loop-outside-sandbox-and-pr-approval.md`
- **The coding agent plan's reasons for that placement.** "First, the sandbox never holds the model key or the GitHub token, which is HD15's rule. Second, a reclaimed sandbox costs a resume rather than a session… Third, the loop needs only `fetch` and state… The sandbox runs commands; it never decides them." — `docs/plans/build-coding-agent.md` "CA4. The loop runs in a Durable Object, outside the sandbox (accepted)"
- **Approval tiers in the coding agent.** "Inside the sandbox, with network limited to the allowlist, commands run without per-call prompts… The harness's permission pipeline still asks before any call that leaves those bounds, such as a new egress host, and that ask becomes a signed pause the owner answers from the CLI or a PR comment (HD5). The owner's merge is the commit point." — `docs/plans/build-coding-agent.md` "CA6. The draft pull request is the approval point (accepted)". ADR 0036 consequence: "The permission pipeline (HD12) is configured for this profile in W2; no new pipeline mode is added."
- **The permission pipeline.** "The pipeline runs hooks, deny rules, ask rules, the mode, allow rules and the host callback, in that order; no match means ask interactively and deny headless… Modes are `default`, `accept_edits`, `read_only`, `bypass` and `shadow`. A classifier may deny or ask as a hook, and may allow only as the host callback." — `docs/decisions/0019-permission-pipeline-and-approval-modes.md` (Accepted). Sticky allowances "refuse interpreter prefixes (`bash -c`, `sh -lc`, `node -e`, `bun run` and similar) and any pattern containing a secret"; "A tool that sets `RegisteredTool.approvalReuse: "none"` takes neither sticky nor grouped resolutions". — `docs/plans/build-harness.md` "HD12. Three middle-ground modes, and no classifier allow outside the host callback"

- **The model cannot widen its sandbox.** "Our harness therefore gives no tool parameter or model output the power to widen the sandbox. - **In-process tools must go through the egress allowlist.** "Claude's `strictAllowlist`, however, is 'Enforced for sandboxed commands only — in-process tools such as WebFetch are not gated by this setting'… Our proxy is default-deny and logs every request, our in-process fetch tools go through the same allowlist, and every backend fails closed". — `docs/guides/agent-harness.md` §6, paragraph "Network isolation is a host-side proxy, and in-process tools often bypass it". ### Inferences
- A browser is the textbook trifecta leg. It reads untrusted pages and can send data out through any GET, form post or image load. Under our rules its traffic must leave through the same `EgressPolicy` allowlist as `bash`, and its page content should be `outputTrust: "untrusted"`.
- A browser running inside the sandbox must not hold logged-in cookies or tokens, because ADR 0036 and HD15 put credentials only at egress. Authenticated browsing would need credential routes or an outside hosted browser whose session is held by the host.
- On the platform, a generated agent that uses a browser falls under ADR 0042's "user's named MCP hosts" rule only if it reaches the browser as a URL-based MCP server. A stdio Playwright MCP command would fail the gate.
- Mock-model tests would have to deny browser tools by name, as AGENTS.md requires for host tools, unless the browser runs against a local fixture page inside the temp directory.

### Gaps
- No document says whether a browser's traffic counts as "commands" (prompt-free inside the allowlist) or as a separate tool class for CA6's approval rule.

## Q3. Where would a browser naturally live, and which interfaces would it reuse?

### Takeaway
Two placements fit our seams. (a) Chromium inside the existing hosted sandbox (Cloudflare Sandbox, E2B or Vercel Sandbox), driven by `exec` or an in-sandbox Playwright MCP server, which inherits `SandboxPolicy` and `EgressPolicy`. (b) A separate hosted-browser seam called from the loop outside the sandbox, like `fetch` through `EgressProxy.fetch` or an HTTP MCP server. That seam would be an eighth portable seam needing a conformance suite under ADR 0033. One Cloudflare detail matters for (a): Cloudflare Sandbox's `allowedHosts` and outbound handlers apply to HTTPS only when `interceptHttps` is on. Otherwise HTTPS "reach[es] every host while `enableInternet` is `true`". The "browser" tier the portable-agents report proposes is a different thing: running the sandbox inside the user's browser tab. It is not browser use.

A Durable Object runs the loop: "Model calls are waits on `fetch`, which do not count against Workers' CPU limit; alarms run for at most 15 minutes, so a long turn ends each step with a wake". — same file §3, bullet "Task runner (W4)"
- **Measurement todos.** N49 measures "Cold start, snapshot and per-call overhead on the hosted backends", with "p50 and p95 per backend". — `docs/todos/ready/N49-hosted-sandbox-measurement.md`. N19 does the same locally for `srt` and Docker. — `docs/todos/ready/N19-sandbox-measurement.md`
- **The Docker backend's network.** It uses "`--cap-drop ALL --read-only --network none`" plus "A proxy socket mount when the policy allows any host (N20)". — `docs/todos/done/N17-docker-backend.md`. A local Chromium would need that socket and the HD15 `CONNECT` proxy.
- **The platform's sandbox restriction.** "Cloudflare Sandbox or E2B behind `SandboxClient`, and never a local `srt` or Docker backend." — `docs/plans/build-agent-platform.md` "PF9. Generated code runs only in a fresh hosted sandbox (accepted, ADR 0042)"

### Inferences
- **(a) In-sandbox Chromium** reuses `SandboxClient`, `SandboxPolicy.network`, `EgressPolicy`, `exec` and the conformance suite, and the sandbox's `stops` covers it. Costs: a larger base image, which touches CA8 and W11 (snapshot cache) and N49's cold-start numbers. Also, on Cloudflare the allowlist covers HTTPS only with `interceptHttps: true`, so N46b's compiler must set it whenever the browser or any HTTPS client runs, or the allowlist does not hold. N46b's scope today says only "`EgressPolicy` compiled to `enableInternet = false`, `allowedHosts` and an `outboundByHost` handler" (`docs/todos/ready/N46b-cloudflare-sandbox-backend.md`). The quote above says HTTPS fails while `enableInternet` is false and interception is off, so a browser would reach no HTTPS site at all unless interception is on.
- **(b) A hosted-browser seam outside the sandbox** (such as Cloudflare Browser Rendering, which the Cloudflare reference skipped as a binding) would be an in-process or provider-executed tool called by the loop. Following the `fetch` precedent and the guide's "in-process tools often bypass it" warning, its target URLs must be checked against the same `EgressPolicy.allow`. Under ADR 0033 it would also need per-target implementations and N45 cases, as an eighth seam.
- MCP is the cheapest integration path. A URL-based Playwright-style MCP server fits N25's "HTTP servers reached through the egress proxy's allowlist" and ADR 0042's "user's named MCP hosts". A stdio one fits N24 locally but is banned for platform tenant code.

- Whether Cloudflare Sandbox's outbound rules apply to every process, Chromium included, is not stated on the fetched page.
- No document covers Cloudflare Browser Rendering's network controls or pricing; the Cloudflare reference only records that its examples were skipped.

## Q6. Which ADR numbers are free, and what is the ADR format?

### Takeaway
ADRs 0001–0042 exist, so the next free number is **0043**. No other branch on `origin` adds ADRs numbered 0043 or later. Records are short (about 19 lines), with a title that states the decision, Status, Date and Plan lines, then Context, Decision and Consequences.

### Cited Findings
- "**Name:** `NNNN-kebab-title.md`, numbered in order of creation. Numbers are never reused." — `docs/decisions/README.md` "Format"
- "**Header:** a title that states the decision, then **Status**, **Date** and a **Plan** link to the section that argues it." — same
- "**Status:** `Proposed` (written, not yet reviewed), `Proposed — owner to confirm` (needs the owner's call), `Accepted` (reviewed in P4 or confirmed by the owner), or `Superseded by NNNN`. A record marked provisional names the todo whose check can change it." — same
- "**Sections:** Context (the question and the evidence, in a few sentences), Decision (what we chose), Consequences (what changes, what follows, and who acts)." — same
- "**Changes:** never rewrite an accepted record. Write a new one and mark the old one superseded." — same
- **The index row format** is `| [NNNN](file.md) | Decision | Status | [Plan anchor](...) |`. The last row is 0042, and "ADRs 0022–0031 record the triage agent's decisions. ADR 0032 defers that agent, so they stay as written". — `docs/decisions/README.md` "Index"
- **Git check.** `git ls-tree` over every remote branch (`origin/main`, `origin/claude/zen-allen-25p088`) found no file `docs/decisions/004[3-9]*`. HEAD is `d7d0a9a Claim U15: research browser use for our agents`.
- **The plan convention.** Each plan's decision table has `# | Decision | Status | ADR` columns, and some decisions carry "none" for ADR (for example CA7–CA9, PF3, PF5, PF10–PF12). — `docs/plans/build-coding-agent.md` §2; `docs/plans/build-agent-platform.md` §2
- **The superseding rule in practice.** A change after N19 "is a new ADR that supersedes this one, because an accepted record is never rewritten." — `docs/decisions/0020-default-sandbox-backend.md`

### Inferences
- A browser placement decision for the coding agent would add a CA11 row in `build-coding-agent.md` §2 plus ADR 0043. A platform rule would add a PF13 row plus 0044. Neither would need to supersede 0036 or 0042 if the browser stays behind `SandboxClient` and `EgressPolicy` and the MCP-by-URL rule.
- If the browser lives outside the sandbox as its own seam, ADR 0033's "same seven seams" would need a superseding record, because 0033 is accepted.
