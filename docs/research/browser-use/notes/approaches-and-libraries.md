## Page representations: what the model sees, what it costs, how reliable it is

### Takeaway
By November 2026 the default representation is an accessibility-tree (ARIA) snapshot in which every node carries a short ref (`e5`, `@e1`, `uid`) that the next tool call passes back. Playwright MCP, Playwright CLI, Chrome DevTools MCP, agent-browser and Stagehand all use it. Screenshots, coordinates and set-of-marks overlays survive as opt-in fallbacks for canvas or visual-only content. Vendors (Anthropic, Playwright, the "Building Browser Agents" paper) are converging on a hybrid: tree first, screenshot when needed. Raw HTML is used mainly for extraction and in older research systems, because it is too large to feed to a model unfiltered.

### Cited Findings
**Accessibility-tree snapshots with refs**
- Playwright MCP "uses accessibility snapshots instead of screenshots. Every tool that interacts with the page returns a structured tree of accessible elements with refs". Example output: `- textbox "What needs to be done?" [ref=e5]`. A ref is `e` plus a number, prefixed with a frame id inside iframes (`f1e12`), "unique within a single snapshot", valid "until the page changes", and "assigned to every node the accessibility tree exposes, not just interactive ones". A stale ref fails with "Ref <ref> not found in the current page snapshot. Try capturing new snapshot." — [Playwright MCP docs: Snapshots](https://playwright.dev/mcp/snapshots)
- Playwright's own comparison table on that page: snapshots are "Low — text only" token cost, "Exact" precision, "Deterministic — same structure = same interaction"; screenshots are "High — image tokens", "Approximate — requires coordinate guessing", "Variable — layout changes break coordinates", and need a vision model. This is a vendor claim with no measured numbers. — [Playwright MCP docs: Snapshots](https://playwright.dev/mcp/snapshots)
- Ways to cut snapshot size in Playwright MCP: `browser_snapshot` takes `target` (snapshot one subtree), `depth`, `boxes`, and `filename` (save to a file instead of returning it); `browser_find` "searches the current page's snapshot and returns only the matching nodes plus a few lines of surrounding context … far cheaper than capturing the whole snapshot"; `--snapshot-mode none` turns off the snapshot that action tools return; `--mobile` is documented as "Mobile pages are usually lighter, which saves tokens". — [Playwright MCP docs: Snapshots](https://playwright.dev/mcp/snapshots); [playwright-mcp README](https://github.com/microsoft/playwright-mcp/blob/main/README.md)
- The underlying Playwright API is public. `Page.ariaSnapshot` has an `'ai'` mode that emits refs, `Page.getByRef` (added in 1.64) "locates an element by its aria ref, such as `e2`", and `Locator.ariaSnapshotJSON` / `Page.ariaSnapshotJSON` (1.63) return the snapshot as JSON with `mode`, `depth` and `boxes` options. A custom TypeScript harness can therefore build ref-based tools on Playwright directly, without MCP. — [Playwright release notes (JS)](https://github.com/microsoft/playwright/blob/main/docs/src/release-notes-js.md)
- Chrome DevTools MCP `take_snapshot`: "Take a text snapshot of the target page based on the a11y tree. The snapshot lists page elements along with a unique identifier (uid)… Prefer taking a snapshot over taking a screenshot." Action tools take `uid` and an optional `includeSnapshot` (default false), so a post-action snapshot is opt-in. — [chrome-devtools-mcp tool reference](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md)
- Chrome DevTools MCP design principle: "Token-Optimized: Return semantic summaries. 'LCP was 3.2s' is better than 50k lines of JSON. Files are the right location for large amounts of data." — [chrome-devtools-mcp design principles](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/design-principles.md)
- agent-browser: "`snapshot` returns the page as compact text with a ref such as `@e1` for each element." `snapshot -i` lists only interactive elements. "Refs describe the page at the time of the snapshot. After navigation or a DOM change, take a new snapshot before using refs again." — [agent-browser README](https://github.com/vercel-labs/agent-browser/blob/main/README.md)
- Stagehand claims "Hybrid accessibility-tree trimming gives agents exactly the page context they need and nothing more", and "Page snapshots merge every frame's accessibility tree by default". Its `act()` resolves to an XPath selector (e.g. `xpath=/html[1]/body[1]/div[1]/span[1]`). — [Stagehand README](https://github.com/browserbase/stagehand/blob/main/README.md); [Stagehand v4 Act docs](https://docs.stagehand.dev/v4/basics/act.md)

**Raw HTML / DOM**
- Mind2Web (2023): "the raw HTML of real-world websites are often too large to be fed to LLMs"; filtering it first with a small LM "significantly improves the effectiveness and efficiency of LLMs". — [Mind2Web, arXiv 2306.06070](https://arxiv.org/abs/2306.06070)
- WebArena (2023) baselines use the accessibility tree as observation. The best GPT-4 agent reached 14.41% end-to-end task success against 78.24% for humans. — [WebArena, arXiv 2307.13854](https://arxiv.org/abs/2307.13854)

**Set-of-marks (SoM) screenshots**
- Set-of-Mark prompting overlays numbered marks (from segmentation models such as SAM) on an image so that a multimodal model can refer to regions by label. — [SoM, arXiv 2310.11441](https://arxiv.org/abs/2310.11441)
- SeeAct (2024): GPT-4V completed 51.1% of live-website tasks *when its textual plans were manually grounded*, but "set-of-mark prompting turns out to be not effective for web agents, and the best grounding strategy … leverages both the HTML structure and visuals". Grounding, not planning, was the bottleneck. — [SeeAct, arXiv 2401.01614](https://arxiv.org/abs/2401.01614)
- VisualWebArena (2024) introduced visually grounded web tasks and identified "several limitations of text-only LLM agents". The abstract gives no SoM numbers; the paper body was not checked here. — [VisualWebArena, arXiv 2401.13649](https://arxiv.org/abs/2401.13649)

**Pure pixels / computer use**
- Anthropic's computer use tool "works through screenshots and coordinates alone". `computer_toolset_20260801` gives 17 member tools (`screenshot`, `left_click`, `type`, `zoom`, …), needs no beta header on Claude 5.x models, and supports batched actions. — [Claude docs: computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)
- Image token cost on Claude (from the docs table): 1000×1000 px ≈ 1,296 tokens; a 1920×1080 screenshot is resized to 1456×819 ≈ 1,560 tokens on the default path, or 2,691 tokens unresized at higher resolution; 3840×2160 ≈ 1,560 (resized) or 4,784 tokens. Each screenshot step therefore costs roughly 1.3k–4.8k input tokens. — [Claude docs: vision](https://platform.claude.com/docs/en/build-with-claude/vision)

**Hybrids**
- Anthropic's browser use tool (`browser_toolset_20260801`, 27 member tools by default such as `navigate`, `read_page`, `left_click`, `screenshot`, plus four optional ones) lets Claude work "through its structure (the accessibility tree, elements, forms, and tabs) and through screenshots and viewport coordinates". The SDK toolset (beta, Python and TypeScript) runs the loop and URL/approval checks, and "you supply the driver"; a reference driver in claude-quickstarts controls Chromium over CDP. — [Claude docs: browser use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/browser-use-tool); [Claude docs: SDK toolsets](https://platform.claude.com/docs/en/agents-and-tools/tool-use/browser-use-sdk)
- Playwright MCP keeps the snapshot as the default and adds coordinate tools behind `--caps=vision` (`browser_mouse_click_xy`, `browser_mouse_drag_xy`, `browser_mouse_move_xy`, `browser_mouse_wheel`, down/up). `browser_take_screenshot` says: "Use browser_snapshot for actions by default. With the vision capability enabled, use screenshot coordinates … for elements not exposed in the accessibility snapshot." `--snapshot-boxes` adds `[box=x,y,width,height]` to every node, which links tree and pixels. — [playwright-mcp README](https://github.com/microsoft/playwright-mcp/blob/main/README.md)
- Chrome DevTools MCP also offers `click_at` (x, y) next to uid-based tools. — [chrome-devtools-mcp tool reference](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md)
- "Building Browser Agents" (production report, Nov 2025): "hybrid context management combining accessibility tree snapshots with selective vision" reached about 85% on WebGames (53 challenges), against about 50% for prior browser agents and 95.7% for humans. The authors argue that "architectural decisions determine success or failure" and that prompt injection makes general autonomous browsing "fundamentally unsafe". — [arXiv 2511.19477](https://arxiv.org/abs/2511.19477)
- OSWorld-Human (desktop, not web): planning, reflection and judging calls dominate latency, later steps take up to 3× longer than early ones, and the best agents take 2.7–4.3× more steps than necessary. Secondary (search summary, not verified in the paper body): adding the a11y tree to screenshots raised per-task latency in several apps. — [arXiv 2506.16042](https://arxiv.org/abs/2506.16042)
- browser-use 1.0 drops the fixed representation altogether. The model writes Python cells against raw CDP in a persistent REPL ("The model, a REPL and CDP. That's the whole agent."), using screenshots when `use_vision` is on. — [browser-use README](https://github.com/browser-use/browser-use/blob/main/README.md)

### Inferences
- For a TypeScript harness, ref-based ARIA snapshots built on Playwright's public `ariaSnapshot({mode:'ai'})` plus `getByRef` are the cheapest deterministic option. Add a screenshot (≈1.5k tokens at 1456×819 on Claude) only on demand or for canvas content.
- The biggest token lever is not the representation itself but *whether every action returns a full snapshot*. Tools that return snapshots only on request (DevTools MCP's `includeSnapshot`, Playwright MCP's `--snapshot-mode none`, `browser_find`, `filename`) control cost more than any choice of format.
- Refs expire on every DOM change, so the harness must re-snapshot after navigation; this is the main source of "stale ref" failures.

### Gaps
- No primary, peer-reviewed head-to-head study measuring tokens *and* success for raw HTML vs ARIA snapshot vs SoM vs pixels on the same 2026 models was found. The paper figures are from 2023–2025 models.
- No vendor-published per-page token figure for a typical ARIA snapshot was found. Third-party figures exist (see the CLI-vs-MCP section) and are secondary.

## Protocols: CDP, WebDriver BiDi, Playwright's protocol, and what hosted browsers expose

### Takeaway
CDP remains the lingua franca: every hosted browser checked (Browserbase, Cloudflare Browser Run, Notte, the providers agent-browser supports) hands out a CDP WebSocket URL, and Playwright, Puppeteer, Stagehand, agent-browser, Chrome DevTools MCP and browser-use all speak it. As of November 2026 WebDriver BiDi is still a W3C Working Draft; Chrome and Firefox implement it and Safari does not ship it. Playwright's own wire protocol (`browserType.connect` to a Playwright server) gives higher fidelity than `connectOverCDP`, but needs a Playwright server on the remote side.

### Cited Findings
- WebDriver BiDi's W3C status is "W3C Working Draft", last updated 13 November 2026. — [W3C TR: WebDriver BiDi](https://www.w3.org/TR/webdriver-bidi/)
- Puppeteer "supports WebDriver BiDi automation with Chrome and Firefox. When launching Firefox … the WebDriver BiDi Protocol is enabled by default. When launching Chrome, CDP is still used by default since not all CDP features are supported by WebDriver BiDi yet"; unsupported features throw `UnsupportedOperation`. Chrome opts in with `protocol: 'webDriverBiDi'`. — [Puppeteer docs: WebDriver BiDi](https://github.com/puppeteer/puppeteer/blob/main/docs/webdriver-bidi.md)
- Safari: caniuse lists Safari up to 26.5 TP as not supporting WebDriver BiDi. WebKit's open-source WebKitWebDriver has BiDi work in progress (Igalia), which is separate from Apple's safaridriver. Secondary (search summaries of caniuse and an Igalia talk). — [caniuse: WebDriver BiDi](https://caniuse.com/wf-webdriver-bidi); [Web Platform DX explorer](https://web-platform-dx.github.io/web-features-explorer/features/webdriver-bidi); [Igalia slides](https://www.igalia.com/downloads/slides/lauromoura-advancingwebdriverbidisupportinwebkit.pdf)
- Playwright `BrowserType.connectOverCDP`: "only supported for Chromium-based browsers. … This connection is significantly lower fidelity than the Playwright protocol connection via `BrowserType.connect`. If you are experiencing issues or attempting to use advanced functionality, you probably want to use `BrowserType.connect`." It accepts `endpointURL`, `headers` and `isLocal`. — [Playwright docs source: class-browsertype.md](https://github.com/microsoft/playwright/blob/main/docs/src/api/class-browsertype.md)
- Playwright 1.65 added `timeout` and `signal` options to `CDPSession.send`, so raw CDP stays reachable from Playwright. — [Playwright release notes (JS)](https://github.com/microsoft/playwright/blob/main/docs/src/release-notes-js.md)
- No mention of WebDriver BiDi appears in Playwright's JS release notes (grep over the full file returned nothing). Playwright's Firefox and WebKit support goes through its own patched builds, not BiDi. The absence was checked; the patched-builds mechanism is from background knowledge, not a source fetched here. — [Playwright release notes (JS)](https://github.com/microsoft/playwright/blob/main/docs/src/release-notes-js.md)
- Browserbase's Playwright quickstart connects with `chromium.connectOverCDP(session.connectUrl)`. — [Browserbase Playwright quickstart](https://docs.browserbase.com/welcome/quickstarts/playwright.md)
- Cloudflare's browser product is now listed as "Browser Run". It offers CDP sessions via `/devtools` endpoints, "Connect Playwright to Browser Run sessions from any Node.js environment … using the Chrome DevTools Protocol", the same for Puppeteer, MCP clients through `chrome-devtools-mcp`, a Workers-side Playwright binding, a deployable Playwright MCP server, a Stagehand server, and Live View. — [Cloudflare Browser Run llms.txt](https://developers.cloudflare.com/browser-run/llms.txt)
- Notte: "Every cloud session exposes a CDP endpoint", used via `p.chromium.connect_over_cdp(session.cdp_url())`. Notte can also attach to "any CDP-compatible browser" with `EXTERNAL_CDP_URL`. — [Notte README](https://github.com/nottelabs/notte/blob/main/README.md)
- agent-browser lists cloud providers Browserbase, Browserless, Browser Use, Kernel and AWS "AgentCore", and the engines Lightpanda and Obscura; its daemon "controls the browser over the Chrome DevTools Protocol". — [agent-browser README](https://github.com/vercel-labs/agent-browser/blob/main/README.md)

### Inferences
- A portable seam for our four targets should be "give me a CDP WebSocket URL (+ headers)". It is the only interface that every hosted browser checked exposes, and it is what Cloudflare Browser Run, Browserbase and the AWS AgentCore Browser (via agent-browser) offer. Use Playwright `connectOverCDP` on it, and accept the documented fidelity loss.
- BiDi is not yet a reason to choose a library. It matters only if we need Firefox, and even Puppeteer keeps CDP as the Chrome default.

### Gaps
- Not checked: AWS Bedrock AgentCore Browser's and Vercel Sandbox's own docs on the protocols they expose (agent-browser's provider list is the only source here).
- No primary Chrome or Mozilla status page for BiDi coverage was fetched.

## Libraries and tools

### Takeaway
The TypeScript-native, actively maintained, permissively licensed options are Playwright (+ Playwright MCP and Playwright CLI), Chrome DevTools MCP / Puppeteer, agent-browser (a Rust CLI shipped through npm) and Stagehand v4 (MIT). Big 2026 shifts: Stagehand v4 removed `agent()` (August 2026), browser-use 1.0 became a Python REPL-over-CDP agent (November 2026), Notte 1.10 removed its agent loop, and the `magnitudedev/magnitude` repo now hosts an unrelated local-inference product. Everyone now ships a CLI with skills next to (or instead of) MCP.

**Playwright MCP (`@playwright/mcp` 0.0.86)**
- Pitch: "structured accessibility snapshots, bypassing the need for screenshots or visually-tuned models"; "Deterministic tool application. Avoids ambiguity common with screenshot-based approaches." — [playwright-mcp README](https://github.com/microsoft/playwright-mcp/blob/main/README.md)
- Core tools include `browser_navigate`, `browser_snapshot`, `browser_find`, `browser_click` (param `target`: "Exact target element reference from the page snapshot, or a unique element selector"), `browser_type`, `browser_fill_form`, `browser_select_option`, `browser_press_key`, `browser_wait_for`, `browser_evaluate`, `browser_run_code_unsafe`, `browser_take_screenshot`, `browser_tabs`, `browser_network_requests`, `browser_console_messages`, `browser_file_upload`, `browser_handle_dialog`. Opt-in groups through `--caps`: `vision` (coordinate mouse tools), `pdf`, `devtools` (tracing, video, highlight), `network` (route/mock), `storage` (cookies, local/session storage, storage state), `config`; testing tools include `browser_generate_locator` and `browser_verify_*`. The README lists 72 tools in total. — [playwright-mcp README](https://github.com/microsoft/playwright-mcp/blob/main/README.md)
- Page-defined WebMCP tools are offered to the agent as `webmcp_<tool>` by default (`--no-webmcp` to opt out), since Playwright 1.64; Playwright bundles MCP and CLI as `npx playwright mcp` / `npx playwright cli` since 1.62. — [Playwright release notes (JS)](https://github.com/microsoft/playwright/blob/main/docs/src/release-notes-js.md)
- Remote and attach options: `--cdp-endpoint`, `--cdp-header`, `--cdp-timeout`, `remoteEndpoint` (a Playwright server WebSocket, with `exposeNetwork`/`headers`), `--extension` (attach to the user's running Chrome or Edge via the "Playwright Extension"), `--isolated`, `--shared-browser-context` for HTTP clients, `--allowed-origins`/`--blocked-origins` (which explicitly "*does not* serve as a security boundary"), `--redact-url-params`, and a Docker image. `--codegen typescript` emits Playwright code for actions taken. — [playwright-mcp README](https://github.com/microsoft/playwright-mcp/blob/main/README.md)

**Playwright CLI (`@playwright/cli`, binary `playwright-cli`)**
- "Playwright CLI with SKILLS". Key feature: "Token-efficient. Does not force page data into LLM." Install skills with `playwright-cli install --skills`, or go "skills-less" and let the agent read `playwright-cli --help`. Commands act on refs (`click <ref>`, `fill <ref> <text>`, `snapshot --depth=N`, `find <text>`, `eval`, `screenshot`). Snapshots are written to `.playwright-cli/page-*.yml` and linked from the output. Named sessions (`-s name`, `PLAYWRIGHT_CLI_SESSION`) persist between calls; headless sessions stop after an hour idle; a dashboard shows live screencasts. `attach --cdp=<url>`, `attach --extension=chrome`; config takes `cdpEndpoint`, `cdpHeaders`, `remoteEndpoint`. — [playwright-cli README](https://github.com/microsoft/playwright-cli/blob/main/README.md)

**Chrome DevTools MCP (`chrome-devtools-mcp` 1.13.0, Google)**
- "Chrome DevTools for agents … available as a Model-Context-Protocol (MCP) server and as a CLI", with skills; "Uses puppeteer to automate actions in Chrome and automatically wait for action results"; officially supports only Chrome and Chrome for Testing. Performance tools may send trace URLs to the CrUX API (`--no-performance-crux` to disable). — [chrome-devtools-mcp README](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/README.md)
- Tool groups (counts from the tool reference): input automation 10, navigation 6, emulation 2, performance 3, network 2, debugging 10, memory 14, network mocks 2, extensions 5, third-party 2, WebMCP 2, PWAs 4, WebAuthn 1. `--slim` exposes a reduced set (navigate, evaluate, screenshot). — [tool reference](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md); [slim tool reference](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/slim-tool-reference.md)
- Remote options: `--browserUrl` (e.g. `http://127.0.0.1:9222`), `--wsEndpoint` with `--wsHeaders` (e.g. an `Authorization: Bearer` header), and `--autoConnect` to a local Chrome 144+ with remote debugging enabled via `chrome://inspect/#remote-debugging`. PWA tools need a pipe connection and do not work over `browserUrl`/`wsEndpoint`. — [chrome-devtools-mcp configuration](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/configuration.md)

**Stagehand (`@browserbasehq/stagehand` 4.4.0)**
- v4 migration: "`agent()` is gone. Nothing in v4 replaces it one-for-one." Rationale: `agent()` "was built for models that couldn't reliably drive a browser on their own". The replacements are **code mode** ("A coding assistant writes a Stagehand script, and you run that script. Browserbase recommends starting here") and **tool calling** (a model drives the full Stagehand API as tools). `act()`, `extract()` (Zod/Pydantic schema) and `observe()` (returns real selectors, so "credentials never reach the model") remain. — [Stagehand v3→v4 migration](https://docs.stagehand.dev/v4/migrations/v3.md); [Stagehand README](https://github.com/browserbase/stagehand/blob/main/README.md)
- Determinism and caching: `selfHeal` "re-infer[s] an action when its recorded selector breaks". Caching in v4 is **server-side on Browserbase only**: the key is "the instruction, page content, and the options you pass", it excludes the model configuration, a hit costs no LLM tokens, it must be requested per project by email, and "With a local browser … the `cache` option has no effect and every call runs inference". Browserbase recommends it only for repeated, non-personalised pages with stable URLs and no sensitive values. — [Stagehand v4 Act](https://docs.stagehand.dev/v4/basics/act.md); [Stagehand v4 caching](https://docs.stagehand.dev/v4/best-practices/caching.md)
- Browsers: `browserbase.launch`, `localBrowser.launch`, or `localBrowser.connect({ cdpUrl })` to attach to any Chromium over CDP. Browserbase regions: us-west-2, us-east-1, eu-central-1, ap-southeast-1. — [Stagehand v4 browser config](https://docs.stagehand.dev/v4/configuration/browser.md)
- Models: any provider via `provider/model` names (e.g. `openai/...`, `anthropic/...`, Google), or omit `model` and let the Browserbase Model Gateway pick one per call. — [Stagehand v4 models](https://docs.stagehand.dev/v4/configuration/models.md)
- Agent integrations: a `browse` CLI plus skill for coding agents ("No LLM key or Browserbase account needed for local use"), an MCP adapter, and native integrations including Claude and OpenAI CUA toolsets, the Vercel AI SDK, Mastra and a Pi extension. — [Stagehand README](https://github.com/browserbase/stagehand/blob/main/README.md); [Stagehand llms.txt](https://docs.stagehand.dev/llms.txt)

**agent-browser (Vercel Labs, 0.43.0)**
- "a native Rust CLI that gives an AI agent a browser it can drive one command at a time". A background daemon per `--session` holds the browser over CDP and closes after one hour idle. A click "fails, instead of reporting success, when the target is hidden, disabled, outside the viewport, or covered by another element". Locators: refs, CSS, text, XPath, semantic (`find role button click --name "Submit"`). Command groups cover network, cookies/storage, tracing, profiler, vitals, React, a11y, WebMCP, `batch`, `flow`, `auth` vault, `confirm`/`deny` and `diff`. Skills are versioned with the binary (`agent-browser skills get core`); the skills.sh stub tells the agent to load them. `agent-browser mcp` starts a stdio MCP server. Docs cover running in Vercel Sandbox. Binaries ship for macOS, Linux (glibc and musl) and Windows. — [agent-browser README](https://github.com/vercel-labs/agent-browser/blob/main/README.md)

**browser-use (Python 1.0.6) and TS options**
- 1.0: "The agent writes Python against raw CDP in a persistent REPL, on Pydantic AI." Default model `bu-4.0` on the Browser Use gateway and a Browser Use Cloud browser ($0.06 per browser-hour per the README). Exact pinning is urged ("releases can break things"). Domain restrictions are "a guard for an aligned model, not a sandbox", and `sensitive_data` redaction is "Not a sandbox: model-written Python can read the value". — [browser-use README](https://github.com/browser-use/browser-use/blob/main/README.md)
- TypeScript: the official project links "Browser Use Pi … Run a TypeScript browser agent built on Pi". The npm `browser-use` package is an "Unofficial, community-maintained TypeScript port … not developed, maintained, or endorsed by the browser-use maintainers", built on Playwright. — [browser-use README](https://github.com/browser-use/browser-use/blob/main/README.md); [webllm/browser-use README](https://github.com/webllm/browser-use/blob/main/README.md)

**Skyvern, Notte, Nanobrowser, Magnitude**
- Skyvern: "Automate Browser-based workflows using LLMs and Computer Vision"; "relies on Vision LLMs" rather than only XPath; "a Playwright extension" where standard actions accept an optional `prompt` for AI element location; TypeScript client `@skyvern/client`; AGPL-3.0 (shields badge). It claims 85.8% on WebVoyager (vendor blog, secondary). — [Skyvern README](https://github.com/Skyvern-AI/skyvern/blob/main/README.md); [Skyvern 2.0 blog](https://www.skyvern.com/blog/skyvern-2-0-state-of-the-art-web-navigation-with-85-8-on-webvoyager-eval/)
- Notte: SSPL-1.0. In 1.10 "The agent loop (`notte.Agent` …), workflows and local function execution were removed"; it now centres on stealth hosted sessions over CDP, vaults and observe/execute/scrape. Node SDK: `npm install notte-sdk`. — [Notte README](https://github.com/nottelabs/notte/blob/main/README.md)
- Nanobrowser: a Chrome extension (Apache-2.0) that "talks to the page only through Chrome's `chrome.debugger` API, and uses Puppeteer to keep track of frames"; supports vision models and local models (16k+ context recommended). — [Nanobrowser README](https://github.com/nanobrowser/nanobrowser/blob/master/README.md)
- Magnitude: the `magnitudedev/magnitude` README now describes "Run open models as fast as your hardware allows", a local inference runtime. The browser-agent npm package `magnitude-core` was last published 0.3.1 on 2026-02-08, and a separate `magnitudedev/browser-agent` repo has ~4.1k stars. Its maintenance status as a browser agent is unclear. — [magnitude README](https://github.com/magnitudedev/magnitude/blob/main/README.md); [npm magnitude-core](https://registry.npmjs.org/magnitude-core)

### Inferences
- The best fit for a TS harness with its own loop is Playwright (library) plus our own ref-snapshot tools, or embedding `@playwright/mcp` / `chrome-devtools-mcp` as an MCP server. Stagehand v4 has itself become a toolset that expects the caller to own the loop, which matches our architecture; its caching, however, is tied to Browserbase.
- "Self-healing" in 2026 means re-inferring a selector when a recorded one breaks (Stagehand `selfHeal`), or generating code once and re-running the model only on breakage (Stagehand code mode, Playwright MCP `--codegen`, `browser_generate_locator`). No library offers local, vendor-neutral action caching in TS any more; that would be ours to build.
- Skyvern (AGPL) and Notte (SSPL) carry copyleft or source-available licences that are risky for a platform serving other users; prefer the Apache-2.0/MIT options.

### Gaps
- Exact star counts and last-commit dates from the GitHub API could not be fetched (GitHub API blocked in this session); the shields.io figures are rounded.
- The current Magnitude browser-agent repo and its latest release were not inspected.
- Whether Stagehand v4 still offers any *local* (non-Browserbase) action cache was not confirmed beyond the caching page's statement that `cache` has no effect locally.

## CLI vs MCP: token claims

### Takeaway
Microsoft's Playwright team states in both READMEs that CLI + skills is "more token-efficient" than MCP for coding agents, but publishes no numbers. Vercel's "93% less context" figure for agent-browser circulates only through third-party write-ups; no Vercel primary statement was found. The most careful independent re-run (Checkly, July 2026) found the gap largely closed, because harnesses now defer MCP tool loading and Playwright MCP can write snapshots to disk.

### Cited Findings
- **Primary (Microsoft):** "Modern coding agents increasingly favor CLI–based workflows exposed as SKILLs over MCP because CLI invocations are more token-efficient: they avoid loading large tool schemas and verbose accessibility trees into the model context … MCP remains relevant for specialized agentic loops that benefit from persistent state, rich introspection, and iterative reasoning over page structure, such as exploratory automation, self-healing tests, or long-running autonomous workflows where maintaining continuous browser context outweighs token cost concerns." — [playwright-mcp README](https://github.com/microsoft/playwright-mcp/blob/main/README.md); identical text in [playwright-cli README](https://github.com/microsoft/playwright-cli/blob/main/README.md)
- **Primary (Google):** Chrome DevTools MCP ships both an MCP server and a CLI with skills, plus a `--slim` mode "for basic browser tasks only". — [chrome-devtools-mcp README](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/README.md)
- **Primary (Browserbase):** Stagehand recommends the `browse` CLI + skill for coding agents rather than the SDK. — [Stagehand README](https://github.com/browserbase/stagehand/blob/main/README.md)
- **Primary (Vercel Labs):** agent-browser describes "each step is one short shell call" and ships both CLI skills and an MCP server; its README makes no numeric token claim. — [agent-browser README](https://github.com/vercel-labs/agent-browser/blob/main/README.md)
- **Secondary:** "Vercel claims 93% less context than Playwright MCP"; other write-ups report 82.5% savings, or 1,364 vs 7,779 tokens on a six-step test. No Vercel source for the 93% was found. — [paddo.dev](https://paddo.dev/blog/agent-browser-context-efficiency/); [DEV: "15x cheaper"](https://dev.to/davekurian/vercels-agent-browser-is-15x-cheaper-than-playwright-mcp-and-thats-not-the-most-interesting-part-3ian)
- **Secondary:** a widely quoted ~114k (MCP) vs ~27k (CLI) tokens for one browser task, with unclear attribution (Playwright team vs a test-lab.ai benchmark, February 2026). Another report cites a sixfold token increase between Playwright MCP 0.0.30 and 0.0.32 on the same task. — search summary of [bug0.com](https://bug0.com/blog/playwright-cli-vs-playwright-mcp-ai-browser-testing-2026) and [Leapwork](https://leapwork.com/?p=13152); not verified
- **Secondary (independent measurement):** Checkly (Stefan Judis, 2026-07-30) ran the same shop task three times in Claude Code with Playwright MCP vs `playwright-cli` + skill. MCP sessions ended at ~48–50k tokens and CLI sessions at ~45–48k. The 2025 upfront cost of Playwright MCP's 48 tool schemas was ~5.9k tokens; skill descriptions cost ~30–50 tokens until loaded. Conclusion: the gap has "largely closed", because harnesses defer MCP tool loading and Playwright MCP writes snapshots to disk. No tool versions were given. — [Checkly blog](https://www.checklyhq.com/blog/mcp-vs-cli-token-efficiency/)

### Inferences
- The token difference comes from two mechanisms, not from the transport: (1) tool-schema preload, which deferred tool loading removes; and (2) whether snapshots and screenshots are inlined into the context or written to files and read selectively. Our harness can get the CLI's savings inside a native tool or MCP design by deferring schemas and returning file paths or diffs instead of full snapshots.
- CLIs presume a shell. For a harness whose loop runs outside the sandbox, a CLI means shelling into the sandbox; a native tool or MCP speaking CDP to a remote browser avoids that.

### Gaps
- No primary Vercel or Microsoft benchmark with numbers was found.
- No measurement against current versions (Playwright MCP 0.0.86, agent-browser 0.43.0) was found.

## Remote browser with the agent loop elsewhere (loop outside the sandbox)

### Takeaway
Almost everything can drive a remote browser over a CDP WebSocket. The loop and the MCP server or CLI daemon run on our side, and only the browser runs in the hosted sandbox. The exceptions are tools tied to a local or extension browser (Nanobrowser, the Playwright and agent-browser extension and auto-connect modes, Chrome DevTools MCP's PWA tools) and Stagehand's caching, which needs Browserbase.

### Cited Findings
- Playwright: `connectOverCDP(endpointURL, { headers })` for Chromium (lower fidelity), or `connect()` to a remote Playwright server (full fidelity). — [Playwright BrowserType docs](https://github.com/microsoft/playwright/blob/main/docs/src/api/class-browsertype.md)
- Playwright MCP: `--cdp-endpoint` + `--cdp-header`, or `remoteEndpoint` to a Playwright server; also an HTTP transport with `--shared-browser-context`. — [playwright-mcp README](https://github.com/microsoft/playwright-mcp/blob/main/README.md)
- Playwright CLI: `attach --cdp=<url>`, `cdpEndpoint`/`cdpHeaders`/`remoteEndpoint` in config. — [playwright-cli README](https://github.com/microsoft/playwright-cli/blob/main/README.md)
- Chrome DevTools MCP: `--wsEndpoint` + `--wsHeaders` (Bearer auth), `--browserUrl`; PWA tools require a pipe and do not work remotely; `upload_file` paths "have to be local to the browser instance (not the MCP)". Cloudflare documents using it against Browser Run sessions. — [chrome-devtools-mcp configuration](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/configuration.md); [tool reference](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md); [Cloudflare Browser Run llms.txt](https://developers.cloudflare.com/browser-run/llms.txt)
- Stagehand: `localBrowser.connect({ cdpUrl })` or `browserbase.launch()`; Cloudflare documents a Stagehand server on Browser Run. — [Stagehand v4 browser config](https://docs.stagehand.dev/v4/configuration/browser.md); [Cloudflare Browser Run llms.txt](https://developers.cloudflare.com/browser-run/llms.txt)
- agent-browser: `--cdp`, plus providers Browserbase, Browserless, Browser Use, Kernel and AgentCore; documented for Vercel Sandbox. — [agent-browser README](https://github.com/vercel-labs/agent-browser/blob/main/README.md)
- browser-use, Notte: cloud browsers by default (browser-use) or CDP sessions (Notte, plus `EXTERNAL_CDP_URL`). — [browser-use README](https://github.com/browser-use/browser-use/blob/main/README.md); [Notte README](https://github.com/nottelabs/notte/blob/main/README.md)
- Anthropic's browser/computer toolsets are client-side: "your application runs every call in an environment you control", and the SDK toolset takes a driver you supply (the reference driver speaks CDP). — [Claude docs: computer use tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool); [Claude docs: SDK toolsets](https://platform.claude.com/docs/en/agents-and-tools/tool-use/browser-use-sdk)
- Security caveats that apply to remote setups: Playwright MCP's origin lists are not a security boundary; browser-use's domain restrictions and secret redaction are "not a sandbox"; browser-use's local Chrome modes open an unauthenticated debugging port on 127.0.0.1. — [playwright-mcp README](https://github.com/microsoft/playwright-mcp/blob/main/README.md); [browser-use README](https://github.com/browser-use/browser-use/blob/main/README.md)

### Inferences
- Pattern consistent with ADR 0036 (loop outside the sandbox, no credentials in it): the loop and the browser tools (Playwright library or an embedded MCP server) run in our worker; the browser runs in Cloudflare Browser Run, Browserbase, AgentCore or Vercel Sandbox; the only shared secret is the CDP URL or header, held by the harness. The CDP endpoint grants full control of the browser, so it must be treated as a credential.
- File uploads and downloads cross the boundary and need explicit plumbing, because paths are local to the browser host.

### Gaps
- Latency of per-action CDP round trips from a Cloudflare Worker or a Lambda to a hosted browser was not measured or found in a primary source. (Stagehand claims it "runs as an extension next to the browser, cutting round-trip latency", a vendor claim.)
- Whether Playwright MCP runs inside a Cloudflare Worker (as opposed to Cloudflare's own deployable Playwright MCP) was not checked.
