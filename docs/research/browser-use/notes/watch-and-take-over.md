# Watching and taking over an agent's in-sandbox browser, as of November 2026

Scope: how a person watches a headless Chromium that runs inside our hosted sandbox (Cloudflare Sandbox first, then E2B and Vercel Sandbox), how they take control and hand it back, and how hosted Live View links are secured. The hosted products' basic Live View features are already covered in [hosted-browsers.md](hosted-browsers.md#cloudflare-browser-run-formerly-browser-rendering-our-first-target). This note re-checks only the facts it cites. Every source was fetched on 2026-11-19 unless marked **[secondary]**. GitHub repositories were read from shallow clones at the commits named below. No downloaded code was run.

## CDP streaming and input injection: what Chrome, Playwright and Puppeteer give us

### Takeaway
A headless Chromium can stream itself with no display server. `Page.startScreencast` pushes JPEG or PNG frames, and the client acknowledges each one. A viewer's clicks and keys go back through `Input.dispatchMouseEvent`, `Input.dispatchKeyEvent` and `Input.insertText`. Playwright 1.59+ wraps this as `page.screencast.start({ onFrame })`. Steel's Apache-2.0 `steel-browser` is a complete open-source viewer built on exactly these calls. It is the closest reference for our own relay.

### Cited Findings
**CDP screencast (tip-of-tree protocol, `browser_protocol.json` on `master`, version 1.3, fetched 2026-11-19):**
- `Page.startScreencast` is marked **experimental**. "Starts sending each frame using the `screencastFrame` event." Its parameters are `format` (`jpeg` | `png`), `quality` ("[0..100]"), `maxWidth`, `maxHeight`, `everyNthFrame` ("Send every n-th frame. Must be a positive integer."), `maxFramesInFlight` ("Maximum number of frames sent until screencastFrameAck is required. Defaults to 3.") and `sendLastFrame`. With `sendLastFrame`, the browser stores "the last produced frame in memory, which is immediately sent upon screencastFrameAck. This way, overall performance is traded for a better latency." — [browser_protocol.json](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/json/browser_protocol.json); [Page domain](https://chromedevtools.github.io/devtools-protocol/tot/Page/#method-startScreencast)
- The `Page.screencastFrame` event carries `data` ("Base64-encoded compressed image"), `metadata` and `sessionId` (the frame number). `metadata` (`ScreencastFrameMetadata`) holds `offsetTop`, `pageScaleFactor`, `deviceWidth`, `deviceHeight`, `scrollOffsetX`, `scrollOffsetY` and optional `timestamp` / `monotonicTimestamp`. `Page.screencastFrameAck({sessionId})` "Acknowledges that a screencast frame has been received by the frontend." `Page.screencastVisibilityChanged` reports when the page is shown or hidden. — [browser_protocol.json](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/json/browser_protocol.json)
- The protocol has no WebP option for screencast (only `jpeg`/`png`), although `Page.captureScreenshot` offers `jpeg`, `png` and `webp`. — [browser_protocol.json](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/json/browser_protocol.json)
- The protocol also has a new experimental video path, `Page.startScreenRecording` / `stopScreenRecording`. "Starts screencast video recording." Its parameters are `audio`, `maxWidth`, `maxHeight`, `frameRate` and `captureArea` (`target` | `browserWindow`), and it returns an `IO.StreamHandle` "that holds resulting screencast data". — [browser_protocol.json](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/json/browser_protocol.json)
- I could not read the git history of the protocol file, because the GitHub API was not enabled for that repository in this session. So I cannot say which Chrome milestone added `maxFramesInFlight`, `sendLastFrame` or `startScreenRecording`. See Gaps.

**CDP input:**
- `Input.dispatchMouseEvent` (stable) takes `type, x, y, modifiers, timestamp, button, buttons, clickCount, force, tangentialPressure, tiltX, tiltY, twist, deltaX, deltaY, pointerType`. `Input.dispatchKeyEvent` (stable) takes `type, modifiers, timestamp, text, unmodifiedText, keyIdentifier, code, key, windowsVirtualKeyCode, nativeVirtualKeyCode, autoRepeat, isKeypad, isSystemKey, location, commands`. `Input.insertText` (experimental) emulates "inserting text that doesn't come from a key press, for example an emoji keyboard or an IME". `Input.dispatchTouchEvent`, `dispatchDragEvent`, `imeSetComposition` and `synthesizeScrollGesture` also exist. — [browser_protocol.json](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/json/browser_protocol.json); [Input domain](https://chromedevtools.github.io/devtools-protocol/tot/Input/)
- `Input.setIgnoreInputEvents({ignore})` (stable): "Ignores input events (useful while auditing page)." — [browser_protocol.json](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/json/browser_protocol.json)

**Headless mode:**
- "Chrome now has unified Headless and headful modes. Since Chrome 132.0.6793.0 the old Headless mode is only available as a standalone binary named chrome-headless-shell." Before that, old Headless "didn't share any of the Chrome browser code in //chrome". — [Chrome Headless mode](https://developer.chrome.com/docs/automation-and-testing/headless)

**Playwright (latest `playwright` 1.65.1, published 2026-11-13; `next` 1.66.0-alpha-2026-11-18):**
- Version 1.59 (published 2026-04-01) added `page.screencast`, "a unified interface for capturing page content". It includes recording with start/stop control, `showActions`, `showChapter` and `showOverlay`, and "Agentic video receipts". Its "Real-time frame capture" option will "stream JPEG-encoded frames for custom processing like thumbnails, live previews, AI vision": `page.screencast.start({ onFrame: ({ data }) => ..., size: { width: 800, height: 600 } })`. — [Playwright release notes](https://raw.githubusercontent.com/microsoft/playwright/main/docs/src/release-notes-js.md); [npm](https://registry.npmjs.org/playwright)
- The `onFrame` callback receives `data` ("JPEG-encoded frame data"), `timestamp` ("when the frame was presented by the browser, in milliseconds since the Unix epoch"), `viewportWidth` and `viewportHeight`. You can pass `path` and `onFrame` together. — [class-screencast.md](https://raw.githubusercontent.com/microsoft/playwright/main/docs/src/api/class-screencast.md)
- 1.61 added the frame `timestamp` and a `cursor` option for `showActions`. 1.64 (published 2026-10-07) added an `fps` option to `Screencast.start`, `recordVideo` and the test `video` option ("Firefox and WebKit currently capture up to 25 frames per second"), and moved video encoding from VP8 to VP9. 1.64 also made video options available "in Playwright MCP and `playwright-cli`". — [Playwright release notes](https://raw.githubusercontent.com/microsoft/playwright/main/docs/src/release-notes-js.md)
- I found no Playwright API that injects viewer input from pixel coordinates beyond the ordinary `page.mouse` / `page.keyboard`. A viewer's input would therefore go through those calls or through a raw `CDPSession` (`context.newCDPSession(page)`). The second half is an inference; the CDP session API is cited in [Browserless docs](https://docs.browserless.io/llms-full.txt).

**Puppeteer (latest `puppeteer` 25.18.1, published 2026-11-17):**
- In the docs at tag `puppeteer-v25.18.1` and on `main`, `page.screencast()` is marked "obsolete. Use Page.record() instead". It returns a `ScreenRecorder`, records "WebM ... VP9 ... 30 FPS" by default and needs ffmpeg installed. The page says it "Works in Chrome 153+". — [puppeteer.page.screencast.md @ v25.18.1](https://raw.githubusercontent.com/puppeteer/puppeteer/puppeteer-v25.18.1/docs/api/puppeteer.page.screencast.md)
- `Page.record()` "Records this page using the Chrome DevTools Protocol Page.startScreenRecording API. Outputs mp4 video stream." (read on `main`). — [puppeteer.page.record.md](https://raw.githubusercontent.com/puppeteer/puppeteer/main/docs/api/puppeteer.page.record.md); [npm](https://registry.npmjs.org/puppeteer)
- Both Puppeteer APIs produce video files. Neither is a live frame callback. A live viewer on Puppeteer uses `CDPSession` and `Page.startScreencast` directly, as steel-browser does (below).

**Open-source viewers built on CDP screencast:**
- **steel-browser** (Apache-2.0, commit `c46d68c`, 2026-11-18): `api/src/plugins/browser-socket/page-screencast.ts` calls `Page.startScreencast` with `format: "jpeg"`, `quality: 75` (`JPEG_QUALITY`), and `maxWidth`/`maxHeight` set to the viewport. It paces acknowledgements at `MIN_ACK_INTERVAL_MS = 1000 / 30`, which caps the stream at about 30 fps. Every viewer of a page shares one screencast. Each viewer keeps a single `pending` frame slot, so a slow viewer gets the latest frame rather than a backlog. Frames go out as `json` or `binary`. `casting.handler.ts` turns viewer `mouseEvent`/`keyEvent` messages into `Input.dispatchMouseEvent`/`Input.dispatchKeyEvent` on the target page, and it also handles `navigation`, `closeTab` and `getSelectedText`. — [steel-browser](https://github.com/steel-dev/steel-browser/blob/main/api/src/plugins/browser-socket/page-screencast.ts) (read at `c46d68c`)
- **Browserless** (commit `aa7044f`): the open-source repo is dual-licensed "MongoDB Server-Side Public License OR the browserless commercial license". Its Live URL is a hosted or Enterprise feature driven by the CDP command `Browserless.liveURL`, with frame options `type` (`jpeg`/`png`), `quality` (default 70), `captureScale` (1 or 2) and `compressed`. The old `/screencast` REST API "has been removed". — [Browserless LICENSE](https://github.com/browserless/browserless); [Browserless docs](https://docs.browserless.io/llms-full.txt)
- **Chrome DevTools frontend:** Cloudflare's Live View is a `devtoolsFrontendUrl` on `live.browser.run` with modes `tab`, `full` and `devtools`, and it can also open in native Chrome DevTools through `devtools://`. — [Browser Run Live View](https://developers.cloudflare.com/browser-run/features/live-view/index.md)

### Inferences
- An in-sandbox viewer needs no Xvfb or VNC. Playwright's `onFrame`, or raw `Page.startScreencast`, gives JPEG frames from the headless Chromium we already plan to run. Input comes back through `Input.*`. This keeps the image small. It also means that only the page is visible, without the browser chrome or native dialogs. File pickers, basic-auth prompts and `alert()` are not drawn into page frames; this follows from screencast capturing the page target.
- Ack-based flow control (`maxFramesInFlight`, default 3) is what makes a remote relay safe. If the viewer or relay is slow, Chrome stops producing frames instead of queuing them. The steel-browser design shows the pattern to copy: one screencast per page, a latest-frame slot per viewer, and acks paced at 30 fps or less.
- Playwright's `onFrame` hides the acks. Raw CDP gives us `everyNthFrame`, `maxFramesInFlight` and `sendLastFrame` to tune latency against bandwidth. A relay that wants explicit backpressure should use raw CDP.

### Gaps
- No primary source gives measured frame sizes, frame rates or CPU cost for `Page.startScreencast` in new headless at typical viewports. Steel's choices (JPEG q75, ≤30 fps) are a design data point, not a benchmark. We should measure in the sandbox.
- The milestones that added `maxFramesInFlight`, `sendLastFrame` and `Page.startScreenRecording` are unknown, because the protocol repo's git history could not be read. The phrase "Works in Chrome 153+" sits on Puppeteer's obsolete `screencast()` page, and the docs do not explain it.
- I found no primary statement that `Page.startScreencast` behaves identically in new headless and headful Chrome. The unified-mode statement and Playwright's headless video recording support it, but only by inference.

## The VNC route and WebRTC alternatives

### Takeaway
E2B Desktop, Cursor's self-hosted workers and Daytona stream a whole X11 desktop over VNC. E2B uses x11vnc plus noVNC. Its "view-only" mode is a client-side noVNC URL flag, and its password is a single VNC password that the RFB protocol truncates to eight characters. That route suits computer-use agents, which need the whole desktop. For a page-only headless browser, CDP screencast is lighter. WebRTC stacks (Neko, Selkies) add video codecs and NAT traversal, which matter only at high frame rates.

### Cited Findings
- **E2B Desktop** (`@e2b/desktop` 2.5.0, published 2026-10-13; `dist/index.mjs` read on unpkg). The stream runs x11vnc on port 5900 (`x11vnc -bg -display ... -forever -wait 50 -shared -rfbport 5900`) and noVNC's `novnc_proxy` on port 6080. With `requireAuth`, it generates a 16-character random password and stores it with `x11vnc -storepasswd`. `getUrl({ viewOnly, authKey })` sets the query parameters `view_only=true` and `password=<authKey>` on the noVNC page URL. — [@e2b/desktop 2.5.0 dist](https://unpkg.com/@e2b/desktop@2.5.0/dist/index.mjs); [npm](https://registry.npmjs.org/@e2b/desktop)
- E2B's docs: "With `require_auth=True` (`requireAuth: true`) the URL carries a generated password, and `view_only` keeps viewers from moving the mouse under the model. Anyone with the URL can watch until the desktop is killed, so do not share it." — [E2B docs](https://e2b.dev/docs/llms-full.txt)
- noVNC's `view_only` parameter means "If the remote session should be in non-interactive mode". The setting is read client-side (`rfb.viewOnly = readQueryBoolean('view_only', false)`). noVNC is MPL-2.0 (commit `e8b5024`). — [noVNC EMBEDDING.md](https://github.com/novnc/noVNC/blob/master/docs/EMBEDDING.md); [vnc_lite.html](https://github.com/novnc/noVNC/blob/master/vnc_lite.html)
- RFB VNC Authentication: "the password is truncated to eight characters", and "This type of authentication is known to be cryptographically weak". — [RFC 6143 §7.2.2](https://www.rfc-editor.org/rfc/rfc6143.txt)
- **Cursor** self-hosted workers: `--share-desktop` takes `view` or `view_and_control` (the default). It "uses a worker-created, isolated agent desktop" that needs `tigervnc-standalone-server`. "A fail-closed input filter on the machine enforces control, and clipboard transfer stays blocked. Pixels leave the machine only through the worker's existing outbound connection. No inbound ports open." Desktop sharing is Linux-only. — [Cursor computer use and desktop sharing](https://cursor.com/docs/cloud-agent/self-hosted/computer-use.md)
- **Neko** (Apache-2.0, commit `8fd303c`) is "a self-hosted virtual browser that runs in Docker and uses WebRTC", built for multiple simultaneous users ("Watch party", "Interactive presentation ... others can control the screen"). — [neko README](https://github.com/m1k1o/neko)
- **Selkies** describes itself as a "low-latency high-performance Linux-native GPU/CPU-accelerated WebRTC HTML5 remote desktop streaming platform" built on GStreamer `webrtcbin`. Its README says a TURN server is needed inside Docker or Kubernetes. — [selkies-gstreamer](https://www.github.com/selkies-project/selkies-gstreamer) (via search summary **[secondary]**)
- **AgentCore** Live View "is powered by AWS DCV. Each browser session launches a dedicated DCV server that streams the browser interface". — [AgentCore Live View](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-dcv-integration.html)

### Inferences
- E2B's view-only is not enforced on the server. A viewer who holds a "view-only" URL also holds the VNC password, and x11vnc runs `-shared` without `-viewonly`. Deleting `view_only=true` from the URL therefore gives full control. Steel's docs warn about the same class of flaw for their URL flag (see the security section). For real view-only on VNC, run a second x11vnc with `-viewonly` and its own password, or filter input in a relay.
- The password travels in a URL query string. With truncation to eight characters, the effective secret is about 62^8 ≈ 2×10^14. That is acceptable only behind E2B's private-traffic token (next section).
- Cursor's design ("no inbound ports", pixels ride an outbound connection, a fail-closed input filter, clipboard blocked) is the pattern we want for in-sandbox streaming, whichever pixel protocol we pick.
- WebRTC needs UDP and usually TURN, which neither Cloudflare Sandbox nor a Durable Object relay offers directly (an inference; I did not check Cloudflare Realtime TURN). It is unnecessary for watching an agent click through a dev server.

### Gaps
- I found no primary measurements of the RAM, CPU or latency of Xvfb + x11vnc + noVNC compared with CDP screencast. Daytona's VNC stack is described in [hosted-browsers.md](hosted-browsers.md#vision-computer-sandboxes); I did not re-check it here.
- Selkies' current repository state (it may have moved to `selkies-project/selkies`) was not confirmed from its raw README.

## How each sandbox backend exposes a port or stream to a viewer

### Takeaway
Cloudflare is the only backend where nothing needs to be public. A Durable Object reaches the container port through `ctx.container.getTcpPort(port).fetch()`, including WebSocket upgrades, and Cloudflare's own docs show a DO bridging that WebSocket to a visitor. E2B can make every port require a per-sandbox traffic token (`allowPublicTraffic: false`, the default for projects created since 2026-10-30). Vercel Sandbox ports are public URLs, and the docs describe no auth on them.

### Cited Findings
**Cloudflare Sandbox / Containers:**
- New guide (Sandbox SDK 1.0 era, updated 2026-10-22): "The server has no public port, so your Worker forwards requests to it." The DO calls `container.getTcpPort(port).fetch(request)`. The server "must listen on `0.0.0.0`, because `getTcpPort()` cannot reach a server that listens only on `127.0.0.1`." — [Preview a web application](https://developers.cloudflare.com/sandbox/previews/index.md)
- "A connection that only passes through the Durable Object does not keep the sandbox running." To fix that, the guide's `bridge()` accepts both ends in the DO. It calls `upstream.accept()` on `response.webSocket` from the container and `server.accept()` on a new `WebSocketPair`, then relays messages both ways with `binaryType = "arraybuffer"` and passes `Sec-WebSocket-Protocol` through. "With the bridge, the sandbox keeps running while any page has a connection open". — [Preview a web application § Keep WebSocket connections open](https://developers.cloudflare.com/sandbox/previews/index.md)
- The same guide's "Share a preview with a link" stores `share:<uuid>` with an expiry in DO storage and serves `/shared/<NAME>/<TOKEN>/` only while the token is valid. "Anyone with the link can open the preview until it expires ... To revoke a link early, delete its key". It warns: "Code in a preview runs on this hostname and can send requests to this route with the visitor's cookies." So "serve the route from another hostname" or authenticate it with a secret the page cannot send. — [Preview a web application § Share a preview with a link](https://developers.cloudflare.com/sandbox/previews/index.md)
- SDK 0.x `exposePort()` URLs are `https://{port}-{sandbox-id}-{token}.yourdomain.com`, with a random 16-character token or a custom 1–16 character token. They need a custom domain with wildcard DNS and `proxyToSandbox()` in the Worker. "Preview URLs provide public HTTPS access to services running inside sandboxes." `sandbox.tunnels.get(port)` (Cloudflare Tunnel) has "No authentication mechanism beyond randomly generated URL". — [Preview URLs (0.x)](https://developers.cloudflare.com/sandbox/sdk/concepts/preview-urls/index.md)

**E2B:**
- "By default, a sandbox's public URLs are reachable by anyone who knows them." `sandbox.getHost(port)` returns the host. — [E2B public URL](https://e2b.dev/docs/llms-full.txt)
- With `network: { allowPublicTraffic: false }`, "Requests without the `e2b-traffic-access-token` header get `403`". The SDK exposes `sandbox.trafficAccessToken`. "Since October 30, 2026, newly created projects default to private sandbox traffic"; older projects keep their default. The setting is create-only. — [E2B restrict public access](https://e2b.dev/docs/llms-full.txt)
- E2B's Claude toolset example sets `allowPublicTraffic: false` with the comment "keeps the desktop stream private", and its `liveView(desktop)` "streams that desktop to a local URL". — [E2B docs § Computer use](https://e2b.dev/docs/llms-full.txt)

**Vercel Sandbox:**
- "Each exposed port gets its own public URL. You can expose up to 15 ports." `sandbox.domain(port)` "resolves a publicly accessible URL for a port you exposed during creation". `sandbox.update({ ports })` replaces the list. — [Working with Sandbox](https://vercel.com/docs/sandbox/working-with-sandbox.md); [SDK reference](https://vercel.com/docs/sandbox/sdk-reference.md)
- "Exposed ports are accessible via a public URL, so be mindful of what services you run." — [Vercel Sandbox security](https://vercel.com/docs/sandbox/concepts/security.md)
- `sandbox.openInteractive()` "returns a WebSocket URL and token for connecting your WebSocket client to a controller-hosted PTY". "Treat the token as a credential". This covers a PTY, not an arbitrary port. — [SDK reference](https://vercel.com/docs/sandbox/sdk-reference.md)

### Inferences
- On Cloudflare, the loop's DO can reach Chromium's CDP port inside the container through `getTcpPort(9222).fetch()` with an upgrade. No preview URL, tunnel or public port is needed. The guide's server must bind `0.0.0.0`, so Chromium needs `--remote-debugging-address=0.0.0.0` (or a small in-container proxy). That port is then reachable from inside the container's network namespace, which is acceptable only because nothing outside the DO can reach it.
- On E2B, the relay can reach CDP or the stream over `getHost(port)` with the `e2b-traffic-access-token` header, held by the loop and never sent to the viewer.
- On Vercel, any port we expose is reachable by anyone who learns the URL. A CDP port must never be exposed there. Either the loop connects outward through a channel the sandbox starts (Cursor's "outbound only" pattern), or an auth proxy inside the sandbox checks a loop-held secret before forwarding. The proxy would sit in the sandbox, so that secret is a sandbox-scoped capability, not a user credential.

### Gaps
- I did not check whether Cloudflare's container `getTcpPort` has its own message-size or throughput limits separate from the DO's.
- Whether Vercel offers deployment protection or another auth layer for sandbox port URLs was not found in the docs read.
- How E2B's `liveView` helper builds its "local URL" (a local proxy that adds the traffic token?) was not checked.

## Relay design: the loop's Durable Object holds CDP and relays frames

### Takeaway
It works on Cloudflare's documented primitives. The DO holds an outbound WebSocket to Chromium's CDP port in the container and relays frames to the viewer over its own WebSocket. The sandbox then exposes nothing. Three limits matter. The outbound CDP socket never hibernates, so the DO stays billed while streaming. Incoming messages are capped at 32 MiB. CPU is 30 s per incoming message by default. Frame bandwidth, not message size, is the real constraint.

### Cited Findings
- "Hibernation is only supported when a Durable Object acts as a WebSocket server. Outgoing WebSockets do not hibernate. However, an open outbound WebSocket connection prevents eviction for up to 15 minutes." — [DO WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/index.md)
- DO limits: "WebSocket message size | 32 MiB (only for received messages)". "CPU per request | 30 seconds (default) / configurable to 5 minutes". "Each incoming HTTP request or WebSocket *message* resets the remaining available CPU time to 30 seconds." There is a soft limit of 1,000 requests per second per object. — [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/index.md)
- DO pricing: "There is no charge for outgoing WebSocket messages". "a 20:1 ratio is applied to incoming WebSocket messages". "Calling `accept()` on a WebSocket in an Object will incur duration charges for the entire time the WebSocket is connected." — [DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/index.md)
- A forced code update disconnects WebSockets, and "The Web Standard WebSocket API prevents hibernation, so its connections are disconnected when the code update is applied." — [DO WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/index.md)
- Each Worker invocation can have "up to six connections simultaneously waiting for response headers ... Outbound WebSocket connections also count toward this limit." — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/index.md)
- Cloudflare's own `bridge()` example accepts the container's WebSocket in the DO with `accept()` and relays it, which shows that a DO can terminate and proxy a container WebSocket. — [Preview a web application](https://developers.cloudflare.com/sandbox/previews/index.md)
- Cursor ships pixels "only through the worker's existing outbound connection. No inbound ports open." — [Cursor desktop sharing](https://cursor.com/docs/cloud-agent/self-hosted/computer-use.md)

### Inferences
- Design shape: the DO holds the CDP socket (outbound, non-hibernating, which is fine while a session is live). It accepts the viewer's socket with `ctx.acceptWebSocket()` (hibernatable server side). Each `Page.screencastFrame` becomes a binary message to the viewer, which costs nothing as outgoing traffic, and the DO acks to Chrome. The DO then holds only one secret, the CDP socket. The viewer sees only frames and a narrow input schema (`mouse`, `key`, `text`, `scroll`), which the DO turns into `Input.*`. It never forwards raw CDP, so a viewer cannot run `Runtime.evaluate` or read cookies.
- Each CDP frame arrives at the DO as an *incoming* message, base64 JSON. That counts toward the 20:1 request billing and resets the 30 s CPU budget, so per-frame CPU is the JSON parse plus base64 decode. At 30 fps that is about 1.5 requests per second after the 20:1 ratio, far below the 1,000 rps soft limit.
- The 32 MiB cap is irrelevant to screencast frames, which are JPEGs well under that (an inference; see Gaps for sizes).
- Bandwidth is the real budget. Cap `maxWidth`/`maxHeight` at the viewport, use JPEG quality 60–75, pace acks at 10–30 fps, and stop the screencast when no viewer is connected (`Page.stopScreencast`). With no viewer, the DO can then drop the CDP socket between model steps and hibernate.
- The loop already holds a CDP connection to drive the browser. The viewer stream can share that socket on the same page target, so the browser needs no second debugging client. (Superseded: fact-check row 337 notes that W12 may drive the browser through a sandbox command with its own CDP session, and Chromium's debugging port accepts any sandbox process.)

### Gaps
- I did not find a Cloudflare limit on outgoing WebSocket bytes per second from a DO, or a stated egress price for DO WebSocket traffic.
- No source gave typical screencast JPEG sizes, so the bandwidth figures above are unmeasured.

## Takeover semantics in shipping products

### Takeaway
Every product that documents a handoff uses the same shape. The automation asks for help with instructions, waits, and resumes when the human marks Done or Failed (Cloudflare `Cloudflare.handoff`, Browserless `Browserless.liveURL` with instructions). OpenAI says ChatGPT doesn't capture what the user types while they control the browser, but that comes from a help-centre page I could reach only through search. AgentCore exposes a switch that disables the automation stream. No vendor documents that the model is shown what the human did; resumption reads the page state.

### Cited Findings
- **Cloudflare Browser Run:** the script subscribes to `Cloudflare.handoffComplete`, calls `Cloudflare.getLiveView` (mode `tab`) and sends `Cloudflare.handoff` with `instructions` and an optional `timeout` ("max 30 minutes, if undefined handoff will have no timeout"). The operator "completes the required actions, and selects 'Done' or 'Failed'". "The automation resumes with knowledge of whether the intervention succeeded." In "Manual detection", the script polls the page instead. — [Human in the Loop](https://developers.cloudflare.com/browser-run/features/human-in-the-loop/index.md)
- **Browserless:** `Browserless.liveURL` takes `instructions` (title, summary, up to 10 steps, `currentStep`), `doneLabel`, `failLabel` and `requesterName`. `Browserless.liveComplete` reports `closed`/`timeout`/`viewerDisconnected`. Without instructions, "your automation ends the handoff by detecting the expected page state and calling `Browserless.closeLiveURL`". The docs also say to "always verify the page state after completion instead of trusting the reason alone". ### Inferences
- Our handoff should be a tool result, not a side channel. The model calls `request_human_takeover({reason, instructions})`. The DO marks the browser `held_by: human`, stops taking model-visible screenshots and snapshots, and rejects browser tool calls while the human holds control. The turn suspends, much like our approval flow. When the human presses Done or Failed, the tool returns `{outcome, url, title}` plus a fresh accessibility snapshot taken *after* release. The model learns the resulting state, not the keystrokes. This matches Cloudflare and Browserless, where completion carries success or failure and the automation re-reads the page.
- Privacy follows from the relay. Viewer input passes through the DO as `Input.*` calls, so the DO must not log key-event payloads, and it must exclude them from the session event log and from OTel spans. Log only `{kind: "human_input", count}`. Screencast frames shown to the human during takeover must never enter model context or the recording. Browserless closing streams when it fills a credential is the mirror image: when a secret is on screen, nobody else watches.
- Arbitration is needed because CDP has no notion of an owner. `Input.setIgnoreInputEvents` blocks all input, including the human's, so it cannot serve as a lock. The DO must be the single writer that decides whose `Input.*` calls go through.

### Gaps
- I could not read OpenAI's primary pages (403), so whether screenshots stop during takeover, and the product's current status, are unverified.
- Browserbase, Steel and AgentCore do not document what happens to an automation's in-flight commands while a human is interacting; both sides can send input at once.
- No product documents giving the model a summary of what the human did.

## Security of view links

### Takeaway
Every hosted vendor's Live View link is a bearer capability. Anyone holding it can watch, and anyone holding an interactive link controls every logged-in account in the session. The good designs mint links server-side and keep them short-lived (Cloudflare: 5 minutes to connect, signed JWT; Browserless: a 30 s default, `?i=<id>` without the API token). They also enforce view-only on the server. Browserbase's documented read-only embed and the URL flags of E2B and Steel are client-side and can be bypassed. No vendor documents an audit log of who watched.

### Cited Findings
- **Cloudflare:** "A Live View URL contains a signed `jwt` value. Anyone with the complete URL can access the permitted connection." `expiresInMs` defaults to 300,000 (minimum 60,000, maximum 3,600,000). It "is the deadline for starting a connection, not the duration of an established connection". `guardrails: { "mode": "readonly" }` blocks interaction, though "A read-only link still exposes visible page data". "A read-only Live View guardrail applies only to the generated connection. Other connections and automation scripts can still control the session." "Generate Live View URLs from trusted server-side code." — [Live View](https://developers.cloudflare.com/browser-run/features/live-view/index.md)
- **Browserless:** links authenticate with "a short-lived `?i=<id>` parameter that is unique to the session" and do not carry the API token. `timeout` defaults to 30,000 ms. `interactable` "is fixed for the life of the link", and a page has one Live URL at a time. "Browserless drops viewer input on the server, not in the iframe ... hiding controls with CSS or blocking events in your page doesn't turn an interactive link into a view-only one." "With `interactable: true`, anyone holding the link controls the browser session, including any logged-in state inside it. They can also choose **Done** and move your script forward." The stream runs over `wss://<host>/live/<id>`. — [Browserless docs](https://docs.browserless.io/llms-full.txt)
- **Steel:** `debugUrl` "holds a token that lets the page open the live view without your API key. The token expires after the session ends". "Anyone who has the `debugUrl` can watch the session, and can control it while the view is interactive." The `interactive=false` URL parameter "can turn input off, but not on. A user who reads the frame's URL can remove the parameter, so use `debugConfig.interactive` when nobody may control the session." It also warns that a recording proxy route "can return the recording of any session in your organization to anyone who changes the session ID in its URL". — [Steel embed a live browser](https://steel.dev/docs/observability/embed-a-live-browser.md)
- **Browserbase:** the documented "Read-only" embed is the same iframe with `style="pointer-events: none;"` and `sandbox="allow-same-origin allow-scripts"`. "Read/Write" is the same iframe without the style. — [Browserbase Live View](https://docs.browserbase.com/platform/browser/observability/session-live-view.md)
- **AgentCore:** the Live View is opened from a presigned URL, and "If the container remains empty, verify that the presigned URL has not expired". — [AgentCore Live View](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-dcv-integration.html). A 300-second default expiry comes from an AWS blog post seen only in a search summary. — [AWS ML blog](https://aws.amazon.com/blogs/machine-learning/embed-a-live-ai-browser-agent-in-your-react-app-with-amazon-bedrock-agentcore/) (via search summary **[secondary]**)
- **E2B Desktop:** "Anyone with the URL can watch until the desktop is killed, so do not share it." — [E2B docs](https://e2b.dev/docs/llms-full.txt)
- **Cloudflare Sandbox shared previews:** the token is the permission, links can be revoked by deleting the storage key, and preview code "can send requests to this route with the visitor's cookies", so the route should sit on a separate hostname. — [Preview a web application](https://developers.cloudflare.com/sandbox/previews/index.md)

### Inferences
- For our relay: the viewer authenticates to our Worker with the owner's session (not a bearer URL) and receives a short-lived, single-use ticket bound to `{session, mode: view|control, user}`. Control mode is enforced in the DO, which drops input from view tickets. Only one control holder exists at a time. Every ticket mint and every connect or disconnect goes into the session event log as `viewer_joined`/`viewer_left`, which gives us the audit trail no vendor documents.
- Serve the viewer from a hostname separate from both the app and any preview hostname. Frames are images, so a viewer never runs page code. Embedding that hostname in an iframe of our own UI is therefore safe, unlike embedding a dev-server preview.
- Add Live View URLs, `debugUrl`s, E2B stream passwords and traffic tokens to `scrubSecrets`, as the report's change 5 already says for CDP URLs.
- For the multi-user platform, the Browserless rule ("anyone holding the link ... can also choose Done and move your script forward") means a handoff completion must be authorized as the tenant user, not only by possession of the link.

### Gaps
- No vendor I read documents an audit log of viewers (who opened a Live View, when, in which mode). Browserless's `viewerDisconnected` event is the closest.
- I did not check whether Browserbase offers a server-enforced read-only mode beyond the CSS-based embed.
