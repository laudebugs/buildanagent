## 0. Spec revision timeline (context for every other section)

**Takeaway.** The current MCP revision is **2026-07-28**, GA on 2026-07-28. It is a breaking revision. It removes the `initialize` handshake and protocol-level sessions, so MCP becomes stateless. It deprecates Dynamic Client Registration in favour of Client ID Metadata Documents (CIMD), and it moves enterprise and machine-to-machine auth into official extensions. The earlier revisions 2025-06-18 and 2025-11-25 are now "legacy" ([SPEC-VER](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)).

**Cited findings**
- The spec directory contains `2024-11-05`, `2025-03-26`, `2025-06-18`, `2025-11-25`, `2026-07-28` and `draft` (https://github.com/modelcontextprotocol/modelcontextprotocol/tree/main/docs/specification). The GA blog post is at `blog/content/posts/2026-07-28-spec-ga`. A release candidate post is dated 2026-05-21 (https://github.com/modelcontextprotocol/modelcontextprotocol/tree/main/blog/content/posts).
- 2025-06-18: "Classify MCP servers as OAuth Resource Servers, adding protected resource metadata"; "Require MCP clients to implement Resource Indicators as described in RFC 8707 to prevent malicious servers from obtaining access tokens"; a new security best practices page; elicitation added (https://modelcontextprotocol.io/specification/2025-06-18/changelog).
- 2025-11-25: OIDC Discovery support (PR #797); "incremental scope consent via `WWW-Authenticate` (SEP-835)"; URL mode elicitation (SEP-1036); "OAuth Client ID Metadata Documents as a recommended client registration mechanism (SEP-991)"; experimental tasks (SEP-1686); PRM discovery aligned with RFC 9728, "making `WWW-Authenticate` header optional with fallback to `.well-known`" (SEP-985) (https://modelcontextprotocol.io/specification/2025-11-25/changelog).
- 2026-07-28 major changes: "Remove protocol-level sessions and the `Mcp-Session-Id` header … Servers that need cross-call state use explicit, server-minted handles passed as ordinary tool arguments (SEP-2567)"; "Make MCP stateless: remove the `initialize`/`notifications/initialized` handshake. Every request now carries its protocol version and client capabilities in `_meta`" (SEP-2575); `server/discover` is mandatory; MRTR replaces server-initiated requests (SEP-2322); SSE resumability is removed ([SPEC-CHG](https://modelcontextprotocol.io/specification/2026-07-28/changelog)).
- 2026-07-28 auth-relevant minor changes: RFC 9207 `iss` (SEP-2468); `application_type` is required in DCR (SEP-837); "clients MUST key persisted credentials by the issuer identifier, MUST NOT reuse them with a different authorization server" (SEP-2352); "Deprecate the OAuth 2.0 Dynamic Client Registration Protocol … in favor of Client ID Metadata Documents (PR #2858)" ([SPEC-CHG](https://modelcontextprotocol.io/specification/2026-07-28/changelog)).
- Deprecated, with earliest removal "First revision released on or after 2027-07-28": Roots, Sampling, Logging and DCR. HTTP+SSE: "Three months after SEP-2596 reaches Final" ([SPEC-DEP](https://modelcontextprotocol.io/specification/2026-07-28/deprecated)).
- The roadmap of 2026-08-22 names "Agent identity and enterprise-ready security" as a priority area: "finalizing Demonstrating Proof of Possession (DPoP) and driving its adoption, and defining an opinionated path for agent identity and delegation through Workload Identity Federation, the ID-JAG grant … and standard token exchange", with engagement in the IETF OAuth and WIMSE working groups (https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/blog/content/posts/2026-08-22-mcp-roadmap.md).

**Inferences**
- Our SDK must be **dual-era** for at least 12 months. It must speak 2026-07-28 per-request `_meta` and also fall back to `initialize`-based legacy servers. The spec defines the detection procedure ([SPEC-VER](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning), [SPEC-HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) "Backward Compatibility").
- DPoP and workload identity are coming next. Keep the token-attachment layer pluggable (bearer now, DPoP-bound tokens later).

**Gaps**
- I did not read the GA blog post body or the full `draft/` diff against 2026-07-28. There may be pending auth changes in `draft` (for example DPoP) that I have not captured.

## 1. MCP authorization (2026-07-28)

**Takeaway.** Authorization is optional, but an HTTP server that implements it is an **OAuth 2.1 resource server**. It MUST publish RFC 9728 Protected Resource Metadata (PRM). Clients discover the AS from PRM, then use RFC 8414 or OIDC discovery. Clients MUST use PKCE S256, MUST send RFC 8707 `resource` on both authorization and token requests, and MUST validate RFC 9207 `iss`. Client registration priority is pre-registered, then CIMD, then DCR (deprecated), then manual entry. Servers MUST audience-validate tokens and MUST NOT pass them through. Scope handling is incremental: the server issues a 403 `insufficient_scope` challenge, and the client re-authorizes with the union of old and new scopes. Enterprise SSO (ID-JAG) and client credentials are official **extensions**, not core.

**Cited findings: scope and roles**
- "Authorization is **OPTIONAL** for MCP implementations." HTTP transports "**SHOULD** conform"; STDIO "**SHOULD NOT** follow this specification, and instead retrieve credentials from the environment" ([SPEC-AUTH](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)).
- Standards baseline: OAuth 2.1 draft-13, RFC 6750, RFC 8414, RFC 7591, RFC 8707, RFC 9728, RFC 9207, draft-ietf-oauth-client-id-metadata-document-00, OIDC Discovery and OIDC Dynamic Registration ([SPEC-AUTH](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)).
- "A protected _MCP server_ acts as an OAuth 2.1 resource server … The implementation details of the authorization server are beyond the scope of this specification. It may be hosted with the resource server or a separate entity." ([SPEC-AUTH](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization))

**Cited findings: PRM (RFC 9728) and AS discovery**
- "MCP servers **MUST** implement OAuth 2.0 Protected Resource Metadata (RFC9728). MCP clients **MUST** use OAuth 2.0 Protected Resource Metadata for authorization server discovery." ([SPEC-AUTH](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization))
- PRM "**MUST** include the `authorization_servers` field containing at least one authorization server". When several are listed, "Clients **MUST** maintain separate registration state (client credentials, tokens) per authorization server" ([SPEC-ASD](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery)).
- Discovery: the server either sends `resource_metadata` in the `WWW-Authenticate` header on a 401, or serves well-known URIs, first path-inserted (`/.well-known/oauth-protected-resource/public/mcp`) and then root. "MCP clients **MUST** support both discovery mechanisms" ([SPEC-ASD](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery)).
- AS metadata probe order for issuers with a path: `/.well-known/oauth-authorization-server/tenant1`, then `/.well-known/openid-configuration/tenant1`, then `/tenant1/.well-known/openid-configuration`. Then: "the `issuer` value in the document **MUST** be identical to the issuer identifier used to construct the well-known URL. If they differ, the client **MUST NOT** use the metadata." ([SPEC-ASD](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery))
- RFC 9728 §3.3: "The resource value returned MUST be identical to the protected resource's resource identifier … If these values are not identical, the data contained in the response MUST NOT be used." (https://www.rfc-editor.org/rfc/rfc9728.txt). A real bug in this area: rmcp (Rust SDK) CVE-2026-63127, "Missing Resource Field Validation in OAuth Protected Resource Metadata Discovery" (https://github.com/modelcontextprotocol/rust-sdk/security/advisories/GHSA-33f5-2c5q-wgwj).

**Cited findings: client registration (CIMD vs DCR)**
- Priority: "1. Use pre-registered client information … 2. Use Client ID Metadata Documents if the Authorization Server indicates that it supports them (via `client_id_metadata_document_supported` …) 3. Use Dynamic Client Registration as a fallback … 4. Prompt the user to enter the client information" ([SPEC-REG](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)).
- CIMD: "The `client_id` URL **MUST** use the 'https' scheme and contain a path component"; the document "**MUST** include at least … `client_id`, `client_name`, `redirect_uris`"; ASes "**MUST** validate that the fetched document's `client_id` matches the URL exactly" and "**MUST** validate redirect URIs" ([SPEC-REG](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)).
- "Dynamic Client Registration is deprecated. New implementations should use Client ID Metadata Documents instead." When DCR is used, "MCP clients **MUST** specify an appropriate `application_type`"; native and localhost clients **SHOULD** use `"native"` ([SPEC-REG](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)).
- AS binding: persisted or pre-registered credentials "**MUST**" be "keyed by the authorization server's `issuer` identifier … clients **MUST NOT** reuse client credentials from a different authorization server and **MUST** re-register". "Client IDs based on Client ID Metadata Documents are portable across authorization servers" ([SPEC-REG](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)).
- The TypeScript and Python SDK bugs that motivated this: "the SDK's OAuth client let the MCP server decide which authorization server received the client's OAuth credentials … the client would send it: the `refresh_token` and `client_secret` stored from an earlier sign-in" (TS CVE-2026-104850, https://github.com/modelcontextprotocol/typescript-sdk/security/advisories/GHSA-6qxp-vccf-f47h; Python CVE-2026-115563, https://github.com/modelcontextprotocol/python-sdk/security/advisories/GHSA-qx49-fqc8-xw99).

**Cited findings: PKCE, `iss`, resource indicators, audience**
- "MCP clients **MUST** implement PKCE … and **MUST** verify PKCE support before proceeding". "If `code_challenge_methods_supported` is absent … MCP clients **MUST** refuse to proceed." ([SPEC-SEC](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations))
- RFC 9207: the client "**MUST** record the `issuer` value … and associate it with the same per-request record used to store the PKCE code verifier". When `iss` is present it is compared by simple string comparison. When metadata advertises `authorization_response_iss_parameter_supported: true` and `iss` is absent, the client must reject. "A future revision … is expected to upgrade authorization server inclusion of `iss` from **SHOULD** to **MUST**." ([SPEC-AUTH](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization))
- BP: "PKCE alone does not prevent [mix-up] because the client transmits the `code_verifier` to the attacker's token endpoint." ([BP](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices))
- RFC 8707: "The `resource` parameter: 1. **MUST** be included in both authorization requests and token requests. 2. **MUST** identify the MCP server … 3. **MUST** use the canonical URI of the MCP server". "MCP clients **MUST** send this parameter regardless of whether authorization servers support it." ([SPEC-AUTH](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization))
- Token handling: "MCP servers **MUST** validate that access tokens were issued specifically for them as the intended audience … MCP clients **MUST NOT** send tokens to the MCP server other than ones issued by the MCP server's authorization server. MCP servers **MUST** only accept tokens that are valid for use with their own resources. MCP servers **MUST NOT** accept or transit any other tokens." ([SPEC-AUTH](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization))
- Bearer token only in the header ("**MUST NOT** be included in the URI query string"), and "authorization **MUST** be included in every HTTP request" ([SPEC-AUTH](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)).
- Audience validation was a real SDK bug in October 2026: TS "Server bearer authentication accepted tokens issued for another service" (CVE-2026-111771, https://github.com/modelcontextprotocol/typescript-sdk/security/advisories/GHSA-rvq5-wwqv-78pq); Python "accepts tokens issued for a different resource server" (CVE-2026-116684, https://github.com/modelcontextprotocol/python-sdk/security/advisories/GHSA-w4fh-qvv9-3v23).

**Cited findings: token passthrough ban**
- "If the MCP server makes requests to upstream APIs, it may act as an OAuth client to them. The access token used at the upstream API is a separate token, issued by the upstream authorization server. The MCP server **MUST NOT** pass through the token it received from the MCP client." ([SPEC-SEC](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations))
- BP lists the risks as "Security Control Circumvention", "Accountability and Audit Trail Issues", "Trust Boundary Issues" and "Future Compatibility Risk". Mitigation: "MCP servers **MUST NOT** accept any tokens that were not explicitly issued for the MCP server." ([BP](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices))

**Cited findings: scopes, step-up, incremental consent**
- Initial scope choice: "1. Use `scope` parameter from the initial `WWW-Authenticate` header … 2. If `scope` is not available, use all scopes defined in `scopes_supported`". "`scopes_supported` … is intended to represent the minimal set of scopes necessary for basic functionality" ([SPEC-AUTH](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)).
- Runtime: "HTTP 403 Forbidden" with `error="insufficient_scope"`, `scope=…` and `resource_metadata`. "servers **SHOULD** include all scopes required for the current operation in a single challenge." ([SPEC-AUTH](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization))
- Step-up: "Determine required scopes by computing the union of the client's previously requested scope set and the scopes from the current challenge"; "Retry … no more than a few times"; "Clients acting on their own behalf (`client_credentials` clients) **MAY** attempt the step-up … or abort". "Servers **MUST** account for scope hierarchies." ([SPEC-AUTH](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization))
- BP on scope minimization: "Minimal initial scope set (e.g., `mcp:tools-basic`)"; common mistakes include "Publishing all possible scopes in `scopes_supported`", "wildcard or omnibus scopes" and "Treating claimed scopes in token as sufficient without server-side authorization logic" ([BP](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)).
- Refresh: clients "**MUST** keep refresh tokens confidential in transit and storage", "**MAY** add `offline_access`" when the AS lists it, and "**MUST NOT** assume refresh tokens will be issued". Servers "**SHOULD NOT** include `offline_access`" in their challenges or PRM ([SPEC-AUTH](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization); SEP-2207 Final, https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/seps/2207-oidc-refresh-token-guidance.md). The AS "**SHOULD** issue short-lived access tokens" and "For public clients … **MUST** rotate refresh tokens" ([SPEC-SEC](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)).

**Cited findings: enterprise-managed authorization (ID-JAG) and client credentials (extensions)**
- Extensions are "Optional", "Additive" and "Composable", and they live in https://github.com/modelcontextprotocol/ext-auth ([SPEC-AUTH](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)). "Both extensions require explicit support from the MCP client — they are never active by default." They are negotiated through `extensions` in `io.modelcontextprotocol/clientCapabilities` (https://modelcontextprotocol.io/extensions/auth/overview).
- EMA (`io.modelcontextprotocol/enterprise-managed-authorization`, from SEP-990) works in two steps. First the client performs an RFC 8693 token exchange at the enterprise IdP, with `requested_token_type: urn:ietf:params:oauth:token-type:id-jag`, `subject_token` set to the ID token or SAML assertion, `audience` set to the MCP AS issuer, and an optional `resource`. Then it redeems the ID-JAG at the MCP AS with `urn:ietf:params:oauth:grant-type:jwt-bearer`. "Do not redirect the user to the MCP Authorization Server's authorization endpoint." The IdP "evaluates access policies … before issuing tokens"; revocation is centralized at the IdP; for account linking, "Use the subject claim as the primary stable identifier" ([EMA](https://modelcontextprotocol.io/extensions/auth/enterprise-managed-authorization)). The underlying IETF draft is draft-ietf-oauth-identity-assertion-authz-grant (https://datatracker.ietf.org/doc/draft-ietf-oauth-identity-assertion-authz-grant/).
- The EMA page lists vendor support: Okta XAA and Ping as Available for both roles; Auth0, WorkOS and Scalekit as Early access for accepting; Keycloak as Experimental; also Cloudflare `workers-oauth-provider` (experimental option since 0.7.0) and FastMCP 4.0 (beta) ([EMA](https://modelcontextprotocol.io/extensions/auth/enterprise-managed-authorization)).
- Client credentials (`io.modelcontextprotocol/oauth-client-credentials`) is for "Background services", "CI/CD pipelines" and "Daemon processes". "JWT Bearer Assertions (recommended)" (RFC 7523) are preferred over client secrets ([CC](https://modelcontextprotocol.io/extensions/auth/oauth-client-credentials)).

**Inferences**
- For a **multi-user platform acting as an MCP client**, publish one CIMD document per deployment, for example `https://<platform>/oauth/client.json`. Use a confidential-client `private_key_jwt` with a JWKS, because a hosted platform can keep keys. Keep DCR only as a fallback, and key every stored client registration by `(AS issuer)`.
- Build one discovery module that enforces all of these checks: PRM `resource` equality, AS `issuer` equality, PKCE S256 presence, `iss` validation, an SSRF-safe fetcher (see §4), and no cross-origin redirects carrying auth headers. Most 2026 SDK CVEs come from missing one of these checks.
- For **our own MCP servers**, emit precise 403 scope challenges. Keep `scopes_supported` minimal. Validate `aud` against the canonical URI.
- Support EMA from the start if we sell to enterprises. It is the only standard path that removes per-server consent prompts and gives IT central revocation.

**Gaps**
- I did not read the normative ext-auth spec text, only the docs summaries. Before implementing EMA, read https://github.com/modelcontextprotocol/ext-auth/blob/main/specification/stable/enterprise-managed-authorization/2026-07-28/enterprise-managed-authorization.mdx.
- I did not see the client support matrix (https://modelcontextprotocol.io/extensions/client-matrix).
- I did not check the status of DPoP or workload identity SEPs (PR #1933 is referenced on the roadmap).

## 2. Transports, sessions and multi-user remote servers

**Takeaway.** There are two standard transports: **stdio** and **Streamable HTTP**. HTTP+SSE (2024-11-05) is formally Deprecated. As of 2026-07-28 Streamable HTTP is POST-only, with no GET stream and no `Mcp-Session-Id`. Every request is self-describing, so remote servers scale horizontally like any HTTP API. Per-user state is the server's job: it uses explicit handles bound to the token's subject. stdio sits outside the auth spec and shares one trust domain with its host.

**Cited findings**
- Bindings: "stdio: newline-delimited messages over the standard streams of a client-launched subprocess" and "Streamable HTTP: each message is an HTTP POST to a single MCP endpoint; replies arrive as a JSON object or a request-scoped SSE stream" (https://modelcontextprotocol.io/specification/2026-07-28/basic/transports).
- "Revision 2026-07-28 changed the behavior of Streamable HTTP … Removal of the GET stream endpoint. Removal of protocol-level sessions." Long-lived change notifications go through `subscriptions/listen` ([SPEC-HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)).
- HTTP security: "Servers **MUST** validate the `Origin` header on all incoming connections to prevent DNS rebinding attacks", answering 403 when the Origin is invalid. "When running locally, servers **SHOULD** bind only to localhost (127.0.0.1)". "Servers **SHOULD** implement proper authentication for all connections." ([SPEC-HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http))
- The client must send `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name` headers (SEP-2243). Tool parameters can be mirrored into `Mcp-Param-*` headers via `x-mcp-header`, and servers MUST reject header/body mismatches ([SPEC-HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http), [SPEC-CHG](https://modelcontextprotocol.io/specification/2026-07-28/changelog)).
- Statelessness: "Servers **MUST NOT** rely on prior requests over the same connection to establish context (e.g., capabilities, protocol version, client identity)"; "State that needs to span multiple requests … **MUST** be referenced by an explicit identifier the client passes on each request." ([SPEC-BASIC](https://modelcontextprotocol.io/specification/2026-07-28/basic))
- List results now carry `ttlMs` and `cacheScope` (`"public"` or `"private"`); "`cacheScope` … controls whether shared intermediaries may cache the response" (SEP-2549, [SPEC-CHG](https://modelcontextprotocol.io/specification/2026-07-28/changelog)).
- BP "State Handle Hijacking" replaces session hijacking: "MCP servers **MUST NOT** treat possession of a state handle as authentication … **SHOULD** bind handles server-side to the authenticated user, for example by keying stored state as `<user_id>:<handle>` where the user ID is derived from the verified token" ([BP](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)). The 2025-11-25 equivalent was "MCP Servers **MUST NOT** use sessions for authentication … **SHOULD** bind session IDs to user-specific information" (https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices).
- Elicitation state: "For remote MCP servers, user identification **MUST** be derived from credentials acquired via MCP authorization when possible (e.g. `sub` claim)" ([SPEC-ELIC](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation)).
- stdio: "the client and a stdio server share one trust domain … neither the protocol nor the SDKs defend one against the other"; "The stdio transport is not a sandbox." ([LOCAL](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/local-server-security))
- Real multi-user bugs in SDKs:
  - Python: "transports routed incoming requests to an existing session based only on the session identifier, without verifying that the request was authenticated as the same principal" (CVE-2026-52869, https://github.com/modelcontextprotocol/python-sdk/security/advisories/GHSA-jpw9-pfvf-9f58).
  - TypeScript: "reusing a single `StreamableHTTPServerTransport` across multiple client requests … JSON-RPC message ID collisions cause responses to be routed to the wrong client" (CVE-2026-25536, https://github.com/modelcontextprotocol/typescript-sdk/security/advisories/GHSA-345p-7cg4-v4c7), plus a follow-up "Shared transport or server instances delivered one HTTP client's messages to another" (CVE-2026-111770, https://github.com/modelcontextprotocol/typescript-sdk/security/advisories/GHSA-jm63-cq47-j5jp).
  - C#: "Missing user ID claims collapse authenticated principals" (`null == null`) (https://github.com/modelcontextprotocol/csharp-sdk/security/advisories/GHSA-x863-g495-4cjc).
  - Tasks not bound to their creator: TS CVE-2026-111767 (https://github.com/modelcontextprotocol/typescript-sdk/security/advisories/GHSA-22jm-h49p-29qw) and Python CVE-2026-52870 (https://github.com/modelcontextprotocol/python-sdk/security/advisories/GHSA-hvrp-rf83-w775).

**Inferences**
- Multi-user remote servers should (a) derive the principal from the validated token on every request, (b) key all state, task IDs and elicitation `requestState` by `sub` plus tenant, (c) never share transport or server instances across requests, and (d) mark per-user `tools/list` results `cacheScope: "private"`.
- If the tool catalogue varies by user or scope, that variation is legitimate, but caches and gateways must respect it.
- Prefer remote (Streamable HTTP plus OAuth) over local stdio for anything that only wraps a SaaS API. LOCAL says: "Prefer the remote version where one exists."

**Gaps**
- I have not checked how far 2026-07-28 support has spread across clients and SDKs (the SDK beta post of 2026-06-29 exists but I did not read it).
- I did not cover WebSocket or other custom transports. Python had a WebSocket Origin-validation CVE, CVE-2026-59950 (https://github.com/modelcontextprotocol/python-sdk/security/advisories/GHSA-vj7q-gjh5-988w).

## 3. The MCP Registry

**Takeaway.** The official registry at `registry.modelcontextprotocol.io` is **still labelled "preview"** as of November 2026. It is a metadata-only catalogue (`server.json`) with namespace verification via GitHub, DNS or HTTP, plus package-level ownership checks. It does **not** scan code. Host applications are meant to consume **downstream aggregators or private registries** that implement the same OpenAPI, not the official registry directly. Server Cards (SEP-2127, Final) add `.well-known` discovery before connection.

**Cited findings**
- "The MCP Registry is currently in preview. Breaking changes or data resets may occur before general availability." It is "the official centralized metadata repository for publicly accessible MCP servers"; "Namespace management through DNS verification"; "A REST API" ([REGISTRY](https://modelcontextprotocol.io/registry/about)).
- `server.json` holds a unique name (`io.github.user/server-name`), the location (npm package, remote URL), execution instructions (args, env vars) and discovery data ([REGISTRY](https://modelcontextprotocol.io/registry/about)). The live API (`/v0.1/servers`) returns entries with `remotes: [{type: "streamable-http", url}]`, the schema `2025-12-11/server.schema.json`, and `_meta.io.modelcontextprotocol.registry/official.status` (queried 2026-11-18: https://registry.modelcontextprotocol.io/v0.1/servers?limit=1).
- Namespaces: GitHub auth grants `io.github.<user>/*`. Org namespaces require org **Owner**, and "`mcp-publisher login github` cannot currently publish to an organization namespace" (issue #1468). DNS auth uses an apex TXT record `v=MCPv1; k=ed25519; p=…` (https://modelcontextprotocol.io/registry/authentication).
- Package ownership: npm `mcpName` in package.json, PyPI/NuGet/Cargo `mcp-name: $SERVER_NAME` in the README, OCI label `io.modelcontextprotocol.server.name` (https://modelcontextprotocol.io/registry/package-types).
- "The MCP Registry delegates security scanning to … Underlying package registries … Downstream aggregators". "The MCP Registry is not intended to be directly consumed by host applications." It does "**not** support private servers"; private registries can implement the OpenAPI ([REGISTRY](https://modelcontextprotocol.io/registry/about)).
- Versions are immutable. "deleted" status hides an entry but "Server metadata is never permanently removed" (https://modelcontextprotocol.io/registry/faq).
- Registry CVEs, May 2026: SSRF in HTTP namespace verification (CVE-2026-44430), stored XSS via `websiteUrl` (CVE-2026-44429), "GitHub OIDC tokens replayable across registry deployments due to shared audience" (CVE-2026-44428), and an OCI validator that skipped the ownership check under rate limiting (CVE-2026-45781) (https://github.com/modelcontextprotocol/registry/security/advisories).
- Server Cards: "Status: Final … Extensions Track … `io.modelcontextprotocol/server-card`"; cards are recommended at `<streamable-http-url>/server-card`, and AI Catalogs can link them for domain-level discovery (https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/seps/2127-mcp-server-cards.md).

**Inferences**
- Namespace verification shows **who published**, not **what the code does**. Our platform should run its own curated or private registry (same OpenAPI), apply allowlists and pinned versions, and record the registry name, version and package digest on each installed connector.
- Registry `server.json` imports are an attack surface: env defaults and runtime args. The Inspector advisory "server.json import: declared environment-variable defaults change what the reviewed command runs (NODE_OPTIONS…)" shows this (https://github.com/modelcontextprotocol/inspector/security/advisories/GHSA-pp85-586h-2m95). Render and approve the *effective* command, including env.

**Gaps**
- I did not confirm the GA date or roadmap for the registry, or the registry aggregator guide.
- I did not read the Server Card schema in `experimental-ext-server-card`.

## 4. Threats and mitigations

**Takeaway.** The spec documents the protocol-plumbing threats well: confused deputy, token passthrough, SSRF in discovery, state-handle hijacking, local server compromise, authorization-URL injection, mix-up and localhost impersonation. It treats **model-level** threats (tool poisoning, rug pulls, shadowing, prompt injection via data) mostly as client responsibilities, with SHOULD-level guidance. The 2025–2026 CVE record is dominated by four classes: (1) local dev tools and bridges turning URL or callback handling into RCE; (2) missing Origin/DNS-rebinding defaults; (3) multi-tenant session and transport mix-ups; (4) path or argument injection in reference servers (filesystem, git).

**Cited findings: spec-documented**
- **Confused deputy** (MCP proxy using a static client ID upstream, plus DCR, plus a consent cookie). Proxies "**MUST** implement per-client consent"; the consent page must show the client name, scopes and `redirect_uri` and use CSRF and anti-framing protection; cookies use `__Host-`, `Secure`, `HttpOnly`, `SameSite=Lax`; exact-match `redirect_uri`; single-use `state` set "only after consent has been explicitly approved" ([BP](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices); [SPEC-SEC](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)).
- **SSRF in OAuth discovery**: a malicious server can point `resource_metadata`, `authorization_servers` or endpoints at `169.254.169.254` and similar. Clients "**MUST** consider SSRF risks"; "**SHOULD** block requests to private and reserved IP address ranges"; validate redirect hops; use an egress proxy (for example Smokescreen); beware DNS TOCTOU. "Avoid implementing IP validation manually." CIMD-fetching ASes face the same risk ([BP](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)). Examples of incomplete guards: rmcp "SSRF filter checks host strings, not resolved addresses" (https://github.com/modelcontextprotocol/rust-sdk/security/advisories/GHSA-5p52-q7pq-9fq2), the fetch server's NAT64 and IDNA bypasses (https://github.com/modelcontextprotocol/servers/security/advisories/GHSA-v38p-wf49-hx2j), and Python "Client fetched server-chosen $ref URLs while validating tool results" (CVE-2026-116686, https://github.com/modelcontextprotocol/python-sdk/security/advisories/GHSA-rwrf-2pqf-9j8j).
- **Authorization URL validation**: "**MUST** only allow `http://` and `https://` schemes"; "**MUST NOT** use shell commands (e.g., `cmd.exe`, `sh`, PowerShell) to open URLs". **stdio proxy escalation**: XSS leads to a stolen proxy token, which leads to spawning arbitrary stdio commands ([BP](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)).
- **Local server compromise / stdio configs as RCE**: one-click install "**MUST**" show "the exact command that will be executed, without truncation", warn, and require approval; clients **SHOULD** sandbox ([BP](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices); SEP-1024 https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/seps/1024-mcp-client-security-requirements-for-local-server-.md). LOCAL threat list: malicious, overcollecting or compromised-dependency servers; a "poisoned tool catalog … without the poisoned tool ever being invoked (often called tool poisoning, or tool shadowing when it targets another server's tools). Definitions are not fixed at install time either: a server can quietly change them after you approved it (a rug pull), so a one-time consent dialog and package pinning do not cover this surface"; "no check proves what a server will do" ([LOCAL](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/local-server-security)).
- **Mix-up**: mitigated by RFC 9207 `iss`. **Localhost redirect impersonation** with CIMD: an attacker can present a legit client's CIMD URL plus their own localhost port; ASes "**MUST** clearly display the redirect URI hostname" ([BP](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices); [SPEC-SEC](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)).
- **Tools**: "there **SHOULD** always be a human in the loop with the ability to deny tool invocations"; "clients **MUST** consider tool annotations to be untrusted unless they come from trusted servers"; servers "**MUST**" validate inputs, apply access control, rate-limit and sanitize outputs; clients "**SHOULD**" confirm sensitive operations, "Show tool inputs to the user before calling the server", "Validate tool results before passing to LLM" and log usage ([SPEC-TOOLS](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)).
- **Sensitive input**: "Servers **MUST NOT** use form mode elicitation to request sensitive information such as passwords, API keys, access tokens"; use URL mode ([SPEC-ELIC](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation)).
- **MCP Apps (UI)**: "Iframe sandboxing", "Pre-declared templates", "Auditable messages", "User consent … for UI-initiated tool calls" (https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/blog/content/posts/2026-01-26-mcp-apps.md). Inspector advisories from October and November 2026 show the weak points: "MCP App escapes its CSP by navigating its own frame" (https://github.com/modelcontextprotocol/inspector/security/advisories/GHSA-h9j8-vj8g-v3gg) and "Remote MCP App can steal proxy auth token and execute arbitrary local commands (RCE)" (https://github.com/modelcontextprotocol/inspector/security/advisories/GHSA-6x67-4w4w-9f3w).

**Cited findings: researchers [secondary]**
- Invariant Labs coined **tool poisoning** in April 2025: hidden instructions in tool descriptions that the model sees and users do not. It also described **rug pulls** (description changes after approval) and **cross-server shadowing** (a malicious server's description changes how the agent uses a trusted server's tools). Mitigations: MCP-Scan and tool pinning. "code isolation or sandboxing … is not a relevant mitigation" for this class (https://invariantlabs.ai/blog/mcp-security-notification) [secondary]. Simon Willison: clients should "show users initial tool descriptions and alert them if those descriptions ever change" (https://simonwillison.net/2025/Apr/9/mcp-prompt-injection/) [secondary].
- **Toxic flow** against the GitHub MCP server, 2025-05-26: a public issue carries an injection, the agent reads private repos, and leaks them through a public PR. "not a bug in the GitHub MCP server code". Mitigations: per-session repo restriction and runtime monitoring (https://invariantlabs.ai/blog/mcp-github-vulnerability) [secondary].
- **Lethal trifecta** (Willison, 2025-06-16): "Access to your private data", "Exposure to untrusted content", "The ability to externally communicate". "The only way to stay safe there is to avoid that lethal trifecta combination entirely." MCP "encourages users to mix and match tools from different sources" (https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/) [secondary].
- **OWASP MCP Top 10** (beta, "Phase 3"): MCP01 Token Mismanagement & Secret Exposure; MCP02 Privilege Escalation via Scope Creep; MCP03 Tool Poisoning; MCP04 Supply Chain; MCP05 Command Injection & Execution; MCP06 Prompt Injection via Contextual Payloads; MCP07 Insufficient AuthN/AuthZ; MCP08 Lack of Audit and Telemetry; MCP09 Shadow MCP Servers; MCP10 Context Injection & Over-Sharing (https://owasp.org/projects/mcp-top-10).

**Cited findings: CVE/advisory record, 2025–2026 (selected)**
- *Inspector / dev tools*:
  - CVE-2025-49596 (critical): "lack of authentication between the Inspector client and proxy, allowing unauthenticated requests to launch MCP commands over stdio" (https://nvd.nist.gov/vuln/detail/CVE-2025-49596).

**Inferences**
- Model-level threats (poisoning, shadowing, injected data) cannot be fixed by OAuth. Our harness needs these controls:
  - (a) **pin tool definitions**: hash name + description + schema + annotations per server version, and diff and re-approve on change, including on `listChanged`;
  - (b) **namespace tools per server** and never let one server's text name another server's tools;
  - (c) **trifecta-aware policy**: label each tool as private-data, untrusted-content or egress, and block or require approval when one session would combine all three;
  - (d) treat tool results and resources as untrusted data;
  - (e) show full tool arguments before sensitive calls, because invisible arguments were a vector in Invariant's research.
- Every local launcher must render the full command plus env, never use a shell to open URLs, and accept no configuration from URL query strings or OAuth callbacks (the Inspector RCE pattern).
- Don't rely on SDK defaults. Explicitly enable Origin/Host validation, body limits and `Content-Type` checks, and run per-request transport instances.

## 5. Token custody

**Takeaway.** The spec implies a custody model with **two token planes**. (1) *MCP-plane* tokens: the client holds tokens for the MCP server, audience-bound to it. (2) *Upstream-plane* tokens: the MCP server holds tokens for third-party APIs, obtained by acting as their OAuth client (often via URL-mode elicitation). Upstream tokens must never reach the MCP client or the model. Per-user delegated tokens are the default. Client credentials are for genuine no-user automation. RFC 8693 token exchange (and ID-JAG on top of it) is the standards path for on-behalf-of flows.

**Cited findings**
- Storage: "Clients and servers **MUST** implement secure token storage"; "Attackers who obtain tokens stored by the client, or tokens cached or logged on the server can access protected resources" ([SPEC-SEC](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)).
- Upstream tokens via URL elicitation: "**The third-party credentials MUST NOT transit through the MCP client** … **The MCP server MUST NOT use the client's credentials for the third-party service** … **The MCP server is responsible for tokens** … (in other words, the MCP server must be stateful)". "The MCP server **MUST NOT** transmit credentials obtained through URL mode elicitation to the MCP client." Pattern: "Bind tokens to MCP user identity". URL mode "is *not* for authorizing the MCP client" ([SPEC-ELIC](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation)). Sensitive-data form: "credentials never pass through the LLM context, MCP client or any intermediate MCP servers" ([SPEC-ELIC](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation)).
- Local credentials: "Pass secrets per server, not globally", "Scope tokens narrowly", "Keep long-lived secrets out of plaintext config" (OS keychain); "Going further: use short-lived credentials issued at launch time by a secrets manager or broker" ([LOCAL](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/local-server-security)).
- Audit: tools "Log tool usage for audit purposes" ([SPEC-TOOLS](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)); "Log elevation events (scope requested, granted subset) with correlation IDs" ([BP](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)); OTel trace context in `_meta` (SEP-414, [SPEC-CHG](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). Passthrough breaks audit because the server "will be unable to identify or distinguish between MCP Clients" ([BP](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)).
- Revocation in enterprise settings: "Revoking an employee's access to MCP servers happens at the IdP level" ([EMA](https://modelcontextprotocol.io/extensions/auth/enterprise-managed-authorization)).
- RFC 8693: impersonation means "A is B within the context of the rights authorized by the token". Delegation means "principal A still has its own identity separate from B … any actions taken are being taken by A representing B. In a sense, A is an agent for B". It is expressed via the `act` claim, with `may_act` for authorized actors (https://www.rfc-editor.org/rfc/rfc8693.txt).
- A2A guidance on credentials passed between agents in a chain: credentials "SHOULD be bound to the agent which originated the request" and encrypted for it; prefer out-of-band delivery (https://github.com/a2aproject/A2A/blob/v1.0.1/docs/specification.md §7.6.3).
- Vendor pattern [secondary]: Auth0 Token Vault stores and refreshes third-party OAuth tokens so they are "not exposed to AI agents or client-side code", exchanged via RFC 8693 at execution time; "Privileged Worker" covers background agents with no user session (https://auth0.com/features/token-vault, https://auth0.com/blog/token-vault-privileged-worker-early-access/).

**Inferences (design for our platform)**
- **Vault outside model and sandbox**: store refresh tokens and client secrets in a broker service. The agent process and sandbox see only an opaque connection handle. The broker attaches the bearer token at an egress proxy or connector gateway. Never put tokens in prompts, tool args, tool results, env vars visible to sandboxed code, or logs (the Inspector advisory "SSE auth/custom headers are logged verbatim" is a reminder: https://github.com/modelcontextprotocol/inspector/security/advisories/GHSA-8qgq-27v6-55w3).
- **Key tokens by (tenant, user, AS issuer, resource canonical URI, client_id)**. Never reuse a token across resources. Re-register when PRM points to a new AS.
- **Per-user delegated tokens by default.** Use a shared service account only for org-owned, non-personal resources, with explicit admin consent and a tool-level ACL on top. For no-user automation, use the client-credentials extension with `private_key_jwt`.
- **Refresh**: rotate (the AS must for public clients), serialize refresh per key to avoid rotation races, and treat refresh failure as "re-consent needed" surfaced to the user.
- **Revocation**: support RFC 7009 revocation on disconnect where the AS offers it, delete vault entries, and propagate IdP de-provisioning (EMA).
- **Audit**: one record per tool call with principal, agent/session, server, tool, args hash, scopes used, upstream resource and trace ID.
- For sub-agents, mint **down-scoped** tokens via token exchange (delegation with `act`), not copies of the parent token. This is the direction of the roadmap's "standard token exchange" and agent identity work.

**Gaps**
- The MCP spec has no normative text on token vaults, RFC 7009 revocation or 8693 on-behalf-of between MCP servers (outside EMA). These are design choices for us.
- I did not survey other vaults (Arcade, Composio, Cloudflare, Microsoft Entra Agent ID).

## 6. Non-MCP connector formats and how they relate

**Takeaway.** MCP is the convergence point. The **OpenAI Apps SDK** is MCP plus MCP-authorization, and its UI layer was standardised as **MCP Apps**, the first official extension (January 2026). **GPT Actions** (OpenAPI plus none, API key or OAuth configured per GPT) still exist but use a simpler, pre-MCP auth model without PRM, resource indicators or CIMD. **A2A** v1.0.x (Linux Foundation) handles agent-to-agent delegation over Agent Cards with OpenAPI-style `securitySchemes`. It complements MCP (agent-to-tool) rather than competing with it.

**Cited findings**
- Apps SDK auth: servers are "expected to implement an OAuth 2.1 flow that conforms to the MCP authorization spec"; PRM at `/.well-known/oauth-protected-resource`; S256 is required ("MCP servers are unsupported when their authorization server metadata omits this field"); CIMD is preferred, with DCR or predefined clients also supported; ChatGPT sends `resource` and you should "copy that value into the access token" as `aud`; "must assume the token is untrusted". ChatGPT "doesn't support machine-to-machine grants" and presents an OpenAI-managed mTLS client cert (https://developers.openai.com/apps-sdk/build/auth).
- MCP Apps: "MCP Apps are now live as an official MCP extension … building on … MCP-UI and the OpenAI Apps SDK … clients like ChatGPT, Claude, Goose and Visual Studio Code have shipped support" (2026-01-26, https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/blog/content/posts/2026-01-26-mcp-apps.md).
- GPT Actions auth: "None (default)", "API key" (stored encrypted in the GPT editor) and "OAuth" (client ID/secret, authorization URL, token URL, scope; the per-user token is sent in the Authorization header; the state parameter is required). The page says nothing about deprecation (https://developers.openai.com/api/docs/actions/authentication).
- A2A releases: v0.3.0 (2025-07-30), v1.0.0 (2026-03-12), v1.0.1 (2026-05-28) (https://github.com/a2aproject/A2A/releases). Auth: "Identity information is handled at the protocol layer, not within A2A semantics"; the client discovers `securitySchemes` in the AgentCard and obtains credentials "Out-of-Band". Scheme types are API key, HTTP auth, OAuth2 (auth code, client credentials, device code), OIDC and mutual TLS. `AgentCardSignature` supports card signing. An authenticated extended Agent Card is available. In-task auth uses `TASK_STATE_AUTH_REQUIRED`, which can chain across agents (https://github.com/a2aproject/A2A/blob/v1.0.1/docs/specification.md §4.5, §7).
- Governance: MCP joined the Agentic AI Foundation on 2025-12-09 (blog post `2025-12-09-mcp-joins-agentic-ai-foundation`, https://github.com/modelcontextprotocol/modelcontextprotocol/tree/main/blog/content/posts).

**Inferences**
- Make MCP (Streamable HTTP plus OAuth 2.1 profile) the connector layer's primary interface. Wrap OpenAPI/Actions-style APIs as MCP servers we host, with the vault holding the upstream tokens, rather than exposing a second auth model to agents.
- Support MCP Apps if we render UI, applying iframe sandbox and CSP and requiring approval for UI-initiated tool calls.
- Use A2A at the agent boundary (delegating to other agents). Map its in-task auth onto the same vault and URL-elicitation-style out-of-band consent.

**Gaps**
- I did not verify A2A v1.1 status. One secondary source claims an RC, which I could not confirm.
- I did not read the Apps SDK changelog in depth.
- The exact current status of GPT Actions versus Apps in ChatGPT product terms is unconfirmed from official sources.
