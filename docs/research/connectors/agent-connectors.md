# Connectors should be pinned MCP servers with per-user OAuth and a vault the agent never sees

Every major agent platform now lets users add connectors, and by November 2026 they all add them the same way: a remote MCP server, reached over Streamable HTTP, that each user signs in to with OAuth. The platforms still differ in who may add a connector, where its tokens live and whether a write needs a click, and those differences decide how much damage a connector can do. The 2025–26 incidents show why. Attackers rarely stole a connector's token. Instead they planted text that made an agent misuse access a user had legitimately granted, or they changed a tool's description after the user approved it. buildanagent has planned none of this yet. The harness plan has an MCP client, a credential proxy and a permission pipeline, but no OAuth, no token vault, no connector record and no pin on a server's tool definitions.

This report is for the project owner, who will decide whether connectors enter the SDK, harness and platform plans, and in what shape. It surveys ten platforms, the MCP 2026-07-28 authorization rules, token custody, the incidents a design must survive, the vendors and open-source kits that could supply the layer, and what our plans already hold. Claims come from four research notes in [notes/](notes/), each citing its primary source, and the [fact-check log](fact-check-agent-connectors.md) records every correction. Claims taken from blogs, press or aggregators are marked "(secondary)", claims taken from a search engine's digest are marked "(search summary)", and versions, prices and statuses are as of November 2026. The report ends with a design, a build-versus-buy call and plan changes for the owner to accept or reject. Its recommendation: **our connector should be a catalog record for a remote MCP server whose tool definitions we pin, with per-user OAuth under MCP 2026-07-28 and a legacy fallback. Its tokens should sit in a host-side vault wired into the HD15 credential proxy, its write tools should ask before they act, and we should build it on open-source kits rather than buy a hosted broker.**

## Every platform has converged on remote MCP with per-user OAuth, and they differ in governance

As of November 2026, the connector unit everywhere is a remote MCP server over Streamable HTTP. Each vendor keeps an older native unit beside it, and each wraps MCP in its own admin controls. The table summarises each platform, and the paragraphs after it give the sources.

| Platform | Connector unit | Who adds it | Who holds the token | Default for tool calls |
| --- | --- | --- | --- | --- |
| Anthropic (Claude) | MCP server, remote or `.mcpb` desktop extension | User on Free to Ultra; Owner on Team and Enterprise | Anthropic's backend; Managed Agents vaults | Prompt in chat; MCP toolsets `always_ask` in Managed Agents |
| OpenAI (ChatGPT, API) | Plugin with an MCP server; `mcp` tool in the API | User, subject to workspace policy; admins grant developer mode in workspaces | OpenAI in ChatGPT; the developer in the API | Ask on impactful actions; API asks before sharing data |
| Microsoft | Power Platform connector; MCP as a flagged custom connector | Makers, governed by tenant DLP | Connections; Foundry project connections | Foundry `require_approval` defaults to `always`, settable per tool |
| Google (Gemini Enterprise) | Data store; Custom MCP Server data store | Admins only, blocked by default | Not documented; Agent Identity auth manager on Agent Engine | Tools off; every action confirmed |
| AWS (AgentCore Gateway) | Gateway target aggregated into one MCP server | Developers through IaC | Token Vault, KMS-encrypted | No built-in human approval |
| Salesforce (Agentforce) | MCP server in Setup | Admins approve in API Catalog (secondary) | Named and External Credentials (search summary) | Not verified |
| Notion, Linear, Slack, GitHub | Per-agent MCP (Notion); MCP servers (Linear, Slack); MCP registry (GitHub) | Admin-gated (Notion, Slack, GitHub) | The authenticating person (Notion) | Write tools "Always ask" (Notion); no prompt in GitHub's cloud agent |

Anthropic runs one directory for claude.ai, Desktop, mobile, Claude Code and Cowork, and its labels describe review depth, not technology ([directory](https://claude.com/docs/connectors/directory.md); [verification](https://claude.com/docs/connectors/verification.md)). Verified means Anthropic tested the tools, but that "isn't a security audit"; Custom means "Anthropic hasn't reviewed it" ([verification](https://claude.com/docs/connectors/verification.md)). On Team and Enterprise only an Owner adds a connector for the organization, and members then sign in with their own accounts ([add unlisted](https://claude.com/docs/connectors/custom/add-unlisted.md)). Enabling a connector "doesn't automatically grant anyone access" ([help center](https://support.claude.com/en/articles/11724452-use-the-connectors-directory-to-extend-claude-s-capabilities)). For registration, Claude offers its published identity (CIMD), dynamic registration or the organization's own OAuth client, and shared static headers are a beta for a limited set of organizations ([add unlisted](https://claude.com/docs/connectors/custom/add-unlisted.md)). Enterprise Managed Auth skips the consent screen with a signed ID-JAG assertion from the customer's IdP or, in beta, from Claude ([enterprise managed auth](https://claude.com/docs/connectors/building/enterprise-managed-auth.md)). Each tool or tool group can be set to Always allow, Needs approval or Blocked, and an Owner's setting binds every member ([getting started](https://claude.com/docs/connectors/getting-started.md); [help center](https://support.claude.com/en/articles/11724452-use-the-connectors-directory-to-extend-claude-s-capabilities)).

OpenAI now calls its unit a plugin: skills, an optional MCP server and optional UI, shared between ChatGPT and Codex in one directory ([plugins](https://developers.openai.com/plugins/concepts/plugins.md)). In the Responses API the unit is the `mcp` tool, and the legacy first-party `connector_id`s for Gmail, Drive, SharePoint and others are deprecated for models released after 2026-09-01 ([MCP and connectors guide](https://developers.openai.com/api/docs/guides/tools-connectors-mcp.md)). ChatGPT uses per-user OAuth 2.1 with PKCE, prefers CIMD and falls back to DCR or a predefined client ([plugin auth](https://developers.openai.com/plugins/build/auth.md)). The API takes the opposite custody stance: it "does not store the value you provide in the `authorization` field", so the developer sends the token on every request ([MCP and connectors guide](https://developers.openai.com/api/docs/guides/tools-connectors-mcp.md)). In a workspace, using developer mode to create custom MCP connections is a member permission the admin grants, and owners can delegate it to groups through RBAC where supported ([plugin controls](https://learn.chatgpt.com/docs/enterprise/apps-and-connectors.md)). AgentKit's Connector Registry promised one admin panel across ChatGPT and the API ([AgentKit](https://openai.com/index/introducing-agentkit/)), but OpenAI deprecated Agent Builder on 2026-06-03 and shuts it down on 2026-11-30 ([deprecations](https://developers.openai.com/api/docs/deprecations.md)), and no OpenAI page says whether the registry survives.

Microsoft reuses the governance it already had, and Google adds the strictest defaults. Copilot Studio implements an MCP server as a custom connector flagged `x-ms-agentic-protocol: mcp-streamable-1.0`, and "if a data policy regulates Power Platform connectors, it also regulates access to the MCP server" ([add existing server](https://learn.microsoft.com/en-us/microsoft-copilot-studio/mcp-add-existing-server-to-agent)). Copilot Studio also syncs a server's tool list automatically when the server changes ([extend with MCP](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agent-extend-action-mcp)). Foundry stores credentials in project connections, caches them for two minutes, and offers a Toolbox that "handles credential injection, token refresh, and policy enforcement at runtime" ([Foundry MCP tool](https://learn.microsoft.com/en-us/azure/ai-foundry/agents/how-to/tools/model-context-protocol)). In Gemini Enterprise, an organization-policy constraint blocks Custom MCP data stores until an admin overrides it, allowlists egress hosts and holds `roles/discoveryengine.editor` ([custom MCP setup](https://docs.cloud.google.com/gemini/enterprise/docs/connectors/custom-mcp-server/set-up-custom-mcp-server)). Once a server is added, "no tools or actions … are enabled", at most 100 can be turned on, and "all calls to any action require confirmation" unless the tool carries `readOnlyHint: true` ([custom MCP setup](https://docs.cloud.google.com/gemini/enterprise/docs/connectors/custom-mcp-server/set-up-custom-mcp-server)).

AWS and Salesforce fill in the rest of the range. AgentCore Gateway aggregates Lambda, OpenAPI, Smithy and remote MCP targets into one virtual MCP server with semantic tool search and three-legged OAuth ([gateway concepts](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-core-concepts.md)). Its Token Vault encrypts tokens with customer- or service-managed KMS keys and validates "every access request … independently … to protect end-user data from malicious or misbehaving agent code" ([AgentCore features](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/key-features-and-benefits.md)). Salesforce splits governance in two: admins approve servers and tools in the API Catalog, and builders pick from the approved subset in the Agentforce Registry (secondary: [MuleSoft blog](https://blogs.mulesoft.com/news/mulesoft-26-mid-year-release-create-ai-experiences/)).

Among the app vendors, Notion, Linear and Slack each narrow what a connector can reach, and GitHub narrows least. Notion gives each Custom Agent its own MCP connection that "uses the credentials of the person who authenticated it", with write tools set to "Always ask" ([Notion MCP connections](https://www.notion.com/help/mcp-connections-for-custom-agents)). Linear's `read` scope yields a token that "can't reach write APIs" ([Linear MCP](https://linear.app/docs/mcp)). Slack's server accepts only directory-published or internal apps and supports neither SSE nor DCR ([Slack MCP server](https://docs.slack.dev/ai/slack-mcp-server/)). GitHub is the outlier. Its registry enforcement "is based only on server name/ID matching, which can be bypassed by editing configuration files", so the stricter option is a URL allowlist in enterprise managed settings. Its cloud coding agent "will not ask for your approval" before using an MCP tool ([allowlist enforcement](https://docs.github.com/en/copilot/reference/enterprise-administrators/mcp-allowlist-enforcement); [enterprise allowlist](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-mcp-usage/configure-enterprise-allowlist); [extend coding agent](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/extend-coding-agent-with-mcp)).

Claude, ChatGPT and Gemini Enterprise share one two-layer governance pattern: an organization enables a connector, then each user consents with their own account. Per-user OAuth with PKCE is the default credential, shared keys are an admin exception, and the defaults split: Gemini Enterprise, Foundry, Anthropic's Managed Agents and Notion's write tools start in an asking state, while GitHub's cloud agent never asks.

## MCP 2026-07-28 makes the connector a stateless OAuth resource server and deprecates dynamic registration

The current MCP revision is 2026-07-28, and `https://modelcontextprotocol.io/specification/latest` redirects to it as of November 2026 ([versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)). The revision breaks compatibility. It removes the `initialize` handshake and the `Mcp-Session-Id` header, so every request carries its protocol version and client capabilities in `_meta`, and servers that need state across calls pass explicit, server-minted handles as tool arguments ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). Servers MUST implement a new `server/discover` RPC that advertises their supported versions, capabilities and identity, which a client may call first ([versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)). Streamable HTTP is now POST-only, with long-lived notifications moved to `subscriptions/listen` ([Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)). Revisions 2025-06-18 and 2025-11-25 are now "legacy", and the spec defines how a client detects which era a server speaks ([versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)). A client that must reach both kinds of server therefore has to be dual-era, and the spec sets no date by which legacy servers go away.

Authorization stays optional, but an HTTP server that implements it acts as an OAuth 2.1 resource server and must follow a precise profile ([authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)). The profile has six client-side rules:

- **Discovery.** Servers MUST publish RFC 9728 Protected Resource Metadata, and clients MUST use it to find the authorization server, through either a `WWW-Authenticate` header or the well-known URIs ([server discovery](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery)).
- **Metadata checks.** The `issuer` in fetched metadata must equal the issuer used to build the URL, and the PRM `resource` must equal the server's identifier, or the client discards the data ([server discovery](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery); [RFC 9728](https://www.rfc-editor.org/rfc/rfc9728.txt)).
- **PKCE.** Clients MUST use PKCE and MUST refuse to proceed when `code_challenge_methods_supported` is absent ([security considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)).
- **Resource indicators.** Clients MUST send RFC 8707 `resource` on both the authorization and the token request, "regardless of whether authorization servers support it" ([authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)).
- **Mix-up defence.** Clients MUST record the `issuer` beside the PKCE verifier and, when the response carries an RFC 9207 `iss`, check it against that issuer before redeeming the code, since authorization servers only SHOULD send it ([authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)).
- **Credential binding.** Clients MUST key stored credentials by the authorization server's issuer and MUST NOT reuse them with another server ([client registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)).

Client registration now prefers pre-registered clients, then Client ID Metadata Documents (CIMD), then DCR, then manual entry, and the revision deprecates DCR: "New implementations should use Client ID Metadata Documents instead" ([client registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)). DCR's earliest removal is the first revision released on or after 2027-07-28 ([deprecated features](https://modelcontextprotocol.io/specification/2026-07-28/deprecated)). A CIMD `client_id` is an HTTPS URL whose document lists at least `client_id`, `client_name` and `redirect_uris`, and the authorization server must check that the fetched `client_id` matches the URL exactly ([client registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)). The platforms already moved: ChatGPT "prioritizes CIMD when it is available" ([plugin auth](https://developers.openai.com/plugins/build/auth.md)), and Claude offers CIMD as "Claude's published identity" ([add unlisted](https://claude.com/docs/connectors/custom/add-unlisted.md)). A hosted platform like ours can publish one CIMD document per deployment and authenticate as a confidential client with `private_key_jwt`, keeping DCR only for servers that lack CIMD (inference in [notes/protocol-auth-security.md](notes/protocol-auth-security.md)).

The spec also fixes how a server treats tokens and scopes. Servers MUST check that a token was issued for them, and the spec bans passthrough: "The MCP server **MUST NOT** pass through the token it received from the MCP client" ([security considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)). Tokens travel only in the `Authorization` header, never in the query string ([authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)). Scopes grow incrementally. A server answers a call that needs more scope with a 403 `insufficient_scope` challenge, and the client re-authorizes with the union of its old and new scopes ([authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)). The best-practices page warns against publishing every scope in `scopes_supported` and against "wildcard or omnibus scopes" ([security best practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)). Enterprise single sign-on through ID-JAG and machine-to-machine client credentials are official extensions, "never active by default", rather than core rules ([auth extensions](https://modelcontextprotocol.io/extensions/auth/overview)). Enterprise-managed authorization is the standard path that removes per-server consent and centralises revocation at the IdP, where "Revoking an employee's access to MCP servers happens" ([enterprise-managed authorization](https://modelcontextprotocol.io/extensions/auth/enterprise-managed-authorization)).

The official SDKs have already broken several of these rules. In 2026 the official TypeScript and Python SDKs let a server choose which authorization server received a client's stored `refresh_token` and `client_secret` ([TS GHSA-6qxp-vccf-f47h](https://github.com/modelcontextprotocol/typescript-sdk/security/advisories/GHSA-6qxp-vccf-f47h); [Python GHSA-qx49-fqc8-xw99](https://github.com/modelcontextprotocol/python-sdk/security/advisories/GHSA-qx49-fqc8-xw99)). Both SDKs' servers also accepted tokens issued for another service ([TS GHSA-rvq5-wwqv-78pq](https://github.com/modelcontextprotocol/typescript-sdk/security/advisories/GHSA-rvq5-wwqv-78pq); [Python GHSA-w4fh-qvv9-3v23](https://github.com/modelcontextprotocol/python-sdk/security/advisories/GHSA-w4fh-qvv9-3v23)). Shared transport instances in the TypeScript SDK routed one client's responses to another ([GHSA-345p-7cg4-v4c7](https://github.com/modelcontextprotocol/typescript-sdk/security/advisories/GHSA-345p-7cg4-v4c7); [GHSA-jm63-cq47-j5jp](https://github.com/modelcontextprotocol/typescript-sdk/security/advisories/GHSA-jm63-cq47-j5jp)). DNS-rebinding protection shipped off by default in both SDKs ([TS GHSA-w48q-cv73-mx4w](https://github.com/modelcontextprotocol/typescript-sdk/security/advisories/GHSA-w48q-cv73-mx4w); [Python GHSA-9h52-p55h-vw2f](https://github.com/advisories/GHSA-9h52-p55h-vw2f)). For us, the lesson is to own one discovery-and-token module that enforces every check above and to set every server-side protection explicitly rather than trust SDK defaults.

The official MCP Registry cannot serve as our trust signal. It is "currently in preview" as of November 2026, it stores metadata only, it does "**not** support private servers", and it "is not intended to be directly consumed by host applications" ([registry](https://modelcontextprotocol.io/registry/about)). Its namespace checks prove who published an entry, through GitHub, DNS or HTTP, not what the code does ([registry authentication](https://modelcontextprotocol.io/registry/authentication)). Server Cards (SEP-2127, Final) add a metadata card, recommended at `<endpoint>/server-card` and discoverable through a `.well-known` AI Catalog, that a client can read before connecting ([SEP-2127](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/seps/2127-mcp-server-cards.md)). A platform therefore needs its own curated catalog, which can implement the registry's OpenAPI and pin versions.

## Token custody works when the model and the sandbox hold only a handle

The spec implies two token planes, and a connector design has to keep them apart. On the first plane, the MCP client holds a token for the MCP server, bound to that server's audience. On the second, the MCP server holds tokens for the third-party APIs behind it, obtained by acting as their OAuth client, often through URL-mode elicitation ([elicitation](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation)). Upstream credentials "**MUST NOT** transit through the MCP client", and URL mode keeps them out of "the LLM context, MCP client or any intermediate MCP servers" ([elicitation](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation)). Servers "**MUST NOT** use form mode elicitation to request sensitive information such as passwords, API keys, access tokens" ([elicitation](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation)). The spec requires both sides to "implement secure token storage" but says nothing about how ([security considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)).

The strongest vendor designs keep secrets out of both the model and the sandbox by substituting them on the way out. Claude Managed Agents vaults hold `mcp_oauth`, `static_bearer` and `environment_variable` credentials as write-only fields, refresh OAuth tokens when given a refresh block, and inject MCP credentials into the server whose URL they are keyed by ([vaults](https://platform.claude.com/docs/en/managed-agents/vaults.md); [MCP connector](https://platform.claude.com/docs/en/managed-agents/mcp-connector.md)). An environment-variable secret sits in the sandbox "as an opaque placeholder … substituted with the real secret at egress. The agent never sees the secret value" ([vaults](https://platform.claude.com/docs/en/managed-agents/vaults.md)). The feature is in beta as of November 2026 and is workspace-scoped, so "any API key with workspace access can reference them" ([vaults](https://platform.claude.com/docs/en/managed-agents/vaults.md)). AgentCore stores per-user tokens under the agent identity and the user ID ([AWS tutorial](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity-getting-started-google.html)), and the Gateway injects them server-side. Its SDK decorators, by contrast, hand the token into agent code ([AgentCore features](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/key-features-and-benefits.md)). Custody can differ by integration path inside one product.

Our own credential boundary already follows the egress-substitution pattern. HD15's credential proxy injects a header on a host-side reverse-proxy route when the request's sentinel matches and the method is allowed, through `CredentialRoute { route; host; methods; header; secret: () => Promise<string> }` ([harness plan HD15](../../plans/build-harness.md#hd15-the-credential-proxy-injects-on-reverse-proxy-routes-not-by-intercepting-tls); [N20](../../todos/done/N20-credential-proxy.md#scope)). The coding agent applies it to its one GitHub App: the control plane mints a one-hour token narrowed to one repository, the token "stays in the control plane and reaches GitHub only through the egress route", and the route rejects pushes outside agent branches ([coding agent plan CA5](../../plans/build-coding-agent.md#ca5-one-github-app-minted-outside-the-sandbox-pushing-only-to-agent-branches-accepted)). The GitHub App design has four parts: mint, narrow, inject and filter. A connector vault can reuse all four (inference in [notes/our-baseline.md](notes/our-baseline.md)). Nothing sits behind the `secret` thunk yet: no vault, no refresh and no per-user lookup ([N20](../../todos/done/N20-credential-proxy.md#scope)).

The research notes converge on six custody rules for a multi-user platform ([notes/protocol-auth-security.md](notes/protocol-auth-security.md)):

- Store refresh tokens and client secrets in a broker, and let the agent and sandbox see only an opaque connection id.
- Key every token by tenant, user, authorization-server issuer, resource URI and client id, and never reuse a token across resources.
- Default to per-user delegated tokens, and keep shared service accounts for org-owned resources with explicit admin consent.
- Serialize refresh per key to avoid rotation races, and turn refresh failure into a visible "re-consent needed" state.
- Revoke at the provider on disconnect where the authorization server supports RFC 7009, then delete the vault entry.
- Write one audit record per tool call, holding the principal, session, server, tool, argument hash, scopes and trace id.

These rules match the spec's MUSTs where the spec speaks and fill its silence elsewhere. Refresh tokens "**MUST**" stay confidential, the authorization server "**MUST** rotate" them for public clients, and log records of scope elevation should carry correlation ids ([authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization); [security considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations); [security best practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)). For sub-agents, RFC 8693 token exchange mints a down-scoped token whose `act` claim names the agent acting for the user, instead of copying the parent's token ([RFC 8693](https://www.rfc-editor.org/rfc/rfc8693.txt)). The MCP roadmap of 2026-08-22 names DPoP, workload identity federation, ID-JAG and "standard token exchange" as its next security work ([roadmap](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/blog/content/posts/2026-08-22-mcp-roadmap.md)). The token-attachment layer should therefore accept bound tokens later as well as bearer tokens now.

## The incidents come from misused access and changing tool definitions, not stolen secrets

The 2025–26 connector incidents fall into five classes, and in most of them no secret was stolen ([notes/platform-connectors.md](notes/platform-connectors.md)). In the first class, indirect prompt injection, connected data carries instructions that make the agent exfiltrate through its own authorized tools. In AgentFlayer, a poisoned document made ChatGPT search the victim's Google Drive for API keys and leak them through a markdown image URL ([Zenity](https://labs.zenity.io/p/agentflayer-chatgpt-connectors-0click-attack-5b41)). In the GitHub "toxic agent flow", a public issue made an agent copy private-repository data into a public pull request using the user's own token, which Invariant calls architectural rather than a server bug ([Invariant](https://invariantlabs.ai/blog/mcp-github-vulnerability)). Agentforce's ForcedLeak, CVSS 9.4, combined a Web-to-Lead injection with an expired allowlisted domain ([Noma](https://noma.security/blog/forcedleak-agent-risks-exposed-in-salesforce-agentforce/)), and EchoLeak was a zero-click exfiltration from M365 Copilot ([MSRC CVE-2025-32711](https://msrc.microsoft.com/update-guide/vulnerability/CVE-2025-32711)).

The second class targets tool definitions, and it defeats one-time review. Invariant Labs showed in April 2025 that hidden instructions in a tool's description hijack an agent. It named two variants: rug pulls, where a description changes after approval, and cross-server shadowing, where one server's text changes how the agent uses another server's tools ([Invariant](https://invariantlabs.ai/blog/mcp-security-notification)). The MCP project's own security guide agrees: a server "can quietly change them after you approved it (a rug pull), so a one-time consent dialog and package pinning do not cover this surface" ([local server security](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/local-server-security)). Cursor's CVE-2025-54136 was a rug pull on configuration, gaining persistent code execution by changing an already trusted MCP config in a shared repository ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2025-54136)). Simon Willison's fix is the one most platforms skip: "show users initial tool descriptions and alert them if those descriptions ever change" ([Willison](https://simonwillison.net/2025/Apr/9/mcp-prompt-injection/)). Copilot Studio's automatic tool sync and GitHub's no-prompt cloud agent carry the most exposure to both classes (inference in [notes/platform-connectors.md](notes/platform-connectors.md)).

The remaining three classes are supply chain, broken tenancy and theft from the integration vendor. The postmark-mcp npm package BCC'd every outgoing email to its author ([Koi, archived](https://web.archive.org/web/2025/https://www.koi.ai/blog/postmark-mcp-npm-malicious-backdoor-email-theft)), and mcp-remote's CVE-2025-6514 turned a malicious authorization endpoint into OS command execution, CVSS 9.6 ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2025-6514)). A bug in Asana's MCP server could let users see other organizations' data, and Asana took the server offline from 5 to 17 June 2025 (secondary: [The Register](https://www.theregister.com/2025/06/18/asana_mcp_server_bug/)). Attackers used OAuth tokens stolen from Salesloft Drift to pull data from Salesforce instances, and Google told customers to treat "any and all authentication tokens stored in or connected to the Drift platform as potentially compromised" ([Google Threat Intelligence](https://cloud.google.com/blog/topics/threat-intelligence/data-theft-salesforce-instances-via-salesloft-drift)). Composio's May 2026 breach is the same class at a connector broker. The attacker reached its tool-execution sandbox, potentially exposed 5,241 API keys held in an auxiliary cache, and leaked about 0.3% of active connections, 5,001 of them GitHub's ([Composio bulletin](https://composio.dev/blog/composio-may-2026-security-incident)). The bulletin adds that "Deleting a connection alone does not guarantee provider-side revocation" ([Composio bulletin](https://composio.dev/blog/composio-may-2026-security-incident)).

A vault answers only the last of these classes. It stops a sandbox or a model from leaking a secret, but the dominant incidents misuse a scope the user granted, so the controls that matter sit around the tool call ([notes/platform-connectors.md](notes/platform-connectors.md)). Simon Willison's "lethal trifecta" names the combination to avoid: private data, untrusted content and a way to communicate externally, in one session ([Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). The spec puts the remaining duty on clients: "there **SHOULD** always be a human in the loop with the ability to deny tool invocations", and clients "**MUST** consider tool annotations to be untrusted unless they come from trusted servers" ([tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)). The controls that answer the misuse classes are read-only scopes and endpoints, asking before writes, tools off until enabled, egress and URL allowlists, and pinned tool definitions with re-approval on change. The OWASP MCP Top 10, in beta, lists the same ground from tool poisoning (MCP03) to shadow servers (MCP09) ([OWASP](https://owasp.org/projects/mcp-top-10)).

## Approvals belong in our harness, and no vendor promises idempotent writes

The connector vendors offer policy gates, not human approval, so the approval step has to live in our harness. Arcade's Contextual Access hooks run "Before each tool execution" and can "Allow, deny, or modify inputs", with no human step on the page ([Arcade contextual access](https://docs.arcade.dev/en/operate/governance/contextual-access)). Composio's Firewall uses decision models to check tool requests and results against your policies ([Composio pricing](https://composio.dev/pricing/platform)), and Merge applies rules and DLP ([Merge Agent Handler](https://www.merge.dev/agent-handler)). Human approval lives in frameworks instead: the AI SDK's `toolApproval` returns `'user-approval'` and can HMAC-sign the request ([AI SDK tool approvals](https://ai-sdk.dev/docs/agents/tool-approvals)), Cloudflare's `waitForApproval` is a durable gate backed by Workflows, and Code Mode's pending approvals survive Durable Object hibernation ([Cloudflare human-in-the-loop](https://developers.cloudflare.com/agents/guides/human-in-the-loop/)). Even there, MCP annotations stay hints: "The MCP client does not turn them into an approval policy automatically" ([AI SDK MCP tools](https://ai-sdk.dev/docs/ai-sdk-core/mcp-tools)).

SDK defaults disagree, so a generated agent cannot inherit a safe one. OpenAI's Agents SDK `hostedMcpTool` defaults to `requireApproval: 'never'` ([Agents SDK MCP guide](../../reference/openai-agents-sdk/source/docs/src/content/docs/guides/mcp.mdx)), although the Responses API itself asks by default ([MCP and connectors guide](https://developers.openai.com/api/docs/guides/tools-connectors-mcp.md)). Copilot asks per call with `kind: "mcp"`, Claude defers MCP tools behind tool search, and Cloudflare's `getAITools()` tools carry no approval unless wrapped (mirror checks in [notes/our-baseline.md](notes/our-baseline.md); [Copilot SDK guide](../../reference/copilot-sdk/guide.md#9-mcp-servers-plug-in-per-session-and-their-tools-arrive-as-server-tool)). The platforms that default to asking (Gemini Enterprise, Foundry's `require_approval: always`, Notion's write tools, Managed Agents' `always_ask`) show the default users already accept ([custom MCP setup](https://docs.cloud.google.com/gemini/enterprise/docs/connectors/custom-mcp-server/set-up-custom-mcp-server); [Foundry MCP tool](https://learn.microsoft.com/en-us/azure/ai-foundry/agents/how-to/tools/model-context-protocol); [Notion MCP connections](https://www.notion.com/help/mcp-connections-for-custom-agents); [permission policies](https://platform.claude.com/docs/en/managed-agents/permission-policies.md)).

No vendor page in the survey documents idempotency keys for connector writes, so exactly-once writes are our job ([notes/connector-infrastructure.md](notes/connector-infrastructure.md)). Retries create duplicates, and the AI SDK's MCP client leaves `maxRetries` for `tools/call` off by default ([AI SDK MCP tools](https://ai-sdk.dev/docs/ai-sdk-core/mcp-tools)). Our research already prescribes the pattern for writes to a system the agent does not own: deduplicated ingress on the way in, and keyed writes with explicit `unknown` outcomes on the way out ([twelve-factor report](../external-designs/twelve-factor-agents.md#conclusion-safety-moves-to-the-edges-once-the-agent-writes-to-a-helpdesk)). MCP's `isError` flag already gives a server a way to report a failed write so the model can correct itself ([server rollback report](../reversible-actions/server-rollback.md)).

Three findings decide the build-versus-buy question. First, every hosted-only option fails the user's-own-cloud constraint. "Zapier MCP runs on multi-tenant cloud infrastructure. Dedicated VPC or on-premises deployments are not currently available" ([Zapier security](https://docs.zapier.com/mcp/manage/security)). Pipedream "is hosted on … AWS … in the us-east-1 region" ([Pipedream security](https://pipedream.com/docs/privacy-and-security)), and Vercel Connect documents only a Vercel-hosted broker ([Vercel Connect](https://vercel.com/docs/connect)). Second, every production self-host or BYOC tier is quote-only. Arcade, Composio and Paragon reach the user's cloud only on Enterprise contracts, and Arcade's Helm chart needs Kubernetes with PostgreSQL and Redis ([Arcade Helm](https://docs.arcade.dev/en/operate/deploy/helm); [Composio custody](https://docs.composio.dev/docs/security/token-custody.md); [Paragon pricing](https://www.useparagon.com/pricing)). Third, the market is churning. Smithery shut its connection services on 2026-10-31 and is "now part of Arcade" ([Smithery](https://smithery.ai/)). Klavis archived its open-source repository to focus on RL environments ([Klavis](https://github.com/Klavis-AI/klavis)), mcp.run became a self-hosted gateway ([mcp.run](https://www.mcp.run/)), and Workday agreed to acquire Pipedream in November 2025 ([Workday](https://newsroom.workday.com/2025-11-19-Workday-Signs-Definitive-Agreement-to-Acquire-Pipedream)).

Buying would not remove the hardest work either. Vendor-managed OAuth apps are for prototypes: Composio says its shared apps are "not built for production scale", and Arcade's mean "your users will see the Arcade brand" and share rate limits ([Composio pricing](https://composio.dev/pricing/platform); [Arcade auth providers](https://docs.arcade.dev/en/references/auth-providers)). A product with users' own keys has to register its own OAuth app with each provider, including Google's and Microsoft's verification, whether it builds or buys (inference in [notes/connector-infrastructure.md](notes/connector-infrastructure.md)). Tenancy stays ours as well. Composio warns that the user id it keys connections on "is not proof of identity" ([Composio custody](https://docs.composio.dev/docs/security/token-custody.md)). Refresh tokens are bound to the client that issued them, so a hosted vault locks connections in. Composio offers "No token export" ([Composio authentication](https://docs.composio.dev/docs/authentication)).

The open-source kits fit our targets but carry their own defects. Cloudflare's `addMcpServer` runs dynamic registration, PKCE and token management, stores tokens "securely … in SQLite", and lets `createMcpOAuthProvider` supply a pre-registered client instead ([Cloudflare MCP client API](https://developers.cloudflare.com/agents/model-context-protocol/mcp-client-api/)). `workers-oauth-provider` stores tokens only as hashes and encrypts `props` with a key "only the token holder can unwrap". The same README warns that "the library advertises the required scopes but doesn't enforce them" ([workers-oauth-provider](https://github.com/cloudflare/workers-oauth-provider)), and the library fixed a PKCE downgrade and a missing `redirect_uri` check in May 2025 ([advisories](https://github.com/cloudflare/workers-oauth-provider/security/advisories)). Vercel's `mcp-handler` verifies bearer tokens and publishes protected-resource metadata but "does not issue tokens or run an authorization server" ([Vercel MCP docs](https://vercel.com/docs/mcp/deploy-mcp-servers-to-vercel)). It also fixed a cross-session tool-response leak, rated high, in March 2026 ([advisory GHSA-w2fm-25vw-vh7f](https://github.com/vercel/mcp-handler/security/advisories)). Nango's 2026 advisories include a proxy SSRF and forged-webhook acceptance ([Nango advisories](https://github.com/NangoHQ/nango/security/advisories)). No option is free of defects. What separates them is whether we can read, pin and patch the code.

## Our plans hold the seams a connector needs, but no connector

The harness plan designs an MCP client for consuming servers, and it stops at static configuration. HD14 wraps `@modelcontextprotocol/client` 2.4.0 behind `McpConnection`, which records the protocol era per server ([HD14](../../plans/build-harness.md#hd14-build-the-mcp-client-on-modelcontextprotocolclient-240-provisional); [ADR 0021](../../decisions/0021-mcp-client-base.md#decision)). The registry names tools `mcp__<server>__<tool>`, defers them by default and marks their output untrusted ([N24](../../todos/ongoing/N24-mcp-stdio.md#scope); [N11](../../todos/done/N11-tool-registry.md#scope)). Every call passes the deny-first permission pipeline, which asks when interactive and denies when headless ([N12](../../todos/done/N12-permission-pipeline.md#scope)). But `McpServerConfig`'s HTTP transport has only a `url`, with no headers, auth or owner field ([harness APIs](../../plans/build-harness.md#33-context-policy-and-tool-registry-apis)). N25 puts "OAuth flows beyond what the client library provides" out of scope and re-registers tools on `tools/list_changed` at the next turn with no re-review ([N25](../../todos/ready/N25-mcp-http-background.md#scope)). N22's `extensions.lock.json` pins in-process extensions by SHA-256 and leaves MCP servers out ([N22](../../todos/done/N22-in-process-extensions.md#scope)). The harness also lists "An MCP-server facade" as a non-goal ([harness plan](../../plans/build-harness.md#1-goal-and-non-goals)).

The platform plan names integrations in one sentence and leaves every mechanism open. "The platform reaches integrations through MCP servers the user names" ([platform plan](../../plans/build-agent-platform.md#1-goal-and-non-goals)). PF9 and ADR 0042 then ban stdio MCP commands in generated configuration and allowlist "the user's named MCP hosts" for egress ([PF9](../../plans/build-agent-platform.md#pf9-generated-code-runs-only-in-a-fresh-hosted-sandbox-accepted-adr-0042); [F11](../../todos/ready/F11-generated-code-isolation.md#scope)). Credential custody covers only the platform's own connections: cloud deploy credentials, GitHub and the user's model key, encrypted under a per-tenant AES-GCM data key ([ADR 0040](../../decisions/0040-tenant-cloud-connections-and-byok.md#decision); [F1](../../todos/ready/F1-platform-tenancy.md#tasks)). No todo says how a user names an MCP server, how its tokens are obtained or stored, or how a deployed agent authenticates to it. PF5 already proposes idempotency keys scoped to `(tenant, session, branch, tool_call_id)` and typed write outcomes in a safety package for generated agents ([PF5](../../plans/build-agent-platform.md#pf5-one-safety-package-inside-every-generated-agent-proposed)).

The deferred triage agent holds the repo's most complete pattern for one outside app. One `Helpdesk` interface is the agent's only way out, with a fake, a shadow wrapper and a real adapter that reaches the helpdesk through the credential proxy ([AD14](../../plans/build-agent.md#ad14-one-helpdesk-interface-is-the-agents-only-way-out-with-a-fake-for-tests-a-shadow-wrapper-for-rollout-and-a-real-adapter-the-owner-names-accepted)). Its tier table is code, and "Any tool without a table entry, including every MCP-sourced tool, gets T3", which always asks one person ([AD2](../../plans/build-agent.md#ad2-the-tier-table-is-code-t5-is-never-registered-and-t4-stays-denied-until-the-owner-sets-the-caps-accepted)). A session that reads untrusted output becomes tainted, and a permission hook then denies any T2+ call ([AD5](../../plans/build-agent.md#ad5-hd1s-per-block-origin-plus-a-per-session-taint-and-no-per-argument-tracking-provisional)). The table pins tool names, though, not definitions, so a server that rewrites a reviewed tool keeps its tier (inference in [notes/our-baseline.md](notes/our-baseline.md)).

Our verification corpus has never run an authenticated MCP flow. All eight SDKs document MCP ([feature table](../../comparison/feature-table.md#tools-all-eight-take-typed-custom-tools-and-all-document-mcp)), and our harnesses ran it for Claude, Cloudflare, Copilot and Vercel, all offline and without auth. Cloudflare's run used `createMcpHandler` and `addMcpServer` over loopback ([Cloudflare guide](../../reference/cloudflare-agents/guide.md#10-serve-mcp-with-createmcphandler-and-connect-to-it-with-addmcpserver)), and Vercel's used an in-process transport ([Vercel guide](../../reference/vercel-ai-sdk/guide.md#10-mcp-tools-become-ordinary-tools)). Cloudflare and Pi are the two of our eight SDKs whose docs describe a client OAuth flow end to end, and neither flow is verified ([Cloudflare fact-check](../../reference/cloudflare-agents/fact-check.md); [Pi MCP docs](../../reference/pi/source/coding-agent/mcp.md#authenticate-with-oauth)). The research reports record Anthropic's vault design ([vendor platforms note](../deployment/notes/vendor-platforms.md#4-tools-mcp-connectors-and-credential-handling)) and MCP configuration as a path to remote code execution ([agent-building platforms report](../deployment/agent-building-platforms.md#approvals-are-common-but-signed-approvals-and-side-effect-undo-exist-nowhere)). It also notes that practitioners increasingly treat remote MCP with OAuth as the credential boundary ([practitioner notes](../practitioners/notes/security-and-build-vs-buy.md#mcp-went-from-insecure-by-design-in-2025-to-the-credential-boundary-for-a-growing-minority-in-2026)). None of them names tool poisoning or rug pulls, although the AI SDK docs we mirror describe the rug pull and ship a check for it (part 5).

## The recommended design: nine parts, each tied to a seam we already plan

The design below assumes one rule from ADR 0036: the loop, and therefore the MCP client, runs outside the sandbox, and no credential enters it ([ADR 0036](../../decisions/0036-loop-outside-sandbox-and-pr-approval.md)). Every part either extends a planned seam or adds one record to it.

### 1. A connector is a catalog record, not a URL in a config file

A connector is a versioned record that the harness, the platform UI and the gate all read. It extends `McpServerConfig` with the fields the platforms and the spec showed we need:

```ts
interface ConnectorRecord {
  id: string;                       // stable, kebab-case
  url: string;                      // https only; canonical MCP resource URI
  publisher: { name: string; registryName?: string; verified: "first-party" | "reviewed" | "unreviewed" };
  auth:
    | { kind: "oauth"; registration: "pre-registered" | "cimd" | "dcr"; scopes: { read: string[]; write?: string[] } }
    | { kind: "static-header"; header: string }            // admin-set shared credential
    | { kind: "none" };
  readOnly?: { scope?: string; header?: [string, string]; url?: string };  // e.g. Linear `read`, GitHub X-MCP-Readonly
  pin: { serverVersion?: string; toolsHash: string; tools: Record<string, ToolPin> };
  tiers: Record<string, "T1" | "T2" | "T3" | "T4">;        // default T3 for every unlisted tool
  trifecta: Record<string, Array<"private-data" | "untrusted-content" | "egress">>;
  triggers?: TriggerSpec[];
}
interface ToolPin { sha256: string; annotations: unknown; firstSeen: string; approvedBy?: string }
```

The record copies three platform choices. It keeps `publisher.verified` as review depth, as Anthropic's labels do ([verification](https://claude.com/docs/connectors/verification.md)). It stores tiers per tool, as Claude, Gemini and Foundry do, and it names read-only routes such as Linear's `read` scope and GitHub's `X-MCP-Readonly` header ([Linear MCP](https://linear.app/docs/mcp); [GitHub remote server](https://github.com/github/github-mcp-server/blob/main/docs/remote-server.md)). The catalog itself is a curated list we maintain, optionally exposed through the registry's OpenAPI, because the official registry is a preview with no code scanning ([registry](https://modelcontextprotocol.io/registry/about)). User-added connectors enter the same record type with `verified: "unreviewed"`.

### 2. Adding a connector validates the URL, reviews the tools and fills the egress allowlist

The add flow runs five steps, each reusing a planned rule:

1. Validate the URL: HTTPS only, no private or metadata address ranges, and no `command`, reusing N20's route rule and F11's gate rule ([N20](../../todos/done/N20-credential-proxy.md#scope); [F11](../../todos/ready/F11-generated-code-isolation.md#scope)).
2. Fetch discovery documents through an SSRF-safe egress proxy, since a malicious server can point metadata at `169.254.169.254` ([security best practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)).
3. Run the OAuth flow of part 3 for the adding user. On the platform a tenant admin enables the connector first, and each user then consents for themselves.
4. Call `tools/list`, show every tool's full description, schema and annotations, and record the user's approval as the pin of part 5, with all tools off until enabled, as Gemini does by default.
5. Add the host to the agent's egress allowlist, which F11 names but no todo fills.

### 3. Per-user OAuth follows MCP 2026-07-28, with a legacy fallback

The harness gains one discovery-and-token module that implements all six client rules, with PKCE fixed to S256. Registration follows the spec's order, with one CIMD document per deployment and `private_key_jwt` for our hosted platform, DCR only as a fallback, and `application_type` set when DCR runs ([client registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)). Step-up handles 403 `insufficient_scope` by re-authorizing with the union of scopes, retrying only a few times ([authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)). For legacy-era servers the module keeps the 2025-11-25 behaviour that `McpConnection` already detects, including optional `WWW-Authenticate` with fallback to `.well-known` ([2025-11-25 changelog](https://modelcontextprotocol.io/specification/2025-11-25/changelog)). Enterprise-managed authorization comes later as an opt-in extension, after we read its normative text, which the notes did not ([notes/protocol-auth-security.md](notes/protocol-auth-security.md)).

The redirect needs a channel to the user. In a CLI or pull-request flow, the harness protocol surfaces an "authorization required" request carrying the URL, modelled on Cloudflare's `authenticating` state and `authUrl` ([Cloudflare MCP client API](https://developers.cloudflare.com/agents/model-context-protocol/mcp-client-api/)). Opening the URL must never go through a shell, since the spec forbids it and Inspector's PowerShell RCE shows why ([security best practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices); [GHSA-q978-78c7-phqw](https://github.com/modelcontextprotocol/inspector/security/advisories/GHSA-q978-78c7-phqw)).

### 4. The token vault sits outside the model and the sandbox and feeds the HD15 credential proxy

The harness defines a `ConnectionVault` interface with one portable backend per deployment target, holding tokens keyed by `(tenant, user, issuer, resource, client_id)` and encrypted with F1's per-tenant envelope keys ([F1](../../todos/ready/F1-platform-tenancy.md#tasks)). The vault feeds two host-side attachment points, and the sandbox reaches neither. First, the MCP client's HTTP transport takes a `connectionId` instead of a header and asks the vault for a fresh access token on each request. The client runs in the loop, outside the sandbox, so the token never enters it. Second, when sandboxed code calls a connector's API directly, a `CredentialRoute` whose `secret` thunk reads the vault injects the token at the HD15 proxy ([HD15](../../plans/build-harness.md#hd15-the-credential-proxy-injects-on-reverse-proxy-routes-not-by-intercepting-tls)). Both points run `scrubSecrets()` before any log append ([N20](../../todos/done/N20-credential-proxy.md#scope)).

The vault refreshes before expiry and on 401 under a single-flight lock per key, marks a connection `needs-auth` when refresh fails, and pauses or hands off the task instead of failing silently. Disconnect revokes at the provider where RFC 7009 is offered and then purges the entry, because deleting a broker's record does not revoke the token ([Composio bulletin](https://composio.dev/blog/composio-may-2026-security-incident)). Each refresh, grant, step-up and revocation writes an audit entry, which gives PF11's undefined "connection change" a schema ([PF11](../../plans/build-agent-platform.md#pf11-an-append-only-audit-log-per-tenant-proposed)).

The owner must decide who holds the vault on the platform. The notes favour the deployed agent's own runtime in the user's cloud, such as the Durable Object SQLite that `addMcpServer` already uses ([Cloudflare MCP client API](https://developers.cloudflare.com/agents/model-context-protocol/mcp-client-api/)). Keeping the vault there keeps our control plane out of custody of runtime connector tokens, in line with ADR 0040's rule that tenant credentials never enter a sandbox or the generated code ([ADR 0040](../../decisions/0040-tenant-cloud-connections-and-byok.md#decision)). Composio's breach shows the cost of the other choice: a central vault becomes an aggregate target ([Composio bulletin](https://composio.dev/blog/composio-may-2026-security-incident)).

### 5. Pinned tool definitions turn a rug pull into a visible re-approval

The harness hashes each tool's name, description, input schema and annotations at approval and stores the hash in the connector's pin, extending N22's `extensions.lock.json` to MCP servers. On every `tools/list` and every `tools/list_changed`, it diffs the live definitions against the pin. An unchanged tool loads. A changed tool stays off until a person approves the diff. A new tool arrives disabled, as it does in Managed Agents with `default_config.enabled: false`, which enables only the tools listed by name ([MCP connector](https://platform.claude.com/docs/en/managed-agents/mcp-connector.md)). The rule replaces N25's silent re-registration ([N25](../../todos/ready/N25-mcp-http-background.md#scope)). The AI SDK already ships the hashing half: `fingerprintTools` digests each tool's description, input schema and title, and `detectToolDrift` diffs two digests, leaving storage and the response to the app ([AI SDK MCP tools](../../reference/vercel-ai-sdk/source/content/docs/03-ai-sdk-core/16-mcp-tools.mdx)). Our pin store can wrap it on Vercel and copy its field list elsewhere, adding annotations.

Pinning catches changes, not a tool that was malicious from the start, so three more rules cover shadowing and poisoning. Tools stay namespaced per server, and a description that names another server's tools fails review. Tool results remain untrusted data and taint the session under AD5's rule ([AD5](../../plans/build-agent.md#ad5-hd1s-per-block-origin-plus-a-per-session-taint-and-no-per-argument-tracking-provisional)). The approval prompt shows the full arguments, since invisible arguments were one of Invariant's vectors ([Invariant](https://invariantlabs.ai/blog/mcp-security-notification)).

### 6. Every connector tool gets a tier, writes ask by default, and read-only scopes come first

An unreviewed connector tool gets T3, which asks one person on every call, as AD2 already rules for MCP-sourced tools ([AD2](../../plans/build-agent.md#ad2-the-tier-table-is-code-t5-is-never-registered-and-t4-stays-denied-until-the-owner-sets-the-caps-accepted)). A review promotes a tool into a tier-table row with AD2's two-owner sign-off. A server's `readOnlyHint` never lowers a tier on its own, because the SDK lets only first-party annotations affect scheduling ([SDK API](../../plans/build-sdk.md#33-sdk-api)). Writes use `approvalReuse: "none"`, so one approval never covers a second write. The trifecta labels in the record let the permission pipeline ask, or deny headless, when one session would combine private data, untrusted content and egress ([Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)).

Scopes do the first cut before any prompt. The add flow requests the record's `read` scopes, or uses its read-only header or URL, and asks for write scopes only when a user enables a write tool, through the spec's step-up challenge. The spec's best practices advise the same minimal starting set ([security best practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)). Generated agents get the same defaults through PF5's safety package, and every generation template sets the approval policy explicitly instead of inheriting the target SDK's ([PF5](../../plans/build-agent-platform.md#pf5-one-safety-package-inside-every-generated-agent-proposed)).

### 7. Every connector write carries an idempotency key and reports a typed outcome

The SDK adds an idempotency key to `ToolContext`, persisted before the call and scoped like PF5's key and the coding agent's GitHub writes ([coding agent architecture](../../plans/build-coding-agent.md#3-architecture-the-loop-in-a-durable-object-the-sandbox-without-credentials)). Our own MCP servers accept the key as an explicit tool argument, the stateless revision's pattern for cross-call state ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). For third-party servers that ignore it, the harness never retries a non-read tool automatically and records the outcome as `unknown` when a call times out ([server rollback report](../reversible-actions/server-rollback.md)). Long-running writes that need approval mid-way can use the MCP Tasks extension's `input_required` state, as the sagas report proposes ([sagas report](../reversible-actions/sagas.md)).

### 8. Triggers enter through one ingress that checks signatures, senders and duplicates

Connector events, such as a Slack message or a Linear issue, enter through a generic ingress that extends W5's GitHub design ([W5](../../todos/ready/W5-control-plane-ingress.md#scope)). The ingress verifies the provider's signature, checks the sender against the connection's owner, strips hidden markup, and deduplicates by the provider's delivery id. Nango's 2026 advisory on handlers that "accept forged provider events" shows the cost of skipping the signature check ([Nango advisories](https://github.com/NangoHQ/nango/security/advisories)). The ingress closes the twelve-factor report's one open gap ([twelve-factor report](../external-designs/twelve-factor-agents.md#five-small-changes-follow-led-by-an-ingress-design)). MCP's own `subscriptions/listen` can feed the same ingress for servers that offer change notifications ([Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)).

### 9. We host our own MCP server on Cloudflare to expose our agents and wrap non-MCP APIs

U12 lists "export as MCP server" as table stakes ([agent-building platforms report](../deployment/agent-building-platforms.md#where-a-new-platform-could-win-what-it-must-match-and-the-first-slice)). A hosted server also lets us wrap an OpenAPI-only app as MCP while the vault holds its upstream token, so agents see one auth model ([notes/protocol-auth-security.md](notes/protocol-auth-security.md)). Cloudflare's `createMcpHandler`, verified in our harness, plus `workers-oauth-provider` 1.2.4 is the natural base ([Cloudflare guide](../../reference/cloudflare-agents/guide.md#10-serve-mcp-with-createmcphandler-and-connect-to-it-with-addmcpserver); [workers-oauth-provider](https://github.com/cloudflare/workers-oauth-provider)). The server must close the gaps those libraries leave. It enforces scopes itself, since the provider does not. It validates `aud` against its canonical URI and emits precise 403 scope challenges, and it builds a fresh transport per request. It keys every handle and task by the token's `sub` and tenant, marks per-user `tools/list` results `cacheScope: "private"`, and validates `Origin` ([Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http); [changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog); [security best practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)). The server would be a separate package, so the harness non-goal can stand.

## Build the connector layer on open kits, and keep Nango and Arcade as named fallbacks

We should build the connector layer and buy nothing for the first release. The core is our own discovery-and-token module on `@modelcontextprotocol/client` 2.4.0, which HD14 already chose, plus the `ConnectionVault` and pin store described above. On Cloudflare, `addMcpServer` with a `createMcpOAuthProvider` override and its Durable Object SQLite is the vault backend, and `workers-oauth-provider` serves our own MCP endpoints. On Vercel, the AI SDK's `authProvider` hook needs a store we supply. Every piece is MIT or Apache-2.0, runs on our targets, and keeps tokens host-side behind the credential proxy ([notes/connector-infrastructure.md](notes/connector-infrastructure.md)). We register our own OAuth app with each provider from the first connector, which the market forces whatever we choose.

Two vendors stay on the list for cases the build does not cover. For a long tail of non-MCP APIs, self-hosted Nango is the moderate option, though production self-hosting needs its Enterprise plan ([Nango self-hosting](https://nango.dev/docs/guides/platform/self-hosting/self-hosting.md)). Its ELv2 licence forbids offering Nango itself "as a hosted or managed service", so the owner would need a licence review before embedding it in a hosted platform ([Nango licence](https://github.com/NangoHQ/nango/blob/master/LICENSE)). For an enterprise customer who wants a supported broker in their own cloud, Arcade's Helm and Marketplace deployments are the strongest documented self-host ([Arcade Helm](https://docs.arcade.dev/en/operate/deploy/helm)). Zapier MCP, Pipedream and Vercel Connect should not hold the vault, because each is hosted only.

## Conclusion

The market has settled the connector's shape. A connector is a remote MCP server, each user signs in to it with OAuth, and the platform's job is everything around that call: who may add it, where its tokens live, what it may change without asking, and how quickly a changed definition is noticed. MCP 2026-07-28 fixes the protocol half, from CIMD over DCR to audience-bound tokens. The incidents show that the other half decides the damage, because agents misused granted access far more often than attackers stole a token. Our plans already hold the seams: an MCP client outside the sandbox, a credential proxy that injects on host-side routes, a deny-first permission pipeline, a tier table that sends unreviewed MCP tools to T3, and a mint-narrow-inject-filter pattern proved on the GitHub App. We should add the connector to them in the nine parts above, with tokens held in the user's own runtime. We should build all of it on open kits, buy nothing for the first release, and start with items 1, 3, 4 and 8 of the table above, because every later part depends on the OAuth module, the vault, the pins and the custody decision.
