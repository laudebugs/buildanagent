# Voice agents run the text loop in a live session, so they must predict turns, forget unheard words and never go silent on a tool

Chapter T35 of the book gets a section on voice and realtime agents (todo [T38](../../todos/done/T38-section-voice-and-realtime.md)), and our plans hold almost nothing to write it from: the SDK references put "the realtime and voice agents" out of scope, and the one finding on record is that the OpenAI TypeScript SDK lacks Python's voice pipeline ([SDK references plan](../../plans/sdk-references.md); [TypeScript gaps](../../comparison/typescript-gaps.md#openai-agents-sdk-typescript-lacks-storage-backends-the-voice-pipeline-and-developer-utilities)). The evidence gathered on 19 November 2026 shows why the topic deserves care. People leave a mean gap of about 208 ms between turns in conversation ([Stivers et al. 2009](https://pmc.ncbi.nlm.nih.gov/articles/PMC2705608/)), while the fastest of three commercial voice agents tested in 2026 took 0.90 s on average to react ([τ-Voice, arXiv 2603.13686v1](https://arxiv.org/abs/2603.13686)). Speech also costs accuracy: on the same tool-using tasks in clean audio, those voice agents completed 31–51%, where GPT-5 working in text completed 85% (same paper).

Five findings answer the research question, with every version, price and status as of November 2026. First, the loop changes shape: a voice agent runs inside one long-lived session that events drive, and a turn detector, not the user's Enter key, decides when a turn ends. Second, latency becomes a correctness property: a reply that waits for a fixed silence arrives after the moment people expect it, so turn detection must predict the end of a turn. Third, interruption means more than cancelling a stream: the agent must stop speaking, cancel or keep the tools in flight, and cut its context back to the words the user actually heard. Fourth, a tool call silences a voice agent unless the agent announces it, runs it in the background or hands it to a backend agent, and spoken tool use is measurably less accurate than typed. Fifth, in TypeScript two of our eight SDKs ship a voice agent (OpenAI's speech-to-speech session and Cloudflare's chained pipeline), two ship experimental live layers (Google ADK and the Vercel AI SDK), and four ship nothing for audio, so a builder on those writes the speech stages around the text loop by hand. This report traces each finding to its sources, adds a short section on transports, session limits and cost, and then turns the findings into what T38 should teach, the examples it needs and proposed plan changes for the owner. Its thesis is that a voice agent runs the same tool loop as a text agent inside a live session paced by a listener, so it must predict when the person has finished, forget what the person never heard and keep its tools from silencing it.

## Eight terms are used one way throughout

A **voice agent** takes speech in and gives speech out within one conversation. A **realtime session** is the long-lived, two-way connection that carries that conversation, over WebRTC, WebSocket or a phone line, instead of one request per turn. A **speech-to-speech** model consumes and produces audio itself, while a **chained pipeline** runs speech-to-text, then a text agent, then text-to-speech; the papers call it a "cascade" and LangChain a "sandwich", and this report uses those words only when it reports their work. **Turn detection** decides when the user has finished speaking, and **voice activity detection (VAD)** is its simplest form, which watches for speech and silence. **Barge-in** is the user speaking while the agent is still talking, and **truncation** is cutting the agent's stored reply back to what the user heard before the barge-in.

## The loop becomes one long-lived session, and events start and cancel each turn

**A text agent sends one request per model step, while a voice agent keeps one session open for the whole conversation.** OpenAI defines a Realtime session as "a stateful interaction between the model and a connected client": a Session object holds the configuration, a Conversation holds the items, and Responses add the model's output to it ([OpenAI, Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations)). With voice activity detection on, which is the default, the client never asks for a turn: "When in Server VAD mode, the server will create Responses automatically", and the client sends `response.create` itself in the other cases, such as after a tool result or when turn detection is off ([OpenAI, client events](https://developers.openai.com/api/reference/resources/realtime/client-events)). The SDK mirrors that shape. `RealtimeSession` in `@openai/agents-realtime` 0.21.0 is "the equivalent of a Runner in text-based agents except that it automatically handles multiple turns", and its `connect()` returns `Promise<void>` rather than a result, so the program learns what happened from events such as `history_updated` and `audio_interrupted` (installed typings, `realtimeSession.d.ts`; [OpenAI and Cloudflare SDK notes](notes/sdks-openai-cloudflare.md)).

**Vendors offer three shapes of voice agent, and the choice decides what the builder still controls.** OpenAI's voice-agents guide lists them as of November 2026:
1. GPT-Live, a full-duplex model that talks to the user and hands reasoning and tools to a separate backend;
2. the Realtime API, where one speech-to-speech model handles "speech, reasoning, and tool use in one session";
3. a chained pipeline, chosen when the builder wants to "inspect or transform intermediate text and replace each component independently" ([OpenAI, voice agents](https://developers.openai.com/api/docs/guides/voice-agents)).

**OpenAI now favours the speaking front model, and the research draws the same line between cascades and end-to-end models.** OpenAI recommends the Realtime API for agents "that need barge-in, low first-audio latency, natural turn taking, and realtime tool use" ([OpenAI, Realtime](https://developers.openai.com/api/docs/guides/realtime)), and since GPT-Live (`gpt-live-1`) arrived it points new conversational apps at that model ([OpenAI, audio](https://developers.openai.com/api/docs/guides/audio)). In the research literature, Kyutai's Moshi, the reference end-to-end model, argues that a cascade loses "non-linguistic information" such as emotion and relies on "a segmentation into speaker turns", and it reports a latency of "160ms, 200ms in practice" ([Moshi, arXiv 2410.00037v2](https://arxiv.org/abs/2410.00037)). Surveys warn that the label "full-duplex" covers "substantially different capabilities", and one finds that current systems achieve only "pseudo-full-duplex" behaviour by switching quickly between listening and speaking ([arXiv 2509.14515v1](https://arxiv.org/abs/2509.14515); [arXiv 2606.19453v1](https://arxiv.org/abs/2606.19453)).

**Inside the session the tool loop survives almost unchanged, so the book can build voice on the loop it has already taught.** A Realtime model adds a `function_call` item, the client runs the function, adds a `function_call_output` item with the same `call_id`, and then sends `response.create` so the model speaks the result ([OpenAI, Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations)). Gemini's Live API works the same way, except that "the Live API doesn't support automatic tool response handling" ([Gemini, Live API tools](https://aistudio.google.com/docs/live-api/tools.md)). A chained pipeline keeps even more of the text loop. Cloudflare's `withVoice` mixin hands each finished transcript to an `onTurn()` method, which typically runs an ordinary AI SDK `streamText` call with its own tools ([Cloudflare Agents, voice, mirrored](../../reference/cloudflare-agents/source/agents/docs/agents/voice.md)). OpenAI's guide states the rule for builders: "choose the audio architecture first, then design the rest of the agent workflow the same way you would for text" ([OpenAI, voice agents](https://developers.openai.com/api/docs/guides/voice-agents)). What changes is everything around the loop: when a turn ends, what happens when it is cut off, and how long a tool may keep the agent quiet.

## A reply that waits for silence arrives late, so turn detection must predict the end of a turn

**People answer within about 200 ms because they predict where a turn will end, so a slow reply carries meaning of its own.** Across ten languages, Stivers et al. measured a mean response offset of +208 ms, from +7 ms in Japanese to +469 ms in Danish ([Stivers et al. 2009](https://pmc.ncbi.nlm.nih.gov/articles/PMC2705608/)). Planning even one word takes longer than that gap. Levinson and Torreira put production latency at "600–1500 ms or more", and conclude that listeners "must predict ... the end of the current speaker's turn in order to prepare their response in advance". They also report that "gaps of 600 ms or longer" lead listeners to infer an unwelcome answer ([Levinson and Torreira 2015](https://pmc.ncbi.nlm.nih.gov/articles/PMC4464110/)). For a voice agent, latency is therefore part of what the reply says, not only a cost.

**A fixed silence threshold forces a trade between cutting people off and answering late.** OpenAI's `server_vad` waits 500 ms of silence by default; shorter values respond "more quickly, but may jump in on short pauses from the user" ([OpenAI, client secrets reference](https://developers.openai.com/api/reference/resources/realtime/subresources/client_secrets/methods/create)). Gemini's server default is "approximately 800ms", and Google warns that 100–200 ms splits one utterance into fragments ([Gemini, Live API capabilities](https://aistudio.google.com/docs/live-api/capabilities.md)). The cost of waiting adds up. In a 2025 robot study, the response times of a baseline with a 1 s silence threshold peaked at about 2.6 s, while predictive turn-taking models cut the median response time from 2.7 s to 1.5 s and the interruption rate from 16.6% to 6.9% ([arXiv 2501.08946v1](https://arxiv.org/abs/2501.08946)).

**Both vendor APIs and Cloudflare's pipeline offer a detector that predicts, and push-to-talk remains the simple escape.** OpenAI's `semantic_vad` "scores the input audio based on the probability that the user is done speaking", and waits longer only when that probability is low ([OpenAI, VAD](https://developers.openai.com/api/docs/guides/realtime-vad)); it is the default turn detection in `@openai/agents-realtime` 0.21.0 (compiled `openaiRealtimeBase.mjs`, read but not run; [SDK notes](notes/sdks-openai-cloudflare.md)). Gemini adds a hybrid mode that detects the start of speech on the server and lets the client end the turn at once ([Gemini, Live API capabilities](https://aistudio.google.com/docs/live-api/capabilities.md)). Cloudflare's chained pipeline lets the speech-to-text model decide: Workers AI Flux has an end-of-turn confidence threshold that defaults to 0.7 (installed typings, `agents/dist/voice/workers-ai.d.ts`). Turning detection off for push-to-talk avoids the trade entirely, and OpenAI notes that it "avoids VAD failures, and it feels snappy because we're not waiting for a VAD timeout" ([OpenAI, Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations)).

**A chained pipeline spends its budget in sequence, so its latency must be measured per stage.** No peer-reviewed per-stage budget for a streaming chained pipeline turned up. The most detailed breakdown is a vendor guide written around the Pipecat framework, which sets a target of 1,500 ms from the user's voice to the agent's and adds up a typical 1,293 ms, with 300 ms for transcription and end-of-turn detection and 650 ms for the model's time to first token, the largest single stage (vendor guide, [Voice AI and voice agents](https://voiceaiandvoiceagents.com/)). Research systems do worse. Moshi's authors describe cascades as having "a typical global latency of several seconds" ([Moshi, arXiv 2410.00037v2](https://arxiv.org/abs/2410.00037)), and the cascade in Full-Duplex-Bench-v3, one Whisper, GPT-4o and OpenAI TTS chain run through LiveKit, took 8.78 s to its first word ([arXiv 2604.04847v1](https://arxiv.org/abs/2604.04847)). OpenAI's guide asks builders to measure "how long callers wait for a useful spoken answer" at the median and the 95th percentile, and to count an acknowledgment such as "I'm checking" apart from the answer ([OpenAI, voice agents](https://developers.openai.com/api/docs/guides/voice-agents)). Cloudflare's voice mixin reports those stages for every turn, from speech start to first interim transcript through the model's first text to the first audio (`VoiceTurnMetrics`, installed typings). Whatever the architecture, the number to watch is the wait for a useful answer at the 95th percentile, measured stage by stage.

## Barge-in must stop the speech, settle the tools in flight and cut the context back to what the user heard

**The model writes its reply faster than the speaker plays it, so after a barge-in the context holds words the user never heard.** OpenAI's reference states the cause: "The server will produce audio faster than realtime", so the client must truncate audio "that has already been sent to the client but not yet played", and truncation also deletes the unheard text "to ensure there is not text in the context that hasn't been heard by the user" ([OpenAI, client events](https://developers.openai.com/api/reference/resources/realtime/client-events)). Who truncates depends on the transport. Over WebRTC and SIP, "the server will automatically truncate unplayed audio", because it manages the output buffer. Over WebSocket, the client must stop playback, record how many milliseconds of the reply the user heard and send `conversation.item.truncate` with that `audio_end_ms` ([OpenAI, Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations)). `@openai/agents-realtime` 0.21.0 does that bookkeeping on WebSocket and emits `audio_interrupted`, but the application must still stop its own playback, and "Responses truncated by interruption do not retain a final transcript" ([OpenAI Agents SDK, building voice agents, mirrored](../../reference/openai-agents-sdk/source/docs/src/content/docs/guides/voice-agents/build.mdx)). A text agent never faces this gap, because a reader sees every token it streams.

**Tools already running at the barge-in need a rule, and the vendors choose opposite defaults.** Gemini cancels: "the ongoing generation is canceled and discarded", only what was "already sent to the client is retained", and the server "discards any pending function calls" ([Gemini, Live API capabilities](https://aistudio.google.com/docs/live-api/capabilities.md)). Its typed cancellation message warns that "If there were side-effects to those tool calls, clients may attempt to undo the tool calls" (`@google/genai` 2.32.0, `LiveServerToolCallCancellation`, installed typings). OpenAI's GPT-Live keeps going: "Interrupting the spoken conversation leaves backend work running", and the application must cancel in the backend and "confirm it succeeded before telling the user that the work was canceled" ([OpenAI, GPT-Live delegation](https://developers.openai.com/api/docs/guides/live-delegation)). Cloudflare's pipeline aborts the turn's `AbortSignal` on barge-in, and the docs' `streamText` example passes `abortSignal: context.signal`. We infer from how `AbortSignal` works that a tool step inside `onTurn` stops only if it honours that signal ([Cloudflare voice doc, mirrored](../../reference/cloudflare-agents/source/agents/docs/agents/voice.md)). Neither choice is safe by default for a side effect. A cancelled payment may already have run, and a running booking may finish after the user said "stop". We therefore propose a rule of our own, built on the idempotency that Chapter T23 teaches ([T23](../../todos/done/T23-chapter-side-effects-that-can-fail.md)): an interruptible tool is either idempotent and safe to finish, or it records its effect so the agent can undo it.

**Not every overlapping sound is a barge-in, and today's systems either yield too easily or hold the floor too long.** Full-Duplex-Bench v1.5 played four kinds of overlap at five systems. On a real interruption, `gpt-4o-realtime-preview-2024-12-17` stopped speaking in 0.23 s, while Gemini Live and Nova Sonic took 2.20 s and 2.25 s. Yet the same OpenAI model also answered 93% of background speech and 91% of speech aimed at someone else. Nova Sonic, by contrast, kept talking through 98% of the background speech, and Gemini through 99% of the side conversations. The authors conclude that "fast yielders excel on true interruptions but over-accommodate incidental speech, while robust holders resist non-addressed input yet delay necessary repairs" ([arXiv 2507.23159v4](https://arxiv.org/abs/2507.23159)). τ-Voice found the same split in 2026: OpenAI's agent scored 100% on responsiveness but only 6% on selectivity, the share of backchannels, vocal tics and side speech it correctly ignored ([arXiv 2603.13686v1](https://arxiv.org/abs/2603.13686)). These numbers describe the model versions tested, and each new release moves them.

**The agent's own voice is the commonest false barge-in, which is why echo cancellation belongs in the design.** A speaker next to a microphone feeds the agent's reply back as input, and a detector that hears it will cut the agent off. The WebRTC audio rules say endpoints "SHOULD include an AEC or some other form of echo control" ([RFC 7874](https://www.rfc-editor.org/info/rfc7874/)), and the Media Capture and Streams draft of 12 November 2026 defines the `echoCancellation` constraint that browsers expose to `getUserMedia` ([W3C, Media Capture and Streams](https://www.w3.org/TR/mediacapture-streams/)). The Pipecat-centred vendor guide adds that echo cancellation "has to run on the device (not in the cloud)" and blames a bot that interrupts itself on echo that leaks through (vendor guide, [Voice AI and voice agents](https://voiceaiandvoiceagents.com/)). Moshi was trained with "a scaled down copy of Moshi's stream" mixed into the user's channel to learn to ignore its own voice ([Moshi, arXiv 2410.00037v2](https://arxiv.org/abs/2410.00037)). Barge-in therefore has three parts to get right: stop the audio, settle the tools, and store only the heard words, all behind a detector that ignores the agent's own voice.

## A tool call silences a voice agent unless the agent announces it, runs it in the background or hands it to a backend agent

**A blocking tool call leaves the user listening to silence, which a phone line turns into a dropped call.** The OpenAI Agents SDK says it plainly: "While the tool is executing the agent will not be able to process new requests from the user", and the same holds while a tool waits for human approval ([building voice agents, mirrored](../../reference/openai-agents-sdk/source/docs/src/content/docs/guides/voice-agents/build.mdx)). Gemini's Live API also "executes sequentially by default", so "you won't be able to continue interacting with the model while the functions are being run" ([Gemini, Live API tools](https://aistudio.google.com/docs/live-api/tools.md)). Google's ADK docs put the cost in one line: "if the agent calls a ten-second API and goes silent, the user assumes the call dropped" ([ADK live tools, mirrored](../../reference/google-adk/source/adk-docs/docs/live/tools.md)). A text agent can show a spinner, but a voice agent has only its voice to say that it is still working.

**The sources offer three remedies, and each has a cost.** The first is to speak before the call. OpenAI calls these "preambles", "short spoken updates that keep a voice agent feeling responsive while it reasons, looks something up, or calls a tool", and `gpt-realtime-2` produces them by default ([OpenAI, voice prompting](https://developers.openai.com/api/docs/guides/voice-prompting)). Filler talks over users, though: in Full-Duplex-Bench-v3, Ultravox put a filler sentence before the answer in 88.0% of responses, and its filler overlapped the user often enough to give a 47.9% interruption rate ([arXiv 2604.04847v1](https://arxiv.org/abs/2604.04847)). The second is to run the call in the background. Gemini marks a function `NON_BLOCKING` and lets each result choose a `scheduling` of `INTERRUPT`, `WHEN_IDLE` or `SILENT`; `gemini-3.8-live` supports this and `gemini-3.8-live-extended-thinking` requires it ([Gemini, Live API tools](https://aistudio.google.com/docs/live-api/tools.md)). OpenAI's `async: true` flag does the same only in the Responses API, for "GPT-6 Astra and later models" ([OpenAI, async tool calling](https://developers.openai.com/api/docs/guides/async-tool-calling)); its Realtime guides document no such flag, as of November 2026. The third is to hand the work to a backend agent. A realtime handoff cannot change the model, so the Agents SDK tells builders who need "a reasoning model like `gpt-5.4`" to "use delegation through tools": a realtime tool that calls `run()` on a text agent with the conversation history ([building voice agents, mirrored](../../reference/openai-agents-sdk/source/docs/src/content/docs/guides/voice-agents/build.mdx)). GPT-Live builds that split into the model, which "can continue speaking while your application reviews a backend result" ([OpenAI, GPT-Live delegation](https://developers.openai.com/api/docs/guides/live-delegation)).

**Spoken tool use is less accurate than typed, and the benchmarks disagree on which architecture loses less.** τ-Voice's voice agents kept only "30--45% of text capability" on its 278 tasks, and "79--90% of failures stem from agent behavior" rather than the audio ([arXiv 2603.13686v1](https://arxiv.org/abs/2603.13686)). Full-Duplex-Bench-v3 measured failures that text cannot produce:
1. tool calls fired before the user finished speaking, from 10.8% of calls for GPT-Realtime to 41.6% for Grok;
2. a silent worker, where Gemini Live 3.1 produced no speech in 22% of cases yet still called tools in 86% of those;
3. mid-sentence self-corrections, where the best system, GPT-Realtime, scored 0.588 and the cascade 0.176, because "Whisper may finalize the original (incorrect) transcription before the user's correction arrives" ([arXiv 2604.04847v1](https://arxiv.org/abs/2604.04847)).

On that benchmark the speech-to-speech GPT-Realtime beat the cascade built on GPT-4o (Pass@1 0.600 against 0.450). VoiceAgentBench found the reverse for argument filling, where "ASR-LLM pipelines outperform end-to-end SpeechLMs" ([arXiv 2510.07978v3](https://arxiv.org/abs/2510.07978)), and a 2026 study measured a gap of only 1.8 to 4.8 points between text and voice on one function-calling benchmark, Confetti ([arXiv 2605.15104v3](https://arxiv.org/abs/2605.15104)). No architecture wins on accuracy everywhere. What every result shares is that spoken arguments arrive less reliably than typed ones. From that, we recommend a rule that no source states: a voice agent should read back the arguments of any consequential call before it runs.

## Browsers should reach the model over WebRTC and servers over WebSocket, and every session has a time limit

**The transport rule follows from the specifications: WebSocket runs over TCP, while WebRTC carries media over UDP.** RFC 6455 describes WebSocket as "basic message framing, layered over TCP" ([RFC 6455](https://www.rfc-editor.org/info/rfc6455/)). TCP delivers in order, so one lost packet holds back the audio behind it, and the WebRTC transport RFC names this "head of line blocking" as a reason TCP relays may perform worse than UDP ([RFC 8835](https://www.rfc-editor.org/info/rfc8835/)). WebRTC, a W3C Recommendation since 13 March 2025, sends media as encrypted RTP, requires full ICE for getting through NATs, and requires the Opus and G.711 codecs; Opus frames run from 2.5 to 60 ms ([W3C WebRTC](https://www.w3.org/TR/webrtc/); [RFC 8834](https://www.rfc-editor.org/info/rfc8834/); [RFC 7874](https://www.rfc-editor.org/info/rfc7874/); [RFC 6716](https://www.rfc-editor.org/info/rfc6716/)). OpenAI's advice matches: from a browser or phone app "we recommend using WebRTC rather than WebSockets for more consistent performance", WebSocket is "a great choice" from server to server, and SIP connects a phone number ([OpenAI, WebRTC](https://developers.openai.com/api/docs/guides/voice-webrtc); [OpenAI, WebSocket](https://developers.openai.com/api/docs/guides/voice-websockets); [OpenAI, SIP](https://developers.openai.com/api/docs/guides/voice-sip)). Gemini's Live API, by contrast, offers only a "Stateful WebSocket connection (WSS)" and leaves WebRTC to partner integrations ([Gemini, Live API](https://aistudio.google.com/docs/live-api.md)).

**A browser never holds the API key, so a server mints a short-lived credential for each session.** OpenAI's server calls `POST /v1/realtime/client_secrets` for a secret that lasts 600 s by default and 10 to 7,200 s at most; the secret limits when a session may start, and "The session itself may continue after that time once started" ([OpenAI, client secrets reference](https://developers.openai.com/api/reference/resources/realtime/subresources/client_secrets/methods/create)). Gemini's ephemeral tokens give one minute to start a session and 30 minutes to send messages by default ([Gemini, ephemeral tokens](https://aistudio.google.com/docs/live-api/ephemeral-tokens.md)). The Vercel AI SDK's experimental realtime follows the same pattern, with sessions that "run in the browser and connect directly to the provider using a short-lived token that you create on your server" (`ai` 7.0.162, shipped docs `36-realtime.mdx`).

**Sessions end on a clock, so a long call needs reconnection that a text agent never wrote.** "The maximum duration of a Realtime session is 60 minutes" at OpenAI ([OpenAI, Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations)). Without context compression, a Gemini audio-only session lasts 15 minutes and a single connection "around 10 minutes", and resumption tokens stay valid for two hours after a session ends ([Gemini, session management](https://aistudio.google.com/docs/live-api/session-management.md)). Google ADK's TypeScript live flow reconnects with the last resumption handle up to five times (`@google/adk` 2.5.0, `MAX_LIVE_RECONNECT_ATTEMPTS = 5` in compiled `llm_agent.js`, read but not run).

**Audio costs more than text per token, and the vendors price it in different units.** As of November 2026, `gpt-realtime-2.1` charges $32 per million audio input tokens and $64 per million output, against $4 and $24 for text, and `gpt-realtime-2.1-mini` charges $10 and $20 for audio ([OpenAI, pricing](https://developers.openai.com/api/docs/pricing)). OpenAI counts one token per 100 ms of user audio and one per 50 ms of assistant audio ([OpenAI, latency and cost](https://developers.openai.com/api/docs/guides/voice-latency-cost)), so a minute of each costs about $0.019 to hear and $0.077 to speak on `gpt-realtime-2.1`, by our arithmetic. Gemini 3.8 Live charges $3.00 per million audio input tokens or $0.005 a minute, and $12.00 or $0.018 a minute for audio output ([Gemini, pricing](https://aistudio.google.com/docs/pricing.md)). GPT-Live charges by time, $0.05 a minute billed per second, with backend model use billed apart ([OpenAI, pricing](https://developers.openai.com/api/docs/pricing)). A cost model for a voice agent should therefore count minutes of speech as well as tokens.

| LangChain 1.6.1 | None; audio only as a content block and in `ChatOpenAI` output | None | None | The ordinary `createAgent` loop | Fake speech stages around the fake chat model |
| Claude Agent SDK 0.3.327 | None; the CLI's dictation appears only as settings | None | `Query.interrupt()` as the hook | The ordinary loop | Text side only, against the mock Messages API |

**OpenAI and Cloudflare chose opposite architectures, and each choice fixes what the builder controls.** OpenAI's `RealtimeAgent` drops `model`, `outputType` and the agent-level guardrails from the text agent's configuration, because "all RealtimeAgents will be handled by the same model within a `RealtimeSession`". Output guardrails move to the session and check the transcript every 100 characters by default (`realtimeAgent.d.ts`, `guardrail.d.ts`). Every shipped transport speaks OpenAI's protocol, though the docs allow a builder to implement `RealtimeTransportLayer` for "a different speech-to-speech API" ([voice transports, mirrored](../../reference/openai-agents-sdk/source/docs/src/content/docs/guides/voice-agents/transport.mdx)). Cloudflare keeps the text loop and swaps only the ends: `Transcriber` and `TTSProvider` are small interfaces, and AssemblyAI, Deepgram, ElevenLabs and telephony adapters arrive as separate `@cloudflare/voice-*` packages. Its docs warn "**Experimental.** This API is under active development and will break between releases" ([Cloudflare voice doc, mirrored](../../reference/cloudflare-agents/source/agents/docs/agents/voice.md)). Its stored history is plain `{ role, content }` text, so tool results from one turn do not reach the next unless the builder stores them (our inference from the type).

**ADK and the AI SDK ship live layers that run beside their text loops, and their docs lag their code.** ADK's `runLive` "is **experimental** and its API may change", and it reuses the same agents, tools and sessions through a separate live flow (`runner.d.ts`). Every page under ADK's live docs is tagged Python or Java, and Python's `CascadeLive` saves "Only the words the user heard" after an interruption, and a search of the TypeScript typings finds no `CascadeLive` ([ADK cascade, mirrored](../../reference/google-adk/source/adk-docs/docs/live/architectures/cascade.md)). The AI SDK's realtime is a browser session in which "Realtime tool execution is client-driven", so its tools leave the `generateText` loop entirely (`ai` 7.0.162, shipped docs `36-realtime.mdx`). Its most useful voice part for a server is `experimental_streamSpeech`, which accepts a `streamText` text stream and starts audio before the text has finished (shipped docs `37-speech.mdx`).

**The other four SDKs have no audio, and neither does the Claude API beneath the Claude Agent SDK.** As of November 2026, "All current models support text and image input, text output" ([Claude, models overview](https://platform.claude.com/docs/en/models/overview)), and the Claude docs index lists no audio, speech or realtime page ([Claude docs index](https://platform.claude.com/llms.txt)). A voice agent on Claude is therefore a chained pipeline with outside speech-to-text and text-to-speech. Anthropic's own voice mode, a beta feature of the Claude apps, says the user's "speech is converted to text" ([Claude Help Center, voice mode](https://support.claude.com/en/articles/11101966-use-voice-mode)). LangChain documents the chained pipeline for JavaScript as well as Python, claims "sub-700ms latency" with some providers, and nothing on either page handles barge-in ([LangChain JS voice agent](https://docs.langchain.com/oss/javascript/langchain/voice-agent)). Each of the four exposes an abort or interrupt call that a chained pipeline can use as its barge-in hook. None of them tells the agent which words were heard, so that truncation is code the builder writes.

## T38 should teach four differences from the text loop in one section, opened by the phone-call analogy

**In our judgement the evidence fits one section of Chapter T35, so T38 need not become a chapter.** T38 asks the research to say whether the topic "needs a chapter after all" ([T38](../../todos/done/T38-section-voice-and-realtime.md)). We judge that it does not, because every finding above is a change to the loop the book has already taught, and each fits in a paragraph with one number to remember. A reader who builds a voice agent will still need the vendor guides for transports and audio formats, and the section should say so and link them. The section should teach four differences, in this order:
1. **The loop is a session driven by events.** Name the three shapes (speech-to-speech, chained pipeline and a speaking front model that delegates) and show that the tool loop survives inside each. The number to remember is the 208 ms gap that people leave between turns.
2. **Turn detection predicts the end of a turn.** Show the trade between a short silence threshold and a late reply, with OpenAI's 500 ms default and the robot study's drop from 2.7 s to 1.5 s, and name push-to-talk as the simple escape.
3. **Barge-in stops the speech, settles the tools and keeps only the heard words.** Show truncation to `audio_end_ms`, the opposite defaults of Gemini and GPT-Live for tools in flight, and the yield-or-hold trade, with GPT-4o realtime's 0.23 s stop beside its 93% reply rate to background speech.
4. **Tools must not silence the agent.** Show announcing, background calls and delegation to a text agent, and close on τ-Voice's 85% against 31–51% as the reason for our rule to read back consequential arguments.

**The phone-call analogy holds, but its break note should name the two duties that the evidence adds.** T38 plans "voice interruption, as a phone call where either side can cut in", breaking where "the agent must cancel speech and tool calls already in flight". The analogy fits, because conversation overlaps in both directions; the Full-Duplex-Bench v1.5 authors, citing earlier studies, put overlap at "over 40% of turns" in natural dialogue ([arXiv 2507.23159v4](https://arxiv.org/abs/2507.23159)). The break note says too little, though. Cancelling every tool in flight is not the rule, since Gemini cancels pending calls while GPT-Live keeps backend work running. A person on the phone also remembers only what was said aloud, while the agent's context holds the unspoken rest of its reply. We propose that the note read: "the agent must stop speaking at once, decide for each tool in flight whether it finishes or is undone, and forget the words the caller never heard". This wording changes an owner-approved analogy, so it is proposed change 3 below.

**Every model name, price and benchmark score in the section will age within months, so each needs its date and version.** GPT-Live and `gpt-realtime-2.1` were current in November 2026, OpenAI's `gpt-4o-mini-tts` shuts down on 6 January 2027 ([OpenAI, text to speech](https://developers.openai.com/api/docs/guides/text-to-speech)), and each benchmark above tested one model version. The section should give scores as "the version tested in 2025" or "in 2026", never as a property of a vendor.

## Two new examples would give the section its listings, led by a scripted OpenAI realtime session

**The first example should run an OpenAI realtime session against the SDK's own scripted transport, because that needs no network and no new dependency.** `@openai/agents-realtime` 0.21.0 ships `ScriptedRealtimeTransport`, "An in-memory Realtime transport for deterministic session tests", and the SDK's testing guide says its doubles "make no model, sandbox provider, or Realtime API requests" (`dist/testing/scriptedRealtimeTransport.d.ts`; [testing guide, mirrored](../../reference/openai-agents-sdk/source/docs/src/content/docs/guides/testing.mdx)). A new `verify/openai-agents-sdk/examples/10-realtime-session.ts` would assert four behaviours with `check()`:
1. a user message and the scripted reply leave `session.history` equal to the script;
2. a scripted `function_call` runs a `tool()` and returns its output through `sendFunctionCallOutput`;
3. a `needsApproval` tool raises `tool_approval_requested` and runs only after `session.approve()`;
4. `session.interrupt()` reaches the transport, and a scripted `audio_interrupted` reaches the session's listener.

Checks 1, 2 and 4 follow the SDK's own doc tests, which type-check against the pin. Check 3 has no doc test, so it stays untested until the example runs.

The example needs one harness change. Our runner skips any source that matches `/@openai\/agents\/realtime|RealtimeSession|RealtimeAgent/`, our own examples included ([`run-examples.mjs`](../../../verify/openai-agents-sdk/scripts/run-examples.mjs)), so the pattern must exempt files that import the testing transport. The listing cannot show truncation itself, because the guide says server behaviour and audio playback "require the real transport", so the section should explain truncation in prose beside it.

**A second example should show the chained pipeline and barge-in on Cloudflare, where the loop stays an ordinary `streamText` call.** A new `verify/cloudflare-agents/examples/11-voice-pipeline.ts` (T44 already claims number 10) would give a `withVoice(Agent)` class a fake `Transcriber` that turns one audio frame into a transcript and a fake `TTSProvider` that returns fixed bytes. Its `onTurn` would run `streamText` on the harness's scripted model with one tool. Over the Agent's WebSocket in workerd, the example would assert:
1. an interim and a final transcript arrive;
2. the tool runs inside `onTurn`;
3. at least one audio frame and a `turn_metrics` message follow;
4. an `interrupt` message sent while the agent speaks aborts `context.signal` and returns the status to `listening`.

This design is untested, because no voice example has run in our workerd harness yet. Our Cloudflare runner skips `agents/voice` only in doc blocks, not in our own examples, so this one needs no harness change ([`run-examples.mjs`](../../../verify/cloudflare-agents/scripts/run-examples.mjs)). The API is marked experimental, so the example pins its behaviour at 0.33.0 and would flag a breaking change on the next upgrade.

**Three smaller examples would close reference gaps but are not needed for T38.** The SDK notes propose a chained pipeline on the AI SDK's transcription and speech mocks, an ADK `runLive` run against a fake `BaseLlmConnection`, and a text-side barge-in on Pi that aborts a streamed reply and checks what the session keeps ([SDK notes](notes/sdks-adk-vercel-langchain-claude-copilot-pi.md)). Each would turn a finding of this report into a checked behaviour, and none blocks the section.

## Voice keeps the agent loop and adds a listener's clock: predict the turn, keep only the heard words, never go silent

The evidence of November 2026 turns T38's one-line plan into four rules a builder can follow. A voice agent keeps the tool loop of a text agent and runs it inside one session that events drive, whether a speech-to-speech model, a chained pipeline or a speaking front model with a backend carries the audio. It predicts when the person has finished, because people answer within about 200 ms and a fixed silence threshold either cuts them off or answers late. When the person cuts in, it stops speaking, settles each tool in flight by finishing or undoing it, and cuts its context back to the words the person heard. It never leaves the person in silence while a tool runs, and, by the rule we propose, it reads back spoken arguments before a consequential call. In TypeScript, OpenAI's and Cloudflare's SDKs carry that session today, ADK and the AI SDK carry experimental parts of it, and the other four leave it to the builder. The two examples the owner approved on 2026-11-19, a scripted OpenAI session (T46) and a Cloudflare pipeline with barge-in (T47), will let the book teach those rules from code that runs offline.
