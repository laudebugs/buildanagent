# Own the loop, rent the sandbox

Most teams should write the thin parts of an agent themselves and buy the heavy infrastructure. That means owning a small, linear agent loop, the tool definitions, the context policy and an append-only session log. It means renting sandboxes, durable execution and observability backends. It also means borrowing designs freely from open-source harnesses rather than forking a whole product. The decision matters because the harness is not plumbing. Holding the model fixed and changing only the harness moved Pass@1 from **19% to 73%** in one adapter comparison, and harness choice alone accounted for a **27.4-point** spread in the same benchmark. The evidence is not one-sided, though. A careful rerun study found that among mature coding harnesses, swapping the harness changes outcomes about as often as rerunning the same one, and that the main reliable difference is **cost**. Choosing an SDK is therefore partly choosing your agent's capability and, more reliably, its token bill. Vendor SDKs sit in three tiers. The **Claude Agent SDK** ships Anthropic's production coding harness, but you configure it rather than own it. **OpenAI Agents SDK, Google ADK, Microsoft Agent Framework and AWS Strands** are library loops you embed. **Cloudflare Agents** is a durable runtime that hosts any loop you bring. Open-source frameworks (LangGraph, Pydantic AI, Mastra, CrewAI) are most useful as sources of primitives to copy: checkpoint and resume, non-blocking approvals, typed tools. The open-source harnesses (OpenHands SDK, OpenCode, Codex, Goose, mini-swe-agent, DeepSeek Harness) have converged on one template: a headless core, a workspace or sandbox abstraction, an event log, a summarizing condenser and MCP for extensions. That template is the reference architecture this report recommends. One caveat runs through everything below. The research environment's network policy blocked many primary sources, including arxiv.org, openai.github.io, developers.cloudflare.com, modelcontextprotocol.io, inspect.aisi.org.uk and several blogs. Some figures therefore come from search-engine summaries and are flagged as such. The last section sets out those limits in full.

## Harness choice can swing scores widely, or mostly change cost

The strongest argument for treating harness design as a first-class engineering problem is empirical. On Claw-SWE-Bench (350 issue-fix tasks across 8 languages and 43 repos), the same GLM 5.1 backbone scored **19.1% Pass@1 with a minimal direct-diff adapter and 73.4% with the full adapter** (abstract figures; the body reports a related 19.3% vs 71.2% comparison). Across its sweeps, model choice moved Pass@1 by 29.4 points and harness choice by 27.4 points under fixed models ([arXiv 2606.12344](https://arxiv.org/pdf/2606.12344); [opentrain summary](https://www.opentrain.ai/papers/claw-swe-bench-a-benchmark-for-evaluating-openclaw-style-agent-harnesses-on-codi--arxiv-2606.12344/)). A paper arguing that agent comparisons must disclose the harness found **Claude Opus 4.5 at 45.9% on SWE-bench Pro under the standardized SEAL scaffold versus 55.4% inside Claude Code** ([arXiv 2605.23950](https://arxiv.org/html/2605.23950)). Terminal-Bench 2.0 coverage reports Claude Opus 4.6 at 58.0% in Claude Code versus 74.7% in a third-party harness, though that comparison was not checked against the official leaderboard ([Vaughan](https://codex.danielvaughan.com/2026/04/09/harness-performance-terminal-bench/)). Harness-Bench (106 sandboxed tasks, 5,194 trajectories) found that completion, process quality and efficiency all vary substantially across model–harness pairs ([arXiv 2605.27922](https://arxiv.org/html/2605.27922)).

The effect has a shape, and that shape should drive build decisions. "Beyond the Model: Demystifying Harness Effects in Software Engineering Agents" (Hu et al., [arXiv 2609.32459](https://arxiv.org/abs/2609.32459)) built NanoHarness on top of mini-SWE-agent to ablate five components: tool registry, context compression, explicit planning, subagents and lazy skills. It concludes that harness effectiveness depends jointly on model capability and task type. A secondary write-up of the paper adds two claims ([agentpatterns.ai](https://agentpatterns.ai/patterns/agent-design/task-shape-harness-payoff/)). On fixed-workflow issue repair, heavy harnesses compensate for weaker models and lose value as models improve: OpenHands' gain reportedly fell from +13.60 to +5.47 points between Claude 3.7 Sonnet and Claude 4 Sonnet. On open-ended repository generation the trend reverses. A separate study, "An Empirical Study of Harness Design for Coding Agents" ([arXiv 2609.20804](https://hyper.ai/en/papers/2609.20804)), found the same decay for context management: its payoff on SWE-bench shrank from 35.7 to 2.7 points as the context window grew from 32K to 128K (secondary summary). A third paper gives the blunt version in its title: "What Does a Harness Buy? Tokens, Mostly." On a 45-task hard subset across five models, swapping among Claude Code, OpenCode and mini-SWE-agent changed the outcome on about as many tasks as rerunning the same harness (about 13% each). The only harness effect that cleared the noise was negative: OpenCode trailed by up to 9 points, partly from runs cut short by its output cap. What the harness reliably decided was the bill. The authors estimate that about 447 tasks are needed to resolve a 5-point difference ([arXiv 2610.04433](https://arxiv.org/pdf/2610.04433)). Read together, the studies say that the biggest harness gains come from fixing a broken interface (the Claw-SWE-Bench adapter), and that differences among mature harnesses are small, noisy and shrinking. Infrastructure is a confound too. Anthropic measured a **6-point swing on Terminal-Bench 2.0 from pod resource limits alone**, with the same model, tasks and harness ([Anthropic](https://www.anthropic.com/engineering/infrastructure-noise)).

Three things follow for a team. First, harness changes are model changes, so every prompt, tool or context-policy change needs an A/B test with the model held fixed. Second, scaffolding that helps today (sprints, context resets, separate planners) is likely to become dead weight with the next model, so build it to be removable. Third, adopting a vendor harness gives you a heavily tuned scaffold for free, which is a real advantage only as long as you stay on that vendor's models.

The most useful question about a vendor SDK is the one practitioners keep asking: who owns the agent loop?

### The Claude Agent SDK trades control for a tuned harness

The Claude Agent SDK is "Claude Code as a library." It provides "the same tools, agent loop, and context management that power Claude Code" ([overview](https://code.claude.com/docs/en/agent-sdk/overview)). Architecturally, **one agent session maps to one subprocess**. That process owns the shell, the working directory and the transcripts on local disk, and turns run "without yielding control back to your code" ([hosting](https://code.claude.com/docs/en/agent-sdk/hosting.md)). You steer the loop through `max_turns`, `max_budget_usd`, effort levels, PreToolUse/PostToolUse/PreCompact hooks, `canUseTool` callbacks, permission modes, custom in-process tools and MCP. Compaction is automatic, and you can shape it with instructions or a hook. No documented option lets you replace the compaction algorithm ([agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop.md)). The operating costs are concrete. The docs suggest **1 GiB RAM, 5 GiB disk and 1 CPU per agent as a floor**. They list no top-level session timeout and no per-subagent wall-clock deadline. None of the local state survives a container restart unless you mirror it. Multi-tenant isolation requires per-tenant config directories, disabled auto-memory and egress proxy rules ([hosting](https://code.claude.com/docs/en/agent-sdk/hosting.md)). Sandboxing is your job, unless you move to Anthropic's hosted Managed Agents.

The Claude Agent SDK is the fastest route to a strong coding- or filesystem-shaped agent, provided Claude-only is acceptable. It is the wrong base when you need custom compaction, custom turn scheduling, cross-vendor model portability or high-concurrency chat, where a 1 GiB subprocess per session is expensive.

### Library SDKs are harness toolkits you can own

OpenAI's SDK calls itself "a lightweight yet powerful framework for building multi-agent workflows." Its primitives are agents, tools (functions, MCP, hosted tools, agents-as-tools), handoffs, guardrails, sessions and tracing. It is MIT-licensed and provider-agnostic across "100+ other LLMs" ([openai-agents-python](https://github.com/openai/openai-agents-python)). In April 2026 it added sandbox agents and a long-horizon harness, described as "separating the harness from the compute" ([The New Stack](https://thenewstack.io/openai-agents-sdk-sandboxes/)). The repo confirms `SandboxAgent` with a `Manifest` and pluggable clients: Unix-local and Docker built in, plus Blaxel, Cloudflare, Daytona, E2B, Modal and Vercel extensions. The Unix-local client adds no OS confinement on Linux ([source notes](harness-architectures.md#openai-agents-sdk-sandbox-agents-harness-as-library)). Pre-April comparisons that say OpenAI lacks sandboxed execution are out of date. Durability is not automatic. You get it through integrations, with the Temporal integration reported GA in March 2026 (search summary; [Temporal docs](https://docs.temporal.io/develop/python/integrations/openai-agents)).

Google's **ADK 2.0** moved "from a hierarchical agent executor to a graph-based execution engine." Its breaking changes to the agent API, event model and session schema mean material describing `LlmAgent` plus Sequential/Parallel/Loop agents is 1.x-era (search summary; [Why we built ADK 2.0](https://developers.googleblog.com/en/why-we-built-adk-20/)). **Microsoft Agent Framework 1.0** went GA on April 3, 2026, and Semantic Kernel and AutoGen are now in maintenance mode (search summary; [Microsoft DevBlog](https://devblogs.microsoft.com/agent-framework/?p=5212)). **Cloudflare Agents** is a different kind of product. Its agents are Durable Objects that "hibernate when idle and wake on demand," with built-in SQLite, cron scheduling, workflows with HITL pause/resume, and isolated-Worker code execution ([cloudflare/agents](https://github.com/cloudflare/agents)). It pairs naturally with a custom loop or with OpenAI's JS SDK. It also shows API churn: several packages are already deprecated.

In practice, choosing among the library SDKs mostly follows your cloud and language: OpenAI for Python/TS, Google for Gemini and multi-language stacks, Microsoft for Azure/.NET, Strands for AWS/Bedrock. Each locks in an orchestration vocabulary (handoffs, graphs) more than a model. No vendor SDK gives you custom compaction, full loop control and cross-vendor model portability together, and that combination is the core case for building your own.

## Open-source frameworks are better quarries than foundations

The open-source frameworks sit along a control spectrum. At the developer-controlled end are LangGraph graphs, CrewAI Flows, Mastra workflows and LlamaIndex Workflows. In the middle are developer-bounded LLM loops: Pydantic AI agents, the Vercel AI SDK's `ToolLoopAgent`, LangChain's `create_agent`. At the LLM-controlled end are CrewAI Crews and smolagents' CodeAgent, where the model writes the control flow as Python. The 2026 consensus is to put deterministic orchestration around the autonomous parts. One practitioner puts it this way: "In every production system I have shipped, Flows wrap Crews" ([jahanzaib.ai](https://www.jahanzaib.ai/blog/crewai-flows-production-multi-agent-guide)).

Each framework has a distinct production story. **LangGraph** (1.0 GA in October 2025, with a no-breaking-changes promise until 2.0) has first-class durable execution, checkpointing and `interrupt()`/`Command(resume=)` for human-in-the-loop ([LangChain blog](https://www.langchain.com/blog/langchain-langgraph-1dot0)). It is praised as "unmatched for time-travel debugging" ([activewizards](https://activewizards.com/blog/langgraph-vs-direct-api-orchestration-when-the-framework-earns-its-weight/)). It is also criticized for boilerplate and non-linear debugging, and one team removed it because tracing simple bugs required walking through several state transitions ([dev.to](https://dev.to/nicolaric/why-we-removed-langgraph-from-our-ai-platform-i9o)). **Pydantic AI** is the typed, testable Python option. It does not build its own checkpoint store. Instead it delegates durability to nine listed engines, Temporal and DBOS among them, turning each model and tool call into a durable activity ([Pydantic AI durable execution](https://pydantic.dev/docs/ai/harness/durable-execution/)). Its deferred tools end a run and resume it later with results keyed by tool-call ID, so an approval never blocks a thread ([pydantic_ai.tools](https://pydantic.dev/docs/ai/api/pydantic-ai/tools/)). **Mastra** is the TypeScript default. It ships storage-backed suspend/resume, tracing, evals, and MCP as both client and server ([GitHub](https://github.com/mastra-ai/mastra)). **CrewAI** has the most GitHub stars (about 60K in November 2026) and the most cautionary reviews: "magical in a demo and expensive in production" ([orange-its](https://www.orange-its.ch/en/insights/crewai-review)). It also had four 2026 CVEs, including an arbitrary file read, all now patched ([Drel](https://drel.ai/blog/crewai-security-review)).

Several practitioner sources argue that many production teams use hand-written loops or thin wrappers. The evidence is directional (one vendor guide), not a survey ([apiscout.dev](https://apiscout.dev/guides/building-ai-agent-architecture-patterns-2026)). Anthropic's long-standing advice points the same way. Frameworks "can add abstraction layers that obscure prompts and responses." Teams should start with LLM APIs directly and add complexity only when it measurably helps ([Anthropic](https://www.anthropic.com/engineering/building-effective-agents)). The right posture is to borrow the primitives these frameworks spent years refining, without adopting their core abstractions:

| Primitive to borrow | Origin | Why |
|---|---|---|
| Interrupt/resume tokens with single-resume guarantee | LangGraph, Mastra | Clean HITL and crash recovery |
| Deferred tool results (run ends, resumes later) | Pydantic AI | Non-blocking approvals at scale |
| Per-tool `needsApproval(args)` predicates, cryptographically bound to the call | Vercel AI SDK | Fine-grained HITL; avoids forged client approvals |
| Composable stop conditions with a default step cap (20) | Vercel AI SDK | Prevents runaway loops |
| Durable-execution adapter (model/tool calls as activities) | Pydantic AI + Temporal | Durability without a bespoke checkpoint store |
| Middleware around model and tool calls | LangChain 1.0 | One extension point for guards, logging, HITL |
| State by reference, not by value | LangGraph practitioners | Avoids 40–60 ms/step serialization overhead |
| MCP as client *and* server | Mastra | Your agents become tools for other agents |
| Optional code-action mode behind a remote sandbox | smolagents | Up to 20% higher success reported for code actions, but heavy sandboxing burden |

Sources: [LangGraph v1](https://docs.langchain.com/oss/python/releases/langgraph-v1); [Mastra resume](https://mastra.ai/reference/workflows/run-methods/resume); [issoh.co.jp](https://www.issoh.co.jp/tech/details/10402/); [activewizards](https://activewizards.com/blog/langgraph-vs-direct-api-orchestration-when-the-framework-earns-its-weight/); [smolagents secure execution](https://huggingface.co/docs/smolagents/main/tutorials/secure_code_execution); [themenonlab](https://themenonlab.blog/blog/code-vs-json-llm-tool-calling).

The steelman for adopting a framework is real. If you need durable checkpointing, HITL and replay across many workflows now, and your team writes Python or TypeScript, LangGraph or Mastra "earns its overhead" ([activewizards](https://activewizards.com/blog/langgraph-vs-direct-api-orchestration-when-the-framework-earns-its-weight/)). Hand-building means owning context windowing, retries, token counting and observability yourself ([ai-tldr.dev](https://ai-tldr.dev/learn/agent-frameworks/choosing-a-framework/agent-without-framework/)).

## Open-source harnesses converged on one template worth copying

All the open-source harnesses examined exist and are permissively licensed, MIT or Apache-2.0 ([OpenHands SDK](https://github.com/OpenHands/software-agent-sdk); [OpenCode](https://github.com/anomalyco/opencode); [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness); [Codex](https://github.com/openai/codex); [Goose](https://github.com/aaif-goose/goose); [mini-swe-agent](https://github.com/SWE-agent/mini-swe-agent)). Goose has moved to `aaif-goose/goose` under the Linux Foundation's Agentic AI Foundation. SWE-agent is in maintenance mode, superseded by mini-swe-agent. The harnesses differ less than their branding suggests. A 70-project empirical study of harness architecture found that design decisions co-occur in bundles forming **five typical patterns**, and that programming language does not predict which pattern a project follows ([arXiv 2604.18071](https://arxiv.org/pdf/2604.18071); [Moonlight](https://www.themoonlight.io/review/architectural-design-decisions-in-ai-agent-harnesses)).

The dominant 2026 shape is a **headless core with many thin clients**. OpenHands exposes an agent server over REST/WebSocket with a generated TypeScript client. OpenCode runs a server (reportedly Hono on Bun, with SQLite sessions) and treats its TUI, desktop and web apps as views over HTTP and SSE ([architecture map](https://ggprompts.github.io/htmlstyleguides/architecture/opencode/index.html)). Cline's `sdk/` powers its CLI, VS Code and desktop clients ([Cline](https://github.com/cline/cline)). OpenClaw centres on a local Gateway control plane ([OpenClaw](https://github.com/openclaw/openclaw)). Each harness then teaches a different lesson:

| Harness | Lesson to take | Fork it? |
|---|---|---|
| **OpenHands Software Agent SDK** (Python, MIT) | Event-sourced state: an immutable append-only log with deterministic replay, `ConversationState` as the only mutable component, a workspace abstraction for local vs. Docker/K8s, and an `LLMSummarizingCondenser` reported to cut cost up to 2x (secondary) | Best fork candidate for a Python product SDK: modular packages, peer-reviewed design (MLSys 2026) |
| **OpenCode** (TS/Bun, MIT) | Client/server split; `build` vs. read-only `plan` agents; LSP diagnostics fed back after edits; compaction as a hidden agent | Good for a TS coding product; internals known mainly from third-party write-ups |
| **Codex CLI** (Rust, Apache-2.0) | OS-native sandboxing (Seatbelt on macOS; bubblewrap + seccomp on Linux, with Landlock only as a legacy flag; Windows ACLs) under one `SandboxPolicy` (`read-only` default / `workspace-write` / `danger-full-access` / `external-sandbox`), with a separate `AskForApproval` policy and an orchestrator that re-approves escalations after a sandbox denial ([source notes](harness-architectures.md#codex-cli-the-sandbox-first-harness)) | Study the sandbox design; forking a Rust CLI is heavy |
| **Goose** (Rust, Apache-2.0) | Every extension is an out-of-process MCP server (70+); foundation governance | Learn the extension model |
| **DeepSeek Harness** (TS, MIT) | "Everything is a Plugin," including the loop itself; model-open | Developer preview with breaking changes expected; reportedly lacks evals and metering ([developersdigest](https://www.developersdigest.tech/blog/deepseek-harness-dsh-first-look)) |
| **Pi** (TS, MIT; `earendil-works/pi`) | Layered packages (LLM API → loop core → coding agent); 4 tools (`read`, `bash`, `edit`, `write`); tree-shaped JSONL sessions so compaction and forks are reversible; no built-in permission system, so it runs inside a container | Good base for a minimal TS harness; the loop core is a separate npm package ([source notes](harness-architectures.md#pi-the-minimal-harness)) |
| **mini-swe-agent** (Python, MIT) | About 100 lines; bash as the only tool; no tool-calling API; stateless `subprocess.run`; linear history; self-reported >74% SWE-bench Verified | Use as the neutral baseline for every harness experiment |

Sources: [emergentmind on OpenHands SDK](https://www.emergentmind.com/papers/2511.03690); [MLSys 2026](https://proceedings.mlsys.org/paper_files/paper/2026/hash/8ae9cf363ea625161f885b798c1f1f78-Abstract-Conference.html); [Codex sandboxing (mintlify mirror)](https://www.mintlify.com/openai/codex/concepts/sandboxing); [cefboud OpenCode deep dive](https://hn.jakechampion.name/reader/https://cefboud.com/posts/coding-agents-internals-opencode-deepdive).

Star counts measure attention, not fitness. DeepSeek Harness showed about 283K stars three months after its August 2026 launch, and OpenClaw about 395K. Neither number says anything about production readiness. Forking makes sense when your product resembles the harness's product, such as a coding agent with a UI. In that case OpenHands SDK (Python) or OpenCode (TypeScript) saves months. For a domain agent (support, research, operations), forking imports coding-specific assumptions you will spend effort removing. Copy the template instead.

## A reference architecture in eight swappable layers

The best-documented template comes from Anthropic's Managed Agents design. It virtualizes three components behind stable interfaces: a **Session** (append-only event log), a **Harness** (a stateless loop that calls the model and routes tool calls) and a **Sandbox** (where code runs), using interfaces such as `execute(name, input) -> string`, `provision()`, `wake(sessionId)` and `emitEvent()` ([Anthropic: Managed Agents](https://www.anthropic.com/engineering/managed-agents)). Moving the harness out of the container made container failure "just a tool error," let a crashed harness resume from the log, and cut **p50 time-to-first-token by about 60% and p95 by over 90%**, because the harness no longer waits for provisioning ([same](https://www.anthropic.com/engineering/managed-agents)). The OpenHands event log, OpenCode's server and Codex's app-server all reach the same separation on their own. The recommended architecture extends it:

| Layer | Build or buy | Design rules from the evidence |
|---|---|---|
| **1. Model gateway** | Build thin; use provider SDKs | Streaming, retry/backoff on 429/5xx, prompt caching, per-run token and cost accounting, routing easy work to smaller models |
| **2. Harness loop** (stateless) | **Build** | Rebuild context from the log → call model → validate tool calls → permission check → execute in parallel → append → check stop conditions (end turn, max turns/tokens/cost/time, done tool, HITL pause). Linear and debuggable; graphs are an optional outer layer |
| **3. Session store** | Build schema; buy storage | Append-only event log as the source of truth from day one; HITL pauses are just persisted "waiting" events; deferred tool results keyed by call ID |
| **4. Tools and MCP** | **Build tools**; adopt MCP SDKs | Few consolidated, namespaced tools; absolute paths; actionable errors; truncated high-signal output; MCP client on the 2026-07-28 stateless core; tool search once tool count grows |
| **5. Context policy** | **Build** | Tool-result clearing first, then summarizing compaction; keep the raw log so compaction stays recoverable; just-in-time retrieval by reference; subagents return condensed summaries |
| **6. Memory** | Build files first; buy services later | Progress files, JSON task lists and git history before vector or graph memory; skills as procedural memory |
| **7. Sandbox and secrets** | **Buy** (or adopt OS sandbox) | `provision`/`execute` interface over pluggable backends; filesystem *and* network isolation; egress proxy; credentials never inside the sandbox |
| **8. Observability and evals** | Buy backend; build suite | OTel `gen_ai.*` spans with a pinned convention version; Inspect bridge for offline evals; pass^k plus cost on every change |

### Tools and context deserve more effort than the prompt

Anthropic reports spending more time optimizing tools than the overall prompt on SWE-bench. Requiring absolute paths eliminated a whole class of errors, and a rewritten tool description cut task time by **40%** ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents); [multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)). Its tool guidance calls for fewer purpose-built tools, namespacing, readable identifiers instead of UUIDs, a concise response format (about one-third of the tokens in its example) and truncation, with Claude Code capping tool responses at 25,000 tokens by default ([Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)). At scale, deferred tool loading cut tool-definition context from **about 77K to 8.7K tokens**. Exposing MCP servers as code APIs that the agent calls from a sandbox reduced one Drive-to-Salesforce workflow from **about 150,000 to 2,000 tokens** ([Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use); [Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)). Context engineering aims at "the smallest set of high-signal tokens," because recall degrades as context grows ("context rot") ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

On MCP, the 2026-07-28 revision reportedly removed the `initialize` handshake and protocol-level sessions, added routing headers for gateways and moved Tasks into an extension. The change makes horizontally scaled harnesses simpler, but it is not fully backward compatible (search summary; [Claude blog](https://claude.com/fr/blog/bringing-mcp-2026-07-28-to-claude); [AAIF migration guide](https://aaif.io/blog/mcp-2026-07-28-whats-changing-and-how-to-migrate)). The spec site was unreachable from the research environment, so these details should be verified before you implement them.

### Planning should start as ReAct and earn every extra agent

No controlled, independent benchmark compares planning patterns under identical models. Practitioner estimates rank ReAct as the cheapest. Plan-and-execute costs more up front but allows cheaper executors and parallel branches. Reflection runs about **2–4x** a ReAct run, and tree-of-thought is rarely used in production (search summaries; [mlflow.org](https://mlflow.org/articles/types-of-ai-agent-architectures-2026-developer-guide/); [generalcompute](https://www.generalcompute.com/blog/react-reflexion-and-chain-of-thought-the-inference-cost-of-reasoning-patterns?agent=true)). Anthropic's own data puts the stakes in dollars. Multi-agent systems use about **15x the tokens of chat**, against about 4x for a single agent, and they beat single-agent Opus 4 by 90.2% on breadth-first research ([multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)). A planner/generator/evaluator harness turned a broken 20-minute, $9 solo run into a working 6-hour, $200 build. After the model upgrade to Opus 4.6, the team removed the sprints, kept the planner and reduced the evaluator to a single pass ([Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)). The default should be ReAct with interleaved thinking. Add a spec or planner for long-horizon work, routing to cut cost, and a skeptical external evaluator only where the task exceeds what the model does reliably alone.

For long-running work, the most effective memory turns out to be external state artifacts. Anthropic's long-running harness has an initializer agent write `init.sh`, a progress log and a JSON feature list of more than 200 entries. JSON was chosen because the model is less likely to overwrite it than Markdown. Each later session then completes one feature, tests it and commits ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). Long-term memory products have contested benchmarks: Zep has publicly disputed Mem0's LOCOMO comparison ([Mem0 paper](https://ar5iv.labs.arxiv.org/html/2504.19413)). Buy a memory service only when you need cross-user personalization.

### Sandboxing needs two boundaries and no secrets inside

Isolation strength rises from OS process sandboxes and plain containers, through gVisor, to Firecracker/Kata microVMs. Anthropic's Claude Code sandbox shows why **both filesystem and network isolation** are required. Without network isolation a compromised agent exfiltrates SSH keys, and without filesystem isolation it can escape to reach the network. The sandbox also cut permission prompts by **84%** ([Claude Code sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing)). WASM alone is not enough. 2026 research found Pyodide escapes across seven products, because the host functions the embedder exposes, not linear memory, are the weak point ([Cyera](https://www.cyera.com/research/sandcastles-not-sandboxes-how-one-architectural-flaw-exposed-seven-products)). Hosted options are E2B and Vercel (Firecracker), Modal (gVisor, strongest for GPU) and Daytona (containers, self-hostable). Cold-start and pricing figures for them come from comparison blogs, some of them vendor-affiliated ([Upstash comparison](https://upstash.com/blog/ai-agent-sandbox-providers-compared-2026)). Keep the approval policy separate from the sandbox policy, as Codex does, and route credentials through a proxy or vault so they never enter the sandbox.

### Observability and evals close the loop

The OpenTelemetry GenAI conventions now define `invoke_agent`, `create_agent`, `plan` and `execute_tool` spans, but **every agent and tool span is still at Development status** ([semconv-genai](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md)). Pin a convention version behind your own attribute constants, emit one `invoke_agent` root per run with `execute_tool` children carrying `gen_ai.tool.call.id`, and turn on message-content capture only outside production. Standard OTLP is also the main hedge against vendor churn: ClickHouse acquired Langfuse in 2026 ([ClickHouse](https://clickhouse.com/blog/clickhouse-acquires-langfuse-open-source-llm-observability)). For offline evals, Inspect's `sandbox_agent_bridge()` runs an unmodified harness binary in any language inside a sandbox and proxies its model calls to the eval model. One caution: by default it does not forward generation settings such as temperature ([inspect_ai agent bridge](https://github.com/UKGovernmentBEIS/inspect_ai/blob/main/docs/agent-bridge.qmd)). Anthropic's eval guidance is to start with **20–50 tasks drawn from real failures**, grade outcomes rather than paths, separate capability suites from regression suites, and report pass^k, since 75% per-trial success gives only about 42% pass^3 ([Demystifying evals, mirror](https://github.com/sullivan-street-projects/anthropic-docs-local/blob/master/engineering/demystifying-evals-for-ai-agents.md)). Public benchmarks are a weak guide. OpenAI stopped reporting SWE-bench Verified after finding that **59.4% of 138 audited hard tasks had material flaws** ([OpenAI](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)).

## Build-vs-buy depends on three questions

The decision comes down to three questions. Do you need to control the loop? Must you stay portable across model vendors? Does your agent look like a coding agent?

| Situation | Recommendation |
|---|---|
| Coding or filesystem agent, Claude-only acceptable, small team, fast time-to-value | **Buy:** Claude Agent SDK (or Managed Agents if you don't want to run sandboxes). Wrap it with your own evals and OTel export |
| Multi-vendor models, conversational or workflow agents, team on one cloud | **Adopt a library SDK** matching your stack (OpenAI Agents SDK, ADK, MAF, Strands), plus Temporal/DBOS for durability |
| Many long-lived, idle-heavy, per-user agents | Run your loop or a library SDK **on Cloudflare Durable Objects**, or behind a durable-execution engine |
| Python/TS team that needs durable HITL workflows across many agents now | **Adopt** LangGraph or Mastra (Pydantic AI + Temporal for typed Python), keeping the agent loop linear inside |
| Coding product with its own UI, model-open | **Fork** OpenHands SDK (Python) or OpenCode (TypeScript) and keep up with upstream |
| Differentiated domain agent where custom compaction, routing, cost control or model portability is the product | **Build** layers 2–5 yourself, buy sandboxes and observability, borrow primitives from frameworks |

For teams that build, the evidence supports a staged path. In the first weeks, ship the minimal harness: model client with retries, schema-validated tool registry, linear loop with explicit stop conditions and parallel tool calls, append-only event log, per-tool allow/deny/ask gate, and one sandbox backend. Measure it against mini-swe-agent and a vendor SDK with the model held fixed. Add compaction, subagents, tool search, code-execution mode, long-term memory and a workflow engine only when a specific eval failure justifies each one. Build every addition so that a future ablation can remove it. Teams that buy should still own the eval suite and the telemetry. Those are what let you leave a vendor SDK when the harness effect turns against you.

## Conclusion

The build-vs-buy question has changed in 2026 because the harness is now known to be a capability multiplier whose value decays with each model generation. Buying a vendor harness gets you its tuning but also its decay schedule and its model lock-in. Building your own gets you control but obliges you to keep re-tuning and re-ablating as models change. The durable investment in either case is the part no vendor or framework supplies: an event-log-centred session schema, a task-specific tool interface, and an eval suite that can measure any harness, yours or a vendor's, against a neutral baseline with the model held fixed. A team with those three assets can switch between buying and building at little cost. A team without them stays locked into whatever it chose first.

The open-source ecosystem has also changed what forking means. Because OpenHands, OpenCode, Codex and Goose converged on the same template, the template is effectively a commodity, and forking a whole product rarely beats copying its design. The scarce engineering skill is no longer writing an agent loop. It is designing tools and context policy, and having the measurement discipline to show which parts of the scaffold still earn their tokens.
