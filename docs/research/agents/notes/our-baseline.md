## Which planned components serve a job-search agent (SDK, harness, coding agent plan, platform plan)

### Takeaway
The SDK and harness plans supply almost every generic mechanism a job-search agent needs: tools with schemas, signed resumable approvals, a pre-emptive USD budget, an append-only session log, a deny-first permission pipeline, a sandbox, a credential-injecting egress proxy, an MCP client and a `Scheduler.wake` seam. The coding agent plan adds the cloud shape: loop in a Durable Object, credentials minted outside the sandbox, a deduplicating ingress, one approval point per task. None of them supplies the job-search domain: mail, job-board and contact-API adapters, a tracker data model, or a multi-user/per-tenant layer.

### Inferences
- Component mapping (ours):
  - Inbox reading → T0 read tool behind a `Mailbox` interface (analogue of `Helpdesk`, AD14) + tool-less reader role.
  - Reply/outreach drafting → tool-less drafter role with `outputTool`.
  - Sending → code-initiated `invokeTool()` T3 call with signed pause.
  - Job discovery → T0 reads via MCP or HTTP through HD15.
  - Contact finding (Apollo-type) → T0/T1 read via a `CredentialRoute`.
  - Application submission → T4-class irreversible call, possibly a sandboxed browser.
  - Tracker → product state outside the session log.
  - Scheduling and follow-ups → `Scheduler.wake`.
  - Approvals → `Approvals.resolve()` + `QuorumPolicy` with quorum 1.
- The coding agent's "one approval point per task" (CA6) maps to "one approval per outreach batch or per application plan", not to per-tool prompts.
- The personal single-user scope of CA1 fits a personal job-search agent well. A multi-user job-search product would need the missing platform plan.

### Gaps
- No platform plan exists, so per-tenant secrets, per-tenant budgets and multi-user installs are undesigned (CA1 explicitly defers tenancy).
- No plan budgets non-model spend, such as contact-API credits or paid job-board calls. D9/HD9 cap model USD only.
- No domain adapters: mail provider (Gmail/IMAP/Graph), job boards, contact-enrichment APIs, ATS application forms.

## Approvals and irreversible side effects: what the reversible-actions reports say, and how draft-first, approve-to-send and idempotent send map onto them

### Takeaway
Our research's rule is: give each write an identity before it runs and an outcome after it runs, and treat the gap between the two as `unknown`. Irreversible actions are drafted first and committed on approval. Multi-step plans with an irreversible pivot get one approval over the whole plan, placed before the first step and bound to the state it was computed from. Sending an email and submitting an application are both pivots in this sense, and an email can only be offset by a correction email.

### Cited Findings
- Four outcome kinds for the result body: `not_applied`, `compensated`, `partial`, `unknown`, each with a retry rule; `unknown` = "Reconcile by operation id, or retry with the **same** key", model must not "Retry with a fresh key" — [docs/research/reversible-actions/server-rollback.md#after-a-rollback-tell-the-model-one-of-four-outcomes-in-the-result-body](../../../../docs/research/reversible-actions/server-rollback.md#after-a-rollback-tell-the-model-one-of-four-outcomes-in-the-result-body)
- Result shape proposal includes `not_reversible: ["customer email sent"]`, `retry`, `next_action`; "None of the four wire formats and none of the eight SDKs has a 'rolled back' or 'partially applied' state" — same section
- Idempotency key from the tool call id, scoped `(tenant, session, branch, tool_call_id)` with an argument hash; replay → stored result, changed payload → 422, concurrent → 409. "A regenerated model turn emits a new id for the same action, so only calls persisted before execution deduplicate"; high-stakes tools add a business key — [docs/research/reversible-actions/server-rollback.md#tool-call-ids-make-good-idempotency-keys-only-after-they-are-persisted-and-scoped](../../../../docs/research/reversible-actions/server-rollback.md#tool-call-ids-make-good-idempotency-keys-only-after-they-are-persisted-and-scoped)
- Irreversible side effects (email, payment, outbound HTTP) move after commit or into a transactional outbox; outbox relays can deliver more than once, so consumers must be idempotent — [docs/research/reversible-actions/server-rollback.md#one-transaction-per-tool-call-works-in-all-three-orms-but-each-hides-a-retry-trap](../../../../docs/research/reversible-actions/server-rollback.md#one-transaction-per-tool-call-works-in-all-three-orms-but-each-hides-a-retry-trap)
- "For anything irreversible, the safest agents therefore draft first and commit on approval"; the harness should enforce the `retry` field in code — [docs/research/reversible-actions/server-rollback.md#reversibility-belongs-in-the-tool-contract-and-the-harness-must-enforce-it](../../../../docs/research/reversible-actions/server-rollback.md#reversibility-belongs-in-the-tool-contract-and-the-harness-must-enforce-it)
- Saga vocabulary (from Microsoft): compensable steps, the **pivot** ("the point of no return"), then retryable steps. An email cannot be unsent, and "Its only remedy is a correction email, which is a new external action rather than a compensation" (marked as the report's inference) — [docs/research/reversible-actions/sagas.md#the-refund-is-the-pivot-so-the-email-must-come-after-it](../../../../docs/research/reversible-actions/sagas.md#the-refund-is-the-pivot-so-the-email-must-come-after-it)
- Plan-level approval: every agent SDK surveyed approves one tool call at a time. Approval should come "before the first compensable step, as one decision whose canonical hash covers every step's arguments" (synthesis). A third expiry condition binds the approval to the state the plan was computed from, failing closed with `stale_approval`. A timed-out approval resolves to "nothing executed" — [docs/research/reversible-actions/sagas.md#approval-belongs-before-the-first-compensable-step-and-covers-the-whole-plan](../../../../docs/research/reversible-actions/sagas.md#approval-belongs-before-the-first-compensable-step-and-covers-the-whole-plan)
- Five-way `SagaOutcome`: `completed`, `failed_compensated`, `failed_needs_human`, `pending` (incl. `awaiting_approval`, `pivot_unknown`), `rejected | stale_approval | expired`; async delivery via MCP Tasks `input_required` — [docs/research/reversible-actions/sagas.md#the-agent-needs-five-outcomes-and-only-masstransit-tells-compensated-from-compensation-failed](../../../../docs/research/reversible-actions/sagas.md#the-agent-needs-five-outcomes-and-only-masstransit-tells-compensated-from-compensation-failed)
- The harness, not the workflow engine, owns step order, approval and outcome. Five parts: per-step `compensate` with a persisted log, a declared pivot, one plan approval, idempotency keys on every call, the typed outcome — [docs/research/reversible-actions/sagas.md#the-harness-not-the-engine-owns-order-approval-and-outcome](../../../../docs/research/reversible-actions/sagas.md#the-harness-not-the-engine-owns-order-approval-and-outcome)
- "Rewind changes what the model sees next; it never reverses a write to someone else's system"; after a rewind the model "is more likely to repeat" effects it can no longer see — [docs/research/reversible-actions/rewind-vs-rollback.md#rewind-cannot-reverse-external-writes-and-replay-tends-to-add-them](../../../../docs/research/reversible-actions/rewind-vs-rollback.md#rewind-cannot-reverse-external-writes-and-replay-tends-to-add-them)
- Treatment rule: undo windows for reversible internal writes, approval first for anything that leaves the org, a saga only once a multi-step plan has an irreversible step. For replies: "Approval of exact text, then a short deferred-send window", modelled on Gmail Undo Send (5–30 s); after that, "a correction is a new T3 reply" — [docs/research/reversible-actions/rewind-vs-rollback.md#triage-needs-undo-windows-for-t1-approval-for-anything-that-leaves-the-org-and-a-saga-only-once-money-moves](../../../../docs/research/reversible-actions/rewind-vs-rollback.md#triage-needs-undo-windows-for-t1-approval-for-anything-that-leaves-the-org-and-a-saga-only-once-money-moves)
- Five log changes: effect identity before execution; `outcome: "not_applied" | "applied" | "compensated" | "partial" | "unknown"` in `tool_result.details`. A call entry with no result resumes as `unknown`, not as an aborted error. Compensation is its own call plus a `product_record` link. The model sees a note when a person undoes a write. Rewind carries "effects still live" forward — [docs/research/reversible-actions/rewind-vs-rollback.md#a-rollback-is-a-new-linked-entry-and-the-model-must-read-it](../../../../docs/research/reversible-actions/rewind-vs-rollback.md#a-rollback-is-a-new-linked-entry-and-the-model-must-read-it)
- Missing crash test: "until that test passes, 'exactly once' in our plans means 'once, if nothing crashes'" — [docs/research/reversible-actions/rewind-vs-rollback.md#two-ledgers-and-the-first-fields-to-add](../../../../docs/research/reversible-actions/rewind-vs-rollback.md#two-ledgers-and-the-first-fields-to-add)
- Platforms: "No platform signs its approval records, and no platform reverses or compensates what an agent did to external systems"; none offers idempotency keys on tool calls — [docs/research/deployment/agent-building-platforms.md#approvals-are-common-but-signed-approvals-and-side-effect-undo-exist-nowhere](../../../../docs/research/deployment/agent-building-platforms.md#approvals-are-common-but-signed-approvals-and-side-effect-undo-exist-nowhere)

### Inferences
- **Draft-first.** The drafter writes into an outbox record. Its approval card shows the exact text, the recipient, the provenance and the rule. Mechanically this is a code-initiated T3 `invokeTool()` that pauses with `approval_requested`.
- **Approve-to-send.** The signed resolution resumes the call. A short deferred-send window (rewind-vs-rollback) then gives a cancel affordance before the message leaves.
- **Idempotent send.** Key on `(owner/tenant, session, branch, call_id)` plus a business key such as `outreach:{contactId}:{sequenceStep}` or `apply:{jobPostingId}`. The business key catches regenerated turns. A provider timeout is `unknown` and must be reconciled, by reading the Sent folder or by Message-ID, before any resend.
- **Application submission as a saga.** Steps: write the tracker card "applying" (a semantic lock; compensable), submit the application (the pivot), send a confirmation or a note to the recruiter (retryable, after the pivot), mark the card "applied". The approval covers the form answers, the résumé version, the cover letter and the follow-up text in one hash. It expires if the posting changes or closes, which is the "reread values" check.
- **The forbidden order** carries over from sagas.md. Never email a recruiter "I've applied" before the submission has succeeded.
- **Tracker card edits** are internal and reversible, so they fit the "undo window" treatment rather than approval.

### Gaps
- Whether mail providers or ATS endpoints accept idempotency keys, delayed sends or cancels is unresearched in the repo. The triage equivalent was left to the owner's helpdesk choice at A24.
- No `SagaOutcome` or `outcome` field has been adopted into `ToolResult` or the entry union yet. These remain recommendations: `ToolResult` has only `isError` per [rewind-vs-rollback.md](../../../../docs/research/reversible-actions/rewind-vs-rollback.md#our-sdks-and-plans-rewind-the-conversation-and-roll-back-no-data).
- Plan-level ("plan" kind) signed requests are proposed in sagas.md but not in the SDK's `kind: "approval" | "clarification"`.

## UI and approval UX: what fits a tracker board and an outbox of drafts awaiting approval

### Takeaway
Our UI research says agent UIs are projections of one event log. Approvals should be durable persisted records, not in-memory promises. Background agents and inboxes move the unit of interaction off the chat. A tracker board plus an approval outbox are exactly such projections. Cloudflare Agents' bidirectional `setState` and its persisted approval parts are the closest verified fit. Vercel AI SDK's signed `toolApproval` is the second.

### Cited Findings
- "The transcript, the tool cards, the plan checklist, the approval inbox, the artifact and the PR review are all views over one ordered, append-only stream"; recommendation: model "every approval as a persisted request with once/always/reject/redirect decisions" — [docs/research/agent-ui/agent-ui-research.md#the-session-event-log-should-be-the-ui-contract](../../../../docs/research/agent-ui/agent-ui-research.md#the-session-event-log-should-be-the-ui-contract)
- Inboxes: ambient agents "react to events and surface only to notify, ask or request review"; LangChain's Agent Inbox types interrupts with `allow_accept`, `allow_edit`, `allow_respond`, `allow_ignore` (vendor blog) — [docs/research/agent-ui/agent-ui-research.md#beyond-chat-the-plan-and-the-review-surface-matter-most](../../../../docs/research/agent-ui/agent-ui-research.md#beyond-chat-the-plan-and-the-review-surface-matter-most)
- Approval storage: callback (dies with the process), paused run, message part. "For a web UI that must survive reloads, the part model is the least work". Cloudflare persists the part in SQLite, so "the answer can arrive on a later connection" and the tool runs exactly once **[verified]** — [docs/research/agent-ui/agent-ui-research.md#approvals-wait-in-a-callback-a-paused-run-or-a-message-part](../../../../docs/research/agent-ui/agent-ui-research.md#approvals-wait-in-a-callback-a-paused-run-or-a-message-part)
- Only Cloudflare syncs app state in both directions: `setState()` saves to SQLite and broadcasts, and clients push back subject to `validateStateChange` **[verified]** — [docs/research/agent-ui/agent-ui-research.md#only-cloudflare-syncs-app-state-in-both-directions](../../../../docs/research/agent-ui/agent-ui-research.md#only-cloudflare-syncs-app-state-in-both-directions)
- Undo design: tag every write with actor and turn ID; make the draft real (agent edits stay out of persistence until Keep); revert by inverse ops that keep later human edits; "Irreversible external action — Confirmation, or a deferred commit with an undo toast — None [after it lands]" — [docs/research/agent-ui/undo-agent-edits.md#a-recommended-design-a-tagged-draft-inverse-op-revert-and-gated-side-effects](../../../../docs/research/agent-ui/undo-agent-edits.md#a-recommended-design-a-tagged-draft-inverse-op-revert-and-gated-side-effects)
- Copilot's diff is "usually a *receipt*, not a *proposal*"; a task-level commit needs a staging area plus one merge, and anything escaping it "needs its own confirmation" — [docs/research/agent-ui/copilot-diff-review.md#conclusion-build-a-per-call-gate-and-a-task-level-staging-area-on-purpose](../../../../docs/research/agent-ui/copilot-diff-review.md#conclusion-build-a-per-call-gate-and-a-task-level-staging-area-on-purpose)

### Inferences
- **Outbox.** One persisted approval record per draft. The decisions are approve, edit (which re-enters the pipeline as new input), reject and respond. The draft text shows with its provenance flags. Signed pauses (D5/HD5) back each record. Grouped approvals stay off for sends (`approvalReuse: "none"`).
- **Tracker board.** The board is a projection of product state plus the effects ledger (sent, applied, replied), not of the conversation. Agent edits to cards are source-tagged with a turn ID and get Keep/Undo. Irreversible columns ("Applied", "Emailed") are receipts that cannot be dragged back.
- **Stack fit.** For a Cloudflare-hosted version, Durable Object state with `setState` (board) plus persisted approval parts (outbox) gives both without new UI infrastructure. The SDK and harness plans have no web UI. CA1 lists it as a non-goal for the coding agent.

### Gaps
- No repo design for a board or outbox UI, and none for "batch approve N drafts" UX that stays safe. HD12 grouped approval requires an identical canonical hash, so differing drafts cannot group.
- The research on approval-fatigue thresholds gives no number for daily outreach volume.

## Ingress: how inbound emails and recruiter replies would wake the agent

### Takeaway
Ingress is the one gap the 12-factor review found, and the coding agent's CA7/W5 is the first design to close it: stable request ids, at-least-once deduplication, sender checks, hidden-HTML stripping. Wakes come through `Scheduler.wake` or an approval's HTTP call to `continueRun`. Email ingress itself is undesigned: W5 covers only the CLI and GitHub, and leaves Slack and schedule triggers out of scope.

### Cited Findings
- 12-factor gap: "No document says how a ticket event or an approval reaches `triage()` or `resolve()`". Proposed fix: a webhook receiver or poller that dedups on the event id and allows one run per ticket version. HD2's lock "cannot stop a re-triage after a run completes" — [docs/research/external-designs/twelve-factor-agents.md#five-small-changes-follow-led-by-an-ingress-design](../../../../docs/research/external-designs/twelve-factor-agents.md#five-small-changes-follow-led-by-an-ingress-design)
- "Ingress deduplication and write keys are two halves of one property"; safety "moves to the edges: deduplicated ingress on the way in, and keyed writes with explicit `unknown` outcomes on the way out" — [docs/research/external-designs/twelve-factor-agents.md#conclusion-safety-moves-to-the-edges-once-the-agent-writes-to-a-helpdesk](../../../../docs/research/external-designs/twelve-factor-agents.md#conclusion-safety-moves-to-the-edges-once-the-agent-writes-to-a-helpdesk)
- Storage-and-wake: a portable run needs storage and "a wake: something outside the process must restart the run later, at a deadline, when a lease needs renewing, or when an approval arrives". `Scheduler.wake(at, sessionId)` "promises to call `continueRun`". "An arriving approval needs no fourth seam" — [docs/research/deployment/storage-and-wake.md#two-seams-exist-one-is-new-and-an-approval-becomes-one-more-wake](../../../../docs/research/deployment/storage-and-wake.md#two-seams-exist-one-is-new-and-an-approval-becomes-one-more-wake)
- Three rules: wakes arrive at least once, so every tool call needs an idempotency key. An engine holds one step per `continueRun` and passes entry ids, not transcripts (Workflows caps payloads at 1 MiB). Only a lapsed lease marks a lock stale — [docs/research/deployment/storage-and-wake.md#three-rules-come-with-the-seams](../../../../docs/research/deployment/storage-and-wake.md#three-rules-come-with-the-seams)
- W5 scope: CLI endpoint, GitHub webhook with signature checks, owner-only sender check, hidden-HTML stripping, dedup by request id. Out of scope: "Slack and schedule triggers" — [docs/todos/ready/W5-control-plane-ingress.md](../../../../docs/todos/ready/W5-control-plane-ingress.md)
- Cloudflare Agents scheduling: `this.schedule(when, "method", payload)` with seconds, `Date` or cron; `scheduleEvery`; `listSchedules`; `cancelSchedule`; runs via Durable Object alarms **[verified: 03]** — [docs/reference/cloudflare-agents/guide.md#6-scheduling-runs-callbacks-on-durable-object-alarms](../../../../docs/reference/cloudflare-agents/guide.md#6-scheduling-runs-callbacks-on-durable-object-alarms)

### Inferences
- **Inbound recruiter reply.** A mail webhook or poller, for example Gmail push or Cloudflare Email Routing; none of these is researched in the repo. It becomes a task request keyed by the provider message id or RFC 5322 Message-ID, is deduplicated, and wakes the session tied to that thread or tracker card.
- **Follow-ups.** `Scheduler.wake(at, sessionId)`, a Durable Object alarm, fires on schedule. On wake the agent re-checks the thread state first, because an inbound reply should cancel or alter the follow-up. That re-check is the sagas "reread values" stale check. Because alarms fire at least once, the follow-up send needs its business key.
- **Shared ingress.** CA7's design is meant to be shared ("the deferred triage agent will reuse the same ingress"), so a job-search agent would extend W5 with an email source rather than design a new one.
- **Senders.** The owner-only sender rule cannot apply to inbound mail, which comes from strangers. Every inbound email is untrusted content, not a trusted trigger.

### Gaps
- No email-ingress design and no mail-provider research. Schedule triggers are explicitly out of W5's scope.
- No thread-to-session or thread-to-card correlation design.
- Harness non-goal: generic "wait for an external event" pauses. A "wait for recruiter reply or N days" step would therefore be modelled as a scheduled wake plus an ingress wake, not as a pause.

## The deferred triage agent: which designs (AD1–AD14) transfer to a job-search agent's email handling

### Takeaway
Triage email handling transfers almost one-to-one:
- the tier table as code, with outbound email at T3 and exact-text approval;

### Inferences
- **Direct transfers:**
  - The reader reads each inbound email (recruiter reply, rejection, interview invite) tool-less and emits enums such as `intent: interview_request | rejection | question | spam` plus validated ids.
  - The planner, which never sees raw bodies, picks next steps: update the card, schedule a follow-up, propose a reply.
  - The drafter writes replies with no tools.
  - Code sends through a `Mailbox` interface that has `fake`, `shadow` and real implementations (AD14 pattern).
  - The AI label (AD8) is the user's choice for personal outreach. It is a product decision, not a transfer.
- **Tier sketch for job search** (ours):
  - T0: read inbox, search jobs, fetch a posting, look up a contact.
  - T1: tracker card edits and internal notes.
  - T2: probably empty, or a contact-credit spend above a threshold.
  - T3: reply to a thread, send outreach, send a follow-up.
  - T4: submit an application. It is irreversible and tied to identity: it sends a CV to a third party.
  - T5: change account credentials, mass-send, delete mail.
- **Recipient binding** is where AD14 breaks. For replies, the recipient can be fixed to the thread's sender. For cold outreach, the recipient is an output of an Apollo-type lookup, which is a tool with untrusted output. That needs a new control: the approval card shows the recipient prominently, and a per-recipient or per-domain rate limit applies, the T3 "per requester per hour" analogue. Rule 2's foreign-identifier scan also needs redefining, since "foreign" means "not the intended contact".
- **Quorum.** A personal agent has one approver, the owner. AD3's two-person bands do not apply, but its expiry windows and "approver is not the requester" logic still do, if a multi-user version lets assistants approve.
- **Release gate.** The pass^5 gate transfers as-is. Safety tasks would include injected job postings and injected recruiter emails, for example "forward your CV and SSN to…".

### Gaps
- No triage design covers recipient selection by the agent.
- AD12's "missing fact → templated question" assumes a single requester. Job search has many correspondents.
- The triage eval suite (30 tickets, seven slices) has no job-search equivalent.

## Security: credentials outside the sandbox, BYOK, per-tenant secrets, prompt injection from inbound email

### Takeaway
The plans keep every credential outside the sandbox and the log. The tools that need them are the mail OAuth token, the contact-API key and the model key. HD15's reverse-proxy routes inject them, and CA5 mints them in the control plane. A job-search agent holds the full "lethal trifecta": a private inbox, untrusted emails and postings, and outbound email. Our guide says injection "cannot be prevented, only contained" and that the outbound leg is the one to cut, which here is T3 approval of every send. Per-tenant secrets and BYOK for many users are undesigned, because the platform plan does not exist.

### Cited Findings
- "Prompt injection cannot be prevented, only contained" (OWASP, Anthropic quotes). The lethal trifecta is "private data, untrusted content, and external communication", and "the outbound leg is the one to cut". An outbound channel includes "replies, emails, webhooks, … rendered links or images" — [docs/guides/agent.md#5-safety-is-a-policy-table-and-a-context-split-tier-every-tool-by-worst-case-effect-bind-identity-and-cut-the-outbound-leg](../../../../docs/guides/agent.md#5-safety-is-a-policy-table-and-a-context-split-tier-every-tool-by-worst-case-effect-bind-identity-and-cut-the-outbound-leg)
- Defenses ranked by authority removed: per-context tool allowlist, identity binding, dual LLM or plan-then-execute, CaMeL (77% vs 84% AgentDojo utility), provenance labels, classifiers ("probabilistic reduction only"). An input guardrail regex is "an API, not a defense" — same section
- The GitHub MCP exploit got through approval fatigue ("many users already opt for an 'Always Allow' confirmation policy"); prompts are a budget, so T0/T1 never prompt — same section; [docs/research/external-designs/twelve-factor-agents.md](../../../../docs/research/external-designs/twelve-factor-agents.md) (departures section)
- HD15 credential routes + `scrubSecrets()`; secrets stay out of sandbox and log — [docs/plans/build-harness.md#hd15-the-credential-proxy-injects-on-reverse-proxy-routes-not-by-intercepting-tls](../../../../docs/plans/build-harness.md#hd15-the-credential-proxy-injects-on-reverse-proxy-routes-not-by-intercepting-tls); [docs/plans/build-harness.md#34-permission-approval-and-sandbox-apis](../../../../docs/plans/build-harness.md#34-permission-approval-and-sandbox-apis)
- Repo rule: spawn third-party code with an allowlisted environment, never `...process.env`, because "Inherited credentials once sent a doc example to a real provider" — [AGENTS.md#coding-standards](../../../../AGENTS.md#coding-standards)
- CA1: model key is "one secret held by the host and added at egress, so it never enters the sandbox"; CA10/ADR 0035: the key ring can come from a read-only cloud secret — [docs/plans/build-coding-agent.md#ca1-one-user-the-owners-repositories-and-the-owners-model-key-accepted](../../../../docs/plans/build-coding-agent.md#ca1-one-user-the-owners-repositories-and-the-owners-model-key-accepted); [docs/plans/build-coding-agent.md#ca10-a-read-only-cloud-secret-can-back-the-key-ring-accepted](../../../../docs/plans/build-coding-agent.md#ca10-a-read-only-cloud-secret-can-back-the-key-ring-accepted)
- Platform market: credential isolation has converged on egress injection. Anthropic vaults use an opaque placeholder ("the agent never sees the secret value"), Cloudflare outbound Workers "can hold secrets the sandbox never sees", and Vercel's firewall injects credentials but defaults to `allow-all`. BYOK: AWS is the one vendor whose hosted harness takes other providers' keys, and hosted builders gate or mark up BYOK. Recommended: "BYO key with zero markup and no silent fallback", Cloudflare `byok_only`, keys "in the user's cloud secret store rather than the builder's database" — [docs/research/deployment/agent-building-platforms.md#no-platform-deploys-a-built-agent-to-cloudflare-or-vercel-and-byo-key-usually-carries-a-markup](../../../../docs/research/deployment/agent-building-platforms.md#no-platform-deploys-a-built-agent-to-cloudflare-or-vercel-and-byo-key-usually-carries-a-markup); [docs/research/deployment/agent-building-platforms.md#where-a-new-platform-could-win-what-it-must-match-and-the-first-slice](../../../../docs/research/deployment/agent-building-platforms.md#where-a-new-platform-could-win-what-it-must-match-and-the-first-slice)
- Low-code security record: Langflow has six CISA KEV entries; MCP config has become an RCE path (Flowise CustomMCP CVE-2025-59528, secondary source) — [docs/research/deployment/agent-building-platforms.md](../../../../docs/research/deployment/agent-building-platforms.md) (testing/security section)
- AD2: MCP-sourced tools default to T3; MCP ToolAnnotations from untrusted servers must not drive decisions — [docs/plans/build-agent.md#ad2-the-tier-table-is-code-t5-is-never-registered-and-t4-stays-denied-until-the-owner-sets-the-caps-accepted](../../../../docs/plans/build-agent.md#ad2-the-tier-table-is-code-t5-is-never-registered-and-t4-stays-denied-until-the-owner-sets-the-caps-accepted)
- AD8 PII minimisation: lookups return only what is needed, span ids are hashed, retention must be set before shadow — [docs/plans/build-agent.md#ad8-code-appends-the-ai-label-spans-hash-identifiers-and-later-stages-need-a-retention-period-accepted-with-hd11](../../../../docs/plans/build-agent.md#ad8-code-appends-the-ai-label-spans-hash-identifiers-and-later-stages-need-a-retention-period-accepted-with-hd11)

### Inferences
- **Credential routes.** Mail OAuth tokens, contact-API keys and job-board keys each become a `CredentialRoute` scoped by host and method. Read routes such as `GET` on messages are separate from send routes such as `POST` on `messages/send`, so a sandboxed or compromised tool cannot send mail through a read route. The CA5 pattern of tokens minted per task, narrowed, outside the sandbox applies to OAuth access tokens.
- **Taint.** Inbound emails and fetched job postings are `origin: "user"`-like untrusted blocks. Any session that read them is tainted, so T2+ proposals from it are denied (AD5 Rule 1). The planner should see only reader enums, never raw bodies. That matters doubly here, because recruiter emails and postings are attacker-writable at scale.
- **Contact data is third-party PII.** AD8's minimisation and retention rules apply more strongly here than in triage.

### Gaps
- No repo research on mail-provider OAuth scopes, Gmail send restrictions or contact-API terms of service.
- Per-tenant secrets, per-tenant egress allowlists and multi-user BYOK are absent from the plans (CA1 single user; no platform plan).
- Application submission via browser automation implies a credentialed browser session inside a sandbox. HD15's reverse-proxy routes cover API calls, not cookie-based logins, and the harness defers TLS interception: "(a) waits for a tool that cannot take a base URL".

### Inferences
- **Fastest path.** A job-search agent built before M5–M7 exist would sit on Cloudflare Agents, the `cloudflare-agents` skill and Vercel `toolApproval`. That stack gives scheduled follow-ups (alarms), a board (`setState`) and an outbox (persisted approval parts) today, all verified offline.
- **What our stack adds later.** Signed, key-ringed approvals that fail closed, a deny-first pipeline with taint hooks, the HD15 proxy, and typed outcomes once adopted.
