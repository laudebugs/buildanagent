# The main report survives fourteen more sources, and only its MCP paragraph needs an update

The first research round seeded ten sources it could not fetch, because the network policy then blocked their hosts ([custom-harness notes](notes/custom-harness-architecture.md), scope note). The main report, [agent-sdks-and-harness-design.md](agent-sdks-and-harness-design.md), therefore leaned on search summaries for the topics those seeds covered: agent architecture, MCP and memory. I fetched all ten on 2026-11-19, plus four sources the repo lacked, and read each against the report; the per-source evidence is in the [notes](notes/source-update-2026-11-19.md). The seeds turn out to matter less than expected. Eight of the ten are vendor pages or explainers, the other two are Wikipedia and a single-author survey, and the three MCP explainers describe a protocol older than the one we target. The useful material came from the primary sources those pages pointed to. In this report I show that none of the fourteen sources reverses a conclusion of the main report, that the MCP 2026-07-28 changelog adds four requirements our MCP client todos lack, and that two primary studies found through vendor pages back the eval plan we already have.

## The blocked seeds were explainers, and the three on MCP are out of date

None of the ten seeds is a spec, an official SDK doc or a measured study. IBM, Google Cloud and Phil Schmid each explain MCP. IBM and Google Cloud present HTTP+SSE as the remote transport, and Schmid presents it too, noting only that it "will be replaced with a more flexible Streamable HTTP transport" ([IBM](https://www.ibm.com/think/topics/model-context-protocol); [Google Cloud](https://cloud.google.com/discover/what-is-model-context-protocol); [philschmid](https://www.philschmid.de/mcp-introduction)). The spec has deprecated HTTP+SSE since revision 2025-03-26 ([MCP 2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog), SEP-2596). IBM also calls the MCP client a "session manager," and Schmid starts every connection with a capability handshake, but revision 2026-07-28 removed both protocol-level sessions and the `initialize` handshake (changelog, SEP-2567 and SEP-2575). IBM modified its page on 2026-11-05 without changing either claim.

The architecture seeds agree with the report without adding evidence. IBM, Parallel and Atlan all describe a perceive-reason-act loop, recommend a single agent first, and call for iteration limits and human checkpoints ([IBM architecture](https://www.ibm.com/think/topics/agentic-architecture); [Parallel](https://parallel.ai/articles/what-is-an-ai-agent); [Atlan](https://atlan.com/know/ai-agent/ai-agent-architecture-explained/)). Those points already sit in the report's [planning section](agent-sdks-and-harness-design.md#planning-should-start-as-react-and-earn-every-extra-agent) and in layer 2 of its [reference architecture](agent-sdks-and-harness-design.md#a-reference-architecture-in-eight-swappable-layers). The arXiv survey 2503.12687 makes its evaluation argument by relaying Kapoor et al. (2024), so I cite Kapoor directly below ([arXiv 2503.12687v1](https://arxiv.org/html/2503.12687v1), §4.1). The freeCodeCamp book warns readers that its case-study numbers are "illustrative composites … not … audited claims," which rules them out as evidence ([freeCodeCamp](https://www.freecodecamp.org/news/ai-agent-engineers-guide-60-patterns-for-building-autonomous-systems-book/)). Fetching the seeds thus closes a gap in the record but moves no conclusion.

## MCP 2026-07-28 deprecated three features and replaced server-initiated requests

Wikipedia led to the finding that changes our harness plans. Its article says the 2026-07-28 revision "deprecated several features that had seen limited use, including sampling … and roots," and that deprecated features "remain functional for a minimum of twelve months" ([Wikipedia](https://en.wikipedia.org/wiki/Model_Context_Protocol), revision 1386480394). The main report's MCP paragraph lists the removed handshake and sessions, `server/discover`, the routing headers and the Tasks extension, but none of the deprecations ([tools and context](agent-sdks-and-harness-design.md#tools-and-context-deserve-more-effort-than-the-prompt)). The changelog confirms the Wikipedia summary and goes further, with four changes that bear on our MCP client:

1. **Deprecations.** Roots, Sampling and Logging are deprecated (SEP-2577). The spec suggests tool parameters instead of Roots, direct provider API calls instead of Sampling, and stderr or OpenTelemetry instead of Logging. A new lifecycle policy sets "a minimum twelve-month deprecation window" (SEP-2596).
2. **Multi round-trip requests.** Servers no longer send `roots/list`, `sampling/createMessage` or `elicitation/create` requests to the client. A server that needs more input returns `resultType: "input_required"` with `inputRequests`, and the client retries the original request with `inputResponses`. Clients must treat results from older servers that omit `resultType` as `"complete"` (SEP-2322).
3. **Cacheable lists.** List results must carry `ttlMs` and `cacheScope` (SEP-2549), and servers should return `tools/list` "in a deterministic order to enable client-side caching and improve LLM prompt cache hit rates."
4. **Trace context.** The spec documents `traceparent`, `tracestate` and `baggage` as `_meta` keys (SEP-414), so a client can carry its trace into a server's spans.

Our MCP client todos predate this reading. [N24](../todos/ready/N24-mcp-stdio.md) probes `server/discover` and falls back to `initialize`, and [N25](../todos/ready/N25-mcp-http-background.md) already re-issues a request after a dropped stream. Neither mentions `input_required`, the deprecated features, `ttlMs` or trace context. The `input_required` result matters most, because it arrives where our loop expects a finished tool result. When a server asks for user input that way, the request should go to the user through the approval and steering path we already plan; the model should never answer it. The 2026-07-28 spec also confirms what the [connectors report](connectors/agent-connectors.md) already covers: the deprecation of dynamic client registration and the ban on token passthrough ([security best practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)).

## Two primary studies found through vendor pages back our eval plan

Atlan's marketing page cites Pan et al., "Measuring Agents in Production" (MAP), an ICML 2026 oral paper built on 20 case studies and a survey of 86 practitioners across 26 domains ([arXiv 2512.04123](https://arxiv.org/abs/2512.04123), v4, abstract). MAP found that "68% execute at most 10 steps before human intervention, 70% rely on prompting off-the-shelf models instead of weight tuning, and 74% depend primarily on human evaluation." Reliability "remains the top development challenge, which practitioners currently address through systems-level design." Because MAP draws on deployed systems rather than benchmarks, it gives independent support to the report's claims that the harness matters and that the loop needs explicit stop conditions and human gates ([harness choice](agent-sdks-and-harness-design.md#harness-choice-can-swing-scores-widely-or-mostly-change-cost); layer 2).

The same page links a second study, CLEAR, a single-author paper with no listed venue that tested six agents on 300 enterprise tasks ([arXiv 2511.14136](https://arxiv.org/abs/2511.14136), v1). It reports that "agent performance drops from 60% (single run) to 25% (8-run consistency)," and that optimizing for accuracy alone "yields agents 4.4-10.8x more expensive than cost-aware alternatives with comparable performance." Kapoor et al. made the same argument in July 2024: "a narrow focus on accuracy … As a result, SOTA agents are needlessly complex and costly" ([arXiv 2407.01502](https://arxiv.org/abs/2407.01502), abstract). Together the three back the report's call for pass^k and cost on every change ([observability and evals](agent-sdks-and-harness-design.md#observability-and-evals-close-the-loop)). Our seed suite already reports pass^5, cost, tokens and steps per task ([N38](../todos/ready/N38-seed-suite-baseline.md)), so the eval plan needs no change.

## Benchmark figures drift between paper versions

Atlan cites Carnegie Mellon results twice on one page, once as 24% of tasks completed and once as "30 to 35%," and its source list names only TheAgentCompany. The paper's v1 abstract (18 December 2024) says "24% of the tasks," and its v3 abstract (10 September 2025) says "30% of tasks" ([arXiv 2412.14161v1](https://arxiv.org/abs/2412.14161v1); [current](https://arxiv.org/abs/2412.14161)). The drift repeats what R1 found in our own report, where Claw-SWE-Bench and Harness-Bench changed their headline figures between versions ([fact-check, R1](fact-check-2026-11-18.md#re-verification-against-primary-sources-r1)). Three papers in two rounds is a pattern, so the research rules should require an arXiv version on every figure, and the plan table below proposes that rule.

## The vendor framework surveys confirm the tier table, and the other pages confirm single facts

The two new framework pages agree with the main report's [tier table](agent-sdks-and-harness-design.md#vendor-sdks-split-into-three-tiers-of-loop-ownership). Langfuse names the same provider SDKs for the same clouds and says a single-model tool loop "can be written in under a hundred lines with a provider SDK," with frameworks earning their place for "durable state, retries, multi-agent delegation, human-in-the-loop steps, and consistent tracing" ([Langfuse](https://langfuse.com/blog/2025-03-19-ai-agent-comparison)). Mastra's guide says "Set an iteration limit on every loop" and scopes human gates "to specific high-risk tool calls rather than entire agent outputs" ([Mastra](https://mastra.ai/articles/ai-agent-architecture)). Both are vendors describing their own market, and the two disagree on simple facts: Langfuse credits Mastra with "more than 40 providers," while Mastra claims "90+." Langfuse's AutoGen status ("maintenance mode," checked in July 2026) is also older than the report's, which R1 checked against the AutoGen README: archived as of November 2026.

The remaining pages each confirm or refute one fact. IBM's claim that CrewAI "operates on top of LangChain" is wrong, because the CrewAI README calls it "a standalone Python framework with its own primitives" ([CrewAI README](https://github.com/crewAIInc/crewAI/blob/main/README.md)). Mem0's memory guide pitches a memory layer for personalization, which matches the report's rule to buy memory only for cross-user personalization ([Mem0](https://mem0.ai/library/agent-memory/what-is-ai-agent-memory)). SWE-bench's own docs confirm that SWE-bench Verified holds "500 engineer-confirmed solvable problems" ([SWE-bench docs](https://www.swebench.com/SWE-bench/)). Anthropic's launch post fixes MCP's origin in November 2024 ([Anthropic](https://www.anthropic.com/news/model-context-protocol)).

## What stays unverified

Several claims in the fourteen pages were not checked against a primary source, and none of them changes a conclusion. The open items are the Gartner and Menlo Ventures figures, the details of the two MCP CVEs, the NSA quote, the Replit database incident, and Langfuse's description of the AI SDK's `HarnessAgent` and `WorkflowAgent`. The SWE-bench docs say nothing about OpenAI's audit of SWE-bench Verified, so the main report's figure of 59.4% of 138 tasks stays ⚠️. The [fact-check log](fact-check-source-update-2026-11-19.md) records every claim in this report.

## Conclusion

Fetching the ten blocked seeds closes the gap the first round recorded, and it confirms that the gap hid little: the seeds were explainers, several of them stale on MCP. The main report's conclusions stand. Own the loop, keep an append-only session log, and measure every harness change with pass^k and cost against a fixed model. The one substantive update comes from the MCP 2026-07-28 changelog, which deprecates Roots, Sampling and Logging and moves server-initiated requests into `input_required` results. That changelog item gives N24 and N25 their concrete work. The owner has three decisions to make: whether a server's input request may pause a turn, whether to edit the frozen report, and whether to require arXiv versions on every figure. Once they are made, the MCP client todos can absorb the 2026-07-28 changes before any code is written.
