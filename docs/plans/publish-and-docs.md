# Publish the SDK to npm and its docs to two Cloudflare sites

- **Status:** Ready (2026-11-19). That day the owner decided to publish under `@buildanagent`, to ship 0.1.0 once a model call works, to build the docs on Astro Starlight and to serve two sites on Cloudflare. They accepted every decision below the same day. L1, L2, L3, L4a and L4b are done; Round L's other todos are ready. On 2026-11-19 the owner also published deprecated placeholders of both packages, so npm already holds them, and then chose to release alphas automatically, starting at 0.1.0-alpha.0, each through an auto-merged "Version packages" pull request ([PB1](#pb1-ship-010-once-a-model-call-works-accepted), [PB2](#pb2-changesets-in-one-fixed-group-published-only-from-ci-accepted)). On 2026-11-22 the owner also decided to publish the protocol, harness and CLI, and `@buildanagent/agent-safety` beside them, together once N30 lands ([PB4](#pb4-publish-the-protocol-harness-and-cli-packages-after-the-gateway-and-sdk-accepted)).

The owner reserved the `@buildanagent` scope on npm and said, on 2026-11-19, "We can start publishing as soon as we're ready to". The same day they asked for library docs ("We also need to build documentation for the libraries") and named where they live ("We'll use cloudflare to deploy docs and the website - buildanagent.fyi"). This plan turns those decisions into Round L, twelve todos in three strands. One strand (L1 to L4b) takes `@buildanagent/gateway` and `@buildanagent/sdk` from private source packages to a 0.1.0 release with provenance; the second (L5 to L8) stands up the website at `buildanagent.fyi` and the docs at `docs.buildanagent.fyi`; the third (L9 to L11) extends the release to four more packages. The plan adapts Lamina PDF's working setup (`laudebugs/laminapdf` at `7b4b37b`): built `dist/` packages, a fixed Changesets group, npm trusted publishing, and Starlight docs on Cloudflare Workers static assets.

## 1. Goal and non-goals

**Goal.** By the end of Round L, a user can `pnpm add @buildanagent/sdk@alpha`, make a model call through the Anthropic adapter, and read how in the docs at `docs.buildanagent.fyi`, whose API reference comes from the packages' TSDoc.

**Non-goals.**
- Publishing the evals or agent packages. The protocol, harness, CLI and agent-safety joined the plan on 2026-11-22 ([PB4](#pb4-publish-the-protocol-harness-and-cli-packages-after-the-gateway-and-sdk-accepted)); `@buildanagent/evals` stays private.
- A blog, a changelog site or search beyond what Starlight ships.
- Versioned docs for more than the latest release and `main`.

### PB2. Changesets in one fixed group, published only from CI (accepted)

**Accepted by the owner on 2026-11-19**, with PB1: "Changesets wait until we publish. We can start publishing as soon as we're ready to".

- **Versioning.** Changesets (`@changesets/cli` 3.0.3, the newest release at least a week old as of November 2026, [npm](https://www.npmjs.com/package/@changesets/cli)) records each change as a `.changeset/*.md` file. `@buildanagent/gateway` and `@buildanagent/sdk` form one `fixed` group, as Lamina's packages do, because the SDK depends on the gateway's types and a user should never mix versions. `access` is `public`. `ignore` lists the `verify/*` harnesses, and `privatePackages` is `{ "version": false, "tag": false }` ([Changesets config schema](https://github.com/changesets/changesets/blob/main/packages/config/schema.json)), so nothing moved the packages off 0.0.0 while they were private, and nothing versions the private apps the plan adds later. L4a dropped `private` on 2026-11-19, so from then on a changeset does move them, and the release plan's 0.0.0 rule keeps the merge itself from publishing ([CI plan §3f](ci.md#3f-releases-through-npm-trusted-publishing-added-2026-11-19)).
- **Changesets waited until we published.** The owner said "Changesets wait until we publish", so L2 added the config, the tooling and the CI gate that requires a changeset, with the gate switched off. L4b switched it on with the first release's changesets. The gate passes a version bump that `pnpm changeset version` made, which `pnpm changeset status` alone would fail ([CI plan §3e](ci.md#3e-a-changeset-check-on-since-l4b-added-2026-11-19)).
- **Changelog.** `changeset version` writes each package's `CHANGELOG.md`. A change that breaks the API must be a `minor` bump under 0.x and must say "Breaking Changes" in its changeset, which D8 requires.
- **Trusted publishing.** A release job publishes with npm trusted publishing: npm exchanges the workflow's OIDC token for a short-lived publish token, so no npm token is stored. npm requires a GitHub-hosted runner, `id-token: write`, npm CLI 11.5.1 or later and Node 22.14.0 or later, and it adds provenance attestations by default ([npm docs](https://docs.npmjs.com/trusted-publishers)). Our `.nvmrc` resolves to the newest Node 22, which ships npm 10, so the release job installs npm 11.5.1 or later before it publishes.
- **The first publish has already run.** npm's `trust` docs list a prerequisite: "The package you're configuring must already exist on the npm registry" ([npm `trust` docs](https://docs.npmjs.com/cli/v11/commands/npm-trust), read 2026-11-19). A new trusted publisher also expires unless it publishes within 2 days ([npm docs](https://docs.npmjs.com/trusted-publishers)). So, on 2026-11-19, the owner published placeholders of both packages from their own machine instead of through a CI `bootstrap` job. As of November 2026, npm shows the same state for each package:
  - Two versions, `0.0.0-bootstrap.0` and `0.0.0-stage`, both deprecated with the message "Placeholder only; install 0.1.0 or later."
  - The `bootstrap` and `latest` dist-tags both point at `0.0.0-bootstrap.0`, so the first publish did set `latest`.
  - No provenance, because the placeholders didn't come from a workflow.

  The bootstrap path in [ADR 0047](../decisions/0047-first-release-and-trusted-publishing.md) therefore needs no CI job and no `NPM_BOOTSTRAP_TOKEN`. On 2026-11-19 the owner added each trusted publisher, and `release.yml` publishes 0.1.0-alpha.0 through trusted publishing when L4b merges, which must happen within the 2 days. The alpha goes under the `alpha` dist-tag, so `latest` stays on the placeholder until the first stable release. The publish job never sees a token.
- **The release flow: each merged Version packages pull request publishes an alpha.** The owner decided on 2026-11-19: "let's make the publishes run on every change to the package". L4b's first answer pushed a version commit straight to `main`; asked whether the version step should instead be "a pr that will be autocompleted", the owner answered "yes" the same day. So a push to `main` that brings a changeset makes `release.yml` run `pnpm changeset version`, which moves both packages to the next prerelease, such as 0.1.0-alpha.1. The workflow checks that the result changes only versions, makes it a commit on the `changeset-release/main` branch through GitHub's API so that GitHub signs it, as `main`'s ruleset requires, opens or updates a "Version packages" pull request and turns on GitHub's auto-merge. Changesets merged while that pull request is open join it. Once the required `checks` status passes, GitHub squash-merges it, and the push to `main` publishes both packages, gateway first, under the `alpha` dist-tag. Last, the workflow creates one `v<version>` tag and GitHub prerelease for both packages. The owner removed the `release` environment's approval rule on 2026-11-19, so the whole flow runs unattended. L4b's merge published 0.1.0-alpha.0 without a version commit. L3 built the workflow. Its publish job uploads tarballs that an earlier read-only job packed, reads no npm token and fails closed when trusted publishing isn't configured. A `workflow_dispatch` is a dry run. The details are in [CI plan §3f](ci.md#3f-releases-through-npm-trusted-publishing-added-2026-11-19).

### PB3. Built `dist/` packages, with a `source` condition for the workspace (accepted)

**Accepted by the owner on 2026-11-19.**

Before L1, each package exported its `src/*.ts` files, because the packages were private and Vitest and tsx read TypeScript directly ([typescript.md](../guidelines/typescript.md)). A published package can't do that: npm users need JavaScript and `.d.ts` files. PB3 adopts Lamina's rule: emit with `tsc` into `dist/`, with `module` and `moduleResolution` `NodeNext`, `.js` specifiers in relative imports, and published `exports` whose conditions list `types` first. Each published `package.json` sets `files: ["dist"]`, `sideEffects: false` and `engines.node`. L1 corrected two of these details and added three build rules, all recorded in [ADR 0051](../decisions/0051-dist-build-corrections-from-l1.md). First, `files` lists the three licence files beside `dist`. Second, the gateway's `sideEffects` lists `./src/testing/setup.ts` and `./dist/testing/setup.js` instead of `false`, because importing the setup installs the offline guards, and a bundler may drop a side-effect import from a package marked `false`. As for the build, each one empties `dist/` first, emits source maps with their sources inlined but no declaration maps, and runs from `prepack`, so every pack ships a fresh `dist/`.

The workspace keeps working without a build step through one extra export condition, `source`, which points at `src/*.ts`. TypeScript and Node pick the first condition that matches, in the order the object lists them, so in the workspace's `exports` `source` comes before `types` and `default`; "types first" applies to the published `exports`. Vitest's `ssr.resolve.conditions` and TypeScript's `customConditions` name `source`, so tests and type-checks in the repo read source while npm users get `dist/`. Vitest 5.1.0 runs on Vite 8, and Vite 8 replaces its default conditions with the list you give instead of adding to it. Because Node tests resolve through `ssr.resolve.conditions`, each Vitest config lists `source` before Vite's server defaults (`module`, `node`, `development|production`) ([Vite docs](https://vite.dev/config/ssr-options#ssr-resolve-conditions)). `@buildanagent/gateway/testing/setup`, which every package's Vitest config loads, resolves through the same list once a file imports it: Vitest 5.1.0 resolves a bare `setupFiles` entry when it loads the config, with Node's default conditions, so each config lists a local `test/setup.ts` that imports it (found in L1). PB3 replaces the TypeScript guideline's line that our private packages export their `src/` TypeScript until L1.

Two rules keep the `source` condition inside the repo:
- **It never ships.** Each package's `publishConfig.exports` lists only `types` and `default`, in that order, and pnpm replaces `exports` with it when it packs ([pnpm docs](https://pnpm.io/package_json#publishconfig)). A user whose own tooling sets a `source` condition would otherwise resolve to `src/` files that the tarball doesn't contain.
- **The build ignores it.** Each `tsconfig.build.json` sets `customConditions: []`, and `pnpm -r build` builds in dependency order, so the SDK compiles against the gateway's `dist/*.d.ts`, not its sources.

### DS3. Workers static assets, and a Preview per pull request (accepted)

**Accepted by the owner on 2026-11-19**, with the build and deploy split below.

Cloudflare's Astro guide deploys a static Astro site to Workers with static assets: a `wrangler.toml` whose `[assets]` directory is `./dist`, and no `main`, because no Worker code runs ([Cloudflare docs](https://developers.cloudflare.com/workers/framework-guides/web-apps/astro/)). Each app's `wrangler.toml` names its custom domain with `custom_domain = true`, sets `not_found_handling = "404-page"`, turns off `workers_dev`, as Lamina's docs config does, and sets `preview_urls = true`. That last setting matters: Previews are served on `workers.dev`, and a new Worker's `preview_urls` starts from its `workers_dev` value, so without it the previews would be off ([Wrangler configuration](https://developers.cloudflare.com/workers/wrangler/configuration/)). A `workers.dev` Preview URL also sends `X-Robots-Tag: noindex` ([Previews](https://developers.cloudflare.com/workers/previews/)). Wrangler is pinned to 4.160.1, the newest release at least a week old as of November 2026 ([npm](https://www.npmjs.com/package/wrangler)).

For pull requests, Cloudflare now recommends Previews (`wrangler preview`, Wrangler 4.135.0 or later) over Version URLs, which share production resources ([Cloudflare docs](https://developers.cloudflare.com/workers/previews/compare-workflows/)). Each site gets three workflows, so no pull request can edit the job that holds the Cloudflare token:
- **Build** (`docs-build.yml`, `site-build.yml`), on `pull_request` and pushes to `main`: builds the site with no secrets and uploads `dist/` as an artifact. Nothing else in the artifact is trusted.
- **Deploy** (`docs-deploy.yml`, `site-deploy.yml`), on `workflow_run` after its build workflow finishes: GitHub always runs this workflow's definition from `main`. It downloads the artifact, takes `wrangler.toml` from `main`, and never checks out or runs the pull request's code. It deploys to production only when the triggering run was a `push` (`github.event.workflow_run.event == 'push'`) to `main` from this repository (`github.event.workflow_run.head_repository.full_name == github.repository`). The repository check matters because a fork's branch can also be named `main`. Every other run from this repository's own pull requests gets `wrangler preview`. For a preview, the deploy job finds the pull request through the API from the run's `head_sha` (`GET /repos/{repo}/commits/{sha}/pulls`), never from anything the build uploaded.
- **Pr-closed** (`docs-pr-closed.yml`, `site-pr-closed.yml`), on `pull_request: [closed]`: holds no secret, checks nothing out and runs no action. Its run only starts the deploy workflow through `workflow_run`, so the job that deletes the preview (`wrangler preview delete`) always runs from `main`'s file. It copies the book's `book-pr-closed.yml`.

Pushes to `main` deploy the website. A fork's pull request builds and passes its checks but gets no preview (changed 2026-11-22, pending the owner's confirmation). DS3 first said forks get previews too, because the secrets live only in the deploy workflow. An Opus security review of the first drafts then showed the flaw: a fork's build runs the fork's own copy of the build workflow, so its artifact can hold any HTML or script, and a preview would serve it publicly under the owner's Cloudflare account. The book made the same choice on 2026-11-19 ([build-book BK15, "Changed after T9"](build-book.md#bk15-an-assets-only-worker-on-a-custom-domain-behind-a-guard-and-a-switch-proposed)). A maintainer can push a fork's change to a branch of this repository to preview it, and a fork's pull request from a branch named `main` gets no production deploy either.

**What L8 settled (2026-11-22).** Both sites use one GitHub environment, `cloudflare`, where the book uses two, because Cloudflare's roles page lists no role for previews alone, so a preview token could, as the book reasons, deploy production anyway ([Workers roles](https://developers.cloudflare.com/workers/authorization/workers/)). Previews go to `workers.dev` for pull requests from this repository's branches only, with `X-Robots-Tag: noindex`, and each is deleted when its pull request closes. Production deploys sit behind two repository variables, `SITE_DEPLOY_ENABLED` and `DOCS_DEPLOY_ENABLED`; previews do not. A guard, `scripts/ci/site-guard-deploy.mjs`, refuses a deploy unless the app's `wrangler.toml` matches its expected lines exactly. The six workflows (two builds, two deploys and two pr-closed files) wait for the owner to commit them ([CI plan §3g](ci.md#3g-both-sites-deploy-to-cloudflare-with-a-preview-per-pull-request-l8-added-2026-11-22)).

### DS4. The docs follow `main` until 0.1.0, then releases (accepted)

**Accepted by the owner on 2026-11-19:** "main until 0.1.0, then releases". Until 0.1.0 ships, pushes to `main` deploy `docs.buildanagent.fyi`. From 0.1.0 on, each release tag deploys `docs.buildanagent.fyi`, so the docs match the published packages, and `main` deploys `next.docs.buildanagent.fyi`, marked unreleased and `noindex`.

The switch needs no manual step. A tag that `release.yml` pushes with `GITHUB_TOKEN` starts no other workflow, but a `workflow_dispatch` does: GitHub's docs say "`workflow_dispatch` and `repository_dispatch` events always create workflow runs" ([GitHub docs](https://docs.github.com/en/actions/concepts/security/github_token)). So after it tags a release, `release.yml` runs `gh workflow run docs-deploy.yml -f tag=<tag>` with `actions: write`, and `docs-deploy.yml`'s `workflow_dispatch` path builds the docs at that tag and deploys production. Its `workflow_run` path for pushes to `main` deploys production while no release tag exists, and `next.docs.buildanagent.fyi` once one does.

The alphas don't count as releases here (L4b, 2026-11-19). A prerelease's tag, such as `v0.1.0-alpha.0`, starts no production docs deploy: `release.yml`'s `docs` job skips prereleases. L8 treats only a stable tag, `v<x.y.z>`, as "a release tag exists", so `main` keeps deploying `docs.buildanagent.fyi` until the first stable release. `docs-deploy.yml`'s `tag` input must match that pattern, exist and be reachable from `main`, and the release build checks out the tag's commit SHA, not its name. L8 adds no visible "unreleased" banner to `next.docs.buildanagent.fyi`, which needs a change to the docs app, so that site is only marked `noindex`.

#### The theme reuse design

`docs/design/book-tokens.json` is the one source of the book's colours: a cream and a brown page, each with a text and an accent colour, and a light and a dark code panel. It also holds the fonts, Instrument Serif for display, Literata for body and Manual Code (Google Sans Code renamed), all under the OFL. The fluid sizes are there too. The book writes them as CSS custom properties, and its dark values sit under `prefers-color-scheme` and `[data-theme="dark"]`. Starlight's theme script sets the same `data-theme` attribute on `<html>`, so those selectors work in the docs unchanged. The design has six parts:

1. **Share code by package name.** `apps/manual/package.json` gains `exports` for its token, contrast and font-subset modules, its `svgkit` and a `figures.css` split out of `components.css`, and the docs app takes `@buildanagent/manual` as a `workspace:*` devDependency. The maintainability checks cover only `packages/`, so they allow it. A private `packages/design` waits for a third consumer, the website.
2. **Generate the tokens.** `tokensCss()` takes the header comment and the font base path as options, `apps/docs/scripts/generate-tokens.ts` writes `src/styles/tokens.css`, and a test fails when that file is stale.
3. **Map the tokens in one file.** `src/styles/starlight.css` holds only `var()` references, and a port of the book's style test rejects a hex value. It maps Starlight's `--sl-color-*` roles to the tokens, sets headings in the display font at weight 400 (Instrument Serif has no bold) and sets `--sl-content-width` to the book's measure. It sits in `customCss`, unlayered, so it beats Starlight's `@layer starlight.base`.
4. **Colour the code.** Starlight's `expressiveCode.themes` take two themes generated from the light and dark code panels, and its style overrides read the panel tokens.
5. **Copy the fonts.** The generator copies the six WOFF2 subsets with their `OFL.txt` and `TRADEMARKS.md` into `apps/docs/public/fonts/`, a test fails on a byte difference, and a `Head` override preloads Literata roman and Instrument Serif regular (168 KB).
6. **Test the extra contrast.** Starlight's roles create pairs the book never measured, such as the current sidebar item. `src/design/pairs.ts` names them and `test/contrast.test.ts` recomputes each from the shipped `tokens.css`. They stay out of `book-tokens.json`, whose test asserts exactly 38 pairs.

The docs keep Starlight's `ThemeSelect` (Auto, Light, Dark), restyled. A reader's choice cannot carry between the book and the docs, which are different origins.

#### The versioning design

## 5. Risks

1. **A trusted publisher added too early expires.** It must publish within 2 days, so the owner added both publishers on L4b's release day, 2026-11-19, and L4b must merge by 2026-11-21 or the owner re-adds them. Until the first stable release, `latest` points at the deprecated placeholder, so `pnpm add @buildanagent/sdk` without `@alpha` installs `0.0.0-bootstrap.0` and marks it deprecated ([fact-check row 74](reviews/fact-check-publish-and-docs.md); [PB2](#pb2-changesets-in-one-fixed-group-published-only-from-ci-accepted)).
2. **The `source` condition could leak.** A published `package.json` that kept the `source` condition would point users' tooling at `src/` files the tarball doesn't hold. `publishConfig.exports` strips it, and an L1 test packs each package and resolves every entry with a `source` condition set.
3. **TypeDoc lags TypeScript.** Pinning TypeScript 6.0.3 for TypeDoc means the reference could disagree with how TypeScript 7 reads a type. L6's check builds the reference and type-checks the packages, so a mismatch surfaces in CI.
4. **A fixed group bumps every package for any change.** With six members, a change to one bumps all six, so a package with no change of its own, or an unstable one, still takes a version and a changelog entry. The cost is accepted for one quotable version ([PB4](#pb4-publish-the-protocol-harness-and-cli-packages-after-the-gateway-and-sdk-accepted)); if it grows, the owner can split the group in a new ADR.
5. **A dependency left off npm would break the harness's install.** The harness depends on `@buildanagent/agent-safety`, which the owner decided to publish. L10's pack test fails any package that will publish and depends on a workspace package outside the six.
6. **A trusted publisher added too early expires.** The same 2-day rule as risk 1, now for four packages that wait on N30. The owner adds them last (§3, item 4).
7. **The pins may move.** Astro, Starlight and Wrangler release weekly. Each todo re-pins to the newest release at least a week old when it starts.

## 6. Conclusion

Round L puts our packages on npm with provenance and our docs on `docs.buildanagent.fyi`, using the setup Lamina PDF already runs. L4b's merge ships 0.1.0-alpha.0, and every later package change ships the next alpha until the owner calls the stable 0.1.0. L5 to L8 then bring the docs and the website, once the owner has set up Cloudflare as §3 lists.
