# Plan: run the local checks on every push, and the full verify on a schedule (Round X)

- **Status:** Done (X1 and X2's first pass, 2026-11-18)
- **Date:** 2026-11-18
- **Asked for by:** the project owner (2026-11-18), who chose to add CI after the SDK rounds
- **Builds on:** the pnpm workspace and the [coding standards](../../AGENTS.md#coding-standards)

## 1. Goal

GitHub Actions runs the same checks we run locally, so a broken push shows up within two minutes, and a scheduled run catches upstream docs drifting from the pinned packages.

## 2. Measured cost (2026-11-18)

Locally on 4 CPUs with a warm install, `pnpm check` takes under 1 second, `pnpm typecheck` 3 seconds and `pnpm test` 9 seconds. The full `verify` for both harnesses takes about 50 seconds. On GitHub's 2-CPU private-repo runners, a cold `pnpm install` of the 1.1 GB store should take 30–90 seconds, or 15–25 seconds with the pnpm store cached. One run should therefore take 1–2 minutes, well inside the free plan's 2,000 minutes a month.

## 3. The workflows

- **`ci.yml` on every push and pull request:** checkout, Node 22, pnpm through corepack, a cached `pnpm install`, then `pnpm check`, `pnpm typecheck` and `pnpm test`. No secrets.
- **A catalog warning in `ci.yml` (added 2026-11-19, B22):** `scripts/ci/catalog-staleness.mjs check` prints a `::warning::` annotation for each shipped price-catalog entry copied more than 90 days ago and for each entry whose optional `retires` date is 90 days away or less, or past. It never fails the run. The date is a copy with its own `asOf`, so the warning asks for a refresh from the provider's deprecations page.
- **The undocumented-export check runs inside `pnpm test` (added 2026-11-22, L6):** the docs app's tests run TypeDoc over each package's `exports` and fail on an export without TSDoc, and one builds the docs and requires a reference page for every export, so `ci.yml` needs no step of its own. `pnpm check:api-docs` runs the same check alone. The docs build that generates the reference gets its own workflow in L8.
- **`book-build.yml` on every push to `main` and every pull request (added 2026-11-19, T8):** it copies the setup of `ci.yml`'s `checks` job, except the user-namespace step that only the Copilot harness needs, and reads no secrets. It then runs `check:book`, `book:switch-report`, the figure staleness test and the book's build, and uploads `apps/manual/dist/` as the `book-dist` artifact, kept 7 days, for T9's deploy ([book plan BK14](build-book.md#bk14-one-ci-job-builds-the-book-and-runs-every-check-proposed)). It has no path filter, because the book's checks read fact-check logs under `docs/`, the listed files in `verify/` and their harness pins, `pnpm-workspace.yaml` and each package's `typecheck` script and tsconfig. A filter that missed one of these would let a pull request break the book unchecked. A filter would also save little: the steps after the install took under 10 seconds locally, against T8's five-minute limit for filtering. Because `ci.yml`'s `pnpm test` already includes the figure test and `book:switch-report`, both run twice on each pull request, for about 4 seconds. We kept them so that `book-build.yml` alone vouches for the artifact T9 deploys.
- **`verify.yml` nightly and on demand:** the same setup, then `pnpm run fetch-docs` for any harness whose mirror isn't committed (Claude), and `pnpm verify`. The workflow fails when a result file changes, which flags upstream drift for review.

### What X1 built (2026-11-18)

- **Pinned actions.** Both workflows pin `actions/checkout` v7.0.1, `pnpm/action-setup` v6.1.1 and `actions/setup-node` v7.1.0 by commit SHA, each the newest release at least a week old (tag commit dates 2026-07-17, 2026-11-03 and 2026-10-07). pnpm's version comes from `packageManager`, and Node's from `.nvmrc`. Checkout runs with `persist-credentials: false`, and the token has `contents: read` only. *Superseded on 2026-11-19 by [§3d](#3d-actions-locked-by-a-lockfile-added-2026-11-19): `uses:` lines now name tags, and the lockfile holds the commits.*
- **User namespaces.** The Copilot harness runs each example in `unshare -rn` and refuses to run without it. Ubuntu 24.04 runners restrict unprivileged user namespaces through AppArmor, so both workflows lift that with `sysctl` first.
- **Drift that ignores noise.** `pnpm test` and `pnpm verify` rewrite `results/*.json` with timings and absolute paths. `scripts/ci/results-drift.mjs` compares each changed file with its committed version after dropping `ms` and `checkedAt` and normalizing the checkout path, temp directories and "N ms" strings. It also ignores `tail` (raw stdout), and for our own examples' `run-examples.json` it compares only each example's file, outcome and exit code, because the examples assert their own claims. The first GitHub runs showed why: stdout carries process ids, and a Claude example made 14 model requests on the runner against 13 locally while passing. It fails on anything else, including new untracked result files. `ci.yml` runs it after `pnpm test`, and `verify.yml` after `pnpm verify`. Both cases were tested locally: a timing-only rerun passes and a changed `outcome` fails.
- **Audit.** `verify.yml` ends with `pnpm audit --audit-level high`. Accepted alerts go in `auditConfig.ignoreGhsas` in `pnpm-workspace.yaml`, each with a comment naming the README that records why. The only entry is picomatch's GHSA-fc5q-39xc-vjpf.
- **Dependabot scope.** GitHub's dependency graph also scans the 24 example manifests inside the mirrored docs (`docs/reference/*/source/`), and Dependabot opened failing security-update runs against them (for example zod in an ADK snippet). `.github/dependabot.yml` excludes `docs/reference/**` and turns off routine version PRs; security updates for our manifests still run. Alerts already raised on the mirror manifests are upstream examples, not our dependencies, and the owner can dismiss them in the Security tab.
- **First GitHub runs (2026-11-18).** `ci.yml` passes in under 3 minutes. The first hand-started `verify.yml` ran every harness in 12 minutes (the runner is about 3× slower than our container), and the audit passed. It failed the drift check on three Cloudflare files. One cause was ours: `git show` exceeded Node's 1 MB buffer on `typecheck-docs.json`, which read as a new file. Another was noise: bundled-code stack positions, now normalized. The rest, two doc blocks whose mismatch cause differs on the runner (`repo__agents__scheduling__30`, `cf__agent-class__run-workflows__23`), does not reproduce locally, so `verify.yml` now uploads the result files as an artifact on failure for an exact comparison. The network guard held: the MCP blocks' 403 is the harness's own refusal. After X3 (all harnesses on the root TypeScript 7.0.2) and X4 (a seeded `Math.random` for the ADK doc runs), the third `verify.yml` run passed: every harness, the drift check and the audit.

## 3b. Dependency security (X2, added 2026-11-18)

The owner set the dependency policy on 2026-11-18. Pins must be at least one week old, down from two weeks. When a pinned dependency has a known vulnerability, the age rule gives way: move to the latest release that fixes it. GitHub's Dependabot flags vulnerabilities on the default branch; on 2026-11-18 it reported 19 (7 high, 9 moderate, 3 low).

X2 works through every open alert, and keeps doing so as alerts arrive:
1. **Find the package.** Map the alert to the harness in `verify/<sdk>/package.json`, or to the root `package.json`, that pulls the package in, directly or transitively.
2. **Upgrade.** Upgrade to the latest release that fixes it. For a transitive dependency, bump the direct dependency that brings it in. Only if no such release exists, add a `pnpm.overrides` entry with a comment that names the alert.
3. **Re-verify.** Run `pnpm check`, `pnpm typecheck`, `pnpm test` and the affected harness's `pnpm run verify`. Record any change in doc-example results in that SDK's fact-check, because the reference states its pinned version.
4. **Record unfixable alerts.** If no fixed release exists, record the alert as accepted in the harness README, with the reason the offline harness is not exposed: mock models, no network, an allowlisted environment.

Once CI exists (X1), the nightly `verify.yml` also runs `pnpm audit --audit-level high` and fails on new high alerts.

## 3c. Weekly SDK updates (added 2026-11-19)

The owner asked on 2026-11-19 for a weekly check that opens a pull request when an SDK we verify has a new version. `.github/workflows/sdk-updates.yml` does it every Monday at 05:37 UTC, and on demand.

- **Plan.** `scripts/ci/sdk-updates.mjs plan` reads each `verify/*/package.json` and asks the npm registry for the newest release of every runtime dependency that is at least seven days old, the age rule in [AGENTS.md](../../AGENTS.md#coding-standards). A stable pin moves only to a stable release; a prerelease pin, such as miniflare's dated betas, may also move to a newer prerelease of the same major version. The job runs no package code.
- **A pin stays inside the range its harness's main package declares (as of 2026-11-22).** A harness exists to test its main package as that package installs. The main package is the one `apps/manual/src/data/harnesses.json` names for the harness, such as `@google/adk` for `verify/google-adk`, and a test fails if a harness lacks one. So when the main package's chosen release declares another pinned package in its `dependencies`, `optionalDependencies` or `peerDependencies`, that pin moves only to the newest release inside the declared range that is also at least seven days old and newer than the pin. With no such release, the pin stays. A package declared in more than one field must satisfy every range. The rule came from #339: `@google/adk` 2.5.0 declares `@google/genai ^2.29.1` and `@a2a-js/sdk ^0.3.10`, but the plan proposed `@google/genai` 3.3.0 and `@a2a-js/sdk` 1.3.0, and two samples broke.
- **The main package moves only when every pin can follow it.** The plan tries the main package's eligible releases newest first. It takes the first one under which every range that release declares on the other pins holds, and every peer range the other pins' chosen releases declare on the main package holds too. When none qualifies, the main package stays at its pin. Either way, the job log gets a `::warning::` naming the newer release it passed over and the range that ruled it out. So a release whose range needs a sibling release younger than seven days waits a week, and the main package never moves alone.
- **Every pin's own peer ranges must hold.** pnpm resolves a package's peers to the harness's own copies, so the plan reads each chosen release's `peerDependencies` on the harness's other pins. When a bump breaks one, the plan undoes it, either the bump of the package that declares the peer or, if that package stays, the bump of the peer, and it repeats until no bump breaks a range. Each undone bump gets a `::warning::`. On 2026-11-22 this held `@cloudflare/computer` at 0.8.0 in `verify/cloudflare-agents`, because the pinned `@cloudflare/think` 0.23.0 declares the peer `^0.8.0` and the plan would otherwise have proposed 0.11.2. A range between two pins that the release doesn't declare as a peer, such as a plain dependency of one pin on another, isn't checked.
- **The plan reads ranges as npm's semver does, and refuses what isn't a range.** It reads caret, tilde (`~>` too), exact, comparator, hyphen, x-range, `*` and `||` ranges, ignores build metadata, and ends an upper bound it adds before that version's first prerelease, as in `<3.0.0-0`. A prerelease release satisfies a range only through a comparator on its own version, except under a prerelease pin, which the plan matches as npm's `includePrerelease` option does, so the pin can move to a newer beta inside a range written for stable releases. A spec that isn't a semver range, such as a dist-tag, an `npm:` alias, a `workspace:`, `file:` or `link:` spec, a git spec or a URL, holds the pin, and the plan writes a `::warning::` rather than guess. It also logs each pin a range held below a newer release.
- **One harness's failure doesn't stop the others.** A harness whose plan throws, as on a registry error or a missing main package, gets an `::error::` line and is left out of the matrix, while the others' updates go ahead. The plan job runs `matrix=$(node scripts/ci/sdk-updates.mjs plan)` in a default `run:` step, which GitHub runs with `bash -e`, so a non-zero exit would drop every harness's update. The plan therefore exits non-zero only when every harness failed. Stdout carries only the matrix, and the notes go to stderr. So when only some harnesses fail, the `::error::` annotation on the run is the only signal: the run stays green and opens no pull request for those harnesses, and nobody is told unless someone reads the run. Fixing that needs a workflow change, such as letting the step record the plan's exit code and fail after writing the matrix. A missing main package can't reach this path from `main` unnoticed: the test that every harness has one runs in `ci.yml` on every pull request, so a change that adds a harness without an entry in `harnesses.json` fails before it merges. A registry error, the other likely cause, has no such check.
- **`apply` and `check` needed no change**, because they hold the update to the bumps the plan prints. Pins of packages that no chosen release declares, and the main package's own pin when its releases break nothing, move as before.
- **Update, without write access.** For each harness with an update, a job bumps its pins, runs `pnpm install` and the harness's `verify`, compares the results with the committed run, and uploads a patch with a summary. It writes the plan job's bumps rather than asking the registry again, so a release that crosses the age cutoff between the two jobs can't fail the check. This job runs the new releases' code, so its token is read-only and its checkout keeps no credentials.
- **Open the pull request, after checking the patch.** A last job, `open-pr`, installs and runs no package code, and its own `GITHUB_TOKEN` only reads. It checks out `main` at the run's commit and applies the patch to the index alone, so the working tree keeps `main`'s scripts. It commits the patch locally, and `scripts/ci/sdk-updates.mjs check` refuses the commit unless it edits only `verify/<harness>/package.json` and `pnpm-lock.yaml` and changes only files under `verify/<harness>/results/`, each a regular, non-executable file. That check matters because the patch comes from a job that ran the new releases' code, and a tampered patch could otherwise rewrite a workflow, the script that holds the token, or the tools that CI and the release install. Only the job's last step then gets a token. It runs `gh` and `scripts/ci/version-commit.mjs`, which import only `node:` modules and the scripts beside them, and opens or updates one pull request per harness. The description starts with the plan's bumps and then quotes the update job's summary of the verify outcome and the drift, marked as text a malicious release could have rewritten. The step counts only a pull request from this repository's branch, never a fork's branch of the same name. The pull request then goes through the same reviews as any other, including re-mirroring the docs at the new tag and fact-checking what changed. Auto-merge stays off, because these pull requests need a person's review, and `auto-merge-guard.yml` turns it off on any branch but the release's.
- **The check reads the two files' contents too (added 2026-11-19, after the first code review).** A path check alone would let a tampered patch add a script to `package.json` or point the root's tools at other packages in the lockfile. So the new `package.json` must be exactly what `apply` writes with the plan job's bumps, and a new script, dependency, override or pnpm setting fails the check. In the lockfile, every section but `importers`, `packages` and `snapshots` must stay byte for byte. The harness's own importer may change only its specifiers and versions, each to a registry version, never a `link:`, `file:` or URL. Every other importer may change only as the next bullet allows. An existing `packages` or `snapshots` entry may be removed but never changed. A new entry must be written in plain lines, a new snapshot's dependencies must be registry versions, and a new package must resolve from the npm registry by its integrity alone.
- **Another importer may follow a peer that the update moved, and nothing else (as of 2026-11-22).** pnpm shares one resolution of a peer across the workspace, so a harness's update can also move a peer in other importers. On 2026-11-22 two honest updates did:
  - In the `verify/cloudflare-agents` update, bumping `@cloudflare/workers-types` to 5.20261115.1 changed `wrangler`'s resolved version in the `apps/docs`, `apps/manual` and `apps/site` importers from `4.160.1(@types/node@26.6.6)` to `4.160.1(@cloudflare/workers-types@5.20261115.1)(@types/node@26.6.6)`, because `wrangler` declares `@cloudflare/workers-types` as an optional peer.
  - In the `verify/langchain` update, `@langchain/anthropic` 1.6.5 depends on `@anthropic-ai/sdk` 1.12.0, which `@anthropic-ai/claude-agent-sdk` 0.3.327 declares as a peer, so the `verify/claude-agent-sdk` importer's peer moved from `@anthropic-ai/sdk@0.129.0(zod@4.6.7)` to `@anthropic-ai/sdk@1.12.0(zod@4.6.7)`. That peer is not one of the plan's bumps.

  So `check` lets any importer but the harness's own change only in the parenthesised peer groups of a resolved `version:`. Its key, every specifier, the version before the parentheses, and the list and order of its dependencies stay byte for byte. The groups that stay keep their order, no peer appears twice, and each new or changed group must name a registry name and an exact version, never a `link:`, `file:` or `npm:` alias, a URL or YAML syntax. Beyond that, the two kinds of importer differ:
  - **A workspace importer** (the root, `packages/*` and `apps/*`) holds the tools CI and the release run, so a new or changed group must name exactly one of the bumps `check` was given, and so must every group nested in it. A group may disappear only if it named another version of a bumped package.
  - **Another harness's importer** may move a peer only to a snapshot that the updated harness's own importer reaches. The harnesses are test fixtures, and the updated harness already installs whatever it reaches, so this extends no new trust to registry code. Holding these importers to the bumps alone would have refused the honest `verify/langchain` update. A group may disappear only if it named a bumped package, or a package the updated harness reaches.
- **The snapshot a moved dependency resolves to must be main's with only its peers changed (as of 2026-11-22).** Without this rule, a tampered patch could keep an importer's peers right but give the dependency's new snapshot other registry versions of its own dependencies. So the new snapshot must match main's snapshot for the old resolution line for line, except for the dependency lines of the peer groups that changed in its key:
  - A changed group changes its line to the group's new text. A new group adds one line, under `optionalDependencies:` if the package's entry in `packages` marks the peer optional, and under `dependencies:` otherwise; the package must declare it as a peer. A dropped group drops its line. No heading is added or moved, and no dependency is listed twice.
  - Any other dependency keeps its version. Its line may change only by gaining or losing peer groups under the same rules, and then its own snapshot is checked the same way, to a depth of 16.
  - The snapshot a changed or new peer line points at must be one that main holds unchanged, or for a workspace importer the snapshot the harness's own importer resolves a bump to, whose dependencies must in turn be ones main holds or other bumps' resolutions. For another harness's importer it must be a snapshot the updated harness reaches.

  For `wrangler`, pnpm renamed the snapshot and added only `'@cloudflare/workers-types': 5.20261115.1` under its `optionalDependencies`, and the new `@cloudflare/workers-types@5.20261115.1` snapshot is `{}`. A snapshot that several importers move to is checked once, but a workspace importer's move is checked under the workspace's rules even when a harness moved to the same snapshot. The rules refuse some changes pnpm could make for an honest bump: a bumped peer of a workspace tool whose own peers aren't bumps, a bump that brings a workspace tool a dependency main lacks, or a snapshot whose `transitivePeerDependencies` or headings change. Such an update fails the check, and a person updates it by hand.
- **GitHub signs the update commit, because the API makes it (added 2026-11-19).** `main`'s ruleset requires signed commits, so a commit pushed with `git` would block the pull request, as it blocked #70 (§3f). The last step therefore makes the checked commit again with `version-commit.mjs`, the script the release uses. The script commits through GraphQL's `createCommitOnBranch` on a staging branch, `deps/staging/sdk-<harness>`, that starts at the run's commit on `main`. It then reads the new commit over REST and moves `deps/sdk-<harness>` to it only if `verification.verified` is true, the tree equals the checked commit's tree and the only parent is that base. Each harness has its own staging branch because the matrix's jobs run side by side; the release keeps `changeset-release/staging`. A rerun on the same `main` finds the verified commit already on the branch and leaves it alone. If the branch's head isn't a verified commit that GitHub committed with the update's headline, as when someone pushed or amended a commit on the pull request, the step fails and leaves the branch alone instead of dropping that work. It reads the branch again just before moving it and stops if the branch moved meanwhile. The commit's author is the token's owner, not `github-actions[bot]`.
- **A personal access token opens the pull request, so CI runs on it.** `main` requires the `checks`, changeset and lockfile statuses, which `ci.yml` reports. A pull request that a workflow opens or updates with `GITHUB_TOKEN` gets `pull_request` runs that wait until someone with write access approves them, and GitHub's docs say a GitHub App installation token or a personal access token avoids that. `GITHUB_TOKEN` would probably make verified commits, since it is an installation token and GitHub signs commits that an app makes with no custom author, but the approval step would hold up every weekly pull request. So the last step uses the `SDK_UPDATES_TOKEN` secret when it exists, and otherwise `RELEASE_PR_TOKEN`, the fine-grained token with Contents and Pull requests read and write that the owner added for the release (§3f). It fails, writing nothing, when neither is set.
- **Owner setup.** None beyond §3f's `RELEASE_PR_TOKEN`. To keep the release token out of this workflow, the owner can add `SDK_UPDATES_TOKEN`, a fine-grained token for this repository with Contents and Pull requests read and write. Give it Workflows read and write too. The check refuses any change under `.github/`, but moving `deps/sdk-<harness>` from last week's commit to this week's spans every workflow change `main` gained in between, and GitHub probably refuses that move to a token without the Workflows permission. `RELEASE_PR_TOKEN` lacks it, so with that token alone the step can fail on such a week; deleting the stale branch lets the next run start it afresh.
- **No shared cache from untrusted code.** The update job runs without the pnpm cache: a cache it saved could be restored by later runs on main, so a tampered store from a bad release would reach CI.
- **Failures still open a pull request.** If `pnpm install` or `verify` fails, the pull request still opens, with the failure in its description. If a harness's `update` job fails outright, the other harnesses' pull requests still open. A run that finds nothing to change opens nothing, and a run dispatched from a branch other than `main` does nothing.
- **Lockfile conflicts.** Several harnesses share packages, such as `ai` and `@ai-sdk/openai`, so merging one harness's pull request can leave the others conflicting on `pnpm-lock.yaml`. The next weekly run rebuilds each open branch from `main`, or a person reruns the workflow by hand.
- **Pinned actions.** The workflow reuses ci.yml's pins and adds `actions/download-artifact` v8.0.2, whose tag commit is dated 2026-10-07, more than a week before it was pinned.
- **Tests.** `scripts/ci/sdk-updates.test.mjs` runs offline, and `ci.yml` runs it on every push. It covers the version choice, including deprecated releases, and the range cap against a fake registry: a major the main package's range excludes is blocked, the newest release inside the range is picked, a spec that isn't a range holds the pin, a bump of the main package moves the cap, and a package the main package doesn't declare still moves. Further tests cover four cases. The main package stays, or moves to an older release, when a pin can't follow its range or a pin's peer range excludes it. A bump that breaks a peer range is undone. A prerelease pin moves inside a stable range, and `optionalDependencies` count. A failing harness stays out of the matrix while the others stay in it. The tests also cover the check on an update's change: another harness, a workflow, a script, an executable file and an empty change are each refused. Content tests refuse a `package.json` with an unplanned version, script or override, and a lockfile that changes the root importer, an existing package, `settings` or `overrides`, adds a tarball-URL package, or uses a YAML alias, an open quote or a duplicate key. The repository's own lockfile passes with any of its entries new, and on 2026-11-19 the check passed real `pnpm install --lockfile-only` bumps of the pi, langchain and Vercel AI SDK harnesses. It parses `sdk-updates.yml` and fails if any step but `open-pr`'s last one reads a secret, if that secret isn't `SDK_UPDATES_TOKEN` or else `RELEASE_PR_TOKEN`, if the workflow names `GITHUB_TOKEN`, or if a job asks for more than `contents: read`. It also fails if a `run:` step expands a `${{ }}` expression, if the `update` job holds a token, or if `open-pr` runs pnpm, uses an action other than checkout and download-artifact, runs node on anything but the check and `version-commit.mjs`, pushes with `git` or turns on auto-merge. It then runs `open-pr`'s own steps against a local bare repository with the stand-in `gh` that `release.test.mjs` uses, now in `scripts/ci/fake-gh.mjs`. Those runs check that the branch gets a verified commit with the checked tree on `main` and that a pull request opens without auto-merge. They check, too, that a rerun changes nothing and edits the open pull request, that a patch which rewrites `version-commit.mjs` stops before any token step, that an unverified commit leaves the branch and the pull request alone, and that a missing token fails before any call. A further run checks that a commit pushed to the update branch by hand stops the step and stays on the branch. `version-commit.test.mjs` adds the staging-branch option: the release's staging branch stays untouched, and a staging branch equal to the target branch is refused.

## 3d. Actions locked by a lockfile (added 2026-11-19)

The owner asked on 2026-11-19 to lock our GitHub Actions the way Lamina PDF does, with GitHub's workflow lockfile, which became generally available on 2026-10-28 ([GitHub changelog](https://github.blog/changelog/2026-10-28-github-actions-workflow-lockfiles-are-generally-available/)). It replaces the commit SHAs in our `uses:` lines, which [§3](#what-x1-built-2026-11-18) records.

- **Tags in the workflows, commits in the lockfile.** Each `uses:` line names a release tag (`actions/checkout@v7.0.1`). `.github/workflows/actions.lock` records the commit each tag resolved to and the ids of the owning account and repository, so GitHub refuses a run if a tag moves or a repository changes hands.
- **How this lockfile was made.** `gh actions-lock` needs GitHub's API for every action's repository, which the session that wrote it couldn't reach. Instead, the entries come from Lamina PDF's verified lockfile (`laudebugs/laminapdf` at `7b4b37b`), which holds all five of our actions at the versions we pin. Each tag's commit was then checked against the action's own repository with `git ls-remote`. All five matched; pnpm's annotated tag peels to the locked commit.
- **Verified on every pull request.** `ci.yml`'s `lockfile` job installs `gh-actions-lock` v0.4.1, the newest release, whose tag commit is dated 2026-11-02, and runs `gh actions-lock --verify`. The job also proves the copied entries: it fails if any of them doesn't match what the tool would write.
- **Updates.** Dependabot now proposes action updates weekly, at least seven days old, grouped for minor and patch releases. An update rewrites the tag and the lockfile entry together. A new workflow, or a new action in one, needs `gh actions-lock` run by hand ([CONTRIBUTING.md](../../CONTRIBUTING.md#changing-a-workflows-actions)).
- **Owner setup.** Once `main` passes with the lockfile, turn on the **Require lockfile** policy (Settings → Actions → General), so GitHub refuses any workflow run the lockfile doesn't cover.

## 3e. A changeset check, on since L4b (added 2026-11-19)

Todo L2 added a `changesets` job to `ci.yml`, as [publish-and-docs PB2](publish-and-docs.md#pb2-changesets-in-one-fixed-group-published-only-from-ci-accepted) plans. It fails a pull request that changes a package's shipped files without a changeset. It stayed off until the first release, because the owner said "Changesets wait until we publish", and L4b switched it on.

- **The check.** The job checks out the full history (`fetch-depth: 0`), so Changesets can find where the branch left `main`, then runs `pnpm changeset status --since=origin/main`. That command fails when a package that Changesets versions has changed and no changeset was added since `origin/main`. `changedFilePatterns` in `.changeset/config.json` limits "changed" to each package's `src/`, `package.json` and `tsconfig.build.json`, matched relative to the package's folder. The first code review added the last two, because a runtime dependency bump or a build setting reaches users as surely as a code change. Docs, tests and workflow edits need no changeset, and a change to those files that users don't see takes `pnpm changeset --empty`.
- **A small install, no shared cache.** The job runs `pnpm install --frozen-lockfile --filter .`, which installs only the root's devDependencies, `@changesets/cli` among them. It doesn't use the pnpm cache: its store is a small part of the full one, and saving it under the shared key would keep the `checks` job's store out of the cache.
- **The switch, thrown in L4b.** L2 left the job off with `if: false`, and L4b removed that line. While the packages were private, the check passed whatever changed, because `privatePackages.version: false` tells Changesets to skip private packages. L4a dropped `private`, so the check applies to both packages. Local runs on 2026-11-19, with L4a's change committed as the base, passed a docs-only commit and failed a `src/` edit without a changeset, matching the throwaway-branch runs below.
- **Version bumps pass (L4b).** `pnpm changeset status --since=origin/main` alone fails any change that runs `pnpm changeset version`, because that command edits each `package.json` and consumes the changesets. A local run on 2026-11-19 failed exactly that way, and so would L4b's own pull request, which versions both packages to 0.1.0-alpha.0. L4b's todo offered two ways out: leave the versioning to a later "Version packages" pull request, or switch the gate on in a follow-up. Neither kept the gate on from L4b's merge onward, so the job now runs `scripts/ci/changeset-gate.mjs` instead. The script passes a change whose shipped files are only `package.json` files, one for every versioned package, each differing from the base in `version` alone and each with a `CHANGELOG.md` section for the new version. All of them must move to one version, later than the base's, so a bump can neither split the fixed group, which would break every later plan, nor move a dist-tag back to an older version. It sends every other change to `pnpm changeset status`, including a bump that also edits `src/`.
- **The bump exception, checked.** Locally on 2026-11-19, the script passed L4b's branch against `origin/main`, where `pnpm changeset status` alone exited 1, and failed the same branch once a commit added a `src/` edit without a changeset. `scripts/ci/changeset-gate.test.mjs` checks both outcomes in throwaway git repositories, with the status run stubbed. A bump must also fit `.changeset/pre.json`: in pre mode only an `alpha` prerelease passes, so a hand-made bump can't give the plan a version it refuses. The exception lets through L4b's pull request, a bump made by hand and every auto-merged "Version packages" pull request (§3f); a test in `changeset-gate.test.mjs` checks such a pull request in pre mode, and `version-pr.test.mjs` runs the gate on the real `changeset version` result for this checkout.
- **A new top-level changeset, not an edited one (medium review, 2026-11-19).** `pnpm changeset status` counts any added or edited `.changeset/*.md` or `.changeset/pre/*.md` file as the change's changeset (`getChangedChangesetFilesSinceRef` in `@changesets/git` 4.0.1). An edit to a changeset in `pre/`, which a prerelease already consumed, would therefore let a `src/` change merge and never publish. So before it runs `pnpm changeset status`, the gate requires a change to shipped files to add or edit a top-level changeset that `changeset version` would consume: not `README.md`, `AGENTS.md`, `CLAUDE.md`, `GEMINI.md` or a dotfile, which Changesets never reads (`@changesets/read` 1.0.1), and not one that names only a package Changesets skips, such as `@buildanagent/manual`. It runs `pnpm changeset status` with an allowlisted environment (`PATH`, `PNPM_HOME`, a temp `HOME`, `TMPDIR`, `LANG`), because that command runs third-party code.
- **No new action.** The job uses the three actions `ci.yml` already locks, so `actions.lock` is unchanged.
- **Tested on a throwaway branch.** On `test/L2-gate`, with the job switched on, `private` dropped from both packages and the push trigger widened to that branch, three runs gave the expected results. A commit that changed only docs passed ([run 44497669322](https://github.com/laudebugs/buildanagent/actions/runs/44497669322)). An edit to `packages/gateway/src/retry.ts` without a changeset failed with "Some packages have been changed but no changesets were found" ([run 44497925125](https://github.com/laudebugs/buildanagent/actions/runs/44497925125)). Adding a `patch` changeset for the gateway made it pass, listing both packages for a patch bump ([run 44498147370](https://github.com/laudebugs/buildanagent/actions/runs/44498147370)).
- **Pull requests checked locally, not yet on GitHub.** Those runs were pushes. In use, only `pull_request` runs can fail the job, because a push to `main` compares `main` with itself; a `pull_request` run checks out a merge commit of the branch into `main`. A local merge commit built the same way, with the widened patterns, gave the same results: a `package.json`-only change failed, and an empty changeset or a `patch` one made it pass. L4b's pull request is the job's first `pull_request` run.

## 3f. Releases through npm trusted publishing (added 2026-11-19)

Todo L3 added `.github/workflows/release.yml`, which publishes `@buildanagent/gateway` and `@buildanagent/sdk` from CI with no npm token stored anywhere, as [publish-and-docs PB2](publish-and-docs.md#pb2-changesets-in-one-fixed-group-published-only-from-ci-accepted) plans. L4b made it publish alphas and published the first one, 0.1.0-alpha.0. Since 2026-11-19, changesets reach npm through a "Version packages" pull request that `release.yml` opens and GitHub auto-merges, so each merged Version packages pull request publishes one alpha, holding every changeset merged before it.

- **Six packages publish since L11 (added 2026-11-22).** L11 dropped `private` from `@buildanagent/agent-safety`, `@buildanagent/protocol`, `@buildanagent/harness` and `@buildanagent/cli`, so all six packages now version and publish together, in one fixed group ([publish-and-docs PB4](publish-and-docs.md#pb4-publish-the-protocol-harness-and-cli-packages-after-the-gateway-and-sdk-accepted)). `RELEASE_ORDER` in `release-plan.mjs` lists them in dependency order: gateway, SDK, agent-safety, protocol, harness, CLI. The plan, the release notes and the Version packages pull request's body read that list. L11 delivered the six-package `release.yml` as a document, [release-yml-for-six-packages.md](reviews/release-yml-for-six-packages.md), because sessions don't edit `.github/`; the owner adds it to L11's branch. Its pack and publish loops name the same six in the same order, so the pack job packs in `RELEASE_ORDER`, and `release.test.mjs` fails while the workflow's loops and the list differ. The first alpha of each of the four publishes only through `release.yml` on a push to `main`, never from a session or a developer's machine. That first alpha carries N24's MCP client, `@buildanagent/harness/mcp`.

  Before the first version commit, the four sit at 0.0.0 beside the gateway's and SDK's alpha. So the plan checks that every package shares one version only after its pending-changeset and pre-mode-exit skips, and throws on mixed versions only when nothing is left to version.

  On a throwaway branch, `pnpm changeset version` (Changesets 3.0.3) moved all six from that state to one `0.1.0-alpha.28`.
- **The plan decides each run.** The `plan` job runs `scripts/ci/release-plan.mjs plan`, which first reads the checkout. It then asks GitHub, with the run's read-only `GITHUB_TOKEN`, whether the release `v<version>` exists. Only when the release is missing does it ask the public npm registry whether each package exists at that version. The plan asks for a version when a changeset is pending or `.changeset/pre.json` says `"mode": "exit"`, and then publishes nothing. Otherwise it publishes only when no package is `private`, the version isn't 0.0.0, the version matches the pre mode, and the GitHub release `v<version>` is missing. With no release, it lists the packages npm lacks; it publishes even when npm holds all six, so the publish job can create the missing release. Since this change, `GITHUB_REPOSITORY` is required on every plan that isn't skipped earlier, and `GH_TOKEN` is used when set: `planRelease` throws "set GITHUB_REPOSITORY to owner/name" right after the pre-mode check, where before only a run that found all six packages on npm needed it. Without a token the request is unauthenticated, at GitHub's lower rate limit, so `release.yml` passes the run's token. Every package must share that version; the check comes after the two skips, as the "Six packages publish since L11" item says. The 0.0.0 rule matters since L4a: dropping `private` alone publishes nothing, because the workspace has never released 0.0.0.
- **A release means released, so the plan never asks npm about a released version.** The owner treats a successful `npm publish` as the confirmation, so the skip on an existing release is deliberate. A release made by hand, or one created over a partial or lost upload, would therefore leave the missing packages unpublished while the run stays green. To recover, delete the GitHub release `v<version>` and its tag, then re-run `release.yml`. The plan then asks npm, and the publish job skips each package npm already holds and uploads the rest.
- **Two tests read the checkout.** Both read the checkout's own `package.json` files. One fails at any version if any of the six sets `private` or loses its publish guard, because a `private` field that came back would make every plan skip with a green run. The other runs the plan on the checkout as it will be on `main` and expects it to publish its version under its dist-tag; in L4b that is 0.1.0-alpha.0 under `alpha`.
- **Errors fail the job.** A registry or GitHub answer other than 200 or 404 fails the job instead of reading as "not published" or "not released". The GitHub request comes first, so that failure ends the job before any npm request.
- **Pre mode sets the version's shape and the dist-tag (L4b).** L3's plan refused every prerelease, because `release.yml` then published to `latest` only. L4b replaced that rule, because the owner chose alpha releases with `latest` left on the placeholder. While `pre.json` says `"mode": "pre"`, the plan accepts only a prerelease whose identifier is `pre.json`'s `tag`, such as 0.1.0-alpha.0 for `alpha`, and publishes it under that dist-tag. Outside pre mode it accepts only a plain x.y.z and publishes it under `latest`. Any other pairing, such as a stable version in pre mode, fails the plan, because publishing it would move the wrong dist-tag. The plan also refuses a `pre.json` tag that npm couldn't use for prereleases, such as `latest` or a version. The publish job passes `--tag` and refuses a prerelease under `latest`. npm 11.21.2 needs the flag anyway: without it, a prerelease publish fails with "You must specify a tag using --tag when publishing a prerelease version" (`lib/commands/publish.js`).
- **Pack with a read-only token, publish without running package code.** The `pack` job installs the root and the packages, runs their tests and runs `pnpm pack` for each package that publishes, whose `prepack` builds `dist/`. Once the owner adds L11's file, it packs in `RELEASE_ORDER`, checks each tarball's name, and checks that the CLI's tarball names `dist/bin.js` as its `buildanagent` binary with a `node` shebang and that the built binary prints its help. It uploads the tarballs and the release notes as an artifact. The `publish` job checks nothing out and installs only npm, then runs `npm publish <tarball> --access public --provenance`, gateway first. npm runs no lifecycle scripts for a tarball publish (`lib/commands/publish.js` in npm 11.21.2 runs them only for a directory).
- **Reruns finish a partial release.** The publish job skips any package npm already holds, so a run that stopped partway can finish. "Re-run failed jobs" reuses the first plan. "Re-run all jobs" or the next push to `main` plans again, and the plan keeps publishing while the GitHub release is missing. A rerun of the version jobs rebuilds the same version commit from the newest `main`, and the `version-pr` job skips the push when the branch already holds that commit. Before it uploads anything, the publish job reads the version in `main`'s `packages/gateway/package.json` and refuses to publish any other. Without that check, re-running an older failed run after a newer release would publish the older version under the same dist-tag and move the tag back. A normal run always passes it, because only a merged Version packages pull request changes `main`'s version, and runs wait for each other. The tarball artifact is kept 30 days, so a failed publish job can be re-run from the same tarballs.
- **The plan asks GitHub for the release before npm, because npm makes an upload public minutes after accepting it (added 2026-11-22).** The publish job creates the release only after its last upload returns, and the concurrency group starts the next run only after that run ends. So once the release exists, every upload has returned, and npm refuses a second one even while its version endpoint still answers 404 (npm made the `0.1.0-alpha.28` uploads public 75 to 187 seconds after `npm publish` returned; the measurements are in the report on PR #338, which isn't on `main` yet, and fact-check row fix/release-plan-released-first-7 marks the figure unverified until it lands). Runs 45067734004 and 45069201063 each planned within 18 seconds of the release ahead of them, read 404 for all six packages, and failed with E409 on the harness and E403 on the SDK. One case still meets npm's lag, we infer; no run has shown it. The comment at the top of `release.yml` still says the workflow publishes "a version npm lacks"; sessions don't edit `.github/`, so rewording it is a follow-up for the owner. When a run fails after some uploads but before the release, a run that plans within npm's lag can read 404 for those uploads and fail with the same E409. A rerun once npm shows them finishes the release.
- **After a Version packages pull request merges, nothing else merges until its release run completes (the owner's rule, 2026-11-22).** A merge that lands while the release run is queued or in progress starts a second run behind it. The owner decided that a successful `npm publish` needs no second check against npm, so the rule waits only for the run. Before merging anything into `main` in that window, check that `gh run list --repo laudebugs/buildanagent --workflow release.yml --branch main --limit 5 --json databaseId,status,conclusion` shows no run whose `status` isn't `completed`, and that the newest run's `conclusion` is `success`. A pull request with auto-merge on counts as a merge, so turn its auto-merge off for that window.
- **Trusted publishing only, failing closed.** The `publish` job runs on `ubuntu-24.04` in the `release` environment, with `contents: write` and `id-token: write` and nothing else. It points npm's user config at a file that names the registry and its global config at a separate empty file. Neither file holds credentials. The two must differ, because npm exits with "double-loading config" when both settings name one file, and that error stopped the first publish ([run 44528880576](https://github.com/laudebugs/buildanagent/actions/runs/44528880576)). The job refuses to run if any npm token variable is set, printing only the variable's name, and leaves out setup-node's `registry-url`, which writes an `.npmrc` that reads `NODE_AUTH_TOKEN`. npm's OIDC exchange never throws: if it fails, npm falls back to whatever token the config holds (`lib/utils/oidc.js` in npm 11.21.2). With no token to fall back on, a missing or wrong trusted publisher ends the publish with ENEEDAUTH. `--provenance` makes the publish fail rather than ship without provenance, which npm adds on its own only from a public repository ([npm docs](https://docs.npmjs.com/trusted-publishers)).
- **npm 11.21.2, installed explicitly.** Trusted publishing needs npm 11.5.1 or later and Node 22.14.0 or later ([npm docs](https://docs.npmjs.com/trusted-publishers)). The job installs npm 11.21.2, published 2026-11-04 and the newest 11.x release at least a week old as of November 2026, and checks both versions before it publishes. npm 12.2.2, from the same day, would also do, but its `engines` field requires Node `^22.22.2`, which would tie the release to a newer Node 22 than npm needs. Node comes from `.nvmrc`.
- **A tag and a GitHub release per version.** After every package is on npm, the job creates the GitHub release `v<version>` at the commit it packed, which creates the tag. That commit is the run's own: the squash commit of the merged Version packages pull request. One tag covers every package, because the fixed group gives them one version. A prerelease gets `--prerelease`, so GitHub marks it as one. The release notes join each package's `## <version>` section from its `CHANGELOG.md`. The job peels an annotated tag to its commit, and fails if an existing tag points at another commit or if the tag lookup fails with anything but a 404.
- **The docs deploy follows a stable tag.** A last job, with only `actions: write`, runs `gh workflow run docs-deploy.yml --ref main -f tag=v<version>`, because a tag pushed with `GITHUB_TOKEN` starts no workflow while a `workflow_dispatch` always does ([GitHub docs](https://docs.github.com/en/actions/concepts/security/github_token)). The plan records whether `docs-deploy.yml` exists, and the job is skipped, not failed, until L8 adds it. It is also skipped for a prerelease, because the production docs follow stable releases ([publish-and-docs DS4](publish-and-docs.md#ds4-the-docs-follow-main-until-010-then-releases-accepted)).
- **The owner's release flow.** The owner decided on 2026-11-19: "let's make the releases automated too. Let's keep it alpha for now until we're ready to publish", and then "let's make the publishes run on every change to the package". L4b's `version` job pushed a version commit straight to `main`, but it ran third-party code, `pnpm install` and Changesets, in a job whose token could push to `main`, and `main`'s branch protection could refuse the push. So L4b switched it off. Asked whether the version step should be "a pr that will be autocompleted", the owner answered "yes", and the jobs below replace it.
- **`version` builds the version commit without a write token.** On a push to `main` whose plan asks for a version, the `version` job checks out the newest `main` with full history and no persisted credentials, installs the root's devDependencies and runs `pnpm changeset version`. Its only token is the run's `GITHUB_TOKEN` with `contents: read`, and no step sets an environment variable. Because Changesets could append its own `base=` line to its step's output file, an earlier step records the starting commit before pnpm is set up. It uploads the change as a patch (`git diff --cached --binary --no-renames`) with the commit it started from, for one day. When Changesets changes nothing, the job says so and the next job is skipped.
- **`version-pr` checks the commit, then recreates it through GitHub's API with the release token.** This job runs no third-party code: no pnpm, no npx and nothing from `node_modules`. Its only actions are `actions/checkout` and `actions/download-artifact`. It checks out `main` with full history, refuses a base that isn't a commit on `main`, and checks out the base. Then it applies the patch to the index alone and commits it, so the working tree stays at the base commit. As a result, `scripts/ci/version-pr.mjs`, which imports only `node:` modules and the two scripts beside it, runs as `main` holds it, never as the patch rewrote it. It checks the commit and writes the pull request's title and body. Only after that check passes does the last step receive `RELEASE_PR_TOKEN`. That step runs `gh` and `scripts/ci/version-commit.mjs`, which imports only `node:` modules and `version-pr.mjs`, and which runs from the base's working tree. The script makes the checked commit again through GitHub's API, as the next item explains, and force-updates `changeset-release/main` to it; the only other branch it writes is its own staging branch. The step then opens the pull request against `main` or updates the open one. Next it reads `main`'s branch protection and fails, leaving auto-merge off, unless `main` requires the `checks` status. gh 2.89.0 merges at once instead of turning on auto-merge when nothing blocks the merge (`isImmediatelyMergeable` in `pkg/cmd/pr/merge/merge.go`), so without that requirement the pull request would merge before CI ran. Last, it runs `gh pr merge --auto --squash` unless auto-merge is already on. The script leaves the branch alone when it already holds a verified commit with the same tree on the same base, so a rerun doesn't restart the checks.
- **GitHub signs the version commit, because the API makes it (added 2026-11-19).** `main`'s ruleset requires signed commits, and GitHub applies that rule to every commit a pull request brings, so an unsigned head commit blocks even a squash merge ([rulesets docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-signed-commits)). The first Version packages pull request, #70, hit that rule: `git push` had put an unsigned commit on its branch, and GitHub reported "Commits must have verified signatures". GraphQL's `createCommitOnBranch` fixes this without a GitHub App. GitHub's docs say its commits "are automatically signed by GitHub if supported and will be marked as verified", authored by the token's owner, and that the mutation takes no author or committer ([GraphQL reference](https://docs.github.com/en/graphql/reference/commits#mutation-createcommitonbranch)). The REST git data API is no alternative: GitHub promises a signature for its commits only when a GitHub App or bot makes the request with no custom author or committer ([commit signature docs](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification#signature-verification-for-bots)). So `version-commit.mjs` turns the checked diff into the mutation's `fileChanges`: each added or edited file is an addition with its contents in base64, each deleted file a deletion, and a changeset moved into `.changeset/pre/` both. The mutation appends to a branch's head, so the commit can't be made on `changeset-release/main` without first moving that branch back to the base, which would leave the open pull request with no commits for a moment. GitHub's docs don't say what it does with such a pull request, so the script instead points a separate branch, `changeset-release/staging`, at the base and commits there. It then reads the new commit through REST and fails, leaving `changeset-release/main` as it was, unless `verification.verified` is true, the tree equals the checked commit's tree and the only parent is the base. Only then does it force-update `changeset-release/main` to the commit. It deletes the staging branch whether or not the commit passed, even when creating that branch failed. Neither the guard nor any other release step creates a commit: the guard only turns auto-merge off, and GitHub makes the squash commit, which it signs. `sdk-updates.yml` now makes its harness update commits the same way, each on its own staging branch (§3c).
- **A version commit may change only versions.** The check reuses the changeset gate's bump rule (§3e): every versioned package's `package.json` changes in `version` alone, all to one later version that fits the pre mode, each with a `CHANGELOG.md` section for it. Beyond those files, the commit may only delete pending top-level changesets, move them unchanged into `.changeset/pre/` in pre mode, and, on leaving pre mode, delete `pre.json` and the changesets in `pre/`. Every file it adds or edits must be a regular, non-executable file. The check refuses everything else, such as a `src/` edit, a workflow, the lockfile or a dependency, so a compromised Changesets dependency can't reach `main` through the token. The versioned packages are read from the base commit, so the commit can't add or unhide one.
- **Why a dedicated token.** GitHub's docs say that events a workflow causes with `GITHUB_TOKEN` "will not create a new workflow run", except `workflow_dispatch` and `repository_dispatch`, and that a pull request it creates or updates gets `pull_request` runs that wait for approval. They recommend "a GitHub App installation access token or a personal access token instead of `GITHUB_TOKEN`" so that those runs start on their own (github/docs at [`39c1e01`](https://github.com/github/docs/blob/39c1e014c75e972ab1fe531a81bc5bd42b543b07/data/reusables/actions/actions-do-not-trigger-workflows.md), the [`GITHUB_TOKEN` page](https://github.com/github/docs/blob/39c1e014c75e972ab1fe531a81bc5bd42b543b07/content/actions/concepts/security/github_token.md); docs.github.com was out of this session's network). With `RELEASE_PR_TOKEN`, `ci.yml` runs on the pull request, so the required `checks` status reports and auto-merge can finish.
- **The squash merge should start `release.yml`.** Auto-merge "merges a pull request automatically after all required reviews and status checks pass" ([github/docs](https://github.com/github/docs/blob/39c1e014c75e972ab1fe531a81bc5bd42b543b07/content/pull-requests/how-tos/merge-and-close-pull-requests/automatically-merging-a-pull-request.md)). The token that enabled auto-merge belongs to the owner, not to `GITHUB_TOKEN`, so the rule that suppresses runs shouldn't apply to the merge's push. GitHub's docs don't state outright which account a merge made by auto-merge counts as (unverified: inferred from the rule above). docs.github.com loaded on a second try on 2026-11-19, and its live auto-merge and `GITHUB_TOKEN` pages still don't say. The first Version packages merge settles it: its `release` run should show the owner under "pushed by". If no run starts, the release is late, not lost: the plan publishes any version on `main` that has no GitHub release, so the next push to `main` publishes it. A `workflow_run` trigger on `ci.yml` wouldn't help, because the same rule would suppress `ci.yml`'s push run. The fix would then be a `workflow_dispatch` sent from the `version-pr` job, which GitHub always runs, with `release.yml` changed to publish from such a dispatch.
- **Several changesets batch into one alpha.** Every changeset merged to `main` starts a release run, which rebuilds the version commit from the newest `main` and force-updates the same pull request. So the pull request holds every changeset merged before GitHub merges it, and in pre mode they share one prerelease number. If GitHub merges the pull request before a waiting run has updated the branch, the merge reaches `main` with that newer changeset pending, so its run publishes nothing and opens the next Version packages pull request instead. That pull request moves the packages one prerelease further, and the version the first one merged is never published.
- **The guard lets only this pull request auto-merge.** `.github/workflows/auto-merge-guard.yml` runs on `pull_request_target` with the `auto_merge_enabled` activity type, which GitHub lists for that event ([github/docs](https://github.com/github/docs/blob/39c1e014c75e972ab1fe531a81bc5bd42b543b07/content/actions/reference/workflows-and-actions/events-that-trigger-workflows.md#pull_request_target)). It turns auto-merge off with `gh pr merge --disable-auto` unless the head is `changeset-release/main` in this repository, the base is `main`, and the change passes the same version-commit check. Auto-merge stays on when someone with write access pushes to the head branch or changes the base, so the guard also checks a pull request with auto-merge on at each `synchronize`, `edited` and `reopened` event. Each run checks the head commit its event names, because `refs/pull/<n>/head` can lag behind a push. The checking job holds only `GITHUB_TOKEN` with `contents: read`. It checks out `main`, the default ref for that event, fetches the pull request's head only to read it with `git`, and passes pull request fields through environment variables. A second job turns auto-merge off on anything but a clear "keep", a failed check included. GitHub lets "people with write permissions to a repository and pull request authors" turn auto-merge off ([docs.github.com](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/automatically-merging-a-pull-request#disabling-auto-merge)), and GitHub's own example turns it on with `contents: write` and `pull-requests: write`. So that job has both, checks nothing out and runs only `gh`. Its job summary, and the checking job's, name the rule that decided. Auto-merge turned on with `GITHUB_TOKEN` starts no guard run, for the reason above; no workflow here does that.
- **The version commit can't loop.** The squash commit of a Version packages pull request leaves no changeset pending, so its release run plans a publish, not a version. The pull request's own commit carries no `[skip ci]`, because `ci.yml` must run on it, and the changeset gate passes it as a version bump (§3e).
- **Quick merges batch, never cancel.** The workflow's `release-push` concurrency group runs one release at a time and never cancels a running one. GitHub keeps one more run pending and cancels an older pending run ([GitHub docs](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)). That loses nothing, because the version job versions the newest `main`, so the run that waited last includes every changeset merged before it. A `workflow_dispatch` dry run waits in its own group, `release-workflow_dispatch`, so it can't cancel a pending push run.
- **Provenance names the merge commit.** The tarballs come from the squash commit, which is the run's own commit, so npm's provenance and the GitHub release name the same commit.
- **A dry run on demand.** A `workflow_dispatch` runs only `plan` and `pack`, because `version` and `publish` require a push to `main`, `version-pr` needs `version`, and `docs` needs `publish`. The pack job's summary lists each tarball's files, and a dry run's summary also names each tarball with its package's own version, since a dry run may pack mixed versions. The first dry run, from the L3 branch, built and packed both packages at 0.0.0, and the plan reported both as still private ([run 44502245024](https://github.com/laudebugs/buildanagent/actions/runs/44502245024)). The first dry run on `main`, on 2026-11-19, ran `plan` and `pack`, and skipped L3's `version-pr` job, `publish` and `docs` ([run 44505430717](https://github.com/laudebugs/buildanagent/actions/runs/44505430717)). The push to `main` that merged L3 ran only `plan` and published nothing ([run 44505312929](https://github.com/laudebugs/buildanagent/actions/runs/44505312929)).
- **No caching, and no new actions.** No job uses a dependency cache, following npm's advice to "never use caching in release builds". The workflow uses the five actions `sdk-updates.yml` already locks, and `actions.lock` gains a `release.yml` entry for them; each tag's commit was rechecked with `git ls-remote`. The guard uses only `actions/checkout`, so its `actions.lock` entry adds no new commit.
- **Tests.** `scripts/ci/release.test.mjs` parses `release.yml`. It fails if any step but the `version-pr` job's last one reads a secret, if that secret isn't `RELEASE_PR_TOKEN`, or if a job sets a token variable other than `GH_TOKEN`. It also fails if a job leaves out its own permissions, if any job but `publish` can mint an OIDC token or write, or if a `run:` step expands a `${{ }}` expression. For the version jobs, it fails if the `version` job holds a token or pushes, or if the `version-pr` job mentions pnpm, npx, npm or `node_modules`, uses an action other than checkout and download-artifact, or runs node with the token on anything but `version-commit.mjs`, or pushes with `git`. It fails, too, if `version-pr.mjs` or `version-commit.mjs` imports anything but `node:` modules and the scripts beside it. For the publish job, it fails if the job loses its environment, permissions, push-to-`main` condition, exact npm version or `--tag`. It checks that the token guard prints only names, that the tag step tags the packed commit, marks prereleases and peels annotated tags, and that the artifact is kept 30 days. It also runs the workflow's own scripts against a local bare repository with stand-in `pnpm` and `gh` commands; the stand-in `gh` answers the ref, commit and `createCommitOnBranch` calls from that repository and marks only commits made through the mutation as verified. Those runs check that no token reaches Changesets, that a merged changeset opens the pull request with auto-merge and leaves `main` alone, that a later changeset updates the same pull request and that a rerun changes nothing. They check, too, that an unsigned commit with the right tree, as on #70, is replaced by a verified one, and that an unverified new commit fails the step before the branch or the pull request changes. `scripts/ci/version-commit.test.mjs` tests the script against a scripted `gh`: how it expresses additions, edits, deletions and moves, the order of its API calls, and each way the new commit can fail its check. They also check that a patch that edits `src/` or rewrites the check itself is refused before any push, that the version job's base can't be forged through Changesets' output file or point off `main`, that auto-merge stays off while `main` doesn't require `checks`, that empty changesets get their own title, and that the publish job's check refuses a version `main` has moved past. `release.test.mjs` also tests the plan's decisions against a stubbed npm registry and GitHub API, including a release that npm holds but GitHub lacks, each pre-mode pairing and the plan this checkout gives on `main`.
- **Tests of the version-commit check, the guard and the tarballs.** `scripts/ci/version-pr.test.mjs` tests the version-commit check case by case and runs the guard's decide step for real, including on an event whose head commit `refs/pull/<n>/head` hasn't reached yet. **How the deploys work.**

- **Six workflows.** `docs-build.yml` and `site-build.yml` run on pull requests and on pushes to `main`. They build with no secrets and no path filter, because TypeDoc and the site read every package's source and a filter that missed a file would skip a pull request that changes it. Each uploads `apps/<app>/dist/` as its only artifact (`docs-dist`, `site-dist`), kept 7 days. `docs-deploy.yml` and `site-deploy.yml` run on `workflow_run` after their build or after their pr-closed workflow, so GitHub runs them from the file on `main`, and a pull request that edits one changes nothing until it merges. `docs-pr-closed.yml` and `site-pr-closed.yml` copy the book's `book-pr-closed.yml`: they run on `pull_request: [closed]`, hold no secret, check nothing out and use no action, and their run only starts `main`'s deploy workflow, so the job that deletes a preview always runs from `main`'s file. `docs-deploy.yml` also takes a `workflow_dispatch` with a `tag` input for DS4.
- **One GitHub environment, `cloudflare`, where the book has two.** The owner created it with deployment branches limited to `main` and the secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. The book keeps a preview token apart from a production token, but Cloudflare's roles page lists no role for previews alone ([Workers roles](https://developers.cloudflare.com/workers/authorization/workers/)). The book infers from this that a preview token could deploy production anyway; no session has tested that. The token's holder can therefore deploy production, so the controls that matter are the ones below: no job runs a pull request's code, and only `main`'s workflow files can name the environment.
- **A pull request's code never runs with the token.** The deploy jobs check out `main`, never the pull request. From the build run they take only the artifact, which `scripts/ci/site-stage-dist.mjs` checks before anything uses it, and the head commit's SHA. The pull request's number comes from `GET /repos/{repo}/commits/{sha}/pulls`, kept to open pull requests whose head is that SHA and whose head and base repositories are both this one, never from the artifact. A closed pull request's number comes from the recently closed pull requests (`GET /repos/{repo}/pulls?state=closed`), kept the same way, because the commits endpoint omits closed, unmerged pull requests. The head repository's name is checked against an `owner/name` pattern before anything compares it, and every value reaches `jq` through `--arg`, never inside the filter's text. Production needs `head_repository.full_name == github.repository` too, so a fork's branch named `main` gets no production deploy.
- **Seven jobs in `site-deploy.yml`, nine in `docs-deploy.yml`.** The docs add `next` and `build-release`. Five rules shape them:
  - **`resolve` picks one target and holds no Cloudflare secret.** The target is production, next, release, previews, deletions or none, decided through the API. `secrets` is the only job that checks whether both secrets exist. When one is missing it leaves a notice, not a failure: a job-level `if` cannot read secrets, and the workflows can then merge before the owner's setup is done.
  - **`production` and `next` check twice that the push is still `main`'s newest commit.** A late build must never replace a newer one. `resolve` checks when it runs, and the docs' `production` and `next` jobs and the website's `production` job check again in the step "Check that this commit is still main's newest", just before `Deploy`. That step holds no Cloudflare secret and skips `Deploy` with a notice when `main` has moved on. The second check matters because jobs can start late, for example after an approval.
  - **The docs' push-path `production` deploy checks for a release that deployed during its window.** The window opens in the step "Check that no stable release exists yet", which records the time minus 60 seconds, and closes in the step "Record when the deploy ended", which records the end of `Deploy` plus 60 seconds; the 60 seconds allow for clock skew. The step "Check that no release deployed during this deploy" then runs when `Deploy` succeeded and a stable tag exists. It reads `docs-deploy.yml`'s dispatched runs, including any still in progress. A release `Deploy` step that succeeded inside the window is an error, because the push's deploy may have replaced it. One that finished after the window passes with a notice, because the release is then live, which is the correct order. The API does not show a dispatch's inputs, so any dispatched release deploy counts: a false alarm is possible, a miss is not. The job's and step's names reach the script through `JOB_NAME` and `STEP_NAME`, and a test pins them to the real names, so a rename fails the test instead of turning the check off. `production` and, for the docs, `next` deploy with `wrangler deploy`.
  - **A preview job deletes its own preview when its pull request has closed.** `preview` runs `wrangler preview --name pr-<number>` once for each pull request and records the preview's URLs in an artifact. Before it deploys, the step "Check that the pull request is still open at this commit" has no Cloudflare secret and reads the pull request through `pull-requests: read`. Unless the pull request is open, at this commit and from this repository, the job skips the deploy and the URL record with a notice. When it finds the pull request closed in this repository, it deletes the preview itself, with the script the `delete-preview` job runs (the file shares it through the YAML anchor `&delete-preview`), because GitHub cancels a waiting job when a newer one joins its concurrency group, so a waiting deletion may never run. `delete-preview` checks that the number is an integer, then runs `wrangler preview delete --config wrangler.toml [--env ""] --name pr-<number> --skip-confirmation` (the `--env ""` is the docs' only). It warns and does not fail when the preview was never deployed, and records a deletion only when it worked.
  - **The comment jobs hold only `pull-requests: write`.** `comment` and `comment-deleted` hold no Cloudflare secret and check nothing out. They keep one comment per pull request, written only while the pull request is from this repository with that commit as its head (open for a preview, closed for a deletion), and take a URL only after checking its exact form against the Worker's name.
- **The stage and guard scripts decide what a deploy may hold.** `scripts/ci/site-stage-dist.mjs` reads the zip artifact itself and reuses the book's checks from `apps/manual/scripts/stage-dist.mjs`: an unsafe name, a link or special file, a name Cloudflare's asset server reads as configuration, a broken or oversized entry or a missing required page refuses the whole artifact before anything is written. L8 added a `required` option to that module's `readEntries`, so the docs require `index.html` and `404.html` and the website, which has no `404.html`, only `index.html`. The artifact's own `_headers` is never written. With `--noindex`, the script writes `X-Robots-Tag: noindex` for every path, because Cloudflare adds that header to `workers.dev` preview URLs but not to a custom domain such as `next.docs.buildanagent.fyi` ([Cloudflare Previews](https://developers.cloudflare.com/workers/previews/), [`_headers` rules](https://developers.cloudflare.com/workers/static-assets/headers/)). `scripts/ci/site-guard-deploy.mjs` then compares the significant lines of the app's `wrangler.toml` (blank lines and whole-line comments removed) with an `EXPECTED` list, in order, and refuses any difference. It parses no TOML, so it cannot read the file differently from Wrangler, and a change to a site's config changes `EXPECTED` in the same commit. It also refuses another Wrangler config or deploy redirect above the app, and a `dist/_headers` that differs from what the stage script writes. `scripts/ci/site-deploy.test.mjs` tests both scripts offline.

Cloudflare's docs say `workers_dev` defaults to `true` only when the configuration has no route, that `preview_urls` "Enables Version URLs and `workers.dev` Preview URLs" and starts from `workers_dev`'s value when no setting exists, and that `wrangler preview` needs the `previews` block, which may be empty ([Wrangler configuration](https://developers.cloudflare.com/workers/wrangler/configuration/), [Preview URLs](https://developers.cloudflare.com/workers/configuration/previews/), [Previews configuration](https://developers.cloudflare.com/workers/previews/configuration/)). The docs file adds `[env.next]`, a second Worker, `buildanagent-docs-next`, on `next.docs.buildanagent.fyi` with `preview_urls = false`. It was published 2026-11-11, is licensed MIT OR Apache-2.0 and has no install scripts. 4.162.0, from 2026-11-13, is the newest release at least a week old as of 2026-11-22, and Previews need 4.135.0 or later.

- **DS4's version policy, in `docs-deploy.yml`.** After a successful `docs-build`, a push to `main` deploys `docs.buildanagent.fyi` while no stable release tag exists and `next.docs.buildanagent.fyi` once one does. Four rules carry it:

The push-path `production` job checks the tags again just before `wrangler deploy` and skips with a notice if a stable tag now exists, because then the release's deploy owns `docs.buildanagent.fyi`. The release-window check above covers the case where the tag arrives mid-deploy.
  - **A dispatch's tag is validated before any build.** The `tag` input must match the pattern, at most six digits per part, before any API call. The tag must exist (an annotated tag is followed once to its commit) and `compare/{sha}...main` must say `identical` or `ahead`.

The legacy Workers Scripts Edit permission maps to Editor at the Workers product scope, and Editor "Cannot create or delete Workers"; product-level Admin can. The page names no DNS permission, and the custom-domains page says "Cloudflare will create DNS records and issue necessary certificates on your behalf" ([Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/)). Our reading that the first deploy needs no DNS permission rests on the docs' silence, so the first deploy checks it.

It checks that every job sets its own permissions and runs on the pinned runner, that no `run:` step expands a `${{ }}` expression, that only jobs in the `cloudflare` environment read a secret and each waits for the `secrets` job, and that those jobs check out only `main`, persist no credentials and hold no write permission. It compares every job's `if:` exactly, checks that `comment` and `comment-deleted` hold only `pull-requests: write`, that the pr-closed files hold no secret, permission, checkout or action, and that every action is in `actions.lock`. It also runs the record, delete and comment scripts against the stand-in and crafted files, pins the release check's job and step names, and covers a preview job that finds its pull request closed.

**Documented limits.**

1. One `cloudflare` environment and token serve previews and production alike. The artifact check, and the `wrangler.toml` and scripts that come from `main`, limit the harm. Cloudflare's roles page lists no role for previews alone, and the book infers from this that a preview token could deploy production.
2. Only `next.docs.buildanagent.fyi` is `noindex`; it shows no visible "unreleased" banner, which needs a change to the docs app.
3. The build workflows' concurrency cannot stop a fork's pull request from naming `main`'s group with `cancel-in-progress`, because GitHub gives the fork's copy of the file control of the group. That can cancel a running build of `main`, which then deploys nothing until the next push. The control is the repository's fork-approval setting (checklist item 7), and the book's build has the same exposure.
4. A pull request that closes in the seconds between the "still open" check and `wrangler preview` can still leave a preview behind, because the deletion run may finish first.
5. The `secrets` job names `environment: cloudflare`, so each preview or deletion run records a second deployment on the pull request, one with no URL, and if the owner adds required reviewers to the environment, every deploy needs two approvals. The book's `*check-secrets` step avoids that; L8 chose the job pattern so that a missing secret is a notice.

It didn't: `package.json`'s `engines` names only `node: ">=22"`, and [ADR 0033](../decisions/0033-three-deployment-targets.md) fixes four deployment targets, local Node, Cloudflare, AWS and Vercel, with Bun named as a candidate for none of them. [`runtime-portability.md`](../research/deployment/notes/runtime-portability.md) had already profiled Bun on paper: strong Node compatibility, a real subprocess API. The portable-agents report's recommendation 7 went further, proposing to type the stdio transport over Web streams so "Deno, Bun and Workers" could reuse it later. Neither had ever run the code. X6 measured whether our own code runs under Bun today, without deciding to add it as a target (that needs its own ADR, since 0033 closed the list) or to allow it as a package manager (AGENTS.md keeps pnpm only).

**Method.** `pnpm install` still manages dependencies. Bun 1.4.4 (published 2026-10-22, pinned in `.bun-version`) then runs the already-installed code in Node's place: `bun --bun x tsc` for a typecheck, `bun --bun x vitest run` for a package's tests, `bun scripts/<file>.mjs` for a harness's own scripts, and `bun test` for a `node:test` file. (Its own CLI, not `node --test`'s flag, is what runs one — `bun --test <file>` fails outright, `Cannot use test outside of the test runner`.) Node here is v24.19.0, not `.nvmrc`'s pinned 22, since that is what this machine runs; the comparison is Bun 1.4.4 against Node 24.19.0, not against the pinned minimum. Every result was cross-checked against the same command under Node on the same machine, so a failure that already happens under Node is not counted as Bun's.

**A first pass used `bun x` without `--bun`, which runs a tool through its own `#!/usr/bin/env node` shebang under Node, not Bun; that pass's "all clean" claim for the packages and `apps/manual` was wrong, because it had measured Node twice. The numbers below are the corrected, `--bun`-forced run.** `bun test`, which is Bun's own test runner rather than a shebang-launched tool, was unaffected by this mistake; its findings stood.

**Nine real gaps, each confirmed absent under Node on the same run, several of them touching many tests at once:**

1. **Miniflare (Cloudflare's local Workers simulator) doesn't work under Bun, and this is the largest gap by test count.** `verify/cloudflare-agents`: all 13 examples return `ECONNREFUSED`. `agent-safety`'s Cloudflare- and workerd-backed tests (`test/stores/cloudflare.test.ts`, `cloudflare-approval.test.ts`, `cloudflare-interrupted.test.ts`, `cloudflare-cost-guard.test.ts`, `workerd-suite.test.ts`): 28 of its 28 failures. `harness/test/cloudflare/cloudflare.test.ts`: 1 failure. Not root-caused beyond this: Miniflare most likely spawns or dials `workerd` in a way Bun's networking or child-process layer doesn't yet support the way Node's does.
2. **Bun has no `module.registerHooks`.** `scripts/transcripts/source-condition.mjs` calls it, and every test that goes through that module fails with `SyntaxError: Export named 'registerHooks' not found in module 'node:module'`. This breaks `sdk/test/book-examples.test.ts` in full and at least `gateway/test/book-examples.test.ts`'s four cases; `harness`'s 7 `book-examples.test.ts` failures are almost certainly the same cause, not separately confirmed.
3. **`@earendil-works/pi-schema` doesn't resolve under Bun's handling of the workspace's `source` export condition.** `sdk/test/workerd-validator.test.ts` (a whole suite) and `cli/test/bin.test.ts` both fail with `Cannot find package '@earendil-works/pi-schema'` or `Cannot find module` for it, resolving fine under Node.
4. **`tsx`'s loader doesn't register under Bun.** `scripts/ci/catalog-staleness.test.mjs` fails to even start, `Cannot find module 'tsx://...'`, because `tsx` hooks into Node's own loader API and Bun ships its own, separate TypeScript loading that doesn't recognize `tsx`'s scheme. [X10](../todos/done/X10-bun-tsx-loader.md) fixed this on 2026-11-26. The test now imports `packages/gateway/src/catalog.ts` with a plain `import()` when `process.versions.bun` is set, and loads `tsx/esm/api` only under Node. Under Bun 1.4.4 that plain import loads the source with no loader, though the source's relative imports use `.js` specifiers. `node --test scripts/ci/catalog-staleness.test.mjs` passes 6 of 6, and so does `bun test` in three runs. Two other test files in `scripts/ci/` use `tsx`, and neither calls `tsImport`, so this fix doesn't touch them. `transcripts.test.mjs` passes `--import tsx` to a spawned `node`, and `live-run.test.mjs` resolves `tsx` to run child processes.
5. **A subprocess spawned with an allowlisted environment can't find `node` on `PATH`.** `protocol/test/package.test.ts` spawns `tsc` through `execFileSync` with the allowlisted environment AGENTS.md's "Running third-party code" rule asks for; under Bun the spawned shell reports `exec: node: not found`, so `tsc`'s own `#!/usr/bin/env node` shebang has nothing to run. Not root-caused further.
6. **`node:assert`'s `throws(fn, message)` rejects an empty message, and the test it breaks was already not checking what it claims to.** `scripts/ci/sdk-updates.test.mjs` calls `assert.throws(fn, bad)` for several `bad` inputs including `""`; Bun's shim throws `The argument 'error' may not be an empty object. Received ''`, where Node accepts an empty string as a plain failure message, not as an expected-error matcher. That same reading means the assertion was never actually checking what `parseBumps` threw for any of its cases, under either runtime; the `""` case only surfaces that, it doesn't cause it. X12 fixed this on 2026-11-26. The test now asserts each thrown error's exact message: `no bumps were planned` for the empty input and `<input> isn't a planned bump` for the other five. `sdk-updates.test.mjs` passes under Bun 1.4.4, 98 of 98 in seven runs. One further run failed (97 of 98) while two review agents ran the same suite in the same worktree; later runs all passed.
7. **A directory listing comes back in a different, equally valid order.** `scripts/ci/changeset-gate.test.mjs` asserts `versionedPackageDirs()`'s result against an explicitly sorted list; the function itself calls bare `readdirSync` with no `.sort()` of its own. Every real caller of `versionedPackageDirs()` is order-insensitive (`.some`, `.filter`, a `Set`), so this is not a behavior bug in `changeset-gate.mjs`, only a fragile exact-order assertion in its test.
8. **Bun's transpiler mangles a literal ✅ inside a `String.raw` template literal, in test source code, not in product code.** `scripts/ci/fact-check-log.test.mjs`'s two failures both come from fixtures written as `` String.raw`...✅...` ``; Bun rewrites the non-ASCII character before `String.raw` sees it, so the fixture's own text becomes the six characters `\u2705` instead of the real ✅. `fact-check-log.mjs`'s `cells()` function is not involved and behaves identically on both runtimes; only the test file's own fixtures would need rewriting to avoid the pattern. [X13](../todos/done/X13-fact-check-log-string-raw-fixture.md) fixed this on 2026-11-26. The two fixtures in `fact-check-log.test.mjs`, now at lines 92 and 103, are ordinary double-quoted strings with doubled backslashes, each equal to its old value under Node, and the file passes 24 of 24 under both `node --test` and `bun test`. The measured evidence covers ✅, – and —, not every non-ASCII character. `fact-check-log.mjs`'s `RANGE_SEP` (line 45) uses the same pattern, and Bun rewrites its dashes too. `RegExp` reads the escapes as the same dashes, so `RANGE_SEP` works; but it works only while its string goes to `RegExp`, so the pattern is fragile, not wrong.
9. **`scripts/ci/live-run.test.mjs` has 5 confirmed Bun-only failures, 2 pre-existing, and a separate, pre-existing hang under Node.** Under Bun it runs in about 4 seconds: 43 pass, 7 fail. Under Node it finishes all 50 tests quickly too (48 pass, 2 fail) but then the process itself hangs for roughly 7 minutes before exiting with "Promise resolution is still pending but the event loop has already resolved" — a pre-existing bug in the test's own async handling, unrelated to Bun, which is why the first pass of this measurement never got a clean comparison and called the finding unconfirmed. Of the 7 Bun failures, 2 need Linux's `unshare -rn` (the same requirement as `copilot-sdk`) and fail under Node too; the other 5 are real, net-new Bun gaps, not yet individually root-caused beyond overlapping with findings 1 and 2 above.

**`harness`'s other ~26 failures** (`test/server/stdio.test.ts`, `test/mcp/hardening.test.ts`, `test/server/framing-interop.test.ts`, several `*-second-process.test.ts` files, `test/sandbox/none.test.ts`, `test/extensions/skills.test.ts`, `test/capstone.test.ts`) are not individually root-caused here; some are likely instances of findings 1 or 2, some may be new. The jump from 104 to 160 skipped tests under Bun suggests at least one test file's `describe`/setup itself throws before its cases register, hiding further failures that a `skip` count alone doesn't show.

**Proposed, for the owner (none applied):**

1. Keep Bun unsupported. The gaps are not small: the two biggest, Miniflare/workerd and `module.registerHooks`, touch every published package that has Cloudflare-backed tests or book examples, which is most of them.
2. If Bun support is wanted later, it needs real investigation, not a quick fix. The owner approved splitting it into one todo per gap, chasing each on its own rather than as one large effort: [X7](../todos/ready/X7-bun-miniflare-workerd.md) (Miniflare/workerd), [X8](../todos/ready/X8-bun-module-registerhooks.md) (`module.registerHooks`), [X9](../todos/ready/X9-bun-pi-schema-resolution.md) (`pi-schema` resolution), [X10](../todos/done/X10-bun-tsx-loader.md) (the `tsx` loader), [X11](../todos/ready/X11-bun-allowlisted-path-node.md) (the allowlisted-`PATH` gap in `protocol`), [X12](../todos/done/X12-sdk-updates-assertion-bug.md) (`sdk-updates`'s real assertion bug), [X13](../todos/done/X13-fact-check-log-string-raw-fixture.md) (the `fact-check-log.test.mjs` fixture rewrite), [X14](../todos/ready/X14-harness-unresolved-bun-failures.md) (`harness`'s remaining ~26 failures), and [X15](../todos/ready/X15-live-run-bun-failures.md) (`live-run.test.mjs`'s 5 confirmed failures, not yet individually root-caused).
3. A Bun CI job is not realistic until most of the above lands; as measured, it would fail across all six published packages.
