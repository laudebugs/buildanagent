# Fact-check: the Vercel Sandbox backend

This log checks the claims that `packages/harness/src/sandbox/vercel/`, the harness README's Vercel section, the changeset and todo N48b's outcome make on 2026-11-25. The primary sources are the pinned `@vercel/sandbox` 3.9.1 package as installed in `packages/harness/node_modules/@vercel/sandbox/` (its `dist/*.d.ts` and `dist/*.js`), the npm registry for versions and dates, and Vercel's Sandbox docs, fetched as Markdown with `curl -L` on 2026-11-25 (each page's `.md` form, such as `https://vercel.com/docs/vercel-sandbox/concepts/firewall.md`, which redirects to `/docs/sandbox/…`). The first draft of this log marked the claims only those docs could settle ⚠️ because vercel.com was unreachable; once it was reachable, rows N48b-5, N48b-13 to N48b-17, N48b-31 and N48b-32 were settled or narrowed against the pages, and rows N48b-38 to N48b-45 record what the pages changed in the code and docs. A claim no page or package source settles stays ⚠️ for the owner's live run (`scripts/vercel-live.ts`).

Legend: ✅ confirmed · ✏️ corrected while drafting · ⚠️ unverified or our own inference.

## The network policy

| N48b-8 | A rule's `transform` sets headers on a matching request, and a rule may `match` on method, path, query string and headers | ✅ | `dist/network-policy.d.ts`, `NetworkTransformer` ("Headers to set on the outgoing request") and `NetworkPolicyMatch` |
| N48b-9 | Rules run in declaration order, a trailing `response` rule with no `match` answers whatever the earlier rules did not claim, and allowing a domain otherwise allows every request to it | ✅ | `dist/network-policy.d.ts`, `NetworkPolicyResponse` and the `response` member of `NetworkPolicyRule` |
| N48b-10 | A rule holds exactly one of `transform`, `forwardURL` and `response` | ✅ | `dist/api-client/validators.js`, `NetworkPolicyRuleValidator` refinements |
| N48b-11 | `subnets.allow` traffic bypasses the domain allowlist, and `subnets.deny` takes precedence over allowed domains and ranges | ✅ | `dist/network-policy.d.ts`: "Traffic to these addresses will bypass the domain allowlist" and "These take precedence over allowed domains and CIDRs" |
| N48b-12 | Vercel reports a sandbox's policy with each injected header's name and its value replaced by `<redacted>`, and the reported form carries no `response` rule | ✅ | `dist/utils/network-policy.js`, `fromAPINetworkPolicy()`, which builds headers from `headerNames` only; the response schema `LegacyCustomNetworkPolicyValidator` in `dist/api-client/validators.js` has `injectionRules` and `forwardRules` and no response rules |
| N48b-13 | A request that matches a `transform` rule leaves the VM with the rule's header, replacing one the process set | ✅ | [Vercel Sandbox firewall](https://vercel.com/docs/sandbox/concepts/firewall), "HTTP and HTTPS": a `transform` rule that sets `Host` means "the header is rewritten before the request leaves the sandbox, so every request that reaches the destination carries the hostname you allowed regardless of the `Host` header the client sent"; "Credentials brokering" example sets `Authorization` the same way |
| N48b-14 | The firewall matches names by TLS SNI, terminates TLS only for a domain with a transformation, forwarding or direct-response rule, and does so with a per-sandbox CA | ✅ | [Vercel Sandbox firewall](https://vercel.com/docs/sandbox/concepts/firewall), "HTTP and HTTPS" ("HTTPS traffic is matched using the SNI"; "The firewall terminates TLS only for domains with transformation, forwarding, or direct-response rules") and "TLS termination" ("A unique, per-sandbox CA is added to the system certificates") |
| N48b-15 | The firewall applies the first rule a request matches, so a second route on one host could not be told apart | ✅ | [Vercel Sandbox firewall](https://vercel.com/docs/sandbox/concepts/firewall), "Matchers": "When multiple rules target the same domain, the firewall evaluates them in order and the first match wins"; "Direct responses": "The first matching rule handles each request" |
| N48b-16 | The firewall matches a host by name and has no port dimension, so the backend refuses an allow entry with a port rather than let it widen to every port | ✅ | [Vercel Sandbox firewall](https://vercel.com/docs/sandbox/concepts/firewall), "Supported protocols": "Domain-based rules identify traffic by the hostname negotiated during the TLS handshake"; the domain-pattern table and `dist/network-policy.d.ts` have no port field. The refusal itself is our design |
| N48b-17 | Denied ranges take precedence over allowed domains, and denying the ranges in `VERCEL_DENIED_SUBNETS` doesn't stop an allowed name from resolving or being reached | ⚠️ | The precedence is confirmed: [Vercel Sandbox firewall](https://vercel.com/docs/sandbox/concepts/firewall), "User-defined": "Denied ranges take precedence over allowed domains and address ranges, but only remove access that an allow rule already granted". That the ranges leave DNS and the allowed hosts working is not on any page; the live run's "an allowed host is reached" check runs with them denied |
| N48b-48 | The per-sandbox CA the firewall uses for interception is added to the VM's system certificates, so every program in the sandbox trusts it | ✅ | [Vercel Sandbox firewall](https://vercel.com/docs/sandbox/concepts/firewall), fetched 2026-11-25: "A unique, per-sandbox CA is added to the system certificates. Standard environment variables are configured automatically to ensure compatibility with most clients" |
| N48b-50 | Denying `::ffff:0:0/96` keeps an allowed name whose AAAA record wraps a denied IPv4 address from being reached, and Vercel accepts the range | ⚠️ | Our own inference, matching the local proxy's rule in `src/credentials/addresses.ts`, which refuses an IPv6 address that wraps a refused IPv4 one. The [firewall page](https://vercel.com/docs/sandbox/concepts/firewall) gives IPv6 ranges no rule of their own and says nothing of mapped addresses; the live run's "an allowed host is reached" check runs with the range denied |
| N48b-51 | Vercel's read-back is incomplete, so it can't show the trailing 403 rule; the backend also refuses a reported `forwardURL` rule | ✅ | [Vercel Sandbox firewall](https://vercel.com/docs/sandbox/concepts/firewall), "Updating policies": "policy readback is sanitized and incomplete, so it cannot reconstruct the policy you supplied"; `dist/utils/network-policy.js`, `fromAPINetworkPolicy()`, rebuilds `injectionRules` and `forwardRules` only; `readBackHosts()` and the test "a reported forwarding rule fails the read-back" |
| N48b-52 | The owner decided on 2026-11-25 that a sandbox holds no credentials by default and authenticated actions run as host-side tools (ADR 0036), and that injection in the provider's egress proxy, TLS interception included, is a narrow opt-in for scoped, revocable or short-lived, low-value tokens, enforced by documentation and review; ADR 0020's no-interception rule stays for our local proxy, and Cloudflare's N46b and N50 wait on a separate ruling | ✅ | The owner's decision of 2026-11-25, which ADR 0060 records in its own pull request (#424) |
