# Fact-check: the OpenAI Agents SDK subagent example

This log checks the claims that `verify/openai-agents-sdk/examples/12-subagent-as-tool.ts`, its header comment and its README section make on 2026-11-22 (todo T42), against the pinned `@openai/agents` 0.21.0 (`@openai/agents-core` 0.21.0), the mirrored docs at tag `v0.21.0` and the run itself.

Legend: ✅ confirmed · ✏️ corrected while drafting · ⚠️ unverified or our own inference.

| # | Claim | Verdict | Source and reason |
| --- | --- | --- | --- |
| T42-1 | `agent.asTool()` turns an agent into a tool that other agents call, and the calling agent keeps the conversation | ✅ | `@openai/agents-core` `dist/agent.d.ts` lines 393–405: "Transform this agent into a tool, callable by other agents", and "the new agent is called as a tool, and the conversation is continued by the original agent" |
| T42-2 | The subagent reads its sources in a nested run of its own | ✅ | `guides/tools.mdx` §4: "the Agents SDK creates a `Runner` and uses that runner to execute the agent within the function-tool call"; `dist/agent.mjs` lines 305 and 350–357 build `new Runner(nestedRunConfig)` and call `runner.run(this, runInput, …)` |
| T42-3 | The default agent tool takes one `input` string, which the orchestrator's scripted call passes | ✅ | `dist/agentToolInput.d.ts` declares `AgentAsToolInputSchema` as `z.ZodObject<{ input: z.ZodString }>`, and `dist/agent.d.ts` says `parameters` "Defaults to `{ input: string }`"; the transcript shows the call `research({ input: "How did tool-call logging change?" })` |
| T42-4 | `customOutputExtractor` receives the subagent's completed run and returns the text the orchestrator receives as the tool output | ✅ | `dist/agent.d.ts` line 54 types it as `(output: CompletedAgentToolInvocationRunResult) => string \| Promise<string>`; the first check finds the summary in the orchestrator's second request, and the transcript records it as the `research` tool result |
| T42-5 | The subagent's tool calls and the source text stay in its run: the orchestrator's transcript holds only the summary | ✅ | The example's second check searches the orchestrator's last request for `read_source` and both source texts and finds neither; its third check finds both texts in the subagent's last request; the transcript shows the same split between `model-1` and `model-2` |
| T42-6 | Each run's model responses report that run's own tokens | ✅ | `dist/result.d.ts` documents `rawResponses` as "The raw LLM responses generated by the model during the agent run", and `dist/model.d.ts` gives each `ModelResponse` a `usage: Usage`; the check finds 800 tokens in the orchestrator's responses and 2400 in the subagent's, the scripted sums |
| T42-7 | The orchestrator's run usage adds the subagent's tokens to its own | ✅ | `guides/results.mdx` "Usage": "Token usage is aggregated in `result.state.usage`"; `dist/agent.mjs` line 306 hands the nested runner the tool's usage recorder (`setRunnerParentUsageRecorder`), and `dist/run.mjs` line 604 passes each nested usage to it; the check finds 3200 = 800 + 2400 |
| T42-8 | The nested run shares the orchestrator's run context, so the subagent's `state.usage` holds the shared running total rather than its own count | ✅ | `guides/context.mdx`: "derived contexts share the same underlying app context, approvals, and usage tracking. Nested `agent.asTool()` runs may attach a different `toolInput`"; `dist/runState.mjs` line 1664 returns `this._context.usage` from `get usage()`; the check reads 2740 at the extractor, the orchestrator's first call (340) plus the subagent's 2400 |
| T42-9 | The token counts are scripted: a `ScriptedModel` step built with `modelResponse()` returns the `Usage` the script gives it | ✅ | `dist/testing/scriptedModel.d.ts` declares `modelResponse(response: ScriptedModelResponse)`, where `ScriptedModelResponse` is a full `ModelResponse`; `dist/usage.mjs` lines 104–111 set `totalTokens` to input plus output when the script omits it; the transcript records each response's scripted `usage` |
| T42-10 | Both models are offered only the two function tools, so no mock model can call a tool that touches the host | ✅ | The example's fourth check reads every recorded request's `tools` from `ScriptedModel.calls` and requires `type === "function"` and a name of `research` or `read_source`; `read_source` returns strings from an in-memory map |
