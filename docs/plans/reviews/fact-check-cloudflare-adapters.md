# Fact-check: the Cloudflare state adapters

This log checks the claims that `packages/harness/src/cloudflare/`, the harness README's Cloudflare section, `packages/harness/docs/cloudflare-live-run.md` and todo N46a's outcome make on 2026-11-25. The sources are the Cloudflare developer docs as fetched on 2026-11-25 (each page's `index.md` form), the pinned `@cloudflare/workers-types` 5.20261103.1 and `miniflare` 5.20261103.0-beta in `node_modules`, and the offline tests in `packages/harness/test/cloudflare/`, which run in workerd through Miniflare.

Legend: ✅ confirmed · ✏️ corrected while drafting · ⚠️ unverified or our own inference.

| # | Claim | Verdict | Source and reason |
| --- | --- | --- | --- |
| N46a-1 | SQL calls in a Durable Object complete synchronously, and `transactionSync(callback)` rolls back every statement the callback ran when it throws | ✅ | [SQLite storage API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/): "`transactionSync(callback)` … If `callback()` throws an exception, the transaction will be rolled back … SQL queries using `ctx.storage.sql.exec()`, which complete synchronously"; `transactionSync<T>(closure: () => T): T` in workers-types `index.d.ts` |
| N46a-2 | A Durable Object is single-threaded, and a synchronous SQLite call doesn't yield to another request | ✅ | [Durable Object state](https://developers.cloudflare.com/durable-objects/api/state/): "SQLite storage operations are synchronous and do not yield the event loop, so they execute atomically"; the docs search result for "single-threaded" quotes "Durable Objects are single-threaded and cooperatively multi-tasked" |
| N46a-3 | Under 16 concurrent requests to one object, one `doLock()` acquire wins and 15 get `would_block`, and one of 16 appends that expect the same tail is written while 15 get a `ConflictError` | ✅ | `cloudflare.test.ts`, "concurrent requests to one Durable Object": each request awaits a timer before it acts, so the requests interleave in workerd |
| N46a-4 | A SQLite string, BLOB or row holds at most 8 MB, so the store's 1 MiB cap on `maxEntryBytes` fits a row | ✏️ | [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/): "Maximum string, `BLOB` or table row size: 8 MB". The first draft of a code comment said 2 MB; it now says 8 MB |
| N46a-5 | An object has one alarm: `setAlarm()` replaces the one already set, and `getAlarm()` returns `null` inside `alarm()` unless `setAlarm()` was called since it started | ✅ | [Alarms](https://developers.cloudflare.com/durable-objects/api/alarms/), Storage methods |
| N46a-6 | Alarms run at least once, and a throwing `alarm()` is retried with exponential backoff from 2 s, up to 6 times; Cloudflare recommends catching errors and setting a new alarm | ✅ | [Alarms](https://developers.cloudflare.com/durable-objects/api/alarms/), "Background" and "Catching exceptions in alarm handlers". This is why `doAlarmScheduler().alarm()` never throws for a handler and keeps the failed wake for `retryMs` |
| N46a-7 | An alarm handler runs for at most 15 minutes of wall time | ✅ | [Workers limits](https://developers.cloudflare.com/workers/platform/limits/): "Durable Object alarm handlers: 15 minutes … maximum wall time … per invocation". The same page says bundled-plan Workers have no such limit; the README states the 15 minutes as the bound to design for |
| N46a-8 | A wake set on workerd's real alarm arrives through the object's `alarm()` at or after its time, carrying the time it asked for, and a wake whose handler throws is delivered again after `retryMs` | ✅ | `cloudflare.test.ts`, "the alarm scheduler on workerd's real alarm", in Miniflare with real time |
| N46a-9 | With the Hibernation API, an idle object can be evicted while its clients stay connected, its constructor runs again on the next event, and its in-memory state is reset | ✅ | [DO WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/), "How hibernation works" |
| N46a-10 | A socket's attachment holds a structured-clone value of at most 16,384 bytes that survives hibernation until either side closes the socket | ✅ | [DO WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/), `serializeAttachment`: "Maximum serialized size is 16,384 bytes"; `serializeAttachment(attachment: any): void` in workers-types. The bridge keeps at most 8 sessions of strings up to 512 characters, and `hibernation.test.ts` checks the attachment stays under half the limit |
| N46a-11 | A timer, an alarm or an incoming request keeps an object out of hibernation | ✅ | [DO WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/): "Events such as alarms, incoming requests, and scheduled callbacks prevent hibernation. This includes `setTimeout`". So a running turn, a lock's renewal timer and the transport's backpressure poll all keep the object in memory |
| N46a-12 | An idle object that only holds hibernatable sockets hibernates after about 10 seconds | ✅ | [DO lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/): "Currently, it is after 10 seconds of inactivity". The live run waits 90 s to leave room, and prints whether the object was rebuilt rather than assume it |
| N46a-13 | Miniflare delivers hibernatable socket events but never evicts an object, so the offline test stands in for eviction by dropping the object's server from memory | ✅ | [DO WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/), local development note: events "are still delivered. However, the Durable Object is never evicted from memory" |
| N46a-14 | After the object's server is dropped, a turn on the same socket is accepted and settles, and without the attachment the same frame is refused, so the replay is what carries the connection | ✅ | `cloudflare.test.ts` (a real socket in workerd) and `hibernation.test.ts` (the attachment cleared) |
| N46a-15 | A peer's close frame should be answered with `close()` in `webSocketClose()`, and a 1006 close has no frame to answer | ✅ | [DO WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/), Hibernation WebSocket API. The bridge repeats 1000 and 3000–4999 and closes with no code otherwise; which other codes workerd accepts in `close()` is not checked here |
| N46a-16 | A Secrets Store binding's `get()` resolves with the secret's text | ✅ | `interface SecretsStoreSecret { get(): Promise<string> }` in workers-types; [Secrets Store with Workers](https://developers.cloudflare.com/secrets-store/integrations/workers/) shows `await env.<BINDING>.get()`; the smoke test reads a ring through Miniflare's Secrets Store binding |
| N46a-17 | `wrangler secret put <KEY>` sets a Worker secret and deploys a new version, and `wrangler secrets-store secret update` changes a Secrets Store secret | ✅ | [Worker secrets](https://developers.cloudflare.com/workers/configuration/secrets/) and [Wrangler Workers commands](https://developers.cloudflare.com/workers/wrangler/commands/workers/), `secret put`; [Wrangler Secrets Store commands](https://developers.cloudflare.com/workers/wrangler/commands/secrets-store/), `secrets-store secret update` |
| N46a-18 | `workerKeyStore()` keeps no key text where `JSON.stringify()` or an error can show it | ✅ | `cloudflare.test.ts`, "workerKeyStore keeps the ring's text out of what it shows": the store stringifies to `{}`, and a failed load's message, cause and stack hold no part of the key |
| N46a-19 | pi-schema and `@cfworker/json-schema` both validate a schema in workerd, where `new Function` is refused, and the harness's MCP client lists and calls a tool there | ✅ | `cloudflare.test.ts`, "the workerd smoke test" |
| N46a-20 | SQLite-backed Durable Objects run on the Workers Free plan | ✅ | [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/): "Workers Free plan: Only Durable Objects with SQLite storage backend are available" |
| N46a-21 | `wrangler secret put <KEY>` reads the value from standard input when it is piped, so the live run never puts the ring or the token on a command line | ✅ | [Wrangler Workers commands](https://developers.cloudflare.com/workers/wrangler/commands/workers/), `secret` section: "The put command can also receive piped input", with an `echo … \| wrangler secret put PRIVATE_KEY` example (found through the docs site's search on 2026-11-25) |
| N46a-24 | `wrangler delete --name <name>` takes its confirmation from standard input, so the live run answers `y` there | ⚠️ | The `delete` section lists `--name`, `--env` and `--dry-run` and says nothing of a prompt or of a flag that skips one; the docs search found a `--force` only for Flagship's delete. The bridge now keeps only the experimental opt-ins and bounds a session id to 128 UTF-16 units; `hibernation.test.ts` serializes the largest state the bounds allow, in two-byte strings, with Node's `v8.serialize()` and finds it under 16,384 bytes. No Cloudflare claim is involved |
