# 0059. Make the manual installable and readable offline with a per-build service worker

- **Status:** Accepted (owner, 2026-11-23, on [issue #175](https://github.com/laudebugs/buildanagent/issues/175))
- **Date:** 2026-11-23
- **Plan:** [Book plan §1](../plans/build-book.md#1-goal-and-non-goals) (the reversed non-goal); todos [T67a](../todos/done/T67a-manual-offline-pwa.md) and [T67b](../todos/done/T67b-manual-save-for-offline.md)
- **Addendum:** 2026-11-23, T67b: the message protocol in its final form and the partial-save rule ([Saving the whole book](#saving-the-whole-book-addendum-2026-11-23))

## Context

The book plan kept an offline service worker out of scope, because the owner's garment book needed its own build script and offline test for one. [The research report on offline reading](../research/book/offline-reading-and-caching.md) found that the deployed Worker revalidates every file but the hashed ones under `/_astro/` before each reuse, so a chapter fails to load when that check fails. The report offered three options, and on 2026-11-23 the owner chose the third: a reader should be able to install the manual and open it with no connection. That choice reverses the non-goal, and this record sets out how the worker stays safe on a public site and correct across deploys.

## Decision

The manual gets a web app manifest, icons drawn from the favicon, an offline page and a service worker at `/sw.js` that stores only the files of the build it came with.

- **One cache per build, checked byte for byte.** After Pagefind, `scripts/offline-build.mjs` lists every file of `dist/` with its size and SHA-256 in `/offline-manifest.json`, and leaves out `_headers`, `sw.js`, the list itself and `404.html`. It bundles `src/offline/sw.ts` with esbuild into one classic script, `/sw.js`, with the list and the build's id stamped above it. The id is the first 16 hex digits of a hash over a format version, the bundled worker's code, the files and the shell, so a deploy that changes only the worker also gets a new id. The worker names its cache `manual-<id>`. It stores a response only when the request is a same-origin GET for a listed path. The response must be a 200 of type `basic`, not redirected, with no `Set-Cookie`, no `Vary: *`, no `no-store` or `private`, and the listed size and hash.

  This build's cache holds only this build's exact files, plus pages a CDN rewrote that carry this build's mark. The list records each page as it is before the build stamps it, with the placeholder `__MANUAL_BUILD__` in its build mark. The id and the placeholder are both 16 characters, so a stamped page keeps the listed size. Before the worker compares a page with the list, it sets the page's mark back to the placeholder, so a page from any build passes exactly when everything but its mark equals this build's page. The worker then stores it with this build's mark written in. A page carried over from an older build, or counted as this build's for the rule on assets, therefore links only this build's files.

  A cache key is the origin and the path, decoded segment by segment with doubled slashes collapsed. A query string or fragment never selects another entry, and an encoded dot segment, slash or control character maps to no entry. Every deploy changes the worker's bytes, so a browser installs each one as an update.
- **Pages a CDN rewrote stay usable, and visible.** Every page carries `<meta name="manual-build">`, which the build step stamps with the id. A page whose bytes differ from the list is stored only while it still carries this build's mark and has grown by no more than 64 KiB. STATUS then reports it under `rewritten`. A script, stylesheet or other file must match its hash exactly. Every file the worker fails to save while installing, or when a page asks it to, is recorded in its cache, and STATUS reports it under `failed` with the reason. A page from another build is not a failure. `scripts/offline-verify-deployed.mjs` checks a deployed copy against its own list, so the owner can confirm after a deploy that no zone feature rewrites the book.
- **The shell on install, the rest on request.** The worker saves the home page, the offline page and the search page with every stylesheet, script, font, icon and manifest they link. The shell also holds every Pagefind file a search needs: its module, web worker, WebAssembly, entry and meta files, and its index chunks and fragments. It comes to 56 files and 1.62 MB in the build of 2026-11-23, of which Pagefind is about 1.07 MB, so a search never run online still works offline. Install fails, and the old worker keeps serving, if any shell file is missing or is not this build's. The page a reader lands on loads before the worker controls it, so `offline.js` then asks the worker to save it and the files it loaded (`SAVE_PAGE`). Pages a reader opens later are saved as they arrive when their bytes match. Saving the whole book is the reader's choice through T67b's control. A first visit should not spend about 5 MB of a reader's data (as of 2026-11-23) unasked.
- **Pages network-first, assets from the same build.** A page comes from the network unless the network fails or takes more than 3 seconds. Then the saved copy shows, or the offline page for a page that is not saved. A slow network with nothing saved is waited for. Offline, a page asked for without its trailing slash gets a 307 to it, as Cloudflare's default `html_handling` gives online. Hashed files (`/_astro/`, Pagefind's index and fragments) come from the cache first. For a page that came from the cache or matched the list, every other asset also comes from the cache first. On a miss, that page gets the network's copy only if it is this build's file, and otherwise the request fails. The worker records such pages in its cache, so the rule holds after the browser restarts the worker. Any other page gets its assets from the network first.
- **Why not stale-while-revalidate, and what Pagefind's worker does.** Stale-while-revalidate for unhashed assets, the first design, would serve an old build's script under a new build's page, so the worker does not use it. Pagefind's own web worker is a separate client that the worker cannot tie to its page. The files it loads therefore come from the network first and from the cache offline; its index files are named by content, and its WebAssembly changes only when a deploy changes Pagefind's version.
- **Updates wait for the reader.** The worker never calls `skipWaiting()` by itself. A new build's worker installs, carries over every saved file whose content is unchanged, a page apart from its build mark, and waits. `public/scripts/offline.js` then shows "A new version of the manual is ready" with Reload and Not now. Reload sends `{ type: "SKIP_WAITING" }` to whichever worker is waiting when the reader presses it, and the page reloads only after the new worker takes control. Another open tab keeps its page and shows "The manual was updated in another tab" with the same Reload. A worker that fails to install sets `data-offline="install-failed"` on the page for T67b's control.
- **An older build's cache stays while a page it served is open.** The new worker deletes older `manual-` caches when it activates, never before, and keeps an older build's cache while a page that cache served is still open (`clients.matchAll()`). That page, which another tab's Reload left on the old build, gets its own build's files from that cache, because the deploy removed them from the server. The worker records those pages in its cache, and it deletes such a kept cache, and no other, once none of its pages is open: on the next page request, the next STATUS message or the next activation. Between activations it deletes only a cache it kept. No worker ever deletes a cache whose own worker is installing or waiting. A worker marks its cache as pending when it starts to install and clears the mark when it activates. That covers a deploy that brings back an older build, whose id and cache name are the same as the kept cache's. A pending mark older than a day comes from a worker that never activated, and it no longer protects the cache.
- **Production host only.** The layout writes the hosts that may register the worker into `<meta name="manual-offline-hosts">`, from the Astro config's `site`. Any other host, a preview at `pr-<n>.manual.buildanagent.fyi` included, registers nothing and removes a worker and `manual-` caches that an earlier visit left. A build may add one host through `MANUAL_OFFLINE_TEST_HOST`, which accepts only `127.0.0.1` or `localhost`, so the browser check can run on loopback and no setting can add a host that serves readers.
- **Headers.** `_headers` adds `manifest-src 'self'` to the policy, because `default-src 'none'` would block the manifest. It sends `/sw.js` and `/offline-manifest.json` with `Cache-Control: no-cache`, and the manifest as `application/manifest+json`. The worker sits at the root, so it needs no `Service-Worker-Allowed` header. The policy's `worker-src 'self'` already covers it, and every script stays a same-origin file.

The page and the worker speak a small message protocol. A reply goes to the message's `MessagePort` when the page sends one, and otherwise to the sending page. The worker answers only a message whose origin is its own and whose sender is a tab or window of that origin (a `window` client whose `frameType` is `top-level` or `auxiliary`), so a frame or a worker is ignored. The book's policy already sends `frame-ancestors 'none'`, so the frame check is a second guard. The table gives the protocol in its final form, after T67b:

| Message | Sent by | Reply |
| --- | --- | --- |
| `{ type: "STATUS" }` | any page | `{ type: "STATUS", build, total: { files, bytes }, stored: { files, bytes }, shell: { files, saved }, saved: { at, build, files, bytes } \| null, partial: { at } \| null, previous: { at, build } \| null, saving: { done, total, bytes, failed } \| null, rewritten: [path], failed: [{ path, reason }] }` |
| `{ type: "SKIP_WAITING" }` | the update notice's Reload | none; the waiting worker activates and the page reloads on `controllerchange` |
| `{ type: "SAVE_PAGE", paths: [path] }` | a page the worker did not control when it loaded | `{ type: "SAVED", saved: [path], failed: [{ path, reason }] }`; at most 100 paths, listed same-origin ones only |
| `{ type: "SAVE_ALL" }` | the save control | `{ type: "SAVE_PROGRESS", done, total, bytes, failed }` after each file, then `{ type: "SAVE_DONE", result, reason?, saved, failed: [{ path, reason }] }`, where `result` is `saved`, `partial`, `cancelled` or `refused` (`not-active` or `busy`) |
| `{ type: "CANCEL_SAVE" }` | the save control | none; the running `SAVE_ALL` answers with `cancelled` |
| `{ type: "REMOVE_ALL" }` | the save control | `{ type: "REMOVED", removed }` |

A failure's reason is `different-bytes`, `no-build-mark`, `not-storable`, `network`, `quota` or `storage`, and `SAVE_DONE` may also give `other-build` for a file a newer deploy replaced. The worker ignores any other message.

## Saving the whole book (addendum, 2026-11-23)

T67b added the reader's control, in the footer of every page, and the worker's side of `SAVE_ALL`, `CANCEL_SAVE` and `REMOVE_ALL`. Four rules keep a saved copy honest.

- **A saved copy is complete or it is partial.** `SAVE_ALL` writes a saved record, `{ at, build, complete }`, into the build's own cache. It writes `complete: false` when it starts and `complete: true` only once the cache holds every listed file. STATUS reports `saved` only while the record is complete and every listed file is still there, and `partial` otherwise. A full quota stops the save at once, because every later write would fail too. A dropped connection, a file from a newer deploy or `CANCEL_SAVE` also leaves the copy partial, and the control offers Try again. The next `SAVE_ALL` skips the files already stored, so a save survives the browser stopping the worker. The date lives beside the files, so a browser that evicts the cache evicts the record with it, and the control shows "Not saved".
- **The page names no URL.** `SAVE_ALL` takes no paths. It downloads the build's own list, six files at a time, and checks each file by the store rules above. A reader therefore cannot make the worker fetch anything the build did not write. A second `SAVE_ALL` while one runs joins it, so two tabs never download the book twice.
- **Only the active worker saves or removes.** A worker is active once it has activated, which it records by clearing its pending mark. A waiting worker answers `SAVE_ALL` with `refused` and `not-active`, so an update never downloads the next build before the reader presses Reload. After the Reload, STATUS reports the older build's complete copy under `previous`, which install carried over. The control then offers "Update the saved copy", and the save downloads only the changed files. An old worker that finds its cache deleted by a newer activation stops and writes no record, so it never brings the cache back.
- **Removing keeps the book usable.** `REMOVE_ALL` stops a running save, keeps the shell, so the book still opens, and deletes every other listed file, the saved record and the problems of the deleted files. It also deletes the older caches that activate kept. Pages the reader opens afterwards are saved as they arrive, as before.

The control does not call `navigator.storage.persist()`. Firefox answers that call with a permission prompt, and Safari grants it mainly to Home Screen web apps, so the call would add a prompt for little gain ([MDN, storage quotas and eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria); [WebKit, updates to storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/)). Instead, the control tells the reader that a browser may still clear the copy, and that Safari may clear it after seven days of Safari use without a visit to the manual.

While building T67b, a gap in T67a came to light. A page an older worker stamped with its own mark is a response the worker built, of type `default`, which the store rules refused. A saved page therefore carried over through one update but not two. A copy read back from the worker's own cache may now be of type `default`. Its bytes are still checked against the list.

## What can rewrite the book on its way

As of November 2026, Cloudflare documents several zone features that change HTML on its way to the reader. Email Address Obfuscation is on by default for a new zone, and it replaces addresses with links and adds a decoding script. Web Analytics' automatic setup, on by default for proxied sites that use it, injects a beacon script. Rocket Loader defers every script and, like Email Address Obfuscation, uses non-standard tags. Auto Minify was deprecated on 2024-08-05. Cloudflare's docs do not say whether these features rewrite responses that an assets-only Worker serves. Email Address Obfuscation leaves out HTML that Worker code adds, and both it and the analytics beacon skip a response marked `Cache-Control: no-transform`. The book's chapters hold example addresses such as `bob@example.com`, so obfuscation would change those pages. The worker therefore accepts a rewritten page that keeps its build mark and reports it, and it refuses any other changed file. After the first deploy, the owner runs `pnpm --filter @buildanagent/manual offline:verify https://manual.buildanagent.fyi`. If it reports rewritten pages, the owner turns the feature off for the host with a Configuration Rule, or adds `no-transform` in a later change.

## Consequences

- **Cost.** The build gains a step, and `esbuild` 0.28.2, already in the lockfile through `packages/agent-safety`, becomes a dependency of the manual. Tests cover the worker's rules, the registration script, the icons and manifest, a fixture build through the offline step and the post-deploy check. `scripts/offline-browser-check.mjs` drives the worker in Chromium offline. It is not part of `pnpm test`, because it needs a browser.
- **Stale caches.** A reader who never presses Reload keeps reading the old build until every tab of the book closes, which is how a waiting worker behaves. A saved page that a deploy changed is gone from the new cache until the reader opens it again or saves the book in T67b.
- **Storage.** Browsers may evict a site's storage under pressure, and Safari may evict it after a period without use, so an offline copy is a convenience, not an archive. The save control tells the reader so, and shows "Not saved" once a copy is gone.
- **Changing the icons.** An edit to `public/favicon.svg` fails the icon test until `pnpm --filter @buildanagent/manual icons` draws the icons again.
- **Rollback.** To withdraw the feature, ship a `/sw.js` that deletes every `manual-` cache and unregisters itself on activate, and remove the registration from the layout. Browsers check `/sw.js` for updates on every navigation to the book, so returning readers pick it up on their next visit. Deleting `/sw.js` alone is not enough, because a browser keeps an installed worker when its update check fails.
